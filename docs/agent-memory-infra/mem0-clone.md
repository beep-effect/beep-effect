# Architecture & storage

Mem0's current OSS core is a memory engine around four concrete components: an embedder, vector store, LLM, and SQLite history manager; optional reranking is initialized separately, and the entity store is a lazily-created second vector-store collection rather than the removed graph-store API (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:444-537`). The TypeScript OSS implementation mirrors that structure with configurable embedder, vector store, LLM, history store, and lazy entity store (`/home/elpresidank/YeeBois/dev/mem0/mem0-ts/src/oss/src/memory/index.ts:172-282`, `/home/elpresidank/YeeBois/dev/mem0/mem0-ts/src/oss/src/config/defaults.ts:3-34`, `/home/elpresidank/YeeBois/dev/mem0/mem0-ts/src/oss/src/types/index.ts:63-103`).

The V3 extraction pipeline is ADD-only for automatic ingestion. Python `add()` gathers recent SQLite messages, retrieves related existing memories, maps real UUIDs to integers to reduce LLM ID hallucination, asks the LLM for additive facts, deduplicates by hash, embeds batches, inserts vector payloads, writes ADD history, and then links extracted entities to a sidecar entity collection (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:868-1158`). TypeScript follows the same shape but returns an empty result on LLM extraction failure where the Python implementation raises `LLMError` (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:907-921`, `/home/elpresidank/YeeBois/dev/mem0/mem0-ts/src/oss/src/memory/index.ts:804-858`).

Legacy ADD/UPDATE/DELETE/NONE prompting still exists in `prompts.py`, but the migration guide says V3 `add` returns ADD only, custom update prompts are deprecated, and graph memory configuration was removed from both Python and TypeScript OSS APIs (`/home/elpresidank/YeeBois/dev/mem0/mem0/configs/prompts.py:176-324`, `/home/elpresidank/YeeBois/dev/mem0/mem0/configs/prompts.py:406-460`, `/home/elpresidank/YeeBois/dev/mem0/docs/migration/oss-v2-to-v3.mdx:14-42`, `/home/elpresidank/YeeBois/dev/mem0/docs/migration/oss-v2-to-v3.mdx:44-75`, `/home/elpresidank/YeeBois/dev/mem0/docs/migration/oss-v2-to-v3.mdx:118-159`). UPDATE and DELETE are explicit API operations, not current automatic LLM-selected mutation operations (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1767-1827`, `/home/elpresidank/YeeBois/dev/mem0/mem0-ts/src/oss/src/memory/index.ts:1566-1593`).

Vector backend support is broad. Python's vector-store factory includes Qdrant, Chroma, pgvector, Milvus, Pinecone, Redis, Weaviate, Elasticsearch, Supabase, FAISS, OpenSearch, S3 vectors, Cassandra, Neptune Analytics, Turbopuffer, and others; TypeScript's factory includes in-memory, Qdrant, Chroma, Redis, Supabase, Vectorize, Azure AI Search, pgvector, Elasticsearch, OpenSearch, Pinecone, S3 vectors, Turbopuffer, Milvus, MongoDB, and Weaviate (`/home/elpresidank/YeeBois/dev/mem0/mem0/utils/factory.py:178-215`, `/home/elpresidank/YeeBois/dev/mem0/mem0-ts/src/oss/src/utils/factory.ts:135-186`). The vector-store base API requires insert/search/list/get/update/delete/reset and offers optional `keyword_search` and `search_batch` hooks (`/home/elpresidank/YeeBois/dev/mem0/mem0/vector_stores/base.py:4-100`).

Postgres/pgvector is real, not just documentation. The Python pgvector adapter creates the `vector` extension, stores rows with `id`, vector, and JSONB payload, builds vector and full-text indexes, supports dense vector search, and implements PostgreSQL full-text `keyword_search`; the config supports connection strings, pools, HNSW, and DiskANN flags (`/home/elpresidank/YeeBois/dev/mem0/mem0/configs/vector_stores/pgvector.py:6-40`, `/home/elpresidank/YeeBois/dev/mem0/mem0/vector_stores/pgvector.py:142-210`, `/home/elpresidank/YeeBois/dev/mem0/mem0/vector_stores/pgvector.py:258-399`). The self-host server uses pgvector by default and the Docker stack runs `pgvector/pgvector:pg17` (`/home/elpresidank/YeeBois/dev/mem0/server/main.py:119-138`, `/home/elpresidank/YeeBois/dev/mem0/server/docker-compose.yaml:32-50`).

Graph memory should be treated as entity-linked retrieval, not a typed knowledge graph. The OSS migration removes `enable_graph`/`graph_store`; platform graph memory says there is no external graph DB, that it has entity nodes, memory nodes, and schema-free connections, and that it affects ranking rather than response shape (`/home/elpresidank/YeeBois/dev/mem0/docs/migration/oss-v2-to-v3.mdx:28-58`, `/home/elpresidank/YeeBois/dev/mem0/docs/platform/features/graph-memory.mdx:6-8`, `/home/elpresidank/YeeBois/dev/mem0/docs/platform/features/graph-memory.mdx:27-55`, `/home/elpresidank/YeeBois/dev/mem0/docs/platform/features/graph-memory.mdx:88-94`). The Python `entity_store` is implemented as a second vector-store collection with `linked_memory_ids`, not as an external graph database (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:516-537`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1039-1142`).

# Retrieval

The retrieval model is hybrid recall over scoped memory. OSS `search()` requires filters containing at least one of `user_id`, `agent_id`, or `run_id`; it rejects top-level entity parameters, supports advanced filters, optional reranking, expiry visibility, and `explain`, but explicitly rejects OSS `reference_date` temporal search (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1331-1474`). The server exposes this as `POST /search`, accepts deprecated top-level IDs by moving them into filters, and forwards `top_k`, `threshold`, `explain`, and `show_expired` into core search (`/home/elpresidank/YeeBois/dev/mem0/server/main.py:451-483`).

The scoring pipeline combines semantic vector results, optional backend keyword/BM25 results, and entity boosts. Python lemmatizes queries, extracts query entities, embeds the query, performs over-fetched semantic search, runs optional `keyword_search`, normalizes scores, applies entity-linked boosts, ranks results, and can include score details in output (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:500-507`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1580-1683`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1685-1765`). Qdrant stores both dense vectors and optional BM25 sparse vectors, while pgvector implements full-text keyword search through PostgreSQL (`/home/elpresidank/YeeBois/dev/mem0/mem0/vector_stores/qdrant.py:93-164`, `/home/elpresidank/YeeBois/dev/mem0/mem0/vector_stores/qdrant.py:186-240`, `/home/elpresidank/YeeBois/dev/mem0/mem0/vector_stores/pgvector.py:365-399`).

The public docs describe the same conceptual retrieval signals: semantic, keyword, entity, and temporal, with a warning that OSS behavior depends on configured vector store, reranker, and graph/entity support (`/home/elpresidank/YeeBois/dev/mem0/docs/core-concepts/how-it-works.mdx:55-64`). Current code evidence supports semantic + keyword + entity-linked recall in OSS; temporal reasoning is mostly prompt-time normalization and metadata filtering rather than a bi-temporal query engine (`/home/elpresidank/YeeBois/dev/mem0/mem0/configs/prompts.py:524-535`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1331-1474`).

# Provenance/temporal/lifecycle

Mem0 records memory history, but that is not the same as the product's claim/evidence/provenance authority. SQLite history stores `memory_id`, old/new memory values, event, created/updated timestamps, deletion flag, actor id, and role; vector payloads hold text, hash, created/updated timestamps, attribution, metadata, and optional expiration fields (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/storage.py:102-120`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/storage.py:150-255`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:943-991`). The product doctrine requires stable evidence source-span IDs, acceptance promotion, and durable truth as claim + evidence + provenance, which Mem0 core does not model in the cited storage structures (`/home/elpresidank/YeeBois/projects/beep-effect5/goals/agentic-professional-runtime/README.md:84-106`, `/home/elpresidank/YeeBois/projects/beep-effect5/standards/memory-architecture/01-memory-layer-taxonomy.md:7-25`).

Temporal support is useful but not authoritative. The extraction prompt tells the LLM to use an observation date to convert relative time to absolute references, payloads include `created_at`/`updated_at`, and `expiration_date` is accepted by add/update/server request models; however, OSS `add()` rejects `timestamp` and OSS `search()` rejects `reference_date` (`/home/elpresidank/YeeBois/dev/mem0/mem0/configs/prompts.py:524-535`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:717-829`, `/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1331-1474`, `/home/elpresidank/YeeBois/dev/mem0/server/main.py:179-207`, `/home/elpresidank/YeeBois/dev/mem0/server/main.py:486-498`). That is materially weaker than the repo taxonomy's requirement to route by certainty and keep semantic layers subordinate to deterministic source records (`/home/elpresidank/YeeBois/projects/beep-effect5/standards/memory-architecture/01-memory-layer-taxonomy.md:111-141`).

Lifecycle support is split across core memory mutation and app wrappers. Core supports explicit create/update/delete/reset/history operations and writes ADD/UPDATE/DELETE history records (`/home/elpresidank/YeeBois/dev/mem0/mem0/memory/main.py:1886-2052`). OpenMemory adds app-level `active`, `paused`, `archived`, and `deleted` states, status history, access-control rows, and memory access logs; the current self-host server adds request logs and API-key auth logs, but those are operational audit artifacts, not evidence-backed claim lifecycle records (`/home/elpresidank/YeeBois/dev/mem0/openmemory/api/app/models.py:30-35`, `/home/elpresidank/YeeBois/dev/mem0/openmemory/api/app/models.py:85-109`, `/home/elpresidank/YeeBois/dev/mem0/openmemory/api/app/models.py:161-188`, `/home/elpresidank/YeeBois/dev/mem0/server/models.py:30-52`, `/home/elpresidank/YeeBois/dev/mem0/server/main.py:270-319`).
