## TL;DR

Graphiti should stay in the **LEARN / donor** bucket for the product runtime, not become the agentic-professional-runtime memory foundation: this repo requires deterministic, evidence-backed, provenance-tracked authority, while Graphiti is an LLM/embedding-built temporal context graph best treated as a managed cache or projection (`standards/memory-architecture/README.md:18-24`, `standards/memory-architecture/05-context-graph-capability-assessment.md:6-14`, `goals/agentic-professional-runtime/README.md:65-105`, `upstream/graphiti/README.md:42-49`).

The most valuable Graphiti primitives to port are its `EntityEdge` temporal contract (`created_at`, `valid_at`, `invalid_at`, `expired_at`, `reference_time`, episode UUID lineage), `EpisodicNode` raw-source/provenance node, and the contradiction -> invalidation flow in `edge_operations.py` (`upstream/graphiti/graphiti_core/edges.py:263-285`, `upstream/graphiti/graphiti_core/nodes.py:318-351`, `upstream/graphiti/graphiti_core/utils/maintenance/edge_operations.py:538-573`, `upstream/graphiti/graphiti_core/utils/maintenance/edge_operations.py:623-847`).

For dev-tooling memory, Graphiti is viable but operationally heavy: the repo currently names `graphiti-memory` as the primary durable repo knowledge base, and the upstream MCP server is real, featureful, and Dockerable, but it is explicitly experimental, defaults to FalkorDB + OpenAI, depends on graph DB / LLM / embedder operations, and has some stale tests alongside a current live FalkorDB test (`AGENTS.md:76-86`, `upstream/graphiti/mcp_server/README.md:10-29`, `upstream/graphiti/mcp_server/README.md:107-117`, `upstream/graphiti/mcp_server/tests/test_live_falkordb_int.py:1-23`, `upstream/graphiti/mcp_server/tests/test_http_integration.py:46-98`).

## Hard-gate verdicts

1. **Self-hostable/local-first: PASS WITH OPS CAVEATS.**
   Graphiti OSS is "self-hosted only" rather than managed SaaS, ships Docker Compose paths for Neo4j and FalkorDB, and has MCP and REST sidecars (`upstream/graphiti/README.md:102-118`, `upstream/graphiti/README.md:296-338`, `upstream/graphiti/docker-compose.yml:1-89`). The caveat is that a useful local deployment still needs Python 3.10+, a graph backend, embeddings, LLM structured output, and concurrency/rate-limit tuning (`upstream/graphiti/README.md:160-172`, `upstream/graphiti/mcp_server/README.md:339-379`, `upstream/graphiti/mcp_server/README.md:668-675`). Local LLMs are possible through OpenAI-compatible endpoints, but upstream warns that smaller/local models frequently fail the structured JSON schemas used for extraction and deduplication (`upstream/graphiti/README.md:542-616`, `upstream/graphiti/mcp_server/README.md:174-197`).

2. **OSI license without copyleft trap: PASS FOR GRAPHITI; FLAG BACKENDS.**
   Graphiti itself is Apache-2.0 in the clone LICENSE and package metadata (`upstream/graphiti/LICENSE:1-3`, `upstream/graphiti/LICENSE:66-128`, `upstream/graphiti/pyproject.toml:1-12`). The backend license decision is separate: this clone uses FalkorDB as an optional dependency and Docker image, including a combined MCP image built `FROM falkordb/falkordb:latest`, while prior repo synthesis flags FalkorDB as SSPLv1 and not OSI open source (`upstream/graphiti/pyproject.toml:31-35`, `upstream/graphiti/mcp_server/docker/Dockerfile:1-6`, `upstream/graphiti/mcp_server/docker/docker-compose-falkordb.yml:1-17`, `explorations/atlas-synthesis/synthesis/21-external-memory-kg-donors.md:343-348`, `explorations/atlas-synthesis/synthesis/21-external-memory-kg-donors.md:359-371`). I did not verify FalkorDB's license from a FalkorDB source in this lane; this finding is a repo-prior flag plus clone evidence that Graphiti deployments can embed or depend on FalkorDB.

3. **TS-native or clean HTTP/MCP API: PASS VIA PYTHON SIDECAR, NOT TS-NATIVE.**
   Graphiti OSS is Python-first and does not provide the managed Zep TypeScript SDK; the README says Zep has Python/TypeScript/Go SDKs while Graphiti requires users to build surrounding tools (`upstream/graphiti/README.md:102-112`, `upstream/graphiti/pyproject.toml:1-20`). The sidecar surfaces are clean enough for `drivers/*`: the FastAPI server exposes `/messages`, `/search`, `/episodes/{group_id}`, `/entity-edge/{uuid}`, delete, group-delete, clear, and healthcheck endpoints; the MCP server exposes HTTP and stdio transports plus typed memory/search/admin tools (`upstream/graphiti/server/graph_service/routers/ingest.py:51-111`, `upstream/graphiti/server/graph_service/routers/retrieve.py:17-56`, `upstream/graphiti/mcp_server/README.md:479-568`).

## Architecture & storage

Graphiti's public model is a temporal context graph with four primitives: entities, facts/relationships with temporal validity windows, episodes as the raw ground-truth stream, and custom Pydantic types (`upstream/graphiti/README.md:65-83`). In code, entities and episodes are graph nodes, facts are `EntityEdge` relationships, and edge/episode objects carry `group_id` partitioning, timestamps, embeddings, and optional typed attributes (`upstream/graphiti/graphiti_core/nodes.py:93-99`, `upstream/graphiti/graphiti_core/nodes.py:318-351`, `upstream/graphiti/graphiti_core/edges.py:49-55`, `upstream/graphiti/graphiti_core/edges.py:263-285`).

The storage model is graph-backend-centric, not Postgres-authority-centric. The core driver enum covers Neo4j, FalkorDB, Kuzu, and Neptune, and the README lists Neo4j 5.26, FalkorDB 1.1.2, Neptune + OpenSearch, and deprecated Kuzu as supported backends (`upstream/graphiti/graphiti_core/driver/driver.py:59-64`, `upstream/graphiti/README.md:160-168`). The Python package dependencies include Neo4j, OpenAI, PostHog, and optional FalkorDB/Kuzu/Neptune/OpenSearch extras; the files I read do not show a Postgres authority layer (`upstream/graphiti/pyproject.toml:13-41`).

Backend support is uneven enough to matter operationally. Neo4j has an async driver wrapper with index creation and real transaction handling, FalkorDB has its own Redis-style Cypher driver and index setup, Neptune requires AWS/OpenSearch plumbing, and Kuzu is marked deprecated both in README and driver warnings (`upstream/graphiti/graphiti_core/driver/neo4j_driver.py:151-216`, `upstream/graphiti/graphiti_core/driver/falkordb_driver.py:125-184`, `upstream/graphiti/graphiti_core/driver/neptune_driver.py:23-195`, `upstream/graphiti/README.md:212-217`, `upstream/graphiti/graphiti_core/driver/kuzu_driver.py:51-54`, `upstream/graphiti/graphiti_core/driver/kuzu_driver.py:137-151`).

The MCP server narrows backend choices to FalkorDB and Neo4j in config/CLI, defaults to FalkorDB, and ships Docker paths for either a combined FalkorDB+MCP container or separate Neo4j/FalkorDB containers (`upstream/graphiti/mcp_server/src/config/schema.py:176-205`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:1129-1133`, `upstream/graphiti/mcp_server/docker/docker-compose.yml:1-44`, `upstream/graphiti/mcp_server/docker/docker-compose-neo4j.yml:1-55`, `upstream/graphiti/mcp_server/docker/docker-compose-falkordb.yml:1-50`).

## Retrieval

Graphiti implements hybrid retrieval as a combination of edge/node/episode/community search methods, including cosine similarity, BM25/fulltext, and graph BFS; rerankers include reciprocal-rank fusion, maximal marginal relevance, graph distance, episode mentions, and cross-encoder reranking (`upstream/graphiti/README.md:120-136`, `upstream/graphiti/graphiti_core/search/search_config.py:32-78`, `upstream/graphiti/graphiti_core/search/search_config_recipes.py:33-153`).

The core `search_` path validates group IDs, generates an embedding when cosine/MMR search needs one, executes configured edge/node/episode/community searches concurrently, then reranks by the chosen recipe (`upstream/graphiti/graphiti_core/search/search.py:98-250`). Edge search specifically fans out over BM25, vector similarity, and BFS and can rerank through RRF, MMR, cross-encoder, node distance, or episode mentions (`upstream/graphiti/graphiti_core/search/search.py:253-460`).

Temporal retrieval is first-class in the filter model: `SearchFilters` can constrain `valid_at`, `invalid_at`, `created_at`, and `expired_at`, and the query constructor emits Cypher predicates against those edge fields (`upstream/graphiti/graphiti_core/search/search_filters.py:55-68`, `upstream/graphiti/graphiti_core/search/search_filters.py:149-209`, `upstream/graphiti/graphiti_core/search/search_filters.py:211-273`). MCP exposes this for facts through `valid_at_after`, `valid_at_before`, `invalid_at_after`, and `invalid_at_before`, which are parsed into `SearchFilters` before calling `client.search` (`upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:555-621`, `upstream/graphiti/mcp_server/src/utils/type_config.py:139-194`).

Backend retrieval has caveats. Kuzu stores edges through a `RelatesToNode_` workaround because it cannot fulltext edge properties, and search utilities note Kuzu limitations around fulltext variables for relevant-node search (`upstream/graphiti/graphiti_core/driver/kuzu_driver.py:51-54`, `upstream/graphiti/graphiti_core/search/search_utils.py:1253-1405`). Neptune search depends on OpenSearch/AOSS setup in the driver, while Neo4j and FalkorDB have backend-specific fulltext/vector/BFS operation classes (`upstream/graphiti/graphiti_core/driver/neptune_driver.py:62-195`, `upstream/graphiti/graphiti_core/driver/neo4j/operations/search_ops.py:76-395`, `upstream/graphiti/graphiti_core/driver/falkordb/operations/search_ops.py:135-430`).

## Provenance/bitemporal/lifecycle

The exact port candidates for temporal edge state are `graphiti_core/edges.py`, `graphiti_core/nodes.py`, `graphiti_core/graphiti.py`, `graphiti_core/prompts/extract_edges.py`, `graphiti_core/prompts/dedupe_edges.py`, `graphiti_core/utils/maintenance/edge_operations.py`, and `graphiti_core/models/edges/edge_db_queries.py` (`upstream/graphiti/graphiti_core/edges.py:263-285`, `upstream/graphiti/graphiti_core/nodes.py:318-351`, `upstream/graphiti/graphiti_core/graphiti.py:980-1223`, `upstream/graphiti/graphiti_core/prompts/extract_edges.py:25-78`, `upstream/graphiti/graphiti_core/prompts/dedupe_edges.py:24-102`, `upstream/graphiti/graphiti_core/utils/maintenance/edge_operations.py:538-847`, `upstream/graphiti/graphiti_core/models/edges/edge_db_queries.py:63-186`).

Graphiti's valid time is explicit: extracted edge schemas ask for `valid_at` and `invalid_at`, prompts tell the model to use episode/reference timestamps and avoid hallucinated bounds, and `EntityEdge` stores `valid_at` and `invalid_at` as when a fact became true or stopped being true (`upstream/graphiti/graphiti_core/prompts/extract_edges.py:40-47`, `upstream/graphiti/graphiti_core/prompts/extract_edges.py:160-175`, `upstream/graphiti/graphiti_core/edges.py:274-281`). Graphiti's transaction/system time is weaker than a product-grade event ledger: `created_at` records node/edge creation, episodes store `created_at` plus `valid_at`, and `expired_at` records system invalidation time, but this is not a Postgres event log with accepted claim lifecycle (`upstream/graphiti/graphiti_core/edges.py:271-281`, `upstream/graphiti/graphiti_core/nodes.py:341-351`, `upstream/graphiti/graphiti_core/graphiti.py:1067-1111`, `goals/agentic-professional-runtime/README.md:93-105`).

Episode provenance is concrete but not sufficient for the product authority model. `EpisodicNode` stores raw episode `content`, source metadata, `valid_at`, and the list of entity edge IDs, while `EntityEdge` stores the list of episode UUIDs that support the fact (`upstream/graphiti/graphiti_core/nodes.py:318-351`, `upstream/graphiti/graphiti_core/edges.py:263-285`). That gives fact-to-episode lineage; it does not by itself provide stable source span IDs, evidence records, human acceptance state, or policy lifecycle required by the product runtime (`goals/agentic-professional-runtime/README.md:93-105`, `standards/memory-architecture/05-context-graph-capability-assessment.md:47-55`).

Contradiction handling is LLM-assisted plus temporal invalidation. The dedupe prompt asks the LLM for duplicate and contradicted fact indices, `resolve_extracted_edge` maps those indices into invalidation candidates, and `resolve_edge_contradictions` uses temporal overlap to set old edge `invalid_at` to the new edge's `valid_at` and `expired_at` to `utc_now()` (`upstream/graphiti/graphiti_core/prompts/dedupe_edges.py:24-102`, `upstream/graphiti/graphiti_core/utils/maintenance/edge_operations.py:699-777`, `upstream/graphiti/graphiti_core/utils/maintenance/edge_operations.py:538-573`). The pattern worth porting is "supersede by validity window, preserve old fact"; the product should not port "LLM contradiction judgment becomes authority" without evidence and acceptance gates (`standards/memory-architecture/05-context-graph-capability-assessment.md:503-533`).

Lifecycle deletion is operational cleanup, not authority lifecycle. `remove_episode` deletes edges created solely by that episode, deletes nodes mentioned only in the deleted episode, then deletes the episode; the MCP `delete_episode` exposes that cascade directly (`upstream/graphiti/graphiti_core/graphiti.py:1765-1793`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:660-686`). For product runtime, deletion/forgetting would need to map to accepted source/evidence/claim lifecycle events rather than destructive graph projection cleanup (`standards/memory-architecture/05-context-graph-capability-assessment.md:47-55`, `standards/memory-architecture/05-context-graph-capability-assessment.md:520-533`).

## Integration surface

The Python library surface is the primary one: `Graphiti.__init__` accepts a graph driver, LLM client, embedder, cross-encoder, and `max_coroutines`, defaulting to OpenAI-based clients when not supplied and Neo4j when no graph driver is passed (`upstream/graphiti/graphiti_core/graphiti.py:150-248`). LLM/embedder/reranker defaults are OpenAI-centric, while generic OpenAI-compatible endpoints support Ollama, LM Studio, vLLM, llama.cpp, and similar servers (`upstream/graphiti/graphiti_core/llm_client/openai_client.py:27-63`, `upstream/graphiti/graphiti_core/embedder/openai.py:24-66`, `upstream/graphiti/graphiti_core/cross_encoder/openai_reranker_client.py:31-120`, `upstream/graphiti/graphiti_core/llm_client/openai_generic_client.py:40-50`).

The REST server is a clean but narrow FastAPI sidecar. It initializes Graphiti during app lifespan, has `/healthcheck`, queues message ingestion through an in-process async worker, supports entity-node writes, fact/episode/group deletes, `/search`, `/get-memory`, and episode retrieval (`upstream/graphiti/server/graph_service/main.py:11-29`, `upstream/graphiti/server/graph_service/routers/ingest.py:13-70`, `upstream/graphiti/server/graph_service/routers/ingest.py:73-111`, `upstream/graphiti/server/graph_service/routers/retrieve.py:17-56`). Its settings default `db_backend` to Neo4j but include FalkorDB fields and a live FalkorDB test exercises `/messages -> /episodes -> /search -> /group` with real OpenAI and a reachable FalkorDB (`upstream/graphiti/server/graph_service/config.py:9-22`, `upstream/graphiti/server/tests/test_live_falkordb_int.py:1-26`, `upstream/graphiti/server/tests/test_live_falkordb_int.py:208-243`).

The MCP server is the strongest Role B integration surface. It creates a `FastMCP` server with instructions documenting episodes, facts, group partitioning, bi-temporal `reference_time`, valid/invalid fact metadata, and tools for memory ingestion, node/fact search, saga/community operations, provenance tracing, destructive deletes, clear, and status (`upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:129-174`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:341-475`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:477-631`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:786-1076`). It supports HTTP, stdio, and deprecated SSE transports, with HTTP recommended/default and `/mcp/` as the endpoint (`upstream/graphiti/mcp_server/src/config/schema.py:77-85`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:1103-1108`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:1231-1272`).

The MCP operational model is asynchronous and stateful. `add_memory` returns after queuing work, episodes in the same group are intended to process sequentially, and `get_status` performs a graph query while `/health` only returns a simple JSON health response (`upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:357-360`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:448-470`, `upstream/graphiti/mcp_server/src/services/queue_service.py:12-47`, `upstream/graphiti/mcp_server/src/services/queue_service.py:49-86`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:1046-1082`). Static-code reliability caveat: `QueueService.add_episode_task` checks `_queue_workers` before scheduling the worker, while `_process_episode_queue` sets the worker flag only after the task starts; I did not reproduce a failure, but concurrent submissions before the task runs could plausibly start more than one worker for the same group (`upstream/graphiti/mcp_server/src/services/queue_service.py:36-47`, `upstream/graphiti/mcp_server/src/services/queue_service.py:49-58`).

## License & maturity

Maturity is mixed rather than immature. The core README presents Graphiti as the OSS engine behind Zep and documents self-hosting, graph backends, LLM providers, local endpoints, MCP, and REST (`upstream/graphiti/README.md:84-118`, `upstream/graphiti/README.md:196-340`, `upstream/graphiti/README.md:542-616`). ## Role A assessment

Role A verdict: **do not adopt Graphiti as product-runtime system of record; port selected patterns behind `drivers/*` or repo-native services.** The product runtime requires claim + evidence + provenance + lifecycle, stable source spans, TypeScript/Effect SDK first, acceptance-gated candidate writes, and external systems of record that remain connected but not replaced (`goals/agentic-professional-runtime/README.md:65-105`). The memory standard says semantic memory products are managed caches over deterministic substrate, and `05-context-graph-capability-assessment` says external services must live behind `drivers/*`, graph projections must be rebuildable, and GraphRAG/OntologyRAG output is never accepted fact until verified (`standards/memory-architecture/README.md:18-24`, `standards/memory-architecture/05-context-graph-capability-assessment.md:518-533`).

Graphiti is compatible as a donor/cache/projection because its primitive split maps cleanly to bounded session memory: `EpisodicNode` is the raw ingested episode, `EntityEdge` is the derived fact with episode lineage and valid/invalid windows, and `SearchFilters` can retrieve facts by temporal windows (`upstream/graphiti/graphiti_core/nodes.py:318-351`, `upstream/graphiti/graphiti_core/edges.py:263-285`, `upstream/graphiti/graphiti_core/search/search_filters.py:55-68`). The direct port list is: temporal edge fields, episode lineage, invalidation/supersession mechanics, hybrid retrieval recipes, group partitioning, and Pydantic custom-type extraction as a design reference for Effect Schema extraction candidates (`upstream/graphiti/graphiti_core/search/search_config_recipes.py:33-153`, `upstream/graphiti/mcp_server/src/utils/type_config.py:79-137`, `upstream/graphiti/mcp_server/src/models/entity_types.py:211-222`, `upstream/graphiti/mcp_server/src/models/edge_types.py:1-78`).

Graphiti is weakly aligned with Postgres authority. The clone's storage and integration surfaces are graph-driver-first, and the files I read show no claim/evidence/provenance lifecycle store comparable to the product's authoritative runtime model (`upstream/graphiti/graphiti_core/driver/driver.py:59-142`, `upstream/graphiti/server/graph_service/zep_graphiti.py:81-127`, `upstream/graphiti/mcp_server/src/services/factories.py:408-482`, `goals/agentic-professional-runtime/README.md:93-105`). If used at all in Role A, Graphiti should sit behind a rebuildable projection/cache driver fed by accepted Postgres/EventLog claim records, not ingest raw professional facts as truth (`standards/memory-architecture/05-context-graph-capability-assessment.md:47-55`, `standards/memory-architecture/05-context-graph-capability-assessment.md:520-533`).

## Role B assessment

Role B verdict: **Graphiti is credible but high-maintenance dev-tooling memory.** The repo currently treats `graphiti-memory` as the primary durable repo knowledge base for MCP clients, and upstream Graphiti MCP provides agent-facing tools that map well to coding-agent recall: `add_memory`, `search_nodes`, `search_memory_facts`, `get_episodes`, `get_episode_entities`, `get_status`, and scoped group filtering (`AGENTS.md:76-86`, `upstream/graphiti/mcp_server/README.md:549-568`, `upstream/graphiti/mcp_server/src/graphiti_mcp_server.py:129-168`).

Recall quality should be better than flat text memory when the graph is healthy because Graphiti combines semantic embeddings, keyword/fulltext, graph traversal, episode lineage, temporal windows, and optional graph-distance/episode-mentions reranking (`upstream/graphiti/README.md:120-136`, `upstream/graphiti/graphiti_core/search/search_config.py:32-78`, `upstream/graphiti/graphiti_core/search/search.py:253-460`, `upstream/graphiti/graphiti_core/search/search_helpers.py:27-70`). The same architecture can also degrade if left unbounded, which is why the repo already requires TTL/windowing, pruning, compression/consolidation, uncertainty, and provenance back-pointers for semantic caches (`standards/memory-architecture/01-memory-layer-taxonomy.md:29-55`, `standards/memory-architecture/05-context-graph-capability-assessment.md:518-533`).

Operational burden is the main Role B risk. A normal local stack includes Python/uv, MCP client config, graph DB, LLM API key or local structured-output-capable model, embedder, indexes, queue monitoring, and concurrency tuning; the MCP docs state each episode involves multiple LLM calls and that excessive concurrency causes 429s/cost while too little causes slow throughput (`upstream/graphiti/mcp_server/README.md:79-83`, `upstream/graphiti/mcp_server/README.md:232-250`, `upstream/graphiti/mcp_server/README.md:339-379`). The default Docker path exposes FalkorDB on 6379, FalkorDB UI on 3000, MCP HTTP on 8000, and persistent volumes; the Neo4j compose path sets heap/pagecache memory values, so this is not a zero-infra memory file (`upstream/graphiti/mcp_server/docker/docker-compose.yml:1-44`, `upstream/graphiti/mcp_server/docker/docker-compose-neo4j.yml:1-20`).

MCP maturity is enough for continued evaluation, not enough for blind incumbency. The server is explicitly experimental, has broad tool coverage and live tests, but also stale tests, a static queue race risk, and a core FalkorDB skip in one integration test (`upstream/graphiti/mcp_server/README.md:10-29`, `upstream/graphiti/mcp_server/tests/test_live_falkordb_int.py:181-256`, `upstream/graphiti/mcp_server/tests/test_http_integration.py:46-98`, `upstream/graphiti/mcp_server/src/services/queue_service.py:36-58`, `upstream/graphiti/tests/test_graphiti_int.py:53-56`). My lane recommendation for the Graphiti side is: keep it only if temporal graph recall and episode provenance are decisive for coding-agent context; otherwise demote it to a donor and choose a lighter dev-memory stack in the final comparative synthesis.

**FalkorDB "open-source" phrasing in `03`: NEEDS CORRECTION FOR DEPLOYMENT DECISIONS.** `03` calls FalkorDB open-source, while `21` flags SSPLv1/non-OSI and the Graphiti clone shows FalkorDB is a real deployment path for both core and MCP (`standards/memory-architecture/03-saas-landscape-assessment.md:62-76`, `explorations/atlas-synthesis/synthesis/21-external-memory-kg-donors.md:343-348`, `explorations/atlas-synthesis/synthesis/21-external-memory-kg-donors.md:375-381`, `upstream/graphiti/mcp_server/docker/Dockerfile:1-6`, `upstream/graphiti/mcp_server/docker/docker-compose-falkordb.yml:1-17`). Graphiti's Apache-2.0 license is clean, but Graphiti+FalkorDB as an operational bundle needs a separate backend license decision (`upstream/graphiti/LICENSE:1-3`, `upstream/graphiti/mcp_server/docker/docker-compose.yml:1-44`).

**"Full provenance" in prior assessments: QUALIFY.** Graphiti provides full lineage from derived facts to episode UUIDs and raw episode content, but the product runtime needs source spans, evidence records, provenance activities, lifecycle state, and approval gates (`standards/memory-architecture/03-saas-landscape-assessment.md:16-22`, `upstream/graphiti/README.md:125-128`, `upstream/graphiti/graphiti_core/edges.py:267-281`, `upstream/graphiti/graphiti_core/nodes.py:318-351`, `goals/agentic-professional-runtime/README.md:93-105`, `standards/memory-architecture/05-context-graph-capability-assessment.md:47-55`).
