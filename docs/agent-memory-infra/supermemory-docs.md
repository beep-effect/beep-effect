## TL;DR

Supermemory no longer matches the prior "nothing to take" assessment. The current official docs describe a supported local/self-hosted binary with the same Memory API as the hosted platform, local embeddings, local disk state, and fully offline model routing through OpenAI-compatible local runtimes (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/self-hosting/quickstart; source: https://supermemory.ai/docs/self-hosting/configuration). That refutes the old claim if it implied there is no self-host path.

It still should not become the agentic-professional-runtime system of record. The docs describe automatically extracted, embedded, inferred, updated, and forgotten memories in a living knowledge graph, with only document IDs/history as the explicit provenance surface I found, not source-span authority or human acceptance semantics (source: https://supermemory.ai/docs/concepts/how-it-works; source: https://supermemory.ai/docs/concepts/graph-memory; source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history). For Role A, treat it as a possible donor/cache/projection behind `drivers/*`, not authoritative runtime truth. For Role B, it is worth a bounded trial because the docs show Codex, Claude Code, and MCP integrations, but hosted MCP and several enterprise controls are platform/paid features (source: https://supermemory.ai/docs/integrations/codex; source: https://supermemory.ai/docs/integrations/claude-code; source: https://supermemory.ai/docs/supermemory-mcp/mcp; source: https://supermemory.ai/docs/self-hosting/configuration; source: https://supermemory.ai/pricing/).

## Hard-gate verdicts

1. self-hostable/local-first: PASS with packaging caveat. Supermemory documents a one-binary local server that runs on the user's hardware, exposes the full Memory API, stores state in `./.supermemory` or `$SUPERMEMORY_DATA_DIR`, computes embeddings locally, and can run with local OpenAI-compatible endpoints such as Ollama, LM Studio, vLLM, or llama.cpp (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/self-hosting/quickstart; source: https://supermemory.ai/docs/self-hosting/configuration). The caveat is commercial packaging: the pricing page says self-hosted deployments are available on Scale and Enterprise, and Enterprise adds fully air-gapped deployments; the self-hosting docs separately position "Supermemory local" as free/open-source for builders and local development (source: https://supermemory.ai/pricing/; source: https://supermemory.ai/docs/self-hosting/local-vs-enterprise).

2. OSI license without copyleft trap: PASS on fetched evidence. The self-hosting docs link the local binary/source as open source, and the linked GitHub repository page identifies the repository as "MIT license" (source: https://supermemory.ai/docs/self-hosting/overview; source: https://git.new/memory). I found no fetched Supermemory page identifying SSPL, BUSL, AGPL, or another copyleft/network-copyleft license.

3. TS-native or clean HTTP/MCP API: PASS. The official SDK page lists JavaScript and Python SDKs, shows `npm install supermemory`, and says both SDKs work against self-hosted Supermemory by setting `baseURL` to `http://localhost:6767` (source: https://supermemory.ai/docs/integrations/supermemory-sdk). The docs also expose HTTP endpoints such as `POST /v3/documents`, `POST /v4/search`, and `POST /v4/memories/list` (source: https://supermemory.ai/docs/add-memories; source: https://supermemory.ai/docs/search; source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history). MCP support exists through a hosted Supermemory MCP Server 4.0 with OAuth/API-key auth, `memory`, `recall`, and `whoAmI` tools, resources, and a `context` prompt (source: https://supermemory.ai/docs/supermemory-mcp/mcp; source: https://supermemory.ai/docs/supermemory-mcp/setup). Local caveat: the self-host configuration page says "Supermemory MCP" managed endpoints are platform-only and not included in the self-hosted binary (source: https://supermemory.ai/docs/self-hosting/configuration).

## Architecture & storage

Supermemory's core abstraction is "Documents" as raw input and "Memories" as extracted knowledge units. The docs say documents can be PDFs, web pages, pasted text, images with text, or videos, while memories are semantic chunks that are embedded, connected through relationships, and dynamically updated over time (source: https://supermemory.ai/docs/concepts/how-it-works). The graph model is not an entity-relation-entity knowledge graph in the docs; it is described as "facts built on top of other facts" with update, extend, and derive relationships (source: https://supermemory.ai/docs/concepts/graph-memory).

The ingestion pipeline is document-first: validate request, store the document, queue processing, extract content, chunk into searchable memories, embed for vector search, and index for retrieval (source: https://supermemory.ai/docs/add-memories). The concept page similarly lists queued, extracting, chunking, embedding, indexing, and done stages (source: https://supermemory.ai/docs/concepts/how-it-works).

Isolation is organized through `containerTag`. The docs call it the primary organization/isolation boundary, auto-create a space on first write, hash each container tag into a dedicated vector namespace, and say embeddings/chunks/memory entries for one tag are stored and searched independently of other tags (source: https://supermemory.ai/docs/concepts/container-tags). API keys and members can also be restricted by container tags; out-of-scope reads/writes return `403 Forbidden` (source: https://supermemory.ai/docs/concepts/container-tags; source: https://supermemory.ai/docs/authentication).

Self-hosted storage is local. The quickstart says first boot creates the embedded graph engine, local embeddings, credentials, a local API key, and a default `./.supermemory` database directory; it also says the data directory contains the graph engine data, auth secret, and embedding model cache (source: https://supermemory.ai/docs/self-hosting/quickstart). The configuration page says uploaded files are stored on local disk inside `$SUPERMEMORY_DATA_DIR` and served at `/files/:key` (source: https://supermemory.ai/docs/self-hosting/configuration).

## Retrieval

Retrieval is semantic/hybrid, not deterministic authority retrieval. The search docs call the API "semantic search across your memories and documents" and recommend `searchMode: "hybrid"` so a single call searches both extracted memories and document chunks (source: https://supermemory.ai/docs/search). Search results include either a `memory` or `chunk`, plus `similarity`, metadata, `updatedAt`, and `version` (source: https://supermemory.ai/docs/search).

The supported modes I found are `hybrid` and `memories`; `hybrid` searches both memories and document chunks, while `memories` searches only extracted memories (source: https://supermemory.ai/docs/search). Query controls include `limit`, `threshold`, `rerank`, and metadata filters, with reranking documented as adding about 100 ms of latency (source: https://supermemory.ai/docs/search). Metadata filters support string equality, string contains, numeric comparisons, array contains, `AND`/`OR` composition, and negation (source: https://supermemory.ai/docs/concepts/filtering; source: https://supermemory.ai/docs/search).

User-profile retrieval is also part of the integration surface. The SDK page shows `client.profile({ containerTag })` returning `profile.static` and `profile.dynamic` values, and the repository README says user profiles are auto-maintained context with stable facts and recent activity (source: https://supermemory.ai/docs/integrations/supermemory-sdk; source: https://git.new/memory).

## Provenance/temporal/lifecycle

The strongest provenance surface I found is document linkage plus version/history metadata, not source-span authority. Direct memory creation returns a `documentId` for traceability, and the memory list endpoint returns `sourceCount`, `documentIds`, `parentMemoryId`, `rootMemoryId`, `history`, `memoryRelations`, and `temporalContext` fields (source: https://supermemory.ai/docs/memory-operations; source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history). I did not find fetched docs promising source-span IDs, source offsets, evidence acceptance, or deterministic verification equivalent to the agentic-professional-runtime authority model.

Temporal semantics are a real documented feature. Update relationships mark current knowledge with `isLatest` while preserving history, versioned memory updates preserve the original with `isLatest=false`, and the list endpoint returns historical versions with timestamps and parent/root memory IDs (source: https://supermemory.ai/docs/concepts/how-it-works; source: https://supermemory.ai/docs/concepts/graph-memory; source: https://supermemory.ai/docs/memory-operations; source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history).

Lifecycle controls include soft deletion and semantic bulk forgetting. A single memory forget is documented as a soft delete that excludes the memory from search while preserving it in the database with `isForgotten=true`; forget-matching semantically searches a container, has a dry-run mode, records a reason, and returns a `forgetBatchId` on apply (source: https://supermemory.ai/docs/memory-operations). Document deletes are different: the add-context page says document deletes are permanent and have no recovery (source: https://supermemory.ai/docs/add-memories).

Automatic forgetting is also part of the memory model. The graph-memory docs say temporary facts can be forgotten after expiration, contradictions are resolved through update relationships, casual/noise content is filtered, facts persist until updated, preferences strengthen with repetition, and episodes decay unless significant (source: https://supermemory.ai/docs/concepts/graph-memory).

## Integration surface

The cleanest product integration path is HTTP or the official JavaScript SDK. The SDK page documents `npm install supermemory`, `import Supermemory from "supermemory"`, add/search/profile operations, and self-host `baseURL` configuration (source: https://supermemory.ai/docs/integrations/supermemory-sdk). The HTTP docs show direct calls for ingestion, search, memory creation, memory listing, settings, and connection management (source: https://supermemory.ai/docs/add-memories; source: https://supermemory.ai/docs/search; source: https://supermemory.ai/docs/memory-operations; source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history; source: https://supermemory.ai/docs/api-reference/settings/get-settings).

MCP support exists but is hosted/platform-shaped. The MCP docs describe Supermemory MCP Server 4.0 on Cloudflare Workers with Durable Objects, OAuth by default, optional API-key auth, and tools/resources/prompts for memory and recall (source: https://supermemory.ai/docs/supermemory-mcp/mcp; source: https://supermemory.ai/docs/supermemory-mcp/setup). The self-hosting overview says coding plugins can target a local server via `SUPERMEMORY_API_URL=http://localhost:6767`, but the self-hosting comparison/configuration pages say Supermemory MCP is a platform-only/managed endpoint feature, not part of the local binary (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/self-hosting/configuration).

Dev-agent integrations are explicit. The Codex plugin uses hooks and skills, recalls context before each prompt, captures conversations after each session, redacts `<private>...</private>` content before storage, derives user/project container tags from environment, and installs `supermemory-search`, `supermemory-save`, `supermemory-forget`, and `supermemory-status` skills (source: https://supermemory.ai/docs/integrations/codex). The Claude Code plugin requires Supermemory Pro, can target a self-hosted server through `SUPERMEMORY_API_URL`, injects context at session start, captures tool usage during the session, and supports skip/capture tool settings (source: https://supermemory.ai/docs/integrations/claude-code).

Connectors are broad in the current docs but not all local. The connectors overview lists Google Drive, Gmail, Notion, OneDrive, GitHub, Granola, and Web Crawler, with webhook/scheduled/manual sync behavior depending on provider (source: https://supermemory.ai/docs/connectors/overview). However, the self-host configuration page says connectors are platform-only for the self-hosted binary, and the API docs for resource fetch/configure say resource management is supported for GitHub for now (source: https://supermemory.ai/docs/self-hosting/configuration; source: https://supermemory.ai/docs/api-reference/connections/fetch-resources; source: https://supermemory.ai/docs/api-reference/connections/configure-connection).

## License, pricing & maturity

License: the linked repository is public and labeled "MIT license" on GitHub (source: https://git.new/memory). The official docs call self-hosted local "free, open source" and link to that repository (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/self-hosting/local-vs-enterprise). I did not find any fetched page stating SSPL, BUSL, or AGPL.

Pricing: the public pricing page has Free at $0/mo, Pro at $19/mo, Max at $100/mo, Scale at $399/mo, and Enterprise custom pricing; it also lists per-usage rates for memory graph, SuperRAG, search/traversal, and operations (source: https://supermemory.ai/pricing/). The pricing page says Free includes Supermemory MCP and community support, Pro adds Google Drive/Notion/OneDrive connectors plus OpenClaw/Claude Code/other plugins, Max adds Gmail/Granola connectors, Scale adds all connectors plus SOC 2 / HIPAA BAA and a self-hosted option, and Enterprise adds air-gapped self-hosting, dedicated managed instances, SOC 2 / HIPAA / GDPR, custom contracts/DPA, Enterprise MCP, custom rate limits, dedicated infrastructure, and SLA support (source: https://supermemory.ai/pricing/).

Maturity: the changelog shows first public release in April 2024, API v2 and organization support in March 2025, initial self-host support in September 2025, and new API/SDK/MCP/connector updates in 2026 (source: https://supermemory.ai/docs/changelog/overview). The docs and changelog show active product movement, but that also means API surface churn is visible: current concept docs prefer singular `containerTag` for v4 while older examples and v3 endpoints still use plural `containerTags` (source: https://supermemory.ai/docs/concepts/container-tags; source: https://supermemory.ai/docs/concepts/filtering; source: https://supermemory.ai/docs/changelog/overview).

## Role A assessment

Verdict: LEARN / LIMITED USE as a donor, cache, or projection driver; do not use as authority. Supermemory has useful patterns for a driver-backed cache: local deployment, a clean HTTP/JS integration path, dedicated container namespaces, hybrid memory-plus-document retrieval, versioned memories, soft-delete, and a graph relation model for updates/extensions/inferences (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/integrations/supermemory-sdk; source: https://supermemory.ai/docs/concepts/container-tags; source: https://supermemory.ai/docs/search; source: https://supermemory.ai/docs/memory-operations; source: https://supermemory.ai/docs/concepts/graph-memory).

The fit stops at the authority boundary. The product runtime requires accepted claims with evidence, provenance, lifecycle, and human promotion into authoritative runtime state; Supermemory's docs describe automatic extraction, semantic chunks, inferred memories, automatic relationship creation, and automatic forgetting, with document IDs/history as the provenance surface found in the fetched docs (source: https://supermemory.ai/docs/concepts/how-it-works; source: https://supermemory.ai/docs/concepts/graph-memory; source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history). That makes it unsuitable as a source of truth for professional evidence or privilege-sensitive decisions, but potentially useful as a replaceable retrieval projection behind `drivers/*`.

For enterprise/data residency, the local binary is strong enough for privacy-sensitive prototypes because it stores data locally, computes embeddings locally, sends no self-host analytics, and can run against local models (source: https://supermemory.ai/docs/self-hosting/configuration). Production residency/compliance controls appear to live in Scale/Enterprise packaging, including self-hosted deployments, air-gapped support, dedicated managed instances, DPA/custom contracts, and SLA support (source: https://supermemory.ai/pricing/; source: https://supermemory.ai/docs/self-hosting/local-vs-enterprise).

## Role B assessment

Verdict: TRY in a bounded dev-tooling lane if the experiment can tolerate hosted/paid features or local plugin-only mode. The Codex plugin is directly relevant because it installs hooks and skills, automatically recalls before prompts, captures sessions at stop, scopes memories by user/project tags, and has an explicit local-server path through `SUPERMEMORY_API_URL=http://localhost:6767` (source: https://supermemory.ai/docs/integrations/codex). The Claude Code plugin is relevant but gated by the Pro plan in the docs; it injects context at session start and captures selected tool usage, which is useful but also increases review/privacy burden (source: https://supermemory.ai/docs/integrations/claude-code).

MCP reliability cannot be proven from the fetched docs. The docs show setup mechanics, OAuth/API-key authentication, and tool/resource/prompt shapes, but they do not provide uptime history, failure-mode documentation, or local MCP parity; the self-host page explicitly keeps managed MCP endpoints platform-only (source: https://supermemory.ai/docs/supermemory-mcp/mcp; source: https://supermemory.ai/docs/supermemory-mcp/setup; source: https://supermemory.ai/docs/self-hosting/configuration). For Claude/Codex agents, the local-footprint option is better through the self-hosted API plus plugins than through MCP if the requirement is local-first (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/integrations/codex; source: https://supermemory.ai/docs/integrations/claude-code).

Maintenance burden is moderate. Running local Supermemory itself is small by the docs: one binary, one local data directory, one API key, and optional env vars (source: https://supermemory.ai/docs/self-hosting/quickstart; source: https://supermemory.ai/docs/self-hosting/configuration). The agent plugins add global client changes: Codex hook registrations, installed skills, optional `~/.codex/supermemory.json`, and debug logs; Claude Code adds plugin installation plus `~/.supermemory-claude/settings.json` and capture/skip policy tuning (source: https://supermemory.ai/docs/integrations/codex; source: https://supermemory.ai/docs/integrations/claude-code).

## Contradictions with prior repo assessments

Prior repo assessment cross-check target: `standards/memory-architecture/03-saas-landscape-assessment.md` rated Supermemory IGNORE and said there was nothing to take.

- Refuted: no useful self-host path. Current docs show a supported local/self-hosted server with one binary, full API, local embeddings, local data directory, and offline model support (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/self-hosting/quickstart; source: https://supermemory.ai/docs/self-hosting/configuration).
- Refuted in part: connector ecosystem is only GitHub. Current connector docs list Google Drive, Gmail, Notion, OneDrive, GitHub, Granola, S3 through the create-connection API, and Web Crawler/Web Crawler docs in the index; the overview lists several as supported connectors (source: https://supermemory.ai/docs/connectors/overview; source: https://supermemory.ai/docs/api-reference/connections/create-connection; source: https://supermemory.ai/docs/llms.txt). However, resource fetch/configuration APIs still state "supported providers: GitHub for now", and self-hosted local excludes connectors, so the earlier caution about uneven connector maturity still has support (source: https://supermemory.ai/docs/api-reference/connections/fetch-resources; source: https://supermemory.ai/docs/api-reference/connections/configure-connection; source: https://supermemory.ai/docs/self-hosting/configuration).
- Partly upheld: opaque internals. The docs now explain documents versus memories, the processing pipeline, container namespaces, update/extend/derive relationships, versioned memories, and lifecycle operations (source: https://supermemory.ai/docs/concepts/how-it-works; source: https://supermemory.ai/docs/concepts/graph-memory; source: https://supermemory.ai/docs/concepts/container-tags; source: https://supermemory.ai/docs/memory-operations). They still do not expose enough deterministic provenance, source-span semantics, inference scoring, or verification machinery to satisfy this repo's authority-layer requirements, based on the fetched docs (source: https://supermemory.ai/docs/api-reference/content-management/list-memory-entries-with-history; source: https://supermemory.ai/docs/concepts/graph-memory).
- Not confirmed from docs: auth reliability issues. The current docs show Bearer API keys, scoped API keys, OAuth for MCP, and optional API-key MCP auth, but I found no fetched official page discussing reliability incidents or failure rates (source: https://supermemory.ai/docs/authentication; source: https://supermemory.ai/docs/supermemory-mcp/mcp; source: https://supermemory.ai/docs/supermemory-mcp/setup).

Updated verdict: change prior IGNORE to LEARN / LIMITED TRIAL. There are now concrete things to take: local-first packaging, simple SDK/baseURL swap, container-tag isolation, memory lifecycle/versioning ideas, and dev-agent plugin ergonomics (source: https://supermemory.ai/docs/self-hosting/overview; source: https://supermemory.ai/docs/integrations/supermemory-sdk; source: https://supermemory.ai/docs/concepts/container-tags; source: https://supermemory.ai/docs/memory-operations; source: https://supermemory.ai/docs/integrations/codex). The "do not use as foundation/system of record" conclusion remains correct because the documented memory model is semantic, inferred, and automatically evolving (source: https://supermemory.ai/docs/concepts/how-it-works; source: https://supermemory.ai/docs/concepts/graph-memory).
