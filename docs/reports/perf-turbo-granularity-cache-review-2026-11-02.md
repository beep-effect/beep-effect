# Turbo input granularity cache review (quality audit M9, M10, K3)

Three over-invalidations in the Turbo graph are narrowed by changing input
sets and one dependency edge per policy task. No command, output, cache flag,
environment declaration, qualification scope, profile, epoch or qualification
state changes. This reviews the declared input-set change only. It is not
evidence that any computation is newly qualified or that a quality gate passed.

## Input-set changes

Root `turbo.json`, inherited by every workspace (subject `//` and all packages):

- `transit`, `build`, `check`, `test` and `test:property` keep
  `$TURBO_DEFAULT$` and gain `!README.md`, `!CHANGELOG.md` and `!LICENSE`.
  These are package-relative, so only each package's own root prose leaves the
  hash. No build, typecheck or test reads it: README-touching tests write
  fixture copies, imported Markdown sits under `src/` (still keyed), and the one
  README generator (`@beep/effect-drizzle`'s `readme` script) writes the README
  and is not part of build, check or test.
- `build` and `transit` also gain `!test/**`. No package `exports` or Vitest
  alias resolves into a `test/` directory (all `@beep/*/test` aliases point at
  `src/test/*.test-kit.ts`), and no build script reads one. Runtime files
  outside `src` (`data/`, `assets/`, `styles/`, `configs/`, `schema.json`,
  `docker/`, `drizzle/`, `spec/`) stay in `transit`, so dependents still replay
  when one changes.

Workspace overlays (subjects `@beep/docket-intake`, `@beep/api-docs`,
`@beep/ciops`, the six `@beep/practice-*` apps, `@beep/todox`, `@beep/oip-web`):
their builds compile `test/` (`tsrs -p tsconfig.check.json`, or `next build`
typechecking a `tsconfig.json` that includes `test`), so each `build` override
restates the root inputs without `!test/**`, keeping `.env*` where it was
declared. Turbo applies every negation after every inclusion, so an
`$TURBO_EXTENDS$` overlay cannot re-include `test/**`.

Policy fingerprint seals (generated by `beep lint policy-fingerprint --write`):

- The seals move from root tasks `//#lint:policy-fingerprint:<key>` (script
  `true`) to script-less CLI-workspace tasks
  `@beep/repo-cli#lint:policy-fingerprint:<key>` with `$TURBO_ROOT$/` inputs.
  Every policy task's fingerprint edge is rewritten to the new id, and the 36
  root `lint:policy-fingerprint:<key>` scripts are removed. Turbo hashes the root
  `turbo.json` into every root task and ignores `!turbo.json` (probed on Turbo
  2.11.10), so a root seal replayed every package policy task on any
  `turbo.json` edit. A CLI-workspace task hashes `packages/tooling/tool/cli/package.json`
  and that package's overlay instead; the manifest is already a shared seal input.
- Root checker configuration leaves the shared seal. Each family goes to the
  seals whose closure holds a code-level string literal naming a family file, or
  naming the tool that discovers it. The live completeness test re-derives every
  chain's reads from its declared modules and fails on a missing file.
- `//#lint:policy-fingerprint` (the drift check) additionally declares the
  fingerprint file and every routed root file.

## Evidence

- `packages/tooling/tool/cli/test/package-role-turbo-inputs.test.ts`: a native
  Turbo fixture where upstream README, CHANGELOG, LICENSE and test edits replay
  nothing downstream, while `src`, `data/` and nested `src` Markdown edits do.
  It also derives the eleven test-compiling builds from their compiler programs.
- `policy-fingerprint-turbo-inputs.test.ts`, `laws-turbo-inputs.test.ts` and
  `root-tasks-turbo-inputs.test.ts`: a `turbo.json` byte edit replays root tasks
  only; a checker config replays a task iff its seal chain or own inputs
  declare it.
- Full-repo dry runs against `@beep/yaml` (79 dependents): README edit 696 → 2
  executable task hashes changed, test edit 701 → 9, root `turbo.json` byte edit
  565 → 192, `biome.jsonc` byte edit 751 → 378.
