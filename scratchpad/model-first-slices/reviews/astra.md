# Verdict

Keep Effect Cluster, explicit domain models, consumer-owned ports, and React machines.
Do not adopt this proposal as an architecture standard yet: several claimed guarantees are false.
The decisive gaps are authorization on retries, durable-schema evolution, projection replay, and causal confirmation.
Make these executable acceptance criteria before retiring a platform implementation or enforcing package counts.

## Wrong on the merits

### 1. Authorization only in `decide` is incomplete, because retries bypass it

On the durable hosting path, receipt lookup precedes `kit.handle`; a duplicate command ID returns the old accepted result without decoding the new command or running the aggregate's membership checks ([D/src/DurableObjects.ts:801–819](~/YeeBois/references/effect/alchemy/packages/domain/src/DurableObjects.ts:801)). The Api forwards a caller-supplied command ID and returns the stored reply, stream and version ([D/src/Api.ts:588–600](~/YeeBois/references/effect/alchemy/packages/domain/src/Api.ts:588)). Therefore a command ID is not merely a deduplication convenience: it is part of a security and request-equivalence protocol.

A concrete counterexample is a caller who is authenticated but no longer authorized, replaying a known accepted ID against the same aggregate. A membership check solely in `decide` does not run. A different payload or command tag with the same ID also does not trigger a mismatch check in this path. This is a source-derived counterexample, not an executed exploit; the public Api strips events from receipts, so I am **not** claiming it returns the whole event payload. Sensitive custom replies remain relevant ([D/src/DurableObjects.ts:804–826](~/YeeBois/references/effect/alchemy/packages/domain/src/DurableObjects.ts:804), [D/src/Api.ts:594–599](~/YeeBois/references/effect/alchemy/packages/domain/src/Api.ts:594)).

**Required design:** authorize access to a cached result independently of deciding a new command; bind idempotency keys to tenant, operation and canonical request fingerprint; define whether the result is visible after grant revocation. Test accepted replay, changed payload, changed command, cross-tenant replay and revoked replay. Also define rejected-command retry semantics: this implementation does not persist the rejection at this point ([D/src/DurableObjects.ts:819–838](~/YeeBois/references/effect/alchemy/packages/domain/src/DurableObjects.ts:819)).

### 2. Event decoding is not a complete durable migration mechanism

The proposal is correct that the kernel uses event-schema codecs. It is wrong to equate that with “upcasting solved.” The kernel chooses the codec using the stored tag **before** decoding, so a new tag's decoder cannot rescue an unregistered old tag. The builder exposes fields and a tagged class; a general whole-record rename/union needs an actual compatible Event implementation, not an assumed `.pipe(...)` result that has lost the Event constructor/statics ([D/src/Kernel.ts:294–315](~/YeeBois/references/effect/alchemy/packages/domain/src/Kernel.ts:294), [D/src/Event.ts:22–27](~/YeeBois/references/effect/alchemy/packages/domain/src/Event.ts:22), [D/src/Event.ts:74–104](~/YeeBois/references/effect/alchemy/packages/domain/src/Event.ts:74)). Field codecs are a legitimate starting point. I did not execute a renamed-field or version-union probe, so that broader recipe remains unproven.

More decisively, aggregate execution loads and decodes persisted state directly. Changing only historical event decoders does not migrate that state. Receipts have their own event and reply decoding, and views decode persisted snapshots too ([D/src/Kernel.ts:1100–1102](~/YeeBois/references/effect/alchemy/packages/domain/src/Kernel.ts:1100), [D/src/Kernel.ts:1616–1637](~/YeeBois/references/effect/alchemy/packages/domain/src/Kernel.ts:1616)). Define compatibility for **state, event, reply, command, request context, workflow payload/result and projection generation**, not just event tags. RequestContext restoration itself depends on registered service keys ([D/src/RequestContext.ts:107–115](~/YeeBois/references/effect/alchemy/packages/domain/src/RequestContext.ts:107)).

“Decodes every stored sample” proves compatibility with those samples, not inclusion of the old accepted language or preservation of meaning. A codec that maps every old amount to zero can pass a decode-only check. Require frozen old-wire fixtures, semantic expected values, round-trip laws, replay equivalence, and an old/new deployment compatibility matrix. Keep the old writer's contract separate from the new reader's widening acceptance.

### 3. “One Model = one bounded context” confuses a library container with a modeling decision

The Model is a list of aggregate/read/process declarations and a hosting composition; the cluster adapter turns its runtime into one entity type with many separate instance IDs ([D/src/Model.ts:117–145](~/YeeBois/references/effect/alchemy/packages/domain/src/Model.ts:117), [D/src/EffectCluster/index.ts:487–498](~/YeeBois/references/effect/alchemy/packages/domain/src/EffectCluster/index.ts:487)). Neither fact establishes a ubiquitous language, ownership boundary or correct aggregate boundary.

Use a bounded context to determine the public language, then choose one or more Models as runtime composition units. One Model per context is a useful default, not the definition of a context. “Fits in an agent context window” is particularly wrong as a boundary test: model/window changes should not change business semantics. Give agents bounded tasks and generated dependency views instead of splitting the domain to fit a transient tool limit.

Likewise, “can refuse” is not a sufficient or necessary classification of aggregates. A fact-only ledger can need ordered durable ownership without business rejections. An upload store can refuse writes and still not be a domain aggregate. Choose aggregates by invariant ownership and serialization requirements. The library even supports accepted no-ops explicitly ([D/src/Aggregate.ts:135–149](~/YeeBois/references/effect/alchemy/packages/domain/src/Aggregate.ts:135)).

### 4. A saga cannot turn an arbitrary cross-aggregate invariant into a hard invariant

Reservation plus compensation only solves the invariant if every conflicting path participates in the reservation protocol. Compensation cannot make an externally observed violation never have happened. A uniqueness aggregate needs ownership, release/reassign rules, fencing, canonicalization, and a defined moment when the assignment becomes authoritative. Otherwise it is a reservation record beside inconsistent state.

The prototype makes the problem concrete: `MergeParties` checks the survivor, self-merge, its org and whether an ID is already in its array. It does not establish that the absorbed party exists, has the same org, is unmerged, or cannot be absorbed by a second survivor. The event then appends its ID ([P/party/model/src/Party/Party.aggregate.ts:50–68](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Party/Party.aggregate.ts:50)). This is a valid sketch of a local append, not proof of a globally correct party merge. The policy also swallows `MergeVetoed`, so accepted claim and completed merge are distinct outcomes ([P/party/model/src/Party/MergeOnSameParty.policy.live.ts:21–29](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Party/MergeOnSameParty.policy.live.ts:21)). Model those outcomes explicitly.

### 5. Projection replay requires a durable sink protocol

The host runs a projection batch and only afterwards updates its processed position and checkpoints. A crash between those actions re-executes the batch ([D/src/DurableObjects.ts:1302–1337](~/YeeBois/references/effect/alchemy/packages/domain/src/DurableObjects.ts:1302)). This is not included in the aggregate transaction guarantee.

The prototype strips delivery identity when producing `DirectoryChange`: the sink receives party IDs and changes, but no source stream/sequence or projection generation ([P/party/model/src/Directory/PartyDirectory.projection.live.ts:16–32](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Directory/PartyDirectory.projection.live.ts:16), [P/party/model/src/Directory/PartyDirectory.store.ts:42–64](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Directory/PartyDirectory.store.ts:42)). Its `Registered` reducer resets `absorbed` to `[]`; its `Merged` reducer deduplicates only an absorbed ID ([P/party/model/src/Directory/PartyDirectory.store.ts:76–83](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Directory/PartyDirectory.store.ts:76)). An immediately repeated complete batch can be harmless, but a repeated old registration after a later merge erases the later result. The advertised “replaying a change leaves the directory as it was” contract is therefore too broad.

Pass source identity, sequence and projection generation to the sink. Atomically commit sink changes with a sink-owned inbox/checkpoint; reject stale application or build a new generation separately. Define ordering across multiple sources. A memory twin must exercise these semantics, not merely implement the same method signatures.

### 6. Actor data is neither an authorization grant nor proof of human approval

Keep event attribution. Separate **initiator, executor, authority and causal parent** rather than pretending one `by` value answers all four. The prototype's agent Actor contains `onBehalfOf`, but that field is a principal ID, not proof of delegated scope or current authority ([P/shared/kernel/src/Actor.ts:23–27](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/shared/kernel/src/Actor.ts:23)). A policy constructing a System actor is compatible with the library, but it must not implicitly acquire all tenant authority ([P/party/model/src/Party/MergeOnSameParty.policy.live.ts:21–27](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Party/MergeOnSameParty.policy.live.ts:21)).

The human-approval example is not a human-only boundary. `HumanDecision` accepts the full Actor union; the saga installs `decision.by` as CurrentActor. `AcceptClaim` checks membership and evidence, but not Human identity or an approval record bound to the proposal ([P/party/model/src/Review/ReviewAssist.saga.ts:24–26](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Review/ReviewAssist.saga.ts:24), [P/party/model/src/Review/ReviewAssist.saga.live.ts:51–60](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Review/ReviewAssist.saga.live.ts:51), [P/party/model/src/Claim/Claim.aggregate.ts:88–92](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/Claim.aggregate.ts:88)). The story supplies a trusted reviewer directly to a signal; it proves that path, not authenticated ingress ([P/party/model/test/Party.story.test.ts:94–99](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/test/Party.story.test.ts:94)). The fixture Session explicitly says it trusts caller-provided identity headers; that is disclosed fixture behavior, not a newly discovered production vulnerability ([P/party/host/src/Session.middleware.live.ts:9–16](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/host/src/Session.middleware.live.ts:9)).

Use an authenticated `ApproveProposal` command that stamps its own actor, checks current authority, binds approval to proposal/evidence version or digest, and records an immutable decision. Let a policy resume the process from that fact. Do not accept a caller-provided Actor as approval evidence. Decide how revocation affects queued commands, retries and open subscriptions: repeated validation of an unchanged actor snapshot is not fresh membership validation ([D/src/RequestContext.ts:93–115](~/YeeBois/references/effect/alchemy/packages/domain/src/RequestContext.ts:93), [D/src/Api.ts:710–721](~/YeeBois/references/effect/alchemy/packages/domain/src/Api.ts:710)).

### 7. Activities and singletons do not confer exactly-once effects

The prototype's comment that an activity means a retried step “does not apply twice” is too strong. The assessment activity calls the external reasoner; the command activities call aggregates ([P/party/model/src/Review/ReviewAssist.saga.live.ts:15–17](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Review/ReviewAssist.saga.live.ts:15), [P/party/model/src/Review/ReviewAssist.saga.live.ts:35–60](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Review/ReviewAssist.saga.live.ts:35)). Cluster workflow execution identifies and persists activity calls, but an external provider is not part of that persistence transaction ([E/src/cluster/ClusterWorkflowEngine.ts:760–805](~/YeeBois/references/effect/effect/packages/effect/src/cluster/ClusterWorkflowEngine.ts:760)). A provider may finish before its activity result is durably recorded. Require provider idempotency keys or explicit uncertain-outcome reconciliation.

A saga key is its execution ID. The prototype keys reviews by ClaimId, so it does not define distinct later review attempts for the same claim ([P/party/model/src/Review/ReviewAssist.saga.ts:35–44](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Review/ReviewAssist.saga.ts:35), [D/src/Saga.ts:470–485](~/YeeBois/references/effect/alchemy/packages/domain/src/Saga.ts:470)). Introduce ReviewRunId and explicit relationships to claim/proposal versions; define retry versus new run, cancellation, supersession and expiration.

Pool portability also has behavioral content. Effect's Cloudflare route says a singleton wake should complete, not run forever, and ClusterCron needs its seed woken by a trigger ([F/README.md:130–158](~/YeeBois/references/effect/effect/packages/platform/cloudflare/README.md:130)). Alchemy's DurableObjectPool describes alarm-backed singleton/cron instances ([C/src/Cloudflare/DurableObjectPool.ts:88–97](~/YeeBois/references/effect/alchemy/packages/effect-cluster/src/Cloudflare/DurableObjectPool.ts:88)). These are separate implementations to test, not interchangeable behavior inferred from both being Layers.

### 8. The React machine loses causality

Counterexample: press Accept, then receive a delayed initial Pending snapshot. `ReviewChanged` clears `sending`; a second press now issues another command even though the first command is still in flight. A late refusal also lacks a command ID and can clear a newer request ([P/PROPOSAL.md:794–818](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/PROPOSAL.md:794)). Keep React and the pure machine; fix the protocol.

Track request identity, server acceptance receipt, read checkpoint and subscription epoch separately. An accepted receipt means the command committed; a causally sufficient read means the UI caught up. Model transport failure as potentially unknown outcome, retry with the same command ID, and distinguish business refusal from consistency timeout. The library's checkpoint wait supplies a useful primitive but has a real timeout result ([D/src/Model.ts:889–920](~/YeeBois/references/effect/alchemy/packages/domain/src/Model.ts:889)). Test reordered updates, duplicate replies, reconnects, no-op commands and overlapping intents.

### 9. Package count and types do not enforce the promised capabilities

The Layer assertion is worthwhile, but a handler can use `fetch`, `Date.now`, mutable globals or an internally provided live Layer while leaving no extra Effect requirement. `decide`'s declared environment is limited to middleware services, which is a useful type constraint rather than referential-transparency enforcement ([D/src/Aggregate.ts:101–112](~/YeeBois/references/effect/alchemy/packages/domain/src/Aggregate.ts:101), [P/party/model/src/Handlers.ts:82–110](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Handlers.ts:82)). A package dependency list also cannot prohibit ambient DOM APIs or built-in runtime imports by itself.

The `/api` import path already reaches aggregate `decide` code, even though it avoids `.live.ts` files ([P/party/model/src/ReviewerApi.api.ts:3–14](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/ReviewerApi.api.ts:3), [P/party/model/src/Party.model.ts:3–11](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Party.model.ts:3), [P/party/model/src/Claim/Claim.aggregate.ts:64–98](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/Claim.aggregate.ts:64)). Decide whether shipping that executable model to all clients is intentional. If the browser needs only wire contracts, generate a contract-only entry or package. Keep a separate executable model closure when its capabilities or dependencies demand it; do not force exactly three packages.

The suffix law also contradicts the file examples. A command file exports an Event and a Rejection as well as a Command, so “every export has the suffix's kind” rejects the demonstrated design ([P/PROPOSAL.md:907](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/PROPOSAL.md:907), [P/party/model/src/Claim/AssertClaim.command.ts:16–54](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/AssertClaim.command.ts:16)). Check one designated primary export, and validate companion exports separately.

### 10. Machine-readable laws cannot replace semantic review

Use Model reflection for structural checks, import analysis for dependency checks, type checks for tracked requirements, and executed tests for behaviors. Do not call these one Model-derived proof. Definition verification reports structural problems such as duplicate event tags; it does not prove that two evidence sources are independent or a merge is semantically valid ([D/src/Kernel.ts:269–305](~/YeeBois/references/effect/alchemy/packages/domain/src/Kernel.ts:269)). The prototype's admission rule counts distinct supplied strings, and the input accepts those strings directly; that demonstrates arithmetic, not independent corroboration ([P/party/model/src/Claim/Claim.rules.ts:54–61](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/Claim.rules.ts:54), [P/party/model/src/Evidence.ts:17](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Evidence.ts:17), [P/party/model/src/Claim/AssertClaim.command.ts:44–48](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/AssertClaim.command.ts:44)).

Counting a rejection tag or message in one story is not transition coverage. Do not drop semantic review on that basis. Agent-generated stories need adversarial assertions derived from invariants, not just examples mirroring the implementation. Likewise, the upstream-recommended no-op `evolve` fallback can conceal an invalid historical sequence; retain total reducers if desired, but add a replay auditor that identifies impossible transitions and fails promotion ([D/src/Aggregate.ts:151–162](~/YeeBois/references/effect/alchemy/packages/domain/src/Aggregate.ts:151), [P/party/model/src/Claim/Claim.aggregate.ts:101–139](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/Claim.aggregate.ts:101)).

## Missing

These are missing production contracts, not reasons to preserve the current architecture.

- **Durable compatibility and upgrade admission.** Define the persisted formats, writer/readers allowed to coexist, schema generations, old-binary fencing, rollback after new writes, and how in-flight workflows are continued. Event decoding alone does not cover persisted state and receipts, as shown above ([D/src/Kernel.ts:1100–1102](~/YeeBois/references/effect/alchemy/packages/domain/src/Kernel.ts:1100), [D/src/Kernel.ts:1616–1637](~/YeeBois/references/effect/alchemy/packages/domain/src/Kernel.ts:1616)).
- **Backup and verified reconstruction.** Specify restore of event logs, receipts, schedules, workflow state, deferred signals and referenced blobs as one recoverable system. Prove rebuild equality, recovery-point boundaries and which external operations require reconciliation. “Own no driver” must not mean “nobody owns restoration.”
- **Replay modes and side-effect suppression.** Separate rebuilding read models from replaying business policies and invoking external systems. Define deployment/backfill generations and audit replay manifests. Upstream already exposes generation-aware backfill concepts; the architecture should assign their operation rather than ignore them ([D/src/Backfill.ts:1–28](~/YeeBois/references/effect/alchemy/packages/domain/src/Backfill.ts:1), [D/src/Backfill.ts:75–97](~/YeeBois/references/effect/alchemy/packages/domain/src/Backfill.ts:75)).
- **Durable integration subscriptions.** Define published integration-event schemas, tenant scopes, key discovery, consumer identity, source incarnation, cursor persistence, retention gaps, bootstrap and catch-up. `stream:seq` alone needs a source namespace and reset/generation contract. Api Stream subscription is a transport surface, not this whole protocol ([P/PROPOSAL.md:843–848](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/PROPOSAL.md:843), [D/src/DurableObjects.ts:1477–1508](~/YeeBois/references/effect/alchemy/packages/domain/src/DurableObjects.ts:1477)).
- **Privacy and data lineage.** The proposed “IDs only for deletable data” rule is contradicted by the prototype: ClaimAsserted stores evidence excerpts, and PartyRegistered stores a person's name ([P/PROPOSAL.md:939–941](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/PROPOSAL.md:939), [P/party/model/src/Claim/AssertClaim.command.ts:29–33](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Claim/AssertClaim.command.ts:29), [P/party/model/src/Evidence.ts:17](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Evidence.ts:17), [P/party/model/src/Party/Party.aggregate.ts:44–47](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/model/src/Party/Party.aggregate.ts:44)). Define retained factual content versus erasable payload, deletion of copies/caches/backups, and what replay does when a referenced payload is gone. An ID can itself remain identifying; indirection does not settle retention policy.
- **Authority lifecycle and administrative access.** Include delegated capability scope, expiry, revocation epochs, scheduled-command authority, subscription revocation, emergency suspension, operator repair rights and cross-context identity translation. Model names and separate entity IDs are storage addressing, not tenant access control ([D/src/EffectCluster/index.ts:591–615](~/YeeBois/references/effect/alchemy/packages/domain/src/EffectCluster/index.ts:591)).
- **Delivery and failure budgets.** Define bounded inboxes, payload limits, hot-key behavior, deadlines, cancellation, retry limits, poison-message isolation, stuck-consumer repair and fencing for old workers. “A job must finish” is not a timeout or recovery specification.
- **Operational evidence.** Define correlation from command to event to policy to workflow to external operation, metrics for lag and age, receipt inspection, safe repair commands and who owns each alarm. Preserve traces without treating them as the durable business audit.
- **Version conflict and intent preconditions.** Define how a caller says “apply to the revision I reviewed,” which inputs are recomputed on retry, and when stale work is rejected. Serialization of an aggregate does not by itself protect a user's stale intent.
- **Actual acceptance gates.** The present proof is in-memory and in-process. Add crash-boundary tests, concurrent ownership tests, restored-state tests, wire codec tests and authenticated streaming revocation tests. Keep runtime/backend conformance separate from story correctness ([P/party/host/test/ReviewerApi.test.ts:15–34](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/party/host/test/ReviewerApi.test.ts:15), [P/README.md:3–6](~/YeeBois/projects/beep-effect/scratchpad/model-first-slices/README.md:3)).

## Ideas beyond the proposal

1. **Make an operation contract the unit agents consume.** Generate an agent-facing catalog with semantic purpose, actor requirements, affected invariant, idempotency scope, expected precondition, durable receipt, observable completion condition and recovery action. A description and a schema tell an agent how to call; this tells it how to know the job is done.
2. **Introduce a capability-bearing execution context separate from Actor.** Preserve actor attribution as a stable fact; authorize with bounded, authenticated authority. Record initiation, delegation and execution separately. Long-running work should re-establish authority at the specified boundary rather than impersonate a historical session.
3. **Use an approval aggregate, not a raw workflow signal, for consequential agent actions.** A proposal becomes a versioned artifact. Approval binds principal, proposal digest, evidence revision, scope and expiry. The workflow consumes that committed fact. Cancellation and supersession become domain operations that both humans and agents can inspect.
4. **Treat effects as obligations with receipts.** Before an external mutation, persist intent plus an idempotency key. Afterwards attach the provider's evidence. On uncertainty, reconcile the obligation. Expose this state to operators; do not collapse “accepted by us,” “sent,” “provider completed” and “read model caught up.” This complements Cluster rather than replacing it.
5. **Specify a backend conformance suite before choosing the host.** The same model should survive duplicate sends, kill-after-commit, lost response, projection crash, alarm redelivery, migration, restoration and authority revocation. Run the suite for PostgreSQL and each intended Durable Object implementation. A backend earns portability by satisfying the same behavioral contract.
6. **Generate contracts for clients, an executable model for trusted reasoning, and a deployment inventory for operators.** These are three different artifacts. They may share one source model without sharing all executable imports. Keep React screens typed against the first; let agent test tools deliberately load the second; let operations use the third.
7. **Replace a blanket “laws” heading with a proof inventory.** For each invariant record its checker, assumptions, counterexamples, evidence artifact and remaining human judgment. Add property-based command sequences and mutation testing: can the suite catch removal of the membership check or corruption of a checkpoint? Those are stronger agent feedback loops than counting story tags.
8. **Publish integration facts intentionally.** A bounded context should choose a stable downstream language rather than expose whichever internal view events happen to exist. Consumer-owned ExternalSystems remain the right inbound dependency boundary. Use separate integration feeds and acknowledgement semantics where a downstream process needs durable catch-up.
9. **Make simulation explicitly non-authoritative.** Agents can evaluate proposed command sequences against a versioned snapshot and report expected events. The real command still names its preconditions and goes through authoritative execution. Never treat a browser-imported `decide` result as authorization or a successful write.
10. **Create an operations Api alongside user and agent Apis.** Define typed commands for pause, inspect, reconcile, retry, rebuild and retire, each with explicit authority and receipts. An agent-operated system needs controlled recovery verbs as much as business verbs.

## Questions for the owner

1. **What are the first hard invariants?** For Party, must merges be acyclic, single-owner, tenant-local and irreversible, and what exact state means “merged”? Select those before finalizing aggregate boundaries.
2. **Where is authoritative permission decided, including cached receipts?** What can an agent do for a person, what may a System process do, and what happens after revocation to retries, queued commands, subscriptions and approvals?
3. **What is the supported durable compatibility contract?** Which historic event/state/context/workflow/reply formats must load, how are old writers fenced, and what constitutes a valid rollback after new writes?
4. **Which hosting implementation is the initial acceptance target?** Choose Alchemy Cluster on PostgreSQL, Alchemy DurableObjectPool, or Effect's Cloudflare integration; name the crash/recovery/portability tests it must pass. Keeping Cluster is already settled.
5. **Which operations need durable human approval and uncertain-outcome reconciliation?** Must approval bind evidence/proposal revision, can it expire, and who may cancel or supersede an agent run?
6. **What may an event retain permanently?** Decide how names, excerpts, principal IDs and model-run data relate to erasable stores, backups and replay.
7. **What are the idempotency and projection contracts?** Define key namespace, request-fingerprint conflicts, cached-result access, sink checkpoints, projection generations and the authoritative cursor for each integration consumer.
8. **Are model source and executable decision rules intentionally shipped to browsers and other contexts?** If not, authorize a generated contract boundary. Do not lock a package count before answering this.
9. **Does one bounded context have to equal one Model, or is Model a composition unit?** Choose based on language and invariant ownership; explicitly reject context-window size as a semantic boundary test.
10. **What exact evidence permits replacing the current driver and standard?** Require adversarial runtime proof and restored-data proof, not just six passing in-memory tests; specify who accepts each result and retains the evidence.
