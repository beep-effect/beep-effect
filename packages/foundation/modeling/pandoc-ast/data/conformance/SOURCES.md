# Pandoc conformance sources

This package separates the Pandoc JSON data model, command-line behavior,
informative filter documentation, and package-owned compatibility policy.

- `pandoc-types` `1.23.1` `Definition.hs` is the approved upstream authority for
  the constructor universe used by the `pandoc-json-1.23.1` profile.
- Pandoc `3.10.2` `MANUAL.txt` is the official behavior reference for the
  selected CLI profile. Most reader, writer, extension, and executable-filter
  behavior is intentionally outside this pure modeling package.
- The filters and Lua filters pages are informative snapshots. They do not
  override the pinned data model.
- The pinned constructor registry and semantic AST are immutable package-reviewed
  implementation baselines. The registry is hand-maintained and has not yet been
  generated from the approved `Definition.hs` bytes.
- The pinned JSON fixtures are immutable package-authored smoke-fixture baselines, not
  output proven to have been generated by the pinned Pandoc executable.

Strict and lossless profiles have different obligations. Strict decoding
models every current pandoc-types 1.23.1 inline and block constructor, rejects
malformed payloads and known constructors used in the wrong structural slot,
and preserves names unknown to the pinned registry through explicit future
lanes without claiming upstream validity. Lossless
decoding retains exact future and malformed wire with issues. Mapping to
`@beep/md` is a third, explicitly lossy compatibility profile.

Normal package tests must remain offline and must not require a local `pandoc`
executable. A future fixture refresh may invoke the pinned executable in a
separate networked/tooling workflow and commit byte-hashed outputs with exact
command provenance.

Every source, profile, and invariant entry decodes directly as the shared
`SpecificationSource`, `ConformanceProfile`, or `InvariantDescriptor` schema
from `@beep/schema/Conformance`. The official filter pages are `bestPractice`
evidence; package registries, models, and fixtures are
`implementationReference` evidence and are not normative Pandoc authority.
Package-local inventory and coverage fields remain outside those shared
entries. Final implementation provenance is supplied by the eventual Git commit and
pull request; these ledgers do not guess a digest for the dirty working tree or
create a self-referential final-tree hash requirement.
