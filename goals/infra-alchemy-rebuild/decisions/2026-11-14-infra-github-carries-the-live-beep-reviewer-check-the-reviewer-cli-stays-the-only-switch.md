Window-5 requirement 2 (window-5 owner via the packet gate, 2026-11-14) asked for one of: (a) the stack does not own the `beep-reviewer` required check, or (b) it reads the live state of that check and carries it through unchanged. Chosen: (b). `GitHub.Ruleset` writes the ruleset as a whole body, so (a), leaving the check out of the body, would delete it on every deploy; carrying it is what the resource model supports cleanly. The workflow captures ruleset 10240248 once (`gh api repos/beep-effect/beep-effect/rulesets/10240248`) and hands the file to the stack as `INFRA_GITHUB_LIVE_RULESET`; `liveReviewerCheck` reads the `beep-reviewer` entry with its App binding and `requiredChecks` appends it after the 15 configured checks, where `beep reviewer ruleset require` puts it. Stack tests prove a live check survives a deploy present (bound to App 5321138) and absent. This supersedes the implementation of the packet-gate ruling 'beep reviewer ruleset edits the stack configuration once the stack is armed' (2026-11-13): with the live check carried, a committed `reviewerCheck` would be ignored and an armed CLI that edits it would silently do nothing, so the committed flag is removed and `beep reviewer ruleset release|require` keeps its direct edit of the live ruleset in every state, which is the hazard that ruling guarded against now closed by the carry. The ruling's goal holds: no deploy can undo the operator's switch. Closing the capture-to-write window (window-5 owner via the packet gate, 2026-11-14): the body is built from a capture, so a `release` or `require --apply` landing between capture and write would be overwritten. Built in the provider, not as a workflow step: `src/RulesetWriteGuard.ts` registers a provider for `GitHub.Ruleset` directly (a direct registration takes precedence over the `GitHub.providers()` collection) that wraps the shipped `RulesetProvider`. For the ruleset named like the capture, its `reconcile` re-reads ruleset 10240248 through the same distilled client, decodes it with the guard's strict decoder, compares it with the capture over the guard's server-fields-excluded fields, and fails with `RulesetChangedSinceCapture` before the PUT if anything differs, so the gap is one API round-trip. A capture without an id fails closed (`CaptureWithoutId`). Tests (`test/RulesetWriteGuard.test.ts`): live equal to the capture writes (one PUT); `beep-reviewer` required, or released, after the capture refuses and sends no PUT. The runbook states that the switch is not flipped while a `Deploy infra-github` run is in progress and that a refused run is re-run with a fresh capture. `deploy-infra-github.yml` is unchanged by this. Exact guarantee (beep-reviewer round 2, 2026-11-14): the write guard closes the capture-to-PUT window except for the single GET-to-PUT round-trip; a switch flipped inside that round-trip is overwritten and not detected; the post-deploy check fails when the ruleset differs from what the deploy wrote, which means it moved after the write and nothing was undone. Window-5 owner ruling (2026-11-14): the write guard plus the runbook practice (the switch is not flipped while a `Deploy infra-github` run is in progress, with the recovery read-and-re-apply after any overlapping run) is sufficient for arming; no conditional update or further deploy-side refusal is required. Later improvement, not built: GitHub's ruleset `PUT /repos/{owner}/{repo}/rulesets/{ruleset_id}` documents no `If-Match` or other precondition parameter (checked in the REST API description, 2026-11-14), and the ruleset GET returns only a weak `ETag` meant for conditional GETs (`If-None-Match`, 304); if GitHub ever honours a precondition on the PUT, the wrapped provider could send it and close the round-trip.
