### New or changed resources

- **`Cloudflare.Telemetry()`** — Layer that sends Effect spans from a Worker to Workers Observability. Provide it on the Worker; `Effect.withSpan` frames show up in the Cloudflare dashboard, nested under the platform’s own spans. No OTLP endpoint and nothing to flush. Composes with `Axiom.Telemetry` for the same waterfall in both. The Worker’s compatibility date must be `2026-07-28` or later (#1444). https://alchemy.run/blog/2026-09-08-beta-77/
- **`Cloudflare.Worker`** — shown both as `class Api extends Cloudflare.Worker<Api>()("Api", { main: import.meta.url }, …)` (KV + R2 dev stack) and as `Cloudflare.Worker("Api", { main: import.meta.url }, …)` (telemetry example). https://alchemy.run/blog/2026-09-08-beta-77/
- **`Cloudflare.KV.ReadWriteNamespace`** — the dev-stack example binds a KV namespace (`Visits`). https://alchemy.run/blog/2026-09-08-beta-77/
- **`Cloudflare.R2.ReadWriteBucket`** — the dev-stack example binds an R2 bucket (`Uploads`). https://alchemy.run/blog/2026-09-08-beta-77/
- **`Cloudflare.KV.ReadWriteNamespaceBinding`** and **`Cloudflare.R2.ReadWriteBucketBinding`** — provided on that Worker via `Effect.provide`. https://alchemy.run/blog/2026-09-08-beta-77/
- **Cloudflare Workflows `schedules`** — wrangler-compatible `schedules`, so a cron expression creates instances natively. The post says this replaces a Cron Trigger Worker calling `workflow.create()` (#1491). Sample: `class Hourly extends Cloudflare.Workflow<Hourly>()("Hourly", { schedules: ["0 * * * *"] }, …)`. https://alchemy.run/blog/2026-09-08-beta-77/
- **`Cloudflare.Workflows.WorkflowEvent`** — yielded inside the workflow; the sample returns `event.schedule?.cron`. https://alchemy.run/blog/2026-09-08-beta-77/
- **`AWS.ElastiCache.SubnetGroup`** — added on `AWS.ElastiCache` alongside the serverless cache (#1422). No prop list is shown. Thanks Henning Pokriefke (`henningpokriefke`). https://alchemy.run/blog/2026-09-08-beta-77/
- **`AWS.ElastiCache.ReplicationGroup`** — Valkey and Redis OSS (#1422). Sample props: `engine: "valkey"`, `nodeType: "cache.t4g.micro"`, `subnetGroupName`, `securityGroupIds`, `replicasPerNodeGroup: 1`, `automaticFailoverEnabled: true`. https://alchemy.run/blog/2026-09-08-beta-77/
- **`AWS.ElastiCache.CacheCluster`** — Memcached (#1422). No prop list is shown. https://alchemy.run/blog/2026-09-08-beta-77/
- **`AWS.ElastiCache` `Connect*` bindings** — “publish the endpoint to a Lambda and attach it to the cache’s VPC” (#1422). The only binding the code names is **`AWS.ElastiCache.ConnectReplicationGroup`**, with `subnetIds` and `securityGroupIds`. The comment in the sample is “inside the Lambda: endpoint env + VPC attachment”. https://alchemy.run/blog/2026-09-08-beta-77/
- **`Railway.Service`** — three additions, all from Dallen Pyrah (`dallenpyrah`) (#1439, #1438, #1440). The post does not map each PR to one addition. Props shown: `project`, `context: "./worker"` (“build from a local directory”), `preDeploy: { command: "bun migrate" }` (“runs between build and start”), `publicDomain: false` (“`{name}.railway.internal` only”). https://alchemy.run/blog/2026-09-08-beta-77/

### Migration notes

- **Keep an old stage** — “Pass `--stage dev_sam` to keep deploying to an old target.” https://alchemy.run/blog/2026-09-08-beta-77/
- **Rename `STAGE` to `ALCHEMY_STAGE`** (#1433). https://alchemy.run/blog/2026-09-08-beta-77/

- **Profile on-disk layout** (#1429) — “the central `profiles.json` and the separate `credentials/` tree are gone. A profile is a directory and each provider is one file holding its method, config, and credentials together.” “Existing installs migrate on first run, with the old layout backed up to `~/.alchemy/.profiles-v0-<timestamp>/`.” The tree the post prints: https://alchemy.run/blog/2026-09-08-beta-77/

```text
~/.alchemy/profiles/
├─ default/
│  ├─ cloudflare.json   # method: oauth, accountId, tokens, scopes
│  └─ aws.json          # method: sso, ssoProfile
└─ work/
   └─ cloudflare.json   # method: stored, apiToken, accountId
```

- **Distilled call sites** — replace `railway.serviceCreate` with `railway.createService` if you call a distilled client directly (#1517). https://alchemy.run/blog/2026-09-08-beta-77/
- **Drop the AWS `local` auth method** (#1480). Local emulation is `alchemy dev`’s job. https://alchemy.run/blog/2026-09-08-beta-77/
- **Workers tracing** — set the Worker compatibility date to `2026-07-28` or later before `Cloudflare.Telemetry()`. https://alchemy.run/blog/2026-09-08-beta-77/

### Tips and tricks

- Git: “You build the HTTP server and mount `alchemy/Git`’s routes into it.” “The engine itself holds no users, no credentials, and no policy.” https://alchemy.run/blog/2026-09-17-beta-78/
- “Because the handlers are yours to call, a route can be overridden with a few lines of application code.” The `receivePack` sample reuses `defaults.protocol.infoRefs` and `uploadPack` and wraps the push. https://alchemy.run/blog/2026-09-17-beta-78/

- “Not a GitHub replacement. No issues, reviews, or Actions.” https://alchemy.run/blog/2026-09-17-beta-78/
- **Clone path:** “After every push the repository writes a ready-to-serve bundle to R2, and a `git clone` is the Worker streaming that file to the client. The Durable Object is not involved, so the number of concurrent clones a repository can serve is limited by R2 and Workers, not by one object.” https://alchemy.run/blog/2026-09-17-beta-78/
- **Benchmark** (real `git`, same client and edge, “a 36 MiB, 15.6k-object repository, a fresh repository on each host”): “GitHub’s throughput is the pack size divided by its clone time”; “the incremental fetch is a `git fetch` with one new commit.” “Four clones at once reached 93 MiB/s aggregate.” “Everyday pushes, which move a few commits, are faster than GitHub; incremental fetches are about even. Large pushes are the one place GitHub is ahead.” https://alchemy.run/blog/2026-09-17-beta-78/
- **Largest real push:** “the alchemy monorepo, 44k objects in a 67 MiB pack, hosted on git.alchemy.run and cloned back byte-identical under `git fsck --strict`.” https://alchemy.run/blog/2026-09-17-beta-78/
- **Hashing:** “Before a ref moves, every object in a push is inflated, SHA-1 hashed, and delta-resolved.” “A Worker’s CPU is slow for exactly this kind of work — tight loops over bytes, inflate, and hashing run several times slower than on a laptop — and there is one thread to run it on: a service binding call executes on the caller’s thread, so fanning out to another Worker buys nothing.” https://alchemy.run/blog/2026-09-17-beta-78/
- **`HasherInline`:** “The first version hashed on the request thread and took 10–13 seconds for the 40 MiB push.” https://alchemy.run/blog/2026-09-17-beta-78/
- **`HasherWorkerLoader`:** “bundles the hasher as a module inside your Worker and loads it into four fresh isolates per push, each with its own 128 MB and its own thread. Nothing new is deployed, nothing leaves Cloudflare, and the same push drops to 5.9–6.5 seconds.” https://alchemy.run/blog/2026-09-17-beta-78/
- **`HasherLambda`:** “one Lambda invocation per chunk, all at once, on a 3 GB function — for pushes wider than four chunks when an AWS account is already in the stack.” https://alchemy.run/blog/2026-09-17-beta-78/

- An embeddable git remote: smart HTTP, a typed REST plane with pull requests, and GitHub REST v3 so `gh api` and Octokit work unchanged, with auth left to your `HttpApiMiddleware` (“the engine itself holds no users, no credentials, and no policy”). https://alchemy.run/blog/2026-09-17-beta-78/
