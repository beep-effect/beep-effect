# Reflection — ci-fleet-endgame (2026-08-10, claude)

## Summary

P1 delivered and proved the shadow one-job-one-VM fleet. Probe `31352410248`
demonstrated a 90-second birth-to-death lifecycle with 10-second teardown lag,
and red-team run `31354960508` passed all three live trust gates. Reaching that
proof required unwinding three stacked defects introduced while adapting the
module to reuse assumptions from the manual burst fleet.

## Tooling experience

- **Worked:** VPC flow logs supplied the decisive localization signal when the
  worker itself supplied no logs. Sustained HTTPS to S3 and SSM, with zero
  packets to GitHub, proved config fetch succeeded and narrowed the third
  failure to the interval before agent start.
- **Didn't:** `enable_cloudwatch_agent: false` left no readable worker log,
  `get-console-output` returned empty, and each failed worker self-terminated
  before inspection.
- **Frustrating:** All three defects presented as the same symptom: a runner
  registered `offline`, then vanished roughly five minutes later. Each fix
  merely uncovered the next defect in the stack.
- **Wished existed:** A durable early-boot timeline covering launch authority,
  user-data execution, config fetch, runtime-user selection, and GitHub agent
  registration.

## Implementation improvement opportunities

- Validate the permissions boundary against the module's actual runner-role
  path. The boundary allowed `iam:PassRole` on `*gha*`, while the module created
  `beep-ci/beep-ci-runner-*`; nothing could launch, and one probe remained
  queued for roughly 20 hours.
- Treat AMI, package manager, and runtime user as one compatibility unit. The
  controller inherited the burst fleet's Ubuntu AMI under a `dnf`-only
  user-data template, then retained `runner_run_as: ubuntu` after moving to an
  image whose only user was `ec2-user`.
- Keep fleet resolution independent. Reusing `stack.resolvedAmiId` coupled two
  fleets that had no reason to share an operating system.

## Goal & prompt critique

The packet correctly demanded live lifecycle and red-team evidence, but its P1
acceptance path should have named four separate preflights: PassRole against the
resolved role ARN, user-data compatibility with the resolved AMI, existence of
`runner_run_as`, and outbound contact with GitHub. That matrix would have made
the stacked failures distinguishable before a dispatched probe.

## TODOs worth codifying

- Make a readable early-boot failure channel part of the ephemeral-runner
  deployment contract.
- Add a fleet-local AMI/package-manager/runtime-user compatibility check.
- Document flow-log localization for workers that terminate before emitting a
  readable log.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Do not reuse a sibling fleet's resolved AMI merely
  because both fleets run CI; resolve the OS from each fleet's own user-data and
  runtime-user contract.
- **MEDIUM — Best practice:** When several failures share one external symptom,
  test the launch path boundary by boundary instead of treating the latest fix
  as completion.
- **LOW — Consideration:** VPC flow logs are coarse, but the presence of S3/SSM
  traffic and absence of GitHub traffic can still localize a boot failure when
  every application-level log surface is gone.
