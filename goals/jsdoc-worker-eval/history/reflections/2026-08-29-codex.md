# Reflection — jsdoc-worker-eval (2026-08-29, codex)

## Summary

The packet proved a read-only worker path with a hosted three-packet baseline,
a Runpod smoke, and a reproducible ten-packet Runpod sample. The evidence
supports candidate generation, not automatic remediation.

## Tooling experience

- **Worked:** Explicit provider/model selection, saved input reports, ephemeral
  Runpod cleanup, and Phoenix spans made the remote evaluation reproducible.
- **Didn't:** The 30B local model did not fit the interactive workstation and
  ran CPU-only.
- **Frustrating:** Cold pod and Ollama model pulls dominated the remote loop.
- **Wished existed:** A prebuilt cached worker image and an automated evaluator
  for policy preservation across candidate drafts.

## Implementation improvement opportunities

- Keep deterministic docgen findings authoritative and require human acceptance
  for every worker draft until quality thresholds are defined and met.

## Goal & prompt critique

The goal should separate transport proof from draft-quality graduation and name
the minimum precision, cost, runtime, and policy-preservation evidence required
before write mode can be considered.

## TODOs worth codifying

- Standardize a read-only model-evaluation rubric with explicit host-fit and
  write-graduation thresholds.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Do not make model output the policy source of truth —
  candidate drafts still contained deterministic policy misses.
- **MEDIUM — Best practice:** Match model size to the selected host — CPU
  fallback can invalidate an interactive evaluation.
- **LOW — Consideration:** Cache remote model images — startup dominated a
  bounded sample more than packet execution did.
