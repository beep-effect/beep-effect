# Reflection — practice-m365-contacts (2026-10-13, codex)

## Summary

The driver contact surface and CSV-only seeding job are delivered. Live execution
resolved all 480 identifiable CSV contacts already present in the scoped mailbox,
created zero contacts, and proved rollback on a persisted empty journal. The
contacts-only smoke created and deleted its one synthetic contact.

## Tooling experience

- **Worked:** Schema-first journals, the existing normalizer, injected mailbox
  fixtures, beep-heavy, and count-only CLI reports kept private data out of evidence.
- **Didn't:** Full app package proof stopped upstream on unchanged Box TS2589.
  Direct app qualification establishes its own behavior separately; S11 owns
  the inherited dependency failure and global JSDoc totals.
- **Frustrating:** Shared admission delayed both the propagation probe and live
  smoke. Submitted time and admitted time need separate receipts.
- **Wished existed:** A package report that clearly marks dependency-build failure
  before a touched package audit, instead of presenting it as an app failure.

## Implementation improvement opportunities

The zero-create path now saves an apply receipt and discovers an existing folder
without creating one. Empty-run undo saves a receipt without deleting contacts
or folders. Missing journals and pending ambiguous creates remain typed failures.
Synthetic tests cover absent and present folders, persistence, no-op undo and
unfinished creates. Fallow identified added undo complexity; extracting journal
selection keeps the same behavior without a suppression or baseline change.

## Goal & prompt critique

Replace a blanket dedicated-folder population requirement with mailbox-wide
resolution plus dedicated-folder creates for missing contacts. Require zero-create
journals from the start. Keep the CSV-only source and never tag existing contacts
merely to manufacture rollback evidence. The explicit Run 4 ruling resolves
these cases; earlier handoff sections retain the original stop assessment.

## TODOs worth codifying

- Require durable receipts for every executed reconciliation run, including no-ops.
- Record heavy submission and admission times independently of permission-cache
  deadlines; preserve terminal receipts instead of rerunning passed proofs.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Preserve existing mailbox contacts across the entire
  folder inventory; a dedicated folder never justifies creating duplicates.
- **HIGH — Critical:** A no-op execution still needs a durable journal and
  rollback receipt. Do not mistake an unfinished ambiguous write for a no-op.
- **MEDIUM — Best practice:** Attribute global gate reds by changed source and
  generated findings, and report direct package qualification separately.
- **LOW — Consideration:** A dedicated no-op status could improve CLI readability;
  current counts and receipts already prove the outcome without another state.
