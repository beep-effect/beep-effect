The pool's later worker-stop operation is started without awaiting it before scheduling the next file (`cli-api.CnMVyzaz.js:3547–3559`), so merely having a lingering OS child after acknowledged completion is a weaker explanation for this mid-run boundary. Start/stop watchdogs (60/90s startup; default 10s teardown warning) are distinct from the unbounded execution-result wait. No actual stuck RPC, leaked handle, or worker stack has been observed.

Ordinary async assertions should encounter their timeout; >30 minutes of silence alone does not identify a test failure.
