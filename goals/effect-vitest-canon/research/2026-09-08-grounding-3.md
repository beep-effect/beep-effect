## 2. Timeouts (4.1.11)

### 2.1 Config defaults (**verified** tagged docs + `resolveConfig.ts`)

From tagged `docs/config/testtimeout.md` / `hooktimeout.md` / `teardowntimeout.md` and `packages/vitest/src/node/config/resolveConfig.ts` (near the end: `resolved.testTimeout ??= resolved.browser.enabled ? 15_000 : 5_000` and `resolved.hookTimeout ??= resolved.browser.enabled ? 30_000 : 10_000`):

| Knob | Type | Default (Node, no browser) | Default (`browser.enabled`) | CLI | `0` means |
| --- | --- | --- | --- | --- | --- |
| `testTimeout` | number (ms) | 5_000 | 15_000 | `--test-timeout` / `--testTimeout` | disable test timeout |
| `hookTimeout` | number (ms) | 10_000 | 30_000 | `--hook-timeout` / `--hookTimeout` | disable hook timeout |
| `teardownTimeout` | number (ms) | 10_000 | 10_000 | `--teardown-timeout` / `--teardownTimeout` | wait-for-close on shutdown, not per-test |

This repo overrides both (`vitest.shared.ts` 128–129) to 30s / 10s, or 300s / 300s under coverage or deep FC sweeps. A wrapper that assumes Vitest's 5s default will be wrong here.

`expect.poll` has a separate default timeout of 1_000 ms (`--expect.poll.timeout`). `vi.waitFor` / `vi.waitUntil` default to 1_000 ms in tagged `docs/api/vi.md`. Those are **not** `testTimeout`.

### 2.2 Per-test effective timeout (**verified** `suite.ts`)

When a test is collected:

```ts
const timeout = options.timeout ?? runner.config.testTimeout
```

Then `task.timeout = timeout` and the handler is wrapped with `withTimeout(..., timeout, false, ...)`.

Override order (**verified**):

1. `runner.config.testTimeout` (config + CLI + `vi.setConfig`).
2. Tag options from `test.tags` merged in priority order (4.1 feature).
3. Suite `describe(..., { timeout })` inherited via `Object.assign({}, suiteOptions, options)`.
4. Per-test `{ timeout }` or third-argument number, which wins.

`TestOptions.timeout` is documented in tagged `docs/api/test.md` as milliseconds, default `5_000` (configured by `testTimeout`). Third-argument timeout cannot be combined with an options object (Vitest 4 removed `test(name, fn, { ... })`).

`timeout: 0` or `Number.POSITIVE_INFINITY` skips the wrapper (`withTimeout` returns `fn` unchanged). **inference:** a watchdog that treats `0` as "5 seconds" would be wrong.

### 2.3 Hook timeouts (**verified** tagged `docs/api/hooks.md` + `context.ts`)

`beforeEach` / `afterEach` / `beforeAll` / `afterAll` / `aroundEach` / `aroundAll` take an optional timeout as the last argument. Default is `hookTimeout` (10s Node). `aroundEach` / `aroundAll` apply that timeout independently to setup (before `runTest`/`runSuite`) and teardown (after).

`onTestFinished` / `onTestFailed` callbacks are wrapped with `withTimeout(handler, timeout ?? runner.config.hookTimeout, true, ...)`.

Timeout error text (**verified** `makeTimeoutError` in `context.ts`):

- Test: `Test timed out in ${timeout}ms.\nIf this is a long-running test, pass a timeout value as the last argument or configure it globally with "testTimeout".`
- Hook: same pattern with `Hook` / `hookTimeout`.

On timeout, `abortIfTimeout` aborts `ctx.signal` with that error.

### 2.4 How `@effect/vitest` maps timeouts (**verified** tag snapshot + installed dist)

`~/.cache/beep/effect-vitest-canon/effect-rc112/packages/vitest/src/internal/internal.ts` (same text as `node_modules/@effect/vitest/src/internal/internal.ts` and `dist/internal/internal.js`):

- `testOptions(timeout)`: a number becomes `{ timeout }`; an object is passed through; `undefined` becomes `{}`.
- Every `it.effect` / `it.live` / `it.prop` / tester method forwards that to Vitest `it(name, testOptions(timeout), (ctx) => ...)`.
- `it.layer(..., { timeout })` is **not** a test timeout. `hookTimeout(options?.timeout)` converts `Duration.Input` to milliseconds and passes it as the last argument to `beforeAll` / `afterAll` / `beforeEach`. If omitted, the argument is `undefined` and Vitest uses config `hookTimeout`.
- Named `it.layer(L)("name", f)` uses `beforeAll` + `afterAll` (hook timeout).
- Unnamed `it.layer(L)(f)` uses `beforeEach` to run the cached build on the first block test and `afterAll` as a fallback closer. The first test's JSON `duration` therefore includes layer build time (**inference** from `run.ts` including `beforeEach` in test duration + unnamed-form `beforeEach` in `internal.ts` 298–312).
- `runPromise` calls `Effect.runPromise(effect, { signal: ctx?.signal })`. Vitest timeout therefore interrupts the Effect.

Contract D14 / EV014 (`{ timeout: "30 seconds" }` on container layers) is a **hook** timeout, because layer build/teardown runs in vitest hooks. It does not change `ctx.task.timeout` for inner `it.effect` tests.

### 2.5 Clocks used by the runner (**verified** `run.ts` + `context.ts`)

```ts
const now = globalThis.performance ? globalThis.performance.now.bind(globalThis.performance) : Date.now
const unixNow = Date.now
```

- Timeout guard (`withTimeout`): monotonic `performance.now()` plus `setTimeout`.
- `task.result.startTime`: `unixNow()` (Unix ms).
- `task.result.duration`: `now() - start` (monotonic ms), spanning `aroundEach` + `beforeEach` + body + `afterEach` + `onTestFinished` + aroundEach teardown. **Does not** include `beforeAll` / `afterAll`.
- JSON file `endTime` is `max(startTime + duration)`: Unix start plus monotonic duration. **inference:** clock jumps can skew file `endTime`; per-test `duration` is the timing field to trust.

PR #9795 (`performance.now` for timeout guard) is on `main` (merged 2026-03-10). **Not verified** as present-or-absent as a delta inside 4.1.11 beyond reading 4.1.11 `context.ts`, which already uses `performance.now` for `withTimeout`. Treat 4.1.11 as already monotonic for the timeout guard.

`runner._currentTaskStartTime` / `runner._currentTaskTimeout` are written by `withTimeout`. They are **not** on the public `VitestRunner` type. Issue #9751 (2026-02-26, open as of the search snippet) notes they sit on a singleton and concurrent tests overwrite them. This repo sets `sequence.concurrent: true`. **Do not read those fields.**

## 3. JSON reporter (4.1.11)

Source of truth: tagged `packages/vitest/src/node/reporters/json.ts`. Compatible with Jest `--json`, with commented-out Jest fields never emitted (`numRuntimeErrorTestSuites`, `wasInterrupted`, per-file `summary` / `coverage`).

### 3.1 How to write a file (**verified**)

```bash
bunx vitest run --reporter=json --outputFile=<abs-path>
```

That is the packet P1 command and is correct for 4.1.11. `outputFile` may also be `{ json: '<path>' }` when combining reporters. Reporter-option `outputFile` wins over top-level.

Without `--outputFile` on 4.1.11, JSON goes to the terminal. Prefer `--reporter=json --reporter=default --outputFile=...` if humans still need the default summary.

`getOutputFile` (**verified** tagged `packages/vitest/src/utils/config-helpers.ts`): string `outputFile` is used as-is; object form picks `outputFile.json`.

### 3.2 Root object `JsonTestResults`

| Field | Meaning (verified) | Limitation |
| --- | --- | --- |
| `numTotalTestSuites` | `getSuites(files).length` | suites, not files |
| `numFailedTestSuites` | suites with `result.state === 'fail'` | |
| `numPendingTestSuites` | suites `run` / `queued` / `mode === 'todo'` | name says pending; includes todo |
| `numPassedTestSuites` | total − failed − pending | not an independent count |
| `numTotalTests` | `getTests(files).length` | includes skip/todo |
| `numPassedTests` | `result.state === 'pass'` | |
| `numFailedTests` | `result.state === 'fail'` | |
| `numPendingTests` | `run` / `queued` / `mode === 'skip'` / `result.state === 'skip'` | **includes skipped tests**, not only in-flight |
| `numTodoTests` | `mode === 'todo'` | |
| `startTime` | `Date.now()` in `onInit` | reporter start, not first test |
| `success` | `(files.length > 0 \|\| passWithNoTests) && no failed suites && no failed tests` | empty project is failure unless `passWithNoTests` |
| `testResults` | one entry per **file** | not per suite |
| `snapshot` | `ctx.snapshot.summary` | present in source; omitted from the docs example |
| `coverageMap` | set only via `onCoverage` | empty/`{}` in the docs example; filled since Vitest 3 when coverage is on |

**There is no root `duration` / `totalMs`.** Packet §5.4 `totalMs` must be derived (see §4).

### 3.3 Per-file `JsonTestResult`

| Field | Meaning | Limitation |
| --- | --- | --- |
| `name` | `file.filepath` (absolute) | not package-relative |
| `status` | `'failed'` if file `result.state === 'fail'` **or** any test `fail`; else `'passed'` | skipped-only files are `'passed'` |
| `message` | first file-level error message or `''` | not a concat of test failures |
| `startTime` | min of test `result.startTime`, or reporter `start` if none | Unix ms |
| `endTime` | max of `startTime + duration` | mixes Unix start with monotonic duration |
| `assertionResults` | every test in the file, including skip/todo | name is Jest-speak; these are tests, not `expect()` calls |

File collect / setup / transform / environment times exist on the runner `File` task (`collectDuration`, `setupDuration`, `importDurations`) but **are not copied into JSON**. Default-reporter `Duration 1.26s (transform … collect … tests …)` cannot be reconstructed from this reporter.

### 3.4 Per-test `JsonAssertionResult`

| Field | Meaning | Limitation |
| --- | --- | --- |
| `title` | `t.name` | the `it` / `it.effect` name only |
| `ancestorTitles` | suite names walking `t.suite`, reversed | includes the empty-string default suite; docs example is `["", "first test file"]` |
| `fullName` | `[...ancestorTitles, t.name].join(' ')` | **space-joined**, leading space when the file suite name is `''`. Not `task.fullName` (` > `) and not `expect.getState().currentTestName` |
| `status` | mapped from `result.state` or `mode`: fail→failed, pass→passed, skip→skipped, todo→todo, run/only/queued→pending | |
| `duration` | `t.result?.duration` (ms, monotonic) | `undefined` if the test never ran; includes that test's `beforeEach`/`afterEach`/`aroundEach`, not `beforeAll` |
| `failureMessages` | `errors.map(e => e.stack \|\| e.message)` or `[]` | |
| `location` | `t.location` | only if `includeTaskLocation` (on by default for UI/HTML reporter; off otherwise) |
| `meta` | `t.meta`, optionally filtered by experimental `filterMeta` | 4.1 `test({ meta })`; shallow merge from suite/tags |
| `tags` | `t.tags \|\| []` | 4.1 |

If any test is still `run`/`queued` when the report is built, the reporter logs a warning calling it an internal Vitest bug.

```

only → pending
pass → passed
```

## 4. Deriving packet §5.4 from JSON

Target shape from the contract:

```
{ package, runner: "node-vitest", capturedAt, totalMs, testCount, files: [{ file, ms, tests }],
  slowest: [{ file, testName, ms }] }
```

| §5.4 field | 4.1.11 JSON source | Caveat |
| --- | --- | --- |
| `package` | not in JSON | fill from the census / cwd |
| `runner` | not in JSON | `"node-vitest"` for the P1 command; bun-native scripts are a different runtime (see §6) |
| `capturedAt` | not in JSON | ISO time of the CLI wrap |
| `totalMs` | **not present** | wrap the process with wall clock, **or** `max(file.endTime) - root.startTime`. Do not sum `duration` under `sequence.concurrent: true` |
| `testCount` | `numTotalTests` or `numPassedTests+numFailedTests` | decide whether skip/todo count |
| `files[].file` | `testResults[].name` | absolute; strip repo root for the digest |
| `files[].ms` | `endTime - startTime` | test-body wall, not collect/transform; overlapping concurrent tests |
| `files[].tests` | `assertionResults.length` | includes skip |
| `slowest[].testName` | prefer `title` plus `ancestorTitles.filter(Boolean).join(' > ')` | do not use JSON `fullName` as-is (leading space, space separators) |
| `slowest[].ms` | `assertionResults[].duration` | skip entries with missing duration |

**inference:** unnamed `it.layer` will inflate the first test's `duration` by layer acquire. Named `it.layer` puts acquire in `beforeAll`, which is invisible in JSON per-test durations and only shows up in file wall if it delays the first `startTime`.

Durations for D1 evidence come from this reporter, not from the instrumented `it` (contract §6.4).

## 5. Public APIs a `@effect/vitest` wrapper can use

Contract D7: instrumented `it` in `@beep/test-utils` composed from **public** `@effect/vitest` API (`makeMethods`, tester wrapping). `@effect/vitest` re-exports `vitest` (`export * from "vitest"`).

### 5.1 Test name — available

Inside the test function, Vitest passes `TestContext` as the first argument. `@effect/vitest` already forwards it: `it(name, testOptions(timeout), (ctx) => run(ctx, [ctx], self))`.

| API | Public? | Value |
| --- | --- | --- |
| Wrapper's own `name` argument to `it.effect(name, …)` | yes | the string the author wrote; available at registration |
| `ctx.task.name` | yes, `TestContext.task: Readonly<Test>` | same as `title` in JSON |
| `ctx.task.fullTestName` | yes | suites + name, ` > `, no file path |
| `ctx.task.fullName` | yes | `filepath > suites > name` |
| `expect.getState().currentTestName` | yes (`ExpectStatic.getState`) | optional string; Vitest format historically `file > suite > test` (issue #4874, 2024). Concurrent-unsafe if using the global `expect` |
| `expect.getState().testPath` | yes | optional file path |
| `ctx.expect.getState()` | yes (extended context from `TestRunner.extendTaskContext`) | bound to this test; use this under `sequence.concurrent: true` |

Tagged test-context docs show `({ task }) => console.log(task.name)` as the supported pattern.

**Recommendation (inference, for P0e design):** log `ctx.task.fullName` or `ctx.task.fullTestName`. Do not parse JSON `fullName`.

### 5.2 Effective test timeout — available at run time, not at wrap time

| API | Public? | Value |
| --- | --- | --- |
| Third arg / `{ timeout }` passed into `it.effect` | yes | only what the wrapper or caller supplied; `{}` if omitted |
| `ctx.task.timeout: number` | yes, on `Test` | **effective** timeout after config + tags + suite + per-test (`options.timeout ?? runner.config.testTimeout`) |
| `ctx.signal` | yes (3.2+) | aborted when the test times out, the run is cancelled, or bail fires |
| `vi.setConfig({ testTimeout, hookTimeout })` | yes | can change remaining file config; no `vi.getConfig` in tagged `docs/api/vi.md` |
| `TestRunner.getCurrentSuite` | exported on `vitest`'s `TestRunner` class (`node_modules/vitest/dist/runners.d.ts` statics; `@effect/vitest` uses it internally) | current suite during **collection**. Not a timeout API. Advanced, undocumented for test authors |

`ctx.task.timeout` is the right public handle for the watchdog limit.

### 5.3 Watchdog placement (**verified** mechanics + contract D7; design is inference)

Facts:

1. `it.effect` provides `TestClock`. `Effect.sleep` on that clock does not advance wall time. A watchdog must use live time (`TestClock.withLive` exists at the tag: `packages/effect/src/testing/TestClock.ts` lines 278 and 580).
2. `it.live` does not provide `TestEnv`; live `Clock` is already in use.
3. Vitest's `withTimeout` and the watchdog are two independent timers. If both use `ctx.task.timeout`, the named hang error races the generic `Test timed out in Nms`.
4. `@effect/vitest` already binds `ctx.signal` to `Effect.runPromise`. When Vitest wins the race, the Effect is aborted with the generic timeout error.
5. `onTestFinished` is a hook-timeout-bounded cleanup; it is not a watchdog.

**inference for P0e (not implementation):** `limit = ctx.task.timeout === 0 ? /* no watchdog, or a hard cap */ : Math.max(0, ctx.task.timeout - bufferMs)` with `bufferMs` large enough that the watchdog dies first (Vitest issue #9751 discusses a 100 ms action buffer for the same reason). `timeout === 0` means "disabled" in Vitest; a watchdog that still fires would change semantics.

JSON durations remain the evidence clock. The wrapper's start/end logs are traces, not §5.4.

### 5.4 Unavailable / unsafe public APIs (flag)

| Wanted | Status |
| --- | --- |
| Remaining timeout budget | **unavailable publicly.** Internal `runner._currentTaskTimeout` / `_currentTaskStartTime` are unsafe under `sequence.concurrent: true` |
| `vi.getConfig()` | **not documented** in tagged `vi.md`. Only `vi.setConfig` / `vi.resetConfig` |
| Effective `hookTimeout` from inside a test | **no public field** analogous to `task.timeout`. Hooks are not `Test` tasks |
| `it.layer` hook timeout from an inner test | **unavailable** unless the wrapper records the `options.timeout` it passed when wrapping `layer` |
| Process wall-clock / collect / transform / setup in JSON | **not in the JSON reporter** |
| Root `totalMs` in JSON | **absent** |
| Stable Jest-shaped `currentTestName` | Vitest format differs (issue #4874) |

## 6. Node vs Bun (this repo)

Packet non-goal: "Bun's test runner". The relevant split is **Vitest running on Node** vs **Vitest running on Bun**, not `bun test`.

**verified from package scripts:**

- Everyday `test` / `beep:test`: `bunx --bun vitest run` (Bun process, Vitest 4.1.11, same JSON reporter class).
- Coverage scripts: `bunx vitest run --coverage` (no `--bun`; Node process). Packet P1 timings explicitly use this lane: `cd <package-dir> && bunx vitest run --reporter=json --outputFile=...`.

**verified Vitest 4.1.11 pool:** default `forks` (`docs/config/pool.md`, `resolveConfig.ts` `resolved.pool ??= 'forks'`). Same reporter code on both runtimes.

Differences that **are** runtime, not reporter schema:

| Topic | Node vitest (P1 / coverage) | Bun-hosted vitest (`bunx --bun`) |
| --- | --- | --- |
| JSON schema | 4.1.11 `JsonTestResults` | same, if the same `vitest@4.1.11` is loaded |
| Wall times | slower under v8 coverage (repo comment: 10x+ on schema decodes) | typically faster; **do not compare** bun-native `test` scripts to node JSON baselines |
| Timeouts | `vitest.shared.ts` 300s under coverage | 30s / 10s unless FC sweep |
| Workers | Node `child_process` forks | Bun forks; **dated** Bun issue `oven-sh/bun#27002` (2026-02-13): intermittent `Timeout waiting for worker to respond` with vitest 4.0.17 + default forks on Linux containers; does not reproduce on Node |
| Coverage | v8 provider in `vitest.shared.ts` | Bun coverage APIs differ; coverage lane is Node on purpose |
| `experimental.viteModuleRunner: false` | 4.1 native Node import path | reported to work on Bun with mock/coverage gaps (InfoQ 2026-05-01 citing GitHub discussion) |

**inference:** a live watchdog using `ctx.task.timeout` + `TestClock.withLive` is runtime-agnostic because both hosts execute the same `@vitest/runner` `withTimeout`. Do not assume Bun's 5s `bun test` default (issue `oven-sh/bun#27422` is about `bun test` / `node:test`, not Vitest).

Default reporter `Duration` percentages (environment / import / transform / tests / setup) are a **docs-HEAD / 5.0** presentation (`https://vitest.dev/guide/improving-performance.html`, dated 2026-08-07). 4.1.11 default reporter still prints a Duration line with those phase times (tagged `docs/guide/reporters.md` example). Those phases are **not** in the JSON reporter on either runtime.

## 7. Implications for D7 + P1 (judgment, not implementation)

1. P1 command is correct for 4.1.11 if `--outputFile` is an absolute path and `--reporter=json` is set. Add `--reporter=default` if the log should stay human-readable.
2. Derive §5.4; do not expect `totalMs` in the file.
3. Record `runner: "node-vitest"` only for the node/coverage command. A bun-native run is a different number.
4. Instrumented `it` should read `ctx.task.name` / `ctx.task.fullName` and `ctx.task.timeout` from the public `TestContext` already passed into `@effect/vitest` testers.
5. Watchdog sleep must be live-clock and strictly less than `ctx.task.timeout` (unless timeout is 0 / Infinity).
6. `it.layer({ timeout })` cannot feed the per-test watchdog; it only extends hooks. Container hangs during acquire fail with `Hook timed out in Nms`, not the watchdog `TestHang`.
7. Live `vitest.dev` JSON default-path text is 5.0. Pin comments and KG entries to the `v4.1.11` GitHub URLs above.
