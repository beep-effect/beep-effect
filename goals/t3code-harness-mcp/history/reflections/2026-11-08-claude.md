# Reflection — t3code-harness-mcp (2026-11-08, claude)

## Summary

Registration was done before this closeout, under a different design than the spec's. Claude, Codex,
Grok and cursor-agent are proven by real turns on every host. Junie's token is proven and its client
is not. Verdict: useful and honest to close, with one named gap.

## Tooling experience

- **Worked:** a sentinel-only prompt kept thread titles out of the receipts and made results greppable.
- **Didn't:** my first prompt, which omitted a target and read as a fleet-wide failure.
- **Frustrating:** `env -i` hid Junie's keyring auth on the hub and looked like a missing login until `DBUS_SESSION_BUS_ADDRESS` was passed.
- **Wished existed:** a harness-neutral `mcp check` command.

## Implementation improvement opportunities

- The authorize script's backups hold old tokens; prune them after a successful renewal.
- Script distribution to hosts is manual because tracked Python is banned. A `beep` port would fix that.

## Goal & prompt critique

The spec's double-load test assumes two distinct names. With one shared name, its question becomes "does the injected entry win", so the proof rests partly on adapter behavior instead of a tool list alone.

## Lessons

- **HIGH:** A pass requires a real turn through the real client; a working token is a weaker claim, so report it as one.
- **MEDIUM:** A second name in a tool list needs explaining before it counts for or against a double-load check. `t3_code_direct` turned out to be T3's own split.
- **LOW:** Automated probes can trigger CLI auto-updates that change the system under test.
