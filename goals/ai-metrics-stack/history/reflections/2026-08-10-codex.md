# Reflection — ai-metrics-stack (2026-08-10, codex)

## Summary

The closeout turned a stale waiting-window packet into a production-backed V1:
one XDG data root, a final credited scorecard, progressive at-least-once OTLP
delivery under real backpressure, and a confirmed sanitized dankserver mirror.
The architecture held; the weakest surfaces were operational truth drift and
capacity observability, not the privacy or schema boundaries.

## Tooling experience

- **Worked:** the dated handoff made recon bounded; systemd and DuckDB evidence
  exposed the actual timer/watermark state; official Phoenix source localized
  the 503; package check plus the full 50-test Vitest file caught the Effect v4
  collection-helper mismatch and proved partial acknowledgement.
- **Didn't:** GET/health reachability did not describe OTLP admission capacity,
  and the CLI's generic error discarded the status needed for diagnosis.
- **Frustrating:** the packet had no opportunities ledger; `bun test` chose the
  wrong runner; hardware-backed SSH lost agent continuity between remote
  checks; the declared remote mirror root was not provisioned; the shared
  Phoenix queue had no visible depth or source attribution.
- **Wished existed:** one sanitized capacity/status command that reports
  Phoenix queue pressure, the last collector response class, and local pending
  watermark without exposing trace payloads.

## Implementation improvement opportunities

- Retry timing can become collector-aware once Phoenix capacity is observable;
  progressive checkpoints provide correctness, but fixed retries still compete
  noisily with the monitoring collector.
- Forwarder status should distinguish source collection success, durable local
  projection, OTLP accepted-prefix progress, and final remote drain.
- The timer's code checkout is now the only checkout-sensitive surface. A
  deliberate post-merge deployment/update mechanism would remove ambiguity
  without moving the XDG-owned data.

## Goal & prompt critique

The handoff's ordered sequence and instruction to trust verified live state over
the stale manifest were load-bearing. I would add one sentence: "A green health
endpoint is not an OTLP proof; send an empty protobuf request and inspect the
pending DuckDB watermark before attributing reachability." I would also name
the monitoring collector as a possible competing Phoenix ingress so capacity
diagnosis begins with both clients instead of only the AI metrics timer.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Align durable checkpoints with remote acknowledgements —
  stable ids prevent duplicates, but only progressive state prevents a bounded
  collector from starving the tail.
- **HIGH — Critical:** Verify the protocol operation that is failing — an HTTP
  GET or `/healthz` can remain green while OTLP POST admission is saturated.
- **MEDIUM — Best practice:** Separate durable data ownership from executable
  checkout provenance; XDG solved fragmentation even though deployment still
  names a checkout.
- **LOW — Consideration:** A source-file cap is not automatically a backlog;
  inspect new archive-object and unique-turn deltas before raising memory-heavy
  production budgets.
