# P4 design — capability projection engine and `beep goals next|explain`

Status: design only; no implementation is authorized by this document.

## Scope and binding doctrine

Workstream D's engine slice (`goals/knowledge-surface-automation/SPEC.md:192-229`):
manifests decode through the canonical `GoalManifest` schema into a disposable
in-memory `bun:sqlite` projection; frontier, blockers, cycles, and
shortest-unlock-path are recursive CTEs behind `beep goals next` and
`beep goals explain <slug>`; a tiny pure-TypeScript reference evaluator
differential-tests the SQL on the sealed fixtures. One deterministic projection
feeds JSON, the Mermaid block, and the later dashboard so renderers cannot invent
divergent semantics.

Everything semantic is already sealed and is NOT reopened here:

- The four normalized row families, evaluator semantics, and six differential
  fixtures (`research/p1-manifest-capability-extension-design.md`, "Deterministic
  normalized projection" through "Pure-TypeScript reference evaluator fixtures").
- D1-D10 (`research/p2-grill-decisions.md`): slug grammar, durable-ability
  granularity, no aliases, informational collisions, duplicate declarations under
  the doctor ratchet, schema-level self-cycle rejection (shipped in the D schema
  slice), frontier-only `executionCapable` exclusion with annotated routing,
  strand-and-redeclare supersession, and the evidence mint lanes/shape.
- The manifest schema itself (`provides`/`requires` with defaults) shipped in the
  D capability slice; this design adds no manifest fields.

This slice ships READ-ONLY commands and one committed report. Per the packet's
phase-0 doctrine, every new finding class surfaces first in a report command;
doctor gates for capability findings come only after the report's false-positive
rate is eyeballed. Evidence-backed readiness (D9/D10) is explicitly out of scope:
this slice computes nominal readiness only, with the output schema reserving the
field so the later evidence projection lands beside it, never over it.

## Decided contract

1. **Raw `bun:sqlite`, not `@beep/effect-drizzle`.** The projection is a
   disposable in-memory query engine over already-decoded schema values: four
   tables, no migrations, no persistence, and every interesting query is a raw
   recursive CTE. Drizzle's sqlite model layer earns its keep on persistent app
   schemas with typed tables; wrapping it around `WITH RECURSIVE` text queries
   would add a dependency without absorbing any invariant. `bun:sqlite` already
   has in-repo precedent (`packages/ecosystem/effect-drizzle/src/sqlite`), and
   the repo-cli runs under Bun exclusively. The `Database` lives behind an
   `Effect.acquireRelease` scope; no handle escapes the command.
2. **The projection compiler is pure.** `compileCapabilityProjection` maps
   decoded manifests (any discovery order) to the four sorted, duplicate-free row
   arrays from the sealed design. It is not an `Effect`; SQLite consumes only its
   output. The same rows feed the pure-TS reference evaluator — the differential
   is row-identical by construction, so any divergence is a query bug, not an
   ingestion bug.
3. **One result schema per question, versioned.** `goals next` returns a
   `goal-frontier/v1` report; `goals explain <slug>` returns a
   `goal-explain/v1` report; the catalog is a `capability-catalog/v1` report.
   JSON output is the canonical pretty rendering of the encoded schema value —
   the same discipline as the knowledge and materialization-plan commands.
4. **Fail closed on decode.** A manifest that parses but does not decode refuses
   the whole graph projection with a typed operational error naming the packet,
   matching the sealed design's "no partial packet rows" rule and the index's
   invalid-manifest treatment. `goals next` over a broken census must never
   silently render a smaller graph.
5. **Nominal readiness only, evidence reserved.** Report schemas carry
   `readiness: "nominal"` (LiteralKit, single member in v1) and an
   `evidence` optional key that stays absent until the D9/D10 projection exists.
   Renderers written now will not need a breaking change to show both.
6. **SQL is differential-tested, never trusted.** Every query result asserted in
   tests is compared byte-for-byte (canonical JSON) against the pure-TS
   evaluator across forward, reverse, and seeded-shuffle insertion orders of all
   six sealed fixtures. A query without a differential is a defect.
7. **The Mermaid INDEX block is a separate second PR.** Commands and report land
   first (pure additions); extending the `goals index` writer changes tracked
   generated bytes across the repo and rides its own PR with byte-parity tests
   for the existing table sections, per SPEC's rendering order (Mermaid before
   dashboard, dashboard deferred).

## Schema sketch (illustrative, not implementation)

New module `commands/Goals/Graph.schemas.ts` (naming follows the family):

```ts
export const CapabilityReadiness = LiteralKit(["nominal"])            // v1; evidence-backed later
export class CapabilityProviderRow extends S.Class(...)({
  capability: CapabilitySlug,
  provider: S.String,                                                  // packet slug
  providerStatus: GoalStatus,
  satisfies: S.Boolean,                                                // status === completed-retained
}) {}
export class GoalRequirementRow extends S.Class(...)({
  capability: CapabilitySlug,
  satisfied: S.Boolean,
  providers: S.Array(CapabilityProviderRow),                           // OR alternatives, sorted
  fog: S.Boolean,                                                      // no provider rows at all
}) {}
export class GoalFrontierEntry extends S.Class(...)({
  slug: S.String,
  title: S.String,
  mission: S.optionalKey(S.String),
  requirements: S.Array(GoalRequirementRow),                           // all satisfied by construction
}) {}
export class GoalFrontierReport extends S.Class(...)({
  schemaVersion: S.tag("goal-frontier/v1"),
  readiness: CapabilityReadiness,
  evidence: S.optionalKey(S.Unknown),                                  // reserved (contract 5): absent until D9/D10
  frontier: S.Array(GoalFrontierEntry),                                // sorted by slug
  fog: S.Array(CapabilitySlug),                                        // orphan capabilities, sorted
  cycles: S.Array(S.Array(S.String)),                                  // sorted SCCs of packet slugs
}) {}
export class GoalUnlockStep extends S.Class(...)({
  slug: S.String,
  executionCapable: S.Boolean,                                         // D7: annotated, never hidden
  provides: S.Array(CapabilitySlug),
}) {}
export class GoalExplainReport extends S.Class(...)({
  schemaVersion: S.tag("goal-explain/v1"),
  evidence: S.optionalKey(S.Unknown),                                  // reserved (contract 5): absent until D9/D10
  slug: S.String,
  status: GoalStatus,
  executionCapable: S.Boolean,
  ready: S.Boolean,
  requirements: S.Array(GoalRequirementRow),
  unlockPath: S.Array(GoalUnlockStep),                                 // empty when ready or cyclic
  cycle: S.optionalKey(S.Array(S.String)),                             // SCC containing slug, if any
}) {}
export class CapabilityCatalogEntry extends S.Class(...)({
  capability: CapabilitySlug,
  providers: S.Array(CapabilityProviderRow),                           // slug + status: reference-provides visible
  consumers: S.Array(S.String),
  collision: S.Boolean,                                                // >1 provider (informational, D4)
  orphan: S.Boolean,                                                   // consumers without providers
  duplicates: S.Array(S.String),                                       // packets declaring it twice (D5)
  stranded: S.Boolean,                                                 // D8: superseded-only providers
}) {}
export class CapabilityCatalogReport extends S.Class(...)({
  schemaVersion: S.tag("capability-catalog/v1"),
  entries: S.Array(CapabilityCatalogEntry),                            // sorted by capability
}) {}
```

The catalog IS the phase-0 report for the D5/D8 finding classes
(duplicate-declaration, stranded-capability, reference-provides): providers carry
their packet status so a `reference` provider is directly visible in the report,
duplicates and strands are explicit fields, and every class surfaces here first; doctor gates arrive in a later PR only after the catalog's
false-positive rate is eyeballed, mirroring the A/B/C pattern.

## Command surface

```text
bun run beep goals next [--json]
bun run beep goals explain <slug> [--json]
bun run beep goals catalog [--json]
```

All three are read-only: decode census → compile projection → open in-memory
database → run queries → render → close. No flags mutate anything; there is no
`--write` anywhere in this slice. `explain` decodes its positional through
`GoalSlug`; an unknown slug is a typed input error naming `goals bootstrap`
(the E-designed funnel message, still without `--create` semantics).

Human rendering mirrors the family: headline counts, one line per entry,
requirement lines indented beneath their packet, fog and cycles as trailing
sections. `--json` prints the canonical pretty encoding.

## SQL shapes (recursive CTEs, differential-tested)

Sketches; binding comes from the differential, not this prose.

- **availability**: `SELECT capability_slug FROM provides_edges JOIN packets ON
  provider = packet_id WHERE status = 'completed-retained' GROUP BY 1`.
- **frontier**: active, execution-capable packets with no requires edge missing
  from availability (`NOT EXISTS` anti-join). No recursion needed; kept in SQL so
  every renderer reads one engine.
- **blocked-on** (explain): the packet's requires edges left-joined to
  availability and to candidate providers with their statuses.
- **cycles**: recursive reachability over consumer→candidate-provider edges
  restricted to unavailable capabilities; `WITH RECURSIVE reach(src, dst)` seeded
  by direct edges, closed transitively with a visited guard; SCC = pairs where
  `reach(a,b) AND reach(b,a)`, grouped and sorted. Fixture 3 pins it.
- **shortest-unlock**: `WITH RECURSIVE walk(frontier_path, tail, depth)` BFS from
  the target's unsatisfied capabilities toward providers, path stored as a
  slug string joined AND bounded by `/` (`'/a/b/'`), with the cycle guard testing
  `instr(frontier_path, '/' || candidate || '/')` so one slug being a substring of
  another can never false-positive, `ORDER BY depth LIMIT 1`
  per capability, D7 annotation joined from `packets.execution_capable`.
  `unlockPath` merges the per-capability shortest paths as a union deduplicated by
  slug, ordered by `(depth, slug)` — a stable "work these, shallowest first" list,
  not a globally minimal unlock set (Steiner-style global minimization is
  explicitly out of v1; if the eyeball wants it, that is a new fixture and its own
  decision). When the only path crosses a non-execution-capable packet the step
  says so; when the target sits in an SCC the report returns the cycle instead of
  a path (fixture 3).

The pure-TS evaluator implements the same four questions with `HashMap`/`HashSet`
set algebra and explicit BFS — small enough to review as obviously correct, which
is its whole job.

## Test plan

1. **Differential:** six sealed fixtures × three insertion orders × four queries;
   SQL and TS outputs byte-equal as canonical JSON.
2. **Evergreen census:** decode every tracked manifest (fail-closed proof against
   the live repo), compile the projection, run all queries; assert the report
   schemas decode their own encodings (round-trip), and assert the live catalog
   contains the four known capability slugs with this packet as provider.
3. **Command surface:** `next`/`explain`/`catalog` through `Command.runWith` in a
   temp-cwd fixture census (happy JSON, unknown slug funnel error, broken
   manifest fail-closed).
4. **Determinism:** two full runs produce identical bytes; discovery-order
   permutation produces identical bytes (sealed test 10).
5. **Zero-write:** porcelain-equality around a full command run, as in the E
   phase-0 suite.
6. **Coverage identity:** new files enter the coverage baseline via the scoped
   `--write-baseline` path in the same PR, with untouched files' floors verified
   unchanged (the #762 lesson, now packet doctrine).

  evaluator, sqlite engine, three read-only commands, tests, and the committed

  E's executor era), evidence-backed readiness (D9/D10), speedrun ghosts,
  substitution routes, bitemporal.

## Open questions for the mini-grill

Nothing here reopens D1-D10, the row families, or the fixtures.

1. Is `beep goals catalog` the right home for the capability catalog, or should
   it fold into `goals next --catalog` to keep the subcommand count down?
2. `goal-frontier/v1` carries `cycles` at the top level; should cycles instead be
   explain-only detail so `next` stays a pure worklist?
3. The shortest-unlock path cap: unbounded BFS on the live census is small today
   (~110 packets); pin a depth cap (proposal: 16) or leave unbounded until the
   census proves otherwise?
4. Mermaid block size: the live graph renders every packet; propose collapsing
   terminal topo layers into relics from the first render (SPEC allows it) —
   confirm, or start fully expanded and collapse only after INDEX bloat is
   observed?
5. May `goals explain` accept a capability (`goals explain cap:knowledge/doctor`)
   in v1, or is packet-slug-only the right first cut?
