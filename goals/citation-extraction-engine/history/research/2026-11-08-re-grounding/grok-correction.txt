## Correction

The fact report's opening treats exhaustive observable parity with Free Law Project eyecite 2.7.6 (`clean_text`, `get_citations`, `resolve_citations`, `annotate_citations`, every upstream fixture) as the contract still to be completed.

Repository fact: that contract is what `goals/citation-extraction-engine/GOAL.md` lines 3–6 and `SPEC.md` lines 5–11 and 95–116 still say. Oracle pin: `04d82c032ad5fd0f9ab72a61c87110c46ee8f52e`. `SPEC.md` lines 455–457 say the current full/short case, `Id.`, supra, 35 U.S.C., and 37 C.F.R. fixtures are an implementation order, and the completion boundary is every phase. `SPEC.md` lines 468–478 already exclude a Python runtime, hosted parsing, citator/good-law, claim lifecycle, matter-wall orchestration, editor UI, and MPEP patterns unless separately accepted.

Product hypothesis: the operator has put that exhaustive contract under reconsideration. Completing it is not the recommendation. The written files stay in force until a later decision edits them. This critique recommends a smaller extraction-only target and states what would show that target is wrong.

## 1. Pre-1.0 and alpha do not show that a bounded v1 is out of reach

Repository fact: the 2026-10-28 donor receipt pins eyecite-ts `0.34.2` at `34133d03143ea65861f48a5ed0eb32c931581666` and eyecite-js `2.7.6-alpha.28` at `53a49f2412da668aaf262e5f92584c2c3781043b`. It says all 5,674 disposition obligations remain unresolved, none is claimed as target parity, and the successful runtime record proves the donor case only (`goals/citation-extraction-engine/history/evidence/2026-10-28-typescript-donor-accounting.md` lines 3–6 and 74–76).

Source evidence, with the report's own limits: the fact report records eyecite-js git head as a pre-release and eyecite-ts npm latest as `0.34.2` described there as pre-1.0. It also records that maintainer claims of Python 2.7.6 parity were not independently benchmarked, and that a rename between the npm repository field and the git head was not checked.

Inference: a pre-1.0 or alpha label means the bounded extractor is **unverified** against the fixture this critique defines. It does not mean the extractor is **demonstrably inferior** to a custom one. Demonstrably inferior requires a recorded disagreement on that fixture, or a failed safety trial. Neither result is in the gathered evidence. The fact report's sentence that the ports "do not close that parity gap" is fair only as "exhaustive parity is unverified." Read as "unable to satisfy a smaller v1," it overclaims.

Passed donor tests are the same kind of metadata. They show those suites ran. They are not evidence about the bounded tuple below.

## 2. An Effect timeout around `RegExp` is not a safety acceptance

Source evidence: the landscape note says to skip native Hyperscan, use a literal-substring prefilter plus per-extractor JavaScript `RegExp`, and wrap the parse in an Effect timeout or interrupt and/or a linear-time engine (`explorations/citation-grounding-hallucination-guard/research/legal-citation-parser-landscape.md` lines 40–41). The same note quotes the JOSS limitation: extraction and annotation may take exponentially long on worst-case inputs, so external time limits are recommended for possibly malicious input (line 41). The fact report's verification note on its excluded claim 5 says the spec's regex identity is `python-re | python-regex-v0`, the worker defaults to a native child, the spec still prefers static-safe JavaScript patterns, and both the spec and the landscape reject native Hyperscan. That note also says the worker command was not traced to a binary.

Inference: the landscape's Effect-timeout sentence does not preempt a synchronous catastrophic match. JOSS asked for an **external** limit. An in-process fiber timeout assumes the matching work yields. A synchronous `RegExp` on the calling thread does not yield. Until someone shows that this runtime interrupts that call, the timeout advice is not a safety mechanism.

Product hypothesis: no extractor, adopted or custom, passes a safety gate on that advice. Pass requires one of the two mechanisms in gate 3 below, demonstrated by execution. "Static-safe" as a preference, and "native child" as an untraced default, are unresolved, not a pass.

## Recommendation

**Adoption, by vendoring a bounded slice, conditional on the comparison and the safety gate. Custom only if that condition fails. Dependency adoption is the loser. Exhaustive completion is not a candidate.**

Product hypothesis, stated as the strongest rule the gathered evidence can carry:

1. Do not implement the exhaustive GOAL as the next build.
2. Do not add `eyecite`, `eyecite-js`, or `eyecite-ts` as a runtime dependency. A dependency cannot drop or replace a catastrophic pattern without taking the whole package. `SPEC.md` lines 156–158 and 470 already forbid that runtime dependency; this recommendation keeps the forbid for the safety reason, not because the packages are pre-1.0.
3. Run the full-case comparison on both pinned donors. There is no quality basis for starting with one of them.
4. Vendor the bounded full-case `get_citations` path from a donor that returns `agree` on every non-waived fixture row and passes gate 3. BSD-2-Clause attribution stays with the vendored text. The landscape note's licensing section (lines 12–13) is the source for "the algorithm and reporter data may be ported with attribution; CourtListener AGPL glue may not be copied." The fact report did not re-fetch the license files. Treat that as the note's claim.
5. If both donors diverge, or both fail the safety gate, write a custom extractor for that same tuple only, under the same gate. Custom work does not add operations to "make the rewrite worth it."
6. If both agree and both pass the safety gate, vendor either slice. Choose by which slice the safety boundary can kill or prove. Do not choose by release label or suite size. Which slice is smaller in source was not measured; measuring it would be an inventory this correction refused.

Inference: recommending a custom engine because the donors are alpha would repeat the error in section 1. Recommending a custom engine that still calls synchronous `RegExp` behind an Effect timeout would repeat the error in section 2.

## Falsifier

The adoption rule is false if any of these is recorded:

- On the frozen full-case fixture, the vendored slice's tuple disagrees with pinned eyecite 2.7.6 `get_citations` on a row that was not waived in writing before the run.
- A known catastrophic pattern, run under the proposed guard, keeps the caller thread busy past the external limit. That kills both "Effect timeout is enough" and any vendor or custom path that relied on it.
- The vendored slice pulls in `resolve_citations`, annotation, or a resource id in order to emit volume, reporter, and page. The slice is then larger than extraction, and the adoption claim fails even if the tuples match.
- A later decision restores exhaustive four-operation parity as the completion target. This recommendation then stops applying. The written GOAL already says that today; the falsifier fires if reconsideration is withdrawn.

The custom alternative is false under the first two bullets as well. A custom extractor does not get a softer oracle.

What would show a donor is demonstrably inferior: the first bullet, on this fixture, with the other candidate or a custom extractor agreeing. Until that row exists, the donor is unverified.

## Proposed acceptance gates

A build of this slice is accepted only when all five are true. These replace the exhaustive SPEC checklist for this decision. They do not delete that checklist.

1. **Scope.** The completion statement names full-case `get_citations` tuples only. The output schema has span start, span end, volume, reporter, and page. It has no resolved resource, no good-law flag, no supports/refutes/insufficient label, and no annotation markup.
2. **Differential.** Every frozen fixture row is `agree` with pinned eyecite 2.7.6, or a written waiver names the row and the reason before the run. Waivers are rows, not percentages. Suite pass counts do not substitute.
3. **Safety.** One of these is demonstrated on a catastrophic pattern, and the record includes the command and the observed caller behavior:
   - every pattern the slice can execute is in a proved linear-time subset, and the proof identifies the pattern source; or
   - the match runs inside an execution boundary that a supervisor outside the matching thread can kill on a wall clock, and the caller remains responsive after the kill.
   An in-process Effect timeout or interrupt around a synchronous `RegExp` is a fail. Skipping Hyperscan is not a pass.
4. **Dependency.** The host runtime does not load Python, eyecite, eyecite-js, eyecite-ts, a hosted parser, or native Hyperscan. Vendored source with the retained BSD copyright and license text is allowed. CourtListener application glue is not vendored.
5. **Non-expansion.** Implementing the slice does not add short-case grouping, `Id.` or supra binding, journals, statutes, regulations, MPEP, court ingestion, or claim-admission changes. Those need their own decision.
