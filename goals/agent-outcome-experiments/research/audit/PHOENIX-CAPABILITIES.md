# Phoenix capabilities for agent improvement

Research date: 2026-10-27. Primary documentation only. Live version supplied by parent audit: Phoenix **20.23.0**. Documentation is rolling and can describe newer server/client features; this matrix proposes use, not a claim that every control or API has been verified on that server. No Phoenix writes, remote host calls, evaluation runs, dataset creation, plugin installation or provider calls were performed by this agent.

## Recommendation

Use Phoenix as the inspectable quality and experimentation surface behind a trustworthy source/coverage ledger. Start with explicit project ownership, source identity, stable sessions and human outcome annotations. Then curate a small sanitized task dataset and compare a single change against a baseline. Build on the existing project dashboards before authoring a replacement interface. The empty `beep-agent-effectiveness` project's intended writer/owner is being investigated in the separate source audit; an empty project alone does not prove failed ingestion.

## Coverage and organization before metrics

This design proposal is specific to the repository audit rather than a Phoenix product claim:

1. Maintain a registry for every actual writer/entry point: account, host class, harness mode, exporter destination, inclusion rules and expected heartbeat. Several clones may share one telemetry configuration, while one account may launch several differently instrumented modes.
2. Give source events stable IDs and preserve original IDs through derived export. Record deduplication, filtered events, delivery failure and late arrival separately. A lack of traces without an expected population remains unknown.
3. Keep synthetic deployment probes outside human-agent outcome totals. The current `ansible-phoenix-health` probe has no explicit project or session; it can add successful operational traces to `default`. See [deployment audit](./DEPLOYMENT-AUDIT.md).
4. Build project and task dashboards only after source coverage can be shown alongside them. Report observation window and retention window independently.
5. Choose one narrow improvement hypothesis, then use annotations → reviewed cases → pinned dataset → paired experiment → human decision. Do not promote a better token or latency figure into a quality claim without outcome evidence.

## Documentation traps and version checks

- An attempted Phoenix `run-experiments` documentation URL redirected to **Arize AX** code-experiments documentation. That page is not evidence of Phoenix 20.23.0 support. This report instead uses the official Phoenix client reference.
- Current Phoenix documentation includes features beyond the deployed release. Server-side evaluators, recent coding-agent plugins, assistant automation and newly documented API fields need a pinned-release/source or deployed-schema check before adoption.
- Phoenix's v18 migration describes session time-range inclusion as interval overlap. Do not interpret a seven-day session count as only sessions started during those seven days. Confirm actual deployed query semantics and timezone. [Official migration guide](https://github.com/Arize-ai/phoenix/blob/main/MIGRATION.md).
- The same migration guide distinguishes persisted **Phoenix assistant conversations** from observed application sessions. Dankserver disables that assistant. Assistant-session retention or UI features must not be confused with coding-harness session collection. [Official migration guide](https://github.com/Arize-ai/phoenix/blob/main/MIGRATION.md).
- Native telemetry remains constrained by exporter behavior, semantic mapping, local filters and transport. Phoenix functionality cannot recover source events that never arrive. Historical Codex counter collisions and scheduled receiver outages are documented in [the deployment audit](./DEPLOYMENT-AUDIT.md).

## Concrete next artifact

A reviewable starter contract should contain the project registry, harness coverage matrix, stable source/session/task identity schema, five small outcome rubrics and a sanitized 10–20-case dataset proposal. Include one baseline experiment specification, an explicit resource budget and a read-only dashboard layout. This research does not authorize creating those live objects or running models.
