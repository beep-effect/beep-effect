# CSF-011: Lab delete prints unowned Postgres DROP instructions

- Severity: Low
- Codex ID: `3869a371a3b88191ad1918b2df2e71ab`
- Source commit: `afe4cdfaa7e28cbdc311150afffe58315c41ed0d`
- Owner: delete-package data ownership
- Status: confirmed; remediate; repo-side remediated

## Public Summary

The delete-package workflow can print an actionable `DROP DATABASE` command for a manifest-declared database even when ownership validation failed or data deletion was not requested. The manifest schema accepts any broadly prefixed lab database name rather than binding it to the package being deleted.

## Current-HEAD Validation

Verdict: `confirmed-vulnerable`; disposition: `remediate`.

Database ownership is enforced only when the destructive `dropData` option is active. Independently, command rendering and registration-geometry evidence emit a manual drop command for the manifest resource, so an unowned or stale manifest entry can still produce dangerous operator guidance.

Evidence:

- `packages/tooling/tool/cli/src/internal/cli/Labs/LabManifest.ts` decodes the broad `lab_*` naming family so contextual ownership checks can report stale declarations.
- `packages/tooling/tool/cli/src/commands/DeletePackage/DeletePackage.policy.ts:120` refuses unowned data only when `dropData` is enabled.
- `packages/tooling/tool/cli/src/commands/DeletePackage/DeletePackage.command.ts:699` renders a manual drop command regardless of that ownership decision.
- `packages/tooling/tool/cli/src/internal/cli/RegistrationGeometry/RegistrationGeometry.probes.ts` also emitted the command as evidence.

## Remediation

DeletePackage now refuses every declared database resource that is not owned by
the selected package, whether or not `--drop-data` was passed. Command output
and registration geometry emit no actionable SQL for stale resources. Manual
SQL appears only after the manifest resource matches the package-derived schema
name.
