# Protected environment installation preparation

The existing private-file installer requires a separately selected provisioning directory. A protected workflow can deliver its independently approved records through step-scoped secrets without first persisting another copy of the issuer material. This component adds explicit `producer-install --from-environment` to that same command. It does not add an approval issuer, verifier, storage service or new execution path.

The fixed records are `BEEP_CACHE_PRODUCER_APPROVAL_JSON`, `BEEP_CACHE_PRODUCER_RUNTIME_JSON` and `BEEP_CACHE_PRODUCER_ISSUER_MATERIAL_BASE64`; `BEEP_CACHE_PRODUCER_STORE` still selects the private execution store. Approval and profile retain the existing schemas and sixteen-KiB UTF-8 limits. Approval is validated before material lookup. Material is redacted, bounded to 128 encoded characters and decoded to exactly 96 bytes. Fixed diagnostics discard decode inputs. The existing initializer checks independent source, target, executable and binding identities, creates exclusively, and revokes its newly reserved store on post-install failure.

File installation remains the default. Environment transport is unavailable to `producer-provision`, so it cannot silently generate a replacement issuer. The actual protected workflow must scope these secret fields to its installation step and keep the independent verifier off the runner. Producer workers must receive neither these environment fields nor a material-bearing mount. Backend/runtime capabilities remain a later, separate load.

Fourteen dispatch controls are authored: one exact-material handoff, one explicit-opt-in/provisioning-denial control and twelve negative inputs. They cover malformed and oversized records, the UTF-8 byte boundary, policy mismatch and schema-error redaction before material lookup, missing/short/long/invalid material, no file fallback, no initializer call on refusal and private-marker suppression. No local test execution was requested. Hosted Check, Build, Integration, Docgen and Repo Sanity passed the error repair at `f13ffb0610`; the full new source still requires fresh hosted proof. The separately owned coverage failure is retained and does not authorize a floor reduction.

The main-only `cache-producer-prepare.yml` caller now requests a credential-free candidate build through the admitted `heavy.yml@main` leaf. Its default-off mode is mutually exclusive with inspection and leaves the ordinary quality matrix intact. The build uses isolated disk-backed scratch, the existing `policy.sh cargo-build-musl`, Rust 1.96.0, cargo-zigbuild 0.20.1 and Zig 0.14.1. The preparation budget is one existing runner for at most twenty minutes, two Cargo jobs, sixteen MiB for the full artifact, sixty-four KiB for its manifest and one-day retention. Frozen scratch selection bounds cleanup to this job, including failure. No protected environment, cache/application/issuer secret, shared cache, adapter startup or signed producer operation is selected.

The candidate artifact contains only `decay` and a bounded `build.json` with exact source, patch, tool, binary and run/attempt identities. Source and patch checks repeat after compilation; an ELF interpreter, wrong architecture or excessive size refuses publication. The artifact requires separate authenticated workflow/source verification, independent executable approval and real runtime qualification. This workflow has not run. The earlier portable-build records remain historical inputs; no credential or signing activation is included. The separate first-trial ten-minute upload/fifty-MiB/operation/retention limits and every whole-goal requirement remain. Reverse by removing the preparation mode and opt-in private reader; retain file installation, issuer stores, verifier authority, ordinary R2 services and historical evidence.
