## Existing JSONL reuse boundary (2026-10-28)

Live source inspection found `packages/foundation/modeling/jsonl/src/Line.ts` already implements UTF-8 byte accounting, CRLF framing and a consumed offset that leaves an incomplete final line unconsumed. `src/internal/tail.ts` pins a sampled file handle/range and detects short/truncated reads; `Journal.ts` reconciles replacement/truncation and preserves replay/live seams. Use these existing semantics when designing the transcript adapter rather than inventing string-length offsets.

The current `Journal.ts` append path opens with append mode and calls `file.writeAll(bytes)` (around lines 923–924), but has no explicit `file.sync` in that append path. The API also documents that independent writers require separate coordination. It is useful framing/watch infrastructure, but an append return by itself is not the foundation's durable disk acknowledgment. Before using it for intake, either qualify an owned explicit sync/single-writer/size-bounded integration or use the repository's existing Effect SQLite route with separately proven transaction, WAL/checkpoint and disk bounds. Neither choice is implemented or qualified by this note. No historical journal or transcript was opened during this inspection.

## Initial local page journal choice and proof (2026-10-28)

The initial implementation uses a dedicated file-backed SQLite connection, injected through Effect's SQL service. `journal_mode=DELETE` with `synchronous=EXTRA` is verified by read-back. This avoids a WAL/checkpoint backlog in the first bounded worker; it trades concurrent-reader throughput for a simpler initial storage boundary. SQLite documents EXTRA's additional directory synchronization for DELETE mode. `max_page_count` constrains the database file; it does not replace separate rollback-journal/filesystem headroom. Sources: [SQLite synchronization modes](https://www.sqlite.org/pragma.html#pragma_synchronous), [database page ceiling](https://www.sqlite.org/pragma.html#pragma_max_page_count), [atomic commit assumptions](https://www.sqlite.org/atomiccommit.html).

The page's sanitized payload and compare-and-swap cursor share one transaction; the receipt returns after the transaction completes. Real SQLite tests prove rollback on an injected cursor failure and on actual database capacity exhaustion. Exact replay returns the original receipt. Independent-process tests now also kill writers before commit and after commit/before acknowledgment, then reopen and compare receipts/cursors. The initial paragraph's killed-process proof frontier is superseded by `IMPLEMENTATION.md`'s process-crash section. Power-loss protection and a network ACK boundary remain unproved. Next: bounded native admission and delivery facts. Keep hardware/filesystem flush assumptions explicit and retain the recovery hold.

Before adding a production driver, reuse the existing runtime-selected SQLite composition pattern in `AgentMessage.layer.ts`. The AI-metrics library requires only the injected `effect/sql/SqlClient`; its in-process tests use the existing `@beep/test-utils/SqlTest` driver. ## Native response semantics to preserve (2026-10-28)

The current [OTLP specification](https://opentelemetry.io/docs/specs/otlp/#partial-success-1) distinguishes full acceptance from a populated partial-success response. An HTTP 200 can carry rejected-item counts. Clients must not retry that partial-success request wholesale. Retryable HTTP responses are 429, 502, 503 and 504; other 4xx/5xx responses are not retried. A partial-success response gives rejection counts, not an authoritative identity list of rejected events. Therefore the receipt model must not arbitrarily mark a subset as delivered or dropped. Record the batch-level ambiguity and reconcile individual backend visibility separately. This is a design consequence of the protocol, not yet an implemented receiver guarantee.

Prefer an atomic local admission boundary: validate and sanitize a bounded request, commit its normalized metadata and intake receipt, then acknowledge. Capacity refusal must happen before acknowledgment and preserve an explicit pre-intake loss window for upstream exporters. Export success, local acceptance and backend query visibility need separate facts. Protocol framing, count limits, compressed-body handling and positive metadata projection still need concrete receiver tests.

The native projection and local admission portions now have the synthetic proof described in `IMPLEMENTATION.md`. The wire subset follows [OpenTelemetry trace.proto v1.9.0](https://github.com/open-telemetry/opentelemetry-proto/blob/v1.9.0/opentelemetry/proto/trace/v1/trace.proto) and its [trace service schema](https://github.com/open-telemetry/opentelemetry-proto/blob/v1.9.0/opentelemetry/proto/collector/trace/v1/trace_service.proto). Cache detail keys and known span kinds were checked against [OpenInference semantic conventions](https://github.com/Arize-ai/openinference/blob/main/js/packages/openinference-semantic-conventions/src/trace/SemanticConventions.ts). This validates field names, not the future deployed provider mapping or Phoenix aggregate totals.

The HTTP boundary must support gzip as well as uncompressed requests, enforce a byte ceiling after decompression, and use matching JSON/protobuf response types. The [OTLP specification](https://opentelemetry.io/docs/specs/otlp/#otlphttp) requires 413 on oversized HTTP requests. Do not label an identity-only/no-gzip handler a qualified OTLP receiver. The next proof needs actual socket requests, bounded concurrency without an unbounded waiting queue, slow/oversized/gzip-bomb bodies, 200/full/partial responses only after local commit, capacity/storage refusal, and separate-process precommit and lost-ACK kills. Keep the original exporter-to-intake volatile window explicit.

## Explicit uncertain expiry (2026-10-28)

`PayloadRetentionPolicy` and `makePayloadReclaimer` replace the earlier unpublished verified-only names. Verified reclamation remains the `reclaim` operation; `expire` is a separate explicit operation, disabled unless `expireAfterMillis` is configured. The versioned policy is immutable per journal. Earlier synthetic policy files are left intact and fail configuration matching instead of being silently migrated. No deployed journal uses these new APIs.

Expiry requires the configured page age and a quiet period after the latest send reservation. Its transaction registers accepted events, snapshots their exclusive delivery-state populations, deletes the payload, and writes a checksummed `retention-expired` disposition. Accepted references to another native page are counted once per page by unique event ID and remain separate from canonical-event fleet totals. Source cursors, original receipts, canonical identity hashes and all delivery facts survive. Expiry itself writes no result or visibility facts. A later independently qualified visibility fact may change the current event state while the expiry snapshot remains unchanged.

An expired exact batch or a retained duplicate-only batch whose original event expired cannot renew its original acceptance. The HTTP route returns 410 with no receipt or retry-after header. A new mixed batch uses `expiredIndices` to reject only expired identities and durably accept new events. Conflict and expiry reasons remain distinct; previous receipt encodings decode absent expiry indices as empty. Receipt lookup remains historical even when reacceptance is permanently refused. Native and reconstructed source identities are not changed.

The [OTLP specification's retryable-response table](https://opentelemetry.io/docs/specs/otlp/#retryable-response-codes), checked 2026-10-28, permits retries for 429/502/503/504 and prohibits retrying other 4xx/5xx responses. Its partial-success contract also prohibits retrying the entire partially accepted request. The 410 and partial-rejection behavior follow those rules; actual harness conformance still requires route qualification.

Synthetic tests cover all five delivery states, fresh mixed batches, retained duplicate references, transcript replay/cursor continuity, disabled policy, failed disposition insertion, policy drift, late visibility, and recent send reservations. Real socket tests inspect permanent refusal and partial counts. Two additional Bun SIGKILL boundaries qualify uncertain expiry before and after commit, with reopened SQLite integrity checks and unchanged unresolved state. These extend the verified-reclamation fixtures; they are not production exposure or a power-loss qualification.

Remaining storage work: compact evidence retention and bounded epoch transition. Payload slots can now be reused for verified and explicitly expired pages, but compact receipts, canonical hashes and delivery facts still accumulate to hard caps. No claim of indefinitely renewable storage or unbounded deduplication is made. The eventual transition must declare its replay horizon, retain aggregate loss/coverage evidence, and distinguish a new observation window from proof about earlier activity. Hard worker limits, production health/queue composition and full CLI/desktop/canary proof remain open.

## Bounded local evidence windows (2026-10-28)

The new evidence-window service makes local duplicate detection explicitly epoch-scoped. Intake initializes epoch zero, preserving the original v1 receipt hashes and source IDs. After a qualified retirement, new receipts include the epoch in their content address and carry `evidenceEpoch`; native trace/span/event identities remain unchanged. Existing owned page tables receive an additive `evidence_epoch` column defaulting to zero. Earlier native receipt/disposition encodings default the missing field to zero. None of this migrates the held historical collector's databases.

`seal(expectedEpoch)` is a compare-and-swap over one owned journal. It refuses an empty or too-young window, any retained payload, recent send activity, excessive work populations, damaged evidence, or conflicting epoch. It scans bounded groups of 32 disposition/event IDs, verifies receipt checksums and ledger states, and computes counts before deletion. Deletion of compact receipts/indexes/delivery facts and advancement to the next checksummed window commit together. Cumulative counters are bounded safe integers; a latest-retirement record and previous digest preserve bounded aggregate accounting rather than an ever-growing audit array. Source cursors and scheduling progress survive.

Retired totals are event observations across windows, not lifetime unique events. Native accepted occurrences include duplicates, and transcript frame occurrences include non-accepted frames. Unknown source/fleet populations remain outside this accounting. Pending, accepted-unverified, visible, rejected and unresolved populations are preserved at retirement. A digest chain does not reconstruct retired details or claim protection against a privileged writer.

A repeated native event may be admitted again in a later window. It has a new local receipt but the same source identities, and outgoing OTLP explicitly marks its local evidence epoch, current-epoch duplicate scope and retired prior local history. The sender and read-back reconstruction use the receipt's epoch, so old metadata from another epoch cannot satisfy exact matching. Backend handling of repeated source trace/span IDs remains a separate qualification; no lifetime deduplication or guaranteed backend overwrite is claimed. An absent local receipt/state after retirement means earlier detail is unavailable, not that the event never existed. Native intake and the delivery ledger expose the evidence window alongside their existing reads.

The window duration is not a minimum retention age for each fact. Only already-disposed payloads can participate; a new fact near a window boundary may have a short local-detail lifetime. Production settings and admission-pause/drain/resume behavior remain unselected and uncomposed. The worker must also qualify a bounded pre-retirement rollback snapshot and restoration before production retirement is enabled. This current synthetic path qualifies transactional rollback and process-death recovery, not recovery of intentionally retired detail after a committed production retirement.

Verification includes reuse across two windows, unchanged source IDs/cursors, native replay scope, all five state populations, a 33-record scan across the query boundary, work-cap refusal, immutable-policy/checksum refusal, failed checkpoint rollback, deadline interruption and two real process-kill boundaries. Actual OTLP decoding verifies the new epoch fields without changing source timestamps or IDs. Initial fixture failures were a missing helper parameter and JSON serialization of an Effect Option without its schema; both were corrected before final qualification.

## Bounded logical retirement recovery (2026-10-28)

The preceding snapshot requirement now has an implemented synthetic proof. Evidence-retention policy v2 copies one generation of the nine owned compact-evidence tables before retirement, in the same SQLite transaction. It stores only already-sanitized receipts, indexes, dispositions, send attempts/results and visibility facts; disposed payloads are not resurrected. The manifest binds the predecessor window, exact successor digest, retirement digest, intake/attempt sequence sentinels, row count, encoded row bytes and a rolling row-digest chain. Source cursors and fair scheduling progress are not copied or rewound.

The default recovery budget is 4,096 rows and 16 MiB of encoded row payloads; configurable ceilings are 262,144 rows and 128 MiB. These are proof defaults, not a selected production profile. Queries page at 32 rows, fields and serialized rows have separate read bounds, and the existing retirement deadline covers copying/restoring. Table/index/manifest overhead remains under the shared SQLite page ceiling. Rollback-journal/filesystem headroom must still be budgeted independently. Recovery capacity exhaustion, SQLite allocation failure or interruption aborts the transaction: original facts, current window and any previous recovery generation survive. A successful subsequent seal replaces the previous generation atomically; it does not grow an archive.

`restore(retirementDigest)` requires the exact successor window, empty current intake/compact tables, and unchanged intake/attempt sequences. It therefore refuses to erase observations accepted after retirement, including when their current rows have subsequently disappeared. It validates copied row checksums, table/column allowlists, population/byte counts and the digest chain before committing the predecessor window and restored marker. Failures after partial insertion roll back all inserted rows. Repeating an already committed restoration returns `already-restored` without mutation, including after later admission. A different digest is a conflict. Reopening earlier v1-policy disposable journals refuses configuration drift; no historical journal has been migrated.

This is **logical undo in the same database**, not an independent backup against database-file corruption, storage failure or device loss. It preserves compact evidence only for the most recently retired generation and never recreates already reclaimed/expired payloads. Independent physical backup/restore, admission pause/drain/resume, hard worker limits and live deployment remain open. None of these tests release the masked forwarder recovery hold.

## Shared admission, drain and maintenance boundary (2026-10-28)

The new scoped `ObservationControl` starts paused. It atomically reserves at most the explicitly configured number of activities (1–8), refuses excess work without a waiting queue, and releases reservations on success, failure or interruption. `pause` closes admission before waiting for the admitted generation to drain; timeout or interruption leaves admission closed. Resume is refused while draining. Maintenance requires paused, drained admission and has an exclusive, nonqueued control permit. Concurrent resume/pause/maintenance requests fail busy rather than accumulating. Maintenance completion or failure does not reopen admission. Scope release permanently closes the controller; status separately reports active work that may still be finalizing.

`makeObservationWorker` composes the native HTTP receiver, sender, exact backend read-back, reconstructed transcript sweep, payload reclamation/expiry and evidence retirement/restore under that shared boundary. It starts paused, exposes read-only journal views and gated activity methods, and does not expose the raw mutation-capable journal. Native HTTP uses the shared controller; paused/closed/refused admission returns OTLP-compatible retryable 503 in the requested encoding without reading the body or returning an acceptance receipt. Standalone native HTTP preserves its existing behavior by creating/resuming a private controller. The composed worker neither starts a listener nor launches a polling loop or held service. The native sender still does not silently export reconstructed transcript pages.

Five controller tests cover bounded nonqueued admission, generation drain, refusal during maintenance, timeout, interrupted work/pause, maintenance failure and terminal scope closure. Three real-socket composition tests exercise a blocked durable admission, a blocked outbound exchange, paused JSON/protobuf refusal, successful explicit resumption, rejected paused sweeps/read-back/sends, and expiry→pause→retirement→restore preserving accepted-unverified evidence. The existing seven HTTP socket and three actual Bun HTTP process-crash tests remain regression coverage. A synthetic backend initially replied with JSON to a protobuf export; the strict sender correctly classified that as unknown. The fixture was corrected to return a matching empty protobuf response, without weakening the decoder.

This is a **single-process coordination boundary**, not an OS-level ownership lock or a resource-limited deployment. Hard process/FD/connection/header/CPU/RSS/disk ceilings, single database ownership across processes, an owned scheduling loop, independent physical backup, live route enrollment and canary/rollback proof remain open. Do not interpret paused/accepting status as coverage or backend health. The production forwarder remains under the recovery hold.
