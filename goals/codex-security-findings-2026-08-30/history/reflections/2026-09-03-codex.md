# Reflection — codex-security-findings-2026-08-30 (2026-09-03, codex)

the remaining finding had already landed through PR #876. The exact eleven-ID

longer detected. Required hosted checks passed, both deployment failures were

## Tooling experience

- **Worked:** Stable Codex IDs and the sanitized triage ledger made the delayed
  closure audit deterministic even after the original branch and PR completed.
- **Didn't:** The Codex closed-list summary reported zero of zero, despite every
  captured detail page exposing Reopen and an automatic-closure notice.
- **Frustrating:** Merge and scanner closure had occurred, but the packet stayed
  active because no same-workflow closeout receipt updated its lifecycle.
- **Wished existed:** A packet-aware exact-ID closure command that reads only the
  allowlist, distinguishes manual from automatic closure, and writes the ledger.

## Implementation improvement opportunities

- Make post-merge exact-ID reconciliation a resumable Codex-findings operation.
- Report dashboard list-count disagreement without treating it as proof that
  captured findings remain open.

## Goal & prompt critique

The packet correctly separated repository proof from scanner closure, but it
did not make delayed automatic closure an explicit evidence shape. The next
template should name automatic no-longer-detected closure alongside manual
Already fixed closure.

## TODOs worth codifying

- Add a friction receipt when list pagination and detail-page state disagree.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Never infer security closure from a list count; inspect
  every captured ID and record its authoritative detail state.
- **HIGH — Best practice:** Keep merged-PR proof, review-thread proof, and Codex
  closure proof independently auditable.
- **MEDIUM — Consideration:** Automatic scanner closure is sufficient only when
  the exact finding says it is no longer detected and the merged remediation is
  independently attributable.
