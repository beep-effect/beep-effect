# Import-convention enforcement and guidance census

## Scope and method

This report inventories repository mechanisms that enforce or teach import style for the planned move from package barrels to per-module imports. It covers Biome and GritQL, ESLint, repo-cli quality checks, Fallow, TypeScript resolution, written guidance and skills, JSDoc/docgen, and CI. Repo claims cite the inspected file and line. Web claims, if any, cite their source URL.

Research status: complete (2026-08-23).

## 1. Executable import enforcement

### Biome and the repo GritQL rules

Biome 2.5.6 is the root formatter/linter (`biome.jsonc:1-8`). Its file set excludes `.beep`, `.repos`, generated output, `scratchpad`, and several generated standards files (`biome.jsonc:17-49`). Those exclusions matter for rollout planning: a rule placed only in the current root config would not inspect those trees.

Import-relevant built-ins and assists are:

- `organizeImports` is enabled, with value imports grouped before type imports (`biome.jsonc:84-105`). This sorts and groups existing declarations; the config contains no module-specifier rewrite.
- `noUnusedImports` is an error with autofix disabled (`biome.jsonc:143-148`).
- `noDeprecatedImports` is an error (`biome.jsonc:163-169`).
- `useImportType` is an error and requires separated type imports (`biome.jsonc:195-202`). The migration must therefore handle type-only declarations without merging them back into value imports.

All four shipped GritQL rules are registered. `no-empty-named-blocks` and `prefer-array-flat-map` are root plugins (`biome.jsonc:9-16`); `no-native-error` applies only to `packages/tooling/**/src/**` and `no-bigint-literals` to source roots and `infra` through overrides (`biome.jsonc:217-234`). Their actual diagnostics are:

| GritQL rule | Actual severity | What it enforces | Import-convention effect |
| --- | --- | --- | --- |
| `no-empty-named-blocks` | error | Rejects `import {} from "..."` (`packages/tooling/policy-pack/lint-rules/rules/no-empty-named-blocks.grit:1-5`). | Import-adjacent, but neutral on barrel versus subpath. It can catch a bad codemod remnant. |
| `prefer-array-flat-map` | error | Replaces `.map(f).flat()` with `.flatMap(f)` (`packages/tooling/policy-pack/lint-rules/rules/prefer-array-flat-map.grit:1-6`). | No change needed. |
| `no-native-error` | error | Rejects `new Error(...)` and explicitly tells users to use `S.TaggedError` from `effect/Schema` (`packages/tooling/policy-pack/lint-rules/rules/no-native-error.grit:1-7`). | Its fix text already teaches a per-module Effect import. Keep it. |
| `no-bigint-literals` | warn | Rejects bigint literal syntax in favor of `BigInt(value)` (`packages/tooling/policy-pack/lint-rules/rules/no-bigint-literals.grit:1-7`). | No change needed. |

The root comment says these rules ship at `warn` (`biome.jsonc:9-12`), but three rule files register `error`. The typed registry agrees with the rule files: `no-native-error`, `no-empty-named-blocks`, and `prefer-array-flat-map` are errors; only `no-bigint-literals` is a warning (`packages/tooling/policy-pack/lint-rules/src/index.ts:199-228`). Treat the file severities, not the stale root comment, as the gate behavior.

### Existing Effect import migration law

The repo already has a ts-morph import rewriter/checker. It starts from app, package, and infrastructure TypeScript globs (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:92-97`), but then applies shared exclusions that remove `/test/`, `/tests/`, `*.test.*`, `*.spec.*`, stories, generated code, docs, and other non-production paths (`packages/tooling/library/repo-utils/src/schemas/TypeScriptSourceExclusions.ts:30-74`, `packages/tooling/library/repo-utils/src/schemas/TypeScriptSourceExclusions.ts:117-122`). It also excludes **all ecosystem member source** (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:125-140`). Both the test exclusion and ecosystem exemption are incompatible with the settled scope; the current tests assert that even explicit-include scans skip ecosystem members (`packages/tooling/tool/cli/test/effect-imports.test.ts:132-159`). It currently implements a mixed policy:

- It converts exactly eight helper symbols—`Array`, `Option`, `Predicate`, `Record`, `Schema`, `String`, `Equal`, and `Boolean`—from the root only when the named import already has the expected short alias (for example, `Schema as S`) (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:81-90`, `packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:195-215`). Plain `Effect`, `Config`, `Layer`, `Match`, and unaliased helper imports are left on the barrel.
- It enters that root-import conversion branch only for value imports, so a root `import type { ... } from "effect"` is invisible to the law (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:195-198`). This misses the settled type-only scope.
- It excludes `effect/Function` from reverse conversion (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:98-103`).
- For every other single-segment stable `effect/*` module that lacks a listed short alias, it converts a namespace subpath import back into a named import from the root `effect` barrel (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:230-295`).
- It skips `effect/unstable/*`, nested stable subpaths, and type-only imports in that reverse-conversion branch (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:100-103`, `packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:255-266`).
- In check mode, any proposed alias rename or stable conversion fails the command (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:298-323`).

This law actively fights the settled full migration. For example, `import * as Config from "effect/Config"` is rewritten to `import { Config } from "effect"`. Its tests explicitly require `effect/Duration` to be rewritten to the root (`packages/tooling/tool/cli/test/effect-imports.test.ts:52-130`). The law and those fixtures must be replaced or inverted before an enforcement ratchet can require per-module imports, and the ecosystem exemption must be deleted. Its current `effect/Function` exception happens to agree with the new decision, but the planned rule should make `pipe`, `flow`, and `identity` named imports from that subpath rather than treating it as a one-off exception.

This is not an isolated advisory command. The root lint-policy battery runs `laws effect-imports --check` (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1835-1867`), and CI makes that battery a full-tree sweep even though local policy runs scope applicable laws to changed files (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1927-1948`). More critically, Yeet's deterministic repair phase runs `beep laws effect-imports --write` before config generation, formatting, and docgen (`packages/tooling/tool/cli/src/commands/Yeet/internal/Planner.ts:255-280`). The law therefore must flip before the first migration batch enters the normal repair/verify workflow.

### Oxlint: incumbent, narrow, and currently neutral

Oxlint is already an incumbent repository tool, not merely a candidate new dependency. Its root config deliberately disables every native rule category and loads only the repo's JavaScript plugin (`.oxlintrc.json:1-21`). The blocking lint-policy lane invokes it with `--quiet`, so only rules configured as errors gate CI; warnings remain visible only in the verbose standalone lane (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1864-1867`).

Two configured rules touch import syntax:

- `beep/no-js-extension-imports` is an error (`.oxlintrc.json:37-40`). It examines imports, re-exports, dynamic imports, and TypeScript import types, but only when a relative specifier ends in `.js`, `.jsx`, `.mjs`, or `.cjs` and the runtime-spelled path does not exist (`packages/tooling/policy-pack/lint-rules/src/rules/no-js-extension-imports.ts:17-43`, `packages/tooling/policy-pack/lint-rules/src/rules/no-js-extension-imports.ts:62-109`). It is neutral on package barrels versus package subpaths and needs no convention edit.
- `beep/namespace-node-imports` is a warning (`.oxlintrc.json:40-43`). It applies only to `node:` built-ins and requires a canonical `Node...` namespace alias (`packages/tooling/policy-pack/lint-rules/src/rules/namespace-node-imports.ts:16-49`, `packages/tooling/policy-pack/lint-rules/src/rules/namespace-node-imports.ts:69-91`). It neither conflicts with nor enforces the planned Effect/foundation convention.

The other four configured plugin rules do not inspect module specifiers (`.oxlintrc.json:37-44`). No current Oxlint rule bans `effect` or foundation package roots. Oxlint could host a future path-aware rule, but the migration does not need to change its existing import rules.

### ESLint profiles

The root ESLint entry point exposes exactly two profiles: `docs` by default and `deprecated-apis` when `BEEP_ESLINT_PROFILE` selects it (`eslint.config.mjs:1-20`). Neither profile enforces import organization or barrel/subpath selection:

- `DeprecatedApisESLintConfig` covers TypeScript under `apps`, `packages`, and `infra`, subject to generated/build/test-type exclusions (`packages/tooling/policy-pack/repo-configs/src/eslint/DeprecatedApisESLintConfig.ts:18-44`, `packages/tooling/policy-pack/repo-configs/src/eslint/DeprecatedApisESLintConfig.ts:90-129`). Its only rule is `@typescript-eslint/no-deprecated: error` (`packages/tooling/policy-pack/repo-configs/src/eslint/DeprecatedApisESLintConfig.ts:130-134`). The repo CLI runs it across explicit workspace-family shards with the profile environment set (`packages/tooling/tool/cli/src/commands/Lint/Lint.command.ts:47-77`, `packages/tooling/tool/cli/src/commands/Lint/Lint.command.ts:466-521`).
- `DocsESLintConfig` applies detailed JSDoc rules to public tooling source (`packages/tooling/policy-pack/repo-configs/src/eslint/DocsESLintConfig.ts:65-97`, `packages/tooling/policy-pack/repo-configs/src/eslint/DocsESLintConfig.ts:135-217`), a file-overview rule to tooling barrels (`packages/tooling/policy-pack/repo-configs/src/eslint/DocsESLintConfig.ts:227-252`), and a TSDoc syntax warning to most app/package/infra production TypeScript (`packages/tooling/policy-pack/repo-configs/src/eslint/DocsESLintConfig.ts:253-285`). None of those rules inspects import paths.

The only ESLint configurations exported by the package root are these two values and their shapes (`packages/tooling/policy-pack/repo-configs/src/index.ts:8-11`, `packages/tooling/policy-pack/repo-configs/src/index.ts:97-118`), while its package map permits both the root and per-module config paths (`packages/tooling/policy-pack/repo-configs/package.json:58-64`). ESLint therefore needs no rule edit for the law flip. Its own source and JSDoc examples still participate in the general source/example migration where they import a scoped root, but that is corpus work rather than an ESLint configuration conflict.

### Repo CLI import and module policies

The root `bun run beep lint` path runs Turbo package lint together with the repo-policy steps for an unscoped, non-fix invocation (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1971-2017`). The import/module/export-relevant policy steps are:

- **Effect imports — required:** the conflicting check described above (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1854-1863`).
- **Package test imports — required:** package-level tests may not reach into any workspace package's `src` tree with relative imports. The analyzer covers static imports, re-exports, and dynamic imports (`packages/tooling/tool/cli/src/commands/Lint/PackageTestImports.ts:208-250`), then reports the corresponding `@beep/<package>/<source-subpath>` alias (`packages/tooling/tool/cli/src/commands/Lint/PackageTestImports.ts:253-329`). This supports the new convention because it preserves a source subpath when one exists; it does not force the package root.
- **Circular imports — required but narrow:** Madge checks only the repo CLI and repo-utils source trees and skips type-only imports (`packages/tooling/tool/cli/src/commands/Lint/Lint.command.ts:416-464`). It is neutral on barrels versus subpaths, although the rewrite can reveal or remove cycles and should rerun it.
- **Oxlint — errors required, warnings advisory:** the `--quiet` policy invocation gates the two error rules while suppressing warnings (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1864-1867`). Existing import rules are neutral, as above.
- **Docgen and JSDoc — required:** policy runs docgen checking and ESLint with `--max-warnings=0`, so even rules configured as warnings become blocking in this lane (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1839-1850`). Their treatment of imports inside examples is inventoried below.
- **TypeScript/plugin policy — required:** `lint:package-test-typecheck` and `lint:tsgo-rules` are in the same battery (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1862-1864`). They do not currently encode a root-barrel ban, but resolution and the namespace-import completion preference matter below.

No live `repo-exports` catalog check is present in the quality battery (`packages/tooling/tool/cli/src/commands/Quality/Tasks.ts:1835-1883`). Barrels are still generated as export surfaces by codegen; that is deliberately compatible with the settled decision to retain barrels and ban importing through them, so export generation itself does not need removal.

## 2. Resolution, package exports, and architectural boundaries

### TypeScript and tsgo

The base compiler contract is strict ESM with `module`/`moduleResolution` set to NodeNext and `verbatimModuleSyntax: true` (`tsconfig.base.json:4-20`). `noUnusedLocals` and `noUnusedParameters` are also enabled (`tsconfig.base.json:25-36`). Consequently, the codemod must preserve value-versus-type intent and cannot rely on TypeScript eliding an incorrectly emitted value import.

The Effect language-service configuration has two convention-relevant settings:

- `namespaceImportPackages` contains `effect`, `@effect/*`, and `@beep/*`, and the short aliases map `Array`, `Option`, `Predicate`, `Record`, `Schema`, and `Equal` to the repository spellings (`tsconfig.base.json:38-55`). This is completion/import-form guidance, not a diagnostic in the explicit all-errors severity map (`tsconfig.base.json:56-157`). It generally supports namespace imports, but its broad root patterns can still suggest a namespace import from a now-banned root, and the `effect/Function` named-import exception cuts across the general preference. Pilot the auto-import experience and narrow or document this setting if needed.
- No `barrelImportPackages` setting is configured in the repo. The installed tsgo documentation distinguishes `namespaceImportPackages` (prefer namespace imports) from `barrelImportPackages` (prefer barrel named imports) and defaults both to empty (`node_modules/@effect/tsgo/README.md:251-258`). There is therefore no tsgo barrel-preference setting to remove.

The root `tsconfig.json` path table already resolves `@beep/utils/*` directly to `src/*` and has both root and subpath entries for other workspaces (`tsconfig.json:37-70`). Those entries are generated from each workspace's `package.json` export map: descriptor construction reads root, wildcard, concrete-subpath, and scoped-wildcard exports (`packages/tooling/tool/cli/src/commands/TsconfigSync/TsconfigSync.plan.ts:282-351`); the planner emits the package root, a package wildcard when available, and concrete/scoped subpaths (`packages/tooling/tool/cli/src/commands/TsconfigSync/TsconfigSync.plan.ts:492-587`, `packages/tooling/tool/cli/src/commands/TsconfigSync/TsconfigSync.plan.ts:618-673`).

That yields two important migration constraints:

- `@beep/utils/Predicate` resolves today because `@beep/utils` exports both `.` and `./*` in source and publish maps (`packages/foundation/modeling/utils/package.json:47-68`), and the root config has the matching wildcard alias (`tsconfig.json:43-46`).
- Not every foundation package has a blanket wildcard. `@beep/schema`, for example, enumerates public modules such as `LiteralKit` and `SchemaUtils`, blocks their private descendants where appropriate, and exposes only a scoped wildcard under `SchemaUtils` (`packages/foundation/modeling/schema/package.json:49-75`, `packages/foundation/modeling/schema/package.json:180-202`, `packages/foundation/modeling/schema/package.json:230-247`). The publish map mirrors those subpaths (`packages/foundation/modeling/schema/package.json:455-480`, `packages/foundation/modeling/schema/package.json:505-524`). A foundation codemod must choose an exported module path, not mechanically derive a path from the source filename. If a desired per-module API is not exported, add the package export first and let tsconfig-sync regenerate aliases.

Effect v4 itself supports the proposed stable-module shape: its package exports the root, named unstable groups, and a stable `./*` file wildcard while blocking internal and `/index` spellings (`.repos/effect/packages/effect/package.json:29-56`). `effect/Effect`, `effect/Schema`, and `effect/Function` therefore resolve in both NodeNext and Bundler projects.

Most build configs inherit the base NodeNext settings directly; `@beep/utils` and `@beep/schema` are representative (`packages/foundation/modeling/utils/tsconfig.json:1-20`, `packages/foundation/modeling/schema/tsconfig.json:1-26`). Their check configs deliberately switch to ESNext/Bundler with no emit (`packages/foundation/modeling/utils/tsconfig.check.json:1-14`, `packages/foundation/modeling/schema/tsconfig.check.json:1-14`). Browser apps also use Bundler and `isolatedModules`; for example, OIP does so while providing only app/UI-specific paths (`apps/oip-web/tsconfig.json:13-29`, `apps/oip-web/tsconfig.json:138-151`), and Professional Desktop does the same with a broad workspace alias set (`apps/professional-desktop/tsconfig.json:14-35`). These deviations do not reject per-module imports, but they make package-export correctness—not only the root `paths` table—a required pilot and batch check.

The other material deviations are finite:

- The four app configs for Trustgraph Workbench, OIP, Professional Desktop, and Storybook use Bundler plus `isolatedModules`; Trustgraph has only its local `@/*` path and Storybook maps `@beep/ui` plus its wildcard (`apps/labs/trustgraph-workbench/tsconfig.json:11-27`, `apps/storybook/tsconfig.json:11-28`). OIP and Professional Desktop are cited above.
- Storybook's separate stories config carries explicit foundation/driver root and wildcard aliases (`apps/storybook/tsconfig.stories.json:15-42`). The UI package has self-root and `lib` wildcard aliases (`packages/foundation/ui-system/ui/tsconfig.json:5-17`), while ontology-server has two driver aliases (`packages/ontology/server/tsconfig.json:5-12`). These mappings can resolve an exported subpath directly, but imports not listed there still rely on package exports.
- Dock, Dock React, Editor, and UI build configs choose ESNext/Bundler instead of inherited NodeNext; Dock is representative (`packages/foundation/ui-system/dock/tsconfig.json:1-10`) and UI combines that mode with its local paths (`packages/foundation/ui-system/ui/tsconfig.json:5-17`).
- The Lambda cache and generated runner SDK configs are standalone NodeNext projects rather than extensions of the base config (`infra/lambda/turbo-cache/tsconfig.json:1-12`, `infra/ci-runners/sdks/ghaRunners/tsconfig.json:1-19`). They do not inherit `verbatimModuleSyntax` or the tsgo plugin, so the enforcement rule—not editor/compiler preferences—must cover them.

None of these deviations defines a root-only Effect or foundation mapping. Test every pilot under at least one inherited NodeNext build, one Bundler check, one isolatedModules app, and docgen's package-export-only example harness.

No live package manifest, TypeScript alias, source import, or Fallow zone named `@beep/invariant` was found in this checkout. Treat that name in the future packet as a planned package or scope label until a concrete workspace exists; do not invent an alias in the migration rule.

### Fallow

Fallow models reachability, unresolved imports, unused dependencies, and package-to-package boundaries. Its root entries deliberately include top-level package modules because they are public package exports (`.fallowrc.jsonc:3-18`), and it has a narrow allowlist for TypeScript-to-TSX resolution gaps rather than a broad unresolved-import exemption (`.fallowrc.jsonc:82-96`, `.fallowrc.jsonc:136-152`). A mass rewrite should therefore run Fallow to catch misspelled or unexported paths.

The generated boundary file extends the root config (`standards/fallow.boundaries.generated.jsonc:1-6`), maps each package's complete `src/**` tree to a package zone—for example, `@beep/schema` and `@beep/utils` (`standards/fallow.boundaries.generated.jsonc:645-649`, `standards/fallow.boundaries.generated.jsonc:747-750`)—and grants dependencies by zone, with separate value and type-only allowlists (`standards/fallow.boundaries.generated.jsonc:795-830`). Root and subpath imports that resolve into the same package source tree therefore have the same boundary result. Fallow does not require a barrel spelling or ban a per-module spelling.

Boundary violations are currently configured as warnings (`standards/fallow.boundaries.generated.jsonc:3453-3457`). The root scripts expose config generation/checking plus dead-code, health, and audit lanes (`package.json:330-341`). No Fallow configuration edit is required for the convention flip; regeneration is needed only if package exports/dependencies change, and the CI lane remains useful migration evidence.

## 4. JSDoc and docgen behavior

Docgen parses JSDoc descriptions and tags with Doctrine (`packages/tooling/tool/docgen/src/Parser.ts:139-176`). That means the repository's titled `**Example**` sections are part of the description, not a special custom AST node. Docgen scans those descriptions and legacy `@example` tag values for TypeScript fences (`packages/tooling/tool/docgen/src/Core.ts:306-365`), emits each fence as a source file, builds an importing entry point, and creates an examples tsconfig (`packages/tooling/tool/docgen/src/Core.ts:335-455`, `packages/tooling/tool/docgen/src/Core.ts:547-570`). It then runs the configured compiler with `--noEmit --project`; packages may also execute examples with Bun (`packages/tooling/tool/docgen/src/Core.ts:488-545`). The main workflow always couples module checks with example typechecking before reporting success (`packages/tooling/tool/docgen/src/Core.ts:768-801`).

The canonical harness uses Bundler resolution, ES2022 modules, and `verbatimModuleSyntax`; representative foundation configs show the same options (`packages/tooling/library/repo-utils/src/schemas/DocgenConfig.ts:457-495`, `packages/foundation/modeling/utils/docgen.json:1-31`, `packages/foundation/modeling/schema/docgen.json:1-31`). At load time docgen forces TypeScript extension support, disables unused-binding diagnostics for illustrative examples, and adds Node/Bun types (`packages/tooling/tool/docgen/src/Configuration.ts:586-606`). It does not rewrite an example's import statement.

Per-module imports compile under this harness when the target is in the dependency's package export map. Managed `@beep/*` `paths` entries are intentionally removed from docgen configs because examples resolve workspace packages through `node_modules` symlinks and package exports; package-local custom aliases survive (`packages/tooling/library/repo-utils/src/schemas/DocgenConfig.ts:498-508`, `packages/tooling/library/repo-utils/src/schemas/DocgenConfig.ts:559-619`). Thus `effect/Effect` and `@beep/utils/Predicate` work, while a guessed unexported foundation path fails—which is the desired feedback.

Live verification used a temporary no-emit ESNext/Bundler/`verbatimModuleSyntax` probe with Node/Bun types and imports from `effect/Effect`, `effect/Function` (`flow`, `identity`, `pipe`), `@beep/utils/Predicate`, and `@beep/schema/LiteralKit`. `node_modules/.bin/tsgo --noEmit --project <probe>` exited 0; the temporary probe files were removed. This confirms the representative paths under the same resolution family as docgen, not every future foundation subpath.

The JSDoc inventory has a separate import-style detector. Today it rejects deprecated `@effect/schema` and named imports from exactly five module paths—`effect/Schema`, `Array`, `Option`, `Predicate`, and `Record`—unless the canonical namespace alias is present (`packages/tooling/tool/cli/src/commands/Quality/internal/JSDocDocumentationInventory.ts:601-646`). It does **not** flag `from "effect"` or scoped foundation roots. If JSDoc examples are in enforcement scope, extend this detector when the law flips; otherwise examples can keep teaching barrels even after source lint is green. Re-export declarations are deliberately exempt from documentation completeness, but their comments still run the import/example checks (`packages/tooling/tool/cli/src/commands/Quality/internal/JSDocDocumentationInventory.ts:855-883`).

The detector's named-import regex accepts either quote style, but its wrong-alias follow-up searches only the double-quoted `from "<module>"` spelling (`packages/tooling/tool/cli/src/commands/Quality/internal/JSDocDocumentationInventory.ts:620-642`). Make the new root checks quote-style independent rather than copying that blind spot.

The inventory feeds a hosted JSDoc ratchet that fails when tracked totals grow (`packages/tooling/tool/cli/src/commands/Quality/internal/JSDocRatchet.ts:343-387`). The lane descriptor marks that hosted context non-required (`packages/tooling/tool/cli/src/commands/Ci/CiLane.ts:456-462`), although it is still a visible failing job and the root preflight runs it (`package.json:303-310`). Docgen itself is required in both lint-policy and the dedicated Docgen context, so stale or broken example imports remain blocking even before the inventory learns the new root ban.

One-shot migration warning: a ts-morph codemod that visits only `ImportDeclaration` nodes will not touch imports embedded in comments. The migration needs an explicit Markdown/JSDoc-fence pass, followed by docgen, or the written corpus above will retain the old convention.

The comment corpus is material, not an edge case. A live exact-line census found 1,906 comment-prefixed root-`effect` import lines across 723 app/package/infra TypeScript files, plus 627 comment-prefixed `@beep/utils`, `@beep/schema`, or `@beep/identity` root import lines across 160 files. Reproduce those counts with:

```bash
rg -n '^\s*\* ?import .* from ["'"']effect["'"']' apps packages infra --glob '*.{ts,tsx}' | wc -l
rg -l '^\s*\* ?import .* from ["'"']effect["'"']' apps packages infra --glob '*.{ts,tsx}' | wc -l
rg -n '^\s*\* ?import .* from ["'"']@beep/(utils|schema|identity)["'"']' apps packages infra --glob '*.{ts,tsx}' | wc -l
rg -l '^\s*\* ?import .* from ["'"']@beep/(utils|schema|identity)["'"']' apps packages infra --glob '*.{ts,tsx}' | wc -l
```

These are corpus counts, not four additional enforcement mechanisms. The reason they matter is that docgen extracts comment fences verbatim (`packages/tooling/tool/docgen/src/Core.ts:306-365`), while the current source import law operates on ts-morph import declarations (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:195-323`). The migration tool must cover both representations.

Scaffolding also teaches future code and must be fixed at the generator rather than only in generated files:

- The service-app templates emit root imports for `Config`, `Effect`, `Layer`, `Context`, and `Match` (`packages/tooling/tool/cli/src/commands/CreatePackage/templates/app-service-src-main.ts.hbs:1-5`, `packages/tooling/tool/cli/src/commands/CreatePackage/templates/app-service-src-runtime-Layer.ts.hbs:1-3`, `packages/tooling/tool/cli/src/commands/CreatePackage/templates/app-service-test-health.test.ts.hbs:1-8`).

That remains correct as export/discovery guidance and needs no edit; it does not tell consumers to import through the barrel.

## 5. Export-surface mechanisms and retired catalog residue

## C. Mechanisms that would fight or undermine the migration

1. **Direct reversal by repair tooling:** `laws effect-imports --write` converts most stable namespace submodule imports back to root named imports, and Yeet repair runs it automatically before formatting/docgen (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:230-295`, `packages/tooling/tool/cli/src/commands/Yeet/internal/Planner.ts:255-280`). This must flip first.
2. **False-green enforcement scope:** the same law excludes all conventional tests/stories, every ecosystem member, and root type-only imports (`packages/tooling/library/repo-utils/src/schemas/TypeScriptSourceExclusions.ts:30-74`, `packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:125-140`, `packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:195-198`). Leaving those exclusions would violate the settled scope while CI reports green.
3. **Authoritative contradictory guidance:** root agent law, Effect laws, EF-4, JSDoc law, and effect-first/JSDoc skill references explicitly teach the root exception (Section 3). If enforcement flips before these files, agents and reviewers will be instructed to reintroduce violations.
4. **Generators that recreate violations:** service scaffolds and architecture shell generation emit root Effect imports, while identity scaffolding emits a root foundation import (`packages/tooling/tool/cli/src/commands/CreatePackage/templates/app-service-src-main.ts.hbs:1-5`, `packages/tooling/tool/cli/src/commands/Architecture/internal/PackageShell.ts:378-420`, `packages/tooling/tool/cli/src/commands/CreatePackage/internal/IdentityExportBlock.ts:48-68`). Fix generator sources, not only existing outputs.
5. **Comment blind spot:** the ts-morph source law does not see imports inside JSDoc/Markdown, and the current JSDoc detector does not ban root packages (`packages/tooling/tool/cli/src/commands/Laws/EffectImports.ts:195-323`, `packages/tooling/tool/cli/src/commands/Quality/internal/JSDocDocumentationInventory.ts:601-646`). A source-only codemod/check can therefore leave a large, compiling old-style documentation corpus behind.
6. **Auto-import drift risk:** tsgo's broad namespace preference includes the root strings `effect` and `@beep/*` (`tsconfig.base.json:38-55`). This is not a hard failure today, but pilot it before ratcheting: editor suggestions that keep selecting forbidden roots would continually fight the lint rule.
7. **Unexported guessed subpaths:** docgen deliberately removes `@beep/*` path shortcuts and resolves package exports (`packages/tooling/library/repo-utils/src/schemas/DocgenConfig.ts:498-508`). This is a useful gate, not a defect, but a naive symbol-to-filename rewrite will fail whenever a curated package such as `@beep/schema` lacks that export (`packages/foundation/modeling/schema/package.json:49-75`). Plan export additions before the batch rewrite.

No current Biome/GritQL rule, ESLint rule, Oxlint rule, Fallow boundary, TypeScript module mode, docgen transform, or barrel generator independently flags a valid exported per-module import. Once the existing Effect law, written laws, generators, and comment detector are corrected, the incumbent toolchain supports the migration without adding a permanent linter.
