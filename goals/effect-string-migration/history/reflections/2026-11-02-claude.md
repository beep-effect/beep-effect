## Tooling experience

- **Worked:** `goals completion refresh --slug effect-string-migration` with the
  copied verdict run directory re-derived `verified` from live GitHub facts in
  one run; `goals doctor` dropped the packet from `completion-gate-unknown`.
- **Didn't:** `goals doctor`, `goals explain` and `session open` could not say
  that another clone already held the receipt.
- **Frustrating:** the receipt is clone-scoped and the verdict is gitignored, so
  "is this goal done" needs a hand census across clones.
- **Wished existed:** `completion refresh --import-run <clone>` that copies the
  run directory itself.

## Implementation improvement opportunities

- None in the migrated code. The rule is armed at `error`; a regression fails
  `Heavy / Check` before it merges.
- The packet CLI: a sibling-clone receipt lookup in `goals doctor` (see
  findings) would have made this closeout a one-command check.

## Goal & prompt critique

The brief assumed the closeout still needed a new final PR through the STRICT
route. Opening one would have changed `finalPullRequest`, which enters the
declaration digest and would have invalidated the verified receipt for #2324.
The right first step was the receipt census, and the brief should say so: "find
the verdict run directory and receipt for the final PR across clones before
planning a new final PR."

## Lessons (confidence-tiered)

- **HIGH — Critical:** Before planning a new closeout PR, census every clone's
  `completion-receipts.ndjson` for `(packet, finalPullRequest)` and the verdict
  run directory. A new final PR invalidates a receipt that already verifies.
- **MEDIUM — Best practice:** Re-derive a receipt by copying the run directory
  bytes unchanged, checking its sha256, and refreshing once; back up the ledger
  first.
- **LOW — Consideration:** The verifying session should flip P3, README and
  write the `completion-verified` note immediately, so the packet never reads
  open after its gate is satisfied.
