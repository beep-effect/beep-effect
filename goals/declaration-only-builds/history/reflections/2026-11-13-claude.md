# Reflection — declaration-only-builds (2026-11-13, claude)

## Summary

Library builds now emit declarations and declaration maps only, and a package's
sources are type-checked once per check run: its check runs the build program
after its own build. Three work PRs landed in plan order (#3178, #3208, #3242),
with two small fixes for inherited reds found on the way (#3192, #3206).
Measured back to back, serial build work fell from 80.9 s to 32.9 s and `dist`
from 232.5 MB to 147.9 MB; a full check run does 15.5 s less compiler work.

## Tooling experience

- **Worked:** the retirement rule in the scripts policy, once written, moved
  182 manifests with one `--write` and keeps the lint honest afterwards. The
  census build-equivalence mode gave a yes-or-no answer per package for
  diagnostics and, later, file sets. `yeet open` for a committed head was the
  reliable way to push while `main` moved several times an hour. Delegated
  children that wrote their report to a file before long verification were
  easy to check and to resume.
- **Didn't:** local final-check under load. Coverage took 45 minutes and timed
  out one unrelated test; skipping it then let three introduced reds reach
  hosted CI on PR 3. `yeet publish --push-only` refused every base-sync merge
  that needed a regenerated file, so each one went through `yeet open`.
- **Frustrating:** every merge of `main` into PR 2 conflicted in generated
  state (cache baseline, lockfile, policy seal, skills lock) because other
  lanes regenerate the same files. PR 2 was merged from `main` five times in
  two hours before it could open.
- **Wished existed:** a hosted census gate; a single command that re-records
  the cache baseline from the current audit and a review file; a final-check
  that knows its PR already merged.

## Implementation improvement opportunities

- `tsconfig.check.json` now has no script reader in 180 packages. It is kept
  for the overlay census and editors; if the census moves to the build
  program, those files can go.
- `@beep/effect-drizzle` and `@beep/markdown` keep the no-emit check because
  their check config includes `scripts`. Moving those scripts to their own
  config, as other packages do, would let both be served by the build.
- `tsconfig.tsbuildinfo` is 63 MB of the 148 MB a build still writes and
  caches. Nobody has asked whether all of it has to travel through the cache.
- `TSRS_FAST` is part of the compiler's incremental state, so builds made by
  lanes with different settings are never shared. Setting it the same way in
  generated builds and in the quality runner would make them one cache key.

## Goal & prompt critique

- The outcome sentence was right and survived contact. Two SPEC details did
  not: the file the emit option was to go in, and the implied size of the
  check-once saving. Both needed one cheap experiment that the exploration
  could have run.
- "Three PRs at most" was a good constraint for the work PRs. It should say
  that fixes for inherited reds and the goals-only final are counted apart, so
  an agent does not fold a `main` fix into a work PR to stay under the cap.
- Proposed edit to `GOAL.md`: add to the workflow list, "Before changing a
  shared config, compile one consumer of it with the change applied", and to
  the done list, "open the final as a goals-only PR and hold it with one
  unresolved review thread until the readiness monitor reports".

## TODOs worth codifying

- Hosted check-census gate, or a compiler-bump gate on the baseline stamp.
- A per-checkout lock for `yeet final-check`, and self-cancel on merge.
- A runbook section on the scripts policy retirement tables.
- A clearer message from the knowledge gate for document-relative paths.

## Lessons (confidence-tiered)

- **HIGH — Critical:** measure before and after in one job on one machine
  state — the first baseline and the first after-run were days apart under
  different load and compilers, and would have shown a compile speed-up that
  does not exist.
- **HIGH — Critical:** check whether a compiler setting is part of incremental
  state before making one pass reuse another's output — `TSRS_FAST` rewrites
  the build info, which decided how check-once could be built soundly.
- **MEDIUM — Best practice:** when a gate is skipped for compute, run the
  touched package's own suite once before the first push — hosted CI found
  three reds that a ten-minute local run would have.
- **MEDIUM — Best practice:** after every merge of `main`, re-run the
  generators and the cache-policy gate before anything else — an inherited
  red there blocks the publish and looks like your own.
- **LOW — Consideration:** a saving of seconds can still be worth a change
  when it removes a second source of truth; say that plainly in the PR, with
  the number.
