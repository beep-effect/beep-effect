### 1.1 Schema construction rules

The P4 and P5 rules carry over: every exported schema carries an `$I.annote*` description from its
package composer; class schemas use `extends Parent.extend<X>()({})`; string-literal domains use
`LiteralKit` without `as const`; set-valued fields use `effect/HashSet` or `effect/HashMap`, encoded
through the `CanonicalHashSet` construction (`packages/foundation/modeling/schema/src/CanonicalHashSet.ts:64`)
wherever the wire form must be deterministic; every effectful function is `Effect.fn` (a literal
name, so the instrumentation harvester sees it) or `Effect.fnUntraced`; no free comments. Values
that hold functions (`Operation`, `ActivityDescriptor`, port shapes) are interfaces or `Context.Service`
shapes, not schemas.

### 1.3 Identity and preimages

One new preimage is defined, `law-distinction/v1` for `DistinctionId` (section 1.2), with a frozen
golden in its definition. `ActivityRecord.id` is the existing `activity/v1` id minted by
`mintActivityId` (`jsonc/src/ActivityStart.ts:221-226`) over the start facts only; `generated`,
`ended` and `outcome` stay outside it (decision `2026-11-19-p0-activity-id-minted-at-start`). The
law claim id is the existing `claim/v1` (`epistemics/src/ClaimCore.ts:77`) over `LawClaimCore`.
The `claim/v1` preimage also hashes `generatedBy` and `knowledgeStart` (`ClaimCore.ts:78-95`), so
any two runs give two ids even within one matter, and "two matters give two ids" proves nothing by
itself. The scope case is therefore stated on cores: two `LawClaimCore` values identical except
for `scope` (same proposition, support, `generatedBy` and `knowledgeStart`) mint different ids, and
two identical cores mint the same id. Both cases run in `lp/domain/test/LawClaim.identity.test.ts`
(row 7), and the two-matter test repeats the first over the A and B captures of the fixture.

`scopeRef` bytes are never re-spelled. They are hashed into `CaptureId` and `OccurrenceId` (P3
capture decision, `SPEC.md:1539`), so a matter-scheme rewrite would change every stored occurrence
id. The wall binds existing spellings (`workspace:<id>` from the workspace resolver,
`workspace/server/src/SourceText/WorkspaceSourceTextResolver.ts:152`, and fixture keys) to a matter
through `MatterScope` instead (decision `matter-authority-port-principal-and-scope-bindings`).

Moved nlp schemas take identifiers under `$NlpProcessingId` (`identity/src/packages.ts:820`), the
P2 precedent (decision `2026-11-22-p2-schema-identifiers-follow-the-package`). No stored row holds a
Core or Graph schema identifier (section 9.1).

## 3. Pure functions and law interpretation

### 3.1 The arrow

`Operation` adopts the sketch (`ops/design/L5.operations.ts:27-30`). `compose` fixes one `(E, R)`
for both sides; the live `Composable.compose` unions them (`nlp/src/Operations/Composable.ts:528-545`),
which makes `compose(pure(identity), f)` a different type from `f`, so the hom-sets are not a
category. `pure` returns a `Pure<A, B>`, an `Operation<A, B, never, never>` carrying a brand that
only `pure` sets, so no effectful arrow can claim to be pure; its run is `Effect.sync(() => f(a))`,
which for a total `f` is observationally the live `flow(f, Effect.succeed)` of `makePureOperation`
(`Composable.ts:368`) and the report's `Effect.succeed(f(a))` (`rebuild-report.md:288`), while a
throwing `f` is a defect inside the effect rather than an exception at call time. Identity needs no
export: L5-1 uses `pure({ name, f: identity })`. Input and output schemas leave the arrow; a tool
attaches its schemas in its own `Tool.make` (section 6). The arrow's `name` is a `TermIri`
(`identity/src/Term.ts:49-60`).

Every combinator suspends its components' `run` (`Effect.suspend`, `Effect.ts:1220`, evaluated
inside the fiber like `Sync`, `internal/effect.ts:1048-1056`), so building a composite runs no
user code and a component that throws when called is a defect of the composite's effect. The
sketch's `flow(self.run, Effect.flatMap(that.run))` (`ops/design/L5.operations.ts:57-77`) and the
live `product` (`Composable.ts:238`) call `self.run(a)` eagerly.

`product` runs `self` then `that` on the same input (`Effect.all([...], { concurrency: 1 })`, the
live order, `Composable.ts:238`). `commute(p, q)` is the one production interchange: it runs `q`
before `p` and returns the pair in `product` order, and it accepts only a `Pure` on the left, which
is the `commutes` witness the report requires before interchange is claimed
(`rebuild-report.md:286`). `traverse` runs left to right. `aggregate` is deleted with the local
`Monoid`; a caller folds with `Reducer.combineAll`.

Graph catalog steps. A `GraphOperation` carries an `Operation` (O6), whose `name` is a `TermIri`,
and the `ResultStore` keys results by operation name and node id
(`np/src/Graph/GraphOperations/ResultStore.ts:118-128`), so ten catalog steps sharing a parent term
would collide in the cache. Row 3 declares ten `operation:` terms for the catalog steps
(`Catalog.ts:65,95,126,156,186,217,251,271,291,311`): `Sentencize`, `Tokenize`, `PosTag`,
`Lemmatize`, `ExtractEntities`, `ParseDependencies`, `ExtractRelations`, `ToLowerCase`,
`ToUpperCase` and `Trim`. `GraphOperation.name: string` (`Operation.ts:68`) is removed, and
`ResultKey.operationName` carries the term IRI string; the cache is in-process, with no stored
reader (decision `graph-catalog-steps-declare-operation-terms`).

### 3.2 The declared observation

The report defines the observation as the `Exit` of a run plus a `Ref` trace
(`research/2026-11-08-rebuild-report.md:288`). P6 states it as a test-support function, in
`np/test/support/OperationObservation.ts`:

- The trace is a `Ref<ReadonlyArray<number>>` (`Ref.ts:178`, `get` `:206`, `update` `:587`) held
  by a test-local `Trace` service. Each generated operation appends its event label before it
  succeeds or fails, so a reordering or a skipped effect is visible.
- A run is observed as `Effect.exit(Effect.suspend(() => op.run(x)))` (`Effect.ts:2504,1220`)
  under a fresh `Trace`, so an operation whose `run` throws when called is observed as `Died`
  rather than escaping the test before any `Exit` exists. Its `Exit` is
  reduced to an `ExitShape`: `Succeeded { value }` when `Exit.isSuccess` (`Exit.ts:406`);
  `Died {}` when `Cause.hasDies` (`Cause.ts:897`), with the defect payload erased; otherwise
  `Failed { error }` from `Cause.findErrorOption` (`Cause.ts:871`).
- The observation is `{ exit: ExitShape, trace }`, compared with `Equal.equals` (`Equal.ts:177-179`).
- Excluded: the defect payload and its stack (a defect is observed only as the `Died` token),
  interruption (no generated operation interrupts and the preamble runs nothing concurrently),
  spans and tracing, and `Operation.name` (the composite carries the name passed to `compose`, not
  its components').

This restates "defects excluded" as "defect payloads excluded". The L5-2 acceptance case needs a
defect to be distinguishable from success and from a typed failure, or a throwing `sync` could not
be compared with anything (decision `the-declared-observation-and-the-l5-2-restatement`).

Generator: `OperationDescriptor`, a test-support schema
`{ event: S.Int, outcome: Succeed { scale: S.Int, shift: S.Int } | Fail { code: S.Int } }` drawn by
`Arbitrary` from the schema (the law-plan generator rule, `research/law-test-plan.md:3`). A law
over generated descriptors holds whatever their events are. A negative control that needs two
orders to differ draws its pair from `DistinctPair`, the descriptor pair filtered to distinct
`event` labels, or uses fixed labels, so a collision cannot make a control pass by accident.
`interpret(descriptor)` is the `Operation<number, number, OperationFailure, Trace>` that appends
`event` and then succeeds with `scale * x + shift` or fails with `OperationFailure { code }`. Every
generated operation shares `(E, R) = (OperationFailure, Trace)`, so the laws are stated at fixed
channels.

### 3.3 L5-1: Kleisli identity and associativity

For descriptors `f`, `g`, `h` and an input `x: S.Int`, with `id = pure({ name, f: identity })`:

- `observe(compose(id, f), x) = observe(f, x) = observe(compose(f, id), x)`;
- `observe(compose(compose(f, g), h), x) = observe(compose(f, compose(g, h)), x)`.

`it.effect.prop` over `[OperationDescriptor, OperationDescriptor, OperationDescriptor, S.Int]`,
`fcRuns` from the package default. The live `flow(self.run, Effect.flatMap(that.run))` satisfies
both by the Effect monad laws; the test guards the named bug, an effectful composition that
reorders (`rebuild-report.md:367`). Two negative controls inside the same file, as plain
`it.effect` cases: a composition that runs `that` before `self` and one that drops `self`'s effect
on success both produce a different trace for a `DistinctPair` with two succeeding outcomes, which
shows the observation can see the bug. A third case composes over a component whose `run` throws
when called and observes `Died` from the composite, which shows the combinators suspend. Title:
`L5-1 Kleisli identity and associativity under the declared observation`.

### 3.4 L5-2: only `Pure` is central

Statement. For a generated total function `p = pure({ name, f: x => a * x + b })` and any generated
descriptor `q`:

`observe(product(p, interpret(q)), x) = observe(commute(p, interpret(q)), x)
  = observe(map(product(interpret(q), p), swap), x)`

where `swap = ([l, r]) => [r, l]`, a test-local pure function (`effect/Tuple` has no swap; its
`renameIndices` is the documented route, `Tuple.ts:292`, and a lambda is the plain spelling). The
first equality exercises production code: `commute` is the reordering a caller may perform only
with a `Pure` witness, so the law tests that the witness is sound, not only Effect's sequencing.

Acceptance. `s = { name, run: () => Effect.sync(() => { throw ... }) }` is not central: for a
`q` with a fixed event that succeeds after appending it, `product(s, q)` observes `{ Died, [] }`
and `swap ∘ product(q, s)` observes `{ Died, [event] }`; for a failing `q`, the second observes
`{ Failed, [event] }`. `s` is not a `Pure`, so `commute(s, q)` does not type-check (a
`// @ts-expect-error` line in the same file, with its one-line reason). A second acceptance case:
a trace-writing `sync` that returns normally is also not central, because the two orders give two
traces for a `q` whose fixed event differs from the sync's. A third: `pure` over a throwing `f` is
observed as `Died`, not as an exception that escapes the test. The cases name the bug in the law
row, "a throwing `sync` is treated as pure" (`rebuild-report.md:368`), and the brand is what keeps
production code from treating it so (decision `pure-is-branded-and-commute-is-the-production-interchange`).
Title: `L5-2 Pure commutes with every operation and a throwing sync is not central`.

### 3.5 `withActivity` is a Writer, and the time model

`withActivity(descriptor)(op)` runs, in order:

1. `descriptor.facts(input)` gives `pin`, `promptDigest` and `used`, before the run (decision
   `2026-11-19-p0-activity-id-minted-at-start`).
2. `started = max(DateTime.now, floor)`, where `floor` is the current `ActivityFloor` (default
   `None`). `DateTime.now` reads `Clock` (`DateTime.ts:880`; `Clock` is a `Context.Reference`,
   `Clock.ts:195`), and `DateTime.max` is at `DateTime.ts:1347`.
3. `start = ActivityStart.make({ operation: op.name, pin, promptDigest, used, started })` and
   `id = mintActivityId(start)`.
4. `op.run(input)` runs with `CurrentActivity` provided (`Effect.provideService`, `Effect.ts:6802`).
   `CurrentActivity.stamp` reads the clock and returns `max(now, started, last stamp)`, recording it,
   so stamps within one activity never decrease and never precede `started`.
5. `ended = max(DateTime.now, started, last stamp)`, read whether the run succeeded or failed.
6. On success the result is `{ value, activities: HashSet.make(ActivityRecord.make({ id, start,
   generated: descriptor.generated(value), ended, outcome: "completed" })) }`. On a typed failure
   `e` (`Effect.catch`, `Effect.ts:2809,2851`) the run fails with `LoggedFailure { error: e,
   activities: HashSet.make(ActivityRecord.make({ id, start, generated: HashSet.empty(), ended,
   outcome: "failed" })) }`, so a failed run still emits its `prov:Activity`. A failure of the facts
   function or of `mintActivityId` happens before the activity starts and fails as a
   `LoggedFailure` with an empty log; a defect or an interruption records nothing, matching the
   declared observation (decision `a-failed-attributed-run-records-its-activity`).

Generation time (O8). An entity a wrapped run produces is generated at a stamp: the run reads it
through `CurrentActivity.stamp` when the entity's record needs a time inside the output, which
`Generation.at` (`annotation/src/Generation.ts:51-64`) and `ClaimCore.knowledgeStart` both do, and
otherwise at `ended`. Either way `started <= at <= ended`. The handoff's "one clock read after
alignment" (decision `2026-11-22-p3-handoff-activity`) is a stamp, and P4's
`GenerationFact { activity, at }` (`epistemics/src/Admission.ts:166-171`) takes the stamp, which
equals the core's `knowledgeStart` for a claim proposed by `ProposeClaim`, so `promote`'s check
`generation.at <= knowledgeStart` (`ClaimCore.ts:212-216`) holds (decision
`with-activity-mints-at-start-exposes-current-activity-and-composes-as-a-writer`).

`composeLogged(f, g, name)` runs `f`, then runs `g` on `f`'s value under
`ActivityFloor = Some(max ended over f's activities)`, and returns `g`'s value with the union of
both logs through `ActivityLogReducer`. When `g` fails, its `LoggedFailure` gains `f`'s log
through the same reducer, so the failure carries every record that started. Because `g`'s
`started` is clamped to that floor, an entity `f` generated is always used by `g` no earlier than
it was generated, under any clock, including one that steps backwards. A composite is a derived view: it has a name and no activity of its own
(`rebuild-report.md:286`).

`R` gains `Digest.Digest`, and `E` becomes `LoggedFailure<E | EF | PreimageMintError>`. Every
wrapped operation in a pipeline has the same shape, so a logged pipeline still has one fixed
`(E, R)`, and `composeLogged` type-checks only at that fixed pair. `CurrentActivity` is eliminated
from `R` by `withActivity`, so it never reaches a pipeline's requirements.

SPEC's exit says "every run emits a `prov:Activity`" (`SPEC.md:458-464`). A plain arrow (`pure`,
a catalog step) emits none; the runs that emit one are those `withActivity` wraps, now on success
and on typed failure. The narrowing to attributed runs is a SPEC amendment, recorded as decision
`spec-amendment-every-attributed-run-emits-a-prov-activity`, not only in the exit table.

### 3.6 L5-3: `generated` is never earlier than `used`, and every output is attributed

Generator: test-support `PipelineDescriptor`, a non-empty array of steps
`{ fanOut: 1..3, fail: S.Boolean }` plus an input entity set, and a `ClockScript`, a non-empty
array of epoch-millisecond readings in any order (backwards steps included). Each step is a wrapped
operation whose `used` is its input ids and whose output ids are minted through the production
`ContentHash` minting from `(step index, input ids)`; the pipeline is the `composeLogged` fold of the
steps. The run is provided a `Clock` that replays `ClockScript` cyclically
(`Effect.provideService(Clock.Clock, ...)`; `Clock` interface `Clock.ts:55-69`), because the
default `TestClock` (`testing/TestClock.ts:571`) does not advance and would make the order hold
vacuously.

For every run, with `L` the log of the success or of the `LoggedFailure`, and `O` the output ids
of a success:

- every record passes `verifyActivityRecord` and has `start.started <= ended`;
- for every `a1, a2` in `L` with `a1.generated ∩ a2.start.used` non-empty, `a1.ended <= a2.start.started`;
- every `used` id of a record that is not a pipeline input is in the `generated` of another record
  of `L`; on success, every id in `O` is in the `generated` of some record of `L`;
- `|L|` equals the number of steps that started, the failing one included, and on failure exactly
  one record has `outcome = failed` and it is the last step that started (the named bug, "a run
  with no activity", `rebuild-report.md:369`, now for failures as well).

A step whose descriptor has `fail: true` fails with a typed error after its activity starts, so
the generator covers failing pipelines and the `fail` flag reaches every property. A second
negative control runs a test-local `withActivity` that records only on success over a failing
pipeline and fails the count property.

Production descriptors. The generator mints its own outputs, so the properties above cannot show
that a production descriptor's `generated` covers what its operation produced. Each production
descriptor therefore gets a coverage case in its owning package's tests (the flow steps in
`lp/use-cases/test/OfficeActionReview.flow.test.ts`, `ProposeClaim` in the write-tools test): it
runs the operation on its fixture and asserts that `generated(output)` equals the set of values of
every `ContentHash`-branded field in the encoded output, found by a test-support walk of the output
schema's AST, minus the ids of the input. A descriptor that forgets an id it minted fails that case
(decision `flow-steps-generate-and-use-content-ids-so-attribution-chains`).

Negative control: the same pipeline folded with a test-local compose that unions logs without
setting `ActivityFloor` fails the second property for a generated clock script with a backward
step, which shows the clamp, not the clock, carries the order. Title:
`L5-3 generated is never earlier than used and every output is attributed`.

The union laws of `ActivityLogReducer` get no test and no ledger row: they are `HashSet.union`'s
upstream behaviour, and a law without a named bug is deleted (SPEC Constraints; decision
`nlp-operations-and-algebra-are-replaced-not-moved`).
