# Question-binding fixture

Normative appendix to [SPEC.md](./SPEC.md), adopted November 5, 2026. This is an
acceptance contract; no fixture implementation or passing run is claimed.

## Boundary

Run this fixture after the first generic Markdown slice. Keep the existing
patent profile, multi-codec acceptance work, repair comparisons, and numeric
kill criteria independently required. Passing this fixture cannot compensate
for failing those gates.

Use independently authored synthetic content and deterministic test answerers
inside the lab app or a lab-local package. No private source material, live
classifier, production approval authority, general workflow engine, Datalog
engine, DSL, or semantic-web projection is required. The domain graph owns
facts and rules; the document supplies content and locations. Do not add
fields or node kinds to the shared Doc model.

The fixture follows the POC's existing import transition when `@beep/md`
becomes `@beep/doc`. It neither expands nor blocks `doc-hub-spokes-inversion`.
It need not wait for `protocol-as-value` Wave 1. Find the existing canonical
identity owner before implementation; a temporary lab-local representation
must not become a competing production encoding owner. Promotion requires
reuse of the authoritative shared contract.

## Synthetic scenario

Use a fictional equipment-release note with a delivery date and a protected
commitment: release requires a current inspection and either authorized
credit approval or an override. This is an invented test policy, not a legal
requirement or a real approval process.

1. Parse the synthetic Markdown through the existing generic profile path.
2. Bind inspection evidence and delivery date to the complete source revision.
   A deterministic rule checks inspection validity at delivery.
3. If current, derive a conditional release obligation awaiting credit or
   override. If evidence is absent or expired, retain that requirement; do not
   solicit irrelevant credit answers to manufacture readiness.
4. Admit a simulated answer only for the exact request occurrence and answerer
   policy. Derive the result with references to evidence, rule revision, and
   the runtime-minted receipt.
5. Replay the same initial basis and admitted observation sequence without
   invoking answerers. Reproduce state and reason references.
6. Change the delivery date beyond the fictional inspection-validity interval.
   Preserve the historical evaluation; refuse to present the previous result
   as current under the changed basis.
7. Display the finding and reasons at the document location. Reject an agent
   edit deleting the protected date or release commitment, even if a diagnostic
   would otherwise disappear.

The fixture initially binds the whole source revision. Any narrower reuse
boundary requires demonstrated independence from edits outside it. Request
content and occurrence identity remain separate; an approval for a previous
occurrence is not standing approval. Duplicate delivery of the same observation
identifier is idempotent; conflicting answers after resolution are refused.
A source or policy revision opens a new occurrence and preserves old history.

## Acceptance cases

Zero safety/identity violations are accepted in these fixtures. This bounded
suite does not prove a universal interpreter theorem.

| ID | Perturbation or action | Expected result |
| --- | --- | --- |
| Q1 | Missing inspection evidence | Located unresolved requirement; no release or successful text-only discharge |
| Q2 | Current inspection, credit unanswered | Conditional result identifies required answer; pending state survives rendering |
| Q3 | Authorized answer for exact open occurrence | Receipt binds request and evidence basis; result cites receipt |
| Q4 | Answer under another request | Cannot discharge target obligation |
| Q5 | Changed source at the same model path | New basis/request; no answer transfer by location |
| Q6 | Delivery date passes inspection validity | Old release result is not current; original evaluation stays replayable |
| Q7 | Policy revision changes answerer requirements | Old answer does not silently resolve new obligation |
| Q8 | Late answer for still-valid pending occurrence | State progresses without losing earlier evidence |
| Q9 | Duplicate observation delivery | One admitted transition; stable replay |
| Q10 | Conflicting answer after resolution | Explicit refusal; prior admitted result preserved |
| Q11 | Same request content, separate approval occurrence | Previous one-time approval does not discharge new occurrence |
| Q12 | High-confidence answer from unauthorized fixture judge | No discharge; policy refusal remains visible |
| Q13 | Agent deletes protected date or commitment | Repair rejected even if diagnostic disappears |
| Q14 | Replay with answerers disabled | Same derived state and reason references; zero answerer calls |
| Q15 | Credit resolved, override unanswered | Outcome decided without an irrelevant answer; no general pivotal-question algorithm claimed |
| Q16 | Re-render or remap locations | Identities survive or become explicitly stale; obligations/receipts do not disappear |

Record inputs, expected outputs, basis identifiers, request/occurrence ids,
rule/policy versions, admitted observation journal, findings and obligations,
coverage, reason references, and answerer-call count. Compare semantic output
rather than unstable display timestamps. Preserve failed-case receipts.

Write `history/question-binding-fixture.md` and machine-readable case results
using the lab's evidence conventions when the experiment runs. Report its
verdict separately from the existing document-loop comparisons. Answer-binding,
authority, or commitment-preservation failures block promotion of affected
core shapes until fixed and rerun.

## Feedback-rule counterexample

One synthetic feedback item proposes a stricter rule. Evaluate the hard-coded
candidate against the original example and at least two contrasting examples.
Include a case where the broader rule wrongly rejects an acceptable input.
Record its proposed scope and an explicit simulated adopt/reject decision in
the fixture report. The proposal alone must not change the active revision.

This fixed case set tests rule scope. It requires no natural-language rule
synthesis, automatic precedent generalization, rule editor, or DSL.

## Limits and failure handling

Only Markdown must carry this additional fixture; the existing multi-codec
work remains independently required. Use existing evidence, receipt, finding,
anchor, and identity owners where available before adding lab-local shapes.

If satisfying the fixture appears to require a general engine, production
service, or shared-model change, record the unmet requirement and a no-go for
that extension. Continue the already scoped document experiment. Do not mark
an unimplemented fixture as passed or silently broaden the goal. Passing the
original document loop alone cannot establish the fixture's guarantees.
