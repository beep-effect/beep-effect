# Reflection — uspto-mcp (2026-07-02, codex)

## Summary

Closed out `goals/uspto-mcp`: implementation and verification were already
green from the 2026-07-01 session (three fixture tests, full lint/docgen
suite), so this pass's job was honest bookkeeping — recording that the
packet shipped via a direct user merge to `origin/main` rather than the
declared PR-gated `/yeet publish --pr` path, updating all packet documents
and the manifest to reflect that, writing this reflection, and flipping the
`@beep/mcp-kit` README's stale "In progress" consumer row to "Landed" now
that the package's real imports are grep-verifiable on `origin/main`.

## Tooling experience

- **Worked:** `goals/README.md`'s packet standard and the two sibling
  manifests (`mcp-kit`, `mcp-host-retrofit`) gave enough precedent (the
  `grandfatheredNote` pattern, the `COMPLETED_STATUS_TOKENS` list read
  straight from `ReflectionArtifact.ts`) to derive a consistent, non-guessed
  closeout shape without needing to ask.
- **Didn't:** Nothing blocked closeout — this was pure documentation
  reconciliation, no code changes, no test runs needed beyond re-reading
  prior evidence already recorded in `PLAN.md`.
- **Frustrating:** The completion-gate honesty requirement (record a direct
  merge without a PR truthfully, not silently mark the gate satisfied) has
  no first-class manifest field to hang it on; `grandfatheredNote` doesn't
  fit (this packet doesn't predate the gate), so an ad hoc `actualOutcome`
  key was the least-bad option.
- **Wished existed:** A documented manifest convention for "gate was not
  exercised as declared, here's what actually happened" distinct from
  "grandfathered" (which means "predates the gate entirely").

## Implementation improvement opportunities

- None — no source code changed in this closeout pass. The one adjacent fix
  was `packages/foundation/capability/mcp-kit/README.md`'s consumer table,
  which was stale independent of anything in this packet's own scope.

## Goal & prompt critique

- The original `SPEC.md`/`PLAN.md` correctly anticipated a closeout
  checklist (P3/P4 Closeout Checklist section) — that structure made this
  pass mechanical rather than exploratory. The one gap: neither document
  anticipated a non-PR shipping path, so there was no template slot for
  recording that deviation; I added one (`completionGate.actualOutcome` +
  a "Closeout deviation record" note in `PLAN.md`) rather than leaving it
  unrecorded.

## TODOs worth codifying

- Standardize an `actualOutcome`-style manifest field (name TBD) for any
  packet whose completion path deviates from its declared `completionGate`,
  so future closeouts don't have to invent the shape from scratch.

## Lessons (confidence-tiered)

- **HIGH — Critical:** When a goal's declared completion gate (PR-mergeable)
  and its actual shipping event (direct merge) diverge, record the
  divergence explicitly in the manifest rather than choosing between "leave
  the gate fields looking satisfied" and "refuse to mark the packet done" —
  both of those lose information the next reader needs.
- **MEDIUM — Best practice:** Before closing out a packet that names a
  shared kit as a dependency, grep the kit's own README/consumer-table for
  staleness — a sibling goal's closeout can leave cross-references pointing
  at the wrong state even after the code itself is merged.
- **LOW — Consideration:** A closeout pass with zero code changes is still
  worth a full reflection — the "what deviated from plan and why" narrative
  is exactly the kind of institutional knowledge that would otherwise live
  only in a chat transcript.
