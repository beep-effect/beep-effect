# Reflection — t3code-fleet-rollout (2026-11-08, claude)

## Summary

The fleet was already live when this closeout started; the packet had not caught up. Verification
confirmed five hosts on one build with a delegated turn each. Reboot proof is real on beep-worker and
dankserver, and open on tbk-worker and tom-pc-1.

## Tooling experience

- **Worked:** `delegate_task` with `environmentId` closed the open turns quickly; the SSH wrappers reused a live master, so probes cost no extra touches.
- **Didn't:** `t3_environment_links` status for grok-bot was only true at the moment it was read.
- **Frustrating:** a `reachable` state file for grok-bot still read `no` while the host answered.
- **Wished existed:** one fleet-parity command printing version, service, link and HTTPS state per host.

## Implementation improvement opportunities

- A parity command would replace the ad hoc loops this receipt needed.
- The AppArmor pin needs drift reporting, or an operator decision to accept a glob as tbk-worker's profile does.

## Goal & prompt critique

Scope lines aged badly. "Every live host" with the list kept in one place would have needed no superseding decisions.

## TODOs worth codifying

- See frontmatter.

## Lessons

- **HIGH:** Read service state, boot time and journal together. `active` alone says nothing about reboot survival; tbk-worker's unit looked the same as hosts that had really rebooted.
- **MEDIUM:** Confirm a probe's failure against a second path before blaming the system under test.
- **LOW:** Expect fleet state to drift during a closeout: a fork publish or CLI auto-update can land between two passes.
