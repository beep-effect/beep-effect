# Reflection — fallow-quality-enforcement (2026-07-11, claude)

## Summary

Retroactive closeout. The packet fully shipped: P0-P2 (research, `beep quality
fallow` advisory integration, generated policy + CI envelopes) landed 2026-06-08
via PR #222, and P3 blocking promotion (fqe-006) landed 2026-06-11 via PR #229,
executed through the sibling goals/fallow-zero-dead-code packet. A deliberate
post-close adjustment (295eb62557, 2026-06-18) kept `fallow:dead-code` blocking
in pre-push and returned `fallow:audit` to advisory. The work was done; only the
paperwork drifted — manifest said "active" for a month.

## Tooling experience

- **Worked:** The packet's own machine-validated artifacts (tasks.jsonc,
  feature-matrix.jsonc, validate-packet.ts) made the retroactive verification
  trivial — every task was `done` with `passed` checks, so "is this actually
  finished?" was answerable from the record alone.
- **Didn't:** Nothing enforced consistency between those artifacts and
  `initiative.status`; the validator checks shape, not lifecycle.
- **Wished existed:** A `goals doctor` lifecycle-consistency check (see todos).

## Goal & prompt critique

The packet was well-instrumented (schema-validated tasks, promotion gates per
feature row, explicit stop conditions), and the per-row promotion design paid
off when the audit lane needed a clean rollback. The gap was procedural: the
closing task was owned by a sibling packet, and no step said "flip this
manifest when fqe-006 closes elsewhere."

## Lessons (confidence-tiered)

- **HIGH — Critical:** Manifest status flips belong in the merge that closes
  the last blocking task, especially when that merge happens in a sibling
  packet's PR.
- **MEDIUM — Best practice:** Post-close gate demotions should update the
  closed packet's prose claims (README status) alongside the code and matrix.
