PLAN slice 7 lands PERIH-11 slice 2. On every main run of `beep-ci-binary.yml` (not a `verify_reproducible` dispatch, not another ref), the job compares the newest `beep-ci-*` release with the pin in `.github/actions/fetch-beep-ci/action.yml`. When they differ, it rewrites the pin and opens or updates one pull request for review.

- The rewrite is `bun run beep ci binary-pin --tag <beep-ci-...> --sha256 <hex> [--check|--write]`, a source-CLI command beside `binary-closure` and `compile-binary`. It decodes the tag (`beep-ci-` plus 12 lowercase hex) and the digest (`@beep/schema/Sha256` `Sha256Hex`), rewrites exactly the `BEEP_CI_RELEASE_TAG` and `BEEP_CI_SHA256` values, and fails typed when the file holds none or more than one of either line. `test/ci-binary-pin.test.ts` covers the idempotent rewrite, malformed tags and digests, missing or duplicated pin lines, and the re-run case. It stays out of `bin-ci.ts`: the release job has the toolchain installed, and the binary surface would grow for a command no pre-toolchain job runs.
- The decision comes from state, not from this run's history (#3299 review, beep-reviewer P2). The first design keyed the pull-request steps on "this run published a release". A re-run after a failed pull-request step never reached them: the first attempt's release already records the run's closure digest, so the re-run takes the closure-unchanged skip path. The rewrite step now picks the newest release with the same query the closure comparison uses, downloads its `beep-linux-x64.sha256`, runs `binary-pin --write`, and reports `changed` from `git diff` on the pin file. The credential, token and pull-request steps run only on `changed == 'true'`.
- No pull request for an unchanged closure or a byte-identical recompile: neither cuts a release, so once a bump has merged the pin equals the newest release and the rewrite leaves the file byte-identical. The "Require the default branch" guard and the ref-keyed concurrency group are unchanged.
- Consequence at merge: main pins `beep-ci-a56516d6d309`, older than the newest release, so the first main run after merge opens a pin-bump pull request even though this PR's own closure change takes the re-record path. That pull request is the first live reading of the gate.
- One pin-bump pull request at a time: `peter-evans/create-pull-request` always uses the branch `ci/beep-ci-pin-bump`. A newer release force-updates that branch and refreshes the open pull request's title and body instead of opening a second one. The pull request is labelled `ready-for-heavy` and is never auto-merged.
- Credential: the knowledge-mint GitHub App (`KNOWLEDGE_MINT_APP_CLIENT_ID`, `KNOWLEDGE_MINT_APP_PRIVATE_KEY`), the same App `knowledge-baseline-mint.yml` uses to open pull requests and `catalog-regeneration.yml` and `skills-update-train.yml` use to push. Its pull requests start workflows (#3015 ran Check and Heavy), which a `github.token` pull request does not. The token is minted in the step right before the pull-request step with contents, pull-requests and issues write (issues only for the label), and only that step reads it. The job's own `permissions` did not grow. The App holds no `workflows` permission and needs none, because the pin is a composite action, not a workflow file. A fail-closed step stops the job when the App variable is missing, and the run summary always prints the four commands an agent runs to open the pull request by hand.
- `bun run beep ci binary-closure` moves on this branch only because the workflow file is a closure input (34ec6eee1b3f to fd2f159d8fc3 at the first push). `bin-ci.ts` and its imports are unchanged, so the first main run after merge should compile identical bytes and take the re-record path, cutting no release.

Still to read on main after merge: the first run re-recording rather than publishing and opening the catch-up pin-bump pull request, which must pass its own Check; after that bump merges, a push with an unchanged closure opening none; and the next real closure change opening one.
