# Reflection — party-slice (2026-11-03, codex)

## Summary

The local implementation graduates the party model, memory ledger and generic
ingestion/review behavior into three packages while retaining law-practice source
vocabulary in its owning adapter. This reflection is prepared for the final
implementation PR. It does not assert completion: published-head hosted readiness,
merge and completion refresh remain required.

## Tooling experience

- **Worked:** Canonical package generation supplied registration and test structure.
  Package verification, synthetic workflow smokes, architecture scans and exact
  parser boundary tests provided distinct, useful checks. The cache baseline
  command required an explicit reviewed basis and preserved qualification scope.
- **Didn't:** Package-local checks alone did not detect the root inline-schema
  lint findings or all documentation inventory findings. Those required the
  packet's additional root gates. Fallow and schema-first also found broad
  functions, repeated claim construction and missing generated-input properties.
  The remediation retained fixed competency tests and used the canonical
  it.prop / it.effect.prop harness for the new properties.
- **Frustrating:** A full documentation inventory is a multi-minute scan even when
  the repair concerns a few package comments. Corrections should be batched before
  regeneration; a run already in progress is not proof of later edits.
- **Wished existed:** A scoped inventory preview using the same detector as the
  final repository ratchet, without changing the final gate's authority.

## Implementation improvement opportunities

The memory ledger is intentionally provisional. Durable id allocation, durable
source evidence and import of previously exported integer review anchors require
a separate storage design. The scripts document that changed input ordering can
change provisional anchors and stale a case; persistence should solve this through
stored source identity, not by weakening case validation.

Mail content identity and review validity now enter explicitly. A future provenance
resolver can enrich old mail indexes, and a separately scoped review-page update
can collect the new context directly. Neither belongs in this implementation's
out-of-scope page or private corpus.

## Goal & prompt critique

Add a line to future graduation packets: “Before removing old modules, map each
old competency assertion to a package-level check and document every intentional
behavior change.” This would have brought exact graph and hierarchy parity into
the initial test plan instead of a late comparison.

Also identify whether legacy source formats contain the required provenance and
validity fields. A format compatibility promise must not silently become a claim
that a parent archive digest identifies a child message, or that observation dates
supply the valid time of a human identity decision.

## TODOs worth codifying

- A competency migration checklist should cover schema rejection, historical
  replay, exact graph relationships, provenance and review uncertainty.
- A scoped documentation preview could use the production inventory detector
  while keeping the full regenerated ratchet mandatory before publication.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Canonical identifier equality does not establish person
  identity. Contact and alias evidence remains Proposed until explicit review.
- **HIGH — Critical:** Source assertions must exist and preserve their anchors;
  a deterministic-looking reference is not evidence by itself.
- **HIGH — Critical:** Keep local passing checks distinct from committed-head and
  hosted acceptance. Completion requires the packet's actual refresh evidence.
- **MEDIUM — Best practice:** Compare competencies by assertions and scenarios,
  not test counts; stronger scenarios may replace several old tests.
- **LOW — Consideration:** A reusable script compatibility boundary may reduce
  future migrations, provided it cannot invent missing source or temporal context.
