# Reflection: inline-schema-compile-hard-error

## Summary

The campaign reconciled 3,087 opening findings to zero and promoted the inline
Schema compiler rule to an error. PR #1019 shipped the migration; PR #1022
shipped the review corrections. Their merged code passes the full local Yeet
proof, and all five review threads are resolved. The packet closes in a
documentation follow-up because both implementation PRs had already merged.

## Tooling experience

- The reproducible census made the scope countable. It reproduced the
  predecessor's 2,931 findings, attributed the additional 156, and identified
  the sole generated owner before migration. The owner matrix contains 106
  passing package-verification receipts.
- Bounded codemod batches worked after whole-corpus analysis reached roughly
  10.9 GiB RSS. Manual handling remained necessary for declaration order,
  assertion signatures, and schema values that depend on function arguments.
- Yeet's review watcher and reply command provided concrete check transitions
  and per-thread write receipts. The final local merged-preview verification
  passed all 33 reported lanes in 43 minutes 35 seconds.
- Silent commands consumed too much operator attention. A live compiler had to
  be confirmed through a separate process inspection during test-TSGo. The
  final verification also repeated the corpus check in cheap gates, the
  dedicated test gate, and the aggregate check lane.
- I wanted a compact progress record and a reason for each repeated proof.
  The existing ledger also records silent JSDoc inventory, buffered lint shard
  output, and repeated repo-cli tests in the same immutable preview.

## Implementation improvement opportunities

Static syntax is insufficient evidence that an expression can move to module
scope. A struct field, spread operand, computed key, array element, or unary
operand may refer to a function parameter. The rule now descends through those
forms before reporting a hoistable compiler. The codemod should apply the same
analysis and establish that every schema value is initialized before the new
compiler declaration.

Proof identity must follow the subprocess environment contract. The first
repair considered `useLocalEnv` alone, while direct commands also inherit
ambient state through `extendEnv`. The next repair still missed values outside
an allowlist. The merged implementation hashes the complete inherited
environment into an inner SHA-256 digest and omits ambient state for isolated
commands. Regression tests brought the affected module to 100% branch coverage
without lowering the coverage baseline.

## Goal & prompt critique

The measurable census and generator-first requirement were useful. I would add
this sentence to future campaign launchers: "Prepare the reflection, lifecycle
update, and review-thread inventory before the implementation PR's final
monitor, and record the local verdict's tree identity alongside the PR head."
This would avoid a documentation follow-up after a manual merge and make the
remaining work clear to another session.

Keep the diagnostic and proof-reuse opportunities as follow-up work. They
deserve tests of their own execution contracts; a large compiler migration
should not silently absorb a repository scheduler redesign.

- Reuse successful proofs by command, environment, dependency graph, and tree

- Test permission continuity during Desktop background continuation. The

## Lessons (confidence-tiered)

- HIGH, critical: classify runtime dependencies and initialization order before
  hoisting. A module-level declaration can still be incorrect when it reads a
  later schema or loses a function parameter.
- HIGH, critical: cache a proof only when all executor-visible inputs match.
  Store digests of environment data, never raw values in proof receipts.
- HIGH, critical: tie acceptance to a verified Git tree. The PR head, local
  merged preview, and squash merge all have tree
  `6a9533d44b007cb26959789f22d7fa7768dc7615`.
- MEDIUM, best practice: prepare closeout artifacts while CI runs and keep
  predecessor discussions in the review inventory.
- LOW, consideration: give long commands a shared progress renderer once their
  event contract is stable; first measure whether it reduces separate process
  inspections without flooding logs.
