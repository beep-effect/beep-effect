# Reflection — epistemic-contradiction-triage (2026-07-30, codex)

## Summary

This packet delivered immutable, evidence-backed contradiction candidates,
atomic human review, and a coordinated full-source highlighting surface from
UTF-16 provenance through persistence, RPC, Effect Atom state, and desktop UI.
The final reviewer/fixer loop strengthened tenant isolation, review-record
quality, temporal state, and observability without widening the packet into a
detection engine.

## Tooling experience

- **Worked:** Schema-first modeling, Effect services, Atom families, constructive
  arbitraries, PGlite migration suites, the opt-in real-Postgres race lane, and
  the browser capture inventory each caught a different class of defect.
- **Didn't:** Changed-package documentation output could not distinguish new
  warnings from inherited ones, and PGlite could not prove independent
  connection locking semantics.
- **Frustrating:** Line-number inventory anchors moved after otherwise harmless
  test edits and required repeated reconciliation.
- **Wished existed:** A single tenant-idempotency proof helper and a
  changed-symbol documentation-quality report.

## Implementation improvement opportunities

- The desktop fixture currently supplies one organization, workspace, and
  reviewer. Multi-user work must derive those identities from the authenticated
  session rather than extending that fixture convention.
- Full-source resolution intentionally materializes and digest-checks the source
  before highlighting. A later operational packet should define source-size
  limits and cache policy without weakening verification.
- Legacy evidence-span normalization is isolated to persistence reads because
  historical rows have no discriminator. New writes stay strict; a future data
  migration can remove the compatibility path once every legacy row is known to
  be rewritten.

## Goal & prompt critique

- The hard P0 fixture gate and explicit "detection never mutates authority"
  constraint prevented design drift.
- Add two acceptance bullets: receipt idempotency is organization scoped across
  storage and recovery, and rejection/supersession reasons are normalized,
  non-empty, and bounded.
- Name the real-Postgres race topology directly: two independent writers, one
  winner, typed losers, then a fresh-reader restart proof.

## TODOs worth codifying

- A reusable cross-tenant idempotency matrix for persistence repositories.
- Stable schema-first inventory identities instead of source-line anchors.
- A documentation rubric mode scoped to added or modified public symbols.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Scope idempotency end to end — a tenant-qualified
  constraint alone is insufficient when ids or recovery queries remain global.
- **HIGH — Critical:** Use real Postgres for locking contracts — deterministic
  in-process database proofs cover different risks.
- **HIGH — Critical:** Normalize immutable review text at both public and
  persistence schemas — audit records should not depend on UI validation.
- **MEDIUM — Best practice:** Pair exact UTF-16 boundary tests with real browser
  highlighting, including astral characters and page transitions.
- **LOW — Consideration:** Add size limits and caching only when operational
  evidence justifies them; preserving digest-verified full-source semantics is
  the first-order contract.
