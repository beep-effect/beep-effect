MEAS-06 (PLAN slice 13). `beep ci unit-timings` (`packages/tooling/tool/cli/src/commands/Ci/CiUnitTimings.ts`, schemas in `CiUnitTimings.schemas.ts`) reads the Vitest JSON reports a Test Unit partition leaves under each workspace's `coverage/` (`unit-results.json`, or `invocation-<n>/unit-results.json` for a package with several invocations) and writes one `unit-timings/v1` projection: a row per executed package invocation with its outcome, wall and summed file time, executed file count and per-file rows.

- Every event. The hosted shard runs it after its tests on every event (`Project Unit test timings`, `continue-on-error: true`, so it never decides the job) and uploads it as `unit-timings-<run>-<attempt>-<partition>` (`Upload Unit test timings`). The failure-only raw report upload is unchanged.
- Expected files. The count a row is judged against is the producer's own selection, read from the partition's sealed coverage manifest (`expectedTestFiles` per invocation). A red shard seals no manifest, so its rows are `unsealed` and carry no expected count; they are still rows, so a red run reports what it executed. An invocation the manifest names with no report is a `missing` row; a report that does not decode is `unreadable`.
- By event. `unitTimingCensus` folds projections into one row per event, counting each partition once per run at its latest attempt (`Re-run failed jobs` gives only the re-run partitions a new attempt) and grouping by run, package and invocation so a sharded package's partitions add their files toward one selection (the producer stamps every shard with the whole package's selection). A group matches when executed equals selected; the census names unmatched and unsealed groups instead of reading them as matches.
- The overflow shard. `check.yml` calls `shard-overflow.yml@main` for a routed Test Unit partition, and `ci-shard-overflow.test.ts` holds its steps identical to the hosted shard's. The two steps are therefore added to `shard-overflow.yml`'s `test-unit-shard` job as well; the call is pinned at main, so overflow runs upload timings from the merge on. No job name, `needs`, `runs-on`, job `if`, matrix or required context changes, and `heavy.yml` is not touched.
- Cache baseline. `bun run beep cache audit` reports 0 blocking findings with this change: the baseline subjects cover Turbo configuration, which neither workflow edit nor the new CLI file touches, and none of the last 25 `check.yml` PRs re-recorded it. A re-record would only rewrite the review block, so none is made.
