## Q2. question 2

- **The official gh pr checks manual documents --watch as “Watch checks until they finish”, --fail-fast as “Exit watch mode on first check failure”, --required as “Only show checks that are required”, JSON fields including bucket and state, that --json’s bucket categorizes state into pass/fail/pending/skipping/cancel, and an additional exit code “8: Checks pending”.**
  - evidence: The manual page states: “When the --json flag is used, it includes a bucket field, which categorizes the state field into pass, fail, pending, skipping, or cancel.” “Additional exit codes: 8: Checks pending”. Options: “--fail-fast Exit watch mode on first check failure”, “--required Only show checks that are required”, “--watch Watch checks until they finish”. JSON Fields: “bucket, completedAt, description, event, link, name, startedAt, state, workflow”.
  - source: GitHub CLI manual: gh pr checks — https://cli.github.com/manual/gh_pr_checks (primary, high)
- **In current cli/cli source, --fail-fast is rejected without --watch and --watch is rejected with --json; default --watch keeps polling until counts.Pending == 0, and only --fail-fast breaks the loop on the first Failed > 0.**
  - evidence: NewCmdChecks returns FlagErrorf("cannot use `--watch` with `--json` flag") and FlagErrorf("cannot use `--fail-fast` flag without `--watch` flag"). Flag help is “Watch checks until they finish” and “Exit watch mode on first check failure”. The watch loop breaks when “counts.Pending == 0 || !opts.Watch”, then separately “if opts.FailFast && counts.Failed > 0 { break }”. Tests assert those flag errors and that “watch some failing with fail fast tty” returns SilentError while still showing 1 pending check.
  - source: cli/cli pkg/cmd/pr/checks/checks.go (trunk) — https://raw.githubusercontent.com/cli/cli/trunk/pkg/cmd/pr/checks/checks.go (repository, high)
- **Pending checks exit 8; any failed check exits 1 and takes precedence over pending; success is 0. A snapshot with mixed failing+pending is SilentError (1), not PendingError (8).**
  - evidence: checksRun returns cmdutil.SilentError if counts.Failed > 0, else cmdutil.PendingError if counts.Pending > 0. ghcmd maps SilentError to exitError=1 and PendingError to exitPending=8; success is exitOK=0. Global help says 0 success, 1 failure, 2 cancelled, 4 auth, and that a command may have more codes. Tests: “some pending” → PendingError; “some failing” (1 failing and 1 pending) → SilentError. Maintainer jtmcg reproduced pending as “echo $? 8” and treated no-checks exit 1 as the normal failure convention.
  - source: cli/cli internal/ghcmd/cmd.go exit-code mapping (trunk) — https://raw.githubusercontent.com/cli/cli/trunk/internal/ghcmd/cmd.go (repository, high)
- **The JSON bucket field is a CLI-side recoding of each check’s state: SUCCESS→pass; SKIPPED/NEUTRAL→skipping; ERROR/FAILURE/TIMED_OUT/ACTION_REQUIRED→fail; CANCELLED→cancel; otherwise (EXPECTED, REQUESTED, WAITING, QUEUED, PENDING, IN_PROGRESS, STALE)→pending. The state field is the raw StatusContext.State or, if empty, CheckRun Conclusion when Status is COMPLETED else Status.**
  - evidence: aggregate.go sets item.State from c.State, else c.Conclusion if c.Status == "COMPLETED", else c.Status. The switch assigns Bucket "pass"/"skipping"/"fail"/"cancel"/"pending" as listed, with the default comment naming EXPECTED, REQUESTED, WAITING, QUEUED, PENDING, IN_PROGRESS, STALE. The check struct JSON tags are `json:"state"` and `json:"bucket"`. This matches the manual’s bucket categories.
  - source: cli/cli pkg/cmd/pr/checks/aggregate.go (trunk) — https://raw.githubusercontent.com/cli/cli/trunk/pkg/cmd/pr/checks/aggregate.go (repository, high)
- **If the rollup has no reported check contexts, gh pr checks errors immediately with “no checks reported on the '<branch>' branch” (exit 1) even under --watch; the watch loop never starts. cli/cli closed a request to wait out that registration race as not planned, citing GitHub API limits.**
  - evidence: populateStatusChecks returns fmt.Errorf("no checks reported on the '%s' branch", pr.HeadRefName) when len(statusCheckRollup.Nodes)==0. checksRun calls populateStatusChecks once before the watch loop and returns that error immediately. Tests expect that error for empty rollups. Issue #7401: after create, the API can briefly say no checks, so `gh pr create && gh pr checks --watch` “will error and return with exit code 1”. Maintainer samcoe: the API “does [not] return any indication that there are any checks scheduled to run”; vilmibm closed it “given the API limitations”.
  - source: cli/cli issue #7401: handle “no checks” races in pr checks --watch — https://github.com/cli/cli/issues/7401 (primary, high)
- **--required only keeps already-reported contexts with IsRequired true; --watch then exits when those currently visible required checks have Pending==0. Unreported required checks and later-enqueued downstream jobs (e.g. GitHub Actions needs) are not waited for. This is an open, acknowledged gap, not a documented wait-for-all-required-checks guarantee.**
  - evidence: aggregateChecks skips contexts when requiredChecks && !c.IsRequired; if none remain it errors “no required checks reported on the '%s' branch”. Issue #8855 (open): --required omits required checks that have not reported yet; BagToad said the team thinks the request makes sense but is unsure the API can support it without admin branch-protection lookup. Issue #9973 (open): --required --watch exited after one required job because a second required job depended on needs and was not in the rollup yet; reporter: “The logic only cares about the required checks running at the moment of executing the command.”
  - source: cli/cli issue #8855: gh pr checks --required should include pending required status checks — https://github.com/cli/cli/issues/8855 (primary, high)

Uncertainties:
- No inspected primary source specifies a GitHub-defined length for the “no checks reported” window; issue #7401 only says “a few moments”, and maintainers suggested sleep 5s/10s as a workaround, not a guaranteed interval.
- cli/cli has not established that the Checks API can list required contexts that have not yet been reported (issues #8855 and #9973 remain open; BagToad said feasibility still needs investigation).
- JSON export returns after Exporter.Write without SilentError/PendingError, so --json likely exits 0 whenever any checks were returned; that exit behavior is not stated on the gh pr checks manual page.

## Q3. question 3

- **GitHub GraphQL documents PullRequest.mergeStateStatus as MergeStateStatus with eight values: BEHIND (head ref out of date), BLOCKED (merge is blocked), CLEAN (mergeable and passing commit status), DIRTY (merge commit cannot be cleanly created), DRAFT (blocked because the PR is a draft), HAS_HOOKS (mergeable with passing commit status and pre-receive hooks), UNKNOWN (state cannot currently be determined), and UNSTABLE (mergeable with non-passing commit status).**
  - evidence: The live GraphQL reference defines MergeStateStatus as “Detailed status information about a pull request merge” and lists those eight values with the quoted one-line descriptions. PullRequest.mergeStateStatus is typed MergeStateStatus! (“Detailed information about the current pull request merge state status”).
  - source: Pull requests - GitHub GraphQL reference — https://docs.github.com/en/graphql/reference/pulls (primary, high)
- **GraphQL PullRequest.mergeable is a conflict-only MergeableState (MERGEABLE, CONFLICTING, UNKNOWN). UNKNOWN means mergeability is still being calculated. REST GET /repos/{owner}/{repo}/pulls/{pull_number} returns mergeable as true, false, or null; null means GitHub started a background job to compute mergeability and the client should retry until a non-null value appears.**
  - evidence: GraphQL MergeableState: CONFLICTING “cannot be merged due to merge conflicts”; MERGEABLE “can be merged”; UNKNOWN “The mergeability of the pull request is still being calculated.” The mergeable field is “Whether or not the pull request can be merged based on the existence of merge conflicts.” REST: “The value of the mergeable attribute can be true, false, or null. If the value is null, then GitHub has started a background job to compute the mergeability. After giving the job time to complete, resubmit the request.” GraphQL also says potentialMergeCommit is absent “if the test merge commit is still being generated.”
  - source: REST API endpoints for pull requests / Get a pull request — https://docs.github.com/en/rest/pulls/pulls (primary, high)
- **Current REST pull-request schemas expose mergeable_state as a required string with no enumerated values, so REST docs do not establish CLEAN/UNSTABLE/BLOCKED/BEHIND/DIRTY/DRAFT/HAS_HOOKS/UNKNOWN; those names are the GraphQL MergeStateStatus enum.**
  - evidence: Create/Get pull request response schema lists mergeable as “boolean or null” and mergeable_state as “required, string” with no Can-be-one-of list. GraphQL is the API that enumerates MergeStateStatus. GitHub’s REST Get a pull request page therefore documents the async mergeable tri-state, not the detailed merge-state vocabulary.
  - source: REST API endpoints for pull requests — https://docs.github.com/en/rest/pulls/pulls (primary, high)
- **Check-run conclusion vocabulary is GraphQL CheckConclusionState ACTION_REQUIRED, CANCELLED, FAILURE, NEUTRAL, SKIPPED, STALE (GitHub-only), STARTUP_FAILURE, SUCCESS, TIMED_OUT. REST update/create conclusion may be action_required, cancelled, failure, neutral, success, skipped, stale, or timed_out; only GitHub may set stale. A check run left incomplete more than 14 days is marked stale. Status-checks docs treat a successful conclusion as usually non-blocking and failure, timed_out, or action_required as usually needing review before merge.**
  - evidence: GraphQL CheckConclusionState lists those nine values; STALE is “marked stale by GitHub. Only GitHub can use this conclusion.” REST PATCH check-run: “Can be one of: action_required, cancelled, failure, neutral, success, skipped, stale, timed_out” and “You cannot change a check run conclusion to stale, only GitHub can set this.” Checks guide: incomplete check runs become stale after 14 days. Status checks page conclusion table includes action_required, cancelled, failure, neutral, skipped, stale, success, timed_out and states “A successful conclusion usually means the check does not block merging. A failure, timeout, or action-required conclusion usually means someone must review the details before the pull request can merge.”
  - source: Checks - GitHub GraphQL reference — https://docs.github.com/en/graphql/reference/checks (primary, high)
- **Required status checks on protected branches and rulesets must report successful, skipped, or neutral before merge; a skipped GitHub Actions job reports Success and does not block even if required. GraphQL still describes UNSTABLE as mergeable despite non-passing commit status. CheckRun.isRequired tells whether a given check must pass for a specific pull request.**
  - evidence: About protected branches: “Required status checks must have a successful, skipped, or neutral status before collaborators can make changes to a protected branch” and “all required status checks must pass before collaborators can merge.” Troubleshooting required status checks: “Successful check statuses are success, skipped, and neutral.” Status checks: “A job that is skipped will report its status as Success. It will not prevent a pull request from merging, even if it is a required check.” Rulesets “Require status checks to pass before merging”: “all required status checks must pass before collaborators can merge.” GraphQL UNSTABLE: “Mergeable with non-passing commit status.” CheckRun.isRequired: “Whether this is required to pass before merging for a specific pull request.”
  - source: About protected branches — https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches (primary, high)
- **Rulesets and classic branch protection both treat required status checks as strict (default: head must be up to date with the base before merge), loose (up-to-date not required), or disabled (no check-based merge restriction). GraphQL BEHIND is only defined as “The head ref is out of date,” not as an explicit alias of the strict setting.**
  - evidence: Available rules for rulesets and About protected branches share the same table: Strict — “Require branches to be up to date before merging” checked — “The topic/branch must be up to date with the base branch before merging” (default); Loose — checkbox unchecked — branch need not be up to date; Disabled — required-status-checks rule off — “no merge restrictions” from that rule. MergeStateStatus.BEHIND is documented solely as “The head ref is out of date.”
  - source: Available rules for rulesets — https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets (primary, high)

Uncertainties:
- GitHub REST and GraphQL docs do not explicitly map failing or missing required checks to BLOCKED versus failing optional/non-required checks to UNSTABLE; that pairing appears in community/Octokit commentary, not in the official enum text.
- REST docs never enumerate mergeable_state string values, so lowercase clean/unstable/blocked/behind/dirty/draft/has_hooks/unknown are not established by current REST reference pages.
- Official docs do not state which MergeStateStatus is returned while required checks are still pending (in progress) versus completed-and-failing.
- REST check-run response schemas list conclusion as success, failure, neutral, cancelled, skipped, timed_out, action_required, or null and omit stale, even though the update parameter and Checks guide document stale.

  - evidence: Docs: queue_conditions are requirements to be accepted into the queue; merge_conditions are requirements to merge once at the front. checks_timeout is “the amount of time the merge queue waits for pending checks to return before dequeueing”; auto uses 95th-percentile CI runtime and applies no timeout until history exists; null disables the timeout. max_checks_retries is “Number of times Mergify will retry failed CI checks before removing the pull request from the queue” for flaky CI. Interrupted (cancelled) checks dequeue as checks-interrupted, distinct from checks-failed.
  - source: Mergify Using Queue Rules / Pull Request Lifecycle — https://docs.mergify.com/merge-queue/rules/ (primary, high)

  - evidence: Conditions treat list operators as any-match: “True if any check named test succeeds” for check-success = test. Attributes include check-success, check-pending, check-failure (cancelled/timed out/action required also count as failure), check-neutral, and check-success-or-neutral. branch_protection_injection_mode default queue injects GitHub branch-protection conditions as required for both queuing and merging.
  - source: Mergify Conditions — https://docs.mergify.com/configuration/conditions/ (primary, high)

## Q5. question 5

- **GitHub documents webhooks as the preferred alternative to API polling (less work, better scale, near-real-time) but standard GitHub webhooks cannot target a local CLI: payload URLs of localhost/127.0.0.1 are unsupported, so local receipt requires a proxy or GitHub CLI forwarding.**
  - evidence: About webhooks: webhooks receive data as it happens versus polling, require less effort/resources, scale better than per-resource API calls, and allow near-real-time updates. REST and GraphQL rate-limit pages say subscribe to webhook events instead of polling. Troubleshooting: “You cannot use localhost or 127.0.0.1 as a webhook URL”; testing docs recommend smee.io or GitHub CLI forwarding.
  - source: About webhooks — https://docs.github.com/en/webhooks/about-webhooks (primary, high)
- **`gh webhook forward` is the official GitHub CLI extension (`gh extension install cli/gh-webhook`) for receiving repo/org webhook events locally; GitHub documents it as testing/development only (not production), one forwarder per repo/org, requiring a gh auth token (org hooks need admin:org_hook). The extension POSTs a name=cli hook and pulls events over a WebSocket (`ws_url`) to a local --url or stdout.**
  - evidence: Docs warn: “Webhook forwarding is only designed for use during testing and development. It is not supported for use in production… only works with repository and organization webhooks… Only one person can use webhook forwarding at a time for each repository and organization.” create_webhook.go posts Name:"cli", Active:false, then PATCHes active and returns res.WsURL; forward.go dials that WebSocket with Authorization and POSTs payloads to --url.
  - source: Using the GitHub CLI to forward webhooks for testing — https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/using-the-github-cli-to-forward-webhooks-for-testing (primary, high)
- **Authenticated REST conditional GETs that send If-None-Match with a prior ETag (or If-Modified-Since) and receive 304 Not Modified do not count against the REST primary rate limit; GitHub calls this especially useful when polling.**
  - evidence: Best practices: “Making a conditional request does not count against your primary rate limit if a 304 response is returned and the request was made while correctly authorized with an Authorization header… each 304 Not Modified response is fast and does not use your rate limit.” Events API: if no new events, 304 and “your current rate limit will be untouched.” Conditional requests are not supported for POST/PUT/PATCH/DELETE unless an endpoint says otherwise.
  - source: Best practices for using the REST API — https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api (primary, high)
- **GraphQL primary limits are point costs, not request counts: users get 5,000 points/hour (10,000 via GHEC-owned apps); each query costs at least 1 point, computed as (unique-connection requests assuming first/last limits) / 100, rounded. Secondary GraphQL scoring is separate: queries 1 point, mutations 5 points, with a 2,000-points-per-minute cap on the GraphQL endpoint.**
  - evidence: GraphQL rate-limit docs give the 5,000/10,000 hourly point budgets, the min-1 and connections/100 formula (example query scores 51), and a secondary table: GraphQL without mutations = 1, with mutations = 5, REST GET/HEAD/OPTIONS = 1, REST POST/PATCH/PUT/DELETE = 5; “no more than 2,000 points per minute are allowed for the GraphQL API endpoint.” Formula and limits “are subject to change.”
  - source: Rate limits and query limits for the GraphQL API — https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api (primary, high)
- **If webhooks cannot be used, GitHub’s documented poll cadence is a fixed schedule no faster than any X-Poll-Interval (Events API example: 60 seconds; “Please obey the header”), plus secondary-limit constraints: ≤100 concurrent REST+GraphQL requests, ≤900 REST points/minute per endpoint (GET=1), serial rather than concurrent requests, and ≥1 second between mutative calls.**
  - evidence: REST best practices: poll only as often as needed on a fixed schedule; if x-poll-interval is present, wait at least that many seconds; make serial requests to avoid secondary limits; wait at least one second between POST/PATCH/PUT/DELETE. Events API shows X-Poll-Interval: 60 and ETag 304. REST rate-limit docs: 100 concurrent; 900 REST / 2,000 GraphQL points per minute; 90s CPU per 60s real time (≤60s of that for GraphQL).
  - source: Rate limits for the REST API — https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api (primary, high)
- **GitHub does not publish a per-event latency SLA for workflow_job or check_run webhooks. Docs only say webhooks are “near real-time,” deliveries “can take a few minutes,” receivers must return 2xx within 10 seconds, and GitHub may throttle on delivery surges; a March 2026 status incident cited an average webhook-delivery baseline of ~5 seconds.**
  - evidence: About webhooks: “Webhooks allow near real-time updates, since webhooks are triggered when an event happens.” Troubleshooting: “Webhook deliveries can take a few minutes to be delivered… GitHub may temporarily throttle the rate of deliveries.” Best practices: respond with 2XX within 10 seconds. workflow_job/check_run pages describe actions and availability only, not delivery delay. githubstatus.com incident x1g78jx4sgfk: “average delivery latency increased from a baseline of approximately 5 seconds to a peak of approximately 160 seconds.”
  - source: Troubleshooting webhooks — https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks (primary, medium)

Uncertainties:
- GitHub docs never say whether a REST 304 also avoids secondary rate-limit points; they only exempt 304s from the primary limit.
- GraphQL docs do not document ETag/If-None-Match or 304 savings; REST says conditional requests are unsupported for POST unless an endpoint notes otherwise, and GraphQL is POST.
- The 2022 changelog called CLI webhook forwarding a limited public beta; current docs omit “beta,” but create_webhook.go still maps HTTP 403 to “you do not have access to this feature,” so access gating is unclear.
- No GitHub product doc gives a typical or p95 latency specifically for workflow_job or check_run; the ~5s figure is an incident baseline, not an SLO.
- X-Poll-Interval: 60 is documented for the Events API, not as a universal REST poll interval; Events API itself is “not built to serve real-time use cases” (latency 30s–6h).
- Whether gh webhook forward remains suitable as a long-lived local-CLI transport is unspecified beyond the production-unsupported warning and the one-forwarder-per-repo/org limit.

## Q6. question 6

- **systemd-run --user creates a transient unit in the calling user's service manager; the default is a detached .service whose parent is that manager and which starts asynchronously, while --scope instead creates a .scope that systemd-run itself parents, inheriting the caller's environment and returning only when the command finishes.**
  - evidence: systemd-run(1): a transient service 'will run in a clean and detached execution environment, with the service manager as its parent process' and systemd-run 'will start the service asynchronously in the background and return after the command has begun execution'; a transient scope 'will be executed by systemd-run itself as parent process and will thus inherit the execution environment of the caller' and 'Execution in this case is synchronous'. --user: 'Talk to the service manager of the calling user, rather than the service manager of the system.' systemd.scope(5): scopes 'manage externally created processes, and do not fork off processes on their own'; 'systemd-run --scope may be used to easily launch a command in a new scope unit from the command line.'
  - source: systemd-run(1) — systemd 262~rc3 (Debian unstable) — https://manpages.debian.org/unstable/systemd/systemd-run.1.en.html (primary, high)
- **systemd-run has no dedicated --on-success option; --collect is CollectMode=inactive-or-failed, -p/--property sets unit properties (including OnSuccess=), and OnSuccess= starts listed units when this unit enters the inactive state.**
  - evidence: systemd-run(1) OPTIONS list --collect/-G as 'Unload the transient unit after it completed, even if it failed' and 'a shortcut for --property=CollectMode=inactive-or-failed'; -p/--property 'Sets a property on the scope or service unit that is created'.
