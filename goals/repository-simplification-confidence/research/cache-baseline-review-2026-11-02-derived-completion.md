# Cache baseline review: derived completion rendering

Reviewed 2026-11-02 for the PR that renders derived goal completion on the operator surfaces
(`session open`, `goals doctor`, `goals explain`, `goals index`) without changing the receipt model
(Decision Log row 2026-11-02 in this packet's `SPEC.md`).

`bun run beep cache audit` reported 2 blocking findings, both introduced by this branch:
configuration drift for `//#lint:policy-fingerprint:goals-index` and
`//#lint:policy-fingerprint:lint-roadmap-refs`, plus the `REVIEW configuration-source-drift: turbo.json`
row those two seals produce.

The cause is one import removal. `packages/tooling/tool/cli/src/commands/Goals/PortfolioIndex.ts` no
longer imports `readGoalLifecycle` from `./Completion.ts`: the generated `goals/INDEX.md` renders committed
manifest facts only (the manifest status group and a `proposed completed-retained via #N` column), because
the completion receipt it used to read is clone-scoped and made the generated bytes differ between clones.
`Completion.ts` carries the Yeet internals (verdict, proof job, review window, merge readiness), the git and
GitHub drivers and their schema closure, so dropping the edge removes that closure from every policy task
whose command path reaches `PortfolioIndex.ts`:

- `//#lint:policy-fingerprint:goals-index` (`//#goals:index`): 352 inputs before, 70 after; 282 removed, 0
  added.
- `//#lint:policy-fingerprint:lint-roadmap-refs` (`//#lint:roadmap-refs`, which imports
  `PORTFOLIO_INDEX_PATH` from `PortfolioIndex.ts`): 371 inputs before, 91 after; 280 removed, 0 added.

The removed inputs are the same files in both seals (`packages/drivers/git/**`, the GitHub driver, the Yeet
internal modules and the `@beep/*` packages only they import). No seal gains an input; the `shared`,
`goals` and `lint` parent seals are unchanged (395, 3 and 3 inputs). The other edits of the PR
(`Completion.ts`, `Doctor.ts`, `Graph.ts`, `Graph.projection.ts`, `Graph.schemas.ts`,
`Goals.schemas.ts`, `Session/Session.command.ts`) add imports only between modules already in each
affected seal's closure, so no other task drifts: `bun run beep lint policy-fingerprint` reports
`current` after `--write`, and the two files it regenerates (`turbo.json` seal inputs and
`standards/policy-tools.fingerprint.json`) are the whole root-config change.

The root (`//`) manifest and its scripts do not change; `bun run beep lint package-scripts` has nothing
to rewrite. Task names, outputs, cache flags and `dependsOn` edges are unchanged; only the two seals'
`inputs` arrays shrink.

Recording subject `//` accepts the existing posture for the two drifted root tasks with their smaller
input sets. No qualification is granted, and no other subject changes.
