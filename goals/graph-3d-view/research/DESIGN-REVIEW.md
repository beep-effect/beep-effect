# DESIGN-REVIEW — adversarial critique (codex, gpt-5.6-sol)

## Verdict: unsound

The document chooses a plausible renderer boundary and covers the eight named decision headings, but it does not pass the binding P0 gate. The required WebKitGTK benchmark is explicitly deferred, the recorded benchmark is not reproducible from its cited artifact, the proposed importance signal contradicts the normative betweenness requirement, and the worker design never specifies a force-directed 3D layout. Depth preservation, selection/reprojection sequencing, StrictMode teardown, and live theming also remain too incomplete to implement safely. These are contract failures, not P1 tuning details.

## Blocking findings

1. **The binding P0 WebKitGTK benchmark was not run, and the reported Chromium results are not auditable from the cited artifact.** SPEC makes the benchmark part of the P0 design gate and warns that no stack is already proven (`SPEC.md:94-96,101-104`); VERIFICATION requires WebKitGTK frame-time distribution, interaction latency, mount/update time, GPU/JS memory, draw calls, label admission/rejection, picking cost, and exact Three dedupe (`VERIFICATION.md:81`). DESIGN instead calls Chromium evidence sufficient to pick the stack and defers the acceptance run to P2 (`DESIGN.md:329-339`). Its only cited source is explicitly untracked and temporary (`DESIGN.md:301-306`), hard-codes 5,000 edges (`.bench-graph3d/main.ts:32-35`), and therefore cannot reproduce the reported 12,500-edge row (`DESIGN.md:323`). The result object records neither mount/update time, memory, nor admitted/rejected labels (`.bench-graph3d/main.ts:537-565`), and the scripted run never calls the picking function, so a zero `lastPickMs` is not a picking measurement (`.bench-graph3d/main.ts:524-529,579-599`). **Fix:** before accepting D1, run the exact candidate inside Professional Desktop/Tauri WebKitGTK at ~2,500 nodes/~300 labels, commit a durable benchmark source plus raw run output, and report every §5.10 metric, WebKitGTK/GPU versions, DPR, warm/cold protocol, and lockfile dedupe. Re-run all configurations from immutable inputs; do not report the absent 12,500-edge run or infer a higher ceiling from a vsync-capped average.

2. **The design substitutes degree for the normative betweenness-centrality signal.** SPEC says label importance is betweenness centrality (`SPEC.md:82-86`). The corpus demonstrates that degree and weighted degree mis-rank important bridge nodes and explicitly rejects either as the sole prominence metric (`demo-behavior-matrix.md:69-78`). DESIGN nevertheless proposes a cheap degree-based proxy and defers true betweenness unless visual QA looks bad (`DESIGN.md:175-181`). That also makes D3's `nodeImportance` comment misleading: the production mapping would not initially be a “bc-analog” faithful to the accepted grammar (`DESIGN.md:104-108`). **Fix:** make true betweenness part of the worker/projection contract now, with an exact directed/undirected and weighted/unweighted definition, normalization, deterministic tie-breaking, and a measured complexity budget at 2.5k. A fallback requires a SPEC change, not a silent P0 downgrade.

3. **No force-directed 3D layout is actually designed.** The objective requires a force-directed 3D graph (`SPEC.md:6-10`). D4 correctly chooses a frozen renderer, but only says that the worker will extend a deterministic seed into a “community-clustered spherical placement” (`DESIGN.md:144-167`); it names no force solver, forces, iteration/termination rule, collision policy, or post-seed relaxation. The current worker merely creates a deterministic 2D phyllotaxis seed (`Session.visualizer.ts:791-821`) and uploads it unchanged (`Session.visualizer.ts:973-987`). “Freeze after worker layout” can satisfy the verify-gate choice, but “render a spherical seed” cannot satisfy force-directed layout. **Fix:** specify and prototype a DOM-free worker algorithm that starts from deterministic xyz, applies named 3D forces with prose-level constants and a deterministic stop condition, emits baked xyz, and is included in the target benchmark. If the intended product is deliberately non-force-directed, change the normative objective first.

4. **The claimed non-destructive z contract is optional, re-derived, and underspecified across the encoded worker boundary.** The binding correction says to preserve baked xyz and flatten/restore non-destructively (`VERIFICATION.md:73`). DESIGN makes `pointDepths` optional and says depth is re-derived on return to 3D (`DESIGN.md:155-167`), which is weaker than preserving the same baked buffer and can change when membership/order/options change. It also says the protocol change flows “automatically” (`DESIGN.md:170-174`), but the actual wire schema embeds `OntologyGraphProjection` in both commands and results (`Session.worker-protocol.ts:73-93,203-218`) and deliberately encodes/decodes it because structured clone is not type preserving (`Session.worker-protocol.ts:248-280`). Delta requests also send the previous projection, so optional/missing-depth behavior must be defined in both directions. **Fix:** make the production 3D depth buffer required for every completed projection (or define an explicit versioned 2D/3D union), retain that exact buffer while toggling renderers, specify its length/invariants and delta behavior, and enumerate codec, fixture, constructor, and worker round-trip changes. The toggle itself must never trigger depth regeneration.

5. **Index-based selection is not safe across the accepted focus reprojection.** Current selection feeds `focusIri` and filters the next projection to a depth-one hierarchy neighborhood (`Session.atoms.ts:1000-1007`; `Session.visualizer.ts:673-689`). DESIGN stores selection in the handle as a node index (`DESIGN.md:112-118,138-139`), immediately writes the IRI atom, accepts the reprojection round-trip, and defers separating focus if it feels jarring (`DESIGN.md:242-249`). Projection nodes are rebuilt in sorted order (`Session.visualizer.ts:887-925`), so the old index can identify a different node after update. D8's assertion that both renderers “read the same” selection does not define the required remap/reapply order (`DESIGN.md:292-295`), and the integration ledger explicitly requires this gate to separate visual selection from focus or intentionally specify the depth-one behavior (`integration-constraints.md:200-208`). **Fix:** decide the model at P0. Either introduce a visual-selection IRI distinct from `focusIri`, or specify the accepted reprojection transaction: emit IRI, suppress callback echo, update projection, resolve that IRI to the new index, then reapply `select`; define behavior when it is absent. Cover tree→canvas, canvas→tree, empty-clear, toggle, and projection-update cases.

6. **StrictMode safety is asserted without a lifecycle contract or representative proof.** SPEC requires complete GL/worker/rAF/observer teardown across mount→cleanup→remount (`SPEC.md:77-81`). DESIGN only says the bridge finalizer will call `destroy` (`DESIGN.md:282-288`). The prototype creates a renderer and controls, installs anonymous click and resize listeners, and starts an unbounded animation loop (`.bench-graph3d/main.ts:151-167,508-514,571-608,619-623`); it exposes no destroy path at all. Thus the benchmark does not exercise the highest-risk part of the proposed custom engine. **Fix:** add an explicit idempotent ownership table and destroy sequence covering rAF, controls, listeners, `ResizeObserver`/theme observer, textures, materials, geometries, canvas removal, worker ownership, and WebGL context loss/restoration; exercise mount→destroy→remount in the P0 prototype and retain the required browser test for P1.

7. **The theming decision has no live update contract and does not fully decide the light-mode mapping.** D3 exposes only mount-time `background` and `labelColor` (`DESIGN.md:120-123`), while D7 says the client observes root-class changes and passes theme-derived values (`DESIGN.md:251-268`). The handle has no theme update method, and no remount policy or exact light values are given. The workbench actually has separate semantic CSS variables and a live class-based color scheme (`integration-constraints.md:104-110`), so this gap will either leave a stale canvas after a theme change or force an undocumented renderer remount. **Fix:** choose one complete contract: either the graph is intentionally always `#111111`/white regardless of app theme, or define exact CSS-token-to-renderer mappings and an idempotent `setTheme`/update path owned by the client bridge. Include edge/dim colors, not only canvas and labels.

8. **The downstream synthesis omits a binding verify-gate correction and leaves community ordinals unstable.** VERIFICATION requires the final 150-node/1,497-captured-of-1,500-edge/six-community facts, metric ranges, and resolved topic/palette mapping to be carried into downstream synthesis (`VERIFICATION.md:75`). DESIGN claims fixes 1–7 are honored (`DESIGN.md:11-12`) but does not record those facts, and its production mapping merely says “community ordinal” while deriving ordinals from cluster identity without defining stable ordering (`DESIGN.md:104-107,175-180`). Palette slots can therefore drift across projections. **Fix:** add an explicit conformance table for every binding §5 item and define deterministic community-ID/cluster-ID→palette-slot assignment that is stable across updates; record the final dataset facts as reference calibration, not as evidence for 2.5k performance.

## Non-blocking findings / risks worth recording

- D1 omits the static-analysis-confirmed cubic self-loop path and specifies only quadratic ribbons (`DESIGN.md:27-35` versus `VERIFICATION.md:26`). Current ontology projection removes same-node edges (`Session.visualizer.ts:942-944`), so this is not immediately reachable, but the driver contract should either reject self-loops or define them.
- The edge-opacity formula becomes negative above 9,025 edges. DESIGN states the unclamped formula (`DESIGN.md:27-32`), while the prototype silently clamps it to 0.10 (`.bench-graph3d/main.ts:263-266`). Make the clamp part of the design before using the 12,500-edge stress case.
- `Graph3DProjection` gives typed-array shapes but no length/index invariants (for example, xyz length = `3 * nodeCount`, links length = `2 * edgeCount`, link indices in range, labels aligned). These should be constructor validation or explicit trusted-boundary preconditions.
- The benchmark's label update always passes `null` instead of the current selection (`.bench-graph3d/main.ts:604-607`), so it does not test selected-label retention/dimming even though D5 says selection overrides label admission (`DESIGN.md:204-207`).
- CPU picking tests every node but only rejects `proj.z > 1`; it does not reject points behind the camera or account for projected node size (`.bench-graph3d/main.ts:487-505`). Correctness should be proven before retaining the 24 px rule.
- D3 defers sparse updates appropriately, but the future “designed-in” claim should not imply topology handling is solved: add/remove compaction, capacity growth, and incident-edge rewrites remain unspecified (`DESIGN.md:129-133`; `library-landscape-3d.md:85-92`).

## Checked-and-clean

- **Driver placement/import topology:** `packages/drivers/graph-3d` is a defensible home for a Three/browser wrapper; ontology `client` imports `@beep/graph-3d/browser`, and slice `ui` does not import the driver (`DESIGN.md:67-89`; `03-driver-boundaries.md:57-59,75-85`; `07-non-slice-families.md:187-195`).
- **Storybook hosting:** the current glob only covers foundation stories, so adding a driver glob is necessary and allowed by the packet (`DESIGN.md:69-72,85-89`; `apps/storybook/.storybook/main.ts:25-28`).
- **Three/Reagraph correction:** Reagraph is correctly rejected because `^0.184.0` excludes `0.185.1`, and the custom candidate adds no competing Three range (`DESIGN.md:42-44,59-65`).
- **Observed visual constants:** DESIGN uses `#111111`, distinguishes static-analysis edge constants from runtime measurement, and retains the confirmed 0.10/0.35 dim values while defining its own click semantics (`DESIGN.md:27-35,232-240,258-260`).
- **Renderer toggle default and cosmos boundary:** cosmos remains the default, the stable ref requirement is recognized, and no cosmos-driver modification is proposed (`DESIGN.md:273-295`; `Session.workbench.tsx:653-665`).
- **Gate-decision coverage:** rendering stack, placement/Storybook, projection, layout ownership, label technique, interaction/selection, theming, and toggle UX all have explicit sections. The findings above concern correctness and completeness of those decisions, not missing headings.
