# Reflection — oip-web-production-hardening (2026-07-14, codex)

## Summary

The retained deliverable is the production-hardened OIP app, Sanity and HubSpot
drivers, OIP-oriented IaC/state/assets, security/PWA/SEO work, and recorded
quality/browser proof. Closeout showed that the remaining work is operational
launch sequencing, not unfinished implementation.

## Tooling experience

- **Worked:** The completion audit and local closure evidence connected every
  prompt requirement to concrete app, driver, infrastructure, and proof assets.
- **Didn't:** Provider-dependent final state could not be represented as one
  universal "done" command without credentials and launch authority.
- **Frustrating:** A single packet status obscured the difference between coded
  infrastructure intent and approval-gated provider cutover.
- **Wished existed:** A first-class packet disposition for shipped code with an
  external launch runbook and named authority gates.

## Implementation improvement opportunities

- Provision Sanity only with least-privilege OIP credentials, then repeat the
  staging content proof before public cutover.
- Keep the B+/80 CSP until a request-bound nonce or hash path is proven against
  the real Next runtime.

## Goal & prompt critique

The closure goal bundled implementation, provider apply, and public-launch
authority. A clearer contract would define code-complete as the retained outcome
and list TLS activation, Sanity provisioning, fresh staging proof, and DNS
cutover as runbook steps with separate triggers.

## TODOs worth codifying

- Model launch-time provider actions as external gates, not open code phases.
- Require explicit approval before production DNS or legacy redirect cutover.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Do not equate provider cutover with implementation
  completion — the shipped app and IaC remain valid before launch authority.
- **MEDIUM — Best practice:** Preserve a reviewed local content fallback — CMS
  credentials should not become a prerequisite for safe rendering.
- **LOW — Consideration:** Pursue A+ only with runtime-compatible CSP machinery —
  a stricter static header was demonstrably unsafe for this Next app.
