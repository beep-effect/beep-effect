# Reflection: runner-trust-boundary (2026-08-25, claude)

## Summary

The packet delivered the ratified posture: heavy pull-request lanes stay on
EC2, and the runner class that runs them has no usable ambient credentials,
boots each job on a fresh VM from a sealed digest-verified image, and is
admitted only through default-branch workflows in a selected organization
group. The final-head red team on `4764cdb4ba` passed every gate exactly once,
including concurrent JIT replay rejection, and all six transferred Codex IDs
closed with deployed evidence. Two exceptions stand: post-release replay is
untested (E1) and four IDs closed a day before the P4 re-proof (E2). The
security design held at every phase; the friction was in rollout mechanics,
ledger discipline, proof scope, and proof latency.

## Tooling experience

- **Worked:** `redteam-verify.sh` as the single proof oracle (scoped
  deregistration, live metadata sampling, the serving-pin default for
  `AMI_PIN`, and the conditional `M_JIT_REPLAY` gate made P4 a one-command
  proof); the jobs API `runner_group_name` and run `referenced_workflows`
  fields as admission evidence; `pulumi up --diff` with the passphrase read
  from the secret manager into the environment; detached runbooks with a
  line-buffered log monitor for long AWS and GitHub waits; Yeet monitor and
  reply for review closeout.
- **Didn't:** the GitHub App installation permission was invisible until the
  first organization registration failed; the IAM simulator could not
  resolve `${ec2:SourceInstanceARN}`, so self-scoping needed live dry-runs;
  `gh run view --log` is unavailable while a run is in progress, which
  delayed fast-path evidence from the push run.
- **Frustrating:** the replay probe waited out its full timeout after the
  rejection; out-of-allowlist and unresolvable-group dispatches burned
  candidate launches; the earlier dashboard closure draft lived only in a
  scratchpad and was lost, so P6 had to re-read the dashboard before it could
  write the ledger; the Codex findings dashboard has no closure API.
- **Wished existed:** an admission pre-check in the scale-up lambda; a
  lockfile-triggered bake; a tracked dashboard closure export.

## Implementation improvement opportunities

- Classify Probe M from a tailed listener log and stop the listener on the
  first anchored match.
- Resolve the runner group before `RunInstances` and make a lookup failure
  non-retryable at the configuration level.
- Skip candidate launches for workflow references outside the group's
  selected workflows.
- Bake and pin on every `bun.lock` change to `main` so the integrity check
  rejects for at most one bake cycle.

## Goal and prompt critique

- Reword the P5 gate to "every remediation PR is merged" and state that the
  closeout PR is documentation; the single-PR wording forced a recorded
  reading rather than a plain check.
- Have `GOAL.md` separate idempotent proof reads from one-shot deployments so
  a fresh session cannot mistake "rerun the proof" for "redo the cutover".
- Name the exact dashboard ledger file in the SPEC's P6 text so the closure
  action and its record are one step.

## TODOs worth codifying

- Probe M early exit on anchored match.
- Same-PR `ops/closures.json` rule, with a doctor check for completed packets
  that transferred Codex IDs.
- Lockfile-triggered bake in `ci-fleet-endgame`.
- Controller group resolution before launch; alarm without relaunch.
- Packet template wording for multi-PR remediation gates.

## Lessons by confidence

- **HIGH, critical:** Prove security state while the worker is alive.
  Terminated instances report metadata `pending`, and a post-run read
  produced a false `METADATA_DISABLED` failure until the verifier sampled
  live (P2, kept through P4).
- **HIGH, critical:** A fail-closed registration path is the proof that no
  fallback exists. Both the permission incident and the absent-group probe
  left zero registrations at any scope; treat launch-and-terminate churn with
  zero registrations as the signature of a group or permission
  misconfiguration.
- **MEDIUM, best practice:** Record every outward action in a tracked ledger
  in the same PR; a scratchpad draft is not a record.
- **LOW, consideration:** Re-baking after a lockfile change is a performance
  concern, not a security one; the correct rejection of a stale image should
  not be confused with a boundary failure.
