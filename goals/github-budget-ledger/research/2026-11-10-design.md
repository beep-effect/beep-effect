## 1. Scope recap and first vertical slice

The goal records what every GitHub request made by repo tooling costs, keyed **identity x resource x command x host**.
It samples the free `GET /rate_limit` per configured identity, which gives fleet-wide truth for the REST buckets.
GraphQL truth comes from GraphQL response headers, with REST samples admitted only after calibration (section 6.5).
It shows a `github-headroom` parcel in `session open`, publishes a 15% reserve signal per identity x resource, and
closes with a 24 h hub baseline and the T3 share threshold. Non-goals (SPEC "Non-Goals"): no polling changes, no ETag
layer, no identity switch, no `gh` PATH shim, no cross-host state, no webhooks, no t3code change.

**First vertical slice.** This follows MAP "First vertical slice" and PLAN "Execution Notes". The path is proven end
to end before attribution is widened:

```text
beep yeet monitor --until-ready                        (command label "yeet monitor", from the loaded command tree)
  └─ GithubLedgerRoot.withGithubLedger                  (ledger + sink + sampler + GhSpawnSink at the root)
  └─ layerGithubClientFor(identity)                     (canonical identity label, passed as budgetLabel)
       └─ @beep/github makeTransport                    (every response → RateLimitObservation → RateLimitSink)
            └─ GithubBudgetLedger.recordTransport       (append Transport row to ledger/rows/<hour>.jsonl)
  └─ monitor poll: sampler.sampleIfDue                  (2 × GET /rate_limit, free → Sample row + latest/sample-<id>.json)
beep github ledger sample   (systemd timer, 5 min)     (Sample rows for non-App identities; latest/summary.json)
beep session open
  └─ hot parcels → github-headroom                      (reads latest/*.json only; no network, no identity resolution)
```

The slice is done when one `yeet monitor --until-ready` on the hub writes rows carrying identity, resource, command,
host, `limit`, `remaining`, `used` and `reset`, and `session open` prints a `github-headroom` line from them. The next
slices add `gh` spawn attribution (section 5) and ledger-first `GraphqlBudget` (section 7).

### 2.1 `GitHubRateLimitResource` (driver, canonical)

`GitHubRateLimitResource` is GitHub API knowledge, so it lives in the driver. The CLI imports it from
`@beep/github/Resilience`. The literal set is the `GET /rate_limit` `resources` keys from the current REST docs
(docs.github.com/en/rest/rate-limit/rate-limit): `core`, `graphql`, `search`, `code_search`, `source_import`,
`integration_manifest`, `actions_runner_registration`, `scim`, `dependency_snapshots`, `dependency_sbom`,
`code_scanning_autofix`, `copilot_usage_records`. It adds three keys that earlier docs and live responses carry
(`code_scanning_upload`, `audit_log`, `audit_log_streaming`) and a closed `unknown` for an absent or unrecognised
header. The docs also say the `x-ratelimit-resource` header names "the rate limit resource that the request counted
against", and that for GraphQL it "will always be `graphql`".

```ts
// D/Resilience.ts (additions)

```

A new GitHub bucket name decodes to `unknown` in a header and is dropped from a `/rate_limit` body (section 2.6). It
is logged at debug level. Adding it later only extends the literal list.

### 2.3 `RateLimitObservation` and `RateLimitSink` (driver)

The transport emits one observation per HTTP attempt. The driver knows nothing about commands, hosts or the CLI's
identity grammar. It reports two separate facts:

- `budgetLabel` is an opaque, non-secret string that the caller passes in and the driver never parses or composes.
  It plays the role of Prow's `X-PROW-GHCACHE-TOKEN-BUDGET-IDENTIFIER`, kept separate from any token (exploration
  `research/2026-11-09-external-landscape.md` section 1).
- `credential` is the technical kind of credential the request carried. The driver knows it without knowing who
  owns the bucket.

```ts
export const RateLimitRequestKind = LiteralKit(["rest", "graphql"]).pipe($I.annoteSchema("RateLimitRequestKind", {
```

`S.brand` (`EFX/Schema.ts:5359`) stops an arbitrary string from standing in for a label. Labels are only built by
`GithubIdentityLabel.make` or a decode.

**How the identity label is derived.** This is `CLI/internal/github/GithubIdentityLabel.ts`, function
`resolveGithubIdentityLabel({ identity, token })`. It runs inside `layerGithubClientFor` after the token is read, and
in the sampler. It is never called on the read side (section 4.1).

| `GithubIdentity.kind` (`GithubIdentity.ts:88`) | Label | How |
| --- | --- | --- |
| `github-app` | `app:<appId>/<installationId>` | From the identity's `appId` and `installationId` (`GithubIdentity.ts:222-245`). The ledger turns `credential: "app-jwt"` rows into `…/jwt` (section 3.4). |
| `gh-cli`, no `GH_TOKEN`/`GITHUB_TOKEN` | `user:<login>` | `gh config get -h github.com user` through `Run.text`. This reads gh's local `hosts.yml` and makes no API call. The output is checked against the login pattern. The alias `sha256(gh auth token)[0..12] → login` is written to `aliases.json` at the same time, at no API cost. |
| `gh-cli` with `GH_TOKEN`/`GITHUB_TOKEN` set, `op-ref` | `user:<login>` from the alias map when the token hash is known | `aliases.json` lookup (no network). |
| `op-ref` | `user:<login>` from `identities.json` when an `OpRef` entry has the same `tokenRef` | Configuration (section 2.8); the alias is recorded too. |
| any token kind, hash unknown | `user:<login>` after one `GET /user` | Section 2.4.1. On any failure of that call the label is `token:<hash>` for this process. |
| `gh-cli` when `gh config get` fails | alias lookup of the `gh auth token` hash, else `GET /user` as above | Hash of the token that `gh auth token` already returned (`GithubIdentity.ts:403`). |

The hash is `sha256(token)`, lowercase hex, first 12 chars, through `effect/crypto/Digest` (`Digest.sha256`,
`Digest.layerWebCrypto`, `EFX/crypto/Digest.ts:85,159`), already used in
`CLI/commands/Accounts/AccountsUsage.service.ts:26`. A 48-bit prefix of a SHA-256 over a high-entropy token cannot be
reversed, and Prow labels its metrics with the full sha256. Labels contain logins and App ids, which are public; they
never contain tokens, paths or machine ids.

#### 2.4.1 One bucket, one label: the alias map

A PAT or OAuth token draws on its owner's user bucket, so `token:<hash>` and `user:<login>` can name one bucket. The
ledger keeps one label per bucket:

```ts
export class IdentityAliases extends S.Opaque<IdentityAliases, { readonly brand: unique symbol }>()(
  S.Struct({
    schemaVersion: S.tag("github-identity-aliases/v1"),
    // token-hash label → user label. Non-secret: a 12-hex hash prefix and a public login.
    aliases: S.Record(S.String.check(S.isPattern(/^token:[0-9a-f]{12}$/)), GithubIdentityLabel),
  }).pipe(…)
) {}
```

- **Where:** `ledger/aliases.json`, 0600, written atomically (section 4.2). It is host-scoped like the rest.
- **Seeding without network:** a `gh-cli` resolution knows both the login and the token, so it records the alias.
  A configured `OpRef` with its `login` records the alias the first time its token is read.
- **`GET /user` fallback:** when a token's hash has no alias, `resolveGithubIdentityLabel` makes one `GET /user` on
  a client built with `budgetLabel: "token:<hash>"`. That request is an ordinary Transport row, nominal 1, under the
  `token:` label. On success it writes the alias and returns `user:<login>`. This happens once per new token lineage
  per host. A PAT rotation is the only trigger, which is rare.
- **Canonical at record time:** the ledger maps a `token:` budget label through the alias map before writing a row.
- **Canonical at read time:** `windowsOf`, `reserveOf`, rollups and the parcel map every row's identity through the
  same map, so rows written before an alias existed join their owner's bucket.
- An App installation token is not a user token and never gets an alias.

**How the host label is derived.** `NodeOS.hostname()` (the repo precedent is
`CLI/commands/Yeet/internal/ArtifactPaths.ts:182`), cut at the first `.` and lowercased. A value that fails
`HostLabel` becomes `unknown-host`.

**How the command label is derived.** `commandLabelOf(root, argv)` walks the loaded `effect/cli` command tree, so only
known group and subcommand names can appear:

1. Skip root flags exactly as `Dispatch.firstPositional` does (`CLI/internal/dispatch/Dispatch.ts:80-89`): a token in
   `ROOT_VALUE_FLAG_NAMES` skips itself and its value, any other `-`-prefixed token skips itself, and `--` stops.
2. Starting at `root` (`Dispatch.makeRootCommand(commands)`, `Dispatch.ts:228-236`), take the next positional token.
   It counts only when it equals the `name` of a command in the current command's `subcommands[*].commands`
   (`EFX/cli/Command.ts:162-165`). Descend into that command and repeat.
3. Stop at the first token that is not a child name, at the first flag after the group, or after three names.
4. No names gives `beep`.

Examples:

- `yeet monitor --until-ready` gives `yeet monitor`.
- `yeet job wait 6f…` gives `yeet job wait`.
- `goals set-status github-budget-ledger` gives `goals set-status`. The slug is not a child name.
- `worktree remove some-lane --archive` gives `worktree remove`.
- `--log-level debug yeet monitor` gives `yeet monitor`.
- An empty argv gives `beep`.

A lazily loaded group whose facade was not imported is a stub with no children (`makeStubCommand`), so its label is
the group name alone. That never happens for the group being run, because `loadDispatchTarget` imports it.

**How the operation is normalised.** The driver reports the route as the caller passed it. Typed routes are already
templates (`GET /repos/{owner}/{repo}/pulls`), but two callers interpolate concrete paths:
`Reviewer/ReviewerRuleset.ts:203` (`` `GET /${path}` ``) and `Ci/LaneTimings.ts:924` (`` `GET /${endpoint}` ``).
`normalizeOperation(raw)` in `GithubLedger.schemas.ts` runs at record time and is pure:

- `METHOD /path?query` drops the query.
- `repos/<a>/<b>` becomes `repos/{owner}/{repo}`; `users/<a>` and `orgs/<a>` become `users/{user}` and `orgs/{org}`.
- A segment that is all digits becomes `{id}`; a segment of 7–40 hex characters becomes `{sha}`.
- The segment after `branches`, `refs`, `heads`, `tags`, `environments`, `secrets`, `variables` or `labels` becomes
  `{name}`.
- After eight segments the rest becomes `…`, and the result is cut to 120 characters.
- A GraphQL operation name (`query X` / `mutation X`) passes through unchanged.

The two callers are not changed; normalisation bounds cardinality for them and for any future interpolating caller.

### 2.5 Ledger rows

There is one tagged union with one row per line. Rows are append-only. An encoded line longer than 4 KiB is
rejected before writing and logged at debug. The cap is a sanity bound against a runaway field, not an atomicity
invariant (section 4.2). The largest row is a `Sample` with all 15 named buckets: about 1,830 bytes measured with
realistic values, so every legitimate row fits with room to spare. A test pins that (section 9).

```ts
export const GithubLedgerSource = LiteralKit(["transport", "gh-spawn", "sample", "calibration"]).pipe(…);
/** The source of a row: the kebab-case of its _tag. */
export const sourceOfRow = (row: GithubLedgerRow): typeof GithubLedgerSource.Type =>
  GithubLedgerRow.match(row, { Transport: () => "transport", GhSpawn: () => "gh-spawn",

export const SelfCost = LiteralKit(["confirmed-free", "unconfirmed"]).pipe(…);

  S.Struct({ resource: GitHubRateLimitResource, limit: S.Int, used: S.Int, remaining: S.Int,
             resetAt: S.DateTimeUtcFromString }).pipe(…)

    at: S.DateTimeUtcFromString, host: HostLabel, command: GithubLedgerCommandLabel, identity: GithubIdentityLabel,
    subcommand: GhSubcommand, resource: GitHubRateLimitResource,   // inferred, see section 5

  },
  /** One GET /rate_limit read: the fleet-wide truth for one identity's REST buckets. */

```

`TaggedUnion` exposes `cases` (`EFX/Schema.ts:6585`), so `SampleRow` is the `Sample` case's decoded type.

**Cost semantics.** Headers report the fleet-wide bucket state after a response, not that request's cost. Concurrent
fleet traffic lands between any two header reads, so a per-row cost cannot be measured from headers alone. The row
therefore stores raw header values, and cost is computed at read time from two parts:

- `nominalCost` is fixed at record time:
  - `0` for status 304. It is free on a correctly authorized request. Goal 2's ETag layer produces these; there are
    none in goal 1.
  - `0` for `GET /rate_limit`, whose docs say "Accessing this endpoint does not count against your REST API rate
    limit".
  - `0` for outcome `rate-limited` (a primary-limit refusal: remaining was 0, so nothing was left to charge).
    Charging it would inflate `attributedNominal` during retry storms, which are exactly the windows of interest.
  - `1` for every other REST attempt, including `secondary-limited` and `error`.
  - `1` for GraphQL. This is GitHub's minimum point cost, so it is a floor.
- True points come from telescoped bucket deltas and the per-operation estimator (section 6.4).

Goal 2 can add an optional `cacheMode` key (Prow's `MISS`/`CHANGED`/`REVALIDATED`/`COALESCED`/`NO-STORE`/`SKIP`).
Old rows still decode because the key is optional. Goal 1 records `free` only as `nominalCost === 0`, through a
getter in the service module.

### 2.7 Reserve signal

```ts

  { key: BucketKey, state: ReserveState }, $I.annote("ReserveSignal", { … })

  /** Background callers back off while Below; interactive and merge-critical callers are never refused here. */
```

`ReserveSignal` uses `S.Class` because it carries getters and methods. `S.Opaque` values are plain structs (the same
split as `RateLimitSnapshot`, `D/Resilience.ts:51`).

`reserveOf(now, calibration)(readings)` is a pure function over the readings for one key:

- For a `graphql` key, sample-basis readings are ignored unless calibration admits them (section 6.5). If only
  sample readings exist and calibration does not admit them, the state is `Unknown{uncalibrated}`.
- No usable reading gives `Unknown{no-reading}`.
- The newest reading older than 10 min gives `Unknown{stale}`.
- `resetAt <= now` gives `Unknown{window-reset}`, because the window rolled.
- `remaining < floor` gives `Below`; otherwise `Clear`.

`Unknown` admits background callers. The first response's headers fill the ledger within the same request, and
`Below` takes effect from the next call. This is a goal 1 choice, and goal 2's worker may tighten it (ambiguity A7).

### 3.1 Options

- `TransportOptions` (`D/internal/octokit.ts:112-147`) gains `budgetLabel: S.optionalKey(S.String)` and

- `GitHubAppOptions` (`D/GitHubApp.ts:832` region) gains `budgetLabel` only. Every App client spreads `options`

  never composes or invents a label.
- The credential is derived, not configured, except for one call:
  - The JWT client (`:1313`, `makeClientShape({ ...options, token: jwt })`) passes `credential: "app-jwt"`.
  - Everywhere else `makeTransport` derives it: a non-empty token gives `token`; an absent or empty token gives
    `unauthenticated`. `asBearer(undefined, …)` builds a client with `Redacted.make("")` (`:1325`), so the bot-user

    real token, so they are `token` and keep the installation's label.

The label is not a token and is never used in a header.

### 3.2 `makeTransport`

`makeTransport` (`D/internal/octokit.ts:277-436`) gains four things.

1. **Capture the sink once at build.** `const sink = yield* RateLimitSink` sits next to the `Ref.make` at `:281`. The
   reference resolves from the context the client layer is built in. The CLI root provides it (section 4.4), so
   every layer built under it sees it. With nothing provided, the sink is a no-op and behaviour is unchanged.
2. **`record` takes context and emits.** The existing `record` (`:284-287`) becomes:

   ```ts
   interface RecordMeta { readonly operation: string; readonly kind: RateLimitRequestKind; readonly status: number;
                          readonly outcome: RateLimitOutcome }
   const record = Effect.fnUntraced(function* (headers: Readonly<Record<string, unknown>> | undefined, meta: RecordMeta) {
     const parsed = O.flatMap(readRateLimitHeaders(headers), S.decodeUnknownOption(RateLimitSnapshot));
     if (O.isNone(parsed)) return;
     // GraphQL always counts against "graphql" (docs); keep a header value when present.
     const snapshot = meta.kind === "graphql" && parsed.value.resource === "unknown"
       ? RateLimitSnapshot.make({ ...parsed.value, resource: "graphql" })
       : parsed.value;
     yield* Ref.set(cell, O.some(snapshot));                    // unchanged last-value behaviour
     const at = DateTime.makeUnsafe(yield* Clock.currentTimeMillis);
     yield* sink.record(RateLimitObservation.make({ snapshot, budgetLabel, credential, at, ...meta })).pipe(
       Effect.timeoutOption(Duration.millis(250)),             // a wedged state dir cannot stall a request
       Effect.catchCause((cause) => Effect.logDebug("github.rateLimitSink", cause)) // never on the error channel
     );
   });
   ```

   `record` returns `Effect<void>` with no error, as it does today. `Effect.catchCause` also absorbs a sink defect.
   The `Ref` keeps the latest snapshot of any resource, which `Transport.rateLimit` (`:190`) still serves.

3. **Every attempt is recorded once, with its outcome.**
   - **REST success** (`request`, `:355`) records with `status: response.status`. The outcome is `not-modified` for
     304 and `ok` otherwise.
   - **Page success** (`pageSource`, `:409`) records the same way with `kind: "rest"`.
   - **Thrown failures** (`attempt`, `:313-318`) classify first, then record `readThrownHeaders(error)` with an
     outcome from `outcomeOf(status, headers, error)`. The order of `record` and `classify` swaps so the error is
     classified before it is recorded. `outcomeOf` follows GitHub's documented rule, in this order:
     1. Status 403 or 429 with `x-ratelimit-remaining: 0` gives `rate-limited` (primary).
     2. Status 429, or status 403 with a `retry-after` header, gives `secondary-limited`.
     3. A 403 body or a GraphQL `rejected` entry whose message matches `/\bsecondary rate\b/i` gives
        `secondary-limited`. This is the plugin-throttling detection, ported; see SOURCES `throttling-detect`.
     4. A GraphQL `RATE_LIMITED` entry (HTTP 200) gives `rate-limited`.
     5. Status 304 gives `not-modified`.
     6. Anything else gives `error`.

     `status` is the error's HTTP status, or `200` for a `GraphqlResponseError`, which has none. That makes the
     GraphQL 200-with-error rows in SPEC "Constraints" explicit. The driver's own retry classifier
     (`D/GraphQL.ts:293-330`, the error `kind`) is **not** changed: retry behaviour for a secondary limit served as
     200 belongs to goal 2 (ambiguity A12). `outcomeOf` only labels the row.
   - **GraphQL success.** This is the gap today. `octokit.graphql` resolves to `response.data.data` only. The
     `@octokit/graphql` 9.0.5 bundle drops the headers on success and keeps them only on a `GraphqlResponseError`
     (`node_modules/@octokit/graphql/dist-bundle/index.js:86-95`). As a result, **no successful GraphQL response is
     recorded today** (`D/internal/octokit.ts:418-433` has no `record` tap). The fix is a per-attempt `fetch` that
     observes the response headers:
     - `@octokit/request`'s `fetchWrapper` uses `requestOptions.request?.fetch || globalThis.fetch`
       (`node_modules/@octokit/request/dist-bundle/index.js:35`).
     - `@octokit/graphql` passes the `request` key through as a non-variable option (`NON_VARIABLE_OPTIONS`, `:40-45`).
     - `@octokit/endpoint` deep-merges `request` over the instance defaults (`mergeDeep`, `:43-48,77`).

     ```ts
     // inside graphql's attempt, per try
     (signal) => {
       let seen: Record<string, string> | undefined;              // per-attempt cell; precedent `let currentSignal` (:370)
       const base = options.fetch ?? globalThis.fetch;              // read at call time, so test stubs win
       const fetch: typeof globalThis.fetch = (input, init) =>
         base(input, init).then((response) => { seen = R.fromEntries(response.headers.entries()); return response; });
       return octokit.graphql<unknown>(document, withRequestOptions(variables, { signal, fetch }))
         .then((data) => ({ data, headers: seen }));
     }
     ```

     `withSignal` (`:474-483`) generalises to `withRequestOptions(params, extra)`. On success, the graphql pipe taps
     `record(result.headers, { kind: "graphql", status: 200, outcome: "ok", operation })` and maps to `data`. On
     failure, the existing thrown-headers path still applies (`readThrownHeaders`, `:486-493`, reads
     `error.headers`).
4. **`budgetLabel` and `credential`** are closed over at build: `O.fromUndefinedOr(options.budgetLabel)`, and
   `options.credential ?? (tokenIsNonEmpty ? "token" : "unauthenticated")`.

Each retry attempt is a real HTTP request, so each attempt is recorded. That is correct because each one is spent.

The module doc's "**nothing in this package throttles on your behalf**" (`D/Resilience.ts:31-33`) still holds.

**Layout.** The root comes from `resolveWorkstationStateDir({ override: "BEEP_GITHUB_LEDGER_STATE_ROOT", store:
"github/ledger" })` (`CLI/internal/state/WorkstationState.ts:73-81`), which gives `$XDG_STATE_HOME/beep/github/ledger`.

```text
ledger/                                    0700
  rows/2026-11-10T14.jsonl                 0600  append-only; all row kinds; one file per UTC hour
  latest/sample-user_alice.json            0600  newest Sample per identity, atomic

  sampler/user_alice.lock                  0600  sampler lease (exclusive create)
```

**Append.** Appends reuse the `JsonLinesStore` mechanics (`CLI/internal/state/JsonLinesStore.ts:214-231`):
`makeDirectory(..., { recursive: true, mode: 0o700 })`, then `writeFileString(file, line + "\n", { flag: "a", mode:
0o600 })`. The partition is the row's UTC hour. Corrupt or torn lines are counted and skipped by
`partitionJsonLines` (`:63`).

**Concurrent writers on one host.** Each row is one `write(2)` of one line on an `O_APPEND` descriptor to a local
regular file. On Linux the append offset update and the write happen under the inode lock, so whole writes of a few
KiB do not interleave. `PIPE_BUF` does not apply: it bounds pipe writes, not regular files. Bun's `FileSystem` is the
node-shared `NFS.writeFile` with `flag: "a"`, which issues one write for a buffer this size. The 4 KiB line cap
(section 2.5) keeps every row far below any size where a short write could split it. A reader that ever meets an
interleaved line skips it as corrupt, as the session ledger already does (same `JsonLinesStore`, host-wide per
`research/2026-11-09-in-repo-bricks.md` table (b)).

**Atomic writes.** Every `latest/*.json`, `aliases.json` and `rollups/*.json` write goes through `writePrivateFile`
(`CLI/commands/Palantiri/Palantiri.service.ts:127-140`): a 0700 directory, a random temp file at 0600, then `rename`.
That helper moves to `CLI/internal/state/PrivateFile.ts` and Palantiri re-exports it, so the ledger does not import
a command module. `writeAlias` reads, merges and renames; two concurrent writers can lose one alias, which the next
resolution of that token writes again.

**Sampler lease.** Acquisition, in order:

1. `fs.open(lock, { flag: "wx" })` (exclusive create; `OpenFlag` `"wx"`, `EFX/FileSystem.ts:472-482`). On success the
   holder writes `{pid, at}` and removes the file in an `Effect.acquireRelease` finalizer.
2. On `EEXIST`, read the lock's `mtime`. If it is younger than 120 s, return `false` (`Skipped{lease-held}`).
3. If it is older, reclaim it by `rename(lock, lock + ".stale." + <random>)`. Only one process can win that rename;
   the loser gets `ENOENT` and returns `false`. The winner unlinks the renamed file and retries step 1 once.
4. The caller re-checks `lastSampleAt` after acquiring the lease (section 6.2 step 3), so a process that wins the
   lease right after another one released it does not sample twice.

### 4.3 Retention, rotation and rollups

Rotation is by file name: one row file per hour, one rollup per closed hour.

| Data | Kept | Why |
| --- | --- | --- |
| `rows/*.jsonl` | 72 h, and at most 256 MiB in total (oldest hours past 24 h removed first) | The baseline needs 24 h. The estimate is about 2,400 rows/h × ~350 B for transport rows plus 12 samples/h/identity × ~1.9 KB, roughly 20 MB/day with three monitors. |
| `rollups/*.json` | 35 days | The `github-webhook-intake` gate reads a 7-day average (MAP "Gated candidates"). |
| `Sample` rows | Inside `rows/`, and as windows and hourly `fleetUsed` in rollups | Rollups keep the per-hour fleet deltas, so 35 days of usage survive the raw rows. |
| `latest/*.json`, `aliases.json` | Overwritten | — |

**When an hour's rollup is written.** `prune` considers every hour H whose raw file still exists and whose rollup is
missing or has `complete: false`:

- It writes a `complete: true` rollup once `now ≥ H + 1 h + 15 min` **and** every key with an anchor in H has an
  anchor after `H + 1 h` (so the window that straddles the boundary is closed). The 15-minute grace covers a row
  stamped `HH:59:59.9` that is appended after the hour ends.
- It writes a `complete: false` rollup once `now ≥ H + 3 h` without that condition (an idle sampler), so 35-day
  history never has silent holes.
- An incomplete rollup is recomputed on later prunes while H's raw file still exists. A complete rollup is never
  rewritten.

Two processes computing the same complete rollup produce the same bytes, because a complete rollup only reads rows
that can no longer change. A rename race between them is harmless.

`prune` runs only off the request path: at the end of `beep github ledger sample` (timer and manual) and in
`beep github ledger report`. After rollups it writes `latest/summary.json` (`summaryOf` over the last 60 min of rows
and the last complete hour's `unattributed`), then deletes raw hours past retention.

```ts
  Effect.fnUntraced(function* <A, E, R>(effect: Effect.Effect<A, E, R>) {
```

```ts

export class GhSpawnObservation extends S.Opaque<GhSpawnObservation, { readonly brand: unique symbol }>()(
  S.Struct({ args: S.Array(S.String), exitCode: S.Int, durationMillis: S.Int, at: S.DateTimeUtc }).pipe(…)

export interface GhSpawnSinkShape {
  readonly record: (spawn: GhSpawnObservation) => Effect.Effect<void>;
}
export const GhSpawnSink: Context.Reference<GhSpawnSinkShape> = Context.Reference(
  $I`GhSpawnSink`, { defaultValue: () => ({ record: () => Effect.void }) }
);

export const attributeGhSpawn = Effect.fnUntraced(function* <A extends { readonly exitCode: number }, E, R>(
  args: ReadonlyArray<string>, run: Effect.Effect<A, E, R>
) {
  const sink = yield* GhSpawnSink;
  const started = yield* Clock.currentTimeMillis;
  return yield* run.pipe(Effect.onExit(Effect.fnUntraced(function* (exit) {
    const ended = yield* Clock.currentTimeMillis;
    yield* sink.record(GhSpawnObservation.make({
      args, at: DateTime.makeUnsafe(ended), durationMillis: ended - started,
      exitCode: Exit.isSuccess(exit) ? exit.value.exitCode : -1,
    })).pipe(Effect.catchCause((cause) => Effect.logDebug("github.ghSpawnSink", cause)));
  })));
});

// RepoRun.executor.ts, runRepoCommand
const run = runCaptured({...}).pipe(Effect.mapError(DomainError.newCause(`Failed to spawn ${commandText}.`)));
return command === "gh" ? attributeGhSpawn(args, run) : run;
```

### 6.1 Read

`readGithubRateLimit: Effect<GithubRateLimitWire, GitHubError, GitHubClient>` is

### 6.2 Service

The live `labelOf` is `configuredLabelOf(entry)` when it is some, otherwise the `gh-cli` resolution of section 2.4

**One sample in `sampleAll`** (per entry). Nothing that costs a request, a mint or a secret read happens before
step 4:

1. A `GithubApp` entry returns `Skipped{app-needs-live-client}` (section 6.3).
2. `label = labelOf(entry)`. If `lastSampleAt(label)` is newer than `SAMPLE_INTERVAL − 30 s` (4.5 min), return
   `Skipped{not-due}`.
3. Acquire the lease (section 4.2); if it is held, return `Skipped{lease-held}`. Re-check `lastSampleAt(label)`; if
   it is now fresh, release and return `Skipped{not-due}`.
4. Build `clientFor(entry)` in a scope and run `samplePair` (below) with it.
5. `recordSample` appends the row and writes `latest/sample-<key>.json`.

**`sampleIfDue`** uses the `GitHubClient` in context and its `GithubBudgetIdentity` label, then runs steps 2–5 with
that client. It never builds a client, so it can sample an App identity whose client already exists.

**`samplePair`** makes two back-to-back `readGithubRateLimit` calls on the same client and keeps the second body as
the sample. `selfCost` is `confirmed-free` when the two bodies have the same `core.used` and the same `core` reset,
and `unconfirmed` otherwise. Both bodies come from their own responses, so a concurrent request on a shared client
cannot distort the comparison (`client.rateLimit` is not read). Fleet traffic between the two reads can only produce
`unconfirmed`, never a false `confirmed-free`. The transport records both requests as Transport rows with operation
`GET /rate_limit` and `nominalCost: 0`. The report shows the share of `confirmed-free` samples; any `unconfirmed`
share is checked against fleet traffic before concluding anything.

### 6.4 Epochs, windows, hourly usage and per-command points

All of this is pure and runs over one host's rows for one canonical key.

**Anchors.** An anchor is a reading of the bucket's fleet-wide `used` and `resetAt`. For REST resources the anchors
are `Sample` buckets. For `graphql` they are chosen by section 6.5. Every anchor carries `used`; a transport anchor
with `used` none uses `limit − remaining`.

**Reset epochs (`epochsOf`).** Anchors are sorted by `at`. Two consecutive anchors are in the same epoch when either:

- `|Δ resetAt| ≤ 5 s` (GitHub's reset epoch jitters slightly), or
- the earlier anchor has `used == 0`. An idle bucket reports `reset = now + 1 h` on every read, so its reset is not
  anchored and a moved reset does not mean a window rolled.

Otherwise the later anchor starts a new epoch.

**Windows (`windowsOf`).** Consecutive anchors `a_i`, `a_{i+1}` form the window `(a_i.at, a_{i+1}.at]`:

- Same epoch: `delta = a_{i+1}.used − a_i.used`, signed and not floored.
- New epoch with `a_i.used == 0`: `delta = a_{i+1}.used`, `crossesReset = false`.
- New epoch with `a_i.used > 0`: `crossesReset = true`, and `resetLowerBound = a_{i+1}.used + max(0, peakBefore −
  a_i.used)`. `peakBefore` is the highest `used` among this host's anchors and Transport rows for the key whose
  `resetAt` is within 5 s of `a_i.resetAt`.
- `attributedNominal` is Σ `nominalCost` of this host's Transport rows in the window with the same key.
- `ghSpawns` counts `GhSpawn` rows with the same identity and inferred resource in the window.

**Hourly fleet usage (`hourOf`).** A window belongs to the hour that contains its end `to`. For hour H and key K:

- `fleetUsed` telescopes per epoch instead of summing floored per-window deltas, which would bias it upward. For each
  epoch that has a window ending in H, take `last − first`, where `first` is the anchor that starts the earliest such
  window in that epoch and `last` the anchor that ends the latest one. Floor that once at 0. Add `resetLowerBound` for
  each reset-crossing window ending in H. Sum over epochs.
- `fleetUsedIsLowerBound` is true when any reset-crossing window ends in H.
- `fleetUsed` is none when H has no window for K.
- `estimatedPoints` is the per-command estimate below, summed.
- `ghEstimated = min(ghSpawns, max(0, fleetUsed − estimatedPoints))`.
- `unattributed = max(0, fleetUsed − estimatedPoints − ghEstimated)`. It covers T3 Code, raw agent `gh`, other hosts,
  uncovered spawn paths and the leaks in section 4.4.
- `overAttributed = estimatedPoints > fleetUsed`.
- `attributedNominal` and `ghSpawns` are summed over the windows ending in H.

**Per-operation GraphQL cost (`operationCostsOf`).** Nominal 1 per GraphQL request is only a floor. Over the report
range, for each pair of consecutive Transport rows with the same `pid`, the same key (`graphql`) and the same epoch,
`Δ = used₂ − used₁`. When `Δ > 0`, `Δ` is a candidate cost for row 2's `operation`. Fleet traffic between the two
rows can only add to `Δ`, so each operation's cost is the **minimum** positive candidate. It is reported only with at
least 3 candidates; otherwise the operation's cost is its nominal floor of 1. REST operations cost 1 (0 for the
nominal-zero cases in section 2.5).

**Per-command points.** For hour H, `byCommand[c].estimatedPoints` = Σ over c's Transport rows in H of the row's
operation cost (`nominalCost` when 0, else the estimate). `requests` counts rows, `nominal` sums `nominalCost`, and
`ghSpawns` counts c's spawns. That gives the SPEC "points per hour per resource, per command".

`beep github ledger report [--since 24h] [--json]` reads rollups (computing missing or incomplete ones from rows),
and prints per hour and per key: `fleetUsed`, `estimatedPoints`, `ghEstimated`, `unattributed`, `byCommand` and the
operation-cost table. That is the "Baseline recorded" criterion's shape, and the history note is generated from it.

### 6.5 GraphQL calibration: which source is GraphQL truth

The repo already distrusts REST's GraphQL numbers: "REST misreports the remaining GraphQL points"
(`CLI/internal/github/GraphqlBudget.ts:14-17`; also `CLI/commands/Yeet/internal/GhOps.ts:1710`). GraphQL response
headers, by contrast, report the fleet-wide `graphql` bucket on every GraphQL call. So:

- **GraphQL anchors are transport-basis by default.** For the `graphql` key, `windowsOf` uses this host's GraphQL
  Transport rows (with headers) as anchors. Sample-basis `graphql` buckets are used only when calibration admits
  them.
- **Calibration** is `beep github ledger calibrate [--pairs 6]`, manual. For each pair, on the gh-cli identity's
  client: `readGithubRateLimit`, then immediately the GraphQL query `query GithubLedgerCalibrate { rateLimit { limit
  used remaining resetAt cost } }`, then `recordCalibration` with both readings and `spanMillis`. Pairs are 10 s
  apart. Each pair costs one GraphQL point (the `cost` field records it), so 6 pairs cost 6 points.
- **Admission rule** (pure, `calibrationOf(rows)`): sample-basis `graphql` readings are admitted when there are at
  least 6 `Calibration` rows for the identity in the last 7 days and the median `|restUsed − graphqlUsed|` is at most
  50 points (1% of a 5,000 limit). Otherwise they are excluded.
- **Fallback when not admitted:** an hour whose `graphql` key has fewer than two transport anchors gets `fleetUsed`
  none. The report says so per hour, and the reserve for a `graphql` key with only sample readings is
  `Unknown{uncalibrated}` (section 2.7).
- **P1 exit runs calibration once on the hub** before the 24 h baseline window starts, and the baseline note reports
  the drift statistics alongside the 430 vs 720–1,440 GraphQL/h answer.

### 6.6 The T3 share bound

The hub's unattributed remainder mixes T3, raw agent `gh`, other hosts, uncovered spawn paths and the leaks in
section 4.4. The T3 share is bounded by a one-off aggregation, with no shared state:

1. During the same 24 h baseline window, each fleet host with repo tooling runs `bun run beep github ledger report
   --since 24h --json` once at the end (through the remote-development route), and the files are copied to the hub's
   scratch area. They contain labels, counts and command names only.
2. The baseline note computes, per hour, for the user identity's `graphql` key: `T3 + uncovered ≤ fleetUsed(hub) −
   Σ_hosts (estimatedPoints + ghEstimated)`, floored at 0. `fleetUsed(hub)` follows section 6.5.
3. The T3 share bound is that residual over `fleetUsed(hub)`, reported as the hourly median and the 90th percentile.
4. The note lists the known in-repo leaks beside it, so they are not read as T3.

The T3-share decision file records the threshold, this measured bound and the method.
