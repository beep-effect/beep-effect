Freshness: 2026-07-08.

## Scope

This note answers P0 Research Task 4 for the legal-document-intake packet by reading the packet context, the in-repo TrustGraph port notes, the local TrustGraph TypeScript checkout, the local Cognee checkout, and the in-repo loop precedents named by the plan. The normative packet rule is D7: KG submissions are epistemic claims, the Librarian proposes candidates, a critic plus symbolic ClaimGate validates them, and only admitted claims materialize KG nodes and edges; the loop turn count is typed configuration, not a constant. ## In-Repo Loop Precedents

`IrToLaw` is the closest legal-domain extraction adapter: it requires grounded extraction labels for office action, claim, rejection reference, and distinction, rejects missing/empty/unaligned required extractions as typed errors, and converts aligned spans into law entities with anchors. Evidence: `packages/law-practice/use-cases/src/IrToLaw/IrToLaw.service.ts:requiredExtraction`, `packages/law-practice/use-cases/src/IrToLaw/IrToLaw.service.ts:anchorOf`, `packages/law-practice/use-cases/src/IrToLaw/IrToLaw.service.ts:buildLawEntities`, `packages/law-practice/use-cases/src/IrToLaw/IrToLaw.ports.ts:IrToLawShape`.

`OfficeActionReview` composes a document-processing and extraction pipeline into candidate epistemic claims: file processing produces source text, LangExtract returns grounded targets, `IrToLaw` maps them to law entities, distinctions become `CandidateClaim` values, distinction anchors become `Evidence`, `ClaimGate.evaluate` runs the symbolic gate, `ClaimTransition.advance` applies the lifecycle step, and the final projection summarizes claim states. `ClaimGate` is already a total symbolic gate over candidate claims and evidence: it builds an RDF dataset, adds evidence quote triples only for internally consistent evidence spans, validates a SHACL shape requiring at least one evidence quote string, returns `admitted` when SHACL conforms and is not truncated, and returns `rejected` with violations as a value rather than an error otherwise. Evidence: `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:toDataset`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:buildRequest`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:toVerdict`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.ports.ts:ClaimGateShape`, `packages/epistemic/domain/src/values/ClaimGate/ClaimGateResult.model.ts:ClaimGateResult`.

The current epistemic lifecycle distinguishes candidate, shape-valid, consistency-checked, and admitted states, but the current transition implementation advances an admitted gate result from `candidate` only to `shape_valid`; a later step is therefore needed before graph materialization can depend on lifecycle `admitted`. Evidence: `packages/shared/domain/src/values/ClaimLifecycle/ClaimLifecycle.model.ts:ClaimLifecycle`, `packages/epistemic/use-cases/src/ClaimLifecycle/ClaimLifecycle.service.ts:makeClaimTransition`, `packages/epistemic/use-cases/src/ClaimProjection/ClaimProjection.ts:toClaimProjectionView`.

`BlockRepair` is the clearest bounded-turn loop precedent: invalid blocks are reported with indices, a repair call receives a one-based attempt number and the pending reports, the provider is forced to call a `repair` tool, returned repairs are matched back to indices, unexpected or invalid repairs are ignored, and the recursion stops after `REPAIR_ATTEMPTS = 2` or no pending reports remain. Evidence: `packages/agents/server/src/AssistantTurn/BlockRepair.ts:REPAIR_ATTEMPTS`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:IssueReport`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:BlockRepairCall`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:defaultRepairCall`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:repairItemToIndexed`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:runRepairAttempts`, `packages/agents/server/test/BlockRepair.test.ts`.

The legal-intake loop should generalize `BlockRepair`'s indexed pending-item loop, attempt count, and redacted structured logging, but it should not copy the final behavior that drops unrepaired items from the result set without making a legal-domain rejection artifact, because D7 requires rejected KG submissions to remain part of the epistemic audit trail. Evidence: `packages/agents/server/src/AssistantTurn/BlockRepair.ts:makeRepairInvalidBlocks`, `goals/legal-document-intake/SPEC.md:D7`, `goals/legal-document-intake/PLAN.md:P4 - End-to-End Claim Flow`.

## Synthesized Recommendation

### Roles and Turn Structure

Use three explicit roles: Librarian, Critic, and ClaimGate. The Librarian should be the only LLM role that proposes candidate KG submissions; the Critic should be the only LLM role that reviews a Librarian proposal; ClaimGate should stay symbolic and return admitted/rejected values, matching the existing `ClaimGateShape.evaluate` contract. Evidence: `goals/legal-document-intake/SPEC.md:D7`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.ports.ts:ClaimGateShape`.

The Librarian prompt should receive a bounded source packet that includes DMS artifact identity, source text chunks or grounded extractions, span coordinates, the current taxonomy/ontology slice, and any prior critic feedback for the same candidate id. This shape combines TrustGraph port's grounded packet/corpus identity, TrustGraph TypeScript's strict JSON proposal prompts, Cognee's chunk provenance, and `IrToLaw`'s grounded span adapter. Evidence: `goals/trustgraph-port/SPEC.md:Retrieval packet extensions`, `/home/elpresidank/YeeBois/dev/trustgraph/ts/scripts/seed-demo.ts:pushConfig(["prompt"])`, `/home/elpresidank/YeeBois/dev/cognee/cognee/modules/chunking/models/DocumentChunk.py:DocumentChunk`, `packages/law-practice/use-cases/src/IrToLaw/IrToLaw.service.ts:anchorOf`.

The Librarian output should be a list of candidate submissions keyed by stable candidate id, with proposed claim kind, subject node, predicate or relation type, object node or value, taxonomy concept ids, epistemic status, DMS artifact id, span start/end/quote, confidence, and a short rationale. This extends the existing `CandidateClaim` plus `Evidence` pair with graph-specific proposal fields in the claim snapshot instead of bypassing the epistemic lifecycle. Evidence: `packages/epistemic/domain/src/entities/CandidateClaim/CandidateClaim.model.ts:CandidateClaim`, `packages/epistemic/domain/src/entities/Evidence/Evidence.model.ts:Evidence`, `packages/epistemic/domain/src/values/EvidenceSpan/EvidenceSpan.model.ts:EvidenceSpan`, `goals/legal-document-intake/SPEC.md:D7`.

The Critic prompt should receive the exact Librarian submissions, the same source spans, the taxonomy/ontology slice, and the admission criteria; it should return one verdict per candidate id so the next Librarian turn can revise only pending or rejected candidates. This follows `BlockRepair`'s indexed pending-report structure while keeping legal candidate ids and rejection reasons audit-visible. Evidence: `packages/agents/server/src/AssistantTurn/BlockRepair.ts:IssueReport`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:RepairEnvelope`, `goals/legal-document-intake/SPEC.md:D7`.

The loop should use a typed max-turn configuration rather than a constant embedded in the implementation; `BlockRepair` proves the bounded recursive loop shape, but D7 explicitly requires a typed configuration for this packet's turn count. Evidence: `packages/agents/server/src/AssistantTurn/BlockRepair.ts:runRepairAttempts`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:REPAIR_ATTEMPTS`, `goals/legal-document-intake/SPEC.md:D7`.

### Critic Checks

The Critic should check epistemic status by confirming that each proposed submission is a claim candidate and not an admitted KG fact before ClaimGate runs, because D7 states KG submissions begin as epistemic claims and only admitted claims materialize graph nodes and edges. Evidence: `goals/legal-document-intake/SPEC.md:D7`, `packages/shared/domain/src/values/ClaimLifecycle/ClaimLifecycle.model.ts:ClaimLifecycle`.

The Critic should check span grounding by verifying that the quoted text, start/end coordinates, and confidence-bearing span are present and internally coherent enough for Evidence creation; `ClaimGate` already discards evidence quotes when `isEvidenceSpanInternallyConsistent` fails. Evidence: `packages/epistemic/domain/src/values/EvidenceSpan/EvidenceSpan.model.ts:EvidenceSpan`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:toDataset`, `packages/law-practice/use-cases/src/OfficeActionReview/OfficeActionReview.service.ts:evidenceOf`.

The Critic should check taxonomy and ontology consistency before symbolic gating: extracted node types and relation types should resolve to the current legal-document taxonomy/ontology slice, following Cognee's ontology resolver pattern and the packet's D5 taxonomy requirement. Evidence: `goals/legal-document-intake/SPEC.md:D5`, `/home/elpresidank/YeeBois/dev/cognee/cognee/modules/graph/utils/expand_with_nodes_and_edges.py:_create_entity_node`, `/home/elpresidank/YeeBois/dev/cognee/cognee/modules/ontology/rdf_xml/RDFLibOntologyResolver.py:RDFLibOntologyResolver`.

The Critic should check graph consistency by rejecting candidate edges whose subject or object endpoints are missing from the candidate graph or the accepted existing graph slice; Cognee filters graph edges when endpoints are absent before integration. Evidence: `/home/elpresidank/YeeBois/dev/cognee/cognee/tasks/graph/extract_graph_from_data.py:extract_graph_from_data`.

The Critic should check provenance sufficiency by requiring DMS artifact identity, chunk/span identity, quote, pipeline/run id, and candidate id before any symbolic gate is called. This combines D7's claim audit requirement, TrustGraph port's grounded packet provenance, Cognee's pipeline provenance stamping, and the existing Evidence model. Evidence: `goals/legal-document-intake/SPEC.md:D7`, `goals/trustgraph-port/SPEC.md:Retrieval packet extensions`, `/home/elpresidank/YeeBois/dev/cognee/cognee/modules/pipelines/operations/run_tasks_base.py:_stamp_provenance`, `packages/epistemic/domain/src/entities/Evidence/Evidence.model.ts:Evidence`.

### Gate Admissions and Rejections

The symbolic gate should admit only candidate submissions that have a Critic-approved verdict, internally consistent evidence span, at least one evidence quote string, a taxonomy-resolved node/relation type, a DMS artifact link, and a source span. The existing `ClaimGate` already proves the evidence-quote SHACL gate and value-level admitted/rejected result; this packet needs to extend that gate with D5 taxonomy checks and DMS/span provenance checks. Evidence: `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:buildRequest`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:toVerdict`, `goals/legal-document-intake/SPEC.md:D5`, `goals/legal-document-intake/SPEC.md:D7`.

The gate should reject, not throw, for ordinary domain failures such as missing span, unresolved taxonomy type, unsupported relation, endpoint mismatch, missing DMS link, critic rejection, or failed SHACL shape; this matches `ClaimGateResult` as a value union and leaves typed errors for infrastructure failures. Evidence: `packages/epistemic/domain/src/values/ClaimGate/ClaimGateResult.model.ts:ClaimGateResult`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:makeClaimGate`, `packages/law-practice/use-cases/src/OfficeActionReview/OfficeActionReview.ports.ts:OfficeActionReviewShape`.

Materialization should run after admission, not during Librarian or Critic turns, because D7 says only admitted claims materialize KG nodes and edges and P4 says admitted claims should materialize as KG rows with DMS links and span provenance. Evidence: `goals/legal-document-intake/SPEC.md:D7`, `goals/legal-document-intake/PLAN.md:P4 - End-to-End Claim Flow`.

### Audit Trail Shape

Persist an audit record per candidate id with source artifact id, DMS link, chunk/span id, span start/end/quote, Librarian proposal payload, Critic verdict and reasons, ClaimGate verdict and violations, lifecycle transition, taxonomy/ontology resolution, loop turn count/config, pipeline/task/run id, and materialized KG row ids when admitted. Each field has a direct precedent: Evidence span fields in `EvidenceSpan`, gate violations in `ClaimGateResult`, lifecycle in `ClaimLifecycle`, turn attempt in `BlockRepair`, and pipeline provenance in Cognee `DataPoint`. Evidence: `packages/epistemic/domain/src/values/EvidenceSpan/EvidenceSpan.model.ts:EvidenceSpan`, `packages/epistemic/domain/src/values/ClaimGate/ClaimGateResult.model.ts:ClaimGateResult`, `packages/shared/domain/src/values/ClaimLifecycle/ClaimLifecycle.model.ts:ClaimLifecycle`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:defaultRepairCall`, `/home/elpresidank/YeeBois/dev/cognee/cognee/infrastructure/engine/models/DataPoint.py:DataPoint`.

Rejected candidates should remain queryable as audit artifacts and should not materialize KG nodes or edges. This follows D7's admission rule and avoids copying `BlockRepair`'s final repaired-block-only return behavior into a legal audit workflow. Evidence: `goals/legal-document-intake/SPEC.md:D7`, `packages/agents/server/src/AssistantTurn/BlockRepair.ts:makeRepairInvalidBlocks`.

## Mapping to the Existing Epistemic Claim Lifecycle

The Librarian's raw proposal maps to `CandidateClaim` with lifecycle `candidate`, while the concrete source quote maps to `Evidence` with an `EvidenceSpan`. Evidence: `packages/epistemic/domain/src/entities/CandidateClaim/CandidateClaim.model.ts:CandidateClaim`, `packages/epistemic/domain/src/entities/Evidence/Evidence.model.ts:Evidence`, `packages/epistemic/domain/src/values/EvidenceSpan/EvidenceSpan.model.ts:EvidenceSpan`.

The Critic's approved verdict maps to the lifecycle's semantic gap between `candidate` and a later consistency-checked or admitted state, but the current implementation only advances a candidate to `shape_valid` after an admitted gate result. Evidence: `packages/shared/domain/src/values/ClaimLifecycle/ClaimLifecycle.model.ts:ClaimLifecycle`, `packages/epistemic/use-cases/src/ClaimLifecycle/ClaimLifecycle.service.ts:makeClaimTransition`.

The current ClaimGate maps to the first symbolic shape gate: it checks internally consistent evidence quotes and a SHACL shape, returns admitted/rejected as data, and lets `ClaimTransition` apply the current step. Evidence: `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:toDataset`, `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:toVerdict`, `packages/epistemic/use-cases/src/ClaimLifecycle/ClaimLifecycle.service.ts:makeClaimTransition`.

The packet's final KG materializer should run only after the claim reaches an admission state that `ClaimProjection` would count as admitted, because the current projection derives `admittedKeys` from lifecycle value `admitted`. Evidence: `packages/epistemic/use-cases/src/ClaimProjection/ClaimProjection.ts:toClaimProjectionView`, `packages/shared/domain/src/values/ClaimLifecycle/ClaimLifecycle.model.ts:ClaimLifecycle`, `goals/legal-document-intake/PLAN.md:P4 - End-to-End Claim Flow`.

The existing OfficeActionReview pipeline already proves the basic mapping from grounded legal extraction to candidate claim plus evidence plus gate plus lifecycle plus projection; the legal-document-intake librarian/critic loop should preserve that lifecycle boundary and add a richer proposal/critic/audit envelope before the symbolic gate. Evidence: `packages/law-practice/use-cases/src/OfficeActionReview/OfficeActionReview.service.ts:makeOfficeActionReview`, `packages/law-practice/use-cases/src/OfficeActionReview/OfficeActionReview.service.ts:candidateClaimOf`, `packages/law-practice/use-cases/src/OfficeActionReview/OfficeActionReview.service.ts:evidenceOf`.

## Proposed SPEC Supersession
