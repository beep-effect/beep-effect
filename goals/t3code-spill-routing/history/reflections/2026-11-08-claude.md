# Reflection — t3code-spill-routing (2026-11-08, claude)

## Summary

The advisory rule is in `orchestrate` and the runbook, with thresholds from a 7-day baseline and the
MemAvailable-0 samples explained as real. The largest finding was unplanned: the recorder had been
dead for days. The drill used a simulated breach.

## Tooling experience

- **Worked:** the parcel carried every field the rule needed, so no new telemetry code was required.
- **Didn't:** the recorder path in the exploration had gone stale without any signal.
- **Frustrating:** the journal no longer covers the boots with the zero samples, so their cause stays inferred.
- **Wished existed:** PSI history in a queryable store rather than a flat file.

## Implementation improvement opportunities

- Remote-host pressure feeds stay out of scope, so the rule still picks a spill target without knowing its load.

## Goal & prompt critique

The spec assumed a live recorder and a read-only analysis. A first step of "confirm the source is still being written" would have surfaced the failure at once.

## TODOs worth codifying

- See frontmatter.

## Lessons

- **HIGH:** Check a data source's newest record before analyzing it; a timer reading `active` does not mean the data is flowing.
- **MEDIUM:** Treat a clamped kernel value as real until shown otherwise. `MemAvailable: 0` looked like an artifact and was not.
- **LOW:** A threshold on a one-sample event is unusable however real the event is; prefer percentiles.
