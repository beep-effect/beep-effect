# Reflection - repo-cli-modularization (2026-07-08, codex)

## Summary

The repo-cli modularization packet completed its implementation waves, then had
to be reconciled against a mainline standards rewrite that closed the original
PR #339. The final closeout kept `origin/main` authoritative, repaired the
remaining quality-gate blockers, refreshed the affected inventories, and
proved the branch with a full `bun run beep yeet verify`.

## Tooling experience

- **Worked:** `bun run beep yeet verify` was the right final arbiter because it
  covered the local lanes that had regressed after the main merge: build,
  global check, knip, jsdoc, lint, full docgen, tests, type-tests, integration,
  fallow, repo sanity, secrets, security, SAST, and Nix.
- **Didn't:** The closed/stale PR state for #339 was not a reliable proxy for
  whether the branch still had useful work. The live checkout and Yeet verdict
  were stronger evidence.
- **Frustrating:** The packet status said "shelved" while the user's active
  objective was to carry it through to completion, so the final pass had to
  repair both code quality drift and packet truth.
- **Wished existed:** A Yeet closeout helper that can reopen or supersede a
  closed branch PR after a final reconciliation, then carry the same branch
  through hosted checks without manual PR-state interpretation.

## Implementation improvement opportunities

- Make schema-first, dual-arity, and native-runtime inventory exceptions more
  symbol-aware so broad line shifts from unrelated main merges do not make
  stale entries look like new issues.
- Add detector regression fixtures for TSX boundary functions and callable
  third-argument `dual` cases whenever those policy detectors change.
- Keep dead helper deletion in the same wave as detector cleanup; otherwise
  Knip can become the last blocker after the behavior fixes are already done.

## Goal & prompt critique

- The packet should have reserved an explicit "final main reconciliation" wave.
  The original one-PR delivery model was coherent for review cost, but it made
  the branch vulnerable to a repo-wide standards rewrite landing first.
- The completion gate should distinguish "mergeable PR" from "merged into
  main" so the packet can state exactly which external GitHub state still
  remains after local proof passes.

## TODOs worth codifying

- Add a future-packet checklist item: after any closed/superseded PR is revived,
  inspect the current PR state, merge base, and mainline overlap before choosing
  between reopen, new PR, or direct branch replacement.
- Codify symbol-keyed exception entries for inventory ratchets.

## Lessons (confidence-tiered)

- **HIGH - Critical:** Reconcile against current `origin/main` before trusting
  old PR conclusions. PR #339 was closed for valid reasons, but current source
  still had repairable quality-gate drift that only live verification exposed.
- **HIGH - Critical:** Generated inventory deletions are acceptable only when
  the owning detector and ratchet gates prove them. Here, full Yeet verify was
  the evidence that the large generated shrinkage was intended.
- **MEDIUM - Best practice:** When a packet status and current user objective
  disagree, update the packet truth as part of the branch rather than leaving
  stale "shelved" language to ship into main.
- **LOW - Consideration:** For wide repo-cli campaigns, a smaller PR sequence
  may be cheaper than one terminal umbrella PR if adjacent standards work is
  already landing on main.
