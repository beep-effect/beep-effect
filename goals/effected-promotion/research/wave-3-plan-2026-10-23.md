### Blockers

1. **`@beep/yaml` silently mis-parses valid YAML.** This blocks `@beep/config-file` (3-3) only. I reproduced the planner's
   repro against `packages/foundation/modeling/yaml/src`:

   | Input | npm `yaml` | `@beep/yaml` |
   | --- | --- | --- |
   | `a: x\n  "y"\n` | `{a: 'x "y"'}` | `{a: "x", y: null}` |
   | `a: x\n  'y'\n` | `{a: "x 'y'"}` | `{a: "x", y: null}` |
   | `a: x,\n  "y"];\nb: 1\n` | `{a: 'x, "y"];', b: 1}` | four keys |

   A plain multi-line scalar whose continuation line starts with a quote character gets split into new keys, with no
   diagnostic. YAML 1.2 `s-ns-plain-next-line` admits any `ns-plain-char` there, so npm `yaml` is right.

   `YamlCodec` would ship this bug to every config reader. So a separate `fix(yaml)` PR (3-Y) merges before 3-3 is cut.
   `@beep/lockfiles` also parses pnpm and yarn YAML through `@beep/yaml`, so 3-Y re-runs the lockfiles suite (lab, or
   in-package if 3-5 merged first).
2. **Adoption PRs and 2d-A contend for the same files.** No package in wave 3 imports another wave-3 package (verified
   from the real imports: `LockfileIntegrity` carries its own `WorkspaceManifest`, and config-file, repo-tsconfig and
   github-reporting import only merged packages). So the five promotions are order-free. The adoption PRs are not. Four
   files are claimed by more than one PR:

   | File | Claimed by | Binding owner and order |
   | --- | --- | --- |
   | `packages/tooling/tool/cli/src/commands/VersionSync/internal/resolvers/RootCatalog.ts` | lockfiles adoption (bun.lock half) and package-json readers (package.json half) | 3-A1 takes the bun.lock half first. 3-A4 takes the package.json half after merging main. |

   Without this order, two lanes rewrite the same reader in incompatible ways.
