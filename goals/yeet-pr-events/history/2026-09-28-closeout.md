## W9 — pr-wave notifier + liveness rule

- `internal/WaveNotifier.ts`: `YeetPrWaveDescriptor` (`yeet-pr-wave-descriptor/v1`:
  waveKey, prNumber, headSha, checkout, rowIds, urgency, ownerReason, summary,
  resumeCommand, desktopTitle, desktopBody, createdAt), `YeetPrWaveOwnerVerdict`
  with a `YeetPrWaveOwnerReason` literal set; `waveKey` = 16 hex of SHA-256 over
  PR number, head, sorted row ids and red-set key.
- `MonitorLoop.ts`: after each `--until-ready` poll's inbox convergence in a
  detached job, reads the PR session registry, runs `isClaudeSessionLive` on
  every Claude record; no record, Codex/unknown harness, stale session,
  unreadable registry or a PR URL without a repository all count as dead
  (D19). Once per wave: the descriptor file is created with an exclusive
  `wx` (the claim, durable across monitor restarts) under
  `.beep/yeet/pr-wave-notifier/waves/<waveKey>.json` (0600), then
  `.claude/hooks/yeet-pr-wave-notifier.sh <descriptorPath>` is spawned via
  `setsid -f`; only the path is on the command line. Attached monitors never
  escalate (their caller holds the exit-2 wave).
- Worker: notify-send (persistent, critical for P0 / normal for P1, body
  carries `yeet resume <pr>` and the one-line attributed summary; closed over
  gdbus when the wave resolves), ntfy through `circuit-breaker.sh` with a
  generic hard-coded body and the bearer token on an inherited fd; polls the
  acks every 30 s, one reminder at 30 m, gives up at 4 h; resolves on the rows'
  acks or on the wave record moving to another head/PR. Ledger namespace:
  `${BEEP_AGENT_EVIDENCE_ROOT}/pr-wave/notification-events/pr-wave-<day>-<waveKey>.ndjson`
  (`yeet-pr-wave-notification/v1`; rows carry wave key, urgency, ownerReason,
  `livenessProbe: "claude-only"`, stage, transport, status, wait time; missing
  ntfy settings recorded as `transport-unconfigured`). Env knobs:
  `BEEP_PR_WAVE_NOTIFIER_{POLL,MAX,REMINDER}_SECONDS`,
  `BEEP_PR_WAVE_NOTIFIER_DESKTOP_ENABLED`.
- `sequence-break-notifier.sh` byte-identical to `origin/main` (asserted by
  test and by `cmp`). `DBUS_SESSION_BUS_ADDRESS` was already forwarded (ttc
  ruling 39); a test now asserts it.
- Tests: `test/yeet-pr-wave-notifier.test.ts` (13): liveness rule, once-per-wave

## W10 — Status chain collapse

The W1 timeline blamed the `--until-ready` Status chain (~44 s of the +74 s
red → row gap), not the `--watch` snapshot. Per-poll subprocess inventory of
`collectYeetStatus`: 7 git + 5 gh (`pr view`, `pr checks`, `pr checks
--required`, `api graphql` threads, `run list`), none growing with the number
of red checks. Collapse chosen: (a) concurrency with outcomes surfaced in the
old order — after `gh pr view` decodes, the four remaining gh reads start
together (`Effect.all` with `mode: "result"`, then `Effect.fromResult` in the
old sequence so the first error reported is unchanged); the three worktree git
reads likewise. Rejected: one GraphQL request (would re-create gh's
`bucket`/`state` mapping), dropping `--required` (gh's checks JSON has no
required field; depends on the GraphQL rewrite), changed-runs-only (already
done by the `triagedReds` skip).

| --- | --- | --- |
| Subprocesses | 12 | 12 |
| gh round-trips deep | 5 | 2 |
| gh peak in flight | 1 | 4 |
| Fake gh at 150 ms/call, wall time | 768 ms | 305 ms |

Rows and snapshot unchanged: `test/yeet-status-chain.test.ts` holds a golden
snapshot recorded against the pre-change `Status.ts`, asserts the exact
subprocess list and the depth from recorded event order (`pr view` alone, then
the other four all start before any ends), and that a failing thread read does
not pre-empt an earlier checks error. The legacy `status.json` fixture still
decodes. Live confirmation of the ~3-round-trip saving is owed to the next
`--until-ready` run on this PR.
