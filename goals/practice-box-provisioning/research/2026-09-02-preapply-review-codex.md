# NOT SAFE

Static pre-apply verdict: do not run the first live apply until P0-1 and the P1 safety findings are fixed and regression-covered. No network, provider mutation, build, check, test, lint, or tracked-file write was performed in this review.

## Findings ranked P0/P1/P2

The static review found one P0, seven P1, and three P2 findings.

### P0-1: Exact-name folders are silently adopted without the required explicit allowlist

- **Evidence:** The normative rule says v1 may adopt only an explicit allowlist of existing resources (`goals/practice-box-provisioning/SPEC.md:23-24`). The desired-state schema has no adoption or ownership field at all (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:399-410`). The planner treats one observed exact-name sibling as `Noop`, records its provider id as the resolution for the desired logical key, and removes it from the foreign-resource set (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:190-251,453-490,563-571`). Dependent collaboration and webhook actions then use that resolved provider id (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:493-527`; `packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:332-371`).
- **Impact:** A pre-existing foreign folder with the desired spelling is not merely reported: it is silently adopted and can receive new collaboration or webhook mutations. That violates the public safety contract and can attach access or automation to an operator-unreviewed resource.
- **Concrete proposed fix:** Add a schema-validated adoption allowlist whose entry binds resource kind and logical key to an expected provider id plus parent/identity digest. In folder planning, emit `BlockedByPolicy` (foreign-name collision) for every pre-existing match unless exactly one candidate satisfies that explicit binding. Keep unallowlisted matches foreign and never resolve them as dependencies. For the first apply, an empty allowlist should make every collision block.
- **Regression test:** **No.** The existing foreign-folder fixture deliberately uses a different name (`packages/drivers/box-provisioning/test/fixtures.ts:78-90`), and its planner test only proves that distinct unmatched resource is foreign (`packages/drivers/box-provisioning/test/BoxProvisioningPlanner.test.ts:40-65`). Add exact-name, allowlisted-exact-id, wrong-id, and ambiguous-candidate cases, including proof that no dependent mutation can target an unallowlisted match.

### P1-1: Folder absence and matching do not implement Box's documented name rules

- **Evidence:** Desired-state duplicate natural keys use raw `left.name === right.name` (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:368-373`). Planning matches `candidate.name` and `folder.name` with exact structural equality (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:453-460`). The last pre-create absence check does the same (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:219-237`) before issuing `folders.createFolder` (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:310-329`). The installed generated Box SDK states both that sibling-name uniqueness is case-insensitive and that trailing spaces, slash/backslash, non-printable ASCII, `.` and `..` are invalid (`node_modules/box-node-sdk/lib/managers/folders.d.ts:580-590`), while the intent accepts only `S.NonEmptyString` for a folder name (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:138-147`).
- **Impact:** A case-only live collision is planned as `Create`; its last precondition passes; Box then rejects the create after earlier actions may have succeeded. An intrinsically invalid desired name also survives validation and fails only during live mutation. Neither case is a typed plan blocker, and a subsequent dry-run repeats `Create` indefinitely.
- **Concrete proposed fix:** Define and document one provider-equivalent folder-name canonicalization backed by Box API research. Use it consistently in desired-state duplicate validation, planner candidate selection, and the just-in-time absence check. A canonical collision should be `BlockedByAmbiguity`/`BlockedByPolicy` unless an explicit adoption entry authorizes exactly one provider id; never discover it via create failure.
- **Regression test:** **No.** Add same-parent case-only and documented whitespace-normalization cases at schema, planner, and applier-precondition levels; assert zero create calls.

### P1-2: Apply treats every blocker as acceptable, not just the two reviewed entitlement blockers

- **Evidence:** The runner gates only the operator opt-in, plan digest, and destructive count before invoking apply (`.beep/box-provisioning/runner.ts:160-180`). The applier converts every `Blocked` action, including `BlockedByAmbiguity` and `BlockedByPolicy`, to a successful receipt outcome and continues (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:445-451,470-497`). The post-apply check then removes **all** blocked actions before asserting `Noop` (`.beep/box-provisioning/runner.ts:183-193`). Yet the planner uses policy blockers not only for the two unavailable capabilities, but also for broken dependencies, discovery-permission failures, live/declared-entitlement conflicts, and in-scope capabilities whose mutation is unsupported (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:345-385,463-479`).
- **Impact:** An attended run can mutate the subset that is currently reachable and print `postApplyActionableResourcesAllNoop: true` while a folder/collaboration dependency, ambiguous match, permission failure, or entitlement contradiction remains unresolved. That success condition is materially weaker than the reviewed starter intent, whose only accepted blockers are one metadata and one retention `BlockedByEntitlement`.
- **Concrete proposed fix:** Before any mutation, validate the exact blocker contract for the reviewed intent: exactly the expected metadata and retention actions, both with `reason._tag === "BlockedByEntitlement"`, correct dependency closure, and no other blocker. In the post-apply plan, require that same blocker multiset plus `Noop` for every other action. Reject any ambiguity or policy blocker at both the runner and public orchestration boundary.
- **Regression test:** **No.** The applier test currently treats two generic blocked outcomes as successful evidence (`packages/drivers/box-provisioning/test/BoxProvisioningApplier.test.ts:53-75`). Add pre-mutation and post-plan cases for ambiguity, dependency, permission, policy, too few entitlement blockers, and extra entitlement blockers; assert zero provider mutations for every rejected plan.

### P1-3: A mid-apply failure leaves successful mutations without a durable partial receipt

- **Evidence:** Actions are dispatched sequentially and the receipt is constructed only after the entire `Effect.forEach` succeeds (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:480-502`). The runner writes the receipt only after `applyReviewedPlan` returns successfully (`.beep/box-provisioning/runner.ts:175-181`). The receipt schema can express only completed `Applied`/`Skipped`/`Blocked` outcomes, not a failed action or partial run (`packages/drivers/box-provisioning/src/BoxProvisioningReceipt.ts:16-20,44-50,73-109,125-166`). The ratified shape calls for sanitized outcomes and failure data (`explorations/practice-office-provisioning/research/r4-provisioning-code-shape.md:259-264`).
- **Impact:** If folder 17 fails, folders 1-16 remain in Box but no durable artifact identifies their provider ids or the failed action. If the collaboration POST has an ambiguous transport outcome, it may have created/sent an invitation even though no receipt exists. A later dry-run can rediscover exact-name resources, but today that recovery is the prohibited silent-adoption path in P0-1; case/normalization mismatches can instead cause a repeated create/conflict loop. This is not rollback-safe or audit-complete for the first law-practice apply.
- **Concrete proposed fix:** Persist a mode-0600 append-only apply journal before dispatch and after every action, containing only action/digest/provider identifiers and a sanitized terminal failure tag. On restart, reconcile journaled action identities through explicit ownership/adoption bindings before proceeding. For ambiguous POST failures, require a read-after-error natural-key lookup and stop for operator review rather than blindly retrying. The final receipt may be derived only after all actions have terminal outcomes.
- **Regression test:** **No.** Existing applier coverage tests only a wholly successful run and failures before the first mutation (`packages/drivers/box-provisioning/test/BoxProvisioningApplier.test.ts:53-137`). Add fail-at-N folder, collaboration rejection after folders, and ambiguous collaboration-response cases; verify partial evidence is durable, safe to render, and the next plan cannot duplicate a successful mutation.

### P1-4: Driver errors retain provider `contextInfo` and schema issue text that can contain confidential values

- **Evidence:** `BoxApiFailureContext` is called sanitized, but accepts any JSON object (`packages/drivers/box/src/Box.errors.ts:98-109`), and `BoxError.fromUnknown` copies the SDK response's `contextInfo` wholesale into the typed error (`packages/drivers/box/src/Box.errors.ts:266-288,323-331`). Box conflict context can contain `FileConflict` entries, and the installed SDK model includes the conflicting resource's `name`, id, etag, and hash (`node_modules/box-node-sdk/lib/schemas/conflictError.d.ts:4-8`; `node_modules/box-node-sdk/lib/schemas/fileConflict.js:30-81`). Schema failures also copy up to 2,000 characters of the issue message into `cause` (`packages/drivers/box/src/Box.errors.ts:333-374`); such messages can quote a decoded folder name, principal, callback, or response value. By contrast, the runner's terminal catch prints only a tag and sanitized bootstrap stage (`.beep/box-provisioning/runner.ts:224-231`), and the driver's internal debug event selects only event, method, provider, reason, SDK version, and status (`packages/drivers/box/src/internal/Box.runtime.ts:131-155`). No `Cause.pretty` use exists in the reviewed reconciler/runner paths.
- **Impact:** This specific runner does not print the sensitive fields, but a surrounding Effect cause renderer, trace exporter, test failure, or future caller can serialize the typed `BoxError` and leak client/matter folder names or principals. JSON-serializable is not the same as redacted. A first-apply 409 is precisely where conflict context is likely.
- **Concrete proposed fix:** Replace arbitrary `contextInfo` retention with a strict allowlist of non-sensitive keys and scalar classifications; never retain provider resource objects. Redact schema failures to schema/path/error-class identifiers that cannot quote actual input. Add an explicit safe diagnostic projection and require all logging/telemetry to use it; mark or remove unsafe error fields so `Cause.pretty` cannot expose them.
- **Regression test:** **Partial, insufficient.** Tests prove raw request bodies and string throws are not copied, but explicitly expect JSON `contextInfo` and detailed schema messages to survive (`packages/drivers/box/test/Box.service.test.ts:318-357,684-727`). Add negative tests with a conflict resource name, login, callback URL, bearer-like token, and schema issue containing each; assert neither encoded error, `String(error)`, nor a rendered Effect cause contains the sentinel.

### P1-5: The plan schema can still carry confidential free-form values

- **Evidence:** The plan model correctly replaces logical keys and desired/live values with SHA-256 digests and constrained technical fields, and foreign resources carry only provider id plus identity digest (`packages/drivers/box-provisioning/src/BoxProvisioningPlan.ts:385-435`). However, it also permits an arbitrary `S.NonEmptyString` `sourceRevision` and arbitrary `planName` inside `BlockedByEntitlement` (`packages/drivers/box-provisioning/src/BoxProvisioningPlan.ts:90-99,416-431`). The planner copies both directly from private desired state (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:345-385,595-610`); the desired-state schemas likewise accept free-form values (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:99-109,399-410`). Therefore a confidential name, login, callback, or token placed in either field is encodable in a nominally redacted plan. Receipt fields themselves are restricted to hashes, provider ids, resource kinds, fixed reasons, time, and plan digest (`packages/drivers/box-provisioning/src/BoxProvisioningReceipt.ts:16-20,100-109,158-166`).
- **Impact:** The current fixture redaction test proves that three intended fields are not copied; it does not prove that the plan codec cannot carry them. An accidental sensitive `sourceRevision` or plan label would be written verbatim into the private plan and printed in the runner summary (`.beep/box-provisioning/runner.ts:69-80,194-204`).
- **Concrete proposed fix:** Make `sourceRevision` an opaque, lexically restricted revision id (for example a bounded hex/VCS revision schema), and make the plan tier a closed literal domain or hash it in public artifacts. Replace other free-form policy strings in artifact schemas with literal/enum codes. Add schema-level forbidden-sentinel tests, not only tests of current planner behavior.
- **Regression test:** **Partial, insufficient.** The planner test checks that one fixture folder name, principal, and callback are absent (`packages/drivers/box-provisioning/test/BoxProvisioningPlanner.test.ts:40-65`), but does not attempt to place sentinels in free-form artifact fields.

### P1-6: `externalCollaboratorCount` is a declaration count, not a provider-verified billing impact or mutation delta

- **Evidence:** Each desired collaboration supplies its own `billingImpact` classification (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:176-185`). The planner counts every desired collaboration marked `external`, regardless of whether its action is `Create`, `Update`, `Noop`, or `Blocked` (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:607-609`). Observed collaborations retain folder, principal/type/id and role, but no owning-enterprise or billable-seat evidence (`packages/drivers/box-provisioning/src/BoxProvisioningObserved.ts:242-254`). The runner presents this field without qualification in the approval summary (`.beep/box-provisioning/runner.ts:69-80`).
- **Impact:** For the starter intent the number is one only because the private author declared it so; the code does not prove that the principal is external, that Business charges for it, or that this apply adds a billable seat. The value stays one on the all-`Noop` re-plan, so it is not the apply's billing delta. An operator can reasonably misread it as authoritative commercial impact.
- **Concrete proposed fix:** Rename the current field to `declaredExternalCollaboratorCount`. Separately report counts by action tag (especially external `Create`) and document the trust boundary. If an authoritative internal/external or paid-seat determination is required, inventory the relevant provider identity/enterprise data and model an `unknown` result rather than accepting a caller assertion as fact.
- **Regression test:** **No semantic billing test.** The planner test merely asserts the fixture's declared value becomes `1` (`packages/drivers/box-provisioning/test/BoxProvisioningPlanner.test.ts:40-52`). Add external `Noop`, `Create`, `Blocked`, incorrectly declared internal/external, and unknown-provider-identity cases.

### P1-7: Dependency state can drift after its action check but before a dependent mutation

- **Evidence:** A `Noop` folder is GET-revalidated once when its own action executes, then its provider id is stored and the action is marked completed (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:273-308,430-497`). A later child folder or collaboration checks only that the parent's action key is in `completed`, resolves the stored id, and validates only the child's absence or collaboration absence (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:219-254,310-350,480-497`). The parent folder's name, parent, and etag are not re-read at the dependent mutation boundary.
- **Impact:** A concurrent rename/move after the parent action check but before the child/collaboration POST can attach the new resource or grant to a folder that no longer matches the reviewed state. The fresh full-plan equality check happened earlier, so it cannot catch this action-to-action time-of-check/time-of-use drift. The same risk applies to a parent freshly created by this apply and then altered before its descendants are created.
- **Concrete proposed fix:** Treat every dependency's relevant live identity digest as a precondition of each dependent write. Immediately before creating a child, collaboration, or webhook, GET/revalidate the target parent/folder against the reviewed dependency digest (and etag where available), then perform the collection-absence check. Abort before POST on any mismatch.
- **Regression test:** **No.** The existing drift test changes a folder etag before that folder's own validation and proves only first-action rejection (`packages/drivers/box-provisioning/test/BoxProvisioningApplier.test.ts:101-137`). Add a controlled mutation between completed parent and dependent action and assert the dependent POST count remains zero.

### P2-1: The public applier has no tenant/subject guard of its own

- **Evidence:** The safe orchestrator re-inventories and runs the planner's expected enterprise/subject checks before calling the applier (`packages/drivers/box-provisioning/src/BoxProvisioning.ts:47-66`; `packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:413-426`). But `BoxProvisioningApplier.apply` itself checks only plan integrity, desired digest, destructiveness, dependencies, action binding, and resource preconditions (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:456-497`). Its layer and service are exported as a public package surface (`packages/drivers/box-provisioning/src/index.ts:8-10`).
- **Impact:** The supplied runner is guarded, but another caller can invoke the exported mutation service against a different Box layer. Create actions have no existing provider id/etag to tie them to the correct tenant, so a valid reviewed plan plus the same desired input could create folders in the wrong tenant's root id.
- **Concrete proposed fix:** Make the raw applier internal, or require a fresh, unforgeable inventory/identity proof and re-check live enterprise and subject inside the mutation boundary. Keep `applyReviewedPlan` as the only public write entry point.
- **Regression test:** **No.** Existing applier tests inject a Box service but never model tenant/subject mismatch (`packages/drivers/box-provisioning/test/BoxProvisioningApplier.test.ts:50-137`).

### P2-2: The ratified plan-expiry precondition is absent

- **Evidence:** The research shape requires a generated timestamp, expiry, and max plan age (`explorations/practice-office-provisioning/research/r4-provisioning-code-shape.md:228-238`). The actual plan contains neither (`packages/drivers/box-provisioning/src/BoxProvisioningPlan.ts:416-431`), and apply has no age check (`packages/drivers/box-provisioning/src/BoxProvisioning.ts:47-66`; `.beep/box-provisioning/runner.ts:160-180`).
- **Impact:** Fresh re-inventory substantially reduces stale-plan risk, but the artifact does not enforce the reviewed operational contract and can be presented/retried indefinitely. It also cannot distinguish a recently reviewed plan from one carried across a long operational window.
- **Concrete proposed fix:** Add `generatedAt` and `expiresAt` (or a bounded `maxAge`) to the sealed plan, make them part of `planDigest`, and reject expired plans before inventory and again immediately before first mutation using an injected/test clock.
- **Regression test:** **No.** Add boundary tests for just-before, exactly-at, and after expiry, proving zero writes on rejection.

### P2-3: Private artifact writes are chmod-after-write, and unknown runner modes exit successfully

- **Evidence:** `writePrivate` recursively creates the parent with requested mode 0700, writes the target, then chmods it to 0600 (`.beep/box-provisioning/runner.ts:44-49`). Thus the file's initial mode depends on process umask, the write is not atomic, and an already-existing parent directory's mode is not tightened. Runner failures set exit code 1 (`.beep/box-provisioning/runner.ts:224-231`), but an unrecognized mode merely prints usage and returns successfully (`.beep/box-provisioning/runner.ts:208-222`).
- **Impact:** On a permissive umask there is a window in which a newly written private artifact is broader than 0600; a crash between write and chmod can leave it that way. A typo in an automation/operator command can be reported as success while doing nothing.
- **Concrete proposed fix:** Open a same-directory temporary file with exclusive create mode 0600, write/fsync/close, atomically rename it, and verify/tighten the parent to 0700. Reject an unknown mode with a typed error or set `process.exitCode = 2` after usage.
- **Regression test:** **No runner test found.** Add process-level tests under controlled umask for initial/final modes, interruption before rename, replacement behavior, invalid mode exit 2, and operational failures exit 1.

## UNVERIFIED Box API assumptions

Network research was prohibited in this lane. The installed generated SDK establishes the request/response shapes and Box's case-insensitive folder-name rule, but the following server behavior still needs a separate primary-documentation or disposable-tenant research lane:

- Whether omitting collaboration `notify` sends an email under the tenant's current settings, and whether explicitly passing `notify: false` suppresses all invite mail while still creating the pending grant.
- Exactly which collaboration representation is returned/listed for a login-based pending external invite: `accessible_by`, `invite_email`, both, login present/absent, and the casing/canonicalization of each.
- Whether Box canonicalizes login case, plus-address aliases, or other login forms when listing a collaboration, and what stable identifier is available before acceptance.
- Whether Box always emits the documented lowercase collaboration roles, and whether it rejects or normalizes wrong-case/unknown role strings accepted by the generated forward-compatible schema.
- Whether Box canonicalizes webhook callbacks (host case, default port, percent encoding, trailing slash, redirects) and whether returned trigger ordering is arbitrary. Trigger ordering is handled locally; callback canonicalization is not.
- The exact HTTP status/code/body returned by every metadata and retention discovery endpoint on a Business tenant. The desired `BlockedByEntitlement` result depends on a 403 whose code is not one of the two locally classified permission codes (`packages/drivers/box-provisioning/src/BoxProvisioningInventory.ts:66-90`).
- Read-after-write visibility/consistency for new folders and especially new/pending collaborations during the immediate post-apply inventory.
- Whether changing folder contents, collaborations, or child membership changes the folder's own etag. The code must not assume this because those child collections are inventoried separately.
- Whether a timed-out collaboration or folder POST can be safely recovered by immediate natural-key listing without duplicating a server-accepted mutation.
- Whether the tenant can contain legacy or otherwise anomalous case-equivalent same-parent folders despite the current documented uniqueness rule; the reconciler must still block deterministically if it encounters them.

A collaboration failure after all folders similarly leaves the tree without a receipt; a clean rejection replans the collaboration as `Create`, while a server-accepted/response-lost invitation depends on pending-collaboration visibility and identity normalization. This is the P1-3 audit gap.

### Q3. Name collisions and foreign resources

The known live staging drop is preserved as foreign only while it has a distinct natural identity: every unmatched observed folder/collaboration/webhook is emitted as a foreign resource with provider id and identity digest, and no delete/prune branch is planned (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:559-594`).

For a same-parent, same-case desired folder name:

- Exactly one candidate is silently treated as the desired resource (`Noop`), its provider id becomes the dependency resolution, and it is removed from the foreign set (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:190-251,480-490,563-571`). This is **adoption**, not a blocker.
- More than one exact candidate becomes `BlockedByAmbiguity` with the candidate count; because no candidate id is marked matched, all candidates remain foreign (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:212-250,563-571`).
- A case-only candidate is not found by planner or just-in-time absence check, so the reconciler attempts `Create` and Box's documented case-insensitive uniqueness rule returns the conflict path described in P1-1 (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:219-237,310-329`; `node_modules/box-node-sdk/lib/managers/folders.d.ts:580-590`).

There is no adoption field or allowlist in desired state (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:399-410`). Consequently adoption is **not** gated as `SPEC.md:23-24` requires. This alone supports the `NOT SAFE` verdict.

### Q4. Collaboration semantics on Business

- `externalCollaboratorCount` is the number of desired collaborations self-labelled `billingImpact: "external"`, with no action-tag or provider-enterprise check (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:176-184`; `packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:607-609`). It is correct as a declaration count for the one template entry, but not an independently verified billable-seat fact or apply delta; see P1-6.
- Create does **not** pass the optional `notify` query (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:341-349`), even though the generated driver exposes it (`packages/drivers/box/src/_generated/Box.models.gen.ts:1200-1204`) and forwards optionals to the SDK (`packages/drivers/box/src/_generated/Box.operations.gen.ts:1007-1019`). The installed SDK omits the query when not supplied (`node_modules/box-node-sdk/lib/managers/userCollaborations.js:278-307`). Whether the server's omission default sends mail is unverified. The POST itself is protected by the explicit attended mutation opt-in (`.beep/box-provisioning/runner.ts:160-163`).
- The template spelling `editor` matches the generated known role spelling (`packages/drivers/box/src/_generated/Box.models.gen.ts:633-635,1381-1384`). However the desired role is any non-empty string, and the generated forward-compatible role union also accepts any string (`packages/drivers/box-provisioning/src/BoxProvisioningIntent.ts:176-184`; `packages/drivers/box/src/_generated/Box.models.gen.ts:633-635`), so wrong case/unknown roles are not rejected before a live request.
- A pending invite with `accessible_by` absent and `invite_email` present is explicitly supported: `collaborationPrincipal` falls back to `inviteEmail`, records a user principal with no provider id, and therefore can match the desired login (`packages/drivers/box-provisioning/src/internal/live.ts:81-110`). The driver schema permits exactly that shape (`packages/drivers/box/src/_generated/Box.models.gen.ts:431-443`). A mixed response with `accessible_by` present but containing only an id, plus `invite_email`, does **not** use the invite fallback: it selects the id and may fail to match the desired login. Provider response behavior for that mixed form is unverified.
- Pending versus accepted status is deliberately/accidentally ignored because normalized observed collaboration has no status field (`packages/drivers/box-provisioning/src/BoxProvisioningObserved.ts:242-254`). That prevents a status transition from causing `Update`, but also makes rejected and pending grants indistinguishable from accepted grants when principal and role match.

### Q5. Drift fail-closed

**Digest contents.** `desiredStateDigest` is SHA-256 over the schema-encoded canonical desired document, whose resource arrays are logical-key sorted and webhook triggers sorted (`packages/drivers/box-provisioning/src/internal/canonical.ts:50-79,93-94`). It therefore commits to version, source revision, expected enterprise/subject, root id, all entitlement assertions, folder names/topology, collaboration principals/types/roles/billing declarations, webhook callbacks/triggers, and metadata/retention intent values—without serializing those private values into the plan.

`liveStateDigest` is SHA-256 over canonical `BoxObservedState` (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:595-602`; `packages/drivers/box-provisioning/src/internal/canonical.ts:81-91`). It includes enterprise/subject/root ids; every inventoried folder's id, parent, exact name, and optional etag; every normalized collaboration's id, folder, principal/type/provider id, and role; every webhook's id, target, exact address, and sorted triggers; and each metadata/retention/sign discovery tag, kind, count/status/code (`packages/drivers/box-provisioning/src/BoxProvisioningObserved.ts:204-214,242-254,282-292,324-340`).

`planDigest` hashes the complete schema-encoded plan after replacing only `planDigest` itself with 64 zeroes (`packages/drivers/box-provisioning/src/internal/canonical.ts:96-112`). Thus it covers plan version/source and identity ids, both state digests, every action tag/key/resource/dependency/destructive flag/before/after digest/precondition/block reason, every foreign resource id/digest, and the summary counts (`packages/drivers/box-provisioning/src/BoxProvisioningPlan.ts:178-187,327-354,385-435`). It is an integrity checksum, not a signature.

**Not covered.** There is no inventory timestamp/expiry; the root folder's own name/etag is not inventoried; non-folder children/files are filtered out; collaboration status, expiry, access-only/path flags and other server fields are omitted; webhook etag and other fields are omitted; metadata templates/instances/cascades, retention policy/assignment identities and Sign objects are represented only by aggregate discovery result/count, not content. State outside the anchored root is outside the folder/collaboration inventory; webhooks and capability counts are tenant-level. Replacing one capability object with another while preserving a count is invisible.

**What drift is caught.** Between operator review and apply, the full re-inventory/replan/equality check catches every represented change: a folder rename/etag change, new collaboration, or new foreign folder under the anchor changes the fresh plan (`packages/drivers/box-provisioning/src/BoxProvisioning.ts:47-66`). Immediately before an existing-resource `Noop` or `Update`, the applier GETs that provider id and compares optional etag plus the full normalized before digest; before a `Create`, it relists the relevant natural-key collection (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:219-308`).

**What can slip.** Any omitted field/content change can pass. After the fresh inventory, unrelated new foreign items pass unless they collide with a pending create. There is also a time-of-check/time-of-use window across actions: once a parent folder's `Noop` precondition is checked and marked completed, dependent child/collaboration actions reuse its id without rechecking its name/parent/etag (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:430-497`). A concurrent rename/move after that completed action but before a dependent write can therefore attach the new child or collaboration to a folder no longer matching the reviewed state. That is not fully fail-closed.

### Q6. Redaction

The normal planner path does not copy folder names, principals, or webhook addresses into action/foreign/receipt fields: actions carry hashes, types, dependencies, booleans, provider ids/etag and typed reason codes (`packages/drivers/box-provisioning/src/BoxProvisioningPlan.ts:178-187,327-354,385-435`), while receipts carry hashes, types, provider ids, fixed outcome reasons, timestamp, and plan digest (`packages/drivers/box-provisioning/src/BoxProvisioningReceipt.ts:16-20,44-50,100-109,158-166`). Desired-state decode errors intentionally drop the schema issue (`packages/drivers/box-provisioning/src/BoxProvisioningArtifacts.ts:15-32`; `packages/drivers/box-provisioning/src/BoxProvisioningErrors.ts:15-47`). The fixture test confirms the ordinary encoder output lacks its sentinel folder names, login, and callback (`packages/drivers/box-provisioning/test/BoxProvisioningPlanner.test.ts:40-65`). No token or signing-key field exists in desired, observed, plan, or receipt models.

That is not a categorical “cannot carry” guarantee. P1-5 documents free-form `sourceRevision`/`planName` fields that can serialize confidential text. P1-4 documents the more serious failure path: driver `BoxError` retains arbitrary JSON `contextInfo` and schema issue messages that can contain names, principals, URLs, or provider values. The runner's catch is currently safe because it prints only `_tag` and a closed bootstrap stage (`.beep/box-provisioning/runner.ts:224-231`), and the reviewed driver log projection is also bounded (`packages/drivers/box/src/internal/Box.runtime.ts:131-155`). A targeted static search found no `Cause.pretty` call in the reconciler, runner, or Box driver paths; nevertheless an Effect failure cause contains the unsafe typed error fields, so an outer `Cause.pretty`/logger can reveal them.

### Q7. Identity guards

For the operator runner's `applyReviewedPlan` path, **yes**: fresh inventory first calls `users.getUserMe` and derives enterprise plus subject (`packages/drivers/box-provisioning/src/BoxProvisioningInventory.ts:189-231`); the planner rejects any expected enterprise or subject mismatch (`packages/drivers/box-provisioning/src/BoxProvisioningPlanner.ts:409-426`); only a fresh plan structurally equal to the reviewed one reaches mutation (`packages/drivers/box-provisioning/src/BoxProvisioning.ts:47-66`). Therefore these two checks precede every mutation in the supported apply path.

At CCG configuration, the schema requires exactly one of enterprise id or user id (`packages/drivers/box/src/Box.config.ts:18-30,57-88`) and the client passes only the present option to the SDK (`packages/drivers/box/src/Box.service.ts:88-100`). Tests cover neither-subject and both-subject rejection (`packages/drivers/box/test/Box.service.test.ts:408-435`). The runner redundantly checks the two environment variables before constructing the schema (`.beep/box-provisioning/runner.ts:51-65`).

The caveat is P2-1: the separately exported raw `BoxProvisioningApplier.apply` has no live identity read/check of its own and should not be a public mutation route.

### Q9. Runner review

- **Modes/default:** `validate`, `bootstrap-identity`, `dry-run`, and `apply`; omitted mode defaults to `dry-run` (`.beep/box-provisioning/runner.ts:18,82-158,160-222`). `validate` has no provider calls. Bootstrap reads identity and rewrites private desired state. Dry-run inventories twice and writes the plan. Apply has explicit opt-in/digest gates, re-inventories, writes receipt, and replans.
- **Exit codes:** Any rejected promise reaches the catch and sets exit 1 (`.beep/box-provisioning/runner.ts:224-231`). Success is 0. Unknown mode prints usage but leaves exit 0 (`.beep/box-provisioning/runner.ts:208-222`), addressed by P2-3.
- **Repeated-plan equality:** `Equal.equals(first, second)` is structural, not reference equality. `BoxProvisioningPlan` is an `S.Class` (`packages/drivers/box-provisioning/src/BoxProvisioningPlan.ts:416-435`), and the unit test demonstrates separately produced plans compare equal, including canonicalized reordering (`packages/drivers/box-provisioning/test/BoxProvisioningPlanner.test.ts:40-48,68-127`). It will also detect any represented live difference between the two inventories.
- **Digest confirmation:** The runner compares the operator-injected digest to the decoded artifact's `planDigest` before the call (`.beep/box-provisioning/runner.ts:164-170`); the orchestrator then recomputes/validates the plan checksum, reproduces the whole plan from fresh state, and requires structural equality (`packages/drivers/box-provisioning/src/BoxProvisioning.ts:47-66`). The applier repeats self-digest and desired-digest checks (`packages/drivers/box-provisioning/src/BoxProvisioningApplier.ts:456-466`). This is strong integrity/drift binding but not cryptographic authenticity.
- **Private writes:** The intended final mode is 0600, but it is applied only after `Bun.write`; the operation is neither exclusive nor atomic and an existing parent is not tightened (`.beep/box-provisioning/runner.ts:44-49`). See P2-3.
- **Post-apply `Noop`:** It filters every `Blocked` action and then checks the remainder (`.beep/box-provisioning/runner.ts:183-193`). It therefore treats expected entitlement blockers correctly, but also incorrectly accepts ambiguity and policy blockers; see P1-2.
