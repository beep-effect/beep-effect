1. **CRITICAL — The normative spec weakens the OS-enforced immutability decision.**  
   **Evidence:** The binding decision requires `/etc/beep/openclaw/<content-hash>/openclaw.json` to be `0644 root:root` and pairs it with an independent drift audit (`explorations/openclaw-deployment-platform/DECISIONS.md:227-233`). The spec says only “root-owned, hash-versioned config root” (`goals/openclaw-workstation-agent/SPEC.md:75-78`) and likewise describes the workstation state merely as root-owned (`goals/openclaw-workstation-agent/SPEC.md:65-67`).  
   **Why this is real:** Ownership does not determine write permissions: a file can be root-owned and still writable by the gateway identity through group/world mode bits or a writable parent/pointer. Such an implementation could satisfy the current wording while reintroducing the exact direct-write bypass behind the first CRITICAL adversarial finding.  
   **Concrete fix:** Carry the exact `0644 root:root` file requirement into `SPEC.md`; specify ownership and permissions for parent directories and the active-generation pointer; and require P0 to prove that the service user cannot truncate, replace, rename, or redirect the file while the authorized applicator can switch generations. State whether the recurring canary alerts only or also repairs drift; if repair was intentionally rejected, record that decision explicitly.

2. **CRITICAL — P0 is called a hard empirical gate, but none of its four spikes has an executable test contract or safe isolation boundary.**  
   **Evidence:** P0’s entire exit criterion is “All four pass with evidence archived” (`goals/openclaw-workstation-agent/PLAN.md:11`), and the acceptance criterion merely repeats the spike names (`goals/openclaw-workstation-agent/SPEC.md:142-146`). The source decision says these prototypes must confirm or reopen four binding decisions (`explorations/openclaw-deployment-platform/DECISIONS.md:362-380`). Meanwhile, the packet recognizes that unnamed credentials, cost, destructive effects, or approvals are stop conditions (`goals/openclaw-workstation-agent/SPEC.md:188-189`).  
   **Why this is real:** A cold agent can produce narrative evidence and declare “pass” without proving the disputed properties. Worse, the spikes involve root-owned files, a real user manager, secret revocation, and SQLite migration/restore; no dedicated profile, temporary state root, test unit, database fixture, credential prerequisites, cleanup procedure, or damage boundary is specified. The supposed safety gate can therefore false-pass or damage live workstation state.  
   **Concrete fix:** Add a P0 gauntlet specification with, for each spike: pinned inputs and versions, isolated paths/unit/profile, required operator-provided credentials and approvals, exact commands or harness, positive and negative assertions, failure signatures, cleanup/restore steps, evidence format, and the exact decision reopened on failure. The SQLite case must force failure after the candidate has opened/migrated cloned shared and per-agent databases, including WAL state, and prove restoration with the previous binary.

3. **MAJOR — The final GATE C appetite cannot actually be exercised.**  
   **Evidence:** GATE C allocates roughly the first fifth of the cycle to the gauntlet and sanctions cutting the proof skill or local-model profile (`explorations/openclaw-deployment-platform/DECISIONS.md:399-409`). The packet repeats the cuts but drops the P0 allocation (`goals/openclaw-workstation-agent/SPEC.md:124-127`; `goals/openclaw-workstation-agent/PLAN.md:35-37`). At the same time, both supposedly cuttable items remain mandatory acceptance and P3 exit criteria (`goals/openclaw-workstation-agent/SPEC.md:156-160`; `goals/openclaw-workstation-agent/PLAN.md:14`), and the manifest hardcodes the proof skill into the P3 phase name (`goals/openclaw-workstation-agent/ops/manifest.json:67-69`).  
   **Why this is real:** Exercising a sanctioned cut leaves acceptance permanently unsatisfied; refusing the cut defeats the binding circuit breaker. Without the approximate P0 timebox, the gauntlet can also consume the entire cycle even though a failed spike is expressly not supposed to expand the budget.  
   **Concrete fix:** Restore the approximate one-fifth P0 budget and define its exhaustion as a stop-and-reshape condition. Make the two tail criteria conditional: they are required unless a dated cut decision is recorded in the SPEC decision log, after which acceptance, PLAN, manifest phase text, and README must be updated together.

4. **MAJOR — The GATE C backup reaffirmation is reduced to an ambiguous single “state backup.”**  
   **Evidence:** GATE C requires both encrypted Pulumi-state archives and SQLite generation snapshots to ship to dankserver over Tailscale (`explorations/openclaw-deployment-platform/DECISIONS.md:464-473`; see also `DECISIONS.md:344-354`). The spec explicitly describes only the Pulumi backend backup (`goals/openclaw-workstation-agent/SPEC.md:121-123`); its SQLite snapshots are described only as local rollback steps (`goals/openclaw-workstation-agent/SPEC.md:79-84`). P2 requires merely that “state backup lands off-machine” (`goals/openclaw-workstation-agent/PLAN.md:13`).  
   **Why this is real:** An implementation can back up only Pulumi state and satisfy the current P2 wording, leaving the application databases in the same workstation disaster domain. That loses the mitigation for Command resources’ inability to reconstruct an orphaned deployment and silently weakens an explicitly reaffirmed GATE C decision.  
   **Concrete fix:** Name both backup classes in SPEC acceptance and P2 exit criteria: encrypted Pulumi state plus encrypted shared/per-agent SQLite snapshots, including WAL-consistent contents, sent to a specified dumb-storage location on dankserver over Tailscale. Require evidence of receipt and a restore drill while explicitly prohibiting any change to dankserver’s OpenClaw/Ansible stack.

5. **MAJOR — The Telegram writer-surface mitigation is asserted but not present in the gauntlet or live-agent exit criteria.**  
   **Evidence:** The prior review requires testing login, logout, identifier migration, pairing, token rotation, reconnect, and every relevant graceful-disable path (`explorations/openclaw-deployment-platform/research/adversarial-review.md:81-87`). The binding decision specifically requires Telegram’s supergroup-migration and `defaultTo` writebacks to take their skip paths in a live channel-under-guard test (`explorations/openclaw-deployment-platform/DECISIONS.md:327-335`). The spec only says the gauntlet and soak “must confirm” writer compatibility (`goals/openclaw-workstation-agent/SPEC.md:103-106`); P0 does not mention Telegram at all (`goals/openclaw-workstation-agent/PLAN.md:11`), while P3 requires only a DM round-trip and synthetic send/receive (`goals/openclaw-workstation-agent/PLAN.md:14`). The provenance ledger nevertheless claims P0 proves every writer surface (`goals/openclaw-workstation-agent/research/SOURCES.md:35-41`).  
   **Why this is real:** Ordinary DM traffic does not trigger supergroup migration, target writeback, logout, or first-owner/pairing persistence. The agent can pass P0 and P3 while a later routine Telegram event crashes or repeatedly fails because immutable mode blocks an untested writer.  
   **Concrete fix:** Add a channel/plugin immutable-mode compatibility matrix and explicit P0/P3 cases for Telegram login/bootstrap, logout, pairing/owner setup, supergroup migration, `defaultTo` resolution, token rotation, and reconnect. Every enabled writer must either be rendered declaratively or demonstrate a graceful no-write path without event-handler failure.

6. **MAJOR — The secret-rotation spike does not prove that rotated credentials are actually current.**  
   **Evidence:** The prior mitigation requires reload status, stale/cold-owner recording, degraded alerting, and authenticated model plus channel probes (`explorations/openclaw-deployment-platform/research/adversarial-review.md:23-29`). The binding decision similarly requires post-rotation reload, degraded alerting, and authenticated model/channel probes (`explorations/openclaw-deployment-platform/DECISIONS.md:306-319`). The spec abbreviates that to reload, alerting, and an unspecified singular “authenticated probe” (`goals/openclaw-workstation-agent/SPEC.md:96-100`). P0 requires only rotation/reload/degraded detection, while the model and channel probes appear later in P3 without being tied to a rotation event (`goals/openclaw-workstation-agent/PLAN.md:11-14`).  
   **Why this is real:** `secrets reload` can complete while an owner remains stale on a revoked old value. A separate model or Telegram check performed before or independently of rotation does not establish that the same-reference update reached every owner. This is the exact day-30 failure the review identified.  
   **Concrete fix:** Define P0 success as: rotate behind the same `op://` reference, revoke the old value, reload, assert no stale/cold eligible owners, exercise the degraded alert path deliberately, and then pass both an authenticated model request and Telegram probe. Add the bounded rotation trigger/timer and the recovery runbook to P3 or operational acceptance.

7. **MAJOR — The drift audit still does not cover the failure modes of `command.local.Command`.**  
   **Evidence:** The adversarial mitigation requires auditing target identity, home, hashes, generation pointer, exact OpenClaw and Node versions, unit text, enabled/active state, and config validation on preview/refresh paths outside Command resources (`explorations/openclaw-deployment-platform/research/adversarial-review.md:41-49`). The spec binds only machine ID, hostname, and UID during preflight and says generally that a drift audit lives outside Command (`goals/openclaw-workstation-agent/SPEC.md:90-95`, `SPEC.md:117-118`). P2 proves only that a manual config edit is detected (`goals/openclaw-workstation-agent/PLAN.md:13`).  
   **Why this is real:** A copied stack can still preview clean on the wrong machine, or retain a wrong package symlink, Node binary, unit, or service state while the config hash remains correct. Detecting one edited JSON file does not mitigate the provider’s lack of read/refresh semantics.  
   **Concrete fix:** Define the drift inventory normatively and require it to run on every preview/refresh-equivalent path outside Command resources. Add expected home and runtime paths to identity binding. P2 must demonstrate failures for a wrong machine/user and deliberate drift in the generation pointer, package/Node version, unit content, enabled/active state, and rendered-config validation—not only a config-file edit.

8. **MAJOR — The lossy schema-export guard from finding 7 disappeared entirely.**  
   **Evidence:** The binding decision says CI must fail when the OpenClaw schema export contains lossy placeholders for extensions the deployment declares (`explorations/openclaw-deployment-platform/DECISIONS.md:264-276`), following the review’s documented size/item-cap behavior (`explorations/openclaw-deployment-platform/research/adversarial-review.md:61-71`). The spec requires candidate `config validate` and negative fixtures but says nothing about schema-export placeholders (`goals/openclaw-workstation-agent/SPEC.md:85-89`, `SPEC.md:147-150`). P1 has the same omission (`goals/openclaw-workstation-agent/PLAN.md:12`).  
   **Why this is real:** Plugin-aware validation of one rendered positive fixture does not reveal that an extension’s exported schema was replaced by permissive `additionalProperties: true`. Negative fixtures designed from that lossy export can also validate the wrong contract.  
   **Concrete fix:** Add a P1 CI and exit criterion that inspects the pinned binary’s plugin-aware schema export and fails on every lossy/omitted-extension placeholder for a declared channel, provider, plugin, or skill surface. Bind the Node version, OpenClaw package, plugin manifests/artifacts, adapter version, and fixtures as one tested compatibility set.

9. **MAJOR — SQLite rollback is only a one-time P0 demonstration, not a required gate on every OpenClaw version bump.**  
   **Evidence:** The CRITICAL review explicitly requires a downgrade/restore test on every version bump (`explorations/openclaw-deployment-platform/research/adversarial-review.md:13-21`). The spec defines the state machine and a general upgrade runbook (`goals/openclaw-workstation-agent/SPEC.md:79-84`, `SPEC.md:111-113`), but its only executable rollback criterion is the initial P0 spike (`goals/openclaw-workstation-agent/SPEC.md:142-146`). Neither the P1 adapter exit nor P2 engine exit imposes a recurring version-bump gate (`goals/openclaw-workstation-agent/PLAN.md:12-13`).  
   **Why this is real:** Passing against one version pair does not establish that the next OpenClaw release has reversible state migrations or that the previous binary can consume the restored snapshot. A later adapter/package update can therefore strand state while satisfying all documented phase criteria.  
   **Concrete fix:** Add a permanent version-bump checklist and test lane: classify shared and per-agent migrations, exercise candidate startup against cloned state, force post-migration rejection, restore all databases/WAL files, and prove the previous binary starts. Irreversible migrations must require a recorded operator gate and forward-recovery plan.

10. **MINOR — The proof skill is no longer constrained to be benign.**  
    **Evidence:** The inherited legal-focus decision requires exactly one **benign** proof skill (`explorations/openclaw-deployment-platform/DECISIONS.md:137-145`). The spec and plan say only “proof skill” (`goals/openclaw-workstation-agent/SPEC.md:156-160`; `goals/openclaw-workstation-agent/PLAN.md:14`).  
    **Why this is real:** Pinning and integrity-checking a skill proves identity, not safety or license suitability. A cold agent could choose arbitrary community code with network, shell, secret, or client-data access and still satisfy the written acceptance criterion.  
    **Concrete fix:** If the skill is not cut, name or define an acceptable fixture: preferably repo-local, deterministically packaged, permissively licensed, no network or shell access, no secret access, no client data, and a narrowly specified harmless behavior.

11. **MINOR — The tracked packet contains execution routing that exists only in the user’s private global configuration.**  
    **Evidence:** `PLAN.md` instructs agents to route implementation through “claudex” and judgment through “Fable” (`goals/openclaw-workstation-agent/PLAN.md:38-39`), repeated in the packet README (`goals/openclaw-workstation-agent/README.md:60-61`). Those terms and the “global routing doctrine” are not defined anywhere else in the repository.  
    **Why this is real:** A cold Codex, CI, GitHub, or other contributor agent cannot comply from files on disk. It also embeds operator-specific quota/session infrastructure in a public execution packet even though that routing has no bearing on the implementation contract.  
    **Concrete fix:** Remove those lines from tracked packet files. Keep private model/quota routing in the user-level agent configuration; if role separation matters publicly, express it provider-neutrally as “implementation” versus “gate-review” responsibilities.

**Verdict:** The packet is **not safe to hand to a cold implementing agent**. It mechanically satisfies the packet standard—the launcher delegates, the manifest/lifecycle/completion gate/reflection fields are present, and provenance links are bidirectional—and I found no plaintext secret or token disclosure; the AGPL clean-room and unlicensed-reference rules are also surfaced. Those mechanical properties do not compensate for an under-specified P0 gate, a weakened immutability boundary, unenforceable appetite cuts, and several dropped adversarial mitigations. A cold agent could legitimately mark the gauntlet passed while failing to prove the properties on which the entire deployment design depends.
