## What this repo actually is

LegalPP is a compact 2020-era PyTorch/DGL research implementation of **legal-provision prediction as transductive
knowledge-graph completion**, accompanying the 2021 CCKS paper “Text-Guided Legal Knowledge Graph Reasoning.” It is
not an ontology, legal rule language, patent corpus, SPARQL system, or deployed inference service. The README says the
LegalLPP data was collected from the Guangdong government-service website; no acquisition code, source URLs, dates,
jurisdiction metadata, or update pipeline are included (`README.md:134-159`).

The mined snapshot is commit `5039b3848adfd9a9962eac5ff3e86084a3fe8596`. Its substantive payload is the valid
20.4 MiB `data.zip` (SHA-256 `eee5f34e88ecc556b20171b8ab557bf627af4270208aa7f7f69d26f386be2f49`), which expands
to 133,378,586 bytes of UTF-8 TSV/text plus one misleadingly named custom record file. The graph has 275,547 entity
identifiers, four relation identifiers, and 276,881 split rows before deduplication.

The executable lane is: load integerized triples and optional BERT node features -> construct a bidirectional DGL
training graph -> encode with R-GCN or relation-blind GAT -> score with DistMult or a SimplE-labelled decoder -> train
with sampled negatives -> rank corrupted endpoints (`dataset.py`, `main.py`, `module/`, `utils.py`). The repository
contains no dependency lock/manifest, tests, model checkpoints, numeric embeddings, TensorBoard logs, reported metric
files, raw/tuned BERT model, or online inference code. `embeds/tsne.zip` contains nine PNG plots only.

## Extractable gold

### 1. A small, explicit legal-task graph grammar

`data.zip::data/relations.txt` and `relation2text.txt` define exactly four directed edge kinds. Their observed endpoint
roles yield this concrete graph shape:

```text
administrative task --base_entry_is--> provision fragment
administrative task --base_law_is----> legal instrument
administrative task --right_is-------> administrative-power label
provision fragment  --belongs_to-----> legal instrument
```

The archive contains 1,552 `task_N` nodes, 935 `right_N` nodes, 269,019 provision-fragment nodes that occur as
`belongs_to` subjects, and 2,843 instruments that occur as its objects. These are **inferred roles**, not declared
classes: there is no type relation or ontology. `entity2text.txt` shows that tasks and `right_N` nodes both carry
human-readable descriptions of government affairs/powers, fragments carry provision text, and instrument nodes carry
long-form instrument text.

The relation inventory is highly imbalanced but structurally crisp:

| Relation | Unique edges | Unique heads | Unique tails | Load-bearing property |
|---|---:|---:|---:|---|
| `belongs_to` | 269,019 | 269,019 | 2,843 | exactly one asserted instrument per fragment |
| `base_entry_is` | 4,585 | 1,477 | 3,411 | multi-label task-to-provision supervision |
| `base_law_is` | 2,153 | 1,477 | 777 | exactly derivable from the two relations above |
| `right_is` | 1,090 | 1,090 | 935 | task-to-administrative-power alignment |

The exact derivability of every `base_law_is` pair is useful: a typed port can materialize it as a provenance-bearing
shortcut while retaining the canonical two-hop derivation. The heterogeneous endpoint roles are also a ready-made
contract for relation-specific candidate types; they should not remain conventions encoded only in string prefixes.

### 2. Text as a first-class feature for every graph node

`data.zip::data/entity2text.txt` contains one tab-delimited text row for every one of the 275,547 entity identifiers:
no missing, extra, malformed, or duplicate IDs were found. Character-length medians are 38 for tasks, 23 for power
labels, 43 for fragments, and 121 for instruments; the global maximum is 3,952. That total text coverage is the core
portable data contract: graph identity and text evidence share one stable entity key.

`embeds/make_bert_embed.py:14-39` batches every entity text, truncates/pads to 128 tokens, and takes BERT's `[CLS]`
vector. `module/graph_encoder.py:16-33,51-73` optionally projects an oversized embedding matrix to the configured
400 dimensions with `TruncatedSVD`, then uses it as the node embedding table. This cleanly separates text-feature
generation from graph training, so alternative encoders can produce the same `entity-id -> vector` boundary.

Do not copy two accidental semantics: no attention mask is passed to BERT, and `nn.Embedding.from_pretrained(embed)`
uses PyTorch's default frozen weights. Moreover, `main.py:207-221` exports `emb_node.weight`, not the R-GCN/GAT output,
so a purported post-graph embedding export can merely reproduce the frozen projected input table.

### 3. A reproducible corpus bundle, plus integrity checks it needs

`data.zip` packages the vocabulary, text lookup, relation labels, ordinary train/dev/test splits, and a task-specific
evaluation view together. The split profile is:

| File | Rows | `belongs_to` | `base_entry_is` | `right_is` | `base_law_is` |
|---|---:|---:|---:|---:|---:|
| `train.tsv` | 221,504 | 215,242 | 3,668 | 872 | 1,722 |
| `dev.tsv` | 27,687 | 26,905 | 458 | 109 | 215 |
| `test.tsv` | 27,690 | 26,906 | 459 | 109 | 216 |
| `target/test.tsv` | 459 | 0 | 459 | 0 | 0 |

`target/test.tsv` is exactly the `base_entry_is` subset of the ordinary test split. Its 459 edges cover 345 tasks and
433 true provision tails. `target/filtered_entities.txt` is exactly the set of all 269,019 `belongs_to` subjects;
`dataset.py:71-80` uses it only as the legal tail-candidate whitelist. This “full graph split plus task-view split plus
typed candidate set” bundle is worth porting as a versioned benchmark artifact.

It also supplies concrete ingestion assertions. There are 26 duplicate rows inside train and one each inside dev/test,
plus six `belongs_to` triples crossing split boundaries. Two entity identifiers contain `/` despite not being provision
fragments, defeating `embeds/visualize.py:24-30`'s slash-based type inference. Thirty-three task nodes and 1,198 other
nodes are never used by any split edge, yet remain embedding and ranking candidates.

`data.zip::data/title2entry.json` is not JSON: it is 1,552 alternating `task_N` lines and JSON-object lines. It records
4,585 task/fragment pairs plus opaque integer annotations, but no repository code reads it. Its pair set differs from
the graph by four whitespace-normalization variants (spaces inside three instrument titles and one ministry/title
string). Preserve this as a normalization-fixture lesson; do not infer score semantics for its integers.

### 4. A compact encoder/decoder experiment lattice

The seven non-sample files under `config/` encode the intended ablation matrix: R-GCN or GAT with DistMult; R-GCN
with the SimplE-labelled decoder; and raw-BERT/tuned-BERT initialization variants for both encoders. Common settings
use 400-dimensional nodes, two graph layers, 10 negatives per positive, a 0.5 message-graph split, and evaluation every
400 epochs (`config/*.json`). This is a concise experiment-manifest pattern even though results are absent.

`utils.py:90-190` makes the training stages explicit:

```text
sample positive edges -> relabel their incident nodes -> corrupt one endpoint 10x
-> reserve half the positives as message-passing structure -> score all positives/negatives with BCE
```

`utils.py:152-174` adds a reverse edge type for each relation. R-GCN consumes all eight directional types with
self-loops and block-diagonal decomposition (`module/graph_encoder.py:26-43`); GAT consumes the same bidirectional
topology but ignores relation IDs (`graph_encoder.py:61-83`). DistMult supplies the standard elementwise triple score;
the SimplE-labelled lane holds forward/inverse relation vectors but shares one entity embedding role
(`module/relation_decoder.py:6-73`).

The useful port is the swappable typed boundary—text initializer, graph encoder, relation decoder, evaluator—not the
framework-era implementation. Make graph direction, relation awareness, feature freeze/fine-tune policy, candidate
types, random seed, dataset digest, and split unit explicit fields in a schema-validated experiment manifest.

### 5. Failure modes that should become Beep benchmark acceptance tests

- **Same-query label leakage:** splitting edges rather than tasks leaves 264/345 target-test tasks with at least one
  training `base_entry_is` edge; 373/459 target edges belong to a task with another training target. A real provision
  recommendation benchmark needs task/group/time-disjoint split modes and leakage reports.
- **Test-set model selection:** `main.py:145-175` calls `eval_filtered(... eval_type='test')` inside training and saves
  the best test MRR; validation data is only added to the known-positive filter. The test set is therefore not held out.
- **Stateful, order-dependent filtering:** `utils.py:199-230` removes the current truth from a shared set and never
  restores it. Earlier truths stop filtering later ranks; after head ranking, all target truths are absent during tail
  ranking. A port needs immutable known-positive indexes keyed by `(head, relation)` and `(relation, tail)`.
- **Metric-domain mixing:** target mode restricts only tail candidates; head candidates remain all 275,547 entities,
  then `eval_filtered` concatenates head and tail ranks into `all` MRR/Hits. Provision prediction should report typed
  tail ranking separately and define any task-retrieval metric independently.
- **Direction-blind scoring:** all four dataset relations are directional, but DistMult is symmetric in head/tail. The
  SimplE-labelled implementation also uses one entity role and commutative products, so it does not recover SimplE's
  asymmetric head/tail capacity. Add swapped-edge adversarial tests before accepting a decoder.
- **Easy/false negatives:** `utils.py:177-190` corrupts either endpoint uniformly within sampled nodes, without endpoint
  types or known-positive rejection. Typed hard negatives and explicit false-negative policy are required.
- **Non-reproducible execution:** no seed, dependency versions, model artifacts, BERT provenance, metrics, or tests are
  shipped. Missing checkpoints silently leave a random model in place (`main.py:183-204`), and the nominal epoch bound
  can be exceeded while test MRR keeps tying or improving (`main.py:168-175`).

## Beep-relevance hooks

- **semantic-foundation SKOS / `@beep/ontology`:** model `AdministrativeTask`, `ProvisionFragment`, `LegalInstrument`,
  and `AdministrativePowerLabel` as typed schemas with stable source IDs; keep the four source predicates as mapped
  assertions with provenance. LegalPP contributes no class hierarchy or SKOS concepts, so do not pretend it does.
- **Epistemic slice:** represent gold labels, derived `base_law` shortcuts, candidate membership, normalization repairs,
  split membership, and negative samples as distinct claims with evidence and confidence; absence from the graph is
  `unknown`, not a negative legal judgment.
- **Patent tooling:** reuse the text-initialized heterogeneous-KGC experiment shape for claim/citation/prior-art or
  provision recommendation only after defining asymmetric relations, typed candidates, hard negatives, and group/time
  splits. LegalPP itself contains no patents and contributes no patent vocabulary.
- **Gov-legal data drivers:** build a digest-addressed LegalLPP import adapter that streams the zip, validates UTF-8 and
  arity, assigns endpoint types from validated relation shapes, deduplicates deterministically, quarantines the four
  whitespace drifts, and attaches jurisdiction/source/effective-time fields absent upstream.
- **OIP practice:** require every model run to emit an immutable experiment/evaluation report: source digest, attribution,
  config, seed, text encoder/version, split policy, contamination inventory, candidate universe, separate head/tail
  metrics, and checkpoint-selection dataset. Treat any leakage or missing artifact as a visible failed/unknown lane.

## Extraction confidence

**High for archive structure, counts, graph semantics, and static code behavior; medium for intended experimental
behavior; low for benchmark validity and legal-data fitness.** All requested targets were readable. `data.zip` was
streamed and parsed directly with Python's `zipfile`; every member, ID/text join, triple arity, relation distribution,
candidate filter, derivation, split overlap, task overlap, and `title2entry` record was inspected. All Python files pass
AST parsing, and the license, configs, decoder, sampler, evaluator, embedding scripts, archive hashes, and t-SNE member
list were read.

The model was not executed: required pinned dependencies and referenced BERT/checkpoint/embedding artifacts are absent,
and the PNG-only t-SNE bundle cannot establish numeric results. The paper body and live Guangdong source were not part
of this repository mine. Accordingly, architectural and data-integrity claims are direct evidence; performance,
scientific conclusions, label quality, legal coverage, currency, and upstream-site rights remain unverified.
