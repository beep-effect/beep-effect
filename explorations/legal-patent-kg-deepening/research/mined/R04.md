## What this repo actually is

This is a small, static **coverage-study dataset**, not an ontology implementation. Its substantive artifact is `mappingfile.xlsx`: a human-curated matrix aligning 26 desired CJEU case-law properties against six existing legal vocabularies.
There is no RDF/OWL source, transformation code, SPARQL, SHACL, executable pipeline, or case corpus in the repository; `README.md` supplies the scope, authors, source versions, and links, while `LICENSE` supplies CC BY 4.0 terms.

The mined snapshot is tag `cjeu-ontology-mappings-v1.0.1`, commit `14c81e0712d54e30eadadebf8179b8694370c501`. Its message is load-bearing: “removes X's so that blank cells now represent no match.”
Consequently, blank mapping cells are negative coverage evidence, not merely missing data.
The workbook SHA-256 in this snapshot is `d89410188841c8f34e7172857da14ebc91996b3b21178f150e50240ff15e9fcf`.

`mappingfile.xlsx` has seven sheets:

1. `Selected properties` defines the 26-property target vocabulary and annotation notes.
2. `European Legislation Identifier` maps against ELI v1.3.
3. `Common Data Model - (CDM)` maps against CDM v4.6.0.
4. `LAKI` maps against the Finnish legislation schema v2020.07.17-011044.
5. `Metalex` maps against MetaLex v1.0.
6. `LKIF` maps against LKIF Core v1.1.
7. `OIKEUS` maps against Oikeus v2013-06-10.

The ontology versions above come from `README.md`; the linked ontology payloads are not vendored here. The workbook is a manually authored assessment with no formulas, but with hyperlinks and analyst comments that qualify several mappings.

## Extractable gold

### 1. A reusable mapping-assertion shape

Every ontology sheet uses the same two-part alignment grid in `mappingfile.xlsx` (`A2:M28`):

- `A:E` repeat the selected property number, name, metadata-presence flag, example, and informal definition.
- `F:I` align the property's **value type** as `Equivalent`, `Superclass`, `Subclass`, or `Approximate`.
- `J:M` align the **property/predicate** as `Equivalent`, `Superproperty`, `Subproperty`, or `Approximate`.

That distinction is the central portable pattern: a source predicate can be a good relation match even when its range/type is too broad, too narrow, or only approximate. Do not collapse the workbook into a two-column `source → target` crosswalk.
A faithful record needs at least:

```text
selectedProperty + targetOntology + facet(type|property) + relationKind + targetTerm
```

It should also retain cell coordinate, source version, note/comment, and review state.
An ontology can contribute several assertions for one selected property; LKIF's `Agent, Role` cells also show that one mapping cell can denote a target set.

### 2. A compact CJEU case-law target vocabulary

`mappingfile.xlsx`, sheet `Selected properties`, cells `A1:F27`, is itself a useful seed dataset.
It splits evenly between properties marked present in source metadata and absent from it: 13 `yes`, 13 `no`.
That flag is valuable as an acquisition hint, but it is not a semantic mapping or a statement that a value is always populated.

An analytical grouping of the 26 workbook terms is:

- **Actors and roles:** `judge`, `judge_rapporteur`, `advocate_general`, `registrar`, `intervening_party`, `referring_court`, `claimant`, `defendant`, `court`.
- **Legal sources and references:** `eu_legislative_history_item`, `domestic_law`, `cited_case`, `relevant_eu_law`, `referring_case_national`.
- **Narrative/procedural units:** `fact`, `domestic_procedure_item`, `preliminary_question`, `opinion_court`, `preliminary_question_answer`, `verdict`.
- **Subject classification:** `law_area`, `law_area_subtopic`.
- **Identity and time:** `case_number`, `ecli`, `date`, `lodge date`.

This grouping is a distillate, not a hierarchy asserted by the workbook. The informal definitions add cardinality and role semantics that should survive extraction: several judges, facts, questions, claimants, or defendants can occur per case, while the judge rapporteur is usually singular.

The researcher notes in `Selected properties!F9`, `F11`, `F22`, `F24`, and `F25` identify five concrete modeling requirements:

- sentence boundaries are not reliable boundaries for facts;
- sentence boundaries are not reliable boundaries for preliminary questions;
- each preliminary question should link to its answer;
- cited legislation articles should link to the individual question that invokes them;
- verdicts may need ordered outcome points rather than one undifferentiated text field.

The `court` note says the preliminary study assumes the CJEU but intends a generalized case-law model, making `court` a data value or relation rather than a universal constant.

### 3. CDM's paired class-and-predicate coverage

`mappingfile.xlsx`, sheet `Common Data Model - (CDM)`, is the densest mapping: 24/26 properties.
It demonstrates the strongest paired mappings, for example:

- `judge` → equivalent type `cdm:judge` plus equivalent property `cdm:case-law_delivered_by_judge` (`F3`, `J3`).
- `advocate_general` → `cdm:advocate-general` plus `cdm:case-law_delivered_by_advocate-general` (`F5`, `J5`).
- `opinion_court` → `cdm:opinion_cjeu` plus `cdm:resource_legal_received_opinion_cjeu` (`F13`, `J13`).
- `law_area` → `cdm:subject-matter` plus `cdm:resource_legal_is_about_subject-matter` (`F15`, `J15`).
- `court` → `cdm:court-formation` plus `cdm:case-law_delivered_by_court-formation` (`F26`, `J26`).

Identifiers show why type and property must remain separate. Both `case_number` and `ecli` map to the value type `adms:Identifier`, but their predicate judgments differ:
`case_number` only approximately matches `cdm:case_court_identifier_year`, while ECLI equivalently matches `cdm:case-law_ecli` (`F18:M19`).

CDM also supplies deliberately lossy bridges:

- `preliminary_question` approximately matches type `cdm:question_written`, while `cdm:submits_preliminary_question` is marked predicate-equivalent (`I12`, `J12`).
- `verdict` approximately matches `cdm:paragraph_legal` and `cdm:manifestation_case-law_operative_part` (`I25`, `M25`).
- `fact` approximately matches the generic `annotation:context` term (`M10`).
- `domestic_procedure_item` approximately matches deprecated `cdm:resource_legal_procedure_comment` (`M11` and its comment).

The comments are epistemic data, not decoration. `I21` and `I22` warn that claimant/defendant need not be a `cdm:person`; a company or member state is possible.
`F15`, `J15`, `M16`, and `J26` preserve alternative candidate mappings.
Any port should represent those as reviewable claims or alternatives, not silently select one.

### 4. LKIF's upper/lower-bound modeling

`mappingfile.xlsx`, sheet `LKIF`, contributes the richest class lattice even though it covers fewer properties than CDM.
For `judge`, `judge_rapporteur`, `advocate_general`, and `registrar`, the workbook records:

```text
superclasses: Agent, Role; subclass: Natural_Person; approximate: Professional_Legal_Role
superproperty: participant; subproperty: actor
```

For `intervening_party`, `Legal_Role` replaces the person/professional-role refinement (`G7:L7`).
The discussion in `LKIF!A8` says the annotator chose to preserve role distinctions instead of reducing entries to natural persons. This ports directly as a role-bearing participation model: person/organization identity and procedural role are separate facts.

LKIF also gives a compact narrative and epistemic ladder:

- `fact` is equivalent to `Fact` (`F10`).
- `domestic_procedure_item` has superclass `Expression` (`G11`).
- `opinion_court` lies under `Reason` and above `Argument` in the study's mapping relation (`G13:H13`).
- `preliminary_question_answer` has superclass `Epistemic_Role` (`G14`).
- `cited_case` is equivalent to `Persuasive_Precedent` with superclass `Precedent` (`F16:G16`).
- `verdict` approximately maps to `Normatively_Qualified` (`I25`).

The hyperlinks preserve LKIF module provenance: `Agent`/`Organisation`/`actor` point to `action.owl`, `participant` to `process.owl`, expression terms to `expression.owl`, and precedent/legal-source terms to `norm.owl`.
Retain those module IRIs when normalizing the local labels.

### 5. Sparse vocabularies are still diagnostic

The sparse sheets show where legislation-oriented vocabularies stop short of full case-procedure modeling:

- ELI maps `domestic_law` under `eli:LegalResource` and records approximate predicates for `based_on`, `is_about`, `cites`, `date_publication`, and `cited_by_case_law_reference` (`G9`, `M9`, `M15:M17`, `M28`).
- LAKI offers only the superclass `laki:Statute` for `domestic_law` and `relevant_eu_law` (`G9`, `G23`).
- MetaLex uses approximate `metalex:BibliographicCitation` value-type matches for domestic law, cited cases, relevant EU law, and the referring national case (`I9`, `I16`, `I23`, `I28`).
- Oikeus supplies superproperties `decisionMaker`, `dc:date`, `dc:identifier`, and `level`, plus `Court` as a superclass and `previousDecision` as an approximate predicate (`G20:K20`, `G26:K26`, `K3`, `K17`, `K19`, `M28`).

The useful lesson is coverage shape, not a winner ranking: CDM is case-law-specific, LKIF is conceptual, while ELI/LAKI/MetaLex/Oikeus mostly contribute broad legal-resource, citation, date, identifier, or court hooks.

### 6. Import and quality traps worth turning into validators

`mappingfile.xlsx` is OOXML with 998/999 styled rows per sheet but only 26 data rows; importers must ignore styled empty tails. There are no formulas, so cached-formula evaluation is unnecessary.
The two example dates are stored as Excel serials `42719` and `43531` with number format `d mmmm yyyy`, rendering as 15 December 2016 and 7 March 2019.

Normalization must preserve raw evidence while fixing comparison keys:

- `Common Data Model - (CDM)!J28` has a leading space before its IRI.
- `OIKEUS!K20` and `K26` contain the label `court level ` with a trailing space.
- LKIF cells spell `Spatio_Temporal_Occurence`, while the hyperlink fragment spells `Spatio_Temporal_Occurrence`.
- `lodge date` is the only selected property label using a space rather than snake_case.
- `Selected properties!A1` carries a legacy comment about `Normatively_Qualified` that appears unrelated to the header cell.

These should become warnings with source coordinates, not destructive rewrites. Store hyperlink target and displayed text separately; several LKIF/Oikeus cells use a short label whose link holds the canonical IRI.

## Beep-relevance hooks

- **semantic-foundation SKOS / `@beep/ontology`:** seed a 26-concept CJEU case-law scheme, then model each workbook cell as a provenance-bearing mapping assertion with facet and match-kind rather than flattening it to `skos:exactMatch`.
- **epistemic slice:** ingest alternatives, deprecation notes, and party-type objections as claims with evidence coordinates, reviewer, and status; blank-at-v1.0.1 becomes an explicit `no-match-observed` claim scoped to ontology version.
- **patent tooling:** reuse the matrix shape as a vocabulary-coverage harness for patent actors, identifiers, citations, procedural events, questions/grounds, and outcomes; keep type compatibility separate from predicate compatibility.
- **gov-legal data drivers:** add ELI/CDM/ECLI/ADMS/DC/Finlex adapters that preserve raw cell text and hyperlink IRI, normalize whitespace/date serials, and reject silent spelling drift.
- **OIP practice:** represent facts, procedural steps, questions, answers, cited provisions, reasoning, and ordered verdict points as addressable spans linked to the source document; the workbook's own notes already identify these relation requirements.

## Extraction confidence

**High for artifact facts and counts.** The workbook was parsed directly from OOXML, including all seven sheets, nonblank cells, styles, hyperlinks, comments, and number formats; counts were recomputed from the v1.0.1 file rather than inferred from the README.

**High for repository provenance and reuse terms.** `README.md`, the full `LICENSE`, git tag/history, and the workbook digest were inspected locally.

**Medium for ontology-semantic correctness.** The repository records expert judgments, but several are explicitly approximate, disputed, alternative, or deprecated.
The six linked ontology versions were not present in the repository and were not independently revalidated during this mine.

**Not available from this source:** ontology axioms beyond the recorded links, SPARQL query shapes, SHACL constraints, extraction code, evaluation cases, precision/recall metrics, or a CJEU case dataset.
Treat this source as a licensed mapping benchmark and requirements artifact, not as executable ground truth.
