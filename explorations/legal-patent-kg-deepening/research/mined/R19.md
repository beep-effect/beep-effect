## What this repo actually is

`patentlego-ontology` is a two-Markdown-file concept release for describing patents as composable functional
blocks. It is not a machine-readable ontology, knowledge graph, patent dataset, matcher, validator, or system
builder. The inspected snapshot is commit `2b78bc06d0a1ce8671ef10f64ce8224a4e9f0ca1` (2026-05-05).
`PatentLEGO_README.md` is the 174-line v0.1 specification; `README.md` is its 75-line launch narrative.

The proposal changes the organizing question from patent ownership to function: what a patented disclosure needs,
does, produces, and can connect to. Its entire executable idea is an unformalized compatibility relation between a
block's typed output and another block's typed input (`PatentLEGO_README.md:13-19`; `README.md:13-31`). Six templates
sketch common functional chains.

“Ontology” here means a prose data-design vocabulary. The checkout contains no OWL/RDF/Turtle/JSON-LD, namespace or
IRI policy, class/property axioms, SKOS scheme, SHACL/JSON Schema, SPARQL, code, tests, issue fixtures, spreadsheet,
seed patent records, or generated documentation. The lone JSON object is illustrative prose. Validator, tagging guide,
50-record seed set, and matching-engine specification remain future work (`PatentLEGO_README.md:133-137`).

## Extractable gold

### 1. A function-first patent profile with explicit composition surfaces

`PatentLEGO_README.md:34-50` gives the complete top-level `PatentBlock` field inventory:

```text
identity/title/purpose -> functional category
typed inputs + typed outputs -> connection points
energy role + scale + technical domains -> operating context
confidence -> epistemic qualifier
```

The fields are `id`, `plain_title`, `purpose`, `purpose_category`, `inputs`, `outputs`, `energy_balance`, `scale`,
`domain`, `connection_points`, and `confidence_score`: identity, function, ports, context, and confidence stay distinct.

The clean-room pattern to recreate is a **functional profile beside the patent record**, not a replacement for it.
A robust design should allow a publication, claim, embodiment, or component to yield multiple functional units and
retain each field's source span/version. “Every patent -> one block” leaves granularity, families, claim dependencies,
alternative embodiments, and prosecution changes unresolved (`PatentLEGO_README.md:36-50`).

### 2. Twelve flat purpose facets, suitable as a seed scheme rather than a class hierarchy

`PatentLEGO_README.md:52-67` enumerates 12 purpose IDs: `GEN`, `STORE`, `CONVERT`, `DISTRIBUTE`, `CONTROL`,
`STRUCTURE`, `SENSE`, `INTERFACE`, `TREAT`, `EMIT`, `COMPUTE`, and `ACTUATE`. They cover creation, retention,
transformation, movement, regulation, structure, detection, coupling, treatment, emission, computation, and actuation.

This flat list has no hierarchy, disjointness, exhaustiveness claim, multi-label rule, or claim-verb mapping. The rule
to prefer compositions over new categories (`PatentLEGO_README.md:151-154`) is useful governance: test whether a
proposal is a primitive, synonym, or ordered composition before expanding the scheme.

### 3. Typed resource ports with direction, qualifiers, and direct-match intent

The launch narrative names five resource families for both sides of a block: energy, fluid, material, signal, and
field (`README.md:23-29`). The example in `PatentLEGO_README.md:84-105` reveals the only concrete port record shapes:

```text
input  = type + subtype + free-text specification + optional
output = type + subtype + free-text specification + is_primary | is_waste
```

Observed labels are `energy.radiative` / `solar_irradiance`, `fluid.gas` / `air_ambient`, `fluid.liquid` /
`water_potable`, and `waste.thermal` / `heat_rejected`; the last adds a sixth family. Irradiance, humidity,
temperature, and water-quality constraints live in one unparsed `specification` string.

The roadmap claims “direct-match subtype mirroring” (`PatentLEGO_README.md:114-122`), but supplies no subtype list,
units, conversions, tolerance, cardinality, aggregation, or algorithm. The portable pattern is **directional typed
ports plus separately evaluated constraints**: subtype equality can suggest candidates, not prove engineering fit.

### 4. Six small system motifs as graph-query seeds

`PatentLEGO_README.md:69-80` supplies six named motifs:

- generation -> storage -> distribution;
- sensing -> control -> actuation;
- conversion -> storage -> conversion;
- treatment -> storage -> distribution;
- source -> treatment -> use -> treatment, described only as a closed loop;
- emission -> sensing -> computation.

These are valuable as query templates over purpose-labelled functional units: search for a path, bind ports between
adjacent nodes, evaluate every edge's constraints, and report missing roles or adapters. They are patterns, not
validated systems or claims of enablement.

The table also exposes vocabulary drift that should become conformance tests. `SOURCE` and `USE` appear in the
closed-loop template but are not among the 12 purpose categories. The ID `SYS-EMIT-SENSE-PROCESS` ends in `PROCESS`
while its pattern ends in `COMPUTE`. Template IDs abbreviate categories inconsistently (`DIST`, `CTRL`, `ACT`,
`CONV`). A port should reference stable concept IDs rather than encode semantics twice in a mnemonic string.

### 5. Orthogonal operating-context facets, presently only examples

`README.md:26-29` is the only bounded-looking inventory for the other axes:

- energy role: producer, consumer, transformer, storage unit;
- scale: personal, residential, industrial, municipal;
- domain: mechanical, electrical, thermal, biological, chemical.

The main specification weakens each with “etc.” (`PatentLEGO_README.md:46-48`), and the JSON example adds domain
`AQUA` without defining it. No meanings, codes, hierarchy, allowed multiplicity, or cross-axis constraints are given.
Treat these as requirements for separate concept schemes, not as an extractable finished taxonomy. In particular,
energy balance should be derived from quantified port flows over a stated boundary and time window when possible,
rather than accepted as a free-standing label.

### 6. Review state belongs beside extraction confidence

The block table constrains `confidence_score` only to 0.0-1.0. The example additionally uses
`review_status: community_reviewed`, and contribution prose says expert review raises both fields
(`PatentLEGO_README.md:50,103-104,145-149`). This is a promising two-axis separation: probabilistic or rubric-based
confidence is not the same thing as workflow state.

The missing contract is equally instructive. There is no confidence rubric, assessor identity, model/version,
evidence link, review history, dispute representation, quorum, calibration dataset, or rule for aggregating reviews.
Recreate the pattern as immutable assessments over field-level claims; derive a display status rather than mutating a
single score until it looks authoritative.

### 7. A sensible staged hardening backlog

The v0.2 list adds temporal and geographic constraints, hazards, cost/complexity, interoperability standards, TRL,
and patent-license/openness flags (`PatentLEGO_README.md:124-131`). Those are precisely the dimensions that can turn
a type-compatible graph edge into an unusable, unsafe, unavailable, or legally constrained connection.

The sequence worth taking is: define a versioned schema and concept schemes -> hand-tag adversarial patents ->
validate shapes and provenance -> specify compatibility as an evidence-producing judgment -> only then rank or
visualize candidate systems. Upstream marks core taxonomies complete before publishing their enumerations, so Beep
should gate “complete” on machine validation, competency questions, fixtures, and coverage evidence.

### 8. Negative-space requirements exposed by the example

- `connection_points` is required by the field table but absent from the “fully tagged” JSON example; no connection
  point shape exists anywhere in the repo.
- `review_status` appears in that example but not in the field table, so even the only instance does not conform to a
  single declared contract.
- The example patent number/title appears synthetic and has no citation, claims, source text, assignee, inventors,
  filing/publication dates, jurisdiction, family, legal status, classification, or evidence spans.
- The prose moves from functional compatibility to “one working system” (`PatentLEGO_README.md:108`) without
  engineering, safety, regulatory, patent-scope, or freedom-to-operate validation.
- No distinction exists between an asserted input/output, an NLP extraction, a reviewer correction, and a measured
  property. Absence is therefore impossible to interpret: not required, not extracted, unknown, or disputed.

These gaps are high-value acceptance tests for a clean-room implementation; they are not reasons to copy the draft's
surface vocabulary.

## Port discipline notes

The repository has no root `LICENSE`, but both files identify CC BY-SA 4.0 and the specification links the
[official Creative Commons deed](https://creativecommons.org/licenses/by-sa/4.0/) (`PatentLEGO_README.md:158-164`).
It permits copying, redistribution, and adaptation, including commercial use, provided appropriate
credit and a license link are supplied, changes are indicated, adapted material is shared under the same or a
compatible license, and no additional restrictions are imposed. The legal code also says patent and trademark rights
are not licensed; licensing an ontology about patents does not license the patents it describes.

The campaign's stricter disposition is **clean-room pattern only**. Do not vendor, translate, or mechanically port
`PatentLEGO_README.md`, `README.md`, their prose definitions, the JSON example, the purpose table, exact template
IDs/arrangement, narrative examples, or branding. Do not turn the two Markdown files into source constants or seed
data. Any direct/adapted port would require a deliberate attribution and ShareAlike distribution plan outside this
lane.

Reimplement only the abstract ideas—functional units, directional typed ports, contextual facets, compatibility
assessments, reusable path motifs, and evidence-bearing review—from canonical patent/data standards and independently
authored schemas, names, examples, fixtures, and documentation. Keep this repo as an external research citation and
comparison target. The README's broad statement that a tool built “on this ontology” inherits openness
(`README.md:45-51`) is not a substitute for artifact-specific license review; this distillate is not legal advice.

## Beep-relevance hooks

- **semantic-foundation SKOS / `@beep/ontology`:** independently author separate schemes for function, resource kind,
  energy role, operating scale, and technical domain; use stable concept IDs, labels, definitions, provenance, and
  reviewed mappings instead of mnemonic strings or a single mixed hierarchy.
- **Epistemic slice:** represent each extracted function, port, constraint, and compatibility edge as a claim with
  patent-text evidence, extractor/reviewer identity, method version, confidence rubric, status history, and explicit
  `unknown`/`disputed`; never let `community_reviewed` erase disagreement.
- **Patent tooling:** add a `FunctionalUnit` view beside publication/family/claim/embodiment entities, with typed
  input/output ports and a compatibility assessment that emits satisfied, violated, and missing constraints. Compose
  systems from assessed edges without implying novelty, enablement, validity, infringement, or freedom to operate.
- **Gov-legal data drivers:** derive candidate units from authoritative patent XML/text while preserving office IDs,
  document kind, family, claims, classifications, legal events, source spans, acquisition/version metadata, and
  rejected/quarantined extractions; keep free-text engineering specifications as evidence until normalized safely.
- **OIP practice:** review each proposed system path as an auditable hypothesis: why every edge matched, which
  constraints remain unknown, active-rights and licensing caveats, safety/regulatory gates, reviewer decisions, and
  the source snapshot. Treat system templates as saved graph queries, not solution claims.
