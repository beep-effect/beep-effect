## What this repo actually is

This is the `develop`-branch source tree for Common Core Ontologies (CCO), inspected at commit `010c99847a856e2fb70eb1b1b1287d19556c9290` (2026-06-29). It is an
OWL 2/BFO 2020-aligned mid-level ontology suite, not a patent ontology and not a populated knowledge graph.

The eleven modules provide reusable upper-domain vocabulary for agents, artifacts, currency, events, facilities, geospatial entities, information entities,
qualities, time, units, and extended relations. Domain ontologies are expected to extend these modules rather than place patent-specific classes into CCO
itself. A case-insensitive search of the modules, merged files, and user-guide text found no `patent`, `inventor`, `invention`, `patent application`, or
`patent claim` term.

The checked-in modules identify themselves as Version 2.1 with version IRIs dated 2026-04-04. `README.md` also says structural modernization is underway toward
3.0 and 4.0, including planned GeoSPARQL, QUDT, information-model, multilingual-overlay, and design-pattern changes. Treat this snapshot as a moving,
pre-modernization substrate rather than a stable patent-domain contract.

## Extractable gold

### 1. Modules are authored once and distributed in import and flattened forms

- `src/cco-modules/*.ttl` contains the eleven source modules; each imports BFO and only the CCO dependencies it needs. The XML catalog at
  `src/cco-modules/catalog-v001.xml` resolves public ontology IRIs to local files, including a pinned local `src/cco-imports/bfo-core.ttl`.
- `src/cco-merged/AllCoreOntology.ttl` is only an import façade. Its own comment says it contains no unique content and “should not be added to”; six direct
  imports transitively reach all eleven modules. This is the clean extension entry point.
- `src/cco-merged/CommonCoreOntologiesMerged.ttl` collapses the same closure plus BFO into one release artifact for consumers that cannot manage imports.
  Preserve the separation between authored modules, import façade, and generated merge.
- The 2019 `documentation/user-guides/CCO Getting Started Guide.docx` says AllCore excludes the Currency Unit Ontology, but the current AllCore file directly
  imports it. The live ontology is authoritative; do not port the old guide's import inventory.

### 2. Stable opaque identifiers carry human semantics and module ownership

- Across `src/cco-modules/*.ttl`, canonical term IRIs use `https://www.commoncoreontologies.org/ont########`; meaning lives in `rdfs:label`, `skos:definition`,
  `skos:altLabel`, examples, scope notes, and sources rather than in the IRI.
- `src/cco-modules/ExtendedRelationOntology.ttl` defines `cco:ont00001760` as `is curated in ontology`, linking every term to its owning module. It also defines
  `definition source`, `doctrinal source`, `doctrinal definition`, `doctrinal label`, `term editor`, and measurement-annotation subproperties. That is a
  concrete provenance vocabulary, not just prose.
- Load-bearing shape from `AgentOntology.ttl`:

  ```turtle
  cco:ont00001017 rdf:type owl:Class ;
                   rdfs:subClassOf obo:BFO_0000040 ;
                   rdfs:label "Agent"@en ;
                   skos:definition "A Material Entity that bears an Agent Capability."@en .
  ```

- `scripts/generate_cco_iris.py` turns the merged ontology into one Turtle document per canonical IRI via ROBOT `filter` + `annotate`, with parallel workers and
  generator-version normalization. The pattern supports dereferenceable term pages without making labels part of stable identity.

### 3. Information content, its subject, and its carrier are deliberately separate

- `src/cco-modules/InformationEntityOntology.ttl` defines Information Content Entity (ICE) as a BFO generically dependent continuant that `is about` some entity
  and depends on an information bearing entity. It then separates three load-bearing branches: `Designative ICE --designates--> entity`,
  `Descriptive ICE --describes--> entity`, and `Prescriptive ICE --prescribes--> entity`. Designative ICE is explicitly disjoint with the descriptive and
  prescriptive branches.
- The same module provides `Non-Name Identifier`, `Code Identifier`, `Legal Name`, `Date Identifier`, `Document Content Entity`, `Document Field Content`,
  `Form Document`, `Report`, `Spreadsheet`, and inverse relation pairs such as `designates/designated by`, `describes/described by`, and
  `prescribes/prescribed by`.
- `src/cco-modules/ArtifactOntology.ttl` keeps the physical/digital carrier distinct: `Information Bearing Artifact` carries an ICE;
  `Material Copy of a Document` is such a carrier constrained to carry a `Document Content Entity`. A patent record should therefore not collapse the
  legal/informational content, PDF/XML rendition, and byte/file carrier into one node.
- `Legal Instrument` is modeled as a `Material Artifact`, while `Document Content Entity` is an ICE. That commitment is useful but too coarse for born-digital
  patent records; adopt the content/carrier distinction, then define patent-domain content classes rather than equating every patent document with CCO's
  material `Legal Instrument`.

### 4. Patent-adjacent agent, regulation, and event vocabulary is unusually concrete

- `src/cco-modules/AgentOntology.ttl` supplies `Agent`, `Person`, `Organization`, `Commercial Organization`, `Government`, `Authority Role`,
  `Organization Member Role`, and the inverse `has organizational context/is organizational context of` pair. Organization is a Group of Agents able to bear
  roles, have members, and have organization rules.
- The same module models a deontic core around `Process Regulation`, with subclasses `Process Requirement` (alternative labels `Duty`, `Obligation`) and
  `Process Prohibition`; relations `requires`, `prohibits`, and `permits` are subproperties of `prescribes`, each with an inverse. This is process-centered
  normativity, not a full rule/exception/violation ontology.
- `src/cco-modules/EventOntology.ttl` provides `Planned Act`, `Act of Communication`, speech-act branches (directive, commissive, declarative, representative,
  deceptive), `Act of Publishing`, `Act of Issuing`, `Act of Official Documentation`, and `Act of Employment`.
- Two classes map directly to patent lifecycle events: `Act of Assignment` transfers rights from assignor to assignee, often under contract; `Act of Ownership`
  explicitly scopes owned property to objects, land, real estate, or intellectual property. These are valuable superclasses for patent assignment and
  patent-right holding events, but they do not encode jurisdiction, effective dates, recordation, shares, claim scope, or chain-of-title evidence.
- `src/cco-modules/ArtifactOntology.ttl` adds `Artifact Design`, a Prescriptive ICE that specifies an object under goals, environment, components, requirements,
  and constraints. This is a strong superclass/pattern for invention disclosures or claimed technical designs, not a substitute for patent claims or claim
  construction.

### 5. Measurement and epistemic-quality distinctions should be ported as a pattern

- `src/cco-modules/InformationEntityOntology.ttl` distinguishes nominal, ordinal, interval, and ratio Measurement ICEs, connected by `is a measurement of` and
  `uses measurement unit`. `UnitsOfMeasureOntology.ttl` then supplies 28 unit categories and 141 unit individuals; `CurrencyUnitOntology.ttl` supplies 128
  currency individuals under Measurement Unit of Currency.
- The epistemically useful split is explicit: `Veracity Measurement ICE` measures how a description conforms to reality; `Reliability Measurement ICE` measures
  repeatable production of an outcome; `Deviation Measurement ICE` measures reality against an expectation, prescription, or prediction;
  `Probability Measurement ICE` measures likelihood in context. This prevents a single overloaded “confidence” field from mixing truth, process reliability,
  conformance, and probability.
- Seven generic literal properties—boolean, text, datetime, URI, decimal, double, and integer value—are `owl:deprecated true` in the current module because
  their predicates add no domain semantics. `has date value` remains. Older guide examples that attach a generic `"1250"` value are therefore stale; define
  specific patent-domain datatype properties or value objects.

### 6. Time, space, and state change form a usable filing/prosecution substrate

- `src/cco-modules/TimeOntology.ttl` implements Allen-style interval relations: starts/started-by, finishes/finished-by, before/after, meets/met-by,
  overlaps/overlapped-by, contains/contained-by, during, equals, and disjoint, plus process first/last instants and calendar interval classes.
- `src/cco-modules/EventOntology.ttl` distinguishes `Change` from `Stasis`; Stasis is a process in which independent continuants endure unchanged. Its
  gain/loss/increase/decrease and role/function/quality stasis families can type prosecution-status intervals without treating status text as the real-world
  process itself.
- `src/cco-modules/GeospatialOntology.ttl` supplies regions, positions, bounding boxes, tracks, topology relations, coordinates, and WKT. `FacilityOntology.ttl`
  supplies facility subclasses. This can anchor offices, assignee sites, courts, and territorial events, but the modernization roadmap says GeoSPARQL alignment
  is still forthcoming.

### 7. The quality/release system is itself portable

- `.github/deployment/sparql/` contains 31 executable QC queries. Concrete shapes check canonical `ont########` IRIs, duplicate numeric IDs across namespaces,
  exactly one label per language, English definitions, module ownership, BFO superclass reachability via `rdfs:subClassOf+`, circularity, duplicate
  declarations, deprecated references, and temporal property domain/range.
- `Makefile` applies a useful sequence per module: merge the XML-catalog-resolved import closure, reason with HermiT, then run ROBOT verification; it repeats
  reasoning and verification after merging all modules. `scripts/release.sh` adds BFO-upstream and module diffs, OWL-DL validation, CCOM/MRO builds, manual
  review gates, and version stamping.
- The modal-relation build is a reusable projection pipeline: merge CCO+BFO+extensions; recursively retain property annotations and blank-node domain/range
  expressions in `scripts/mro_extract.py`; generate old-to-new IRIs with `scripts/mro_rename.sparql`; ROBOT-rename; then normalize ownership, roots, external
  class declarations, whitespace, and ontology headers in `mro_postprocess.py`.
- Do not copy enforcement claims blindly. `test-*`/`verify` currently use `--fail-on-violation false || true`, so SPARQL findings are advisory. Also,
  `no_multiple_parents.sparql` says “at most one” but its `HAVING` clause flags only counts above two. Port the query inventory and orchestration, then make
  severity and thresholds executable.

### 8. The promised design-pattern library is not actually present here

- `documentation/user-guides/design-patterns/README.md` promises each entry will contain a Mermaid graph, visualization, competency questions, and a SPARQL
  query. In this checkout that directory contains only the README; there are no pattern entries to extract or vendor.
- `documentation/user-guides/Common Core Ontologies 2024.pdf` does describe three real patterns: space/time tracking, information-content/carrier/design, and
  measurement-linked stasis. These are explanatory prose and figures, not machine-checkable example graphs. The paper itself notes that its patterns are complex
  and identifies smaller repeatable chunks for simple datums such as vehicle weight, person name, and geospatial identifiers.

## Port discipline notes

BSD-3-Clause permits copying, modification, source/binary redistribution, and commercial use of CCO-owned ontology, query, and tooling content. A port must
retain the 2017 CUBRC copyright notice, the three license conditions, and disclaimer; binary distributions must reproduce them in supplied documentation. CUBRC
and contributor names may not be used to endorse the port.

Porting term IRIs, labels, definitions, axioms, QC queries, or scripts is allowed with that attribution. Preserve `definition source` and
`is curated in ontology` metadata where terms are ported; they are part of the provenance contract, not decorative annotations.

Do **not** vendor `src/cco-merged/CommonCoreOntologiesMerged.ttl` as BSD-only content: it embeds `src/cco-imports/bfo-core.ttl`, whose ontology header declares
CC BY 4.0. Either depend on BFO, vendor it with its separate attribution/license compliance, or port only CCO-owned terms against an existing BFO dependency.
Likewise, external pages, standards, and images merely cited by `definition source` are not relicensed by those citations and must not be copied on that basis.

Because `develop` is mid-modernization, pin the source commit and record a mapping from imported CCO IRIs to Beep symbols. Do not silently mirror future 3.0/4.0
changes into persisted Beep data.

## Beep-relevance hooks

- **semantic-foundation SKOS / `@beep/ontology`:** port the opaque-IRI + `rdfs:label` + `skos:definition` + module-curation metadata contract, with module
  source and source-version as first-class provenance; generate convenient labels without making them identifiers.
- **epistemic slice:** model veracity, reliability, deviation, and probability as separate typed measurements attached to the described entity, method/process,
  expectation, and evidence source; never flatten them into one confidence number.
- **patent tooling:** create a CCO-aligned patent extension rooted in Document Content Entity, Information Bearing Artifact, Artifact Design,
  Agent/Organization/Role, Act of Assignment, Act of Ownership, Publishing/Issuing, and Process Regulation; add patent, application, claim, inventor, assignee,
  priority, prosecution, and jurisdiction terms locally.
- **gov-legal data drivers:** normalize governments/offices, delimiting domains, legal names, dates, locations, and `requires/prohibits/permits` inverse pairs
  at ingestion; retain source identifiers as Designative ICEs and source records as carriers of separately modeled content.
- **OIP practice:** adopt module source + import façade + generated merge, catalog-pinned imports, parse/reason/validate before SPARQL contract checks, and
  version-stamped releases; change the CCO advisory checks into failing gates and regression-test every imported threshold.

## Extraction confidence

**High for ontology and tooling facts.** All eleven Turtle modules, both merged forms, the XML catalog, 31 SPARQL checks, Make/release scripts, MRO projection
scripts, license, citation metadata, and current README were read. The Turtle was fully parsed with N3 rather than sampled for counts and hierarchies. The
DOCX/PPTX guides were unzipped and XML-extracted; the PDF was text-extracted.

**Medium for intended design-pattern guidance.** The narrative guides are readable but span 2016, 2019, 2024, and 2026-era artifacts and demonstrably drift from
current source. The promised pattern directory has no actual entries. No ROBOT/HermiT release run was performed, so this extraction confirms pipeline code and
parseability, not a fresh consistency/QC pass.
