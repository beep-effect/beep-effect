## What this repo actually is

`Legal-Ontology-Learning` is a small, script-driven 2019 experiment for inducing candidate lexical/topic structure
from United States case-opinion text. The inspected checkout is commit `575e08d12545bdaec579c17b66589d04cf51435e`
on `master`. Its README is only a title and the sentence
“Ontology learning project on legal domain”; the executable design has to be reconstructed from the source.

The real pipeline is: load JSON Lines case records -> extract an XML-like opinion segment -> replace named entities
with entity-type tokens -> normalize words -> select terms by TF-IDF and document frequency -> learn LDA/LSI topics
-> embed and hierarchically cluster topic vectors -> inspect dendrograms, PCA, coherence, and cluster scores.

It is not an ontology repository or a knowledge-graph implementation. The tracked tree contains no OWL, RDF, SKOS,
SPARQL, SHACL, spreadsheet, corpus, trained model, cluster assignment, or generated vocabulary artifact. `src/data/`
and `src/visual/` are ignored by `.gitignore:203-205`; neither exists. Tests and `setup.py` are empty.

“Ontology” therefore describes an intended downstream use of unsupervised clusters, not a delivered formal model.
The code stops before concept naming, synonym adjudication, relation assertion, axiom induction, expert validation,
or serialization. That boundary is central to what can safely be taken from this source.

## Extractable gold

### 1. A concrete legal-text-to-candidate-concepts stage graph

- `src/data_loading.py:7-31` defines the first artifact boundary: newline-delimited JSON is loaded into a DataFrame;
  each `casebody.data` is normalized, and its token list is pickled as `data/case_documents_5000.data`.
- `src/evaluation.py:11-39` shuffles a processed 20,000-document corpus, persists 18,000 training and the remainder
  test documents, and saves one shared Gensim dictionary.
- `src/topic_model.py:11-45`, `src/topics_clustering.py:17-23,64-80,132-140`, and
  `src/clusters_evaluation.py:13-37` form a model -> terms -> vectors -> hierarchy -> intrinsic-score chain. Reproduce
  this separation as typed, provenance-bearing artifacts rather than Python pickles.
- The reusable pattern is a proposal pipeline: every stage emits candidates and evidence for the next stage;
  none of its statistical output should silently become an ontology assertion.

### 2. Legal opinion isolation plus named-entity abstraction

- `src/preprocess.py:15-19` keeps only text after the first literal `<opinion ` marker and returns an empty
  string when the marker is absent. This is a brittle parser, but it captures an important legal-driver rule:
  choose the legally relevant document section before learning vocabulary.
- `src/preprocess.py:27-43` replaces every spaCy-recognized mention with its type label, so entities contribute
  category tokens rather than proper nouns. This aids concept induction and privacy reduction if the original span
  and abstraction provenance remain available outside the learner.
- `src/preprocess.py:57-149` then applies NFKD-to-ASCII conversion, lowercase, punctuation deletion, numeric
  replacement with `_number_`, English stop-word removal, and WordNet lemmatization using a per-token inferred
  part of speech. The exact order is part of the experiment contract because it changes the learned vocabulary.
- Do not port the literal implementation unchanged: the medium spaCy model is loaded once per document,
  `ent.merge()` uses an obsolete spaCy API, and absent opinions become empty documents without a typed reason.

### 3. Two complementary salience filters

- `src/data_preparation.py:32-62` ranks each document's TF-IDF term IDs, selects `int(term_count * threshold)`, then
  preserves selected terms in original order. LDA retains 60% (`src/topic_model.py:17,109`).
- `src/data_preparation.py:7-25` separately counts document frequency once per token type and retains a token
  only under this strict interval:

  ```python
  N * lower_limit < document_frequency[token] < N * upper_limit
  ```

- LDA and embedding paths use `(0.03, 1.0)`, removing terms present in 3% or fewer documents and also terms in
  every document (`src/topic_model.py:18`; `src/topics_clustering.py:70-71`). The LSI path deliberately uses the
  narrower `(0.15, 0.60)` band (`src/topic_model.py:54`).
- The portable gold is the distinction between **within-document salience** and **across-corpus prevalence**.
  Record both thresholds with the corpus snapshot; do not collapse them into an unexplained “keyword” flag.
- A short document can retain zero terms because the selected count is floored. Empty documents and vocabulary
  loss therefore need explicit metrics and fail/skip semantics in a production port.

### 4. Flat topic discovery with a hierarchy-oriented handoff

- `src/topic_model.py:23-43` trains Gensim LDA over the TF-IDF-weighted corpus with symmetric alpha, `eta=0.3`,
  one pass, online updates, 50 iterations, and a 0.01 minimum topic probability. It returns the model, corpus,
  and dictionary as one handoff tuple.
- `src/topic_model.py:48-70` provides LSI/SVD as an alternate flat latent-space model, using five-item chunks, one
  pass, ten power iterations, and 100 extra samples. LSI naturally consumes TF-IDF, whereas feeding TF-IDF weights
  to probabilistic LDA is a modeling choice to test, not inherit as doctrine.
- `src/topic_model.py:95-125` sweeps topic counts from `start` to but excluding `limit` and computes UMass
  coherence. The example range is 2 through 14 (`src/topic_model.py:137-149`). `src/evaluation.py:42-66` adds a
  held-out corpus-bound path and a test-corpus UMass path.
- `src/topic_model.py:73-78,81-92` emits pyLDAvis HTML and top-term probability bar charts. These are review
  surfaces, not machine-readable ontology results.
- No random seed is set in LDA or train/test shuffling, so scores and candidate topics are not reproducible as
  written. A port needs corpus/model fingerprints, seeds, parameters, and deterministic candidate IDs.

### 5. Topic-to-vector transformation exposes three hypotheses

- `src/topics_clustering.py:17-23` takes each LDA topic's top 30 terms, sorts topics by first-term probability,
  and drops all probabilities. The load-bearing shape is:

  ```python
  topic_words = [[word[0] for word in topic[1]] for topic in topics]
  ```

- `src/topics_clustering.py:64-80` trains a 100-dimensional Word2Vec model on the same filtered legal corpus
  (`window=10`, `min_count=1`) and represents each topic by the unweighted mean of its available term vectors.
  This turns lexical overlap/distributional similarity into a clusterable topic representation.
- `src/topics_clustering.py:103-126` offers the same unweighted-mean representation using an external GloVe
  text file. `src/topics_clustering.py:83-100` offers Doc2Vec inference as a third hypothesis.
- Preserve the hypothesis comparison, not the implementations: LDA term weights are discarded; broad exception
  handlers hide missing vocabulary; zero matched words cause division by zero; and the Doc2Vec branch joins each
  token list into a string before constructing `TaggedDocument`, so it risks training over characters rather
  than word-token sequences.
- The printed “words found” count (`src/topics_clustering.py:42,59`) is a primitive but valuable coverage metric.
  Promote it to a required structured field per candidate topic.

### 6. Hierarchy induction is geometric, not ontological

- `src/topics_clustering.py:132-140` applies SciPy hierarchical linkage to topic vectors with Euclidean distance
  and a caller-selected method; the active example uses Ward linkage and renders a dendrogram
  (`src/topics_clustering.py:176-177`).
- `src/clusters_evaluation.py:13-37` evaluates K-Means or agglomerative assignments using Euclidean silhouette
  score and includes a Calinski-Harabaz function. The active experiment tries Ward, complete, average, and single
  linkage for two, three, and four clusters over five LDA topics (`src/clusters_evaluation.py:92-98`).
- `src/clusters_evaluation.py:40-50` projects topic vectors into three PCA dimensions for inspection; the
  Word2Vec/GloVe comparison at lines 53-64 uses the same visual surface for both embedding hypotheses.
- `src/h-lda.py:7-56` is a second, genuinely hierarchical discovery branch: it converts filtered tokens to
  integer sequences and runs three-level hierarchical LDA with `alpha=10`, `gamma=1`, `eta=1`, seed 0, and 100
  samples. It prints topics but does not persist the tree.
- `src/words_clustering.py:12-68` also clusters every retained corpus word into four Ward clusters and sweeps
  silhouette scores. This supplies a lexical-cluster baseline distinct from clustering topic centroids.
- A dendrogram edge says “close under this representation and linkage,” not `skos:broader` or subclass. Any
  ontology port needs a separate, reviewable relation-proposal stage with evidence and rejection reasons.

### 7. Evaluation is usefully stratified but empirically incomplete

- Topic-count evaluation uses UMass coherence and a held-out model bound (`src/evaluation.py:42-66`); cluster
  evaluation uses silhouette and Calinski-style dispersion (`src/clusters_evaluation.py:13-37`); PCA and
  pyLDAvis provide human inspection. Those are distinct metric families and should remain distinct.
- The functions print or plot results rather than returning a versioned evaluation record. There are no checked-in
  scores, expected values, corpus statistics, expert labels, competency questions, or regression fixtures.
- `calinski_harabaz_score`, agglomerative `affinity=`, Word2Vec `size=`, and `pyLDAvis.gensim` are legacy APIs.
  `requirements.txt` pins nothing and omits imported `contractions`, `inflect`, SciPy, and model/data setup.
- The clean extraction is an evaluation matrix: stage, candidate family, intrinsic metric, human judgment,
  accepted/rejected/unknown result, method version, corpus snapshot, and evidence artifact.

### 8. The referenced corpus and outputs are specifications, not extractable datasets

- `src/data_loading.py:34-37` references `data/Arkansas-20181204-xml/data/data.json`; code inspection establishes
  only JSON Lines, a nested `casebody.data` field, and XML-like opinion markup. The repository does not document
  the dataset's producer, download URL, license, record count, schema version, or checksum.
- Other absent inputs are `case_documents_5000.data`, `case_documents_20000.data`, `train_corpus.data`,
  `test_corpus.data`, `common_dictionary.data`, and GloVe 6B 100d/200d files. Absent outputs include the pyLDAvis
  HTML, topic plots, PCA plots, dendrograms, models, term lists, and assignments.
- Consequently there are no actual learned legal classes, term hierarchies, or evaluation results to port. The
  paths are useful for reconstructing artifact roles only; they are not evidence that those artifacts are
  redistributable or reproducible.

## Port discipline notes

The root `LICENSE` is MIT, copyright 2019 Sunghun Jung. It permits use, copying, modification, merging, publication,
distribution, sublicensing, and sale. A substantial code port must retain the copyright, permission notice, and
disclaimer. Record source and commit beside ported stages so attribution survives generated artifacts.

The pipeline shapes, thresholds, and artifact-boundary ideas may be reimplemented; direct code copying is also
allowed with attribution. Prefer a modern schema-first reimplementation because the original APIs, silent failure
modes, untyped pickles, and nondeterminism are material liabilities.

Do **not** vendor the Arkansas case JSON, derived pickles, GloVe files, spaCy model, NLTK corpora, or generated
visuals under the repository's MIT license. None is present, and the repository does not establish rights for
them. Clear and record each upstream dataset/model license separately. `src/preprocess.py:12` also credits an
external preprocessing walkthrough; verify that source before copying substantial preprocessing code verbatim.

## Beep-relevance hooks

- **semantic-foundation SKOS / `@beep/ontology`:** turn each induced topic or lexical cluster into a versioned
  `ConceptCandidate`, with proposed labels, weighted supporting terms, corpus spans, vector coverage, and a
  review state; only accepted candidates graduate to SKOS concepts or `broader`/`related` assertions.
- **epistemic slice:** represent every topic, cluster, and proposed parent edge as a claim whose evidence records
  corpus snapshot, preprocessing recipe, model/embedding/linkage parameters, seeds, metric family, score, and
  human adjudication. Model missing source data or zero embedding coverage as `unknown`, not low confidence.
- **patent tooling:** run section-aware candidate discovery separately over claims, specification, abstract, and
  prosecution text; compare LSI, flat-topic-plus-linkage, and hierarchical-topic branches, then route candidates
  through examiner/practitioner review before mapping them to CPC or patent-domain vocabulary.
- **gov-legal data drivers:** build a typed adapter for JSONL plus embedded opinion markup that preserves record,
  court/jurisdiction, section, source span, and source-license provenance while emitting both original mentions
  and deterministic NER abstractions. Reject or quarantine absent/malformed opinion sections explicitly.
- **OIP practice:** make the pipeline a reproducible candidate-generation lane with immutable stage artifacts,
  structured coverage/quality reports, intrinsic-metric separation, expert-review gates, and golden fixtures;
  never let a visualization or favorable silhouette score serve as ontology publication proof.
