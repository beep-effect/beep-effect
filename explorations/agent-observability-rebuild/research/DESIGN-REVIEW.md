# Design review of BRIEF.md

2026-10-28 UTC. Reviewed the proposed brief against the packet's source/deployment/independent audits, sanitized Phoenix aggregate evidence and `standards/architecture/12-observability.md`. No new broad research, live queries, source edits or project changes. Only this report was authored.

## Verdict

**Acceptable direction for a bounded first implementation design, after the corrections below; not yet a complete implementation specification or production rollout approval.** The brief correctly separates unknown coverage from zero activity, preserves the recovery hold, avoids invented outcome judgments, treats native and reconstructed identity carefully, and reuses existing tooling/driver boundaries. A one-host, one-repository, CLI-plus-desktop slice with five reviewed examples is useful if the precise two surfaces and available signal capabilities are named before admission. Seven-harness expansion should remain a staged requirement, not an inferred capability of this first slice.

## Conditional project deletion request

The operator requested investigating `default` and `beep-agent-effectiveness` and removing them **if `harness-otel` is the only one used** (`CAPTURE.md:19`). That condition is not currently satisfied by “only one project contains real harness traces.”

- `default` has an active deployment-probe producer: the Phoenix Ansible role posts `ansible-phoenix-health` without an explicit project. The live parent evidence identifies the canary there. Deletion without rerouting the producer can recreate the project or break expectations. Migrate the canary destination in the owning dankserver contract first, then verify behavior and references.
- `beep-agent-effectiveness` has an implemented derived-export purpose, but **“its empty state is a failed/missing derived feed” (`BRIEF.md:104`) is too categorical**. Empty means no retained records in the queried project/window; an intentionally held producer, disabled schedule, wrong destination, never-run writer or retention can yield that state. The independent audit proves the local scheduled derived path is masked/held, not that a currently running writer failed. Name the implemented owner and whether its future purpose is retained or superseded before deciding retirement.
- No deletion is needed for this first slice. Preserve the user's conditional cleanup intent and record a concrete retire-or-retain decision after producer migration/ownership resolution. A bounded export where data exists and verified deletion/reference semantics are sensible recovery steps; do not manufacture an additional permission requirement for deletion already covered by the user's explicit condition. The present obstacle is the unmet factual condition and remaining design decision.

## First-slice acceptance

Accept the first slice when two named routes produce sanitized, versioned metadata with source/session/run identity and declared signal limits; every fixture event has a reconciled terminal or pending state; restart/retry/copy/rotation fixtures show bounded loss-free replay within the promised durability horizon; and one known token/cache fixture yields correct Phoenix values without treating absence as zero. Show unknown timing/outcomes explicitly. Demonstrate one human annotation and one version-pinned five-example dataset projection against a disposable backend, with no automatic acceptance judgment or broad performance claim.

The first implementation may defer sophisticated critical-path analytics, a 10–20-case experiment, all seven harness adapters and project deletion. It must not defer correct timestamps, cross-root attribution, privacy enforcement, deterministic event identities, explicit receipt semantics or visible collection failure. These are the foundations that make later measurements interpretable.
