## Sources and boundaries

1. `packages/tooling/library/ai-metrics/src/models.ts:122-142`: the transcript source domain is precisely `codex`, `claude`, `openclaw`. `ingest.ts:137-159` dispatches only those sources. `internal/transcript-utils.ts:56-67` resolves the Claude/Codex source roots; `forwarder.ts:1317-1343` performs actual selection.
2. `packages/tooling/library/ai-metrics/src/hook-pulse.ts:219-232`: hook kinds include `claude-code`, `codex-cli`, `cursor-cli`. `forwarder.ts:1577-1583` maps transcript sources only to Claude Code/Codex CLI; OpenClaw has no hook mapping and Cursor has no transcript source. Hook support and transcript-forwarder support therefore differ.
3. `packages/tooling/library/ai-metrics/src/AiMetrics.instruments.ts:49-59`, `87-91`: the attribute vocabulary includes Claude/Codex/Cursor/Grok/Muse/Junie and providers including Meta/JetBrains. The targeted source search found this declaration/catalog vocabulary, not a matching full set of producer adapters. An enum entry is not collection proof.
4. `packages/drivers/ai-provider-cli/src/AiProviderCliSession.stdio.service.ts:88-92`, `217-248` implement native launch/protocol negotiation for Codex/Cursor/Grok; its wire schemas verify model/session responses (`AiProviderCliSession.wire.models.ts:150`, `174`, `257`). This driver is distinct from metrics ingestion. `AiProviderCliSession.profile.service.ts:29-44` allows only HOME/PATH and optionally CODEX_HOME in its managed launch environment; do not assume arbitrary parent OTEL flags propagate into these managed sessions.
5. Local launcher inspection: `~/.local/bin/claude`, `codex`, and `grok` resolve to native binaries; `cursor-agent` is a small launcher whose lines 32-35 exec its Node entry. `~/.local/bin/muse:1123` execs the selected binary; `~/.local/bin/junie:678`, `855` do likewise. Targeted text searches found no OTEL/telemetry enable injection in the inspected Muse/Junie/Cursor launchers. This excludes aliases/functions and separate shell sourcing, which the fleet audit must establish. `claudem` did not resolve through `command -v` in this noninteractive shell; that does not establish absence from interactive shell functions.

## Native producer fields versus Phoenix projection semantics

The transcript exporter creates its own semantic layer. It must be kept distinguishable from native harness emission:

- Claude transcript summaries retain a bounded event type and optional timestamp (`ingest.ts:108-119`); Claude privacy attribution hashes the file path as session identity and derives primary/subagent role from path (`privacy.ts:678-682`). The forwarder separately reads native `sessionId` for hook binding (`forwarder.ts:103-143`). The exported session ID is consequently not simply the original Claude session ID.
- Codex attribution reads `session_meta` payload ID, optional parent session/thread/fork data and explicit subagent role/nickname (`privacy.ts:564-620`, `684-701`). Those fields can support lineage; they do not identify whether CLI or desktop initiated the run. No inference from model-looking filenames is justified.
- OTLP trace/session span IDs are deterministic derivatives of source kind, source role and source path hash (`otlp.ts:540-555`). Phoenix `session.id` is the metrics `agentSessionId` (`562-587`, `594-628`). A Phoenix session here means a path-bound metrics session, not guaranteed native conversation/task identity.
- The exporter sets OpenInference `AGENT`, `TOOL`, `LLM`, `CHAIN` categories from its own projection and event-name heuristics (`otlp.ts:438-470`, `562-628`). It does not preserve measured native invocation semantics by virtue of those category names.
- The live sender gives spans export-time start/end with zero duration (`otlp.ts:821-854`, `890-898`), while original event time is only an attribute. This is not native request latency or work elapsed time.
- Provider is deliberately `unknown` for Claude and Codex projections (`otlp.ts:438-443`). Thus a Claude Code transcript passing through a proxy cannot establish Anthropic, Meta Muse, or another upstream provider in Phoenix.

Repository source alone cannot identify the initiating desktop application. The subsequent server-side [safe producer sample](./phoenix-safe-producer-sample.json) supplies positive self-reported runtime evidence: among the latest 300 spans, 291 carry `service.name=claude-code-desktop`, `terminal.type=non-interactive`, and `claude.deployment_mode=1p`; the other nine have terminal type `ghostty` without a service name in that sample. All 300 report `llm.provider=anthropic`; model fields occur on a subset (73 Opus 5.5, six Haiku 5.5). This is a convenience sample, not a random sample, seven-day census, independently authenticated application identity, or end-to-end completeness proof. It supports presence of a Claude Code desktop runtime while leaving ordinary Claude Desktop chats and Cowork coverage unresolved. A controlled canary plus explicit launcher/surface correlation is still needed for completeness claims. Native logs, metrics and traces may also be different signal types; their conversion into Phoenix traces must be established from the collector pipeline rather than assumed.

### Why model names can appear while Phoenix token counters are blank

The separate [attribute-key convenience sample](./phoenix-attribute-key-sample.json) includes 31 `claude_code.llm_request` spans with native `model`, `input_tokens`, `output_tokens`, `cache_read_tokens`, and `cache_creation_tokens` fields; the same sample includes `llm.model_name` on those 31 spans. No `llm.token_count.*` keys appear in that inspected sample. The coordinating collector audit reports no mapping from the native token fields into those OpenInference token-count keys. The supported inference is a semantic mapping gap: model attribution reaches the field Phoenix recognizes while native token counters remain under different names. Blank Phoenix token aggregates therefore do not establish absence of native token data. Verify the mapping with a synthetic request and define cache-token accounting explicitly before enabling a repair; do not assume native input totals and cached totals can simply be added. These counts describe only the inspected 100-span attribute sample and must not be extrapolated to the full project.

Codex configuration evidence should be reported with its exact signal setting: an exporter set to `none` is not interchangeable with a claim about a separately named trace exporter. This implementation report makes no native Codex tracing-disabled claim; the host audit owns that signal-specific configuration determination.

## Who owns `beep-agent-effectiveness`?

It has an explicit implemented owner, not just an unused prospective name:

- `agent-effectiveness.ts:1456-1484` defines it as the dedicated project for the repo-owned effectiveness loop, including dataset/prompt/experiment bundles.
- Builders stamp it into outputs (`agent-effectiveness.ts:3815`, `3851`, `4020`).
- Current OTLP sender independently defaults `openinference.project.name` to that same project (`otlp.ts:792-813`). Its comments describe prior accidental writes to `default` alongside a separate coding-harness fan-out. Those comments record intent/history, not current service proof.

An empty project therefore cannot be dismissed as intentionally unused based on repository implementation. It could mean no derived export has been delivered, an older checkout is deployed, a route override directs data elsewhere, retention/window filters hide records, or another condition. Which explanation applies requires sanitized installed configuration plus backend receipt evidence. It is also possible for raw/native harness telemetry to populate another project while this derived pipeline remains empty; project totals must be classified by producer before comparison.

## Rebuild requirements implied by this audit

Keep separate fields for application surface, harness/runtime, launcher, provider route, requested model and observed model. Record explicit unknown values. Maintain a capability matrix per adapter stating which signals are supported, enabled and end-to-end proven. Correlate native IDs with path occurrences, project membership and host identity instead of collapsing them. A synthetic canary for each requested surface should prove producer creation, collector acceptance and query-visible backend arrival without containing real prompt/output text.

Graft discovery for this extension reported approximately 124,520 tokens saved; its monetary estimate was not independently verified. No tests or canary runs were executed in this extension.
