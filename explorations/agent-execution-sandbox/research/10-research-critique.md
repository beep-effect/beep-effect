## [high] Competing agent-CLI sandbox implementations are absent from the isolation slice: OpenAI Codex CLI's open-source sandboxing (Landlock+seccomp on Linux, Seatbelt on macOS, network-disabled default), Google Gemini CLI's sandbox profiles (macOS sandbox-exec profiles + Docker/Podman container mode), and the Kubernetes SIG 'agent-sandbox' project; the slice also never checks the deprecation/stability status of macOS sandbox-exec/Seatbelt, which both Anthropic's srt and any macOS local tier depend on.
The slice's build-vs-buy conclusion rests almost entirely on Anthropic's sandbox-runtime as 'the only permissively-licensed TS-native option'. Codex CLI and Gemini CLI are the two direct competitors solving the identical problem with open, inspectable implementations; their design choices and the Seatbelt-deprecation risk could change the packet-level choice of base layer and the macOS tier strategy.

## [high] No dedicated egress-enforcement prior art beyond Claude Code's own proxy docs: missing Stripe Smokescreen (the canonical open-source egress proxy with ACLs), mitmproxy/TLS-terminating MITM proxy patterns, Envoy egress-gateway policy, eBPF-based per-process network policy (Cilium, Tetragon), and DNS-as-exfiltration-channel controls (DNS filtering/logging, DoH bypass).
Destination- and purpose-aware egress is the packet's most novel requirement, and the entire external evidence base for enforcing it is a single vendor doc (code.claude.com sandboxing page) that itself admits the hostname-allowlist floor is bypassable. Whether the design needs a TLS-terminating proxy, an eBPF layer, or per-run netns routing is a packet-level architecture decision currently supported by one source; DNS exfiltration is an unaddressed hole in every domain-allowlist design surveyed.

## [high] Delegation-chain and agent-identity standards are missing from the authz slice: no RFC 8693 (OAuth 2.0 Token Exchange — the standards-track on-behalf-of/impersonation mechanism with act/may_act claims), no GNAP (RFC 9635), no IETF WIMSE working group, and none of the 2025-2026 'auth for AI agents' industry work (Auth0 for GenAI / Okta agent identity, WorkOS agent auth, OpenID Foundation AI-agent drafts).
The repo's AgentPrincipal already requires onBehalfOfUserId, and the packet's grants must name the full principal lineage (user → orchestrator → subagent). The slice covers capability tokens (Biscuit/UCAN/macaroons) but not the OAuth-ecosystem delegation standards the MCP surface (OAuth 2.1 resource servers per ext-agentsec) will interoperate with; choosing between capability-token chains and token-exchange chains is a packet-level grant-model decision made blind right now.

## [medium] A cluster of load-bearing sources was never actually fetched or license-verified, per the agents' own notes: LlamaFirewall component license, Kata Containers repo LICENSE, Wasmtime's exact license text (hedged), immudb's BUSL-1.1 change date/Additional-Use-Grant terms, mcp-injection-experiments and Romern/redactionschemes licenses, the MCP Security Best Practices page and 2025-11-25 changelog ('seen in search results, not fetched in full'), MCPTox, the Schneier-Kelsey paper, the Byun/Bertino/Li PBAC PDFs, the AICPA TSC document, and the actual FRCP 37(e) rule text.
Several of these are dispositioned as portable or cited as normative despite unverified licensing or unfetched primary text; immudb's BUSL terms and Wasmtime/Kata license exactness affect the build-vs-buy shortlist, and the MCP best-practices/changelog claims are treated as normative protocol requirements the boundary must satisfy.

## [medium] The repo has no encryption-at-rest, key-management, retention/legal-hold, or crypto-shredding seam mapped by either repo slice — and spot-checks confirm none exists (rg for kms/envelope-encryption/encrypt/legal-hold across packages/**/src yields only incidental hits such as packages/tooling/library/ai-metrics/src/retention.ts and the m365 driver token cache). The ext-ledger storage-class design (per-matter DEKs, key destruction as erasure, legal hold freezing key destruction) lands on an unmapped void, and the only credential-custody surface today — packages/drivers/onepassword-cli/src/OnePasswordCli.service.ts plus packages/shared/domain/src/values/OnePasswordReference/OnePasswordReference.model.ts — was noted only as a reference schema, not mapped as the custody seam.
The immutable-execution-record design cannot be shaped without knowing where key management and retention clocks would attach in this monorepo; if the answer is 'greenfield capability', that materially changes the records workstream's scope and its dependency ordering against the ingestion-security-secret-governance vault candidates.

## [medium] The tamper-evident-records slice omits trusted timestamping and legally recognized anchoring: RFC 3161 timestamp authorities, eIDAS (qualified) electronic timestamps, FRE 902(13)-(14) self-authentication of hash-certified electronic records, and OpenTimestamps-style public anchoring are all absent, despite the product being legal-tech whose ledger consumers include courts, auditors, and opposing counsel.
The slice's anchoring answer (tlog checkpoints + witness cosigning + S3 Object Lock) is technically sound but has no evidentiary-recognition story; RFC 3161/eIDAS timestamps are what courts and regulators already accept as proof of existence-at-time, and countersigning periodic checkpoints via a TSA is cheap. Whether the ledger anchors to witnesses, a TSA, or both shapes the records design.
