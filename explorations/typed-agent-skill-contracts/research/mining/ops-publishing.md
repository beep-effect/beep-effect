## Per-skill notes

### iodbc-dsn-manager

- What it actually does: detects `www_sv`, local ODBC configuration, or a user-supplied REST bridge and then exposes list/inspect/test operations for system and user DSNs; direct creation/editing remains prose-driven INI mutation rather than a transactional script (`iodbc-dsn-manager/SKILL.md`, `iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Mode C models a four-tab DSN wizard—data source, server type, communications, options—and distinguishes MT, Virtuoso, and Unix Lite parameter shapes (`iodbc-dsn-manager/SKILL.md`, `iodbc-dsn-manager/references/mt-dsn-parameters.md`, `iodbc-dsn-manager/references/www_sv-endpoints.md`).
- Mode B has matching Python and dependency-free Node/TypeScript JSON endpoints: `/health`, `/info`, `/dsns`, `/dsn/<name>`, `/drivers`, `/driver/<name>`, and POST `/test` (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- The bridge defaults to loopback and the launchd unit preserves that default; LAN exposure is explicitly opt-in (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`, `iodbc-dsn-manager/server/com.openlink.odbc-rest-server.plist`).
- Connectivity is a real process-level probe: it invokes `iodbctest`/`iodbctestw`, falls back to `isql`, supplies a small SQL query, imposes a 15-second timeout, and returns captured output (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Notable files worth a human read: `iodbc-dsn-manager/SKILL.md`; `iodbc-dsn-manager/server/odbc_rest_server.py`; `iodbc-dsn-manager/server/odbc_rest_server.ts`; `iodbc-dsn-manager/references/mt-dsn-parameters.md`; `iodbc-dsn-manager/references/connection-string-formats.md`; `iodbc-dsn-manager/references/odbc-error-codes.md`.
- Standout mechanism: capability routing is explicit and inspectable instead of implicit—probe interfaces in priority order, report the chosen path, and honor a user-selected override (`iodbc-dsn-manager/SKILL.md`).
- Standout mechanism: system/user configuration is reported separately, which is a useful provenance boundary when identical DSN names shadow each other (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Standout mechanism: error guidance maps SQLSTATE and driver-manager signatures to a diagnostic sequence rather than immediately rewriting config (`iodbc-dsn-manager/references/odbc-error-codes.md`).
- Weakness: the REST bridge has no authentication or authorization; when exposed on `0.0.0.0`, any reachable caller can enumerate configuration and submit arbitrary test SQL (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Weakness: passwords are embedded in child-process arguments (`DSN=...;PWD=...` or positional `isql` arguments), and the HTTP request contains them in plain JSON; loopback reduces but does not remove process-list, local-client, and log risk (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Weakness: the HTTP handlers do not cap request bodies, constrain queries to read-only SQL, attach request IDs, redact driver output, or emit an auditable operation record (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Weakness: direct INI writes have no required backup, atomic replacement, diff preview, rollback, or post-edit parse gate; “Always add to both sections” is only an instruction (`iodbc-dsn-manager/SKILL.md`).
- Weakness: the two implementations duplicate the same contract without shared conformance tests, and the TypeScript INI parser lowercases keys while section lookups remain case-sensitive (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Smell: version/scope documentation drifts—the main skill is v2 with Linux support, while the README says v1 and lists “macOS only” as a limitation (`iodbc-dsn-manager/SKILL.md`, `iodbc-dsn-manager/README.md`).

### openlink-request-broker-configurator

- What it actually does: discovers ODBC DSNs or JDBC JARs, elicits selected targets and connection parameters, then prescribes additions to alias tables, `[Environment ...]`, `[generic_...]`, and ordered `[Mapping Rules]` sections before broker reload (`openlink-request-broker-configurator/SKILL.md`).
- Its core model is an ordered seven-field policy rule, `domain:database:uid:opsys:machine:application:mode`, whose first match accepts an agent or rejects with a message (`openlink-request-broker-configurator/references/rulebook-structure.md`).
- ODBC configuration derives a normalized token, a dedicated agent section, and a specific rule inserted before the catch-all; JDBC configuration discovers SPI driver classes and assigns a JDBC slot plus `CLASSPATH` (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/odbc-dsn-examples.md`, `openlink-request-broker-configurator/references/jdbc-driver-registry.md`).
- Mode C edits through `www_sv` forms; Mode A uses line-precise direct edits and requires `inicheck` before reinitialization (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`).
- Notable files worth a human read: `openlink-request-broker-configurator/references/rulebook-structure.md`; `openlink-request-broker-configurator/SKILL.md`; `openlink-request-broker-configurator/references/odbc-dsn-examples.md`; `openlink-request-broker-configurator/references/jdbc-driver-registry.md`; `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`.
- Standout mechanism: discovery feeds an explicit selection prompt rather than mutating every discovered resource; both ODBC and JDBC wizards stop for a target set (`openlink-request-broker-configurator/SKILL.md`).
- Standout mechanism: the skill preserves rule precedence as a first-class invariant—specific generated rules must precede the generic catch-all (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/rulebook-structure.md`).
- Standout mechanism: reload and restart are separated; reinitialize is preferred because it reloads configuration while retaining connections, and a full restart requires confirmation (`openlink-request-broker-configurator/SKILL.md`).
- Standout mechanism: `RawConfigParser(strict=False, delimiters=('=',))` captures a subtle grammar constraint: colons belong to rule keys, not INI delimiters (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/rulebook-structure.md`).
- Weakness: this is largely a procedural prompt, not an implemented planner/editor; there is no script producing a typed plan, preserving comments, detecting collisions, or applying a patch atomically (`openlink-request-broker-configurator/SKILL.md`).
- Weakness: it offers a downloadable backup but does not make backup and restore a blocking precondition for direct or HTTP edits (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`).
- Weakness: credentials travel via `curl -u` command arguments over plain HTTP on port 8000, and the state-changing `brkinit` operation is documented as GET (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`).
- Weakness: success detection is string matching against HTML (“Configuration Updated” versus failure text), with no structured response schema or read-after-write semantic comparison (`openlink-request-broker-configurator/SKILL.md`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`).
- Weakness: suggesting a generated passwordless-sudo rule is disproportionate and lacks username/path validation, rollback instructions, or least-privilege policy review (`openlink-request-broker-configurator/SKILL.md`).
- Smell: the docs claim Environment sections can be managed fully but also say `www_sv` does not directly expose them, leaving the advertised Mode C surface internally inconsistent (`openlink-request-broker-configurator/README.md`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`).

### screencast-recorder

- What it actually does: elicits an ordered scene list, writes a `shot-scraper video` YAML storyboard, optionally converts RDF/Turtle to YAML, records WebM plus MP4, optionally generates and approves narration before muxing, and writes an RDF log (`screencast-recorder/SKILL.md`).
- It distinguishes “URLs recovered from prior curl work” from directly supplied browser URLs, then asks the operator to confirm ordering, labels, pauses, cursor behavior, and viewport before recording (`screencast-recorder/SKILL.md`).
- Distribution is treated as a contract: presentation HTML must embed the primary MP4, include fallback sources, use bundle-relative paths, provide POSH enclosure plus JSON-LD `VideoObject.contentUrl`, and include on-behalf-of attribution (`screencast-recorder/SKILL.md`).
- The RDF vocabulary represents the storyboard as `schema:HowTo`/`HowToStep` plus browser/host action subclasses and output metadata (`screencast-recorder/references/screencast-ontology.ttl`, `screencast-recorder/references/storyboard-schema.md`).
- Notable files worth a human read: `screencast-recorder/SKILL.md`; `screencast-recorder/references/storyboard-schema.md`; `screencast-recorder/references/screencast-ontology.ttl`; `screencast-recorder/scripts/ttl-to-yaml.py`; `screencast-recorder/scripts/yaml-to-ttl.py`; `screencast-recorder/assets/templates/minimal-storyboard.ttl`.
- Standout mechanism: human confirmation precedes a time-consuming capture, and narration approval precedes destructive muxing; the silent original is retained by default (`screencast-recorder/SKILL.md`).
- Standout mechanism: visual evidence, its executable plan, and a machine-queryable log are co-routed as one bundle rather than being scattered (`screencast-recorder/SKILL.md`, `screencast-recorder/scripts/yaml-to-ttl.py`).
- Standout mechanism: opaque iframe access is treated as an expected state to catch and skip, not an exceptional failure that aborts presentation behavior (`screencast-recorder/SKILL.md`).
- Cross-reference: artifact routing and the distribution contract are delegated to `agent-rdf-memory/howto/artifact-routing.ttl` and `agent-rdf-memory/howto/screencast-distribution-artifacts.ttl`; those files were intentionally not re-mined in this lane (`screencast-recorder/SKILL.md`, `screencast-recorder/references/common-patterns.md`).
- Weakness: the supplied Turtle templates use `sc:PauseAction`, but the converter recognizes `schema:SuspendAction` and not `sc:PauseAction`; pauses in those templates are silently dropped (`screencast-recorder/assets/templates/minimal-storyboard.ttl`, `screencast-recorder/assets/templates/server-demo-storyboard.ttl`, `screencast-recorder/scripts/ttl-to-yaml.py`).
- Weakness: action order is encoded with `schema:position` by YAML-to-TTL, but TTL-to-YAML iterates graph objects without sorting actions by that position; round trips can reorder steps within a scene (`screencast-recorder/scripts/yaml-to-ttl.py`, `screencast-recorder/scripts/ttl-to-yaml.py`).
- Weakness: there is no SHACL/schema validator or round-trip test, unknown actions are silently omitted, and the local runtime check could not execute converters because `rdflib` is not declared/installed by the prerequisite helper (`screencast-recorder/scripts/ttl-to-yaml.py`, `screencast-recorder/scripts/yaml-to-ttl.py`, `screencast-recorder/scripts/ensure-shot-scraper.sh`).
- Weakness: ontology domains say several properties apply to `schema:HowTo` while templates use them on `schema:HowToStep`, and datatype properties are marked asymmetric/irreflexive—object-property characteristics that add noise rather than useful validation (`screencast-recorder/references/screencast-ontology.ttl`, `screencast-recorder/assets/templates/server-demo-storyboard.ttl`).
- Weakness: the narrative says the default voice is `onyx`, but the actual TTS script defaults to `coral` (`screencast-recorder/SKILL.md`, `screencast-recorder/scripts/screencast-openai-voiceover.py`).
- Weakness: “verify both files exist” and two grep checks do not validate duration, dimensions, codecs, playback, narration alignment, captions, checksums, or whether recorded scenes reached asserted UI states (`screencast-recorder/SKILL.md`).
- Smell: the RDF “log” is generated from the intended storyboard, not observed browser events; without actual timestamps, outcomes, hashes, or deviations it is plan provenance, not proof of execution (`screencast-recorder/scripts/yaml-to-ttl.py`).

### pinchtab

- What it actually does: this directory is a skill/documentation wrapper around an external local Chrome daemon; it supplies CLI, HTTP, and MCP command contracts but no browser implementation (`pinchtab/SKILL.md`, `pinchtab/references/api.md`, `pinchtab/references/mcp.md`).
- The primary interaction loop is session creation, navigation plus snapshot, action against a fresh accessibility ref, then `--snap-diff` or a new snapshot to verify state (`pinchtab/SKILL.md`, `pinchtab/references/commands.md`, `pinchtab/references/agent-optimization.md`).
- Caller identity scopes the current tab: session token first, then agent ID, then a shared anonymous default; explicit tab IDs override that state (`pinchtab/references/api.md`, `pinchtab/references/env.md`, `pinchtab/references/commands.md`).
- Multi-agent controls include tab locks with owner and expiry, 409 conflict behavior, and human handoff/resume endpoints for CAPTCHA or login intervention (`pinchtab/references/api.md`).
- Evidence outputs include accessibility snapshots, readable text, screenshots, PDFs, and redacted-by-default HAR/NDJSON network exports (`pinchtab/references/api.md`, `pinchtab/references/article-collection.md`).
- Notable files worth a human read: `pinchtab/SKILL.md`; `pinchtab/references/agent-optimization.md`; `pinchtab/references/api.md`; `pinchtab/references/mcp.md`; `pinchtab/references/article-collection.md`; `pinchtab/TRUST.md`.
- Standout mechanism: refs have an explicit lifetime—navigation, reload, and dynamic rerender invalidate them; actions should return a new post-action state (`pinchtab/SKILL.md`, `pinchtab/references/agent-optimization.md`, `pinchtab/references/mcp.md`).
- Standout mechanism: `--snap-diff` combines mutation and postcondition observation, avoiding a race and a redundant full snapshot (`pinchtab/references/agent-optimization.md`, `pinchtab/references/commands.md`).
- Standout mechanism: tool selection is evidence-sensitive—text for prose, accessibility snapshots for controls/visible state, screenshots for layout, PDFs for document state, and network capture for request-level debugging (`pinchtab/SKILL.md`, `pinchtab/references/article-collection.md`).
- Standout mechanism: article capture hands downstream KG work a small provenance contract: URL, title, canonical URL, author/publisher/date, access date, capture method, and explicit uncertainties (`pinchtab/references/article-collection.md`).
- Standout mechanism: evaluate, upload, download, network interception, and challenge solving are default-off/high-impact capabilities, while authenticated work is routed to dedicated low-privilege profiles (`pinchtab/SKILL.md`, `pinchtab/TRUST.md`).
- Standout mechanism: MCP output is explicitly untrusted and domain allowlists are named as the prompt-injection boundary (`pinchtab/references/mcp.md`).
- Weakness: the package validator checks frontmatter strings, file existence, executable presence, and a repository symlink; it does not test any command contract, ref freshness, security default, or API/MCP compatibility (`pinchtab/scripts/validate-pinchtab-skill.js`).
- Weakness: documentation drifts: the API/older comments advertise shorthand such as `ss` or `tabs`, while the command reference says those are wrong and requires `screenshot` and `tab` (`pinchtab/references/api.md`, `pinchtab/references/commands.md`).
- Weakness: direct API examples omit authentication and repeatedly use a globally shared localhost daemon; safety depends on external server configuration not included here (`pinchtab/references/api.md`, `pinchtab/references/env.md`).
- Weakness: cookies are “available” despite the otherwise default-off security table, and network export documents `redact=false`; policy text, not a typed per-call capability token, prevents exfiltration (`pinchtab/TRUST.md`, `pinchtab/references/api.md`).
- Smell: the trust document makes implementation and release assertions that cannot be substantiated from this skill directory because the executable source/build manifests are absent (`pinchtab/TRUST.md`).

### weblog-from-webdav

- What it actually does: bootstraps a live Virtuoso VSP engine over a DAV collection, then treats ordinary HTML/Markdown PUT plus custom DAV properties as the ongoing publishing interface (`weblog-from-webdav/SKILL.md`, `weblog-from-webdav/references/isql-mode.md`, `weblog-from-webdav/references/webdav-mode.md`).
- The engine enumerates resources dynamically, suppresses Apple sidecars, deduplicates Markdown when an HTML rendition shares its stem, sorts pins before recency, embeds posts, and offers feed/facet variants (`weblog-from-webdav/templates/deploy-weblog-opl-site.sql`, `weblog-from-webdav/templates/deploy-weblog-opl-site-facet.sql`).
- `schema:category` drives facets and `schema:position` drives pinning; metadata can be applied during publication, from TSV, by scheduled server-side inference, or by an OPAL-registered stored procedure (`weblog-from-webdav/references/facet-metadata-contract.md`, `weblog-from-webdav/scripts/publish_with_metadata.py`, `weblog-from-webdav/templates/register-category-refresh-scheduler.sql`, `weblog-from-webdav/templates/register-weblog-pinning-tool.sql`).
- The facet variant scopes full-text search to the collection, applies date filtering, builds category counts from the query/date candidate set, and uses `dict_iter_next` to enumerate aggregates (`weblog-from-webdav/templates/deploy-weblog-opl-site-facet.sql`).
- Notable files worth a human read: `weblog-from-webdav/references/webdav-weblog-engine-gate.md`; `weblog-from-webdav/templates/deploy-weblog-opl-site-facet.sql`; `weblog-from-webdav/templates/register-weblog-pinning-tool.sql`; `weblog-from-webdav/scripts/publish_with_metadata.py`; `weblog-from-webdav/scripts/validate_generated_weblog_bundle.py`; `weblog-from-webdav/references/facet-metadata-contract.md`.
- Standout mechanism: the terminal-state gate is excellent—either live route and feeds are verified, or a complete deployable bundle passes an offline gate and is reported as not deployed (`weblog-from-webdav/SKILL.md`, `weblog-from-webdav/references/webdav-weblog-engine-gate.md`).
- Standout mechanism: engine/bootstrap capabilities and day-to-day content publication are separate modes; WebDAV PUT success is never allowed to imply that routing, VSP execution, indexing, ACLs, or OPAL registration exist (`weblog-from-webdav/references/isql-mode.md`, `weblog-from-webdav/references/webdav-mode.md`).
- Standout mechanism: managed publication couples PUT, metadata PROPPATCH, and metadata PROPFIND read-back; mounted/third-party writes get a scheduled repair path (`weblog-from-webdav/scripts/publish_with_metadata.py`, `weblog-from-webdav/templates/register-category-refresh-scheduler.sql`).
- Standout mechanism: calling-agent certificate identity and delegated principal identity are modeled separately via mTLS and `On-Behalf-Of`/`-W` (`weblog-from-webdav/SKILL.md`, `weblog-from-webdav/references/isql-mode.md`, `weblog-from-webdav/references/webdav-mode.md`).
- Standout mechanism: a database-native operation can become agent-callable through stored-procedure registration and generated OpenAPI/MCP exposure (`weblog-from-webdav/references/opal-tool-mode.md`, `weblog-from-webdav/templates/register-weblog-pinning-tool.sql`).
- Weakness: the base deploy template declares `feed_param` and `feed_type` but never assigns them before RSS/Atom/AtomPub branches; the base feed links therefore appear implemented while the request switch is absent (`weblog-from-webdav/templates/deploy-weblog-opl-site.sql`).
- Weakness: the generated-bundle validator only searches for strings such as `rss`, `atom`, `string_output`, and `VHOST_DEFINE`, so it passes that broken base template; local execution confirmed both package marker validators pass, but that is not behavioral proof (`weblog-from-webdav/scripts/validate_generated_weblog_bundle.py`, `weblog-from-webdav/scripts/validate_weblog_bundle.py`, `weblog-from-webdav/templates/deploy-weblog-opl-site.sql`).
- Weakness: deployment deletes the current `index.vsp` before uploading its replacement and removes route mappings before redefining them, with no transaction, backup, ETag/precondition, or compensation path (`weblog-from-webdav/templates/deploy-weblog-opl-site.sql`, `weblog-from-webdav/templates/deploy-weblog-opl-site-facet.sql`).
- Weakness: WebDAV helper dry-runs stringify the full curl command, which can expose environment-derived passwords, bearer tokens, or certificate passphrases; non-dry-run subprocess arguments expose the same values to the local process table (`weblog-from-webdav/scripts/publish_with_metadata.py`).
- Weakness: `set_pinned_post.py` performs no target-existence preflight, sibling-pin clearing, PROPFIND read-back, or rendered-order verification even though the skill promises all four; only the server-side SQL procedure enforces a single pin (`weblog-from-webdav/scripts/set_pinned_post.py`, `weblog-from-webdav/SKILL.md`, `weblog-from-webdav/templates/register-weblog-pinning-tool.sql`).
- Weakness: the OPAL pinning procedure accepts an arbitrary DAV collection/path and DAV username while running as a privileged stored procedure; it has no collection allowlist or caller-to-resource authorization policy in its contract (`weblog-from-webdav/templates/register-weblog-pinning-tool.sql`).
- Weakness: uploads and property changes are not atomic; a successful PUT followed by failed PROPPATCH leaves a published but uncategorized post, and the helper returns failure without a compensation record (`weblog-from-webdav/scripts/publish_with_metadata.py`).
- Smell: `apply-schema-category.sql` is a large, site-specific staging dump, and keyword inference matches broad substrings such as `rest`, `entity`, `gpt`, and `sql`; neither is a reusable domain-modeling mechanism (`weblog-from-webdav/templates/apply-schema-category.sql`, `weblog-from-webdav/templates/register-category-refresh-scheduler.sql`, `weblog-from-webdav/scripts/publish_with_metadata.py`).

### website-from-webdav

- What it actually does: accepts an already-rendered `generated/` plus `assets/`, preserves the upstream SHACL/Jinja boundary, validates a deployment bundle, PUTs files recursively, and optionally bootstraps a static `VHOST_DEFINE` route (`website-from-webdav/SKILL.md`, `website-from-webdav/references/rdf-content-mode.md`).
- The route contract is intentionally static: `is_dav=>1`, browsing off, `index.html` as default, no VSP, no request-time SPARQL (`website-from-webdav/references/webdav-website-engine-gate.md`, `website-from-webdav/templates/deploy-website-route.sql`).
- The publisher assigns MIME types and compares GET content byte-for-byte for HTML/CSS/JS after PUT; other binary assets are reported as uploaded but not verified (`website-from-webdav/scripts/publish_static_bundle.py`).
- The generated-bundle validator requires non-empty HTML, `site.css`, `theme.js`, route remove/define markers, static route settings, HTTP/DAV verification queries, no `$<digit>` macro tokens, and run notes (`website-from-webdav/scripts/validate_generated_website_bundle.py`).
- Notable files worth a human read: `website-from-webdav/SKILL.md`; `website-from-webdav/references/webdav-website-engine-gate.md`; `website-from-webdav/references/rdf-content-mode.md`; `website-from-webdav/scripts/publish_static_bundle.py`; `website-from-webdav/scripts/validate_generated_website_bundle.py`; `website-from-webdav/templates/deploy-website-route.sql`.
- Standout mechanism: generated output is immutable at this layer; failed SHACL/build gates route back to source RDF/templates rather than encouraging patches to derived HTML (`website-from-webdav/references/rdf-content-mode.md`, `website-from-webdav/SKILL.md`).
- Standout mechanism: first-time route bootstrap and content-only republish are different plans, preventing routine publishing from casually rewriting routing (`website-from-webdav/SKILL.md`, `website-from-webdav/references/isql-route-mode.md`, `website-from-webdav/references/webdav-publish-mode.md`).
- Standout mechanism: “published” requires live-route comparison; unavailable credentials yield a validated deployable bundle and an explicit blocked-live status (`website-from-webdav/SKILL.md`, `website-from-webdav/references/webdav-website-engine-gate.md`).
- Standout mechanism: the OPAL extension is explicitly declined until server-side state exists; refusing a useless stub is a good capability-design decision (`website-from-webdav/references/opal-tool-mode.md`).
- Weakness: dry-run output includes the assembled curl command and ends with “published N files”; it can leak password/certificate arguments and falsely narrate a successful publish (`website-from-webdav/scripts/publish_static_bundle.py`).
- Weakness: text verification decodes remote and local data with different semantics and skips binary hashes; it does not record ETag, Last-Modified, digest, HTTP status, or final route identity (`website-from-webdav/scripts/publish_static_bundle.py`).
- Weakness: recursive local asset paths are PUT directly, but the script never creates missing remote subcollections with MKCOL, so nested assets depend on undocumented pre-existing DAV directories (`website-from-webdav/scripts/publish_static_bundle.py`).
- Weakness: the validator is marker-based; it does not parse SQL, check unexpanded target literals, resolve HTML asset links, validate MIME coverage, or prove that route values agree across SQL and run notes (`website-from-webdav/scripts/validate_generated_website_bundle.py`).
- Weakness: route deployment removes the previous mapping before defining the new one, outside a documented transaction or rollback plan (`website-from-webdav/templates/deploy-website-route.sql`).
- Smell: the template uses real-looking site/host/path literals as replacement tokens rather than unmistakable typed placeholders, making partial substitution easy to miss (`website-from-webdav/templates/deploy-website-route.sql`, `website-from-webdav/references/isql-route-mode.md`).

## Cross-cutting patterns in this lane

- Detect → choose mode → elicit missing inputs → preview/validate → mutate → reload/publish → read back is the common successful shape (`iodbc-dsn-manager/SKILL.md`, `openlink-request-broker-configurator/SKILL.md`, `weblog-from-webdav/SKILL.md`, `website-from-webdav/SKILL.md`).
- The best skills distinguish capability presence from content presence: a DAV file is not a weblog engine, a generated folder is not a live site, and a browser ref is not valid after rerender (`weblog-from-webdav/references/webdav-weblog-engine-gate.md`, `website-from-webdav/references/webdav-website-engine-gate.md`, `pinchtab/SKILL.md`).
- Useful elicitation narrows irreversible scope: select DSNs/JARs, confirm recording scenes, choose identity/deployment mode, and identify first-time bootstrap versus republish (`openlink-request-broker-configurator/SKILL.md`, `screencast-recorder/SKILL.md`, `website-from-webdav/SKILL.md`).
- Identity has multiple dimensions that should not collapse: tool caller/session, local profile, certificate-bearing agent, delegated principal, and target resource owner (`pinchtab/references/env.md`, `weblog-from-webdav/references/isql-mode.md`, `weblog-from-webdav/references/webdav-mode.md`).
- Verify-after-write appears repeatedly, but its strength ranges from genuine read-back (`publish_with_metadata.py`) to byte comparison (`publish_static_bundle.py`) to HTML substring matching (`www_sv`) to marker-only static validators (`validate_*_bundle.py`) (`weblog-from-webdav/scripts/publish_with_metadata.py`, `website-from-webdav/scripts/publish_static_bundle.py`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`).
- “Deployable” and “deployed” are separate terminal states in the WebDAV skills; this is stronger than a generic success/failure boolean (`weblog-from-webdav/references/webdav-weblog-engine-gate.md`, `website-from-webdav/references/webdav-website-engine-gate.md`).
- Machine-readable sidecars recur—RDF screencast logs, DAV properties, HTTP route rows, OpenAPI tool descriptions—but observed provenance is usually thinner than claimed (`screencast-recorder/scripts/yaml-to-ttl.py`, `weblog-from-webdav/references/facet-metadata-contract.md`, `weblog-from-webdav/references/opal-tool-mode.md`).
- Most dangerous gaps sit at privilege boundaries: raw credentials in argv/dry-run logs, unauthenticated loopback services that can be exposed, broad stored procedures, passwordless sudo, and remove-before-replace deployments (`iodbc-dsn-manager/server/odbc_rest_server.py`, `weblog-from-webdav/scripts/publish_with_metadata.py`, `openlink-request-broker-configurator/SKILL.md`, `website-from-webdav/templates/deploy-website-route.sql`).
- Validators are useful as packaging smoke tests but are repeatedly mislabeled as semantic gates; they should be layered beneath parsers, simulators, integration tests, and live postconditions (`pinchtab/scripts/validate-pinchtab-skill.js`, `weblog-from-webdav/scripts/validate_generated_weblog_bundle.py`, `website-from-webdav/scripts/validate_generated_website_bundle.py`).

## Steal-worthy for beep-effect (ranked, concrete — name the mechanism and the port)

1. **Typed operation-plan state machine.** Port the lane-wide Detect/Plan/Validate/Apply/Verify sequence to `effect/Schema` discriminated unions: `DetectedMode`, `IdentityMode`, `OperationPlan`, `ValidationEvidence`, and terminal `LiveVerified | DeployableBlocked | FailedWithPartialEffects`; execute through `Effect` services rather than prose branching (`website-from-webdav/SKILL.md`, `weblog-from-webdav/SKILL.md`, `iodbc-dsn-manager/SKILL.md`).
2. **Fresh-ref leases for browser/desktop automation.** Represent each UI ref as `{ sessionId, tabId, documentEpoch, ref }`; invalidate the epoch on navigation/rerender and require every mutating action to return a new snapshot/diff. Add typed `StaleRef`, `LockConflict`, and `HandoffRequired` errors plus a fencing token for fleet locks (`pinchtab/SKILL.md`, `pinchtab/references/api.md`, `pinchtab/references/agent-optimization.md`).
3. **Evidence bundle beside every automation artifact.** Replace storyboard-derived “logs” with an Effect-native `EvidenceBundle` containing the requested plan, observed events, timestamps, tool/version, actor/delegated principal, target URI, exit status, screenshots/video/HAR paths, SHA-256 digests, assertions, and deviations; serialize JSON plus optional PROV-O RDF (`screencast-recorder/SKILL.md`, `screencast-recorder/scripts/yaml-to-ttl.py`, `pinchtab/references/article-collection.md`).
4. **Deployable-versus-live completion algebra.** Make `LocalBuilt`, `BundleValidated`, `PublishAttempted`, and `LiveVerified` impossible to confuse in domain types and CLI wording; missing credentials should produce `DeployableBlocked` with explicit missing capabilities, never success (`weblog-from-webdav/references/webdav-weblog-engine-gate.md`, `website-from-webdav/references/webdav-website-engine-gate.md`).
5. **Configuration compiler with ordered-rule invariants.** Parse broker/DSN config into schemas, normalize names deterministically, detect alias/slot collisions, compile a proposed diff, prove specific-before-catch-all ordering, snapshot the original, atomically replace, run the native validator, reload, and health-check; expose rollback as data (`openlink-request-broker-configurator/references/rulebook-structure.md`, `openlink-request-broker-configurator/SKILL.md`).
6. **WebDAV publication saga.** Model PUT → PROPPATCH → GET/PROPFIND → public-route verification as durable Effect steps with ETag/`If-Match`, per-file digest evidence, parsed `207 Multi-Status`, retry policy only for transient failures, and compensation or a typed partial-publication record (`weblog-from-webdav/scripts/publish_with_metadata.py`, `website-from-webdav/scripts/publish_static_bundle.py`).
7. **Capability gate before resource mutation.** Encode required capabilities—route exists, engine executable, index available, write rights proven, full-text enabled, OPAL installed—separately from artifacts and block downstream phases when capability evidence is absent (`weblog-from-webdav/references/isql-mode.md`, `website-from-webdav/references/isql-route-mode.md`).
8. **Agent-callable domain operation generated from one schema.** Port the stored-procedure-to-OpenAPI idea, but derive Effect RPC/OpenAPI/MCP contracts from the same `Schema`; wrap every operation in resource allowlists, caller authorization, idempotency keys, audit events, and postcondition checks (`weblog-from-webdav/templates/register-weblog-pinning-tool.sql`, `weblog-from-webdav/references/opal-tool-mode.md`).
9. **Default-off high-impact capability set.** Define capabilities such as `EvaluateJs`, `UploadFile`, `ReadCookies`, `ExportBodies`, `RestartService`, and `RewriteRoute`; grant them per task/session rather than via ambient config, with low-privilege profiles as the default (`pinchtab/TRUST.md`, `pinchtab/SKILL.md`).
10. **Filtered-candidate facet contract.** For legal/patent KG browsing, compute facet counts from the candidate set after text/date/security filters but before the selected facet is applied; represent category/provenance metadata as validated sidecars with explicit source and confidence (`weblog-from-webdav/references/facet-metadata-contract.md`, `weblog-from-webdav/templates/deploy-weblog-opl-site-facet.sql`).
11. **Human-handoff as a protocol state.** Adopt PinchTab’s pause/reason/timeout/resume shape for login, MFA, CAPTCHA, desktop permission prompts, and configuration approval; persist it as resumable fleet state rather than an ad hoc chat interruption (`pinchtab/references/api.md`, `pinchtab/references/profiles.md`).
12. **Static package checks as the lowest validation tier.** Keep cheap marker/inventory checks, but label them `PackageSmoke` and require parser/typecheck, contract tests, integration tests, and live assertions for stronger verdicts (`pinchtab/scripts/validate-pinchtab-skill.js`, `weblog-from-webdav/scripts/validate_weblog_bundle.py`, `website-from-webdav/scripts/validate_website_bundle.py`).

## Exploration-packet leads (open questions worth a deeper research phase)

- Can browser refs carry a server-issued document generation/fencing token so stale refs are rejected structurally rather than by convention (`pinchtab/references/api.md`, `pinchtab/references/mcp.md`)?
- How should a multi-agent browser lock interact with session-scoped current tabs, crashes, lease renewal, and human handoff to avoid split-brain control (`pinchtab/references/api.md`, `pinchtab/references/profiles.md`)?
- What minimum evidence makes a screencast a QA artifact: synchronized accessibility snapshots, assertion outcomes, HAR, console logs, source commit, media hashes, or all of them (`screencast-recorder/SKILL.md`, `screencast-recorder/references/storyboard-schema.md`)?
- Can one Effect Schema generate YAML storyboard validation, JSON evidence, PROV-O projection, and an MCP operation surface without the lossy dual converters seen here (`screencast-recorder/scripts/ttl-to-yaml.py`, `screencast-recorder/scripts/yaml-to-ttl.py`)?
- Which WebDAV servers reliably support ETag preconditions on PUT/PROPPATCH, and how should `207 Multi-Status` property failures be normalized into typed partial outcomes (`weblog-from-webdav/scripts/publish_with_metadata.py`, `website-from-webdav/scripts/publish_static_bundle.py`)?
- Can route replacement and VSP upload be staged under a new path, live-tested, then atomically switched instead of delete-before-replace (`weblog-from-webdav/templates/deploy-weblog-opl-site.sql`, `website-from-webdav/templates/deploy-website-route.sql`)?
- Under which SQL security context do OPAL-registered procedures execute, and how can collection-scoped authorization be proven before exposing DAV mutation to a fleet (`weblog-from-webdav/templates/register-weblog-pinning-tool.sql`)?
- Is `www_sv` capable of TLS, CSRF protection, structured responses, and credential sources safer than command-line Basic auth, or should it be wrapped behind a typed local broker (`iodbc-dsn-manager/references/www_sv-endpoints.md`, `openlink-request-broker-configurator/references/broker-www_sv-endpoints.md`)?
- How can INI comment/order preservation and native validation be combined with a semantic AST/diff for legacy operational config (`openlink-request-broker-configurator/references/rulebook-structure.md`)?
- Would SHACL shapes and Effect Schema be generated from a common domain contract, or should parity tests prove equivalent constraints across RDF ingestion and TypeScript services (`website-from-webdav/references/rdf-content-mode.md`)?
- How should provenance distinguish intended plan, attempted action, observed server state, and public-route observation—the current RDF log and DAV metadata collapse some of these layers (`screencast-recorder/scripts/yaml-to-ttl.py`, `weblog-from-webdav/references/facet-metadata-contract.md`)?
- A disposable Virtuoso integration harness should test both deploy templates, feeds, search quoting, date filters, property typing, pin uniqueness, and route rollback; the base-feed initialization defect shows marker validation is insufficient (`weblog-from-webdav/templates/deploy-weblog-opl-site.sql`, `weblog-from-webdav/scripts/validate_generated_weblog_bundle.py`).

## Dead ends (what to NOT spend time on, and why)

- Do not port the Python and TypeScript ODBC bridges as parallel implementations; first define one authenticated, least-privilege contract and generate clients/servers or share conformance tests (`iodbc-dsn-manager/server/odbc_rest_server.py`, `iodbc-dsn-manager/server/odbc_rest_server.ts`).
- Do not reuse raw `curl -u`, bearer, or `--cert file:passphrase` command assembly in agents; it leaks through argv and dry-run logging. Use secret-reference/injected credential providers and redactable process APIs (`weblog-from-webdav/scripts/publish_with_metadata.py`, `website-from-webdav/scripts/publish_static_bundle.py`).
- Do not adopt the screencast ontology as-is; its class/property constraints conflict with templates, it lacks SHACL, and conversion silently loses actions/order (`screencast-recorder/references/screencast-ontology.ttl`, `screencast-recorder/assets/templates/minimal-storyboard.ttl`, `screencast-recorder/scripts/ttl-to-yaml.py`).
- Do not treat a storyboard-derived RDF file as observed provenance; it records intent unless augmented with runtime events, outcomes, timestamps, and artifact hashes (`screencast-recorder/scripts/yaml-to-ttl.py`).
- Do not spend packet space on the large site-specific category INSERT corpus or generic keyword classifier; keep only the metadata sidecar/read-back/scheduler mechanism (`weblog-from-webdav/templates/apply-schema-category.sql`, `weblog-from-webdav/templates/register-category-refresh-scheduler.sql`).
- Do not copy literal-replacement SQL templates with real-looking hosts and paths; use unmistakable schema-validated parameters and render a deterministic plan (`website-from-webdav/templates/deploy-website-route.sql`, `weblog-from-webdav/templates/deploy-weblog-opl-site.sql`).
- Do not equate marker gates with semantic validation; both WebDAV package validators pass while the base weblog feed dispatcher is uninitialized (`weblog-from-webdav/scripts/validate_weblog_bundle.py`, `website-from-webdav/scripts/validate_website_bundle.py`, `weblog-from-webdav/templates/deploy-weblog-opl-site.sql`).
- Do not expose the pinning stored procedure fleet-wide without target allowlists and authorization checks; its current parameters permit arbitrary DAV paths/users (`weblog-from-webdav/templates/register-weblog-pinning-tool.sql`).
- Do not copy broad passwordless-sudo advice into a skill. Service reload should be a narrowly mediated capability with explicit target, audit, and rollback (`openlink-request-broker-configurator/SKILL.md`).
- Do not over-invest in `pinchtab/TRUST.md` marketing assertions from this repo alone; the executable, source, build workflow, and release attestations live elsewhere. The useful material here is the capability policy and interaction contract (`pinchtab/TRUST.md`, `pinchtab/SKILL.md`).
- Do not port fixed presentation styling, brand copy, or enormous embedded VSP strings; port the engine/capability gate, typed publishing saga, facet semantics, and evidence rules (`weblog-from-webdav/templates/deploy-weblog-opl-site.sql`, `weblog-from-webdav/templates/deploy-weblog-opl-site-facet.sql`).
