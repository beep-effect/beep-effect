# Contract Kernel and Evidence/Provenance Capability Inventory

**Date:** 2026-08-13

The repository already contains unusually strong raw material for typed agent contracts: schema-derived literal domains and annotations, persisted Yeet proof state and verdicts, schema-validated goal/reflection and QA outputs, verified text anchors, epistemic claim gates, and QA artifact provenance stamps. Those facilities are, however, local to their workflows. None supplies a reusable `SkillContract` root, a gate registry whose blocking evidence makes completion unrepresentable, the packet's ordered evidence-ladder algebra, or a schema-defined bounded-recovery service with durable attempt receipts. Ports 1, 2, and 4 are therefore ports of proven shapes into a common kernel, not greenfield invention; their integration and transition semantics remain net-new.

## 1. `@beep/schema` contract-building substrate

- **Package and public surface.** The package is `@beep/schema` (`@beep/schema` — `packages/foundation/modeling/schema/package.json:2`). Its root barrel exports `DomainModel`, `EntitySchema`, `LiteralKit`, `Model`, and `SchemaUtils` (`@beep/schema` — `packages/foundation/modeling/schema/src/index.ts:112`, `:149`, `:293`, `:416`).
- **Literal domains and derived operations.** `LiteralKit` accepts a non-empty literal set and derives `Options`, `HashSet`, `is`, `Enum`, `pick`, `omit`, `$match`, a thunk, and `toTaggedUnion` (`@beep/schema` — `packages/foundation/modeling/schema/src/LiteralKit/LiteralKit.schema.ts:655-680`, `:701-805`). Its implementation derives the guard with `S.is`, constructs an `S.Enums` view, and delegates tagged-union construction to Effect's `S.toTaggedUnion` (`@beep/schema` — `packages/foundation/modeling/schema/src/LiteralKit/LiteralKit.schema.ts:810-861`). This directly covers the literal families needed for gate ids, severities, applicability states, ladder stages, and terminal outcomes.
- **Identity and annotation composers.** `$I` is not defined by `@beep/schema`; it is exported by the sibling `@beep/identity` package (`@beep/identity` — `packages/foundation/modeling/identity/src/packages.ts:46`). The composer exposes `annote`, `annoteSchema`, `make`, `use`, and related identity operations (`@beep/identity` — `packages/foundation/modeling/identity/src/Id.ts:931-940`); `annote` and `annoteSchema` attach stable identifiers, titles, descriptions, documentation, and arbitrary annotations (`@beep/identity` — `packages/foundation/modeling/identity/src/Id.ts:979-1020`, `:1133-1136`). `$SchemaId` and `$ProvenanceId` provide already-named identity roots (`@beep/identity` — `packages/foundation/modeling/identity/src/packages.ts:250`, `:266`).
- **Defaults.** `SchemaUtils.withKeyDefaults` applies selected property defaults both while constructing values and while decoding them, rejecting missing schema keys up front (`@beep/schema` — `packages/foundation/modeling/schema/src/SchemaUtils/withKeyDefaults.ts:18-72`). That is suitable for safe contract defaults such as a default gate severity or recovery policy, provided absence has an unambiguous meaning.
- **Model classes.** `DomainModel` is a concrete `Model.Class` with named audit/default fields (`createdAt`, `updatedAt`, soft-delete metadata, version, and source) (`@beep/schema` — `packages/foundation/modeling/schema/src/DomainModel.ts:36-45`, `:69-74`). It is persisted-model infrastructure, not a `SkillContract` factory. Schema-first entity definitions become Drizzle tables through `EntityTable.pgTableFrom` (`@beep/drizzle` — `packages/drivers/drizzle/src/EntityTable.models.ts:509-516`).
- **Template literals and URI schemas.** The package uses `S.TemplateLiteral` for structured strings such as semantic versions (`@beep/schema` — `packages/foundation/modeling/schema/src/SemanticVersion.ts:62-68`). Its AT URI type is instead a validated, branded schema with an identity annotation (`@beep/schema` — `packages/foundation/modeling/schema/src/AtURI.ts:265-272`). **NOT FOUND:** no generic TemplateLiteral-based URI-schema constructor was found in `@beep/schema`; a contract URI/reference type would need either an existing concrete URI schema or a new named schema.
- **Named constructors requested in the brief.** `Model.Class` and `DomainModel` are present. **NOT FOUND:** there is no general `Table.make` or `DomainModel.make` constructor in `@beep/schema`; current persisted-table generation is `@beep/drizzle`'s `pgTableFrom`. Matches for `Table.make` elsewhere were document/AST node constructors, not schema persistence infrastructure.

## 2. Yeet gate, verdict, and proof machinery

- **Phases.** The `beep yeet` command family exposes `verify`, `repair`, `publish`, `monitor`, `merge`, `closeout`, `reply`, and status/utility commands (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/Yeet.command.ts:357-390`, `:450-465`). `verify` produces local proof, `publish` can commit/push and establish hosted state, and `monitor` observes and may recover hosted checks.
- **Typed issue envelope.** `QualityIssue` records category, severity, blocking status, confidence, message, evidence text, remediation, package/file/source anchor, producing tool/parser/command, exit code, raw-output reference/excerpt, and routing (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/Yeet.schemas.ts:232-272`). The supporting literal domains include issue category, severity, confidence, and attribution (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/Yeet.schemas.ts:29-47`, `:84-88`, `:121-125`, `:158-162`). A `QualityIssueIndex` groups and counts those issues (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/Yeet.schemas.ts:317-327`). This is the closest existing gate-evidence envelope, but it is an observed-issue format rather than a declaration registry: it has no applicability predicate and does not bind every declared blocking gate to required evidence.
- **Verdict state.** A verdict lane records phase, status (`passed`, `failed`, `skipped`, `not-run`, or early-stop), duration, exit code, and repair command (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/Verdict.ts:48-53`, `:143-156`). `YeetVerdict` additionally records base/branch/head identity, timestamps, mode, outcome, packet paths, pushed/committed facts, attempt/index state, base freshness, stash/flake state, failed step, failure kind, and merge readiness (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/Verdict.ts:479-513`). Merge readiness is coherently recomputed from closeout-run, checks-green, and threads-resolved criteria rather than trusting a lone boolean (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/Verdict.ts:203-208`, `:352-396`).
- **Proof identity and reuse.** Per-lane proof state records the command text/hash, diff fingerprint, step identity, and verification time; run state binds proof to branch, base, commit SHA, full diff fingerprint, proof command, and tier (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/ProofState.ts:33-68`). The diff fingerprint hashes status, unstaged diff, and staged diff (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/ProofState.ts:201-245`), and reuse checks compare branch/base/head/commit/fingerprint/tier before accepting prior proof (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/ProofState.ts:737-767`). This is a real evidence-freshness contract.
- **Durable artifacts.** Branch-scoped artifacts live under `.beep/yeet/runs/<run-id>` with a state file (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/ArtifactPaths.ts:64-65`, `:111-118`, `:138-139`). The implementation writes schema-coded `verdict.json`, quality indexes/raw logs, closeout state, reply artifacts, proof state, and an `attempts.ndjson` journal. Attempt markers distinguish started from finished and embed the exact finished verdict; appends are synchronized and compacted to a retained history (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/AttemptJournal.ts:24-25`, `:42-57`, `:73-105`, `:244-270`).
- **Reply drafts and partial effects.** `ReplyDraft` and `ReplyDrafts` form a schema-validated input contract; outcomes are tagged `posted`, `resolved`, `stale`, or `failed`, and the final report counts requested, posted, resolved, stale, and failed operations (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/Reply.schemas.ts:172-214`, `:247-260`, `:282-323`). The handler preserves the case where a reply was posted but thread resolution failed, so the report is an existing typed partial-effects receipt (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/Reply.ts:806-859`, `:907-937`).
- **Closeout contract.** Closeout gates have typed names and statuses, and the report is bound to the reviewed head SHA (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/closeout/Closeout.schemas.ts:59-102`, `:155-179`). The handler writes `pr-closeout.json` before failing on unresolved closeout issues (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Yeet/internal/Handler.ts:772-808`).
- **Gap relative to port 2.** **NOT FOUND:** there is no `Accepted -> Persisted -> Delivered -> SemanticallyApplied` state algebra, nor `LiveVerified | DeployableBlocked | FailedWithPartialEffects` terminal union, in `packages/**/src`. Yeet records many equivalent operational facts, but as lane statuses, booleans, criteria, and workflow-specific outcomes. It does not require evidence at each monotonic rung, and its generic verdict failure does not enumerate all partial external effects. The reply report covers that property only for review replies.

## 3. Reflection artifacts, goal manifests, and accepted-proof machinery

- **Reflection artifact contract.** `bun run beep lint reflection-artifacts` is backed by schemas for confidence, trigger, categories, finding entries, and reflection frontmatter (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Lint/ReflectionArtifact.ts:40-95`). YAML frontmatter is decoded through the schema (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Lint/ReflectionArtifact.ts:155-179`), and completed goal packets are scanned for a conforming reflection before the lint command returns (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Lint/ReflectionArtifact.ts:268-358`). This is a direct precedent for a schema-validated agent deliverable that gates packet completion.
- **Manifest-validation gap.** The reflection linter reads goal status through a raw manifest-shaped cast rather than decoding the canonical goal schema (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Lint/ReflectionArtifact.ts:226-234`). The deliverable is validated; its trigger condition is not validated at this boundary.
- **Goal manifest.** The goal schema defines lifecycle and phase-status literal domains (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Goals/Goals.schemas.ts:51-55`, `:112-116`), a completion-gate record with operator, pull-request and mergeable requirements, statement, and grandfathering (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Goals/Goals.schemas.ts:195-234`), and a `GoalManifest` containing lifecycle, phases, dependencies, capabilities, risks, labels, and notes (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Goals/Goals.schemas.ts:448-472`). `CapabilitySlug` is itself a TemplateLiteral schema (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Goals/Goals.schemas.ts:348-361`). The manifest describes one completion gate, not a registry of gate declarations with evidence receipts.
- **`AcceptedProofManifest`.** Architecture tooling defines an `AcceptedProofFile` descriptor with role, stage, path, and writer and a statically ordered list of accepted-proof files (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Architecture/internal/AcceptedProofManifest.ts:38-48`, `:116-130`). Despite its name, it is a generator manifest for expected architecture-lab files, not persisted proof acceptance, a proof receipt, or an evidence-ladder transition.
- **Architecture-lab proof.** Architecture generation uses those descriptors to plan accepted-proof outputs. **NOT FOUND:** no architecture-lab schema was found that represents proof as `accepted`, then persisted/delivered/semantically applied, or that proves runtime application of generated architecture output.

## 4. `qa-inventory/v1` judge inventory

- **Schema.** `QaInventory` fixes `schemaVersion` to `qa-inventory/v1` and records session, round, creation time, scenario, judge metadata, findings, summary, and `requiredCount` (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Inventory.schemas.ts:474-517`). Findings have a TemplateLiteral id, severity, lens, title, repro steps, required non-empty evidence, fix guidance, and optional resolved round (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Inventory.schemas.ts:209-214`, `:347-394`). Evidence refs contain event ids, a frame range, kind, and artifact path (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Inventory.schemas.ts:141-145`, `:258-285`). A schema check requires `requiredCount` to equal the count of unresolved P0/P1 findings (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Inventory.schemas.ts:413-450`).
- **Judge ingest gate.** Ingest parses and schema-decodes model output, cross-checks it against session evidence, then writes the JSON and Markdown views (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/JudgeIngest.ts:112-132`, `:151-200`). The cross-check rejects missing artifact paths, missing witness event ids, unsafe/out-of-root paths, and incoherent rounds (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/JudgeCheck.ts:43-59`, `:168-189`, `:259-314`, `:343-355`). The lint command re-decodes committed inventories and reruns evidence/round checks (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/JudgeLint.ts:49-90`).
- **Boundary.** This is the strongest in-repo example of “agent output = schema plus evidence gate.” Its evidence check proves that cited artifacts exist under the session root and cited witness sequence ids exist. **PARTIAL:** it does not validate that a frame range semantically demonstrates the finding, cryptographically bind each ref to content, or generalize findings into a reusable gate registry. Semantic judgment remains the model's responsibility.

## 5. Epistemic and evidence-span substrate

- **Verified text anchors.** `@beep/provenance` defines `TextAnchor` as start/end offsets plus an exact quote and checks non-negative width (`@beep/provenance` — `packages/foundation/modeling/provenance/src/TextAnchor.ts:48-58`, `:88-93`, `:161-167`). `SourceTextIdentity` binds scope/source/locator to source and text SHA-256 digests, extractor identity/version, and normalization version (`@beep/provenance` — `packages/foundation/modeling/provenance/src/SourceTextIdentity.ts:30-38`, `:74-86`, `:125-150`).
- **Receipt versus runtime proof.** `TextAnchorVerificationReceipt` persists the expected and resolved identities, anchor, normalized quote, verification time, and verifier version, while its documentation explicitly says the receipt is not itself runtime proof (`@beep/provenance` — `packages/foundation/modeling/provenance/src/VerifiedTextAnchor.ts:126-172`). The opaque `VerifiedTextAnchor` can only be created by the verifier (`@beep/provenance` — `packages/foundation/modeling/provenance/src/VerifiedTextAnchor.ts:188-243`), which checks scope, source identity, digests, offsets, and exact slice equality (`@beep/provenance` — `packages/foundation/modeling/provenance/src/VerifiedTextAnchor.ts:370-398`). This is the clearest existing pattern for separating serializable evidence receipts from live capability/proof objects.
- **Epistemic evidence.** `EvidenceSpan` records normalized text, offsets, quote, confidence, extraction run, and selector context, with a width invariant (`@beep/epistemic-domain` — `packages/epistemic/domain/src/values/EvidenceSpan/EvidenceSpan.model.ts:47-52`, `:105-134`, `:162-198`). `Evidence` links fixture keys to an `EvidenceSpan` persisted as JSONB (`@beep/epistemic-domain` — `packages/epistemic/domain/src/entities/Evidence/Evidence.model.ts:55-82`). `EvidenceVerification` is append-only and stores a manifestation key and the verified-anchor receipt as JSONB (`@beep/epistemic-domain` — `packages/epistemic/domain/src/entities/EvidenceVerification/EvidenceVerification.model.ts:24-34`, `:46-75`).
- **Claim gate.** `ClaimGateResult` is an admitted/rejected tagged verdict with typed violations (`@beep/epistemic-domain` — `packages/epistemic/domain/src/values/ClaimGate/ClaimGateResult.model.ts:81-140`). The service receives a claim plus evidence array, emits a SHACL dataset, requires at least one quote-bearing evidence item, validates it, and returns the typed verdict (`@beep/epistemic-use-cases` — `packages/epistemic/use-cases/src/ClaimGate/ClaimGate.service.ts:36-82`, `:132-138`). This is a domain-specific gate with typed input evidence.
- **Claim-to-source boundary.** `CandidateClaim` stores lifecycle and snapshot data but no direct evidence ids (`@beep/epistemic-domain` — `packages/epistemic/domain/src/entities/CandidateClaim/CandidateClaim.model.ts:49-73`). The relation `claim -> evidence -> span -> source` exists compositionally when callers supply the evidence array and join the verified-anchor sidecar, but it is not one canonical persisted relation enforced by the claim model.
- **Citation/knowledge extraction.** **NOT FOUND:** searches of package names and `packages/**/src` for citation-extractor/citation-extraction symbols found no citation-extraction package or implementation, and no package named `knowledge*`. Legal citation value objects and repository-document reference extraction are separate concerns; neither supplies a general claim-to-citation-span extractor.

## 6. Exif/XMP QA provenance stamping

- **Namespace and tags.** `@beep/exiftool` registers the `https://beep-effect.dev/ns/qa/1.0/` namespace, `beepQA` prefix, and eight string tags (`@beep/exiftool` — `packages/drivers/exiftool/src/ExiftoolConfig.ts:39`, `:55`, `:72`, `:88-101`). `BeepQaProvenance` requires action id, capture time, scenario name, and session id, and optionally carries clock offset, commit SHA, source video, and tool versions (`@beep/exiftool` — `packages/drivers/exiftool/src/Exiftool.models.ts:680-730`). Assignment and readback cover exactly those fields (`@beep/exiftool` — `packages/drivers/exiftool/src/ExiftoolConfig.ts:410-432`, `:483-500`).
- **Write safety.** The service schema-validates the write request, writes through generated tag assignments, uses a temporary output, and atomically renames the result over the target (`@beep/exiftool` — `packages/drivers/exiftool/src/Exiftool.service.ts:505-533`).
- **QA extraction integration.** QA extraction builds `BeepQaProvenance` from each captured action (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Extract.ts:502-519`). Still images are stamped through ExifTool; video artifacts receive equivalent container tags (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Extract.ts:521-570`). `sourceVideo` is stored session-relative rather than as an absolute machine path (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Extract.ts:902-905`).
- **Schema drift and enforcement boundary.** The QA capture model describes a canonical `CaptureProvenance` that also contains `schemaVersion` and numeric `actionSeq` (`@beep/qa-capture` — `packages/tooling/library/qa-capture/src/QaCapture.models.ts:588-595`, `:618-672`), while the actual XMP schema has neither a schema-version tag nor a numeric action-sequence tag; extraction maps the action sequence into string `ActionId`. **PARTIAL:** provenance stamping is best-effort. Image/video stamping errors are accumulated as warnings and extraction continues (`@beep/repo-cli` — `packages/tooling/tool/cli/src/commands/Qa/Extract.ts:556-560`, `:674-707`), so “artifact has verified provenance” is not currently a blocking completion gate.
