### Answer first

- **T3's periodic sweeps spend GraphQL points, not REST core.**
  - Every periodic sweep reads GitHub through batched, aliased GraphQL.
  - The only REST reads on a sweep path are the stack read and the checks-panel revalidation, and both send ETags.
  - The stack read happens only when the sync needs it: the snapshot changed or is null, a refresh was requested, or a stack read is being retried (`PullRequestSyncReactor.ts:493-520`, `GitHubPullRequestApi.ts:2039-2048`). The checks-panel read is reached only through the client RPC (`ws.ts:2810` → `PullRequestService.ts:3113-3116` → `GitHubPullRequestProvider.ts:458-462`, `gitHubConditionalChecks.ts:53-190`).
  - **T3's sweeps were therefore not the cause of the 21:31Z core-bucket exhaustion.** They share the *GraphQL* bucket with Yeet's monitors. Other T3 REST reads that are client-driven or rare are not counted here: the checks panel, App coverage and stack reads.
- **T3 always authenticates as the user.** The order is: a token pinned to the request, then a token saved in Settings, then the T3 Code GitHub App sign-in (skipped when a request asks for a `personal` credential), then `GH_TOKEN`/`GITHUB_TOKEN`, then `gh auth token` (`GitHubRequestPolicy.ts:289-319`, `GitHubCredentials.ts:121-137,153-176,201-212`).
  - The App sign-in uses the OAuth device flow (`GitHubAppSignIn.ts:302-324,384-418`), so its token is a **user access token** (user-to-server).
  - GitHub says user access tokens share the user's primary limit with that user's other requests, PATs and other apps included ([REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). The GitHub Apps rate-limit page only says the limit depends on the token type and on GitHub Enterprise Cloud ownership. Whether the Enterprise Cloud exception applies here is (unverified).
  - So every T3 host spends the same 5,000 REST/h and 5,000 GraphQL points/h as `gh` and the PATs.
  - T3 caches the `gh auth token` result for 5 minutes (`GitHubCredentials.ts:33`). That the command itself makes no API call is (unverified: gh source not read).
- **T3 already holds back a reserve.**
  - `GitHubQuota` reads `x-ratelimit-*` from each response, keyed by host, resource and credential scope. Background reads stop when `remaining < 10% × limit`, which is 500 for a 5,000 bucket. They resume after the reset. Interactive reads may go down to 1 (`GitHubQuota.ts:10,61-75,77-95`). Requests are non-interactive by default (`SourceControlRateLimit.ts:23-27`).
  - REST reads use the `core` resource and GraphQL reads use the `graphql` resource. In both, `allowReserve` defaults to the interactive flag (`GitHubRest.ts:139-141,204`, `gitHubGraphQlClient.ts:72-73`).
  - Because the headers report the shared user bucket, every T3 host sees the whole fleet's spend. T3 stops at about 500 remaining, while Yeet drives the bucket to 0.
  - **Side effect:** once Yeet pushes a bucket under 10%, T3's watch sweep skips every group whose fingerprint read comes back rate-limited (`PullRequestWatchReactor.ts:446-459,642`). Its sync sweep also pauses per project and host until the retry time (`PullRequestSyncReactor.ts:582-590,604-612`). Watched threads are then not woken until the reset.
- **Sharing:**
  - **Within one host:** threads watching or linking the same PR in the same project share one read (grouping at `PullRequestWatchReactor.ts:609` and `PullRequestSyncReactor.ts:391`).
  - **Within one host, different projects:** the same repository opened as several projects (for example clone plus worktree) gets one group per project. Each project gets its own summary, detail and activity reads, because the persisted cache key includes `projectId` (`PullRequestService.ts:2889-2898`). The GraphQL batch key is credential fingerprint plus credential scope (`gitHubGraphQlClient.ts:218-223`), so those per-project summary reads may still share one aliased document when the credential matches. Each still uses its own alias.
  - **Across hosts:** nothing is shared. Each host has its own projection database, its in-memory caches, and a 60 s persisted read cache under its own cache directory (`PullRequestReadCache.ts:121-128,237-241`).
- **With no watches and no linked PRs, T3 makes almost no calls.** The sync and watch timers still tick but find nothing to read. The remaining calls are branch lookups, which are event-driven and also fire on headless hosts, plus one startup backfill.

**ETags in summary.** T3 sends conditional requests only on two REST paths. The first is `revalidatedRestRead` and its one caller, the stack read (`GitHubPullRequestApi.ts:1199-1230,2042`). The second is the checks revalidator (#6). Both keep their stores in memory per process. Every recurring sweep read is GraphQL, which has no 304 path, so ETags cannot help it.

### Estimated cost per host [est, from code; not traced]

Variables per host:
- **Nₐ** = linked open PR groups (distinct project+PR) updated in the last 30 min
- **N_q** = quiet linked open PR groups
- **M** = watched groups, of which **M_ci** have checks pending or unknown mergeability
- **R** = remark-fingerprint changes per watched PR per hour (new comments or reviews)
- **T** = terminal runs per hour on threads with a branch

- **Sync (GraphQL points/h)** ≈ 60·⌈Nₐ/25⌉, or 12·⌈N_q/25⌉ when Nₐ = 0. Quiet PRs that are due join the same batch. That is **about 60/h for up to 25 linked PRs**. REST ≈ 0, because stack reads only follow changes and return 304 when unchanged.
- **Watch (GraphQL points/h)** ≈ 30·⌈M/25⌉ for fingerprints, plus about 30·M_ci for detail, plus about 17·(2 + R)·M for activity (≈ 13 `ReviewThreads` + 2 activity + 1 commit stats + 1 detail). REST is 0.
  - Idle watched PR (checks settled, no new remarks): about 2 full reads/h ≈ **35 points/h**.
  - Watched PR with CI running and 3 bot reviews/h: about 30 + 5·17 ≈ **115 points/h**.
- **Discovery and status (GraphQL)**: up to about 60 batched documents/h while a client is attached, plus about T forced lookups on headless hosts.

| Scenario per host | GraphQL points/h | REST/h | × 6 hosts |
|---|---|---|---|
| Nothing linked or watched, headless | ≈ T (terminal runs only) | 0 | ≈ 6T |
| N = 10 linked (active), M = 0 | ≈ 60 | ≈ 0 | ≈ 360 |
| N = 10, M = 3 (1 in CI, R = 2) | ≈ 60 + 30 + 30 + 3·4·17 ≈ 320 | ≈ 0 | ≈ 1,900 |
| N = 25, M = 10 (3 in CI, R = 2), client attached | ≈ 60 + 30 + 90 + 10·4·17 + 60 ≈ 920 | ≈ 0 | ≈ 5,500 (above the GraphQL bucket) |

**Cross-check.** The post-reset sample in CAPTURE.md, taken with 2–3 monitors running, measured about 430 GraphQL/h fleet-wide. That caps T3's fleet-wide GraphQL spend at that moment at ≤ 430/h, an average of ≤ ~72 points/h per host. This is an average, not a per-host cap, because one host could hold most of it. It fits sync sweeps plus at most a few idle watches. The same sample also conflicts with the reduction plan's 720–1,440 GraphQL/h per monitor: 2–3 monitors at that rate would exceed 430 on their own. Either the monitor GraphQL estimate is too high or the sample window missed it. This needs to be resolved before the sample is used to bound T3.

**The activity-read estimate (about 17 points) is the weakest number here and drives the heavy scenarios.** GitHub sums the requests each connection needs (multiplied through the parent `first`/`last` limits), divides by 100 and rounds, with a minimum of 1 ([docs](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). Counting `reactors(first:10)` once per comment under the unpaged `reactionGroups` list gives about 1 + 100 + 1,000 for threads, plus about 300 for PR comments and reviews, ≈ 13 points. That basis matches the in-file note that the earlier 100×100 shape was charged 104 points (`pullRequestReviews.graphql:44-46`). It is still not measured.

### Duplicate readers, which matter for "one reader per fact"

- The same PR can be read, all independently, by:
  - T3 sync on host A (the orchestrator's thread linked it)
  - T3 sync and watch on host B (the lane thread)
  - each further project on the same host (separate reads, though possibly in a shared aliased document)
  - Yeet `monitor --until-ready` (480–840 REST/h and 720–1,440 GraphQL/h per the reduction plan; the GraphQL figure conflicts with the 430/h sample, see above)
  - merge-gate
  - the gate poll.

  T3 has no cross-host or cross-process snapshot.
- Within a host, T3 already does the in-process half of S5: one read per (project, PR) feeds N threads. Sync and watch also invalidate each other's cache entries through scope revisions (`PullRequestReadCache.ts:181-201`).

### Patterns worth porting into Yeet

1. **A cheap batched gate before expensive reads.** One fingerprint query of about 1 point [est] covers up to 25 PRs: state, mergeable, head oid, comment, review and thread counts, and check counts by state. The full detail and activity reads run only when it changes, or every 30 min. This is S4 plus the H6 early return.
2. **A per-credential quota admit/observe with a 10% background reserve and an interactive bypass** (`GitHubQuota.ts`). This is a working, small design for S9. It needs no extra call, because it learns from response headers instead of calling `/rate_limit`.
3. **Cadence that decays with PR activity**: quiet after 30 min, final after merge or after 24 h closed. This is S3.
4. **Group by PR so that N watchers make one read.** This is S5 at host scope.
