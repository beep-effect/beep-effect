## What was not established as implemented

- No generic durable cross-provider agent mailbox service surfaced. `Mailbox` source hits predominantly describe Microsoft 365/product mailboxes; ACP has no mailbox hit. Yeet inbox is explicitly a remediation protocol.
- No general subscription prompt-execution harness surfaced under tooling `AgentHarness`/`agent-harness` names. `AiProviderCli` public contract proves auth/home support only. The Codex quality-loop command is a specific subprocess helper, not a provider-neutral runtime.
- No implemented driver package for `eventlog`, `message-storage`, `workflow` or `sharding` exists in the enumerated driver files. `standards/ARCHITECTURE.md:1605-1608` names these as architecture examples. Do not convert these examples into inventory claims.
- Scratchpad ontology `AgentCoordinator`/workflow work exists, but it is scratchpad, product-specific pipeline/checkpoint work. It should be treated as reference code pending architecture admission, not a reusable production mesh service.
- No evidence was collected for authenticated remote delivery, ordering under restart, sender authorization, durable per-recipient cursor, exactly-once processing, resumption permission preservation, provider-neutral turn lifecycle, or cross-provider backpressure. Those are research/design gaps.

## Architecture recommendation

Build around capabilities and explicit adapter coverage: `session lifecycle`, `prompt`, `stream events`, `cancel`, `steer while running`, `resume`, `permission handling`, `durable delivery`. Keep unsupported capability states explicit; do not make provider name imply support. ACP can implement some capabilities where a real peer speaks ACP. CLI stream-json adapters may implement narrower subsets, without falsely promising live steering.

Repo-operational coordination belongs under **tooling**, initially composed in the existing CLI command structure with narrow services. A reusable operational protocol may earn a `tooling/library` home when it has consumers. Concrete external runtime/SDK/stdio wrappers belong in flat **drivers**, following `@beep/acp` and `@beep/ai-provider-cli`. A new generic `foundation/capability` runtime must first pass the negative gate and show multiple consumers or explicit platform rationale; architecture says repo operations route to tooling first (`standards/ARCHITECTURE.md:468-489`). Product-facing agent business processes stay in the agents slice's use-cases/server, not in drivers or shared.

Preserve authority boundaries: session ledger/register declare ownership; message transport carries envelopes; scheduler admits work; the orchestrator/owner decides routing and authorized continuation; Yeet decides quality and merge readiness. A message receipt does not confer authority to run another provider, rehydrate a Desktop thread, modify another lane, or merge a PR.

The smallest credible exploration spike is read-only, disposable and receipt-emitting: one local peer pair; schema-backed message envelope with participant/run/sequence/correlation identities; injected fake transport proving cancellation, overflow and replay behavior; a durable local spool whose acknowledgement semantics are specified; then a bounded provider adapter test only if separately authorized. Reuse register, admission, auth isolation, protocol framing and quality inbox integration; do not add a memory service or second code index. Durable communication receipts are operational state, while Graft remains the sanctioned regenerable structure graph.
