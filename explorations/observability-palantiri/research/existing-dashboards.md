# Existing dashboards: references and lessons (2026-10-14)

The operator pointed at three live Grafana dashboards, with a caveat
(2026-10-14): the dankserver dashboards were generated by an earlier model
and have known problems, so they are **reference inputs, not templates** —
they must not weight what the Palantiri sets up. Where they are cited below,
it is for a signal worth keeping or a defect worth not repeating.

Two are provisioned
as code from the dankserver control-plane repo and were read from there
(`dankserver:ansible/roles/monitoring/files/grafana/dashboards/*.json`,
provisioned by `dankserver:ansible/roles/monitoring/tasks/main.yml`). The
third lives on the gated host's own LAN Grafana; the operator supplied its
JSON and only its host panels were reviewed.

## `dankserver-host-overview` (dankserver Grafana, Serve route `:8443`)

- Source: `dankserver:ansible/roles/monitoring/files/grafana/dashboards/dankserver-host-overview.json`
  (schemaVersion 39, no template variables).
- Panels: CPU temp, reboot-needed, pending (security) updates, swap, uptime,
  CPU %, RAM, I/O pressure (`node_pressure_io_waiting_seconds_total`), load
  1/5/15, root disk %, SMART disk temps, disk throughput, SSD latency,
  network rx/tx.
- Metric naming: node_exporter names (`node_cpu_seconds_total`, …) plus
  textfile-collector series `os_reboot_required`, `os_upgrades_pending`,
  `os_security_upgrades_pending`.
- **Reuse verdict: reference only (signal inventory).** Every query hard-codes
  `job="node"`, one host, and literal device names (`eth0`,
  `nvme0n1|sda|sdb|sdc|sdd`). For the fleet it needs a `host` template
  variable keyed on the MagicDNS short name (the one `host.name` join
  described in [`fleet-and-hub.md`](./fleet-and-hub.md)) and regex device
  matching. Its update/reboot stats are fleet-relevant signals the
  OTel-hostmetrics dashboard (grafana.com 24638) does not carry, so the
  fleet overview keeps them as a node_exporter-textfile row for Linux
  hosts.

## `openclaw-operations` (dankserver Grafana)

- Source: `dankserver:ansible/roles/monitoring/files/grafana/dashboards/openclaw-operations.json`.
- Panels: messages processed/queued, total tokens, total cost (USD), run
  duration p95, queue-wait p95, throughput, cost rate by provider×model,
  duration p95 by outcome, breakdowns by outcome/channel/token type/lane,
  context-token p95, queue depth, session state transitions.
- Metric shape: OTel-exported counters and histograms
  (`openclaw_*_total`, `*_milliseconds_bucket`) with low-cardinality
  attributes (`openclaw_provider`, `openclaw_model`, `openclaw_outcome`,
  `openclaw_lane`, `openclaw_state`), every stat guarded with
  `or on() vector(0)`.
- **Known defect (operator):** the dashboard never seems to keep its data
  across OpenClaw updates. Probable cause, from the queries and the
  collector config (UNVERIFIED, needs a live check against Prometheus):
  1. Stat panels sum **raw cumulative counters**
     (`sum(openclaw_message_processed_total)`) instead of
     `increase(...[$__range])`, so every process restart resets the totals
     to zero.
  2. The collector's Prometheus exporter runs with
     `resource_constant_labels: ["*"]` and `metric_expiration: 180m`
     ([`fleet-and-hub.md`](./fleet-and-hub.md) §2). If any resource
     attribute changes per restart (e.g. `service.instance.id`), each update
     mints a new series set and the old one silently expires three hours
     later, so history fragments instead of continuing.
  3. The pull exporter keeps only the latest point, so nothing is
     backfilled across a gap.
- **Reuse verdict: anti-pattern catalogue plus a signal list.** The signals
  are the right ones for an agent workload (tokens and cost by
  provider×model, latency histograms by outcome, queue/lane activity), but
  the layout and queries are not adopted. The Palantiri's rules instead:
  totals are always `increase()` over the panel range; per-process identity
  (`service.instance.id`, pids) never becomes a metric label; resource
  attributes promoted to labels come from the closed `beep.*` v2 metric-safe
  set, not `"*"`; and every dashboard has a restart-survival test (restart
  the emitter, assert the range total did not drop).

## Gated host's own Grafana (LAN-only; JSON supplied by the operator)

- A separate, self-contained Grafana on the gated host's LAN serves a
  community-maintained dashboard for the security-sensitive workload
  described in [`DECISIONS.md`](../DECISIONS.md) (fleet scope entry). The
  operator pasted its JSON on 2026-10-14 (Grafana 9.5 export, schemaVersion
  38); it is not stored in the repo. **Only its host-telemetry panels are in
  scope.** Everything workload-specific is ignored, and the Palantiri never
  links, scrapes, or proxies that Grafana.
- Host panels it carries: uptime of the main workload process, CPU temp,
  reboot-needed, pending OS updates, swap %, CPU % and RAM split into
  *workload processes vs system total*, I/O pressure, root + second disk
  space, disk temps, SSD read/write latency, network rx/tx and cumulative
  totals, peer counts per client.
- **Ideas worth taking (host telemetry only):**
  1. *Workload-vs-system split.* CPU and RAM are shown as the named
     workload's processes (`process_cpu_seconds_total`,
     `process_resident_memory_bytes` per job) stacked under the system
     total, with a "single core cap" reference line (`100 / count(cpus)`).
     That is exactly the question the attorney-PC and fleet views need to
     answer ("is *our* process the load, or something else?"), and it maps
     onto OTel `process.*` metrics keyed by a closed process-role enum.
  2. *Every panel carries a description* saying what the number means and
     what to do when it is bad. The Palantiri's panel spec should make a
     description mandatory (schema field, not optional prose), which also
     feeds the agent-facing parcel text.
  3. *Maintenance-window signals.* The dashboard surfaces "safe to restart
     now?" signals for the workload. The generic analogue for the fleet is a
     per-host "busy" parcel (active proof jobs, open agent lanes, running
     heavy scopes) so agents and the operator know when a host can be
     rebooted or upgraded.
  4. *Implementation-agnostic queries.* Each panel ORs the metric names of
     several interchangeable clients with `or on() vector(0)`. The Palantiri
     gets the same effect without the query sprawl by normalising names at
     the collector (one name per signal), not in dashboard PromQL.
- **Defects not to repeat:**
  - Hard-coded, empty selectors (`device=""`, `chip=""`, `sensor=""`) that
    each operator must hand-edit; no `host`/`device` template variables.
  - RAM panels use unit `bits` for byte-valued series (8× wrong axis).
  - Cumulative counters shown raw in stat panels ("Total Net I/O" since
    boot, workload activity totals that reset on restart).
  - `irate` in stat panels and long OR-chains that silently pick whichever
    client happens to exist, hiding a missing exporter instead of flagging
    it as "no data".
  - No staleness signal: a stopped exporter shows the last value, not an
    alert.
- **Reuse verdict: idea source for host views; dashboard not adopted.**

## Implications for the decomposition

- Neither dankserver dashboard is a starting template. New dashboards are
  designed from the Palantiri's own signal schema and proven with tests
  (restart survival, no-data guards, label-cardinality budget), then
  generated as code (typed Foundation-SDK pipeline or the dankserver
  provisioning path), never hand-built in the UI.
- Kept from them: the Linux update/reboot textfile signals, the
  agent-workload signal list, the workload-vs-system CPU/RAM split with a
  single-core reference line, mandatory panel descriptions, and a per-host
  "busy / safe to restart" signal. Kept as lessons: the counter-reset and
  series-expiry defects above.
