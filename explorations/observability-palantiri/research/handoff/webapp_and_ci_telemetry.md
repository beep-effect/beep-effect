# Web app (Next.js + Effect on Vercel) and CI (GitHub Actions + Turborepo) telemetry into one OTLP pipeline

Research date: 2026-10-14. All Vercel doc pages cited carry `last_updated` stamps from 2026-08 to 2026-09 unless noted.

## Q1. Vercel in 2026: drains, tracing, @vercel/otel, plan gating, pricing, coexistence with Effect's OTel SDK, and how to get data off-platform to a tailnet-only backend

### Takeaway
Vercel Drains (logs, traces, Speed Insights, Web Analytics) are Pro/Enterprise only, cost $0.50/GB (measured as uncompressed JSON), and push only to a **public HTTPS** endpoint (OTLP/HTTP only for traces, JSON/NDJSON for logs). The one hard constraint: Trace Drains and Session Tracing work only when the app is instrumented through `@vercel/otel`. A hand-built SDK (for example Effect `NodeSdk` alone) loses them. A Vercel function cannot reach a tailnet-only collector directly, so you need a public authenticated ingress: Tailscale Funnel, a small cloud collector, or a SaaS backend.

### Cited Findings
**Drains: types, gating, price**
- Drain data types: Logs (runtime, build, static), Traces (OpenTelemetry format), Speed Insights (requires Speed Insights Plus, custom endpoints only), Web Analytics (custom endpoints only), Connect events, and Audit Logs (Enterprise only). — [Vercel: Working with Drains (updated 2026-09-01)](https://vercel.com/docs/drains)
- Drains require Pro or Enterprise. Hobby and Pro Trial must upgrade. Price is the same for every data type: **$0.50 per GB of "Drains Volume"**. Billed GB is "the uncompressed JSON serialization of each drained record", so protobuf or compressed delivery bills higher than the bytes the receiver sees. — [Vercel: Working with Drains](https://vercel.com/docs/drains)
- Each drain carries one schema (`log` v1, `trace` v1, `analytics` v2, `speed_insights` v1, `audit_log` v1, `connect` v1). Drains can be created through the REST API and their delivery validated before go-live. — [Vercel: Working with Drains](https://vercel.com/docs/drains)
- Custom endpoint delivery: HTTPS POST, the endpoint must return 200, payloads batch up to 1 MB. Formats: logs JSON/NDJSON, traces JSON or Protobuf over OTLP/HTTP, Speed Insights and Analytics JSON/NDJSON. Optional `x-vercel-signature` verification secret. **Custom headers** are supported (bearer tokens, API keys), which makes an authenticated OTLP gateway feasible. — [Vercel: Using Drains (updated 2026-09-17)](https://vercel.com/docs/drains/using-drains)
- Log and trace drains support sampling rules (by environment, percentage, and optional path prefix). Rules apply top to bottom. Unmatched requests are dropped. With no rules, 100% is forwarded. — [Vercel: Using Drains](https://vercel.com/docs/drains/using-drains)
- A drain shows as errored, and the team gets an email, when more than 80% of deliveries fail or there are more than 50 failures in the past hour. — [Vercel: Using Drains](https://vercel.com/docs/drains/using-drains)
- Logs emitted during traced requests (`console.log`) are automatically enriched with `traceId` and `spanId`. This does not apply to build logs. — [Vercel: Using Drains](https://vercel.com/docs/drains/using-drains)
- Trace Drains use **OTLP/HTTP only**. gRPC (4317) is not supported, so target `:4318/v1/traces`. Vercel adds the resource attributes `vercel.projectId` and `vercel.deploymentId`. — [Vercel: Trace Drains Reference (updated 2026-08-21)](https://vercel.com/docs/drains/reference/traces)
- Native drain integrations in the Marketplace include Dash0 (logs) and Braintrust (traces). — [Vercel: Using Drains](https://vercel.com/docs/drains/using-drains)

**Tracing on Vercel (infra spans, always-on, limits)**
- Vercel instruments infrastructure spans (routing, middleware, caching, function lifecycle) and outbound fetch spans with no code changes. Framework spans and custom spans require `@vercel/otel`. — [Vercel: Tracing (updated 2026-09-16)](https://vercel.com/docs/tracing)
- Sampling is whole-trace: one keep-or-drop decision per trace, so traces are never partial. Always-on tracing and Trace Drains have **separate rule sets**. With no rules, always-on collects nothing while a Trace Drain forwards everything. — [Vercel: Tracing](https://vercel.com/docs/tracing)
- Inbound `traceparent`: a span is emitted only if both the inbound sampled flag and Vercel's sampling rules say sample. An upstream "not sampled" always drops. — [Vercel: Instrumentation (updated 2026-09-15)](https://vercel.com/docs/tracing/instrumentation)
- Limits: 10 MB of compressed trace data per traced request. Spans over 1 MB compressed are truncated, largest attributes first, each marked `<attr>.truncated=true`, and dropped if they still exceed the limit. **Custom spans from Edge-runtime functions do not appear in traces, however they are collected.** — [Vercel: Tracing](https://vercel.com/docs/tracing)
- Always-on tracing is in Beta on Hobby, Pro, and Enterprise, billed in span units after sampling. Hobby includes 1M span units/month. Pro costs $0.50 per 1M, Enterprise from $0.50 per 1M. One span unit is 2 KB. Beta retention: Hobby 1 hour, Pro 1 day, Enterprise 3 days. Up to 10 sampling rules per project, also scriptable with `vercel traces config`. — [Vercel: Always-on Tracing (updated 2026-08-24)](https://vercel.com/docs/tracing/always-on-tracing)
- Sentry SDK v8+ installs its own OpenTelemetry setup, which conflicts with `@vercel/otel` and breaks propagation. The fix is Sentry's custom-setup mode or `skipOpenTelemetrySetup: true`. — [Vercel: Tracing](https://vercel.com/docs/tracing)

**@vercel/otel and custom SDK coexistence**
- **Limitation:** "If your app uses manual OpenTelemetry SDK configuration without the usage of `@vercel/otel`, you will not be able to use Session Tracing or Trace Drains." — [Vercel: Instrumentation](https://vercel.com/docs/tracing/instrumentation)
- `@vercel/otel` defaults: it picks the export path automatically and uses a Vercel tracing integration when one is configured, otherwise an OTLP exporter set through env vars. It uses W3C Trace Context propagators, traces all requests by default (a `traceSampler` can reduce that), adds resource attributes (`deployment.environment.name`, `cloud.provider`, `vcs.ref.head.name`, `vercel.*`, `service.version`), and enables fetch instrumentation (`propagateContextUrls`, `dontPropagateContextUrls`, `ignoreUrls`). `traceExporter` and `spanProcessors` let you add your own export path. — [vercel/otel README](https://github.com/vercel/otel/blob/main/packages/otel/README.md)
- Next.js docs: a manual `NodeSDK` "is not compatible with edge runtime", so import it only when `process.env.NEXT_RUNTIME === 'nodejs'`. "If edge runtime support is necessary, you will have to use `@vercel/otel`." — [Next.js: OpenTelemetry guide (updated 2026-08-06)](https://nextjs.org/docs/app/guides/open-telemetry)
- Effect v4 `@effect/opentelemetry` `OtelTracer.layerGlobal` / `layerGlobalTracer` / `layerGlobalProvider` install an Effect tracer backed by the **already-registered global OTel TracerProvider**. The module creates no exporters or processors, so spans export only if the provider was configured elsewhere. Effect parents take precedence over active OTel spans. `withSpanContext` and `makeExternalSpan` continue a remote trace and should preserve `traceFlags` and `traceState`, otherwise sampling defaults to sampled. `currentOtelSpan` works with both the OTel API and the lightweight OTLP module. — [Effect v4 API: OtelTracer](https://effect.website/docs/v4/api/opentelemetry/OtelTracer)
- Effect v4 also ships SDK-free OTLP exporters: `effect/observability` `Otlp.layer({ baseUrl, headers, resource, *ExportInterval, maxBatchSize, shutdownTimeout, ... })` posts to `/v1/{logs,metrics,traces}` and requires an `HttpClient` plus `OtlpSerialization`. `layerJson` and `layerProtobuf` fix the format. `layerFromConfig` reads standard OTel configuration. — [Effect v4 API: Otlp](https://www.effect.website/docs/v4/api/effect/observability/Otlp); [Effect v4 API: OtlpTracer](https://www.effect.website/docs/v4/api/effect/observability/OtlpTracer)
- Effect `NodeSdk.layer` enables tracing, metrics, and logging only for the signals you give processors or readers. `WebSdk` is the browser counterpart. — [Effect v4 API: NodeSdk](https://effect.website/docs/v4/api/opentelemetry/NodeSdk); [Effect v4 API: WebSdk](https://www.effect.website/docs/v4/api/opentelemetry/WebSdk)

**Getting off Vercel to a private backend**
- Vercel Static IPs (fixed egress for allowlisting) cost **$100/month per project** plus Private Data Transfer at regional rates, on Pro/Enterprise. — [Vercel: Networking/Static IPs](https://vercel.com/docs/networking/static-ips) (price confirmed in the search snippet of the Vercel networking page; third-party corroboration: [QuotaGuard, 2026](https://www.quotaguard.com/blog/vercel-static-outbound-ip-github-allowlisting))
- Tailscale Funnel exposes a tailnet service publicly on **ports 443, 8443, or 10000 only**, TLS only, on tailnet-domain DNS names. Bandwidth limits apply and cannot be configured. It needs MagicDNS, HTTPS certs, and a `funnel` node attribute in the policy. — [Tailscale: Funnel docs](https://tailscale.com/kb/1223/tailscale-funnel)
- No OTel Collector receiver exists for Vercel's JSON/NDJSON log-drain format. Vendors terminate it themselves: SigNoz uses a JSON custom endpoint, Elastic runs a managed `/vercel` endpoint, and Mezmo documents a syslog path. — [SigNoz: Vercel to SigNoz](https://signoz.io/docs/userguide/vercel-to-signoz/); [Elastic: Vercel OTel integration](https://www.elastic.co/docs/reference/integrations/vercel); [Mezmo: Vercel](https://docs.mezmo.com/docs/ingestion-integrations/vercel.md)
- The contrib `webhookeventreceiver` (beta, logs only) accepts arbitrary HTTP POSTs as log records. It supports `required_header` (a shared-secret gate), `split_logs_at_newline` (NDJSON), JSON-boundary splitting, and header-to-attribute conversion, and is meant to pair with the transform processor. It can ingest Vercel NDJSON log drains into a Collector. — [otel-collector-contrib webhookeventreceiver README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/webhookeventreceiver/README.md)

### Inferences
- **Recommended Vercel server topology:** keep `@vercel/otel` as the owner of the global TracerProvider in `instrumentation.ts`, which keeps Trace Drains, Session Tracing, and Edge support. Layer Effect on top with `OtelTracer.layerGlobal` in the Effect `ManagedRuntime` used by route handlers and server actions, so Effect spans join Next's root `GET /route` span. Do **not** also start Effect `NodeSdk` in the same process. Two providers means double registration and loses Vercel drains. Effect's SDK-free `Otlp.layer` stays an option for Effect-only workers outside Vercel.
- Two egress paths exist. (a) A **Trace Drain** to a custom endpoint gets infra, fetch, framework, and Effect spans post-sampling, billed at $0.50/GB with no export code in the function and no cold-start or flush cost. (b) **In-function OTLP export** through a `traceExporter` / extra `spanProcessors` costs function time, because the batch has to flush before the function freezes, and misses Vercel infra spans. Path (a) fits a small shop better. Path (b) only makes sense when you need metrics or logs signals that drains do not carry as OTLP.
- **Tailnet reachability:** Vercel functions and drains are on the public internet, so the homelab needs a public authenticated ingress. Options, from cheapest up:
  1. **Tailscale Funnel** on 443 to a Collector `otlphttp` receiver plus `webhookevent` receiver, with a bearer-token gate (Collector `bearertokenauth` extension or a reverse proxy) and the drain signature check. Free, but bandwidth is capped and unconfigurable, and the homelab becomes a public endpoint.
  2. A **tiny cloud VM / Fly / Cloudflare-fronted Collector gateway** that receives publicly and forwards over Tailscale to the homelab. It decouples availability, can buffer when the homelab is down, and adds one hop.
  3. A **SaaS backend** that is the drain target directly (Grafana Cloud, Dash0, SigNoz, Honeycomb), optionally fanned out back home.
  Static IPs at $100/month per project only make sense for allowlisting and are poor value here. Header auth plus signature verification is enough.
- Vercel bills drains on uncompressed JSON size, so trace-drain sampling rules (for example 10% of prod, 0% on `/health` and static paths) are the main cost lever.

### Gaps
- Whether `@vercel/otel` reads `OTEL_EXPORTER_OTLP_*` env vars natively, and the exact names of its exporter classes (`OTLPHttpJsonTraceExporter` / `OTLPHttpProtoTraceExporter`), were not shown on the README version fetched.
- Whether Vercel "Observability Plus" ($1.20 per 1M events; Pro base fee reported as $10/month; 30-day retention vs 1 day on base Pro) is still required for anything drain-related. Search snippets from Vercel docs conflict on the base fee. See [Vercel: Observability limits and pricing](https://vercel.com/docs/observability/limits-and-pricing) and [Vercel: Observability Plus](https://vercel.com/docs/observability/observability-plus). I did not fetch these directly.
- No first-party documentation found on Fluid-compute-specific flush semantics for in-function OTLP exporters (`waitUntil` behavior with BatchSpanProcessor).
- Exact Tailscale Funnel bandwidth numbers are not published.

## Q2. Browser side: OTLP from the browser, web vitals, RUM / session replay, privacy (oip.law vs todox.ai)

### Takeaway
Browser OTel is usable but young. The official OpenTelemetry Browser SDK had its first release around May 2026, while `sdk-trace-web` and `context-zone` are stable. Browsers can only send OTLP/HTTP, and the collector must allow CORS with tight origins and accept `traceparent`. Grafana Faro is the most complete OSS RUM option (web vitals, errors, OTel spans), but its collector receiver is experimental. Vercel Speed Insights and Web Analytics can be drained only on Pro, and Speed Insights draining also requires Speed Insights Plus.

### Cited Findings
- The OpenTelemetry Browser SIG "just shipped the first release of the OpenTelemetry Browser SDK" (release tag `browser-instrumentation-v0.5.2`, opentelemetry-browser repo), with a core API, baseline auto-instrumentations, and a live sandbox. Upcoming work covers Resource Timing capture and `browser.document.url.full`. — [Datadog OSS OTel news, May 2026](https://opensource.datadoghq.com/otel-news/2026/05/)
- `@opentelemetry/sdk-trace-web` and `@opentelemetry/context-zone` are reported stable (captured 2026-08). Export must be OTLP/HTTP because browser gRPC is unavailable. Flush on `visibilitychange`/`pagehide`, not `unload`. Scope `propagateTraceHeaderCorsUrls` narrowly, and the server must allow the `traceparent`, `tracestate`, and `baggage` headers. — [ollygarden otel-browser agent skill (secondary)](https://tessl.io/registry/skills/github/ollygarden/opentelemetry-agent-skills/otel-browser)
- Direct cross-origin browser requests to remote OTLP endpoints are blocked by CORS. The recommended pattern is a CORS-enabled gateway collector (Grafana Alloy OTLP receiver `cors { allowed_origins, allowed_headers, max_age }`) restricted to the site's origin. — [Embrace blog](https://embrace.io/?p=6917)
- Grafana Faro: `@grafana/faro-web-sdk` captures Web Vitals (LCP, INP, CLS), navigation timing, JS errors, console, custom events, and OTel browser spans, and posts to Alloy or the Faro collector. Alloy `otelcol.receiver.faro` is **experimental** and is required for Grafana Cloud Frontend Observability. A contrib faro receiver with CORS also exists (sample tested on contrib v0.128.0). — [Grafana Alloy: otelcol.receiver.faro](https://grafana.com/docs/alloy/v1.19/reference/components/otelcol/otelcol.receiver.faro/); [Grafana Cloud: instrument Next.js](https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-applications/frontend-observability/get-started/instrument-nextjs/)
- Grafana Cloud Free includes 50k Frontend Observability sessions per month. Pro charges $0.75 per 1k sessions beyond that. — [Grafana pricing](https://grafana.com/pricing/)
- Vercel Speed Insights drains need Speed Insights Plus. Web Analytics drains are custom-endpoint only with a basic sampling rate. — [Vercel: Using Drains](https://vercel.com/docs/drains/using-drains)
- Speed Insights and Web Analytics events bill at about $0.65 per 1M on paid plans. Hobby includes 10k Speed Insights events. — search summary of [Vercel: Speed Insights limits and pricing](https://vercel.com/docs/speed-insights/limits-and-pricing) (not fetched directly; a third-party $10/month figure conflicts)

### Inferences
- **todox.ai (product app):** OTel web SDK (`sdk-trace-web` with fetch and document-load instrumentation), or Effect `WebSdk` for Effect-driven client code, exporting OTLP/HTTP to the same authenticated public gateway. Propagate `traceparent` only to the app's own `/api` origin so browser → route handler → Effect spans form one trace. Add `web-vitals` callbacks recorded as span events or metrics. Faro is the shortcut if the backend is Grafana. Session replay (Faro does not provide one; the alternatives are PostHog, Sentry, or Highlight) needs an explicit opt-in and masking review.
- **oip.law (law-firm marketing site):** minimize. Prefer aggregate, cookieless signals: Vercel Speed Insights and Web Analytics in their own dashboards, or a web-vitals-only beacon with no user identifiers, no replay, and no form-field capture. Session replay on a site where prospective clients may type matter details is a confidentiality and consent risk. Browser telemetry auth is necessarily public (any token shipped to the browser is visible), so rely on origin allowlisting, rate limiting, and sampling at the gateway, not on secrecy.
- Browser trace context carries into Vercel only if Vercel's sampling also keeps the trace. Browser-side head sampling should therefore be at least as permissive as the Vercel rules, or the browser trace orphans its server half.

### Gaps
- No primary source found for GDPR/ePrivacy or state-bar advertising-rule implications of RUM on a law-firm site. This needs legal input, not web research.
- I did not confirm the exact npm package name of the new official OpenTelemetry Browser SDK.
- No source compared Effect `WebSdk` bundle size or zone-context behavior against the plain OTel web SDK.

## Q3. Next.js specifics: instrumentation.ts, instrumentationHook status, App Router span coverage, cold starts, gaps

### Takeaway
`instrumentation.ts` has been stable since Next.js 15.0.0, so `experimental.instrumentationHook` is obsolete. `register()` runs once per server instance before requests. `onRequestError` (also v15) reports server errors with `routeType: 'render' | 'route' | 'action' | 'proxy'`, which covers server actions. Next's built-in spans cover the request root, App Router render, fetch, route handlers, metadata, and module resolution. There is no documented dedicated server-action span, and Edge custom spans do not reach Vercel traces.

### Cited Findings
- Version history: v13.2.0 introduced instrumentation as experimental. v14.0.4 added Turbopack support. **v15.0.0 made `instrumentation` stable and introduced `onRequestError`.** — [Next.js: instrumentation.js reference (updated 2026-06-09)](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation)
- `register()` is called once when a new server instance starts and must complete before the server handles requests. It may be async. The file works in Node and Edge, branching on `process.env.NEXT_RUNTIME`. — [Next.js: instrumentation.js](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation)
- `onRequestError(error, request{path,method,headers}, context{routerKind, routePath, routeType: 'render'|'route'|'action'|'proxy', renderSource, revalidateReason, renderType: 'dynamic'|'dynamic-resume'})`. Async work inside it must be awaited. The error may be React-processed, so use `digest`. — [Next.js: instrumentation.js](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation)
- Default spans (`next.span_type`): `BaseServer.handleRequest` (root `[method] [route]`), `AppRender.getBodyResult` (render route (app)), `AppRender.fetch`, `AppRouteRouteHandlers.runHandler` (executing api route (app)), `Render.getServerSideProps`/`getStaticProps`/`renderDocument`, `ResolveMetadata.generateMetadata`, `NextNodeServer.findPageComponents`, `NextNodeServer.getLayoutOrPageModule`, `NextNodeServer.startResponse` (zero-length TTFB marker). Custom attributes: `next.route`, `next.rsc`, `next.page`, `next.segment`. `NEXT_OTEL_VERBOSE=1` emits more spans. `NEXT_OTEL_FETCH_DISABLED=1` disables the fetch span so another fetch instrumentation can replace it. — [Next.js: OpenTelemetry guide](https://nextjs.org/docs/app/guides/open-telemetry)
- Next.js 13.4+ propagates incoming OTel context automatically. — [Vercel: Instrumentation](https://vercel.com/docs/tracing/instrumentation)
- The Next.js guide recommends `@vercel/otel` (with `@opentelemetry/sdk-logs`, `@opentelemetry/api-logs`, `@opentelemetry/instrumentation`) and says it works both on Vercel and self-hosted with a Collector. — [Next.js: OpenTelemetry guide](https://nextjs.org/docs/app/guides/open-telemetry)

### Inferences
- **Server actions** run under the root request span (POST to the page route) plus render spans, with no `executing server action` span type listed. Wrap each action body in an Effect `Effect.fn("action.name")` span to get named, typed spans. `onRequestError` with `routeType: 'action'` gives error capture.
- **Cold starts:** `register()` runs per new server instance, so its duration is effectively the cold-start init cost. Recording a `process.start` span or metric inside `register()` (with `faas.coldstart=true`) is a cheap way to see cold starts. No first-party doc describes a built-in cold-start span, so treat Vercel's infra spans as the source of truth for invocation lifecycle.
- Keep Effect runtime construction (`ManagedRuntime.make(layer)`) at module scope, not per request, so layer build cost lands once per instance and shows up as part of cold start.

### Gaps
- No source found listing a dedicated server-action span type or PPR-specific span types beyond `renderType: 'dynamic-resume'` in `onRequestError`.
- Behavior of Next's AsyncLocalStorage-based OTel context vs Effect's fiber-local parent span when Effect code calls back into non-Effect OTel-instrumented libraries is not documented beyond "Effect parents take precedence".

## Q4. CI: GitHub Actions and Turborepo to OTel; CI/CD semconv; test results to OTLP; where ephemeral runners send data

### Takeaway
There are three complementary layers:
1. **Pipeline/job/step traces with zero workflow edits** through the Collector contrib `githubreceiver` (alpha), which needs a publicly reachable webhook. Alternatively, a `workflow_run`-triggered exporter action (`dash0hq/otel-cicd-action`, formerly corentinmusard) that needs only egress.
2. **Turborepo `experimentalObservability.otel`** for run and task metrics (cache hit/miss, durations), metrics only, no traces.
3. **Test-level spans** from Vitest's experimental OpenTelemetry support, or JUnit → OTLP through the inception-health action pair.

CI/CD semconv is at Release Candidate. Ephemeral GitHub-hosted runners can join the tailnet as ephemeral tagged nodes through `tailscale/github-action@v4` with OIDC workload identity, so push-style CI telemetry can stay tailnet-only. The webhook-based receiver cannot.

### Cited Findings
**Semantic conventions**
- The CI/CD semantic conventions (spans, metrics, logs) are at **Release Candidate** status. — [OTel semconv: CI/CD](https://opentelemetry.io/docs/specs/semconv/cicd/)
- Pipeline run span: name `{action} {pipeline}`, kind SERVER, required `cicd.pipeline.result`, `error.type` on failure/error, opt-in `cicd.pipeline.action.name` (BUILD, RUN, SYNC). Task run span: kind INTERNAL, required `cicd.pipeline.task.name`, `cicd.pipeline.task.run.id`, `cicd.pipeline.task.run.result`, `cicd.pipeline.task.run.url.full`. Result enum: `cancellation`, `error`, `failure`, `skip`, `success`, `timeout`. — [OTel semconv: CI/CD spans](https://opentelemetry.io/docs/specs/semconv/cicd/cicd-spans/)

**GitHub Actions exporters**
- `githubreceiver` (otelcol-contrib, **alpha**): one org-level webhook on `workflow_run` and `workflow_job`. Workflow → job → step spans with deterministic IDs from the run ID and check-run ID. Config: `webhook.endpoint` (e.g. `0.0.0.0:19418`), `path: /events`, `secret`. A `scrapers` block is required by validation even for tracing-only use. **The collector must be publicly reachable for GitHub webhooks.** The author recommends IP allowlisting or a WAF on GitHub's webhook ranges, plus pinning the collector version. — [CNCF blog, George Sims, 2026-09-08](https://www.cncf.io/blog/2026/09/08/distributed-tracing-for-ci-pipelines-without-touching-a-single-workflow-file/)
- The same receiver also scrapes VCS metrics through GitHub's REST and GraphQL APIs. — [OneUptime, 2026-02-06](https://oneuptime.com/blog/post/2026-02-06-github-receiver-opentelemetry-collector/view); [SigNoz: GitHub Actions traces](https://signoz.io/docs/cicd/github/github-actions-traces)
- The krzko actions (`setup-telemetry`, `run-with-telemetry`, `export-job-telemetry`) generate deterministic trace and span IDs (from run ID and attempt, and job name) designed to line up with githubreceiver traces. This lets in-job spans (build commands) attach to webhook-derived job spans. — [krzko/setup-telemetry](https://github.com/krzko/setup-telemetry); [krzko/run-with-telemetry](https://github.com/krzko/run-with-telemetry)
- `corentinmusard/otel-cicd-action` now resolves to **`dash0hq/otel-cicd-action`** (the repo appears to have moved). It exports a completed workflow run as a trace, via a `workflow_run` trigger or a final job. It "must be run when the workflow is completed". Inputs: `otlpEndpoint` (https/http/grpc schemes), `otlpHeaders`, `otelServiceName`, `runId`, `extraAttributes`, `githubToken`, `otlpInsecureSkipVerify`. It claims CI/CD semconv compliance and adds `github.head_commit.*` and `service.instance.id` per attempt. Permissions: `actions: read` and `contents: read` (private repos), plus optional `pull-requests: read` and `checks: read`. Examples use `@v4`. — [dash0hq/otel-cicd-action](https://github.com/corentinmusard/otel-cicd-action)
- `inception-health/otel-upload-test-artifact-action` converts a JUnit report into an OTLP trace file and uploads it as an artifact. Inputs: `jobName`, `stepName`, `path` (glob), `type=junit`, `otelServiceName`. The companion `otel-export-trace-action` downloads it in a `workflow_run` workflow, links it to the producing step span, and exports. No releases are listed and there are 8 open PRs, so maintenance is low. — [inception-health/otel-upload-test-artifact-action](https://github.com/inception-health/otel-upload-test-artifact-action)
- Honeycomb `gha-buildevents`: spans per step or command and always sends a build trace even on failure. The newer version starts the trace in the first job and ends it in the last job, with unique step IDs. Older kvrhdn variant is Linux-only. — [Honeycomb: build pipelines](https://docs.honeycomb.io/integrations/build-pipelines); [kvrhdn/gha-buildevents](https://github.com/kvrhdn/gha-buildevents)
- `otel-cli` (equinix-labs): `exec`, `span`, `span background`/`event`/`end`, and `server tui`/`json`. It honors a `TRACEPARENT` env var and `{{traceparent}}` substitution. Endpoint comes from `OTEL_EXPORTER_OTLP_ENDPOINT`: bare host:port means gRPC, `http(s)://` means HTTP, and `http/json` is unsupported. Badged "experimental", one release maintainer. — [equinix-labs/otel-cli](https://github.com/equinix-labs/otel-cli)

**Turborepo**
- Turborepo 2.8.13 added experimental observability with an OpenTelemetry backend (plus an example Grafana dashboard). — [newreleases: turbo 2.8.13](https://newreleases.io/project/npm/turbo/release/2.8.13)
- Config requires `futureFlags.experimentalObservability: true`. `experimentalObservability.otel` fields: `enabled`, `protocol` (`grpc` default or `http/protobuf`), `endpoint` (must be https), `headers`, `timeoutMs` (10000), `intervalMs` (15000, with a final flush at run end), `resource`, `metrics.runSummary` (default true), `metrics.taskDetails` (default false), `metrics.runAttributes.{id,scmRevision}`, `metrics.taskAttributes.{id,hashes}`, and `useRemoteCacheToken` (sends the remote-cache bearer token as auth). Env overrides use the form `TURBO_EXPERIMENTAL_OTEL_*`. Run metrics cover duration, tasks attempted/failed/cached, exit code, and SCM branch. Task metrics cover duration and cache hit/miss with source. **Metrics only. Traces are not documented.** — [Turborepo: configuration reference](https://turborepo.dev/docs/reference/configuration)
- A later commit made run and task ID attributes opt-in for cardinality control and removed `turbo.task.cache_time_saved_ms` from metric attributes (it stays in the run summary JSON). — [turborepo commit a73b432 via SemanticDiff](https://app.semanticdiff.com/gh/vercel/turborepo/commit/a73b43241b6b1f8d32ca9fb12eae7f8f2afbff70)

**Tests**
- Vitest experimental OpenTelemetry: `test.experimental.openTelemetry: { enabled: true, sdkPath: './otel.js' }`. The SDK module must start itself and default-export the SDK so Vitest can flush and shut it down. It instruments the main process and each worker. Adds startup cost per worker unless isolation is off. Fake timers must be reset. Browser mode propagates context and takes a separate `browserSdkPath`. — [Vitest: OpenTelemetry guide (v4 docs)](https://v4.vitest.dev/guide/open-telemetry); [main docs](https://main.vitest.dev/guide/open-telemetry)

**Ephemeral runner → tailnet**
- `tailscale/github-action@v4` creates an ephemeral node per run that is logged out and removed after the workflow. Auth options: **workload identity federation via GitHub OIDC (recommended; needs `id-token: write`, `auth_keys` scope)**, an OAuth client, or a reusable, ephemeral, tagged auth key. Tags are required and drive ACLs. `ping` waits up to 3 minutes for connectivity. Works on GitHub-hosted and self-hosted runners. Page last validated 2026-01-30. — [Tailscale: GitHub Action](https://tailscale.com/kb/1276/tailscale-github-action)

### Inferences
- **Recommended CI shape for a tailnet-only backend:**
  - In each heavy workflow, add `tailscale/github-action@v4` (OIDC, tag `tag:ci`, ACL limited to the collector's `:4318`) early in the job. Then point `TURBO_EXPERIMENTAL_OTEL_ENDPOINT` (http/protobuf), Vitest's OTel SDK, and otel-cli at the tailnet collector over MagicDNS HTTPS (Turbo requires `https://`, and Tailscale serve certs supply it).
  - For whole-run traces, a `workflow_run` job running `dash0hq/otel-cicd-action` (also on a Tailscale-joined runner) exports the finished run's workflow/job/step tree, again egress-only.
  - The `githubreceiver` route is the only zero-edit option, but it needs **inbound** public reachability. That means Funnel plus webhook secret, or a public gateway with GitHub IP allowlisting, which conflicts with tailnet-only unless you accept a Funnel endpoint.
- Tailscale join adds seconds to minutes per job (`ping` can wait up to 3 minutes), so join only in jobs that emit telemetry, or run telemetry export from one `workflow_run` job instead of every job.
- Correlating Turborepo metrics, Vitest spans, and the workflow trace needs shared resource attributes, for example `cicd.pipeline.run.id = GITHUB_RUN_ID`, `vcs.ref.head.revision = GITHUB_SHA`, and `service.instance.id = run_id-attempt`, set through `OTEL_RESOURCE_ATTRIBUTES` and Turbo's `resource` field. Deterministic trace IDs (the krzko scheme) let in-job spans parent under webhook or exporter-generated job spans.
- Turbo's `useRemoteCacheToken` is designed for exporting to a Vercel-remote-cache-authenticated endpoint. For a self-hosted collector, use explicit `headers` instead, and keep `taskAttributes.hashes` off to avoid cardinality blowup.

### Gaps
- Grafana's GitHub Actions exporter (as named in the brief) was not located in this pass. Grafana's GitHub data source or an "exporter" may exist, but it was not verified.
- Turborepo remote-cache analytics (Vercel dashboard cache hit stats) and the `--summarize` JSON run-summary schema in 2026 were not fetched. I did not verify whether `--summarize` still exists alongside the OTel exporter.
- The exact `githubreceiver` config keys were taken from the CNCF blog, not the contrib README. Verify them against the pinned collector version.
- No release dates found for dash0hq/otel-cicd-action v4 or otel-cli.
- CI/CD semconv resource attributes (`cicd.pipeline.name`, `cicd.pipeline.run.id`, `cicd.worker.*`) and metrics (`cicd.pipeline.run.duration`, etc.) were not visible on the spans page fetched. They live on the registry and metrics pages, which I did not fetch.

## Q5. Cost and retention shapes for a small shop, and what a single operator actually watches

### Takeaway
At small-shop volume the Vercel side is cheap if sampled: drains at $0.50/GB, always-on tracing at $0.50 per 1M span units with 1-day Pro retention. Grafana Cloud Free (50 GB logs, 50 GB traces, 10k series, 50k frontend sessions, 14-day retention) or a homelab LGTM stack covers the backend. A single operator's useful view is short: error rate and p95 per route, web vitals (LCP/INP/CLS p75), deploy markers keyed on `vercel.deploymentId`, and CI duration and cache-hit trends.

### Cited Findings
- Vercel Drains: $0.50/GB on uncompressed JSON size, Pro/Enterprise only. — [Vercel: Drains](https://vercel.com/docs/drains)
- Vercel always-on tracing (Beta): Hobby 1M span units included, Pro $0.50 per 1M span units (2 KB each). Retention: Hobby 1 hour, Pro 1 day, Enterprise 3 days. — [Vercel: Always-on Tracing](https://vercel.com/docs/tracing/always-on-tracing)
- Vercel Observability Plus: $1.20 per 1M events, 30-day retention vs 1 day on base Pro. Enabled by default for teams created or upgraded to paid Pro on or after 2026-04-03. The Pro base fee is reported as $10/month, but Vercel pages conflict. — search summary of [Vercel: Observability limits and pricing](https://vercel.com/docs/observability/limits-and-pricing) (not fetched directly; verify)
- Grafana Cloud Free: 10k active series and 50 GB each of logs, traces, and profiles per month, 14-day retention, 50k frontend sessions. Pro: $19/month platform fee, then logs and traces from $0.05/GB process + $0.40/GB write + $0.10/GB retain, 30-day retention, metrics $6.50 per 1k series with 13-month retention, frontend $0.75 per 1k sessions. — [Grafana pricing](https://grafana.com/pricing/)
- Vercel trace resources carry `vercel.deploymentId`, and `@vercel/otel` sets `vcs.ref.head.name` and `deployment.environment.name`. These are usable as deploy markers and environment split keys. — [Vercel: Trace Drains Reference](https://vercel.com/docs/drains/reference/traces); [vercel/otel README](https://github.com/vercel/otel/blob/main/packages/otel/README.md)

### Inferences
- **Minimal viable dashboard set for one operator:**
  - (1) Per-app RED: request rate, 5xx/`onRequestError` rate, and p95 latency by `next.route`.
  - (2) Web vitals p75 (LCP, INP, CLS) per route for todox.ai, and an aggregate-only view for oip.law.
  - (3) Deploy annotations, from a GitHub deploy-success event or the first-seen `vercel.deploymentId`, overlaid on (1) and (2).
  - (4) CI: workflow duration p50/p95, failure rate by job, and Turbo cache-hit ratio over time.
  - (5) A drain health alert, mirroring Vercel's own >80%-failure notice.
  Alert only on (1) error-rate spikes and drain or collector down. Everything else is a weekly glance.
- **Retention:** short native Vercel retention (1 day) argues for draining anything worth keeping. A homelab backend (e.g. 14 to 30 days traces, longer for metrics) costs disk only. Grafana Cloud Free's 14 days is an adequate offsite fallback.
- **Rough cost sanity check** (inference, not sourced): a low-traffic marketing site plus an early product app likely drains well under 10 GB/month at 10% trace sampling, which is under $5/month in drain fees. The fixed cost is the Pro seat that drains require.

### Gaps
- No authoritative per-request byte size for Vercel log or trace drain records, so GB/month estimates are unsourced.
- Honeycomb, Dash0, and SigNoz Cloud free-tier and retention terms for 2026 were not fetched (they may be covered by the backend-landscape researcher).
- No published "what solo operators watch" study was found. The dashboard list above is practitioner inference.
