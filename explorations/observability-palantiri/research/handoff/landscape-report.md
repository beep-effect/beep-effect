# The Palantiri need wiring, not new capability

The full 2026 surface for a unified beep-effect observability overhaul is already within reach, and most of it is already installed. Effect 4.0.x core ships a dependency-free OTLP exporter for traces, logs and metrics plus a Prometheus exporter. `@beep/observability` wraps nearly all of it. Where the package falls short, the causes are wiring defects and unused layers, not missing capability: a probable layer-ordering bug that can divert OTLP traces into DevTools, a DevTools tracer that never sends span ends, loggers that silently drop log-to-span bridging, and five server layers with zero consumers. Outside the repo, every candidate hub backend speaks OTLP and nearly all ship an official MCP server, so the deferred backend choice is a capacity and operations question that can wait for beep-worker and the incoming Linux box without blocking anything else. The hard constraints come from the edges, not the hub. **Vercel and GitHub webhooks can only push to public HTTPS**, so the tailnet-only design needs one authenticated public ingress. **Claude Code strips `OTEL_*` from its MCP children and ignores repo-level exporter settings**, so the repo-owned MCP server and CLI must carry their own exporter config. **Windows host agents all need an admin install**, so the attorney PC's floor is self-reported telemetry from the MCP server through an in-process allowlist. The research found no published telemetry data for Cursor, Grok Build, the Grok bot box or Muse, and no ethics opinion that addresses software telemetry metadata. Those are the real open items, alongside a handful of operator calls listed at the end.

## Effect v4 already ships the exporter stack beep keeps rebuilding

The v3 OTLP modules moved into core. `@effect/opentelemetry/Otlp*` became `effect/observability/Otlp*`, and `Otlp.layer`/`layerJson`/`layerProtobuf` post to `/v1/{logs,metrics,traces}` with batching, retry, temporary disabling after repeated failures and a final flush on shutdown (migration map (`~/YeeBois/references/effect/effect/migration/v3-to-v4.md`); OtlpExporter.ts (`~/YeeBois/references/effect/effect/packages/effect/src/observability/OtlpExporter.ts`)). `Otlp.layerFromConfig` reads the standard `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_EXPORTER_OTLP_*`, `OTEL_BSP_*` and `OTEL_BLRP_*` variables (otlpEnv.ts (`~/YeeBois/references/effect/effect/packages/effect/src/observability/internal/otlpEnv.ts`)). `PrometheusMetrics.layerHttp` mounts a scrape route on an `HttpRouter`. `@effect/opentelemetry` is now only the bridge to the official OTel JS SDK (`NodeSdk`, `WebSdk`, `OtelTracer`, `OtelLogger`, `OtelMetrics`, `Resource`), and it is needed only to interoperate with third-party OTel-instrumented libraries or a provider someone else registered (opentelemetry/src (`~/YeeBois/references/effect/effect/packages/opentelemetry/src`)). The installed **effect 4.0.2 already has the same `observability` surface as the 4.0.4 reference** ([node_modules/effect/dist/observability](../../../../node_modules/effect/dist/observability)). Beyond the exporters, v4 adds span levels (`CurrentTraceLevel`, `MinimumTraceLevel`) that filter spans the way log levels filter logs, a first-class `ErrorReporter` with `Effect.withErrorReporting`, `Effect.track*` combinators that bind metrics to exits, durations and errors, and automatic HTTP server and client spans tuned through `Context.Reference` knobs (`TracerDisabledWhen`, `SpanNameGenerator`, `TracerPropagationEnabled`) rather than v3 combinators (Tracer.ts (`~/YeeBois/references/effect/effect/packages/effect/src/Tracer.ts`); HttpMiddleware.ts (`~/YeeBois/references/effect/effect/packages/effect/src/http/HttpMiddleware.ts`)).

`@beep/observability` (v0.0.3, about 6.6k LOC) is already v4-native and wraps almost every one of these pieces ([package src](../../../../packages/foundation/capability/observability/src)). Adoption is the problem, not coverage. Across the repo, roughly 20 files import `/CauseRedaction` (mostly `logRedactedCause`), and only **two call sites mount a server layer**: the professional-desktop sidecar uses `layerLocalLgtmServer`, and a CLI RunPod eval uses `layerNodeSdkServerTraces` to reach Phoenix. The HttpApi telemetry middleware, Prometheus scrape layer, ErrorReporter, trace-context helpers and `layerWebSdk` have **no consumers outside the package**. The browser renderer in `agents/client` bypasses `layerWebSdk` and calls `Otlp.layer` directly ([ClientObservability.ts](../../../../packages/agents/client/src/ClientObservability.ts)). Usage counts show the same split. The repo has about 6,031 `Effect.fn("…")` named spans and 77 `Metric.counter` sites, but **zero histograms, gauges, `Effect.track*`, span levels, `Logger.batched`, `Otlp.layerFromConfig` or `effect/ai` telemetry customizations**. All metrics are counters, and token usage exists only as schema fields (about 89 `inputTokens` references), never as a metric.

Four concrete defects should open the first goal. First, `layerLocalLgtmServer` merges `Otlp.layerProtobuf` and `layerFilteredDevTools` as siblings in `Layer.mergeAll`. The DevTools layer captures `Effect.tracer` at build time, so it likely wraps the native tracer, and its `Tracer` output likely overrides the OTLP tracer whenever both are enabled. The fix is `provide`/`provideMerge` ordering, and this needs a live test before it is called a bug ([server/Layer.ts](../../../../packages/foundation/capability/observability/src/server/Layer.ts)). Second, beep's filtered DevTools tracer **sends only the span-start snapshot**. Upstream `DevToolsClient.makeTracer` patches `span.end` and `span.event`, so beep's DevTools view likely shows every span stuck in "Started" ([beep DevTools.ts](../../../../packages/foundation/capability/observability/src/server/DevTools.ts); upstream DevToolsClient.ts (`~/YeeBois/references/effect/effect/packages/effect/src/devtools/DevToolsClient.ts`)). Third, v4's `Logger.layer` **replaces** the default `{defaultLogger, tracerLogger}` set unless `mergeWithExisting: true`. `layerConsoleLogger`, semantica, Dock and the IPC sidecar all replace it, which drops the bridge that turns log lines into span events (Logger.ts (`~/YeeBois/references/effect/effect/packages/effect/src/Logger.ts`); [Logging.ts](../../../../packages/foundation/capability/observability/src/Logging.ts)). The IPC case is deliberate stdout hygiene, but every exporting runtime should re-add `tracerLogger` on purpose. As the privacy section shows, the privileged tier needs it stripped on purpose too. Fourth, 4.0.4 fixes HTTP server spans being lost when a runtime shuts down immediately (#9066). That matters for the CLIs and eval runners that will export their own spans (CHANGELOG (`~/YeeBois/references/effect/effect/packages/effect/CHANGELOG.md`)).

Two traps sit in instructions, not code. The global rule's old HTTP path wording (with the retired `unstable` path segment) predated upstream #8354, which moved those modules to `effect/http` and `effect/http-api`. The export under the retired `unstable` path segment no longer exists in either the installed or the reference package, and `Quality.command.ts` still names it in reason strings (MIGRATION.md (`~/YeeBois/references/effect/effect/MIGRATION.md`); [Quality.command.ts](../../../../packages/tooling/tool/cli/src/commands/Quality/Quality.command.ts)). An agent following the rule literally would write imports that do not resolve. Separately, `effect/ai/Telemetry` applies GenAI-semconv span attributes (`gen_ai.usage.*`, `gen_ai.request.model`) automatically through the Anthropic, OpenAI and OpenRouter providers, but **emits no token metrics** (ai/Telemetry.ts (`~/YeeBois/references/effect/effect/packages/effect/src/ai/Telemetry.ts`)). Token and cost panels have to come from spanmetrics in the collector or from beep's own `Effect.track` counters.

## The backend stays deferred, but Phoenix's role and the LGTM compose's fate are already settled

Deferring the hub until beep-worker and the new Linux box are enrolled costs nothing, because every candidate ingests OTLP over 4317/4318 and nearly every one has an official MCP server. Some facts are already fixed, though. **Phoenix ingests traces only.** It accepts OTLP over HTTP and gRPC, converts to GenAI semantic conventions automatically since May 2026, and now serves a **built-in remote MCP endpoint at `/mcp`**. The `@arizeai/phoenix-mcp` stdio package is maintenance-only ([Phoenix MCP docs](https://www.arize.com/docs/phoenix/sdk-api-reference/typescript/mcp-server.md); [OpenObserve LLM tools survey](https://openobserve.ai/blog/llm-observability-tools/)). Whatever general store wins, Phoenix stays the GenAI and eval lane. The collector **fans out**: GenAI and OpenInference spans go to Phoenix, every span goes to the general trace store, and both are keyed by the same trace_id. Phoenix's ELv2 license only matters if it is offered as a managed service to third parties, which is not the case here.

The stale Grafana LGTM compose is not a hub candidate. `docker-otel-lgtm` bundles a Collector, Prometheus, Tempo, Loki, Pyroscope and Grafana in one container that its README calls **"intended for development, demo, and testing environments"**. It has no Mimir or Alloy and defaults to 2 GB of memory ([grafana/docker-otel-lgtm](https://github.com/grafana/docker-otel-lgtm)). dankserver already runs Prometheus 3, Grafana 13 and a collector, so the image duplicates that box. Its real value is the local dev loop: one container, OTLP on 4317/4318, and **Tempo's MCP server enabled by a single env var** (`TEMPO_EXTRA_ARGS=--query-frontend.mcp-server.enabled=true`) ([Grafana docs: Docker OTel LGTM](https://grafana.com/docs/opentelemetry/docker-lgtm/)). That gives the laptop and worktree loop the same MCP surface as the eventual hub. `layerLocalLgtmServer` should be renamed for what it actually targets, an OTLP sink, and the compose should be retired as a deployment.

When the hub decision comes, it narrows to three shapes, judged on RAM headroom next to the existing stack and on agent query surface:

| Shape | Agent surface | Footprint and maturity | Fit |
|---|---|---|---|
| Stay Grafana: add Loki + Tempo behind Grafana 13 | OSS `mcp-grafana` (40+ tools; read-only and per-category flags) plus Tempo `/api/mcp` | Tempo is on the v3.0 line; Grafana 13 redesigned Loki; AGPLv3 | Keeps one pane, PromQL/TraceQL/LogQL, and the typed TS Foundation SDK for dashboards |
| Victoria*: VictoriaLogs + VictoriaTraces behind Grafana | `mcp-victoriametrics`; a read-only VictoriaTraces MCP (official status unconfirmed) | Lowest RAM by reputation; **VictoriaTraces is pre-1.0 (v0.9.4) and needs lock-step upgrades** | Serves Tempo-compatible APIs so Grafana reads it; TraceQL parity is likely partial |
| ClickHouse: SigNoz or ClickStack | First-party MCP in both (SigNoz since 2026-05-01; ClickStack OSS uses a bearer key) | **4 GB minimum, 8 GB realistic**; SigNoz idles at about 1.6 GB, half of it ZooKeeper | Replaces the Grafana/Prometheus pane rather than extending it |

Sources: [mcp-grafana](https://github.com/grafana/mcp-grafana); [Tempo MCP docs](https://grafana.com/docs/tempo/latest/api_docs/mcp-server/); [VictoriaTraces v0.9.4](https://newreleases.io/project/github/VictoriaMetrics/VictoriaTraces/release/v0.9.4); [SigNoz MCP changelog](https://signoz.io/changelog/2026-05-01-introducing-the-signoz-mcp-server-r5iwnkpxtsz88akwt6abqddn/); [ClickStack MCP docs](https://clickhouse.com/docs/clickstack/mcp); [virtua.cloud footprint comparison](https://www.virtua.cloud/learn/en/tutorials/self-host-signoz-openobserve-vps).

Two pieces of the decision are toolchain facts. The **Grafana Foundation SDK is the only first-party typed TypeScript dashboards-as-code option**; Grafonnet is unsupported, and Perses has only Go and CUE SDKs ([Foundation SDK docs](https://grafana.com/docs/grafana/latest/as-code/observability-as-code/foundation-sdk/); [CNCF Perses](https://www.cncf.io/projects/perses/)). Wrapping it in an Effect Schema `DashboardSpec` fits the repo's schema-first law, and it tilts the decision toward staying on Grafana. ClickStack and SigNoz offer no comparable typed dashboard SDK. Second, the existing collector is **Ansible-managed from the dankserver repo**, and hand-edits get erased on the next run ([p0 attribute contract](../../../../goals/harness-otel-adoption/research/p0-attribute-contract.md)). Every collector change in this overhaul, including fan-out, the redaction fence and the OTLP-to-Prometheus hop, lands in that repo, wherever the hub ends up. Prometheus 3's native OTLP receiver flags and out-of-order ingestion window were not verified. They decide whether a laptop's multi-day offline backlog can be backfilled, and they should be checked before the gateway-to-Prometheus hop is designed.

## Every harness can emit, but only two emit anything documented

The locked rule that every harness emits attributed telemetry and consumes a repo MCP server plus an equivalent CLI meets uneven ground. **Claude Code has the richest native exporter**: OTLP metrics (`claude_code.cost.usage` in USD, `token.usage` split by input, output, cache read and cache creation, `active_time.total`), log events (`api_request`, `tool_result` with duration and sizes, `api_error`, `mcp_server_connection`) and **beta traces** (`claude_code.interaction → llm_request / tool / hook / subagent`). All content flags are off by default ([Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage)). **Codex** exports `codex.*` events and metrics, including token counts on `sse_event`, configured only in user-level `~/.codex/config.toml [otel]`. Project-level `[otel]` is ignored with a warning, and `[analytics] enabled = false` also disables custom metrics exporters ([Codex advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced)). Neither harness is documented as emitting `gen_ai.*` semconv, so a unified agent-sessions view needs a collector-side transform. The research found **no telemetry documentation for Cursor, Grok Build, the Grok bot box or Muse**. For those four, "emits attributed telemetry" may mean a launcher wrapper that emits a session span around the process and the repo CLI's own spans inside it. That is a research task for the exploration's first phase, not a solved problem.

The existing `beep.*` contract is the attribution spine to inherit. v1 pins `beep.repo`, `beep.branch`, `beep.task_class`, `beep.goal_slug`, `beep.schema_version` and `host.name`, injected through `OTEL_RESOURCE_ATTRIBUTES` by a launcher wrapper. It bans session ids, paths and prompt-derived values from metric labels, and it lets live dashboards read native OTel while the transcript pipeline stays the analytical system of record ([p0 attribute contract](../../../../goals/harness-otel-adoption/research/p0-attribute-contract.md)). Its recorded gap still stands: Codex `span_attributes` is static user config that applies to traces only, so **Codex metrics cannot carry per-checkout attribution**. A multi-provider fleet widens that gap. The overhaul should bump the contract to v2 and add the fields the fleet now needs: `beep.harness` (since `service.name` varies by vendor), `beep.provider_account` (the quota pool), `beep.lane`, and `beep.tier` for the privacy work. It should also give the contract the typed home v1 deferred, an Effect Schema in `ai-metrics`, so the SDK allowlists, collector config and dashboards all derive from one artifact.

Three Claude Code behaviours shape the repo MCP server and CLI. **Exporter vars in repo `.claude/settings.json` are ignored, and Claude Code does not pass `OTEL_*` to the Bash tool, hooks or MCP servers** ([Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage)). The repo server and CLI therefore need their own exporter config, through a repo config file or a `BEEP_OTEL_*` prefix, or their spans vanish. On the other side, **Bash subprocesses inherit `TRACEPARENT`**, and `-p`/SDK sessions read an inbound one. A CLI that honours `TRACEPARENT` nests its spans under the agent's tool span for free, which is a strong reason to make the CLI the primary agent path and MCP the path for clients without a shell. Langfuse makes the same recommendation for its own agent skill ([Langfuse MCP docs](https://langfuse.com/docs/api-and-data-platform/features/mcp-server)). For MCP, **SEP-414 is Final** and reserves unprefixed `_meta.traceparent/tracestate/baggage` ([SEP-414](https://modelcontextprotocol.io/seps/414-request-meta)). One user report says Claude Code does not yet populate `_meta` with the session trace ([claudeissues #76391](https://claudeissues.com/issue/76391-feature-propagate-cowork-claude-session-trace-context-prompt-id-into-mcp-tool-ca)), so the server should read `_meta` first and fall back to the HTTP header. It should emit MCP-semconv SERVER spans (`mcp.method.name`, `gen_ai.tool.name`, `mcp.server.operation.duration`). That convention is still Development status and has moved to `open-telemetry/semantic-conventions-genai` ([GenAI MCP conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md)).

The server's job is federation plus context economy, not reimplementation. It should front the self-hostable official servers that accept static tokens over the tailnet: `mcp-grafana` with `--disable-write` and a service-account token file that is re-read per request, Tempo `/api/mcp`, Phoenix `/mcp`, and Netdata's agent-embedded MCP if adopted. It should leave OAuth-only SaaS servers optional, because headless sessions cannot complete an interactive login ([mcp-grafana](https://github.com/grafana/mcp-grafana); [Netdata MCP](https://learn.netdata.cloud/docs/netdata-ai/mcp)). The best-documented output discipline is Axiom's. CSV costs about **29% fewer tokens** than JSON for the same rows, a global cell budget prioritizes summaries, every truncated result carries a "Showing 100 of 2,340 rows" receipt, and auto-binning to about 15 bins cut a histogram from 874 tokens to 127 ([Axiom: MCP for wide events](https://axiom.co/blog/designing-mcp-servers-for-wide-events)). Datadog adds a `max_tokens` cap on every tool, truncation with continuation instructions, and `toolsets`/`omit_tools` filtering at connect time ([Datadog MCP docs](https://docs.datadoghq.com/bits_ai/mcp_server/)). Claude Code caps MCP tool output at about 25,000 tokens by default ([Sume](https://www.sume.com/blog/mcp-tool-exceeds-maximum-allowed-tokens)). The resulting design has a small core of fixed-shape summary cards (`host_health`, `agent_sessions`, `ci_run_summary`, `recent_errors`, `quota_status`), raw PromQL, LogQL, TraceQL and SQL behind an opt-in toolset with hard caps, and a budget receipt on every response. For the CLI, Grafana's **gcx** (GA 2026-07-28: clean JSON or YAML, structured errors, predictable exit codes, auto-detected agent mode) is the contract to copy. `grafanactl` was archived on 2026-06-01 ([gcx GA](https://grafana.com/whats-new/2026-07-28-gcx--the-cli-for-you-and-your-ai-agents--now-generally-available/)).

LLM quota is a Palantiri signal, but no harness exports quota-window state. Claude Code supplies per-account cost and tokens (`OTEL_METRICS_INCLUDE_ACCOUNT_UUID` is on by default), and Codex supplies token counts. Neither reports how much of a subscription window is left. A repo-owned poller has to emit the quota gauge, keyed on `beep.provider_account`, and spend has to be joined to it at query time. The gauge should be one of the first real `Metric.gauge` uses in a codebase that today has none.

## The tailnet carries the fleet, but push-or-pull splits by uptime

Use a hybrid topology. Always-on Linux hosts (dankserver, beep-worker, grok-bot-box-1 and the new box) keep being scraped over the tailnet by node_exporter. Scraping is free, gives `up{}` liveness, and matches dashboard 1860 directly. Anything intermittent, meaning the Windows PCs and CI runners, should **push OTLP from a local agent-mode collector** to the dankserver gateway, with a `file_storage`-backed sending queue. The default `retry_on_failure.max_elapsed_time` is **300 seconds**, after which the oldest data drops. A laptop's offline period would be lost unless that default is raised to hours or days with a bounded queue ([OTel Collector resiliency](https://opentelemetry.io/docs/collector/resiliency/)). The only agent with native OTLP for all three signals, a persistent queue and per-process metrics on both Linux and Windows is **otelcol-contrib** or a slim `ocb` build, because the `hostmetrics` `process` scraper covers Windows ([hostmetricsreceiver README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/hostmetricsreceiver/README.md)). The other agents fall short for specific reasons. windows_exporter is pull-only, with its `process` collector off by default. Alloy wraps windows_exporter but installs only as a LocalSystem service with admin rights. Netdata's remote write does not buffer on failure. Beszel tracks containers, not processes, so it cannot answer "is practice-kg-mcp slowing the attorney's PC" ([windows_exporter](https://github.com/prometheus-community/windows_exporter); [Alloy Windows install](https://grafana.com/docs/alloy/latest/set-up/install/windows/); [Netdata exporting](https://learn.netdata.cloud/docs/exporting/exporting-reference)).

That choice carries a dashboard cost. **Dashboards 1860 and 24390 key on exporter metric names** (`node_cpu_seconds_total`, `windows_cpu_time_total`), while OTel `hostmetrics` lands as `system_cpu_time_seconds_total`. Hosts on the OTel agent will show "No data" on the community dashboards ([grafana.com 1860](https://grafana.com/grafana/dashboards/1860/revisions); [24390](https://grafana.com/grafana/dashboards/24390-windows-exporter-dashboard-2025/)). The overhaul has to pick one naming per host class and build the Fleet Overview landing page against it. The thing that actually makes it a single pane is one `host.name`, the MagicDNS short name, set by the `resource` processor on every path.

Tailscale supplies most of the plumbing. **Serve** exposes Grafana and Phoenix tailnet-only with automatic HTTPS and injects `Tailscale-User-Login` headers, which Grafana's auth proxy can use for passwordless login. Those headers are **not populated for tagged devices**, so bots and agents still need API tokens ([Tailscale Serve](https://tailscale.com/kb/1312/serve)). **Tailscale Services** give a stable `svc:` name that survives moving the hub. That suits the deferred backend decision, because `svc:otel-gateway` can move from dankserver to beep-worker without touching any client. Services require tagged hosts and an explicit grant on the `svc:` destination ([Tailscale Services](https://tailscale.com/kb/1552/tailscale-services)). Every node exposes its own Prometheus metrics at `:5252/metrics` after `tailscale set --webclient`, which covers per-host network and DERP health tiles ([client metrics](https://tailscale.com/docs/reference/tailscale-client-metrics)). Grants are deny-by-default and union-combined ([grants syntax](https://tailscale.com/kb/1538/grants-syntax)), so a tag model of `tag:otel-gateway`, `tag:monitor`, `tag:server`, `tag:ci` and `tag:fleet-win` can confine Windows PCs to the gateway's OTLP ports. Prometheus has no native Tailscale service discovery, and the third-party `tailscalesd` maintainer has gone quiet ([tailscalesd](https://pkg.go.dev/github.com/cfunkhouser/tailscalesd)). Five or six hosts are better served by static MagicDNS targets.

Ephemeral CI runners can join the tailnet through `tailscale/github-action@v4` with **OIDC workload identity**, one ephemeral `tag:ci` node per run ([Tailscale GitHub Action](https://tailscale.com/kb/1276/github-action)). The free plan's **1,000 ephemeral minutes per month** covers about a hundred 10-minute jobs. Hard limits are "not currently enforced", and a node that lives longer than four hours counts as one of 50 tagged resources instead ([pricing FAQ](https://tailscale.com/docs/reference/faq/pricing)). Joining can wait up to three minutes for connectivity. The economical pattern is one telemetry-export job per workflow, not a join in every job.

## The privileged tier must be enforced where the collector cannot undo it

The operator has locked the hard part: the strictest tier is shape-only, enforced in the SDK through a per-tier Effect Schema allowlist, with Tailscale node identity and ACL tag as the tier authority. The sources back that placement. The collector-contrib `redaction` processor does delete every attribute not on `allowed_keys` and supports `hmac-sha256`, but it is **beta for traces and alpha for logs and metrics**, and it only scrubs data that has already left the process ([redaction processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/redactionprocessor/README.md)). OTel's own guidance is that the best protection is not collecting sensitive data at all ([OTel: handling sensitive data](https://opentelemetry.io/docs/security/handling-sensitive-data/)). No OTel-native allowlist exporter exists for the JS SDK, so the closed-schema exporter is custom work. In Effect terms it is a `Tracer`/`Logger` wrapper that re-encodes each record through a tier-specific `S.Struct` with no index signatures, drops and counts anything that fails decode, and never forwards it. The collector `redaction` processor, with `allowed_keys` generated from the same schema and `summary: info`, is the second fence. A Weaver live-check or Rego policy at ingest is the third ([OTel Weaver](https://opentelemetry.io/blog/2025/otel-weaver/)).

The research surfaced leak paths that a key allowlist on span attributes alone would miss, and several are Effect-specific. **Exemplars**: attributes removed by a metric View "may still be exported on Exemplars", so the privileged tier needs the `AlwaysOff` exemplar filter ([Metrics SDK spec](https://opentelemetry.io/docs/specs/otel/metrics/sdk/)). **Span events from logs**: v4's default `tracerLogger` copies log annotations and a pretty-printed `effect.cause` onto the current span as events (internal/effect.ts (`~/YeeBois/references/effect/effect/packages/effect/src/internal/effect.ts`)). A cause routinely echoes input, so the privileged exporter must strip span events and log bodies wholesale, which is the opposite of the fix the dev tier needs. **stderr**: stdout is the JSON-RPC channel for a stdio MCP server, so diagnostics go to stderr, and Claude Desktop may persist that stream. The allowlist has to govern stderr logging, not just OTLP. **Semconv attributes that look harmless**: `mcp.resource.uri` can embed a matter name or path, and `jsonrpc.request.id` adds linkability. Opt-In `gen_ai.tool.call.arguments` and `.result` are flagged as sensitive in the MCP conventions themselves ([GenAI MCP conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md)). **Keyed hashes**: HMAC defeats brute force on small input domains, but it still links events. "The same document opened 40 times" is itself a fact about a matter, so the privileged tier should not hash content-derived values at all. Mozilla's rule that combinations of individually benign fields can become highly sensitive is the right lens ([Mozilla Data Collection](https://wiki.mozilla.org/Data_Collection)).

Resource telemetry is safe at the strictest tier if it is coarsened. Windows' minimum "Required" diagnostic level already includes per-app processor time, memory and uptime ([Windows diagnostic data](https://learn.microsoft.com/en-us/windows/privacy/configure-windows-diagnostic-data-in-your-organization)). The risk is the side channel. Exact byte sizes fingerprint documents, and per-call resource samples reveal what was processed. The privileged tier should export process CPU and RSS as 1- to 5-minute min/max/p50/p95 aggregates with no per-tool attributes, power-of-two size buckets, latency histograms keyed only on a shipped tool-name enum, and timestamps rounded to the window. Claude Code's practice of collapsing user skill names to `"custom_skill"` is the precedent for enum-only names ([Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage)).

Making Tailscale the tier authority settles who decides the tier, but three facts constrain how it works. First, **tagging a device requires admin action, and tagged devices lose user identity in Serve headers** ([Tailscale Serve](https://tailscale.com/kb/1312/serve)). The attorney PC becomes an infrastructure node in the operator's ACL, and if it sits on the operator's tailnet it uses one of six free user seats. Second, the authority can be unreachable while the PC is offline or tailscaled is stopped. The SDK must **fail closed to shape-only** whenever it cannot resolve its own tag, and the tier must be stamped on records at capture time, before they reach the spool. A later tier raise then cannot expose anything, because the content was never captured. Third, the precedents agree that lowering needs no authority but raising does. In Windows, the more restrictive of two policies wins, and Claude Code and Codex both refuse to let project config enable or redirect telemetry ([Windows diagnostic data](https://learn.microsoft.com/en-us/windows/privacy/configure-windows-diagnostic-data-in-your-organization); [Codex advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced)). Env vars and flags should be able to lower the tier and never raise it. The tag should set the ceiling, and the binary should refuse an OTLP endpoint that did not come from the same authority.

The attorney PC's delivery floor follows from the Windows facts. Every mainstream agent needs an admin install, and none documents a per-user service. The MCP server should therefore write tier-filtered OTLP-JSON to a local spool under `%LOCALAPPDATA%`, encrypted at rest because the persistent-queue docs promise no encryption ([exporterhelper README](https://github.com/open-telemetry/opentelemetry-collector/blob/main/exporter/exporterhelper/README.md)). A collector ships the spool once one exists, and direct tailnet push is acceptable only while the PC is online. The proof harness is engineering the sources do not supply but do support. Seed fixtures with high-entropy canaries and assert that no exported byte contains them in any encoding, snapshot the key set per event type, keep an on-device negative ledger of dropped key names and counts, keep a hash-chained tier-change log, and give the attorney a `telemetry --show` view modeled on the Windows Diagnostic Data Viewer ([M365 privacy controls](https://learn.microsoft.com/en-us/microsoft-365-apps/privacy/overview-privacy-controls)). The legal frame is Rule 1.6's "reasonable efforts", scaled by sensitivity ([Rule 1.6 Comment 18](https://law.uh.edu/faculty/adjunct/dstevenson/2019/008.pdf); [ABA Op. 477R summary](https://www.lawpay.com/about/blog/protection-of-client-information-what-aba-opinion-477r-means-for-you/)). That supports a strict attorney tier and a lenient family tier, **provided no client data ever reaches the family PC**. If it does, that machine inherits the strict tier. No ethics opinion addresses software telemetry metadata specifically, so the line between software operation and information relating to the representation remains for the attorney to confirm.

## Vercel and GitHub force one public door into a tailnet-only design

On Vercel, the provider question is settled by one limitation: **"If your app uses manual OpenTelemetry SDK configuration without the usage of `@vercel/otel`, you will not be able to use Session Tracing or Trace Drains"** ([Vercel: Instrumentation](https://vercel.com/docs/tracing/instrumentation)). Next.js adds that a manual `NodeSDK` does not run on the edge runtime ([Next.js OTel guide](https://nextjs.org/docs/app/guides/open-telemetry)). `@vercel/otel` must own the global TracerProvider in `instrumentation.ts`, which has been stable since Next.js 15. The Effect `ManagedRuntime` behind route handlers and server actions joins it through `OtelTracer.layerGlobal`, which installs an Effect tracer over the already-registered provider without creating exporters ([Effect v4 OtelTracer](https://effect.website/docs/v4/api/opentelemetry/OtelTracer)). Starting `NodeSdk` as well would mean two providers and the loss of drains. Next has no dedicated server-action span, so each action body should be an `Effect.fn("action.name")`, with `onRequestError` (`routeType: 'action'`) for error capture ([instrumentation.js reference](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation)). Custom spans from Edge functions do not appear in Vercel traces.

Getting the data home is where the tailnet design bends. Drains are **Pro or Enterprise only**, cost **$0.50 per GB measured as uncompressed JSON**, and POST only to a **public HTTPS** endpoint. Trace drains are OTLP/HTTP only, and log drains are JSON or NDJSON. Custom auth headers and an `x-vercel-signature` check are supported ([Vercel: Drains](https://vercel.com/docs/drains); [Using Drains](https://vercel.com/docs/drains/using-drains)). No collector receiver parses Vercel's log format natively, but the contrib `webhookeventreceiver` (beta) with `required_header` and NDJSON splitting can ingest it ([webhookeventreceiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/webhookeventreceiver/README.md)). Static egress IPs cost **$100 per month per project** and are poor value here ([Vercel Static IPs](https://vercel.com/docs/networking/static-ips)). So the overhaul needs exactly one authenticated public ingress. The options are Tailscale Funnel on 443 (free, but public, beta, with unconfigurable bandwidth limits and no identity headers) ([Tailscale Funnel](https://tailscale.com/kb/1223/funnel)), a small cloud collector that relays over the tailnet and buffers while the homelab is down, or a SaaS drain target. Trace-drain sampling rules are the main cost lever. On the browser side, todox.ai can use the OTel web SDK or Effect `WebSdk` behind a CORS-locked gateway. Grafana Faro is the complete OSS RUM shortcut, but its Alloy receiver is experimental ([otelcol.receiver.faro](https://grafana.com/docs/alloy/v1.19/reference/components/otelcol/otelcol.receiver.faro/)). For oip.law, where prospective clients type matter details, the defensible posture is aggregate, cookieless signals with no session replay and no form capture.

CI telemetry splits the same way. The only zero-edit option, the contrib `githubreceiver`, is **alpha and needs inbound public webhook reachability**, so it would use the same public door ([CNCF: tracing CI without touching workflows](https://www.cncf.io/blog/2026/09/08/distributed-tracing-for-ci-pipelines-without-touching-a-single-workflow-file/)). The egress-only alternative is a `workflow_run` job running `dash0hq/otel-cicd-action` on a tailnet-joined runner. It exports the finished workflow, job and step tree and claims CI/CD semconv compliance; that convention is at **Release Candidate** ([otel-cicd-action](https://github.com/corentinmusard/otel-cicd-action); [CI/CD semconv](https://opentelemetry.io/docs/specs/semconv/cicd/)). **Turborepo 2.8.13+ `experimentalObservability.otel` exports metrics only**: run duration, tasks attempted, failed and cached, and per-task cache hit or miss when `taskDetails` is enabled. It requires an `https://` endpoint, which Tailscale Serve certificates supply. Task hashes should stay off to avoid a cardinality blowup ([Turborepo configuration](https://turborepo.dev/docs/reference/configuration)). The active `turborepo-cache-trust-observability` goal is a natural consumer and must be reconciled, not duplicated ([goal README](../../../../goals/turborepo-cache-trust-observability/README.md)). The same applies to the `ci-hang-observability` exploration. Vitest's experimental OpenTelemetry mode adds per-test spans from the main process and every worker, at some startup cost per worker ([Vitest OTel guide](https://v4.vitest.dev/guide/open-telemetry)). To correlate the three layers, every run should set `cicd.pipeline.run.id = GITHUB_RUN_ID`, `vcs.ref.head.revision = GITHUB_SHA` and `service.instance.id = run_id-attempt` through `OTEL_RESOURCE_ATTRIBUTES` and Turbo's `resource` field.

For the local dev loop, docker-otel-lgtm with Tempo MCP is the agent-drivable sink. otel-desktop-viewer exposes a DuckDB-backed JSON-RPC API at `POST /rpc` that a thin MCP wrapper could front, while otel-tui is human-only ([otel-desktop-viewer](https://github.com/CtrlSpice/otel-desktop-viewer); [otel-tui](https://github.com/ymtdzzz/otel-tui)). Effect v4's `DevToolsServer` speaks an unstable newline-delimited JSON protocol that may break in minor releases, so it should be pinned if a repo collector consumes it ([DevToolsServer API](https://effect.website/docs/v4/api/effect/devtools/DevToolsServer)). **WebStorm integration was not researched.** JetBrains' own telemetry policy is documented, but nothing was found on surfacing traces or Effect DevTools inside the IDE ([JetBrains usage statistics](https://www.jetbrains.com/help/idea/settings-usage-statistics.html)). It remains an open research item inside the locked dev-tooling scope.

## What the facts have already decided, and what the operator still owns

Some calls are now forced by the evidence. The exporter stack is Effect-native, and `@effect/opentelemetry` is reserved for Vercel (`OtelTracer.layerGlobal`) and other third-party-provider interop. Phoenix remains the GenAI lane behind collector fan-out, whatever the hub. The LGTM compose retires as a deployment and survives as the laptop sink. The repo MCP server and CLI carry their own exporter config and parent on `TRACEPARENT` and `_meta`. Intermittent nodes push with a persistent queue and a raised retry ceiling, while always-on hosts stay scraped. The privileged tier strips span events, exemplars, URIs and stderr content in-process and fails closed when the tag cannot be resolved. Vercel keeps `@vercel/otel` as provider owner. Collector changes land through the dankserver Ansible repo. The table below separates those from the calls that remain.

| Decided by facts | Still the operator's call |

## Conclusion

The overhaul's center of gravity has moved. A year ago this would have been a backend project. In October 2026, OTLP is universal, official MCP servers are table stakes, and Effect ships its own exporter, so the backend is the least consequential decision left and the operator was right to defer it. The consequential work sits at three seams nobody vendors: the attribution contract (v1 never reached the multi-provider fleet, and Codex still cannot attribute metrics), the in-process privacy fence (the only layer a misconfigured collector cannot undo, and the one where Effect's own default logger is a leak path), and the single public door that Vercel and GitHub force onto a tailnet-only design. Moving `svc:otel-gateway` and the `beep.*` v2 Schema to the front lets every later goal run against stable names while the hub is still undecided.

One implication runs against intuition. The repo CLI matters more to agents than the MCP server does. Claude Code hands `TRACEPARENT` to Bash but strips `OTEL_*` from MCP children, and Langfuse already recommends its skill and CLI over its own MCP. A CLI-first Palantiri gets correctly parented agent traces for free, while the MCP server is the compatibility surface for clients without a shell. The exploration should graduate the CLI goal and the attribution-contract goal first, the privacy-tier goal right behind them (it gates practice-kg-mcp telemetry), and the hub goal last, once the new hardware lands.
