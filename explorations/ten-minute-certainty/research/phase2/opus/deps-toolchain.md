# Phase 2 audit, Opus 5.5 seat: H: dependencies, install, toolchain

Produced 2026-11-09 by a `claude-opus-5-5` (medium) auditor from the shared brief and the phase 1 inventory; read-only. Paths are repository-relative or `~`.

## Verdict

Area H can take roughly 1 minute off the PR critical path and about 70-100 hosted runner-hours a week. It cannot carry the 10-minute target by itself, because its biggest per-job item, the setup tax, is a fixed 30-75 s per job and is parallel rather than serial. I measured two green PR runs (42646019844 and 42656046751): checkout plus setup is 14.0-17.3% of hosted job-seconds and 6.8-7.1% on EC2. By job class it is 68-69% of short hosted lanes (Lint shards, Shadcn, PR Size, Heavy Admission, Ecosystem, Codegen, Nix, Security, SAST), 16-20% of mid lanes, 9-14% of Test Unit shards, 18% of the hosted integration partitions, 32-39% of short EC2 Heavy jobs and 2.7% of the long EC2 jobs. Across 91 hosted jobs the frozen install has p50 34 s, p90 47 s and max 60 s. The same install with `--ignore-scripts` (Security, SAST, Coverage Regression; n=6) takes 15.6-24.3 s, so lifecycle scripts cost about 14 s per hosted job. Only 2.3 s of that is root scripts; the rest is default-trusted dependency scripts (ssh2/cpu-features node-gyp, better-sqlite3 prebuild-install, @pulumi/command, workerd, esbuild x2, and others). In 114 job logs there were zero "postinstall cost" warnings, so the inventory's 31 s ssh2 figure was a one-off. The best levers are: (1) an explicit trustedDependencies allowlist; (2) moving Heavy Admission and PR Size Label onto the pinned compiled CI binary so they skip the install (Admission is on the Heavy critical path, 66-77 s wall, 40-50 s of it setup); (3) trimming unneeded native payloads (duckdb musl binding 87 MB, onnxruntime-node 92 MB that only scratchpad pulls in). Scoped `--filter` installs are worth much less than the inventory claimed: any lane that runs `bun run beep` needs root plus repo-cli, which is 1,687 lock entries, about two-thirds or more of the install. The AMI fast path bakes only the Bun binary, so refreshing it saves about 1 s per job; retire it or drop its lockfile key. The triple typecheck pass is negligible (Turbo check misses average 0.4 s, n=217). Checkout (15-24 s per job, about 40% of the setup tax) is the largest single remaining setup item, but it belongs to the hosted-ci seat.

## Ranked levers

### H-L2. Replace Bun's default trust list with an explicit trustedDependencies allowlist that excludes ssh2, cpu-features and other unneeded native or plugin scripts

- **Mechanism:** Add a `trustedDependencies` array to the root package.json. When it is set, Bun uses it instead of its default list. Allow only packages whose lifecycle scripts a lane needs: candidates are esbuild and workerd if their binaries need install.js, better-sqlite3 only if a test loads it, and msw only if a test runs its postinstall. Leave out ssh2 and cpu-features: testcontainers talks to the local Docker socket (packages/tooling/test-kit/test-utils/src/SqlTest.ts) and ssh2 falls back to pure JS. Leave out @pulumi/command (an infra deploy-time plugin download), msgpackr-extract (an optional speedup), tsc-rs and @mui/x-telemetry. Root prepare/postinstall still run because root scripts are not gated by trust. Regenerate bun.lock. Applies to every hosted job, EC2 job, the head-install preflight and local installs.
- **Grain:** repo. Install configuration is global by nature. The decision is per package (each trusted entry), and every consumer gets the same tree, so no lane-specific layout is introduced.
- **Savings:** basis: derived; hostedRunnerMinPerPrRun: ~6-8 (44 installing hosted jobs x 8-11 s; measured lifecycle delta ~14 s/job minus 2.3 s of root scripts, the remainder attributed mostly to dependency scripts); criticalPathMinPerPrRun: ~0.2 (Heavy Admission install plus the EC2 Heavy install on the Change Profile -> Admission -> Heavy chain); localWallMinPerPublish: ~0.05 (head-install preflight is a fresh node_modules; local CPU is faster, guess 2-4 s); localWallMinPerVerify: ~0.05; cpuSeconds: ~500-700 CPU-s per PR run of node-gyp and script work avoided. Sources: --ignore-scripts jobs 15.6-24.3 s vs scripted jobs p50 33.9 s (runs 42646019844, 42656046751); Lint (lint-b) log root-script timings; bun pm untrusted + node_modules script scan
- **Trust risk:** low. Failure mode: A package whose install script produces a binary that a test loads at runtime (better-sqlite3 native binding, an esbuild or workerd platform binary) is no longer built or verified. Tests would go red rather than falsely green, unless a code path silently degrades: ssh2 without native crypto is slower but functionally equal. Mitigation: Build the allowlist by elimination. Run the full hosted matrix once with the allowlist on a PR (all lanes, ready-for-heavy) and compare test censuses and verdicts with main. Grep test imports for better-sqlite3, ssh2 native and workerd. Add a repo-sanity check that fails when a newly added dependency has an install script and is neither allowlisted nor explicitly denied.
- **Admission gate:** A/B measurement with controls: same head, one run with the allowlist and one without, comparing per-job 'packages installed [Ns]', test census and verdict parity across the whole matrix, followed by a dependency-script census guard in repo sanity.
- **Prior art:** The keytar prebuild-install failure was removed by dropping keytar from @beep/m365 (comment in setup-monorepo-ci). check.yml already uses --ignore-scripts for Coverage Regression, Security and SAST (lines 924, 1721, 1847). No trustedDependencies decision is on record, and no rejection covers this.
- **PR slices:** chore(deps): explicit trustedDependencies allowlist (drop ssh2/cpu-features/pulumi plugin scripts) [S]; chore(quality): repo-sanity guard for untrusted-but-undeclared install scripts [S]
- **Confidence:** medium
- **Open questions:** How much of the ~12 s is ssh2/cpu-features node-gyp versus better-sqlite3 prebuild-install network time? A single hosted job with BUN_DEBUG timing or `--concurrent-scripts=1` timestamps would split it. | Does any test load better-sqlite3 (reachable only through drizzle-orm's optional peer)? | Do esbuild 0.25/0.28 and workerd run correctly without install.js under Bun's optionalDependency platform packages?

### H-L10. Treeless checkout (filter tree:0) in place of blob:none full-history checkout for jobs that only need the merge base and diff

- **Mechanism:** actions/checkout currently uses fetch-depth 0 with filter blob:none. That costs 15-24 s per hosted job (1,009-1,025 job-s per run, about 40% of the setup tax). This is not a shallow checkout: the commit graph stays complete, so merge-base proofs hold. The hosted-ci seat owns it; listed here because it is the largest remaining part of the setup tax.
- **Grain:** repo. Per-job git transport choice. The commit graph is preserved.
- **Savings:** basis: guess; hostedRunnerMinPerPrRun: ~4-8 if checkout halves (about 50 jobs x 8 s); criticalPathMinPerPrRun: ~0.15; localWallMinPerPublish: 0; localWallMinPerVerify: 0. Sources: job step timings, checkout 15-24 s per job in both runs; Lint (lint-b) log 16:34:20.7 to 16:34:37.7

Tools assuming local objects could fail red offline. Mitigation: Replay all consumers of git history (change-profile, coverage base rows, route diff, semantic-delta) on a side workflow and compare outputs and wall time.
- **Admission gate:** A/B measurement with controls on a side workflow: identical consumer outputs and checkout seconds.
- **Prior art:** Shallow checkout was rejected (repository-performance.md:124: no merge-base proof). Treeless keeps every commit, so that rejection does not apply, but the evidence must show it.

### H-L1. Scoped `bun install --filter` for package-scoped hosted lanes (parity experiment only)

- **Mechanism:** For lanes whose work is confined to a known workspace set, install with `bun install --frozen-lockfile --filter './' --filter '@beep/repo-cli' --filter '<affected...>'` on the hoisted linker. Parity experiment design: in one fresh ubuntu-24.04 job on a side workflow, (1) run the full frozen install and record a manifest of node_modules/**/package.json as path, name and version; (2) in a second fresh clone, run the filtered install and record the same manifest. Require subset-and-same-path: every installed package sits at the same hoisted path with the same version, so resolution cannot pick a different copy. Also require that root prepare/postinstall succeed (they need infra/node_modules and the @tsrs and @typescript binaries). (3) Run the lane's command on a forced Turbo miss (no cache read) in both trees and diff the outputs. (4) Confirm Turbo task hashes are identical; they come from the lockfile, so cache hits remain valid. Repeat for each candidate lane class.
- **Grain:** affected-set. Sound only if the partial tree is a same-path subset of the full hoisted tree, which is what the experiment checks. Otherwise a missing or differently placed module could change resolution.
- **Savings:** basis: derived; hostedRunnerMinPerPrRun: ~1 (about 13 short lanes x ~5 s; root plus repo-cli is already 1,687 lock entries, about two-thirds or more of the install, so only the remaining third or less can be saved); criticalPathMinPerPrRun: ~0.05; localWallMinPerPublish: 0 (the preflight must stay a full install; it proves the committed lockfile); localWallMinPerVerify: 0. Sources: closure.py over bun.lock: root 916, repo-cli 1,501, root+repo-cli 1,687 of 3,319 keys (2,336 installed on linux)
- **Trust risk:** medium. Failure mode: Phantom dependencies hidden or changed by a different hoisted layout. On a Turbo miss, a partial tree could resolve another copy of a module and pass where the full tree fails. Cache hits replay full-install verdicts, so the risk sits on misses. Mitigation: Same-path subset check on every run (cheap: compare the manifest against the lock's hoisted plan). At least one lane per run keeps the full install. - **Admission gate:** Parity ledger: the experiment above passes N=10 consecutive PR heads per lane class with zero manifest or output divergence before enforcement.
- **Prior art:** Inventory deps L1 rated high. No rejection on record. Archive and dependency caching are rejected (repository-performance.md:126) and this is not caching.
- **Depends on:** H-L9 (lanes that only need the CLI should move to the binary instead of a filtered install)
- **PR slices:** ci: side-workflow parity experiment for filtered hoisted installs [M]
- **Confidence:** low
- **Open questions:** Does `--filter` on a hoisted linker install root devDependencies when './' is matched, and does it honor overrides and patches? | Which lane classes need neither repo-cli nor root tooling? Probably none in check.yml.

## Contradictions with the phase 1 inventory

- The inventory says the ssh2 postinstall costs 31 s per job (deps L2 'up to 31 s per hosted job'). In 114 green job logs from two runs there were zero 'postinstall cost' warnings, so the 31 s was a single outlier. The real measured lifecycle cost is about 14 s per hosted job (scripted p50 33.9 s against --ignore-scripts jobs 15.6-24.3 s), spread across ssh2, cpu-features, better-sqlite3, @pulumi/command, workerd, esbuild and others.
- Inventory section 1 gives a cold bun install of 44-62 s on ubuntu-24.04. Across 91 hosted jobs, p50 is 33.9 s, p90 46.7 s and max 59.7 s; 44-62 s is the upper tail.
- The inventory rates L1 (scoped --filter install) high. The closure analysis shows root plus repo-cli alone is 1,687 lock entries (about two-thirds or more of the 2,336 installed), and nearly every lane runs `bun run beep`. Scoped installs can save at most about a third of download and extract time; moving CLI-only jobs onto the compiled binary (H-L9) is the better form.
- Inventory sections 1 and 3 call the AMI 'the only warm-image path' that is dead. It bakes only the Bun binary, not dependencies, so its staleness costs about 1.2 s per EC2 job. Its misses come from an unnecessary bun.lock equality key, not from stale dependencies.
- Open question 199 ('Which postinstall is Blocked 1 postinstall'): it is @mui/x-telemetry, and nothing depends on it.
- The inventory's 'setup' figures mix checkout and install. Checkout (fetch-depth 0, blob:none) is 1,009-1,025 job-s per run, about 40% of the setup tax, and is a separate lever (H-L10).
