## 2026-08-10 — D1: Event storage = per-event CAS files

**Question.** How do control-plane events physically live in the repo:
per-event CAS files, branch-scoped JSONL + union merge driver, or a hybrid
(JSONL per run, CAS checkpoint on publish)?

**Answer.** Per-event immutable CAS files: `ops/events/<seq>-<type>-<digest>.json`,
each carrying a parent digest and expected revision. Two children of one head
= a detectable fork surfaced by doctor, never silent last-writer-wins.
Projections (readiness snapshots) are cached with a `sourceTip` digest +
projector version.

**Rationale.** Decisive external evidence: spec-kitty issue #569 lost mission
audit history when its single `status.events.jsonl` hit a git 3-way merge —
exactly the failure mode the driver's two edit lanes + operator parallel
worktrees would reproduce. CAS files make concurrent appends conflict-free
in git and make forks first-class. *Rejected:* branch-scoped JSONL + union
merge driver (driver must be installed in every clone/worktree/CI — a
silent-failure surface); hybrid run-JSONL + publish-checkpoint (extra
machinery before any need is proven; run telemetry can stay in existing
driver/Yeet journals). Yeet's AttemptJournal crash/corruption/dedupe *test
matrix* transfers to file granularity; its storage shape does not.

## 2026-08-10 — D2: Day-0 approval anchor = protected docs-PR merge on digest subjects

**Question.** What makes an approval unforgeable by the gated agent: protected
docs-PR merge, docs-PR + immediate in-toto envelope, or human-signed commit
trailers?

**Answer.** Approval = the merged, review-protected PR whose subject *is* the
approved artifact (DESIGN.md digest, change tree). The packet stores only
references — PR URL + commit SHA + subject digests — and doctor re-derives
staleness whenever subject digests drift. Sigstore/in-toto is deferred until
a consumer outside GitHub's trust boundary exists and will actually verify
(never generate attestations without a fail-closed verifier).

**Rationale.** Lane 4: gitsign-by-default has three practical blockers
(public Rekor identity/timing leak, GitHub "Unverified" UX, verifier bugs in
the TCB — CVE-2024-51746), while GitHub protected review already gives
digest-binding mechanics free (stale-approval dismissal, tip-bound approvals,
merge-base-change dismissal). Matches the existing KSA practice of grill
outcomes landing as docs-PRs before implementation PRs. Empirical constraint
honored: approvals must be few and digest-bound (93% rubber-stamp rate,
~1-in-3 dangerous-action miss rate). *Rejected:* immediate in-toto emission
(costs a CI verifier now for no present consumer); signed commit trailers
(loses stale-dismissal, weaker socially).

## 2026-08-10 — D3: Stage = two derived values; stored `stage` retired

**Question.** Is `stage` a high-water mark or a resume cursor (pass 3 F1), and
does either stay a stored field?

**Answer.** Both readings ship as pure derivations of the D1 event chain:
`furthestStage` (monotonic high-water mark over stage-entered events) and
`resumeStage` (cursor from the last transition event). Manifest carries them
only as clearly-marked generated projection fields regenerated by the single
writer; the ambiguous hand-edited field is retired at migration. Readiness
derives from events + approvals only — artifact presence is never a signal
(pre-seeding is sanctioned practice; pass 3 F2). README convention text
updates to match.

**Rationale.** The stored field is self-contradictory on every sanctioned
loop-back today. *Rejected:* cursor-only (loses the cheap "ever shaped?"
query for portfolio views/tier routing); keeping a stored cursor field
(re-opens the stored-state-drift class the redesign exists to close).

## 2026-08-10 — D4: Tier = computed floor + recorded override

**Question.** What decides Light/Standard/Full and who can move it?

**Answer.** Doctor computes a tier *floor* from the declared change tree —
public-export delta, packages touched, protected-path globs (migrations,
auth/security, CI/build/release) — using existing fallow impact/export-map
machinery. Signals forcing Full: public/serialized/persisted contract
changes, auth/security boundaries, CI/build/release infra, data migrations,
3+ packages. Light: mechanical/docs/tests-only, single package, zero
public-export delta. Agents may raise tier freely; only the operator may
lower below the floor, and that override is itself a recorded, challengeable
event. The auto-approval envelope is bounded by the same signals.

**Rationale.** Designs against both lane-6 failure modes: everything-Full
(status theater) and everything-Light (permission laundering). *Rejected:*
operator-assigned tier with advisory lint (weak against tier drift over a
packet's life); signals-only with no override (blast-radius heuristics have
false positives — e.g. wide mechanical renames — and leave no relief valve).

## 2026-08-10 — D5: Design gate = 5th graduation check; DESIGN.md seeded at graduation

**Question.** Where are the exact change tree + significant-symbol ledger
authored, and when does DESIGN.md exist?

**Answer.** Change tree + significant-symbol ledger become a fifth graduation
definition-of-ready check authored in MAP.md — off-lane, where shaping is
unbounded and cheap. DESIGN.md is seeded at graduation the way SPEC.md seeds
from BRIEF.md, so in-lane cost is a review pass, not authorship.
Exploration-skipping goals author DESIGN.md in-lane — exactly where the D4
tier decision forces an explicit record. Light-tier goals skip DESIGN.md
entirely. Ledger scope per the Codex narrowing: architecturally significant
symbols only, kept living via event-diffed amendments — never a frozen
every-symbol checklist.

**Rationale.** Queueing (pass 3 J, lane 6): front-loading design cuts in-lane
service-time variance in a WIP-capped pipeline; the same gate is nearly free
before graduation and expensive after. *Rejected:* always-in-lane authoring
(pays authorship inside the scarce slot); MAP.md-only with no DESIGN.md
(breaks exploration-skipping goals; no per-goal normative surface for
amendments to diff against).

## 2026-08-10 — D6: First generated-surface flip = ATLAS wholesale + README status blocks

**Question.** Which hand-edited drift surfaces flip to generated in the first
migration PR?

**Answer.** PR one generates `explorations/ATLAS.md` wholesale (plus a lint
that it contains nothing underivable from manifests — mechanizing the
existing "navigation, never doctrine" rule) and regenerates each packet
README's `Stage:`/`Status:` block from the D3 derived values. Trail and
Next-Open-Question lines stay authored prose. PLAN.md phase-status columns
wait for a later ratchet rung.

**Rationale.** ATLAS is doctrine-free by rule, so wholesale generation is
safe; README status blocks are the most common per-packet drift surface and
pure projections of D3. *Rejected:* ATLAS-only (leaves README drift open
during the migration window where confusion costs most); including PLAN
columns (touches every goal packet's PLAN.md in PR one — blast radius and
rollback cost too high for the first flip).

## 2026-08-10 — D7: OPPORTUNITIES.md promoted: schema + fleet roll-up + mechanical writes

**Question.** Does OPPORTUNITIES.md become a schema-validated canonical
artifact, and what writes to it?

**Answer.** Schema-validate the per-packet file (what happened / evidence /
what would have prevented it / disposition / owner); generate a fleet-wide
roll-up projection; contract-and-above design amendments auto-draft an entry
(they represent a design-process miss worth systematizing). Scope narrowed
per the Codex revision: systemic/repeatable process+tooling misses only —
never every implementation-local discovery. The 7+ existing divergent files
migrate cleanup-on-touch. Schema stays light enough to preserve
record-at-the-moment friction receipts.

**Rationale.** The roll-up is where cross-packet patterns (the payoff)
become visible; mechanical amendment-writes need a typed target. *Rejected:*
schema-only (defers the payoff); ad-hoc status quo (7+ divergent formats
already; nowhere typed for mechanical writes to land).

## 2026-08-10 — D8: One packet-core library behind existing command groups

**Question.** New `beep packets` group, shared core behind existing groups,
or goals-only?

**Answer.** One internal packet-core library (transition table, event
journal/fold, derivations, trace projection) consumed by `beep goals` and a
net-new minimal `beep explore --check`/doctor. `set-status` evolves into the
single guarded-transition writer. No `beep packets` fork; no new package
until the core proves it needs one — it lives with the existing goals-CLI
machinery. Exploration checks start read-only (invoked by the /explore
skill), run advisory in CI, then flip blocking through the established
ratchet (pass 3 M1: this is net-new command work, estimated as such).

**Rationale.** Avoids forking vocabulary the fleet knows and conflicts with
KSA Workstream E. *Rejected:* `beep packets` group (vocabulary fork);
goals-only v1 (leaves the D5 fifth graduation check with no mechanical
enforcement).

## 2026-08-10 — D9: Pilot #1 = self-host this packet's graduated goals

**Question.** Which packet first exercises the new machinery in advisory
mode?

**Answer.** The first goal graduated from `packet-system-redesign` is itself
created, transitioned, designed, and closed using the new machinery in
advisory mode. The bootstrap paradox stays resolved per pass 2 C: v1 is
built with the *current* process, then the system adopts onto itself. The
Codex three-pilot set (small feature, cross-package, migration/refactor)
follows as the ratchet widens.

**Rationale.** Tightest feedback loop; gate friction surfaces on the work
that defines the gates. *Rejected:* KSA-first (couples two large
workstreams' schedules); small-unrelated-feature-first (slower learning;
gate friction lands on work that didn't sign up for it).

## 2026-08-10 — D10: Goal closure adopts two-phase done

**Question.** Does goal closure separate "landed" from "closed"?

**Answer.** Yes. Phase 1 = deterministic land (Yeet verify green, PR
merge-ready and merged). Phase 2 = goal CLOSED only when evidence receipts
are sealed against the merged commit's digests and required approval
references verify. Both are derived states in the D1 event fold — closure
without fresh receipts becomes unrepresentable. Landed-not-closed is a
tracked WIP count (no hard cap yet; see D11 metrics).

**Rationale.** AgentOps merge-door analysis: probabilistic review on the
critical merge path thrashes under agent throughput, and "landed feels
done" drift is the observed failure mode; graphnosis map-proof found the
in-repo instance (prose quoting numbers nothing recomputes). Cleanly splits
driver run-state (owns landing) from packet truth (owns closure).
*Rejected:* single-phase with same-PR receipts (forces evidence-sealing
onto the critical path); day-one hard WIP cap (blocking the fleet on a
guessed number before close-latency is measured).

## 2026-08-10 — D11: v1 instrumentation = four core flow metrics, observational only

**Question.** Which metrics ship with the first machinery?

**Answer.** Approval-wait p50/p95, parked-lane age (with park-reason
taxonomy), gate wall-time + cache-hit rate, and amendment-rate-by-tier —
all derivable from artifacts the machinery already produces (events, proof
manifests, PR timestamps); no new telemetry infrastructure. All metrics are
observational, never optimization targets (Goodhart / pass 2 B8). Standing
rule adopted from lane 6: if approval-wait and parked-lane age dominate,
stop adding gates and fix envelopes/memoization first. Defect-escape-by-tier
and token-cost wait for closed-goal volume.

**Rationale.** These four answer the two questions that can kill the
redesign: are the gates affordable, and is the D4 tier floor calibrated
(amendment-rate is the only signal for the latter). *Rejected:* minimal
two-metric set (loses tier calibration); full outcome set (noise at
near-zero early volume invites premature tuning).

## 2026-08-10 — D12: Packets app respects KSA-D; React v2 is a MAP candidate goal

**Question.** How does the operator's read-only React `packets` app enter the
plan, given KSA's ratified do-not-reopen decision D (projector → Mermaid →
static self-contained HTML dashboard, no React build)?

**Answer.** KSA-D stands: static HTML v1 ships first inside KSA scope
(pulse-shaped per D13). The React app becomes a named candidate goal in this
packet's MAP.md, downstream of KSA's projection engine, gated on v1 daily

spec seed: read-only (no mutate endpoints, no drag-and-drop), no
client-side re-derivation of frontier/blocker semantics, one projector
feeding every renderer, `sourceTip` staleness as first-class chrome.

**Rationale.** Lane 7: single-file HTML boards are a finished product shape;
the build-regret class is real; the justified exception is a thin viewer
over an existing projector. Fastest relief for the operator's pulse
bottleneck is the v1 rung. *Rejected:* React-first (reopens a ratified
decision, delays pulse relief); parallel shaping (commits a lane slot
before the projection contract stabilizes). Deferred to decompose: where
the app lives (likely `apps/`, existing Vite + portless conventions) —
belongs in the MAP candidate-goal definition.

## 2026-08-10 — D13: Pulse-first information architecture

**Question.** What is the primary screen of both the static v1 and any
React v2?

**Answer.** Pulse-first: frontier ("you can start these N now, in
parallel"), blocked-by explanations, landed-not-closed (D10), and the
operator queue (approvals/parks awaiting the operator — the D11 metrics
rendered). Kanban, DAG, roadmap, and tabbed markdown drill-in are secondary
navigation.

**Rationale.** The operator's stated bottleneck is "what do I do next /
what's active / priority" — the surviving internal ops dashboards are one
screen with needs-action on top, not nav-heavy SPAs (lane 7). *Rejected:*
kanban-first (buries the actual question under column-scanning); DAG-first
(graphs need reading; lists need glancing).

## 2026-08-10 — D14: v2 realtime = scoped reproject + push with poll fallback

**Question.** Realtime mechanism for the React v2.

**Answer.** Scoped watch only (`goals/*/ops/**`, `explorations/*/ops/**`,
projection output) → debounced reproject → atomic `projection.json` write;
Vite plugin emits a custom HMR event (`packets:projection`), TanStack Query
invalidates; a 2–5s ETag poll is the always-on fallback so the UI fails
closed to visibly-stale. Staleness chrome regardless of transport:
`sourceTip` short-hash, age, projector version, red banner on
disk-tip ≠ projection-tip.

**Rationale.** Sub-second realtime is vanity for one operator; monorepo-wide
watchers fail loudly; unlabelled staleness trains false trust (lane 7).
*Rejected:* poll-only (loses the HMR-for-data feel the operator wants at
trivial extra cost); push-only (dropped connection without fallback is the
silent-staleness failure mode).

## 2026-08-10 — D15: Git-markdown packets are the sole system of record

**Question.** Does a hosted tracker (Linear-class) enter the picture — as
replacement or mirror — or do packets stay the sole system of record?

**Answer.** Packets + the event chain remain the *only* system of record.
Every board, roadmap, kanban, and pulse view is a generated read-only
projection (static HTML v1 → React v2 per D12–D14). Hosted trackers are
ruled out as a system of record; if a non-repo stakeholder ever needs a
view, ship a generated non-normative export, never a second writer. This
extends the full-document-editor D27 precedent (Notion = non-normative
mirror) from one packet's ruling to standing convention across hosted
trackers.

**Rationale.** The operator's own objections — drift, a second system to
maintain, agent accessibility — are the documented failure modes (catalog
maintenance trap; dual-write; API-mediated agent access vs native files).
The packet domain (event-derived stages, digest-bound approvals, frontier
CTEs, receipts) has no faithful issue/epic representation; flattening it
into Linear would discard the semantics D1–D11 establish. Where hosted wins
(multi-human collab, notifications, mobile), this repo has one operator.
*Rejected:* Linear as one-way mirror trial (sync cost + mirror-invites-
edits drift, competing with the v1 dashboard that solves the same pulse
problem); full migration evaluation (only coherent if the docs-as-code
premise itself is doubted, which it is not).

## 2026-08-10 — D16: No state folders — packet paths are permanent; state is projected

**Question.** Should packets move between state-named subfolders under the
explorations and goals roots (for example, active and completed) so the file
tree shows every packet's state at a glance?

**Answer.** No. Packet directories are permanent homes keyed by slug; state
is derived (D3) and made glanceable through generated projections — ATLAS
grouped by status, README status blocks (D6), generated INDEX, the pulse
dashboard (D12–D13), and a generated by-state tree view added to the
projection backlog so the file-tree glanceability want is met without
moves.

**Rationale.** A path is the most aggressive form of stored state — it
reintroduces the stored-vs-derived drift class D1/D3 exist to close (doctor
would need "path says parked, events say active"). Path instability breaks
dense cross-links (manifest links, ATLAS, graduation back-links, ROADMAP
refs, slug-citing commits the completion gate greps, memory files) and
KSA's discover-beacons identity model; a state-move in one lane plus
content edits in another is a rename/edit merge conflict under the driver's
two edit lanes + operator worktrees; moves spuriously invalidate
subtree-digest gate memoization, turbo inputs, and `--since` counting; and
transition PRs balloon into rename diffs (the operator's own objection).
*Rejected:* per-state folders (all of the above); terminal-only `_archive/`
variant (defensible — one-way, once, conflict-free — but not adopted now;
may resurface as a decompose-stage decluttering option if the 112+ packet
count becomes a real search/context cost).
