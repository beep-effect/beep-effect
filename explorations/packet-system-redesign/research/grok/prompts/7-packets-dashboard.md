An internal read-only "packets" dashboard app for a docs-as-code planning system. CONTEXT SPECIFICS: beep-effect (TypeScript Effect monorepo, public repo, one operator + coding-agent fleet) tracks work as markdown+JSON "packets" on disk (explorations/ and goals/ directories: README/SPEC/PLAN/DECISIONS markdown + ops/manifest.json + soon append-only control-event files). A deterministic projection engine is already planned (bun:sqlite over decoded manifests; frontier, blockers, cycles, parallel groups as recursive CTEs; one projection feeds JSON + Mermaid + dashboard so renderers cannot invent divergent semantics). A ratified v1 decision ships a single SELF-CONTAINED static HTML dashboard (kanban + DAG, no server, no React build). The operator now wants to research a richer v2: a local React web UI (Vite dev server, .localhost proxy) showing kanban by status, roadmap, execution order, dependency/prerequisite DAG, which goals can run in parallel; clicking into a packet opens tabs rendering each canonical markdown file; the UI reflects on-disk packet changes in near-realtime (file watching; "HMR for data"). It must stay a READ-ONLY projection consumer - any write goes through the CLI single-writer.

RESEARCH QUESTIONS: (1) Prior art for repo-local docs-as-code portfolio dashboards: Backstage catalog, GitHub Projects as code, obsidian-kanban, markwhen/timeline tools, jira-alternatives-from-markdown, VS Code extensions, mkdocs/docusaurus-based status sites, gum/glow TUIs - what worked, what rotted, and why local single-user dashboards beat (or lose to) hosted trackers. (2) Realtime data-from-files patterns in Vite/React dev setups: chokidar watch -> WebSocket/SSE push, Vite HMR API custom events for DATA (import.meta.hot), TanStack Query invalidation from fs events, when polling is actually fine; gotchas watching large git worktrees. (3) React libraries proven for this UI shape in 2025-2026: DAG/graph rendering (React Flow/xyflow, elkjs/dagre layouts, d3-dag), kanban boards (dnd-kit patterns, library vs hand-rolled for read-only), markdown rendering (react-markdown/MDX/shiki), tabbed file viewers. (4) The "dashboard becomes second source of truth" failure mode: teams whose status UI drifted from the artifact of record; read-only-projection discipline; how tools mark staleness. (5) Whether people regret building internal dashboards vs using existing tools - honest build-vs-buy postmortems for internal dev dashboards.
