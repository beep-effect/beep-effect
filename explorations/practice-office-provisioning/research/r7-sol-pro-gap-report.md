# Solo IP Practice Office Provisioning Gap Report

_As of August 30, 2026 (America/Chicago). Status tags mean: **CONFIRMED** = directly supported by a current authoritative source; **LIKELY** = strongly supported but an entitlement, packaging, or behavior detail still needs tenant/vendor validation; **UNVERIFIED** = current authoritative evidence was not sufficient to treat the point as settled._

## A — Licensing paths for bulk PST import

1. **CONFIRMED — The PST-import license belongs on the target mailbox user, not merely on the administrator who runs the job.** Microsoft’s current Purview service description says that bulk PST import user rights are provided by Exchange Online Plan 2, Microsoft 365 E3/E5, Office 365 E3/E5, Microsoft Purview Suite and specified Purview information-protection/governance SKUs; it separately says that, for user mailboxes, the user must have the required license assigned. The import operator needs the Mailbox Import Export and Mail Recipients roles, or Global Administrator, but Microsoft’s import documentation does not say that an admin needs a second PST-import entitlement merely to execute the job. For this practice, license the attorney/target mailbox; use the existing Global Admin or least-privilege import roles for the operator. Source: [Microsoft Purview service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-365-service-descriptions/microsoft-365-tenantlevel-services-licensing-guidance/microsoft-purview-service-description) and [PST import overview](https://learn.microsoft.com/en-us/purview/pst-import-overview), accessed 2026-08-30.

2. **CONFIRMED — Exchange Online Plan 2 is the lowest public list-price entitlement that directly appears in the PST-import user-rights list.** Microsoft’s U.S. storefront lists Exchange Online Plan 2 at **$8.00/user/month, paid yearly**, an annual auto-renewing subscription, or **$96/year for one seat**. The public storefront did not expose a product-specific month-to-month price in this research. Source: [Exchange Online plans and pricing](https://www.microsoft.com/en-us/microsoft-365/exchange/exchange-online-business-plans-and-pricing), accessed 2026-08-30.

3. **CONFIRMED — A single Microsoft 365 E3 seat also grants PST-import rights, but is economically excessive for this one-purpose use.** Current U.S. list price is **$39/user/month, paid yearly**, or **$468/year**, after Microsoft’s July 1, 2026 pricing change. Office 365 E3, which also appears in the Purview user-rights list, is **$26/user/month, paid yearly**; it is worth knowing about, but it is still materially more expensive than Exchange Online Plan 2 for a temporary import gate. Sources: [Microsoft 365 Enterprise pricing](https://www.microsoft.com/en-us/microsoft-365/enterprise/microsoft-365-plans-and-pricing), [2026 Microsoft 365 pricing update](https://www.microsoft.com/en-us/licensing/news/2026-m365-packaging-pricing-updates), and [Office 365 E3](https://www.microsoft.com/en-us/microsoft-365/enterprise/office-365-e3), accessed 2026-08-30.

4. **CONFIRMED — There is now a Business-Premium-specific Purview Suite add-on that changes the prior licensing picture.** Microsoft currently lists **Microsoft Purview Suite for Microsoft 365 Business Premium at $10/user/month, paid yearly**, with a 300-seat maximum and an explicit Business Premium prerequisite. Microsoft’s page states that the current $10 offer is a promotional first-year price during a Copilot commercial-customer promotion running through **December 31, 2026** and requires an annual commitment. The current Purview service description lists “Microsoft Purview Suite” among PST-import user-rights licenses. Taken together, assigning this Business-Premium-specific Purview Suite to the attorney is the cleanest Purview add-on path on the existing base plan. Sources: [Purview Suite for Microsoft 365 Business Premium](https://www.microsoft.com/en-us/security/small-medium-business/microsoft-purview-suite-business-premium) and [Purview service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-365-service-descriptions/microsoft-365-tenantlevel-services-licensing-guidance/microsoft-purview-service-description), accessed 2026-08-30.

5. **CONFIRMED — The enterprise Microsoft Purview Suite is not a substitute add-on that can simply be bolted onto Business Premium.** Microsoft lists the enterprise Purview Suite at **$12/user/month, paid yearly**, but requires Microsoft 365 E3, or Office 365 E3 plus EMS E3. Other E5/Purview component SKUs are named in the PST-import entitlement list, but current public U.S. pricing and Business-Premium prerequisites for every component SKU were not exposed in the authoritative pages reviewed. For this tenant, do not buy the enterprise $12 Purview Suite unless the base license is also changed to an eligible enterprise prerequisite. Source: [Microsoft Purview pricing](https://www.microsoft.com/en-us/security/microsoft-purview-pricing), accessed 2026-08-30.

6. **LIKELY — Exchange Online Plan 2 and an E3 license can coexist at the tenant level beside Business Premium, but the exact overlapping Exchange service-plan assignment should be tested before the import window.** Microsoft documents that a user can have multiple product licenses from different licensing plans and that additional licenses can be assigned while retaining existing ones. It also documents service-plan conflict errors as a class of licensing problem. The public licensing pages do not give a product-pair-specific guarantee for “Business Premium with Copilot for Business + Exchange Online Plan 2” on one user. Operationally, buy one EOP2 seat, assign it to the attorney, verify the effective Exchange/Purview service plans, and do not disturb the existing Business Premium bundle unless the admin center reports a conflict. Source: [View Microsoft 365 licenses and services with PowerShell](https://learn.microsoft.com/en-us/microsoft-365/enterprise/view-licenses-and-services-with-microsoft-365-powershell?view=o365-worldwide) and [Assign licenses to users](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/assign-licenses-to-users?view=o365-worldwide), accessed 2026-08-30.

7. **CONFIRMED — Public direct-buy pricing does not make EOP2, E3, or the Business-Premium Purview add-on a true one-to-three-month purchase.** The product pages above expose annual commitments. Microsoft’s New Commerce platform supports monthly, annual, or three-year terms for *many* subscriptions, and Microsoft states that a monthly-commitment subscription can be canceled without an early-cancellation penalty while annual commitments may incur one; however, the authoritative public pages reviewed did not expose a current U.S. month-to-month SKU or price for EOP2, M365 E3, or the Business-Premium Purview Suite specifically. Therefore a CSP/New Commerce quote is required before assuming these can be held for only 1–3 months. Sources: [New commerce license-based overview](https://learn.microsoft.com/en-us/partner-center/customers/new-commerce-license-based) and [Microsoft 365 additional-services billing terms](https://www.microsoft.com/en-us/microsoft-365/business/additional-services-plans-and-pricing), accessed 2026-08-30.

8. **CONFIRMED — Microsoft’s auto-expanding-archive/PST-import documentation remains internally contradictory, but the newer import overview supports staged imports beyond 100 GB.** The September 11, 2025 troubleshooting article says auto-expanding archives do not support PST import/migration scenarios. The newer June 11, 2026 PST import overview says an import to an archive cannot exceed 100 GB in one import and instructs administrators with more than 100 GB to divide the data into multiple imports and allow time for the archive to auto-expand between imports. Because the latter is newer, purpose-built for the current import workflow, and explicitly addresses the >100 GB case, it is the stronger operational instruction—but the contradiction is not formally retracted. Sources: [PST import issues](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365/purview/pst-import-service/issues-with-pst-import-job) and [PST import overview](https://learn.microsoft.com/en-us/purview/pst-import-overview), accessed 2026-08-30.

9. **CONFIRMED — For approximately 100–300 GB, capacity expansion is a schedule risk, not just a license checkbox.** Microsoft recommends PSTs of **20 GB or less**, reports an approximate import rate of **24 GB/day per mailbox** with multiple PSTs to the same mailbox processed sequentially, and says auto-expanding archive conversion begins around **90 GB** and additional storage can take **up to 30 days** to provision. The safe plan is therefore: enable the attorney’s archive and auto-expansion before bulk work; verify the archive state; split/normalize source PSTs to ≤20 GB; import to a segregated `TargetRootFolder`; stage the first tranche below the 100-GB archive boundary; verify additional archive capacity before the next tranche; reconcile item counts/failures after each job; and leave schedule slack for expansion. Sources: [PST import overview](https://learn.microsoft.com/en-us/purview/pst-import-overview), [Enable auto-expanding archiving](https://learn.microsoft.com/en-us/purview/enable-autoexpanding-archiving), and [PST import FAQ](https://learn.microsoft.com/en-us/purview/pst-import-faq), accessed 2026-08-30.

10. **LIKELY — For this specific migration, open a Microsoft support case before relying on the second/third >100-GB tranche, even though the newer overview permits it.** This is not a technical prerequisite; it is risk containment for a documentation contradiction whose failure mode is “archive fills while a historical migration is running.” Preserve the import job manifests, PST hashes, AzCopy logs, mapping CSVs, item counts, and the support response as migration evidence. Do not automatically clear the import-created `RetentionHoldEnabled` state until the attorney has accepted the reconciliation. The underlying import/retention behavior is documented by Microsoft; the support-case recommendation is an operational inference. Source: [PST import overview](https://learn.microsoft.com/en-us/purview/pst-import-overview), accessed 2026-08-30.

## B — Box plan economics and Business-plan reality

1. **CONFIRMED — Box still imposes a three-seat minimum on Business, Business Plus, Enterprise, and Enterprise Plus.** Current displayed U.S. pricing is: Business **$20/user/month month-to-month or $15/user/month on annual billing**; Business Plus **$33 or $25**; Enterprise **$47 or $35**; Enterprise Plus **$50/user/month on the monthly view**, while the annual Enterprise Plus price was not exposed in the fetched page. At the three-seat floor, that is $60/month month-to-month or $45/month effective annual for Business; $99 or $75 for Business Plus; and $141 or $105 for Enterprise. Source: [Box pricing](https://www.box.com/pricing), accessed 2026-08-30.

2. **CONFIRMED — Plain Business does not provide the custom metadata-template layer needed for a conventional metadata-driven legal DMS.** Box’s developer packaging page says custom metadata templates are available on **Business Plus and above**. A matter taxonomy that depends on custom fields such as client ID, matter ID, application number, jurisdiction, lifecycle state, responsible attorney, or retention class therefore cannot be implemented as first-class Box custom metadata on Business. Metadata cascade is consequently not a usable custom-matter-taxonomy mechanism on plain Business. Source: [Box free developer plan / plan capabilities](https://developer.box.com/guides/getting-started/free-developer-plan), accessed 2026-08-30.

3. **CONFIRMED — Business has only 50 accessible file versions; Business Plus also has 50; Enterprise has 100; Enterprise Plus has unlimited.** Box also says customers below Enterprise Plus that purchase Box Governance can choose unlimited version history. For a law practice, this makes the practical Business→Business Plus upgrade about metadata/collaboration/admin capability, **not** about longer version history; the version-history step occurs at Enterprise or through Governance. Source: [Accessing Version History](https://docs.box.com/en/box-fundamentals/for-users/staying-organized/organizing-and-tracking-content/accessing-version-history), accessed 2026-08-30.

4. **CONFIRMED — Plain Business does include document watermarking, so watermarking is not an Enterprise-only gap.** Box’s current pricing page states that its Business plans include document watermarking. There is an important Sign interaction: Box says a watermarked source file, or a source in a watermarked destination folder, cannot be started as a Box Sign request because Sign treats watermarking as a security restriction. Sources: [Box pricing](https://www.box.com/pricing) and [Box Sign FAQ](https://support.box.com/hc/en-us/articles/4404077080595-Box-Sign-FAQ), accessed 2026-08-30.

5. **LIKELY — The prior “Governance requires a tier above Business” conclusion remains operationally safe, but Box’s current packaging documentation is not perfectly consistent about add-on eligibility.** Box’s developer-facing plan page, modified August 25, 2026, lists the Box Governance add-on as available on Business Plus, Enterprise, or Enterprise Advanced and does **not** list Business; it describes retention/legal-hold APIs as Governance capabilities. Other Box packaging material surfaced during research describes Governance as included in higher suites and sold as an add-on on other business plans. Because the current developer matrix is both recent and explicit, do **not** design retention automation on the assumption that the existing Business tenant can buy Governance until Box Sales confirms the SKU for this tenant in writing. Box does not publish a decision-grade U.S. Governance add-on price on the public pages reviewed. Source: [Box plan/add-on capabilities](https://developer.box.com/guides/getting-started/free-developer-plan), accessed 2026-08-30.

6. **CONFIRMED — Full Box Shield is not a plain-Business capability.** Box’s current developer packaging describes Box Shield as a purchased add-on for qualifying enterprises. The Enterprise pricing tier now includes selected “advanced security” functions—native classifications, classification-based access policies, threat-detection rules and alerts—while Box Sign’s plan matrix specifically says Enterprise requires purchasing Box Shield for the Sign-Shield integration. Therefore do not treat the Enterprise plan’s included advanced-security row as equivalent to “all Shield functionality is included.” Sources: [Box plan capabilities](https://developer.box.com/guides/getting-started/free-developer-plan), [Box pricing](https://www.box.com/pricing), and [Box Sign plan matrix](https://docs.box.com/en/box-sign/box-sign-for-admins/box-sign-features-in-box-individual-and-business-plans), accessed 2026-08-30.

7. **CONFIRMED — “Unlimited Box Sign” on Business refers to web-app sending, not unlimited custom integration/API volume.** Box’s July 8, 2026 plan matrix lists web/mobile e-sign sending as unlimited on Business and above, while signature requests sent through third-party/custom integrations are capped per customer per year at **100 on Business, 150 on Business Plus, 250 on Enterprise, and unlimited third-party / 1,000 custom on Enterprise Plus**. Additional signature-request volume can be purchased. Box’s pricing page lists a Sign API add-on at **$1.20 per signature request with a 100-request/year minimum and annual commitment** for incremental platform volume. Sources: [Box Sign plan matrix](https://docs.box.com/en/box-sign/box-sign-for-admins/box-sign-features-in-box-individual-and-business-plans) and [Box pricing](https://www.box.com/pricing), accessed 2026-08-30.

8. **CONFIRMED — Business also has an integration-cost reality beyond Sign.** The current plan page lists **50,000 API calls/month** for Business and Business Plus and **100,000/month** for Enterprise and Enterprise Plus; Box additionally enforces per-user/per-endpoint rate limits and advises exponential backoff after HTTP 429. For a one-attorney provisioning/reconciliation workload, 50,000 calls/month is probably adequate, but a backfill scanner should cache IDs, use event/webhook deltas, and avoid repeatedly walking the entire tree. Sources: [Box pricing](https://www.box.com/pricing) and [Box API rate limits](https://developer.box.com/guides/api-calls/permissions-and-errors/rate-limits), accessed 2026-08-30.

Do not buy a higher tier merely to get watermarking; Business already has it. The recommendation is an inference from the verified plan matrix.

## C — Legal-ethics operational layer

1. **CONFIRMED — The generic U.S. ethics baseline is “reasonable efforts,” not a rule that commercial cloud storage is forbidden.** ABA Model Rule 1.6(c) requires reasonable efforts to prevent inadvertent or unauthorized disclosure/access, and Comment 18 makes reasonableness contextual: sensitivity of the information, likelihood of disclosure absent safeguards, cost and difficulty of additional safeguards, and adverse effect on representation. State-bar cloud opinions such as New York State Bar Association Opinion 842 and Florida Ethics Opinion 12-3 likewise permit cloud use when the lawyer exercises reasonable care regarding confidentiality, security, access, and the provider. Sources: [ABA Model Rule 1.6](https://www.americanbar.org/groups/professional_responsibility/publications/model_rules_of_professional_conduct/rule_1_6_confidentiality_of_information/), [NYSBA Ethics Opinion 842](https://nysba.org/ethics-opinion-842/), and [Florida Ethics Opinion 12-3](https://www.floridabar.org/etopinions/etopinion-12-3/), accessed 2026-08-30.

2. **CONFIRMED — For this practice, “reasonable care” should be implemented as a repeatable vendor-and-configuration control, not a one-time selection of Box.** At minimum: MFA/phishing-resistant authentication where practical; least-privilege admin/app scopes; documented collaborator policy; encryption and breach-notification terms; the ability to export client content on termination; periodic review of Box/Microsoft/AI integrations; and incident-response procedures that identify affected client matters. ABA guidance on electronic communications and breach response emphasizes risk-sensitive safeguards and client notification when a breach materially compromises client information. Sources: [ABA Model Rule 1.6](https://www.americanbar.org/groups/professional_responsibility/publications/model_rules_of_professional_conduct/rule_1_6_confidentiality_of_information/) and ABA guidance associated with Formal Opinions 477R/483, accessed 2026-08-30.

3. **CONFIRMED — There is no generic USPTO rule saying “retain every patent prosecution client file for five years.”** The five-year language in 37 C.F.R. §11.115 concerns complete records of client funds and other property/trust-account records after termination of the representation. That is an important floor for those records, but it should not be misapplied as a universal destruction date for prosecution correspondence, invention disclosures, opinions, drafts, or the entire client file. Source: [USPTO MPEP Appendix R — Patent Rules / USPTO Rules of Professional Conduct](https://www.uspto.gov/web/offices/pac/mpep/mpep-9020-appx-r.html), accessed 2026-08-30.

4. **CONFIRMED — Some patent-prosecution originals can remain evidentially important even after electronic filing.** MPEP §602 states that a copy of an originally executed oath/declaration is encouraged for filing and that the original should be retained by the applicant or representative as evidence of authenticity because the USPTO may require it if authenticity is questioned. This supports a retention policy that distinguishes “replaceable/public prosecution history” from “client-supplied originals and authenticity evidence.” Source: [MPEP §602 — Oaths and Declarations](https://www.uspto.gov/web/offices/pac/mpep/s602.html), accessed 2026-08-30.

5. **LIKELY — A patent practice should retain its substantive matter file on a longer horizon than ordinary short-lived business records, but the exact period must be jurisdiction- and engagement-specific.** Patent prosecution can span years, issued patents can remain economically relevant for much longer, and later disputes may require reconstructing instructions, disclosure decisions, priority claims, inventorship communications, filing decisions, and client approvals. The operationally safe policy is to define matter closure explicitly and then apply a written schedule that accounts for governing state rules, client instructions, limitation/repose periods, litigation or claims holds, patent lifecycle, and special document classes. This is a risk-management inference, not a statement that one nationwide number applies. Source baseline: [ABA Model Rule 1.6](https://www.americanbar.org/groups/professional_responsibility/publications/model_rules_of_professional_conduct/rule_1_6_confidentiality_of_information/) and [USPTO Rules of Professional Conduct](https://www.uspto.gov/web/offices/pac/mpep/mpep-9020-appx-r.html), accessed 2026-08-30.

6. **UNVERIFIED — No universal malpractice-carrier mandate for a specific DMS product, version-count, or patent-file retention period was established from a current carrier underwriting source in this research.** Do not encode “the carrier requires seven years,” “the carrier requires immutable versioning,” or similar language without the attorney’s actual policy/application. The controls that are defensible regardless of carrier wording are a centralized matter file, reliable version history, reproducible audit logs, client/matter naming discipline, email capture for substantive instructions, docket/deadline controls, backup/export capability, documented closing procedures, and a litigation/claim hold that overrides destruction. Source basis for version capability: [Box Version History](https://docs.box.com/en/box-fundamentals/for-users/staying-organized/organizing-and-tracking-content/accessing-version-history), accessed 2026-08-30.

7. **LIKELY — Automatic deletion without attorney disposition approval is the most dangerous retention automation for this environment.** A timer can be wrong because the matter was never truly closed, related applications remain pending, a patent is still active, the client has requested return/transfer of material, a claim/litigation hold exists, or a record class has a different retention rule. Use automation to *calculate eligibility and queue disposition*, not to destroy the authoritative client file. The attorney should approve destruction at the matter or disposition-batch level, with an immutable record of what policy applied, what was excluded/held, and what was actually deleted. This is an operational inference from confidentiality/property duties and Box Governance’s disposition model. Sources: [USPTO Rules of Professional Conduct](https://www.uspto.gov/web/offices/pac/mpep/mpep-9020-appx-r.html) and [Box Governance description](https://support.box.com/hc/en-us), accessed 2026-08-30.

| Option | Cost | Gates | Recommendation |
|---|---|---|---|
| **Manual retention; no automated destruction** | Staff/attorney review time; no Governance SKU required. | Requires disciplined matter-closure state and periodic review; storage is effectively not the limiting factor on Box Business. | **Safe go-live default.** Automate reports and reminders, not deletion. |
| **Policy engine + attorney disposition queue** | Engineering effort; Box Governance cost may apply if enforcement is moved into Box. | Must model closure date, record class, hold status, client instructions, jurisdiction, and approval evidence. | **Recommended target state.** Human-in-the-loop disposition gives automation without silent loss. |

## D — FreshBooks integration depth

1. **CONFIRMED — The FreshBooks API surface is mature enough for the proposed billing integration.** FreshBooks maintains first-party JSON APIs for clients, invoices, payments, reports, expenses, projects and related resources; the Payments API supports reading and managing invoice-payment records, and the Clients API supports client lifecycle data. For a Box integration, FreshBooks can remain the billing system of record while the tooling synchronizes client identifiers, invoice status, payment state, and invoice artifacts into matter/client folders. Sources: [FreshBooks API introduction](https://www.freshbooks.com/api/start), [Clients](https://www.freshbooks.com/api/clients), and [Payments](https://www.freshbooks.com/api/payments), accessed 2026-08-30.

2. **CONFIRMED — FreshBooks webhooks should be treated as low-latency notifications, not as a guaranteed event log.** FreshBooks explicitly says it does **not guarantee webhook delivery speed** and that notifications can arrive from seconds to several minutes after the event. Registration has a callback-ownership verification flow: FreshBooks POSTs a verification code and callback ID; the application returns them via the callback API, and the verification code is also used as the secret for verifying subsequent webhook signatures. Source: [FreshBooks Webhook Callbacks](https://www.freshbooks.com/api/webhooks), accessed 2026-08-30.

3. **UNVERIFIED — The current authoritative page surfaced in this session did not establish a decision-grade retry schedule or an “exactly once” delivery guarantee for FreshBooks webhooks.** Therefore webhook handlers should be idempotent, persist event/entity keys, fetch the current FreshBooks entity after a notification, and run a periodic reconciliation poll so a delayed or missed callback does not strand invoice/payment state. This is an engineering recommendation based on FreshBooks’ explicit latency non-guarantee. Source: [FreshBooks Webhook Callbacks](https://www.freshbooks.com/api/webhooks), accessed 2026-08-30.

4. **CONFIRMED — Refresh-token rotation is a material implementation gotcha.** FreshBooks’ current migration guidance says an OAuth access token “can expire at any time” and calls the refresh token **single-use**: refreshing returns a new access token *and a new refresh token*. The integration must therefore serialize refreshes and atomically persist the replacement refresh token; two workers refreshing the same token can race and strand the second worker. A fixed access-token or refresh-token lifetime should not be hard-coded from folklore because the current authoritative guidance surfaced here does not make a stable lifetime part of the contract. Source: [FreshBooks Classic-to-current API migration guidance](https://www.freshbooks.com/api/how-to-migrate-from-the-classic-xml-api), accessed 2026-08-30.

5. **CONFIRMED — FreshBooks uses several identity namespaces, and mixing them is a common source of 404/empty-result bugs.** Accounting endpoints use an `account_id`; time-tracking endpoints use a `business_id`; newer report examples can use a business UUID. FreshBooks explicitly tells integrators to obtain the correct account/business identifiers through its Identity Model. Persist these as typed identifiers in the integration model rather than a generic `freshbooksId: string`. Source: [Classic migration / endpoint mapping](https://www.freshbooks.com/api/how-to-migrate-from-the-classic-xml-api), accessed 2026-08-30.

6. **CONFIRMED — Pagination must be implemented deliberately.** FreshBooks silently caps `per_page` at **100**; requesting page 0 returns page 1, and asking beyond the last page returns an empty item list. Reconciliation jobs should follow returned page metadata or advance until exhaustion and must not assume one response is complete. Source: [FreshBooks Search, Paging and Includes](https://www.freshbooks.com/api/parameters), accessed 2026-08-30.

7. **UNVERIFIED — The exact current numeric API request-rate ceiling was not recovered from the authoritative Request Limits page in this browsing pass.** Build for 429 handling, bounded concurrency, jittered exponential backoff, and incremental `updated_*` filters where available rather than coding against an unverified requests-per-minute number. The Payments API, for example, exposes updated-date filters that are useful for reconciliation. Sources: [Payments](https://www.freshbooks.com/api/payments) and [FreshBooks API introduction](https://www.freshbooks.com/api/start), accessed 2026-08-30.

8. **CONFIRMED — FreshBooks maintains an official Node.js SDK and starter app.** The official Tools and Libraries page lists both a FreshBooks-supported Node.js SDK and Python SDK; for a TypeScript/Effect monorepo, the Node SDK is a reasonable transport/client layer, while the application should still wrap it behind an Effect service so pagination, OAuth rotation, retries, observability, and domain typing remain under local control. Source: [FreshBooks Tools and Libraries](https://www.freshbooks.com/api/libraries), accessed 2026-08-30.

9. **UNVERIFIED — A stable, first-party “download this invoice as PDF bytes” API contract was not confirmed from the authoritative pages surfaced in this session.** Do not build production automation around a browser-only `my.freshbooks.com` URL or scrape rendered HTML. ## E — New or changed Microsoft surfaces

1. **CONFIRMED — Microsoft Graph now has a first-party mailbox import/export API family that can address primary, shared, and archive Exchange Online mailboxes and preserve full-fidelity exported item streams.** Microsoft’s 2026 conceptual and resource-overview pages say mailbox content is exposed as folders/items, exports can be an opaque full-fidelity stream, and items can be imported to the same or a different mailbox, including archive mailboxes. Sources: [Mailbox import/export conceptual overview](https://learn.microsoft.com/en-us/graph/mailbox-import-export-concept-overview) and [Mailbox import/export API overview](https://learn.microsoft.com/en-us/graph/api/resources/mailbox-import-export-api-overview?view=graph-rest-1.0), accessed 2026-08-30.

2. **LIKELY — The core mailbox import/export surface is now in the Microsoft Graph v1.0 documentation, but this report does not treat every operation/edge case as proven GA.** The current resource overview is published under `view=graph-rest-1.0`, which is a strong signal that the documented core resource has moved beyond beta; however, the authoritative snippets recovered in this pass did not provide a separate GA announcement, per-operation licensing table, or every operation’s version status. Before production use, pin the exact operation URLs and permissions from their individual v1.0 pages in integration tests. Source: [Mailbox import/export API overview](https://learn.microsoft.com/en-us/graph/api/resources/mailbox-import-export-api-overview?view=graph-rest-1.0), accessed 2026-08-30.

3. **CONFIRMED — The Graph mailbox API does not replace Purview network upload as a raw-PST ingestion mechanism.** Microsoft describes a mailbox-folder/item API and an opaque full-fidelity item export/import stream; it does **not** describe “upload a PST file and ingest it.” A PST estate would still need parsing/conversion into supported mailbox items plus folder mapping and reconciliation, which turns the job into a custom migration product. For 100–300 GB of historical PSTs already ratified for Purview/AzCopy, Purview remains the operationally appropriate bulk-PST path. Source: [Mailbox import/export conceptual overview](https://learn.microsoft.com/en-us/graph/mailbox-import-export-concept-overview), accessed 2026-08-30.

4. **UNVERIFIED — A separate commercial license/consumption charge and a PST-scale aggregate-size limit for the Graph mailbox import/export API were not established from the authoritative pages surfaced here.** The conceptual docs establish mailbox support and fidelity, not a 300-GB PST migration entitlement. Do not use the new API to bypass the known Purview PST licensing gate unless Microsoft explicitly documents that scenario. Source: [Mailbox import/export API overview](https://learn.microsoft.com/en-us/graph/api/resources/mailbox-import-export-api-overview?view=graph-rest-1.0), accessed 2026-08-30.

5. **CONFIRMED — Ordinary Graph message creation remains a “new/draft message” API, not a historical-mail import API.** The `POST /messages` API creates a draft from JSON or MIME; MIME allows Internet headers and full MIME content. The current page explicitly notes a **4-MB limit for S/MIME message payloads**. Large normal attachments have separate upload-session mechanics, but none of this gives the caller a documented way to set Exchange’s historical delivery metadata as if the server had received the message years earlier. Sources: [Create message](https://learn.microsoft.com/en-us/graph/api/user-post-messages?view=graph-rest-1.0) and [Send messages with MIME content](https://learn.microsoft.com/en-us/graph/outlook-send-mime-message), accessed 2026-08-30.

6. **LIKELY — The prior finding about received-date fidelity therefore stands.** A MIME `Date`/Internet-header representation can preserve message-header information, but the create-message endpoint is still semantically creating a new Exchange item; no authoritative create-message contract surfaced here guarantees caller control over the mailbox item’s historical `receivedDateTime`. Use Purview PST import or the mailbox import/export API when historical fidelity matters; do not “replay” an archive through ordinary Graph draft creation. Sources: [Create message](https://learn.microsoft.com/en-us/graph/api/user-post-messages?view=graph-rest-1.0) and [Message resource](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0), accessed 2026-08-30.

7. **CONFIRMED — Personal contact folders and organization/GAL contacts are distinct Graph/Exchange objects with different blast radii.** Graph exposes user `contactFolders` and personal contacts and supports delegated/application Contacts permissions; Microsoft’s permissions reference separately describes organizational contacts as contacts managed by the organization and different from a user’s personal contacts. For extracted client entities intended to appear in the attorney’s Outlook contacts, create/update contacts in a dedicated personal contact folder under the attorney mailbox. Reserve organizational/GAL contacts for identities the whole tenant should see. Sources: [Create ContactFolder](https://learn.microsoft.com/en-us/graph/api/user-post-contactfolders?view=graph-rest-1.0), [List contacts](https://learn.microsoft.com/en-us/graph/api/user-list-contacts?view=graph-rest-1.0), and [Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference), accessed 2026-08-30.

8. **LIKELY — For org/GAL contact creation, Exchange administrative surfaces are the safer provisioning lane than pretending personal-contact Graph APIs create directory contacts.** The Graph permissions page surfaced an application permission for reading organizational contacts, but this research did not establish a corresponding Graph write contract for creating org contacts. If firm-wide mail contacts are required, provision them through the supported Exchange administrative command/API surface under narrowly scoped app-only RBAC; for ordinary clients, avoid the GAL entirely. Source: [Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference), accessed 2026-08-30.

9. **CONFIRMED — New deployments should use Exchange Online RBAC for Applications rather than create new Application Access Policies.** Microsoft says RBAC for Applications can grant an app permissions paired with a resource scope to limit which mailboxes it can access and explicitly says it **replaces Application Access Policies**. The legacy policy page says not to create new Application Access Policies because they will eventually require migration. Sources: [RBAC for Applications in Exchange Online](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac) and [Application Access Policies — legacy](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-access-policies), accessed 2026-08-30.

## F — Provisioning identity and tenant hygiene

1. **CONFIRMED — Box supports server-side Platform Apps using Client Credentials Grant, and production server-auth apps require administrator authorization.** Box’s current app-creation docs make CCG the default server-auth method for new server apps; CCG/JWT server authentication automatically creates a service account, and Box’s authorization docs say server-auth methods require explicit Admin authorization because the service account can perform privileged actions when granted suitable access. Business plans have production Platform API capability, so the existing Business plan is sufficient to create the provisioning app; higher tiers are needed for specific premium APIs, not for CCG itself. Sources: [Create your first Box application](https://developer.box.com/guides/getting-started/first-application), [Client Credentials Grant](https://developer.box.com/guides/authentication/client-credentials), [Authorization](https://developer.box.com/guides/authorization), and [Box plan capabilities](https://developer.box.com/guides/getting-started/free-developer-plan), accessed 2026-08-30.

2. **CONFIRMED — Box scope/access changes are an authorization lifecycle event.** Box says that changing a CCG/JWT app’s scopes, access level, or advanced features after authorization requires an administrator to reauthorize the app in Admin Console → Integrations → Platform Apps. Treat the authorized app configuration as versioned infrastructure state and surface drift rather than silently widening it. Source: [Create your first Box application](https://developer.box.com/guides/getting-started/first-application), accessed 2026-08-30.

3. **LIKELY — Use the Box service account as the stable provisioning identity, but do not make it the human-facing signer identity.** A service account is purpose-built for server automation and is not tied to the attorney’s interactive login. That is ideal for folder creation, metadata when licensed, collaborations, reports, and webhooks because disabling or changing a human user does not kill the automation identity. Box Sign, however, treats the authenticated requester as the request owner/sender and requires the requester to have access to the source file. For engagement letters, create Sign requests in the attorney’s user context through an authorized user token/“act as user” capability when the client-facing sender/ownership should be the attorney, while leaving provisioning/webhook reconciliation under the service account. Sources: [Box service-account/app setup](https://developer.box.com/guides/getting-started/first-application) and [Create Box Sign Request](https://developer.box.com/guides/box-sign/create-sign-request), accessed 2026-08-30.

4. **LIKELY — This hybrid identity model also improves collaboration visibility.** Put authoritative client/matter content under the firm’s intended human/managed content ownership model, and grant the provisioning service account only the collaboration/admin rights it needs. Avoid quietly moving the canonical client tree into a hidden automation-owned root unless that is an explicit design decision, because Box user ownership affects what ordinary users see and how collaboration is administered. This is an architectural inference from Box’s service-account/user model. Source: [Box user types / server app setup](https://developer.box.com/guides/getting-started/first-application), accessed 2026-08-30.

5. **UNVERIFIED — Box’s exact zero-downtime client-secret rotation behavior, such as whether two CCG client secrets can overlap, was not established from the authoritative pages surfaced here.** The verified constraint is that auth-type/scope/access changes can force reauthorization. Store the CCG secret in 1Password, make secret version/last-rotated metadata part of the reconcile runbook, test a staged rotation before production dependency, and assume a reset can be disruptive until Box documents otherwise for this tenant. Source: [Client Credentials Grant](https://developer.box.com/guides/authentication/client-credentials), accessed 2026-08-30.

6. **CONFIRMED — Certificate-based app-only authentication is the correct Microsoft lane for unattended Exchange/Microsoft 365 automation where supported.** Microsoft’s current Exchange Online PowerShell documentation describes certificate-based authentication for unattended app-only scenarios and requires an Entra application, tenant/application identifiers, the appropriate app/RBAC configuration, and a certificate. It also notes practical constraints: some Purview/eDiscovery cmdlets remain unsupported with app-only auth, current ExchangeOnlineManagement module versions matter, and connection examples use the tenant’s primary `.onmicrosoft.com` domain as the organization identifier. Source: [App-only authentication in Exchange Online PowerShell](https://learn.microsoft.com/en-us/powershell/exchange/app-only-auth-powershell-v2?view=exchange-ps), accessed 2026-08-30.

7. **CONFIRMED — Exchange app scoping and Entra consent are separate layers.** Entra/Graph application permissions can be broad by default; Exchange RBAC for Applications supplies the resource scope limiting which mailboxes an app can access. For the one-attorney firm, the bulk-mail/contact app should be scoped to the attorney mailbox rather than tenant-wide mail access unless a reconciliation operation genuinely requires more. Source: [RBAC for Applications in Exchange Online](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac), accessed 2026-08-30.

8. **LIKELY — Use overlapping certificate rotation on Microsoft, with only the private key in 1Password.** Upload the new public certificate credential to the Entra app, deploy the new private key/certificate version from 1Password, validate token acquisition and Exchange/Graph calls, then remove the retiring credential. Avoid client secrets for the bulk app when certificates are practical. The exact Entra “multiple simultaneous cert credentials” mechanics should be covered by an integration test, but this rotation pattern is consistent with Microsoft’s certificate-based app-only model. Source: [App-only authentication in Exchange Online PowerShell](https://learn.microsoft.com/en-us/powershell/exchange/app-only-auth-powershell-v2?view=exchange-ps), accessed 2026-08-30.

9. **CONFIRMED — FreshBooks’ single-use refresh token is the credential-rotation exception that requires runtime state discipline even if secrets are centralized in 1Password.** A worker that refreshes OAuth credentials must immediately persist the newly returned refresh token before another worker attempts refresh. Serialize the refresh operation with a distributed lock or single refresh owner, update the 1Password item atomically through the chosen automation path, and keep the previous version only for forensic rollback—not for concurrent use, because the old refresh token is already consumed. Source: [FreshBooks migration/authentication guidance](https://www.freshbooks.com/api/how-to-migrate-from-the-classic-xml-api), accessed 2026-08-30.
