RATIFIED-CONFLICT: none. The ratified v2 gate, cloud-permitted doctrine, and composition direction are not contradicted.

## BLOCKING

1. **Bullets 1 and 4 — “salvage integration” and “no data loss” have no preservation protocol.** The only defined fact is that the source is a removable drive; there is no immutable snapshot/image, source mount mode, pre-copy filesystem inventory, unreadable-sector policy, checksum ledger, ACL/ADS/symlink handling, or two-copy verification before restoration starts. The predecessor’s bar was merely one spot-checked copy plus a zero-uncovered move manifest, which cannot prove whole-source preservation ([CAPTURE.md:15](explorations/oppold-corpus-overhaul/CAPTURE.md:15), [README.md:20](explorations/oppold-corpus-overhaul/README.md:20), [SPEC.md:111](goals/oppold-corpus-refresh/SPEC.md:111)). Acting before this is specified risks irreversible loss.

2. **Bullet 4 — the recycle-bin model is dangerously oversimplified.** “Restoration is re-pairing” assumes every `$R` has a valid `$I`, one-to-one pairing, trustworthy original paths, compatible metadata versions, and no collisions. There is no disposition for orphan `$R`/`$I` files, corrupt metadata, duplicate restored paths, path traversal, case-folding collisions, multiple Windows SIDs, or partial files ([CAPTURE.md:26](explorations/oppold-corpus-overhaul/CAPTURE.md:26)). A malformed original path could overwrite another restored artifact unless restoration is constrained to a derived namespace with collision-safe naming.

3. **Bullet 5 — “dedupe and prune” leaves destructive ordering undefined.** The predecessor dedupes by raw content digest before copying and preserves duplicate provenance ([SPEC.md:84](goals/oppold-corpus-refresh/SPEC.md:84)). The overhaul does not distinguish:

   - raw-byte dedupe before restoration;
   - logical dedupe after `$R`/`$I` pairing;
   - derived-file dedupe after type repair or DOCX conversion;
   - semantic/near-duplicate dedupe after extraction.

   Pruning before restoration, extraction, privilege review, or lineage capture can discard the only evidence that two identical byte streams came from different original paths, messages, matters, or deletion events. “Prune” also has no definition of deletion versus quarantine, reviewer authority, reversible disposition, or retention period ([CAPTURE.md:31](explorations/oppold-corpus-overhaul/CAPTURE.md:31)).

4. **Bullet 6 — the mail requirement contains a type contradiction.** It says `.p`, `.d`, and similar attachments must be repaired to their true types and “converted/restored to `.docx`” ([CAPTURE.md:33](explorations/oppold-corpus-overhaul/CAPTURE.md:33)). If the true type is PDF, image, spreadsheet, archive, executable, or another mail container, DOCX conversion is invalid and destructive. The vision needs a type-directed disposition matrix, not a universal DOCX target.

5. **Bullet 6 — the live libpff brick does not implement the promised attachment repair.** Its public descriptor supports only `pst` export ([Libpff.service.ts:49](packages/drivers/libpff/src/Libpff.service.ts:49)). During EML assembly it copies attachment bytes and uses the exported basename unchanged; there is no MIME detection, extension correction, recursive processing, or conversion ([Libpff.pffexport.ts:703](packages/drivers/libpff/src/Libpff.pffexport.ts:703)). Worse, the default mode is `items`, not `all` or `recovered`, so deleted/recovered mail is omitted unless orchestration explicitly overrides it ([Libpff.pffexport.ts:213](packages/drivers/libpff/src/Libpff.pffexport.ts:213)).

6. **Bullet 4’s “no-loss” result is unverifiable through the current manifest contract.** Libpff can skip a non-portable child, an item record, or EML assembly because of a fixed 64 MiB materialization budget and emit only generic warnings ([Libpff.pffexport.ts:420](packages/drivers/libpff/src/Libpff.pffexport.ts:420)). The completed capability explicitly records that archive-export warnings have no manifest record home; only an aggregate warning count survives ([manifest.json:83](goals/file-processing-capability/ops/manifest.json:83)). You cannot prove complete mail restoration when skipped artifacts cannot be tied durably to source paths and reasons.

7. **Privacy, privilege, and PII controls are missing despite cloud processing being permitted.** The predecessor explicitly prohibited external processing, LLM content handling, and content logging ([SPEC.md:29](goals/oppold-corpus-refresh/SPEC.md:29), [SPEC.md:96](goals/oppold-corpus-refresh/SPEC.md:96)). The overhaul expands into NLP, span extraction, enrichment, and cloud-permitted execution without defining privilege triage, provider allowlists, retention/training policy, regional processing, encryption, access logging, redaction, or which document classes may leave the machine ([CAPTURE.md:40](explorations/oppold-corpus-overhaul/CAPTURE.md:40)). “Cloud-permitted” is authorization to design a controlled lane, not authorization to send the entire legal corpus indiscriminately.

## MAJOR

8. **Bullet 2 — “from scratch,” “everything,” and “exhaustively” create an unbounded program.** There is no corpus denominator, supported-format matrix, nested-container depth, encrypted/password-protected policy, corruption policy, maximum file size, malware/macro handling, OCR boundary, or definition of coverage ([CAPTURE.md:19](explorations/oppold-corpus-overhaul/CAPTURE.md:19)). The live V1 capability explicitly excludes OCR, conversion, production retention, and KG assembly, and only classifies rather than extracts XLS/XLSX/DOCM ([file-processing README.md:149](goals/file-processing-capability/README.md:149), [file-processing README.md:154](goals/file-processing-capability/README.md:154)). “Exhaustive” therefore contradicts the actual coverage ceiling unless the missing engines become named scope.

9. **Bullet 3 — “ideal T-Box” has neither an acceptance definition nor a safe ordering.** There are no competency questions, ontology profile, version pin, mapping confidence, validation set, change-control rule, or A-Box migration policy ([CAPTURE.md:21](explorations/oppold-corpus-overhaul/CAPTURE.md:21)). Freezing it before corpus inventory risks modeling imagined data; waiting until after semantic extraction prevents ontology-guided extraction. The vision needs an explicit bootstrap-seed → representative extraction → T-Box refinement → version freeze → full ingestion sequence.

10. **The composition claim overstates dependency readiness.** Semantic-foundation M1 is locally complete, but no vendor slice is live-wired and its real asset-pack manifest currently fails closed against the loader schema ([semantic-foundation README.md:40](goals/semantic-foundation/README.md:40), [semantic-foundation README.md:49](goals/semantic-foundation/README.md:49)). Patent-document-schema has every phase still pending ([patent manifest.json:55](goals/patent-document-schema/ops/manifest.json:55)). FOLIO/Lynx has every phase pending and is blocked by SPAR wiring plus license/vetting proof ([FOLIO manifest.json:22](goals/folio-lynx-taxonomy-browse/ops/manifest.json:22), [FOLIO manifest.json:65](goals/folio-lynx-taxonomy-browse/ops/manifest.json:65)). Composition is the ratified direction, but these are dependencies with exit gates—not existing finished bricks.

11. **The document drivers do not provide fidelity-verified conversion.** `doc-text` supports only PDF text layers and DOCX raw-text extraction ([DocText.service.ts:65](packages/drivers/doc-text/src/DocText.service.ts:65), [DocText.service.ts:157](packages/drivers/doc-text/src/DocText.service.ts:157)). Tika exposes detection, text extraction, and metadata extraction, not conversion ([Tika.service.ts:40](packages/drivers/tika/src/Tika.service.ts:40)). The capability roadmap identifies LibreOffice/Gotenberg conversion as future work and explicitly excludes bidirectional conversion from V1 ([manifest.json:145](goals/file-processing-capability/ops/manifest.json:145), [manifest.json:172](goals/file-processing-capability/ops/manifest.json:172)). Conversion engine selection, sandboxing, version pinning, fidelity comparison, and exception review are missing workstreams.

12. **ExifTool is being confused with a corpus-provenance system.** Its public service can read tags, write tags, and write a QA-specific XMP packet ([Exiftool.service.ts:43](packages/drivers/exiftool/src/Exiftool.service.ts:43)). XMP writes are limited to PNG/JPEG/GIF/WebP ([Exiftool.models.ts:244](packages/drivers/exiftool/src/Exiftool.models.ts:244)). It can contribute observed metadata, but it does not establish source-to-restored-to-converted-to-extracted lineage, chain of custody, transformation versions, or confidence. Calling this “metadata/exif provenance” hides a missing provenance model ([CAPTURE.md:47](explorations/oppold-corpus-overhaul/CAPTURE.md:47)).

13. **Bullet 7 — “full capability incorporation … and more” is unbounded and lacks composition contracts.** It does not identify which artifacts each engine consumes and emits, precedence when Tika and doc-text disagree, confidence reconciliation, failure fallback, or whether NLP/langextract operate on originals, converted files, extracted text, or ontology-shaped chunks ([CAPTURE.md:40](explorations/oppold-corpus-overhaul/CAPTURE.md:40)). Package existence is not pipeline integration.

14. **Bullet 8 — self-improvement “at every step” makes runs non-reproducible.** If evaluation can mutate rules, prompts, schemas, or engine selection during the same run, early and late artifacts are produced by different pipelines with no comparable baseline ([CAPTURE.md:42](explorations/oppold-corpus-overhaul/CAPTURE.md:42)). The packet needs immutable run versions, shadow evaluations, promotion gates, regression fixtures, and improvements applied only to a subsequent run.

15. **Bullet 9 — “every avenue” for enrichment is unlimited scope and an epistemic contamination path.** There is no source-authority hierarchy, licensing rule, contradiction handling, evidence confidence, temporal validity, matter boundary, human approval gate, or rule preventing external records from silently overwriting corpus-derived assertions ([CAPTURE.md:44](explorations/oppold-corpus-overhaul/CAPTURE.md:44)). Enrichment must remain separately sourced assertions, not mutation of restored evidence.

16. **Incremental reruns and mid-pipeline recovery are absent.** The predecessor is run-isolated and stops on any source read or coverage mismatch ([SPEC.md:92](goals/oppold-corpus-refresh/SPEC.md:92), [SPEC.md:140](goals/oppold-corpus-refresh/SPEC.md:140)). Libpff reruns offer only `fail` or `replace`; replacement recursively removes existing export output before a successful replacement exists ([Libpff.pffexport.ts:175](packages/drivers/libpff/src/Libpff.pffexport.ts:175), [Libpff.pffexport.ts:581](packages/drivers/libpff/src/Libpff.pffexport.ts:581)). There is no checkpoint graph, retry class, quarantine lane, atomic stage/promote protocol, idempotency key, or resume-from-failure contract.

17. **The cost premise has no cost model.** The packet begins from “it is expensive” yet provides no corpus byte/file counts, estimated extracted tokens, cloud price schedule, storage amplification, conversion cost, retry multiplier, concurrency limits, sampling plan, or budget stop condition ([CAPTURE.md:8](explorations/oppold-corpus-overhaul/CAPTURE.md:8)). “Quality-first” still requires knowing whether a proposed avenue costs hundreds or tens of thousands of dollars before the expensive run is authorized.

18. **“Best-quality knowledge graph” has no measurable quality bar.** There is no gold corpus, extraction precision/recall target, entity-resolution metric, provenance-completeness threshold, unsupported-format ceiling, ontology-consistency check, or regression comparison to v1 ([CAPTURE.md:8](explorations/oppold-corpus-overhaul/CAPTURE.md:8)). Without declared metrics, bullets 2, 3, 7, 8, and 9 can never reach a defensible terminal state.

19. **The reusable-solo-practice claim is a hidden productization expansion.** Making this “usable for other potential solo-practice attorneys” introduces tenant isolation, configuration, deployment, support, licensing, jurisdictional variation, and separation of Oppold-specific taxonomy/data from reusable pipeline code ([README.md:11](explorations/oppold-corpus-overhaul/README.md:11)). None of those concerns has a boundary or non-goal.
