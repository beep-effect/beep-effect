## RATIFIED-CONFLICT

1. **RATIFIED-CONFLICT — BLOCKING: “hash the full drive first, then copy it” doubles reads before redundancy exists.** A SHA-256 manifest requires reading every source byte once; the subsequent copy requires reading it again. That directly conflicts with the ratified claim that removable-drive risk “retires before anything else,” especially when the drive is already treated as the urgent loss risk in [CAPTURE.md:26-30](explorations/oppold-corpus-overhaul/CAPTURE.md:26). A disk failure during the first hashing pass can destroy the only copy before acquisition starts. This needs operator re-ratification as either:

   - one-pass copy while hashing source and destination, followed by destination verification; or
   - image-first acquisition with a provisional manifest, then full hashing from the durable image.

No other material ratified conflicts found.

## Full-drive acquisition and archive

2. **BLOCKING: `path + size + sha256` is not a full-drive manifest.** The census was only a `find`/`du` aggregate scan and explicitly collected counts, sizes, and extensions, not filesystem identity or metadata ([restoration census:3-5](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:3)). The plan does not even record whether the source filesystem is NTFS, exFAT, or something else. If NTFS is involved, hashing the unnamed stream omits named alternate data streams, extended attributes, hard-link topology, security descriptors, object IDs, reparse data, sparse extents, compression/encryption state, and four timestamps. Microsoft’s backup-stream contract distinguishes all of those stream types, including `ALTERNATE_DATA`, `EA_DATA`, `LINK`, `SECURITY_DATA`, `REPARSE_DATA`, and `SPARSE_BLOCK`. [Microsoft WIN32_STREAM_ID specification](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-bkup/71b49aa4-1f4f-4e1b-84a4-56f560002cf6) A plain file copy cannot satisfy “no loss” until the preservation unit is explicitly defined.

3. **BLOCKING: the manifest has no namespace-object model.** Two implementers can disagree about whether to include empty directories, symlinks/reparse points, hard links, device-like entries, unreadable objects, ADS, sparse logical size versus allocated extents, or filesystem errors. Hard links cannot be recovered from path/hash alone; Microsoft’s prescribed backup flow records file identity and every link name separately. [Microsoft hard-link backup guidance](https://learn.microsoft.com/en-us/windows/win32/backup/backing-up-and-restoring-hard-links) The schema needs object type, raw/native path representation, parent identity, stable file identity, all streams, metadata, and an explicit error state—not merely a file row.

4. **BLOCKING: there is no failure-consistent acquisition protocol.** Missing requirements include source quiescence/read-only mounting, behavior when a file changes between enumeration and hashing, retries for short reads/I/O errors, bad-sector accounting, resumable checkpoints, atomic destination names, `fsync`/flush semantics, post-copy source and destination hashes, and how partially written files are quarantined. “100% verifies” is undefined if even one path becomes unreadable or disappears.

5. **MAJOR: archive capacity and durability are unbudgeted.** The named numbers naïvely total 177.5 GB—6.4 + 48 + 11 + 112.1 GB—before counting the 564 `.doc` files and everything else ([restoration census:11-34](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:11)). Those surfaces may overlap, so even that total is not a valid capacity estimate. The plan lacks:

   - a disjoint byte census;
   - destination free-space and inode checks;
   - extraction/conversion expansion allowance;
   - staging and temporary-space allowance;
   - an independent second durable copy;
   - archive-manifest hashing/versioning and recovery testing.

“Durable corpus archive” is a label, not an evidenced durability property.

6. **MAJOR: timestamps and metadata provenance are promised elsewhere but absent from acceptance.** CAPTURE demands “metadata/exif provenance” ([CAPTURE.md:40-41](explorations/oppold-corpus-overhaul/CAPTURE.md:40)), while the bar records only path, size, and hash. NTFS distinguishes creation, access, write, and change times. [Microsoft FILE_TIMESTAMPS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_timestamps) The plan must say which timestamps are source-native, copy-induced, inferred from `$I`, or unavailable.

## `$RECYCLE.BIN`

7. **BLOCKING: the claimed “one orphan” does not follow from the counts.** The census gives 54 `$I` records and 55 `$R` entries and concludes one orphan ([restoration census:11-19](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:11)). Counts alone do not prove 54 matching suffixes. The same totals could represent 53 valid pairs, one unmatched `$I`, and two unmatched `$R` entries. Acceptance must require an identifier-set join with four explicit classes: valid pair, missing `$R`, orphan `$R`, and duplicate/ambiguous identifier.

8. **MAJOR: `$I` parsing is underspecified.** There is no requirement to recognize format version, validate structural length, decode UTF-16LE strictly, validate FILETIME, compare recorded size against `$R`, or preserve malformed/truncated raw records. Versions 1 and 2 encode paths differently; the common header includes an eight-byte version, original size, and deletion FILETIME. [Documented `$I` v1/v2 layout](https://www.recyclebinparser.com/en/docs/the-i-file-format) A parser that assumes one version can emit plausible but wrong paths.

9. **MAJOR: restore-name collision behavior is undefined.** Multiple deletions can have the same original path. Additional collisions arise from case folding, Unicode normalization, trailing spaces/dots, reserved Windows names, forbidden destination characters, path-length limits, and drive-letter/root differences. “Restore under its recovered name” ([restoration census:15-19](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:15)) provides no deterministic collision suffix, escaping rule, containment check, or ledger representation. A naïve implementation will overwrite data or write outside the restoration root.

10. **MAJOR: directory restoration has no recursive reconciliation.** Twenty of the 55 `$R` entries are directories ([restoration census:11](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:11)). The plan assumes internal names are sufficient, but does not require per-descendant hashes, empty-directory preservation, metadata capture, collision handling, or confirmation that recursive descendants equal the archived `$R` subtree.

11. **MAJOR: the two pre-extracted trees have no lineage or overlap test.** `f-recyclebin-C` contains 1,831 files/48 GB and `f-recyclebin-E` contains 1,211 files/11 GB ([restoration census:12-13](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:12)). “Already name-recovered” is unverifiable: there is no tool/version, source `$R` identity, mapping ledger, hash equivalence, or evidence that these trees are complete. The plan needs a three-way relation among live `$R`, pre-extracted path, and content digest; otherwise dedupe can collapse independent provenance or preserve corrupted earlier output as canonical.

## PST and attachment restoration

12. **BLOCKING: the cited pipeline does not perform magic-byte repair.** The live process command classifies exclusively from the filename extension at [Strategy.schema.ts:528-550](packages/foundation/capability/file-processing/src/Strategy/Strategy.schema.ts:528) and wires that directly into processing at [Process.ts:565-597](packages/tooling/tool/cli/src/commands/Files/internal/Process.ts:565). Bare `.p` and `.d` attachments therefore classify as `unknown` and are skipped at [Process.ts:924-929](packages/tooling/tool/cli/src/commands/Files/internal/Process.ts:924). CAPTURE’s “file classification” brick ([CAPTURE.md:51-57](explorations/oppold-corpus-overhaul/CAPTURE.md:51)) is not evidence of content-based detection. A separate byte-signature detector, ambiguity policy, nested-container handling, and extension-rewrite ledger are required.

13. **BLOCKING: the current CLI is structurally unsafe at 112.1 GB scale.** It reads each complete source into a `Uint8Array` ([Process.ts:565-590](packages/tooling/tool/cli/src/commands/Files/internal/Process.ts:565)) and prepares chunks of 16 files concurrently ([Process.ts:1178-1201](packages/tooling/tool/cli/src/commands/Files/internal/Process.ts:1178); concurrency constant at [Files.progress.ts:39-44](packages/tooling/tool/cli/src/commands/Files/Files.progress.ts:39)). The libpff driver then writes another full temporary PST snapshot before export ([Libpff.pffexport.ts:982-1003](packages/drivers/libpff/src/Libpff.pffexport.ts:982)). Large PSTs can therefore cause multi-file RAM exhaustion plus duplicate source I/O and temporary-disk pressure. The restoration plan needs a path-based/streaming libpff runner with PST concurrency of one unless measured otherwise.

14. **BLOCKING: default libpff settings silently exclude recovered mail and most assembled EML at corpus scale.** The driver defaults to export mode `items`, not `all` ([Libpff.pffexport.ts:213-224](packages/drivers/libpff/src/Libpff.pffexport.ts:213)). Upstream defines `all` as allocated, orphan, and recovered items. [Upstream pffexport options](https://github.com/libyal/libpff/blob/main/pfftools/pffexport.c) It also defaults to a cumulative 64 MiB EML materialization budget per PST and turns overruns into warnings ([Libpff.pffexport.ts:420-430](packages/drivers/libpff/src/Libpff.pffexport.ts:420), [Libpff.pffexport.ts:767-785](packages/drivers/libpff/src/Libpff.pffexport.ts:767)). The CLI still marks the archive successful while retaining only a warning count ([Process.ts:838-851](packages/tooling/tool/cli/src/commands/Files/internal/Process.ts:838)). “Extraction succeeded” can therefore mean recovered items were never attempted and EML assembly stopped after 64 MiB.

15. **BLOCKING: extracted PST children are not hash-verifiable.** `buildChildEntries` records child path and size but no digest ([Libpff.pffexport.ts:657-678](packages/drivers/libpff/src/Libpff.pffexport.ts:657)). That cannot prove attachment bytes, bodies, or metadata survived export. Acceptance needs hashes for every emitted child, counts reconciled by PST/folder/item/attachment, and explicit records for skipped or failed children.

16. **MAJOR: corruption, encoding, and partial recovery collapse into one opaque failure.** The code acknowledges that corrupt PSTs can segfault `pffexport` ([Libpff.pffexport.ts:551-577](packages/drivers/libpff/src/Libpff.pffexport.ts:551)), but all nonzero process outcomes become generic `archive-export-failed` with at most an exit code ([Libpff.error-translation.ts:128-137](packages/drivers/libpff/src/Libpff.error-translation.ts:128)). The wrapper also omits upstream’s codepage and log options and drains process output. There is no per-store validation, password/protection classification, corruption diagnosis, alternate recovery lane, item-count reconciliation, or partial-success record.

17. **MAJOR: interrupted PST exports are not resumable.** Existing outputs default to `fail`; the alternative recursively removes stale trees before restarting ([Libpff.pffexport.ts:163-180](packages/drivers/libpff/src/Libpff.pffexport.ts:163), [Libpff.pffexport.ts:581-604](packages/drivers/libpff/src/Libpff.pffexport.ts:581)). At 53 stores/112.1 GB, a crash either leaves an unrestartable target or destroys partial recovery work. The plan needs per-PST staging, attempt IDs, checkpoint semantics, atomic promotion, and retained failed-attempt evidence.

## Binary `.doc` conversion

18. **BLOCKING: none of the cited bricks implements conversion or fidelity verification.** The file-processing contract explicitly says its IR is extraction-oriented and does not promise reconstruction ([SPEC.md:154-171](goals/file-processing-capability/SPEC.md:154)); its V1 behavior for DOC/DOCX is text and metadata extraction only ([SPEC.md:210-222](goals/file-processing-capability/SPEC.md:210)); bidirectional conversion is explicitly out of scope ([README.md:154-162](goals/file-processing-capability/README.md:154)). `doc-text` supports only PDF and DOCX text extraction ([DocText.service.ts:50-70](packages/drivers/doc-text/src/DocText.service.ts:50)). The claimed “brick” in CAPTURE is therefore not an implementation path for the 564 conversions.

19. **MAJOR: “fidelity-verified” has no measurable acceptance contract.** Missing dimensions include page count, rendered visual difference threshold, text/order comparison, headers/footers, tables, footnotes, comments, tracked changes, fields, embedded OLE objects, equations, images, links, macros, fonts, password/corruption cases, and manual-review escalation. Tool/version/font-container pinning is also absent. Two implementers can both claim success while producing materially different `.docx` files.

20. **MAJOR: the 564 count is extension-based, not format-validated.** The census calls them “binary `.doc`” but reports an extension census generated through `find`/`du` ([restoration census:30-34](explorations/oppold-corpus-overhaul/research/2026-08-17-restoration-census.md:30)). The plan lacks magic validation for mislabeled RTF, HTML, OOXML, encrypted OLE2, zero-byte, truncated, or corrupt inputs. The conversion denominator is therefore unproven.

## Dedupe and final acceptance

21. **BLOCKING: the acceptance test can pass while every transformation is useless.** “Original retained” satisfies byte preservation even if PST export emits zero children, magic repair classifies everything as unknown, or `.docx` conversion produces blank files. Preservation acceptance and transformation completeness must be separate gates with explicit source-to-output reconciliation.

22. **BLOCKING: dedupe against the prior catalog is not 100% archive verification.** The prior run stored only 12 of 8,336 walked records and represented 8,324 as provenance-only ([P1 salvage report:11-28](goals/oppold-corpus-refresh/history/outputs/2026-07-03-p1-salvage-report.md:11)). Only 150 provenance-only rows were checked ([P1 salvage report:44-50](goals/oppold-corpus-refresh/history/outputs/2026-07-03-p1-salvage-report.md:44))—about 1.8% of those 8,324 rows. If the new run treats the existing catalog as proof that duplicate bytes are durable, it violates the new 100% bar unless every referenced canonical blob is rehashed now.

23. **MAJOR: the prior manifest writer already exited 0 with silent corruption.** Record 1 became a NUL block despite success status ([P1 salvage report:52-62](goals/oppold-corpus-refresh/history/outputs/2026-07-03-p1-salvage-report.md:52)). The new bar says the manifest “verifies 100%” but does not define structural validation, row counts, duplicate-key detection, truncation detection, manifest self-hash, durable flush, or independent parser verification. Exit zero is demonstrably insufficient in this corpus.

24. **MAJOR: dedupe provenance semantics are undefined across four representations.** The live drive, live `$R`, pre-extracted recycle trees, and PST/doc-derived outputs can contain identical bytes with different legal provenance, original paths, deletion times, container ancestry, and transformation histories. Content dedupe may share a blob, but it must never collapse those provenance edges. The plan needs immutable occurrence records plus content-object records and explicit `derived-from`, `recovered-from`, `duplicate-of`, and `contained-in` relations.

25. **MINOR: ledger schemas and terminal states are unnamed.** “Mapping ledger,” “loss ledger,” “orphan flagged,” “100% verified,” and “original retained” have no schema version, mandatory fields, status enum, failure reason taxonomy, or invariant checks. At minimum, define `pending`, `copied`, `verified`, `transformed`, `quarantined`, `unreadable`, `collision-renamed`, `missing-pair`, and `waived`, with acceptance rejecting every nonterminal or unapproved state.
