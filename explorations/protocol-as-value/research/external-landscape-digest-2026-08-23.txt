TRACK: Multiparty session types and choreographic programming, state of the art 2024-2026

CLAIM: The canonical MPST result is Honda, Yoshida, Carbone 'Multiparty Asynchronous Session Types': a global type describing all participants' interactions is projected to per-participant local types, and processes typed against those projections are communication-safe and deadlock-free. Best canonical citation is the journal version: JACM 63(1), 2016, doi 10.1145/2827695 (conference original: POPL 2008, doi 10.1145/1328438.1328472).
SRC: Multiparty Asynchronous Session Types — https://dl.acm.org/doi/10.1145/2827695 (JACM 2016); full text at https://www.doc.ic.ac.uk/~yoshida/multiparty/multiparty.pdf
REL: This is exactly the exploration's 'topology as a value one level above agent schemas, each agent's local type a projection of the global type' — the theorem already exists; the exploration's contribution would be the digest-named value form, not the projection theory.

CLAIM: Classical syntactic MPST projection is incomplete (rejects safe protocols); Li, Stutz, Wies, Zufferey give a sound AND complete automata-based projection ('Complete Multiparty Session Type Projection with Automata', CAV 2023).
SRC: Complete Multiparty Session Type Projection with Automata — https://arxiv.org/pdf/2305.17079
REL: If beep models projection as a fold over a global-type value, the choice of projection operator is a real design axis: the standard one is conservative, and the complete one requires automata, not a structural recursion.

CLAIM: Scribble is the original MPST protocol-description language (started by Kohei Honda in 2006 from his W3C WS-CDL work; TGC 2014 paper): global protocol in, validation and per-role projection out. Its GitHub org's repos are described as stale since roughly 2020; it survives mainly as the input syntax other toolchains extend.
SRC: Scribble (MPSTs) | PLS Lab — https://www.pls-lab.org/en/Scribble_(MPSTs) ; The Scribble Protocol Language — https://dl.acm.org/doi/10.1007/978-3-319-05119-2_3
LIC: unknown/stale => reference only
REL: Scribble is the closest existing artifact to 'protocol as a first-class document', but its identity story is a file name, not a canonical byte form with a digest — supporting the exploration's gap claim.

CLAIM: nuscr (νScr) is the maintained OCaml successor toolchain for Scribble-style protocols: define global protocols, project to local types, emit CFSMs and OCaml code; explicitly designed for extensibility; released under GPLv3.
SRC: nuscr — https://github.com/nuscr/nuscr ; tool page http://mrg.doc.ic.ac.uk/tools/nuscr/
LIC: GPL-3.0 => clean-room only (study behavior/design, do not port code)
REL: The most current reference implementation of global-type -> projection -> codegen; its pipeline is the shape beep would reimplement Effect-natively, but its code cannot be ported into a permissively-licensed repo.

CLAIM: effpi (Scalas et al., PLDI 2019 'Verifying message-passing programs with dependent behavioural types') embeds behavioural types in Dotty/Scala 3 with type-level model checking for safety and liveness, including channel passing; self-described experimental; MIT licensed.
SRC: Effpi — https://alcestes.github.io/effpi/ ; https://github.com/alcestes/effpi ; PLDI 2019 paper https://dl.acm.org/doi/10.1145/3314221.3322484
LIC: MIT => port-with-attribution
REL: Demonstrates protocols encoded as types checked by the host compiler — the static end of the spectrum; beep's Effect/TypeScript setting cannot do type-level model checking, pushing it toward the value-level/digest approach.

CLAIM: Teatrino (Barwell, Hou, Yoshida, Zhou, 'Designing Asynchronous Multiparty Protocols with Crash-Stop Failures', ECOOP 2023) extends Scribble+Effpi codegen with crash-stop semantics: crash-handling branches with no new global-type syntax, preserving deadlock-freedom, protocol conformance, and liveness under crashes.
SRC: Designing Asynchronous Multiparty Protocols with Crash-Stop Failures — https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2023.1 ; extended version https://arxiv.org/pdf/2311.11851
REL: State of the art for failure handling in MPST: crash-stop only (no byzantine, no partition healing) and only reached tooling in 2023 — a live limitation the exploration must budget for in any multi-agent async design.

CLAIM: Ozone (Plyukhin, Peressotti, Montesi, ECOOP 2024, LIPIcs 313:31) gives a choreographic programming model in which processes execute fully out-of-order (adapting to message arrival) while guaranteeing absence of communication-integrity violations and deadlocks.
SRC: Ozone: Fully Out-of-Order Choreographies — https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2024.31 ; https://arxiv.org/abs/2401.17403
REL: 2024 SOTA on relaxing the fixed deterministic execution order of choreographies — directly relevant to async agent swarms where message delay is the norm.

CLAIM: Choral (Giallorenzo, Montesi, Peressotti, 'Choral: Object-Oriented Choreographic Programming', TOPLAS 2024) is the most mature choreographic language: choreographies as Java-compatible objects, compiled per-role to pure Java libraries; the compiler is LGPL-2.1 (VSCode extension MIT).
SRC: Choral: Object-oriented Choreographic Programming — https://dl.acm.org/doi/10.1145/3632398 ; https://github.com/choral-lang
LIC: LGPL-2.1 => use-as-dependency ok, porting code requires clean-room; ideas freely portable
REL: Proves choreographies can be modular, typed, first-class program values in a mainstream OO language — the nearest existing realization of 'protocol as a value', minus any content-addressed identity.

CLAIM: HasChor (Shen, Kuper et al., ICFP 2023) implements choreographic programming as a Haskell library (freer-monad based) with higher-order choreographies and location polymorphism; BSD-3-Clause on GitHub/Hackage.
SRC: HasChor — https://github.com/gshen42/HasChor ; paper https://dl.acm.org/doi/10.1145/3607849
LIC: BSD-3-Clause => port-with-attribution
REL: The library-level (no compiler) embedding is the pattern most portable to Effect: endpoint projection done at runtime by interpreting one choreography value per role — a direct blueprint for an Effect-native port.

CLAIM: ChoRus (Kashiwa, Shen, Zare, Kuper, CP@PLDI 2024) is library-level choreographic programming in Rust, MIT licensed, published on crates.io; projection is done by dynamically injecting per-node operator implementations.
SRC: ChoRus — https://github.com/lsd-ucsc/ChoRus ; paper https://users.soe.ucsc.edu/~lkuper/papers/chorus-cp24.pdf
LIC: MIT => port-with-attribution
REL: Second data point that library-level CP works in a mainstream typed language without macros-only tricks; its 'transport' abstraction maps cleanly onto an Effect service boundary.

CLAIM: Klor (Lovro Sdunic, NLnet-funded, Heart of Clojure 2024) is a choreographic DSL embedded in Clojure with compile-time projection via macros; licensed 'EPL-2.0 OR GPL-2.0-or-later WITH Classpath-exception-2.0'.
SRC: Klor — https://github.com/lovrosdu/klor ; NLnet project page https://nlnet.nl/project/ChoreographicProgramming/
LIC: EPL-2.0 OR GPL-2.0+ w/ Classpath exception => weak-copyleft dual; prefer clean-room for code, ideas portable
REL: Shows a Lisp/macro route to projection in a dynamic language — closer to a runtime-value treatment of choreographies than compiler-based systems, which is beep's regime.

CLAIM: TypeScript-adjacent options exist but are thin: (1) STScript/RouST (Miu, Ferreira, Yoshida, Zhou, CC 2021) generates TypeScript APIs from Scribble protocols for WebSocket web apps (Node.js server, React browser) using a routed MPST theory; (2) ChoreoTS (shumbo/choreography-ts) is a small (~9 stars, no visible license) library-level CP monorepo in TypeScript with Express and Socket.IO transports, used as an evaluation vehicle in the PLDI 2025 census-polymorphism paper.
SRC: Communication-Safe Web Programming in TypeScript with Routed Multiparty Session Types — https://dl.acm.org/doi/10.1145/3446804.3446854 ; choreography-ts — https://github.com/shumbo/choreography-ts
LIC: ChoreoTS: no license found => reference only; STScript: research artifact, license unverified => reference only
REL: Nothing in the TypeScript ecosystem is production-grade or Effect-native, and neither treats the protocol as a digest-named runtime value — the implementation lane for beep is open.

CLAIM: The 2024-2025 frontier is participant-set polymorphism: MultiChor (arXiv 2406.13716) and 'Efficient, Portable, Census-Polymorphic Choreographic Programming' (PLDI 2025, doi 10.1145/3729296) formalize conclaves and multiply-located values so one choreography abstracts over the number and identity of participants, with implementations demonstrated in Haskell, Rust, and TypeScript.
SRC: Efficient, Portable, Census-Polymorphic Choreographic Programming — https://arxiv.org/abs/2412.02107 ; MultiChor — https://arxiv.org/abs/2406.13716
REL: Directly addresses the dynamic-agent-population problem a multi-agent system has: the global protocol value must be polymorphic over who shows up, or every roster change mints a new protocol digest.

CLAIM: Rust has two static-leaning MPST libraries: MultiCrusty ('Stay Safe under Panic: Affine Rust Programming with Multiparty Session Types', arXiv 2204.13464) using affine types for failure/cancellation, and Rumpsteak ('Deadlock-free asynchronous message reordering in Rust with multiparty session types', arXiv 2112.12693) for async message reordering.
SRC: https://arxiv.org/pdf/2204.13464 ; https://arxiv.org/pdf/2112.12693
REL: Shows MPST embedded in an industrial language via affine typing and codegen from global types — the maturity bar the exploration should benchmark against, and evidence that failure = cancellation/affinity is the tractable industrial fragment.

CLAIM: Asynchronous session subtyping is undecidable (Bravetti, Carbone, Zavattaro, 'Undecidability of Asynchronous Session Subtyping', 2017): decidable only under syntactic restrictions or channel bounds; only sound-but-incomplete algorithms exist.
SRC: Undecidability of Asynchronous Session Subtyping — https://arxiv.org/pdf/1611.05026 ; A Sound Algorithm for Asynchronous Session Subtyping — http://mrg.doc.ic.ac.uk/publications/a-sound-algorithm-for-asynchronous-session-subtyping/main.pdf
REL: Hard ceiling on protocol evolution: 'is protocol v2 a safe refinement of v1 under async buffering' is not decidable in general, so a digest-named protocol registry cannot promise a complete compatibility check — it must pick a conservative, decidable fragment.

CLAIM: Dynamic topologies were addressed early — Deniélou & Yoshida, 'Dynamic Multirole Session Types' (POPL 2011, pp. 435-446) types protocols where an arbitrary number of participants dynamically join and leave a role — but this line did not make it into mainstream MPST toolchains.
SRC: Dynamic Multirole Session Types — https://dl.acm.org/doi/abs/10.1145/1925844.1926435 ; PDF https://www.doc.ic.ac.uk/~yoshida/paper/main.pdf
REL: The theory for agents joining/leaving mid-session exists but is unimplemented at scale — a known limit the exploration inherits, and a reason to prefer census-polymorphic formulations.

CLAIM: Protocol update-at-runtime has dedicated theory: 'Dynamically Updatable Multiparty Session Protocols' (Castro-Perez et al., ECOOP 2023) and 'Dynamic Software Update for Message Passing Programs' (Anderson & Rathke, APLAS 2012) identify restricted runtime points where a session-typed protocol can be swapped while preserving safety/liveness.
SRC: Dynamically Updatable Multiparty Session Protocols — https://dcastrop.github.io/files/2023-ecoop-dynamically.pdf ; Dynamic Software Update for Message Passing Programs — https://link.springer.com/chapter/10.1007/978-3-642-35182-2_15
REL: Versioning/evolution of a live protocol value is studied but restrictive — supports designing protocol digests as immutable with explicit migration points, mirroring the repo's 'derived-storage migrations are immutable' doctrine.

CLAIM: Runtime conformance monitoring against MPST projections is established theory: Bocchi, Chen, Demangeon, Honda, Yoshida, 'Monitoring networks through multiparty session types' (TCS 2017; FMOODS/FORTE 2013) give decentralised monitors per endpoint with proven safety/transparency; Aceto et al. 'On the Monitorability of Session Types' (2021+) delimits which properties monitors can actually catch. None of this work persists a hash-linked or content-addressed conformance log.
SRC: Monitoring Networks through Multiparty Session Types — https://link.springer.com/chapter/10.1007/978-3-642-38592-6_5 ; On the Monitorability of Session Types — https://arxiv.org/pdf/2105.06291
REL: Closest academic prior art to 'auditable conformance': monitors check projections at runtime, but evidence is ephemeral — no journal, no digests, no proof-by-recomputation. The exploration's audit-journal marriage remains unclaimed here.

CLAIM: The auditable-conformance-log idea exists for BPMN choreographies on blockchains: 'Untrusted Business Process Monitoring and Execution Using Blockchain' (Weber et al., BPM 2016) and ChorChain ('Engineering Trustable and Auditable Choreography-based Systems Using Blockchain', ACM TMIS 2022) compile choreography diagrams to Solidity contracts whose immutable execution trace lets auditors verify conformance continuously. The protocol's identity is a deployed contract address, not a content digest of a typed global protocol, and there is no projection-to-local-types type theory.
SRC: Engineering Trustable and Auditable Choreography-based Systems Using Blockchain — https://dl.acm.org/doi/10.1145/3505225 ; Untrusted Business Process Monitoring and Execution Using Blockchain — https://www.researchgate.net/publication/303996559_Untrusted_Business_Process_Monitoring_and_Execution_Using_Blockchain
REL: Partial novelty refutation: 'protocol + tamper-evident conformance log' is built — but with BPMN not session types, a global VM not local projections, and location-addressed (contract address) not content-addressed identity.

CLAIM: Nomos (Das, Balzer, Hoffmann, Pfenning, Santurkar, 'Resource-Aware Session Types for Digital Contracts', CSF 2021 / arXiv 1902.06056) uses shared binary session types plus linear types and amortized resource analysis to enforce interaction protocols of smart contracts on a ledger; protocols are compiled types, not digest-named values.
SRC: Resource-Aware Session Types for Digital Contracts — https://arxiv.org/abs/1902.06056
REL: Second partial refutation: session types already run inside an auditable ledger environment — but the ledger audits state transitions, not typed protocol conformance, and protocol identity is nominal.

CLAIM: Digest-as-schema-name is standardized practice for DATA schemas: Apache Avro's spec defines schema fingerprints over a Parsing Canonical Form (SchemaNormalization: Rabin CRC-64-AVRO, MD5, SHA-256), and Avro single-object encoding puts the 8-byte schema fingerprint on the wire before every message; Confluent Schema Registry has an open issue to adopt fingerprints as identifiers.
SRC: Avro SchemaNormalization — https://avro.apache.org/docs/1.8.1/api/java/org/apache/avro/SchemaNormalization.html ; Schema Registry fingerprint issue — https://github.com/confluentinc/schema-registry/issues/1294
REL: Strongest 'pieces already exist' evidence: canonical byte form -> digest -> universal name is production practice for value schemas. Nobody has lifted it one level to behavioral/global session types — which is precisely the exploration's claim.

CLAIM: Unison (v1.0 released 2025-11-25) identifies every definition by a SHA3-512 hash of its syntax tree and ships computations between nodes by hash — content-addressed CODE identity with distributed execution — but has no session/protocol typing layer; the unit of identity is a function, not an interaction protocol.
SRC: Unison: The Big Idea — https://www.unison-lang.org/docs/the-big-idea/ ; https://github.com/unisonweb/unison
LIC: Unison: MIT (compiler/runtime) => ideas and code portable, though only the naming discipline is relevant here
REL: Proves digest-named program values work end-to-end in a distributed runtime, including dependency pinning by hash — the exact mechanism the exploration wants for a global protocol value, applied one abstraction level lower.

CLAIM: IPVM/UCAN (Fission) specifies content-addressed computation: function invocations, results, and workflows are named by CIDs and authorized by capability chains; it is a Wasm/IPFS execution substrate, not a typed multiparty protocol system, and has no projection notion.
SRC: IPVM — https://fission.codes/ipvm/ ; IPVM Q1 2023 update — https://fission.codes/blog/ipvm-computation-ipfs/
REL: Adjacent decentralized-web prior art for content-addressed workflow identity; confirms the ecosystem addresses computations and data by digest but leaves protocol/topology types nominal.

CLAIM: A March 2026 design sketch by Gordon Brander ('Pi hash-addressed sessions') content-addresses AI agent session FILES (Blake3 blob + lineage sidecar, explicitly mirroring Git's object model) for p2p distribution — 'session' in the chat-log sense, with no session-type or protocol theory.
SRC: Pi hash-addressed sessions (gist) — https://gist.github.com/gordonbrander/70b3caf6ee5414ee7f9ee7516424b1ed
REL: Evidence the agent-tooling world is independently converging on content-addressed interaction artifacts — the journal half of foldlab — while still lacking the typed-protocol half; the marriage remains open.

CLAIM: A 2024 Springer survey chapter, 'Programming Language Implementations with Multiparty Session Types', catalogs the implementation landscape and its gaps; features like delegation and dynamic participants remain largely theory-only across mainstream toolchains, which mostly support fixed-roster, first-order protocols.
SRC: Programming Language Implementations with Multiparty Session Types — https://link.springer.com/chapter/10.1007/978-3-031-51060-1_6
REL: The authoritative map of what real MPST tools actually support — use it to bound what beep promises: fixed-census, delegation-free protocols are the implementable fragment today.

CLAIM: In-repo check: @beep/identity exists at packages/foundation/modeling/identity (package name "@beep/identity"; modules Curie.ts, Id.ts, PnLocal.ts, Vocab.ts, packages.ts), and journal-bearing source appears across at least packages/ontology/{domain,client,use-cases}, packages/epistemic/server, packages/law-practice/domain, packages/tooling/library/ai-metrics, and packages/drivers/postgres — consistent with the exploration's premise of multiple independent journal/fold instances plus a literal-typed identity layer (exact count of five not audited).
SRC: repo paths: ~/YeeBois/projects/beep-effect18/packages/foundation/modeling/identity/package.json ; rg -il 'journal' over packages/**/src
REL: Grounds premise (3) of the exploration: the raw material (journals, identity fibration) exists in beep-effect; a digest-named protocol value would sit above already-present machinery rather than requiring greenfield substrate.

TRACK: Content-addressed code and its runtime consequences

CLAIM: Unison identifies every definition by a 512-bit SHA3 hash of its syntax tree, computed after replacing named variables with positional references and dependency names with the dependencies' own hashes; names are 'just separately stored metadata'.
SRC: The big idea · Unison programming language — https://www.unison-lang.org/docs/the-big-idea/
LIC: MIT (unisonweb/unison)
REL: Exact industrial precedent for foldlab's 'one canonical byte form -> digest as universal name': the canonical form is a normalized AST (alpha-invariant, dependency-inlined-by-hash), so the digest names meaning, not spelling.

CLAIM: Because names are metadata, renaming in Unison is 'instant non-breaking renames' — no dependent code changes since dependents reference by hash; and because a definition's hash transitively incorporates its dependencies' hashes, 'dependency conflicts and the diamond dependency problem are just not a thing' — multiple versions coexist as distinct hashes and upgrades are explicit rebinding done 'at your leisure'.
SRC: The big idea · Unison programming language — https://www.unison-lang.org/docs/the-big-idea/
LIC: MIT (unisonweb/unison)
REL: Shows the two runtime consequences the exploration needs: (1) the human-name layer is a separate mutable register over immutable digests, and (2) digests pin the entire transitive dependency closure — a digest-named protocol would pin every agent schema it projects to.

CLAIM: Unison's codebase is 'a proper database of code' with a compilation cache that is 'never invalidated' ('we can parse and typecheck definitions once, and then store the results in a cache'), and the README adds perfect test caching: deterministic tests rerun only when their dependencies' hashes change.
SRC: The big idea — https://www.unison-lang.org/docs/the-big-idea/ ; unisonweb/unison README — https://github.com/unisonweb/unison
LIC: MIT (unisonweb/unison)
REL: Digest-keyed memoization of typecheck/test results is proof-by-recomputation with cached proofs — the same economics foldlab's fold results and verification ladder rely on.

CLAIM: Unison's distributed story is hash-sync of code: 'arbitrary computations can just be moved from one location to another, with missing dependencies deployed on the fly' — the receiver requests hashes it lacks and caches them permanently.
SRC: The big idea · Unison programming language — https://www.unison-lang.org/docs/the-big-idea/
LIC: MIT (unisonweb/unison)
REL: The distribution mechanism for a digest-named protocol value already exists as a pattern: agents that lack the protocol's digest fetch it by name, and identical digests guarantee identical protocol semantics on every node.

CLAIM: On Unison Cloud, 'every deployed service is known by its ServiceHash' derived from content hashing (identical code deploys to the same hash; updates mint new versions); Remote is the foundational ability ('the I/O of the Cloud'), services are 'typed, versioned, Cloud-hosted functions' callable across nodes without serialization, and durable storage (Cell, OrderedTable, Database) persists typed Unison values under a Transaction ability.
SRC: Core concepts | The Unison Cloud Platform — https://www.unison.cloud/docs/core-concepts/
REL: A running service's identity IS a digest — the closest existing system to 'topology as a digest-named value'; but the digest names one service's code, not the multi-party interaction between services.

CLAIM: Abilities are Unison's algebraic effects (based on the Frank language of Lindley, McBride, McLaughlin); effect requirements appear in function types as 'a ->{IO} b', typing what a single computation may do.
SRC: Abilities and ability handlers · Unison language reference — https://www.unison-lang.org/docs/language-reference/abilities-and-ability-handlers/
LIC: MIT (unisonweb/unison)
REL: Abilities are per-agent local effect types — they constrain one participant's side of an interaction, with no construct relating two parties' types to a shared global type; this is the seam the protocol-as-value thesis fills.

CLAIM: Unison Cloud's storage cheat sheet enumerates OrderedTable, Cell, Blobs, Batch, Config, Scratch, Table, Database, and the Storage ability — no append-only journal, event-log, or ledger abstraction appears, and no Unison documentation found connects Unison to session types, choreographies, or multiparty protocol conformance (searches for Unison + session types/multiparty return only unrelated MPST literature). UNCERTAIN: this is an absence-of-evidence claim from docs inventory and search, not an explicit statement by the Unison team.
SRC: Storage types cheat sheet | The Unison Cloud Platform — https://www.unison.cloud/docs/storage-solutions/
REL: Directly establishes track item (b): Unison content-addresses code and service identity but leaves journals and multi-party protocol conformance to the application — the exploration's proposed layer does not duplicate Unison.

CLAIM: Multiparty session types formalize exactly the projection discipline the exploration proposes: interactions are specified as a global type, projected onto local types per participant, and 'local conformance of all participants induces global conformance of the network to the initial global type'.
SRC: A Very Gentle Introduction to Multiparty Session Types (Yoshida & Gheri) — http://mrg.doc.ic.ac.uk/publications/a-very-gentle-introduction-to-multiparty-session-types/main.pdf
REL: The 'each agent's local type is a projection of the global type' thesis is MPST verbatim; the novel move in protocol-as-value is making the global type a digest-named, content-addressed VALUE rather than a static artifact of the type system.

CLAIM: Nix RFC 0062 makes derivation outputs content-addressed ('rather than deriving these output paths from the inputs of the build, we derive them from the output'), yielding early cutoff ('substantial build cutoffs') via resolved derivations — if two derivations differ only in deps with equal output hashes, 'resolved(drv) and resolved(drv′) will be equal' — and introduces a Realisation structure that 'decouples trust (tracked via signatures on realisations) from storage', letting mutually untrusting users share one store.
SRC: RFC 0062: content-addressed paths (NixOS/rfcs) — https://github.com/NixOS/rfcs/blob/master/rfcs/0062-content-addressed-paths.md
LIC: Nix implementation is LGPL-2.1 (copyleft — clean-room only if porting code); the RFC itself is a design document (reference only)
REL: Input-addressed vs content-addressed is the recipe-name vs result-name distinction a fold engine must choose per layer, and the signed-Realisation split is prior art for foldlab's fenced register (attested decisions) sitting beside recomputable content.

CLAIM: Dhall's semantic integrity check freezes an import to the SHA-256 of the CBOR binary encoding of its alpha-beta-normalized form — 'the semantic integrity check is not a hash of the raw underlying text' — an implementation 'MUST fail and alert the user if hash verification fails', the failure is not recoverable via the `?` fallback operator, and verified imports are cached keyed by the hash with multihash prefix 1220.
SRC: Dhall standard: imports.md (dhall-lang/dhall-lang) — https://github.com/dhall-lang/dhall-lang/blob/master/standard/imports.md
LIC: BSD-3-Clause (both dhall-lang/dhall-lang and dhall-lang/dhall-haskell) — port-with-attribution
REL: Strongest precedent that the 'one canonical byte form' should be a NORMAL form: behavior-preserving refactors keep the digest, so semantically-equal protocol values share one name and conformance checks become digest equality; the hard-fail-on-mismatch rule is a typed refusal.

CLAIM: Gabriella Gonzalez explicitly frames these semantic hashes as a replacement for version-number trust: 'Semantic integrity checks are the next generation of semantic versioning'.
SRC: Semantic integrity checks are the next generation of semantic versioning (Haskell for all) — https://www.haskellforall.com/2017/11/semantic-integrity-checks-are-next.html
REL: Gives the exploration its versioning story: protocol version negotiation between agents collapses to comparing the protocol value's digest, with no semver social contract needed.

CLAIM: A CID is 'a self-describing content-addressed identifier' — concretely 'a tuple of (content-type, content-address)' built from multihash (hash function + length), multicodec (payload type), and multibase (string encoding) — designed so 'any compatible hash-linked structure may be addressed within the same Merkle forest'.
SRC: CID (Content IDentifier) Specification (multiformats/cid) — https://github.com/multiformats/cid
LIC: Spec text CC-BY-3.0 (attribution required for prose); the ipld/ipld spec repo is dual Apache-2.0/MIT (permissive) — implementation repos carry their own licenses
REL: Solves digest-format governance the exploration will hit immediately: a bare sha256 hex string cannot survive hash migration or codec ambiguity, while a CID-style self-describing digest lets five existing beep-effect digest instances unify without agreeing on one hash function forever.

CLAIM: In the IPFS merkledag, 'links to objects can authenticate the objects themselves' and 'every object contains a secure representation of its children' — edges are merkle-links, so one root digest authenticates an entire DAG.
SRC: IPFS — Content Addressed, Versioned, P2P File System (Juan Benet) — https://arxiv.org/pdf/1407.3561
REL: A chained journal is a merkle-linked list: the head digest authenticates the whole history, so foldlab's proof-by-recomputation inherits tamper-evidence for free and agents can trust a journal prefix by verifying one digest.

CLAIM: 'At the core of Git is a simple key-value data store' — a content-addressable filesystem where blobs, trees, and commits are keyed by SHA-1 of header+content, trees reference blobs/subtrees by hash, commits reference a tree and parent commits by hash (forming a DAG), and identical content is stored exactly once.
SRC: Pro Git, ch. 10.2 Git Internals — Git Objects — https://git-scm.com/book/en/v2/Git-Internals-Git-Objects
LIC: git itself is GPL-2.0-only (COPYING: 'the only valid version of the GPL as far as this project is concerned is _this_ particular version') — copyleft, clean-room only for code; concepts freely citable
REL: Git is the journal/register split at world scale: the commit chain is a chained journal of tree digests, and refs/branches are the mutable register naming immutable content — evidence the exploration's two-surface design is the stable fixed point this class of system converges to.

CLAIM: 'Build Systems à la Carte' defines build correctness AS recomputation agreement: the result is consistent with the tasks iff 'for all non-input keys k ∈ O, the result of recomputing the corresponding task matches the value stored in the result: getValue k result == compute task result' (Definition 3.1, §3.6).
SRC: Build Systems à la Carte (Mokhov, Mitchell, Peyton Jones), Proc. ACM Program. Lang. ICFP 2018 — https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems.pdf (DOI: https://dl.acm.org/doi/10.1145/3236774)
REL: Peer-reviewed formal warrant for foldlab's proof-by-recomputation: correctness of a cached/fold-derived store is DEFINED as 'recomputing the fold reproduces the stored value' — the exploration's R-ladder is a graded version of Definition 3.1.

CLAIM: The paper's rebuilder taxonomy (§4.2): verifying traces store only hashes of dependencies and result to decide staleness; constructive traces 'additionally store the resulting value... it makes sense to record many constructive traces per key, and to share them with other users, providing cloud-build functionality' (a matching value can be copied in 'without doing any work'); deep constructive traces record only terminal input hashes, 'require the tasks to be deterministic' when skipping ≥2 levels, cannot support early cutoff, and enable shallow builds.
