# Adopt Alchemy Domain without rewriting blindly

**Date: 2026-11-03.** **beep-effect should adopt `@alchemy.run/domain` 2.0.0-beta.85 as its domain-definition kit, build a Postgres Platform that implements the exact `Platform`/`WorkflowEngine` contract rather than a generic event store, migrate by strangling one bounded context at a time behind genesis-seeded aggregates and old-shape projections, and prove the whole thesis first on law-practice scoped to DocketIntake (Matter, OfficeAction, DocketDeadline and the intake pipeline) with epistemic as runner-up.** The library already supplies the hard domain semantics — pure `decide`/`evolve`, typed rejections, single-writer aggregates, versioned Views, at-least-once Policies, durable Sagas through an Effect `WorkflowEngine`, Stories that run the real Model in memory, and Api projections to HTTP/OpenAPI, CLI and MCP — so the remaining engineering risk is not whether the domain language works but whether a Postgres host can honour its atomic-commit, delivery, checkpoint and deadline guarantees as faithfully as the shipped InMemory and Cloudflare Durable Objects hosts. Local package version is `2.0.0-beta.85` ([Source](packages/domain/package.json:3)), while beep-effect pins `2.0.0-beta.84` with effect `4.1.1` ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/package.json:3)), so the pin bump and a `Domain.verify` plus Story-suite pass are the first, cheap gate before any design is trusted.

## One Model, many Apis, one Platform is the whole architecture

The governing composition is **Model → Api → Platform**, and collapsing any two of those layers is the foundational anti-pattern. A `Domain.Model` is a bounded context declared as `Domain.Model(name, { aggregates, views?, policies?, projections?, streams?, sagas? })` ([Source](packages/domain/src/Model.ts:232)), hosted by exactly one Platform Layer, while one or more `Domain.Api` values project named subsets of that same Model to different clients. The canonical hosting line makes the separation visible: `Model.layer(handlers)` hosts aggregates, views and streams first, then builds policy, projection and saga handler Layers “after the aggregates, views and streams exist, so a handler can resolve them while it is constructed”, requiring only the ambient `Platform` ([Source](packages/domain/src/Model.ts:115)), and the in-memory idiom is `Bank.layer(BankPolicies).pipe(Layer.provide(Domain.InMemory))` ([Source](packages/domain/src/Model.ts:225)). An Api is “the public surface of a domain for one client”; the Model stays private except what the Api lists ([Source](packages/domain/src/index.ts:220); [Source](https://alchemy.run/domain/api)). HTTP, CLI, MCP and Foldkit are therefore projections of an Api, never parallel models, and restricting a client means making a smaller Api rather than filtering at a projection layer. The worked reference is the bank in `examples/cloudflare-domain`, whose `Bank.model.ts` lists 4 aggregates, 7 views, 6 policies, 2 projections, 1 stream and 1 saga ([Source](examples/cloudflare-domain/packages/domain/src/Bank.model.ts:1)), and whose per-audience split is explicit: `CustomerApi` serves customer commands, views, streams and `aggregates:["Account"]` while `SupportApi` serves `FreezeAccount/ChangeOwner/ApproveTransfer`, different views, `streams:[], aggregates:[]` ([Source](examples/cloudflare-domain/packages/domain/src/CustomerApi.api.ts:1); [Source](examples/cloudflare-domain/packages/domain/src/SupportApi.api.ts:1)).

For beep-effect this maps directly onto the existing law that one slice is one bounded context and that a process touching multiple slices' events does not belong in any of them ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/standards/architecture/10-cross-slice-coordination.md:1)). The immediate corollary is to resist one mega-Model for the whole product: the Alchemy doctrine is “Keep one language per model / Give each model its own data” ([Source](https://alchemy.run/domain/model)), so a slice in beep terms approximates one Model in its own domain package and cross-slice reactions become Policies or Sagas over promoted, versioned contracts. The fit with beep's rich-domain standard is mechanical rather than aspirational, because beep already requires schemas to own shape, validation and pure decisions and forbids infrastructure in domain `R` ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/standards/architecture/04-rich-domain-model.md:103)), and Alchemy enforces the same split by construction: `decide` is pure, `evolve` only folds, and I/O lives only in Policy, Saga, Projection and External System Layers. Project layout follows the same discipline, one file per block named `<Noun>.<kind>.ts` (`.aggregate/.command/.view/.policy/.saga/.projection/.stream/.external/.api/.model/.middleware/.context/.rejection/.id`), folders per subdomain, a pure domain package importing only `@alchemy.run/domain` plus `effect`, a server package that hosts, and a web package that is Foldkit ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1); [Source](https://alchemy.run/domain/project-layout)). Before any Model is hosted, `Domain.verify(Model)` is the cheap pre-flight: it returns “every problem that would otherwise fail its Layer's build… Returns all of them, in definition order; an empty array means the Model is valid”, catching defects such as a view consuming a differently-keyed source without `keyOf`, a policy listening for an event no source emits, or a stream with two writers ([Source](packages/domain/src/Model.ts:284)), and the skill checklist requires a test that expects that array to be empty ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1)).

The **Aggregate is the sole consistency boundary**, and its three-function contract is the idiom everything else depends on. An aggregate is defined by `{ id, state, initial, commands, decide, evolve, reply?, read? }` ([Source](packages/domain/src/Aggregate.ts:122)); `decide` “returns the events to commit… an empty array for an accepted no-op, or one of the command's declared rejections” and may be an Effect that reads only the context its command's middleware provides and may require nothing else ([Source](packages/domain/src/Aggregate.ts:139)); `evolve` “covers every state and never fails” because `decide` refuses before it records an event a state cannot follow ([Source](packages/domain/src/Aggregate.ts:153)); and `reply` is computed from the updated state and committed events and likewise never fails ([Source](packages/domain/src/Aggregate.ts:166)). The processing guarantee is that each command goes to one aggregate instance and decide, events, state and reply commit at once, while consumers catch up after the commit via deliveries ([Source](https://alchemy.run/domain/model)). Commands, Events and Rejections divide validation cleanly along the same line. A `Domain.Event(tag, fields?, { attributes? })` is a `Schema.TaggedClass` carrying past-tense fact and no behaviour ([Source](packages/domain/src/Event.ts:53)), a `Domain.Command(tag, { target, input?, middleware?, events?, rejects?, reply?, attributes? })` builds an Effect RPC whose payload is `{ target, commandId?, input }`, whose success is `{ reply, stream, version }` and whose error is the union of `rejects` ([Source](packages/domain/src/Command.ts:193)), and target discipline is type-enforced in both directions so a mismatched `target` is a type error at the aggregate's `commands` entry ([Source](packages/domain/src/Aggregate.ts:734)). Schema decode validates shape at the boundary and business validation lives exclusively in `decide`, which is why the beep schema-first laws are satisfied rather than translated: the Command, Event and Rejection classes are the schemas. The anti-patterns are precise negatives of these facts. Commands must carry intent rather than outcome fields, because Events carry the decided outcome such as `balanceAfter` so that `evolve` copies rather than recomputes and only `decide` creates events ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1); [Source](https://alchemy.run/domain/event)); rejections are the only refusal channel and handlers never `throw` but fail with tagged errors ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1)); `evolve` and `reply` never guard by throwing; cross-aggregate invariants never live inside one aggregate; and compensation commands are never refused ([Source](https://alchemy.run/domain/aggregate)). Idempotency is a command property, not a client hope, because “Pass a `commandId`, and a resend with the same id returns the first receipt instead of applying the command again” ([Source](packages/domain/src/Command.ts:183)), exposed client-side as `CommandOptions.commandId` ([Source](packages/domain/src/Api.ts:284)). Event upcasting beyond “Keep old events readable” is **UNVERIFIED** in depth ([Source](https://alchemy.run/domain/event)), so the playbook stores a `schema_version` per persisted event and treats decode-time upcasting as beep-owned design until the library contract is read more closely.

Views, Projections and Streams are three different answers to the read-side question, and choosing among them by habit rather than by ownership is the most common design error the library is built to prevent. A **View** folds events into a per-key read model the platform owns, defined by `{ from, key, keyOf?, state?, initial?, evolve?, events?, emit?, computed?, version?, middleware?, rejects?, validate? }` where `from` is aggregates and/or views and `key` is an aggregate or a string Schema ([Source](packages/domain/src/View.ts:194)); its `evolve` returns `null` to delete the key, its `emit` runs after `evolve` with `{ before, after }`, and without declared `events` a view re-emits every applied event unchanged ([Source](packages/domain/src/View.ts:226)). A **Projection** consumes events into a store you own, defined by `{ from, key, keyOf?, on, writes? }` and implemented through `toLayer(build, options?)`, whose handler receives a `batch: Input[]` and requires nothing per call because dependencies resolve once in `toLayer` ([Source](packages/domain/src/Projection.ts:140); [Source](packages/domain/src/Projection.ts:38)). A **Stream** is the model-owned special case, a keyed append-only log a Projection writes and clients read like a View, defined by `{ key, entries, middleware?, rejects?, validate? }` ([Source](packages/domain/src/Stream.ts:46)), with `peek`, `watch`, `events`, `list` for readers and writer-only `append(origin, ...events)` where “Only a projection that lists this stream in `writes` may append, and a replayed or redelivered input appends nothing twice” ([Source](packages/domain/src/Stream.ts:77)). The decision rule follows from ownership: use a View when the platform should own storage, replay, security and live reads; use a Projection when you own the store, as beep will for existing Drizzle tables during migration; use a Stream for feeds and cards where the latest entry is the current value without inventing a table per feed. Two disciplines keep the read side honest. First, a Projection “never sends commands: replaying it must never act on the world again” ([Source](packages/domain/src/Projection.ts:170)), and its idempotency idiom is to key rows by `` `${envelope.stream}:${envelope.seq}` `` ([Source](packages/domain/src/Projection.ts:198)), with read-your-write available through `Ledger.caughtUp(receipt)` and `Progress.caughtUp(receipt, options?)` returning `Effect<void, ConsistencyTimeout>` ([Source](packages/domain/src/Projection.ts:242)). Second, Views are versioned and rebuildable: “Bump it whenever you change what the view computes… Only ever increase it”, with single-source views rebuilding in place lazily and others rebuilding from history before deploy finishes ([Source](packages/domain/src/View.ts:250)), and `lazy: [ViewName]` on `Model.layer` deferring rebuild of single-aggregate-keyed views to first read ([Source](packages/domain/src/Model.ts:188)). Forgetting the version bump after changing `evolve`, `emit`, `keyOf` or state, querying aggregates for reads, and putting authorisation in clients instead of `validate` are the named View anti-patterns. The live-read idiom is equally specific: “Render a snapshot, then follow it”, because `snapshot` returns `{state, cursor}` and `events(key, {after: cursor})` then misses nothing and duplicates nothing ([Source](packages/domain/src/Api.ts:182); [Source](https://alchemy.run/domain/view)), while consistency failures stay typed as `WaitTimeout` and `ConsistencyTimeout{view,key,stream,version}` ([Source](packages/domain/src/View.ts:21)).

Policies and Sagas divide reaction from process, and the boundary between them is duration and compensation rather than complexity. A **Policy** is a standing “whenever X, do Y” rule whose declaration holds only `from/on/key/keyOf` while its `toLayer(build, options?: { retry?: Schedule })` handler resolves all services once at construction so that “the handler itself requires nothing” ([Source](packages/domain/src/Policy.ts:85); [Source](packages/domain/src/Policy.ts:247)). It runs after the triggering event commits, at least once, in order per key, receiving `{ key, route, source, event, envelope, state }` ([Source](packages/domain/src/Policy.ts:18)), and “the commands a policy sends get ids derived from the event, so a second run sends the same commands” ([Source](packages/domain/src/Policy.ts:124)) through deterministic `PolicyRun` command ids ([Source](packages/domain/src/Aggregate.ts:634)). Tuning lives on the Layer, never the declaration, through `options.retry` ([Source](packages/domain/src/Policy.ts:37)). A **Saga** is a durable multi-aggregate process as an Effect Workflow, defined by `{ key, input?, result?, rejects? }` where starting again with the same key returns the same run because `idempotencyKey = payload.key` ([Source](packages/domain/src/Saga.ts:84); [Source](packages/domain/src/Saga.ts:268)); its client offers `start(key, input)` returning at once and `get(key)` returning a `Run` whose status is `NotStarted|Running|Completed|Rejected|Interrupted|Died` ([Source](packages/domain/src/Saga.ts:104)); steps are `Activity`s whose results are kept, undo is `withCompensation` sending compensating commands rather than erasing history, and saga-step sends receive deterministic command ids so re-run steps resend identical commands ([Source](packages/domain/src/Saga.ts:208); [Source](packages/domain/src/Aggregate.ts:644)). The rule is single reaction to Policy, multi-step with time or compensation to Saga ([Source](https://alchemy.run/domain/saga)), and the two cardinal Saga anti-patterns are waiting for a Saga inside a Policy — “Don't wait for it in a policy. `start` it, keyed by the aggregate it's about, and react to the events its steps record” ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1)), reinforced by “A run can take days, so wait in tests and scripts, not in a policy or a request” ([Source](packages/domain/src/Saga.ts:119)) — and attempting a distributed transaction across aggregates, which the model explicitly forbids because no transaction spans two aggregates. **External Systems** complete the effectful perimeter: `Domain.ExternalSystem` declares outside systems in domain language as typed ops with `args/success/error` schemas, producing an Effect service with one `Effect<Success, Error>` function per op plus per-op references for Stories ([Source](packages/domain/src/ExternalSystem.ts:308)), implemented by `toLayer` in the server package with schema-checking of every call unless `validate: false` ([Source](packages/domain/src/ExternalSystem.ts:196)), and called only from Policies and Sagas. Outside events become commands through an in-process Api client acting as a system actor, never direct aggregate writes ([Source](https://alchemy.run/domain/external-system)), which gives beep a clean mapping from its driver and port contracts: the declaration lives in the domain package, the adapter Layer lives in the server package, and the domain package still imports only domain plus effect ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1)).

Authorisation, uniqueness and deadlines are where the library's opinion is strongest, and each replaces a database habit with a domain construct. Authorisation is declared, not sprinkled: middleware is an ordered `RpcMiddleware.Service` list such as `[Session, MfaChallenge]`, meaning authenticate then challenge, and what middleware provides is exactly what `decide` may `yield*` ([Source](packages/domain/src/Middleware.ts:1); [Source](packages/domain/src/Command.ts:161)). `Domain.RequestContext<Self>()(key, schema)` declares a schema-carried per-request service such as `CurrentActor` encoded with the command or read so it survives crossing to a Durable Object or another process ([Source](packages/domain/src/RequestContext.ts:31)). Reads share one security contract across Views, Streams and aggregate `read`: `{ middleware?, rejects?, validate?(request:{mode,key}, state) }` runs “on every `get` and `list`, and on every change while a client watches: failing ends the watch”, and without it “anyone who reaches the Api may read every key” ([Source](packages/domain/src/Read.ts:59)). The doctrine is to write the rule once in `validate`, rule by key, give each audience its own View, re-check every change, and remember that client `where` filters never widen access because “access never depends on analyzing them” ([Source](packages/domain/src/Read.ts:43); [Source](https://alchemy.run/domain/view-security)). Field-level redaction is deliberately not a View feature, because “A view decides who may read it, not which parts they may see. To show an audience different data, make another view” ([Source](https://alchemy.run/domain/view-security)), so per-field filtering as security and auth checks in HTTP handlers are both anti-patterns. Sessions follow the same shape, with cookie sign-in, signed sessions, tokens out of URLs and MFA as a second middleware ([Source](https://alchemy.run/domain/sessions)), and a better-auth variant wires external sign-in to the same `CurrentActor` contract ([Source](https://alchemy.run/domain/better-auth)); the exact cookie signing and rotation mechanics live in project middleware rather than the library, which is **UNVERIFIED** at library level by design. Cross-instance uniqueness is an aggregate keyed by the value, as with a `UsernameClaim` keyed by username, claimed before registering and race-tested through Stories ([Source](https://alchemy.run/domain/unique-values); [Source](examples/cloudflare-domain/packages/domain/src/Bank.model.ts:1)), because uniqueness via read-then-write in a Policy is racy. Deadlines are scheduled commands the aggregate adjudicates: declare a non-rejecting deadline command, `schedule(id, cmd, {at|after, commandId})`, cancel with `unschedule(id, commandId)`, let aggregate state decide the race between deadline and action so the loser is a no-op, and expect `AlreadyExecuted`, `AlreadyCancelled` or `NotScheduled` failures ([Source](packages/domain/src/Aggregate.ts:224); [Source](https://alchemy.run/domain/deadlines)). A `setTimeout` deadline is therefore not a simplification but a correctness bug, since only the durable schedule is Story-clock testable and crash-safe.

**Stories are the specification surface, and they are stricter than conventional unit tests.** `Story.make(Model, { layer: HandlerLayers, stub?: [ExternalSystem...] })` returns a `story(...steps)` runner whose vocabulary is exactly `given, when, then, rejected, replied, state, view, emitted, streamed, call, succeed, fail, die, returned, failed, died, clock, advance, provide, signal, saga, none` ([Source](packages/domain/src/Story.ts:1478)), and the steps are type-checked so that a `rejected` step only accepts rejections the last `when` command declares, a `replied` step only accepts its reply type, and a `when` requires prior `provide` for every middleware-provided service, with wrong steps becoming type errors naming the fix ([Source](packages/domain/src/Story.ts:215)). Strict accounting is the point: “A story fails on any committed event, rejection, external system call or saga defect it doesn't account for” ([Source](packages/domain/src/Story.ts:1400)), and “Every recorded event needs a `then`, on every instance, including the ones a policy writes” ([Source](https://alchemy.run/domain/testing-models)). Stories run the real Model in memory with policies, sagas, external calls and clock all live; stubbed external calls suspend until answered through `call` before `succeed/fail/die`, unstubbed calls run real Layers and are asserted with `returned/failed/died` ([Source](packages/domain/src/Story.ts:1430)), sagas are asserted with `Story.saga` and driven with `Story.signal` ([Source](packages/domain/src/Story.ts:1467)), and time is deterministic because stories start at `2026-01-01T00:00:00Z`, `Story.clock(at)` sets and `Story.advance(duration)` moves forward only, with scheduled commands firing when the clock passes them ([Source](https://alchemy.run/domain/testing-models)). Failures are diagnosable as `StoryFailure{ step, reason, steps: StepReport[], events: per-aggregate tags }` ([Source](packages/domain/src/Story.ts:41)). Api testing is tiered on top of the same discipline: in-process through `clientInProcess` with signed test actors, then over HTTP, then against a deployment, with a fresh Model per test through `Effect.scoped` and a World Layer ([Source](https://alchemy.run/domain/testing-apis); [Source](website/src/content/docs/domain/testing-apis.mdx:1)), and the adapter-parity prescription is to “Run the same tests against every adapter” ([Source](https://alchemy.run/domain/testing-models)). The beep pyramid follows directly: Story files per rule covering happy path, every rejection and every policy reaction in the domain package; Api tests for authorisation matrices; no unit tests of Saga internals, since the prescription is to test outcomes and not a saga's internal steps ([Source](packages/domain/skills/alchemy-domain/SKILL.md:1)); and time travel only through the Story clock, never mocked `Date.now` in domain code. The auxiliary oracles are `Domain.verify`, `Aggregate.predict` and `View.evolve`, and the in-memory control surface `InMemory.make({manual?, now?})` exposing `drain, idle, failures, deaths, commits` serves non-Story tests ([Source](packages/domain/src/InMemory.ts:46)). Exact beep test-runner wiring beyond the assumed `@effect/vitest` `it.effect/it.live` style ([Source](packages/domain/src/Story.ts:1410)) is **UNVERIFIED**.

The remaining surfaces are mechanical projections, and treating any of them as architecture is the error they exist to prevent. Plain HTTP and OpenAPI come from `DomainHttp.toHttpApi(Api)` returning `{ group, api, layer, layerFor }` with `OpenApi.fromApi(BankHttp.api)` producing the document and `HttpApiBuilder.layer(api, {openapiPath:"/openapi.json"})` serving it ([Source](packages/domain/src/Http.ts:316)); the mapping is `POST /<Command>` with body `{target, commandId, input}`, `GET /<Name>/{key}`, `/{key}/snapshot`, `/{key}/list?order&take&after`, `/{key}/watch` as SSE and `/{key}/events?after` as SSE, with `?stream=&version=` expressing the `atLeast` wait ([Source](packages/domain/src/Http.ts:264)). Errors are disciplined: a typed failure answers its `httpApiStatus` annotation or else 422, schema-refused input answers 400 before the model, an undeclared failure is a defect answering 500, a pre-first-value live-read failure answers with status and a later failure ends the SSE stream with an `effect/http-api/stream/failure` event ([Source](packages/domain/src/Http.ts:273); [Source](https://alchemy.run/domain/http-api)). The limits matter as much as the mapping: read `where` filters are not published because they cannot be represented in a URL, and differently-shaped public JSON requires a custom `HttpApi` group calling the Api client ([Source](packages/domain/src/Http.ts:287)). The CLI is `toCli(Api, {...})` from the separate `@alchemy.run/domain/Cli` import so non-CLI apps never load `effect/cli`, generating one kebab subcommand per served call against the deployed Api over the HTTP protocol, with typed failures printing wire JSON to stderr and exiting 1 through `CallRejected` ([Source](packages/domain/src/Cli.ts:24); [Source](https://alchemy.run/domain/cli)). MCP and AI tooling come from `Ai.toToolkit` and `toMcp`, generating one tool per non-streaming call named `<api>_<name>_<operation>` such as `BankApi_DepositMoney_send`, annotated Readonly, Destructive or Idempotent, while streaming calls are excluded because `isToolCall = !op.stream` ([Source](packages/domain/src/Ai.ts:174); [Source](packages/domain/src/Ai.ts:102)). Observability is automatic tracing of the command-to-event-to-reaction flow with correlation ids, where the only declaration required is `attributes: (cmd|event) => Record<string, unknown>` on Commands and Events, “Nothing from the input is recorded unless you return it here, and a `Redacted` value is recorded as `<redacted>`” ([Source](packages/domain/src/Command.ts:219); [Source](packages/domain/src/Event.ts:58)), plus the `telemetry` option on `Model.layer` ([Source](packages/domain/src/Model.ts:175)) and correlation through `Envelope.correlationId` with sender span in `SendMeta.trace` ([Source](packages/domain/src/Aggregate.ts:242)). Nothing in domain source or docs is labelled experimental, since text search for “experimental” over `packages/domain/src`, `packages/cloudflare/src/Domain` and the domain docs found no experimental flags on 2026-11-03 ([Source](packages/domain/src/index.ts:1)), so the pre-1.0 beta versioning itself is the stability signal. The doc-versus-code gaps to carry into adoption are that Filter and OrderBy, Key, CatchUp and Predict are public code but doc-light and must be treated through source and integration tests as normative; that Foldkit, Ai/MCP, Cli and Http are separate-entrypoint modules requiring subpath imports; and that the vendored skill file `packages/domain/skills/alchemy-domain/` is the most current idiom summary and should be copied into beep agent instructions alongside the docs.

## A Postgres Platform copies prior art, not a generic event store

The single most important implementation fact is that **the Postgres Platform does not implement append and load; it implements `Platform.model(model) → ModelHost` with five per-concept stores plus optional `start` and `history`, and it must also provide the Saga `WorkflowEngine` that the shipped hosts bundle alongside `Platform`.** The entry point is a `Context.Service` with exactly `model: (model: HostedModel) => Effect<ModelHost, never, Scope>` ([Source](packages/domain/src/Platform.ts:662)), where `HostedModel = { modelName, id, sagas: string[], legacyData }`, two models sharing an aggregate definition must never share data, and hosting two different models with the same name on one platform fails ([Source](packages/domain/src/Platform.ts:643)). The `ModelHost` factories are `aggregate(aggregate, kit)`, `view(view, kit)`, `policy(policy, kit)`, `projection(projection, kit)` and `stream(stream, kit)`, each called once per entity while the Model Layer is built, plus optional `start?(targets, planOf, backfill)` and `history?(target)` for cross-deploy catch-up and backfill ([Source](packages/domain/src/Platform.ts:607)). The kernel Kits do all domain logic and the platform only persists and moves JSON, because “The kernel owns the schemas; platforms only move and store these values” with `type Json = unknown` ([Source](packages/domain/src/Platform.ts:36)); the Kits the platform must drive are `AggregateKit.handle/seed/deliver/replay/push` ([Source](packages/domain/src/Platform.ts:190)), `ViewKit.apply/deliver/history/replay/observe/push` with generation and catch-up helpers ([Source](packages/domain/src/Platform.ts:343)), `PolicyKit.run(delivery)` ([Source](packages/domain/src/Platform.ts:440)), `ProjectionKit.run(key, batch: Accepted[])` ([Source](packages/domain/src/Platform.ts:476)) and `StreamKit.push(...)` ([Source](packages/domain/src/Platform.ts:561)). No Postgres or SQL platform exists in the checkout, since `Platform.ts` and `InMemory.ts` contain no SQL store and only InMemory and Cloudflare Durable Objects hosts are shipped ([Source](packages/domain/src/Platform.ts:662); [Source](packages/cloudflare/src/Domain/index.ts:2257)), so every table and protocol below is beep-designed against these contracts and marked accordingly where it extrapolates.

Each store contract is small and precisely bounded. `AggregateStore` requires `send(id, command: Json, meta: SendMeta) => Effect<SendResult>`, `schedule(id, command, meta, due) => Effect<number, AlreadyExecuted>`, `unschedule(id, commandId) => Effect<void, AlreadyExecuted|AlreadyCancelled|NotScheduled>`, `state(id)`, `changes(id)` and `tail(id, after)`, with optional `events?`, `seed?` and `connect?` for WebSocket upgrade ([Source](packages/domain/src/Platform.ts:247)), and must guarantee “single writer per id; dedupe by `commandId`; persist events, state, receipt and deliveries atomically; then deliver at least once, in order” ([Source](packages/domain/src/Platform.ts:249)). `ViewStore` requires `receive(key, deliveries)`, `read(key)`, `changes(key)`, `list(key)` and `tail(key, after)` with optional `connect?` ([Source](packages/domain/src/Platform.ts:419)), where `ViewKit.apply` “Drops duplicates. Persist the snapshot and entries together, then send the downstream deliveries” ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Platform.ts:311-435](/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Platform.ts)). `PolicyStore` requires only `receive(delivery)` under the rule “Run deliveries at least once, in order per key” ([Source](packages/domain/src/Platform.ts:449)). `ProjectionStore` requires `receive(delivery)` to accept into a per-key input log, drop dupes by `(source, seq)`, process in order in batches, plus `checkpoints(key) => Effect<Record<string, number>>` ([Source](packages/domain/src/Platform.ts:510)), where `Accepted{position (from 1), delivery, at}` is the immutable per-key input log and `ProjectionKit.run` “Succeeds only when every write the handler made succeeded; the platform then records the run as processed” ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Platform.ts:454-518](/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Platform.ts)). `StreamStore` requires `append(key, write)`, `advance(key, checkpoints)`, `read(key)`, `changes(key)`, `list(key)` and `tail(key, after)` with optional `connect?`, and append must drop writes whose origin is not after the last applied origin ([Source](packages/domain/src/Platform.ts:579)). Deliveries are at-least-once, in order per `(source, target)`, deduped by targets on `(source, seq)` ([Source](packages/domain/src/Platform.ts:63)), and the envelope carries `id`, `stream`, `seq` “within its stream, starting at 1”, `at`, `commandId` and `correlationId`, stamped as `seq: version + index + 1` ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Platform.ts:41-52](/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Platform.ts); [/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Aggregate.ts:491-497](/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Aggregate.ts)). The Durable Objects commit is the reference implementation to port rather than InMemory, because InMemory has no crash boundary: inside `state.storage.transaction` the DO host checks `receipt:${commandId}`, runs `kit.handle`, then in one transaction puts `event:${pad(seq)}` rows, `meta{state,version}`, `receipt:${commandId}`, updated `routed` and `outbox.stage(live.send)`, with delivery afterwards through `outbox.kick` ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/cloudflare/src/Domain/index.ts:726-790](/home/elpresidank/YeeBois/references/effect/alchemy/packages/cloudflare/src/Domain/index.ts)). Its outbox is a durable ordered queue staged in the same transaction as its cause, drained under a 60-second storage lease, with the row deleted only after its work succeeds and a 10-second durable-callback backstop if the instance dies before `kick` ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/cloudflare/src/Domain/index.ts:197-260](/home/elpresidank/YeeBois/references/effect/alchemy/packages/cloudflare/src/Domain/index.ts)), and scheduled commands use a token protocol where `scheduled:<commandId>` holds a random token or `CANCELLED`, the fired job re-reads the key and no-ops if the token no longer matches, then commits and deletes the key so the receipt takes over ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/cloudflare/src/Domain/index.ts:797-875](/home/elpresidank/YeeBois/references/effect/alchemy/packages/cloudflare/src/Domain/index.ts)). Sagas do not run on `Platform` at all but on Effect's `WorkflowEngine`, since `Saga` delegates `scheduleClock` to the engine ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Saga.ts:414](/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/Saga.ts)) and InMemory's Layer provides `Platform | WorkflowEngine` together ([/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/InMemory.ts:98-99](/home/elpresidank/YeeBois/references/effect/alchemy/packages/domain/src/InMemory.ts)), so whether beep builds a durable Postgres `WorkflowEngine` or reuses an Effect Cluster or Workflow backend is the largest open scoping question and remains **UNVERIFIED** from the sources read.

Prior art divides into what to copy literally, what to copy conceptually and what to avoid, and the closest system to beep's stack is **Emmett**, a TypeScript event store whose Postgres schema creates partitioned `emt_streams`, `emt_messages` and `emt_subscriptions` tables ([Emmett PostgreSQL event store](https://event-driven-io.github.io/emmett/event-stores/postgresql.html)). Its source DDL gives `emt_streams(stream_id TEXT, stream_position BIGINT, partition TEXT, stream_type TEXT, stream_metadata JSONB, is_archived BOOLEAN, PRIMARY KEY(stream_id, partition, is_archived))` partitioned by list on partition, `emt_messages` with `stream_position`, `global_position BIGINT DEFAULT nextval('emt_global_message_position')`, `transaction_id XID8`, `message_type`, `message_data JSONB` and primary key `(stream_id, stream_position, partition, is_archived)` plus an index on `(transaction_id, global_position)`, and `emt_processors` keyed by `(processor_id, partition, version)` carrying `last_processed_transaction_id XID8` and `last_processed_checkpoint` (https://github.com/event-driven-io/emmett/blob/main/src/packages/emmett-postgresql/src/eventStore/schema/tables.ts). Its append is a PL/pgSQL function returning success, next stream position, global positions and transaction id, where a null expected version reads current, zero means stream-does-not-exist enforced by insert primary-key violation, minus-one means stream-exists enforced by update, and otherwise a conditional `UPDATE streams SET stream_position = next WHERE stream_id=? AND stream_position = expected` with row count zero signalling conflict, after which messages are inserted with `row_number() OVER () + expected` as stream position (https://github.com/event-driven-io/emmett/blob/main/src/packages/emmett-postgresql/src/eventStore/schema/appendToStream.ts). **Marten** contributes the lifecycle split rather than table shapes: `mt_events` carries `seq_id` as sequential primary key, `stream_id`, per-stream `version`, `data` JSONB and `type`, with uniqueness on `(stream_id, version)` as `pk_mt_events_stream_and_version`, `mt_streams` holds stream metadata and `mt_event_progression` is “a durable record about the progress of each async projection through the event store” keyed off the sequential `seq_id` ([Marten event storage](https://martendb.io/events/storage.html)), while projections are inline when “executed at the time of event capture and in the same unit of work”, async through a background daemon, and an aggregate snapshot is a projection of a stream into a queryable document ([Marten projections](https://martendb.io/events/projections/)). KurrentDB contributes expected-revision API semantics in which append takes an expected stream revision and the server rejects on mismatch with expectations of any, no-stream, stream-exists or exact revision ([KurrentDB appending events](https://docs.kurrent.io/clients/node/legacy/v6.2/appending-events)), and `$all` catch-up subscriptions reading in global chronological order from a `{commit, prepare}` position the client persists to resume ([KurrentDB subscriptions](https://docs.kurrent.io/clients/python/v1.3/subscriptions)). Axon contributes table separation across `domain_event_entry`, `snapshot_event_entry`, `saga_entry` with `association_value_entry`, tracking-processor tokens in `token_entry` and a separate `DeadlineManager` abstraction ([Axon 5 event-store migration](https://docs.axoniq.io/axon-framework-reference/5.4/migration/paths/event-store/); [Axon deadline managers](https://docs.axoniq.io/axon-framework-reference/5.1/deadlines/deadline-managers/)), while eventsourcing.py contributes the minimal design in which a single `stored_events` table's composite primary key `(originator_id, originator_version)` is itself the optimistic-concurrency enforcement ([eventsourcing.py postgres module](https://eventsourcing.readthedocs.io/en/stable/_modules/eventsourcing/postgres.html)) and Equinox contributes snapshot-in-tip, where a per-stream Tip document holds snapshots or unfolds while events remain the source of truth ([Equinox documentation](https://github.com/jet/equinox/blob/master/DOCUMENTATION.md)). The copy list is therefore Emmett's compare-and-swap append and `(transaction_id, global_position)` checkpoint shape, Marten's inline-versus-async split with snapshots as queryable JSONB documents, Axon's separation of event, snapshot, saga, token and deadline tables, eventsourcing.py's composite-key backstop, Equinox's snapshot-in-tip and the Durable Objects token-timer and staged-outbox protocols. The avoid list is equally explicit: bare `BIGSERIAL` global watermarks, Effect Cluster `MessageStorage` as an event journal since it is a durable mailbox and not a journal ([Effect cluster sharding handbook](https://eugene1g.github.io/effect-handbook/systems/cluster-sharding), secondary source with primary details **UNVERIFIED**), exactly-once delivery claims, saga state stored only as serialized blobs, and `LISTEN/NOTIFY` as a delivery mechanism rather than a wakeup hint. Upcasting belongs in the codec layer at decode time, never as an update over stored JSONB, consistent with the consensus to keep stored events immutable, version schemas, transform old shapes at deserialisation with incremental upcasters and prefer a new event type when semantics change ([Microsoft event-sourcing pattern](https://learn.microsoft.com/th-th/azure/architecture/patterns/event-sourcing?view=azurermps-6.1.0), **UNVERIFIED** at page-fetch depth).

The recommended v1 blueprint is **one Postgres schema per Model with nine tables**, and its transaction boundaries are the design. The `streams` head table carries kind, name, id, version equal to last seq, materialised JSONB state, a JSONB checkpoints map and generation, making `state(id)` an O(1) read in the Equinox tip style. The `events` table carries stream, seq, a `global_seq` from a sequence used only as a scan aid, event id, tag, `schema_ver` for upcast dispatch, event JSONB and the full envelope, with primary key `(stream, seq)` as the eventsourcing.py backstop. The `receipts` table keys `(stream, command_id)` to the stored `SendResult`; the `outbox` table stages deliveries in the commit transaction with a `(target, source, seq)` unique constraint and lease columns; the `input_log` table holds accepted projection deliveries with primary key `(consumer, key, position)` and unique `(consumer, key, source, seq)`; the `checkpoints` table holds per-consumer processed position, per-source seq map and generation; the `timers` table holds scheduled commands with due time, token and cancelled tombstone; and the `reservations` table holds set-validation claims with scope, value, owning stream and state. A dedicated snapshots table is deliberately skipped in v1 because the head row is the snapshot, to be added only when state exceeds roughly 100KB or rebuild cost hurts. Aggregate `send` is one transaction that locks the head row with `SELECT … FOR UPDATE`, checks receipts, runs the pure Kit, inserts events, updates head state and version, inserts the receipt and stages outbox rows before commit and relay kick, which prevents lost update, partial commit and duplicate command. View `receive` locks the view head, drops deliveries at or below the checkpoint, applies the Kit, persists snapshot, entries and checkpoints together and stages downstream deliveries, which prevents double-apply and checkpoint-ahead-of-state. Projection `receive` inserts into the input log with conflict-do-nothing on `(consumer,key,source,seq)`, processes unprocessed positions in order in batches and updates checkpoints in the handler's transaction when the handler writes to the same database, which prevents out-of-order invocation and skipped positions. Timer fire claims due rows with `FOR UPDATE SKIP LOCKED`, verifies token and cancelled flag, runs send semantics and deletes the row so the receipt guards refire, which prevents fire-after-cancel and double-fire on failover; timer claiming by `FOR UPDATE SKIP LOCKED` with pg_cron as an optional short-interval poller is the established Postgres job pattern ([Postgres SKIP LOCKED job scheduling](https://reliableuptime.com/blog/postgres-skip-locked-job-scheduling); [Citus pg_cron](https://www.citusdata.com/blog/2023/10/26/making-postgres-tick-new-features-in-pg-cron)). Outbox relay claims pending rows in position order per target, delivers, deletes on success and backs off on failure, with immediate kick after every commit plus a five-to-ten-second poller backstop and optional NOTIFY wakeup, and the relay choice among polling, Debezium CDC and LISTEN/NOTIFY follows the established comparison that notifications are signals rather than durable messages and must be backed by a table scan ([Transactional outbox / CDC comparison](https://sandgraal.github.io/letstalkcdc/transactional-outbox/)). Concurrency control is per-key head-row locking as the Marten `UseAppendEventForUpdateLock` analogue, backed by the `(stream, seq)` primary key and a version compare-and-swap, and explicitly not global `SERIALIZABLE`, which invites retry storms where per-key serialisation already gives the single-writer semantics Alchemy assumes. Backfill and `start`/`history` record which consumers exist and launch catch-up scans over events by tag and global-seq ranges feeding history-flagged deliveries, while single-source per-key catch-up reads its own aggregate's events directly; the full `Backfill.ts` replay protocol of scanner, relay and plan was only skimmed through call sites and is **UNVERIFIED** in detail.

The hardest correctness problems deserve naming because each maps to a failure that no amount of application care prevents after the fact. **Global order versus commit visibility is the hardest Postgres-specific problem**: `nextval()` assigns global positions in insert order but transactions commit in a different order, so a projector advancing a single global watermark can permanently skip a late-committing lower position, and Emmett's `(transaction_id XID8, global_position)` checkpoint exists precisely to make “has everything committed before position P been seen?” decidable. Alchemy sidesteps most of this through per-`(source,target)` ordering and per-source checkpoints, so the design must not reintroduce a global watermark except through Emmett's visibility-checked variant if a true `$all` feed is ever required. The saga exactly-once illusion follows because workflows react at-least-once and issue commands and external effects that are not transactional with the event store, so a crash between command sent and progress recorded replays the step and the only defences are idempotent commands through `commandId` receipts, idempotency keys on external calls and compensation. Deadline firing under failover requires DB `now()` rather than app clocks, absolute `due_at` computed once at schedule time and token re-check inside the fire transaction. Projection ordering requires assigning input-log position under the key's lock and never from arrival timestamps, with checkpoint-after-success plus idempotent handlers as the only correct mode when a projection writes outside Postgres. Generation rebuilds racing live traffic require compare-and-swap on generation inside the receive transaction with stale-generation deliveries dropped, because silently mixed old and new state is the worst failure mode precisely because nothing errors. The single-database assumption breaks where outbox and projector load contends with appends during rebuild scans, where per-key row locks serialise hot aggregates until partitioning by model or tenant is required, where `XID8` visibility tricks and advisory locks do not survive logical replication or Citus-style distribution, and where `LISTEN/NOTIFY` does not cross PgBouncer transaction pooling and therefore needs a dedicated connection.

## Strangling CRUD into aggregates without dual writes

Today's slice is schema-first CRUD in which the entity class is simultaneously the Effect Schema and the Drizzle table. The base tier is `EffectDrizzle.make("pg", () => ({ defaultColumns: baseColumns }))` with `createdAt`, `rowVersion` as an integer `Pg.version()` optimistic-concurrency column defaulting to 1 and `updatedAt` ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/EntityKit.ts:112-115)); the audit tier adds `createdByPrincipal` and `updatedByPrincipal`, soft-delete `deletedAt` and `deletedByPrincipal`, `schemaVersion` and `source` ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/EntityKit.ts:133-151)); the org tier adds indexed `orgId` ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/EntityKit.ts:169-170)); and the product tier adds a branded serial primary key, an `entityType` literal column and a url-safe `publicId` with a `{table}_public_id_unique_idx` unique index ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/ProductEntity.ts:1-128)). `Principal` is a tagged union of User, ServiceAccount, Agent, ConnectorAccount and System principals with Runtime, Sync, Migration, Policy and Generator components ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/Principal.ts:15-282)), and `SourceKind` is `LiteralKit(["User","Agent","Admin","Application","System","Sync","Connector"])` ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/SourceKind.ts:12-50)). The fleet is roughly 57 entity classes across 9 domain packages heavily skewed to law-practice, counted by file survey as law-practice domain 257 files and about 18 entity classes, epistemic 56 and about 10, workspace 30 and about 10, shared 108 and about 11, documents 26 and about 4, agents 16 and about 3, architecture-lab 15 and about 1, ontology 6 and 0, party 13 and 0, with the census **UNVERIFIED** as an exact count because factory-alias declarations undercount. Because the entity declaration fuses schema and table, migration is not adding events beside the table: the entity definition must split into aggregate state and events, a projection or view reproducing the old table shape, and the Drizzle table retired last, and any step that keeps `ProductEntity.Entity` as the write model blocks the strangler.

**Genesis seeding uses one `Imported` or `Genesis` event per existing row carrying the full current row payload plus legacy provenance, and never fabricates synthetic history.** Kurrent's gradual CRUD-to-event-sourcing recipe prescribes exactly “a one-time conversion event” per existing record, converting records one at a time into aggregates, projecting events into replacement tables “with the same names and structure as what it looked like before the migration started”, routing converted entities to the event store and unconverted to old tables via a repository marker, and not hesitating “to release intermediate step in production” ([Source](https://kurrentdb.kurrent.io/blog/a-recipe-for-gradually-migrating-from-crud-to-event-sourcing/)). Community import guidance agrees that each existing record imports as a genesis or initial-state event rather than invented historical events, with snapshots as rebuild optimisation rather than substitute for initial history ([Source](https://mdjnewman.me/2018/01/vetted-importing-data/), full text **UNVERIFIED**). Alchemy supports the approach structurally because a genesis-seeded stream is replayable into new views and projections without special-casing, since consumers added later receive history first ([Source](alchemy:website/src/content/docs/domain/model.mdx:154-182); [Source](alchemy:website/src/content/docs/domain/projection.mdx:1-50)), and current rows already carry the provenance a genesis event needs in `createdByPrincipal`, `source`, `schemaVersion` and soft-delete fields ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/EntityKit.ts:133-151)), with SystemPrincipal's Migration component as the genesis provenance pair ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/shared/domain/src/entity/Principal.ts:15-35)). The genesis shape per entity is therefore legacy serial id, `publicId`, `orgId`, the row snapshot of its own fields, legacy `createdAt` and `updatedAt` as data rather than event time, creator principal, `source: "Migration"`, `schemaVersion` and optional `deletedAt`, with soft-deleted rows seeded as genesis-with-deleted state so one-event-per-row parity counting stays trivial. Rows whose current state is unreachable through the new aggregate's `decide` invariants go to a quarantine list rather than a forced genesis, either through a permissive `Imported` evolve branch on an import path that writes events directly or through manual remediation before cutover, and the parity harness counts them. Synthetic history is justified only where an external audit legally requires event-level history that actually exists elsewhere, which is **UNVERIFIED** per slice and assumed absent by default. No dedicated Alchemy migration or genesis guide exists in `website/src/content/docs/domain/` beyond `backfill.mdx`, whose timings are Cloudflare-measured and must not be quoted as Postgres expectations.

Read-model parity is what makes the strangler safe, and it works because **the new projection first reproduces the old table exactly, with optimised projections only after migration**, again following Kurrent's recipe of projecting into replacement tables with the same names and structure ([Source](https://kurrentdb.kurrent.io/blog/a-recipe-for-gradually-migrating-from-crud-to-event-sourcing/)). Alchemy makes replay-diff cheap because view state is derived and always recomputable and changing `evolve`, `emit`, `keyOf`, state or sources requires a version bump where one must “Only ever increase a version. To undo a change, change the code back and bump again” ([Source](alchemy:website/src/content/docs/domain/model.mdx:154-182)), and because a Projection writes into a store you own and is replayable while never sending commands ([Source](alchemy:website/src/content/docs/domain/projection.mdx:1-50)), so the old Drizzle table itself can be the projection target during transition. The parity harness has three layers: replay-diff, in which a checker folds each stream to state, encodes through the old entity schema's table encoding and diffs field-by-field against the Drizzle row emitting `{entity, id, field, old, new}` records; shadow reads, in which the server reads the old table authoritatively while async-sampling a percentage to the new projection and logging diffs without serving them; and a cutover gate of zero diffs over a full replay plus a soak window. Byte-comparable means encoded-side comparable against Drizzle row values rather than decoded domain objects, because DateTime and bigint encodings differ otherwise, and parity must include soft-deleted rows and `orgId` scoping rather than live rows only, since deleted rows are where CRUD-to-event-sourcing migrations usually drift. Whether Alchemy's Postgres target offers the same rebuild semantics as the verified Cloudflare backfill is **UNVERIFIED**, so the spike must prove it rather than assume it.

Dual-write is forbidden by construction rather than by discipline. During transition there is exactly one writer per entity instance, the old CRUD path before genesis and the Alchemy aggregate after, because writing business change and event publish as separate commits is not atomic across systems, whereas writing the change and an outbox record in the same database transaction and relaying asynchronously keeps consumers idempotent against at-least-once duplicates while preserving ordering ([Source](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)). The strangler shape is incremental replacement behind seams with old and new coexisting under transitional architecture ([Source](https://martinfowler.com/bliki/StranglerFigApplication.html)), and Fowler gives no rollback procedure, so rollback here is designed rather than cited. The per-entity cutover sequence is branch-by-abstraction at the repository seam, genesis seeding of all rows while CRUD still writes, freeze-and-catch-up using the per-row `rowVersion` and `updatedAt` high-water marks to seed rows changed since the first pass without day-one CDC, flipping the marker so writes go to the aggregate while the projection maintains the old-shaped table invisibly to other slices, shadow-reading then flipping reads, and finally dropping the old write path so the table becomes a pure rebuildable projection. Rollback before the point of no return is flipping the seam back to CRUD and regenerating old-table rows from the projection, which is the old table, losing only event granularity for the transition window. **The point of no return is dropping the old table, deleting the genesis-import code, or letting another slice consume the event stream as its source of truth**, after which un-migrating breaks consumers. The outbox direction is the opposite of the usual expectation: legacy CRUD slices that must notify already-migrated aggregates write an outbox row in their Drizzle transaction and a relay delivers it to the aggregate as a command, never as direct event writes, because commands preserve invariants. No existing outbox or CDC infrastructure was found in the survey, which is **UNVERIFIED** as exhaustive, so a polling relay on `rowVersion` and `updatedAt` is the lower-infrastructure v1 with Postgres logical decoding as the later option.

The old kit maps onto Alchemy by converting columns into event metadata, stream mechanics and projection fields. The serial `id` survives only inside genesis and a stream-id mapping table during transition while new aggregates key on the branded EntityId value. `publicId` stays the external identity, enforced Alchemy-idiomatically by a `PublicIdClaim`-style unique-value aggregate with the projection unique index retained as belt-and-braces to catch import collisions at genesis. `createdAt` and `updatedAt` become projection-computed from the genesis payload's legacy values and then first and last event timestamps, never mutable aggregate fields, and genesis must carry legacy timestamps as data or parity fails on every row. `rowVersion` becomes stream version, with the parity rule defined per entity because multi-event commands break any naive one-to-one mapping between version bumps. Creator and updater principal, source and schema version become command and event envelope metadata persisted on each event, with the projection maintaining `updatedByPrincipal` as the last event's principal. Soft delete becomes a `Deleted` event and state variant while the projection keeps the columns so existing `WHERE deletedAt IS NULL` queries work unchanged. `orgId` tenancy becomes part of aggregate identity and keying plus view keys and `validate` rules, so tenant isolation stops being an implicit indexed-column filter and becomes an explicit authorisation decision per view. Database constraints split three ways by scope, since single-aggregate invariants belong in `decide`, cross-aggregate uniqueness belongs in a unique-value aggregate because “Making Customer check every other customer would need a transaction across all of them, which doesn't exist” ([Source](alchemy:website/src/content/docs/domain/aggregate.mdx:248-275); [Source](alchemy:website/src/content/docs/domain/unique-values.mdx:1-70)), and foreign-key or referential rules belong in projection-side checks or policy and saga coordination, consistent with the rule that cross-slice event contracts are promoted and versioned and never read directly cross-slice ([Source](/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/standards/architecture/10-cross-slice-coordination.md:22-74)). A per-entity constraint census through a `uniqueIndex`, `references` and `check(` pass is required before the first slice, and whether Alchemy events carry principal natively in the envelope or the model must add it is **UNVERIFIED** until `event.mdx` and `command.mdx` are checked against the final audit mapping.

## Local-first stops at intents, and MCP inherits the Api's discipline

**Alchemy Domain has no sync engine and no generic optimistic helper; its local-first story is honestly offline-tolerant optimistic UI over a server-authoritative event log.** The docs state plainly that “The bank example keeps its own queue and line Model. The adapter has no generic pending-state helper.” (`website/src/content/docs/domain/optimistic-updates.mdx:8`), and the four local-first levels are explicit, with only the first two working today: optimistic updates where the server decides, and offline intents where the server still decides and the queue survives reload, while a local copy of server aggregates is deferred because “Making that safe takes a sync engine… `@alchemy.run/domain` doesn't include one.” and device-decides CRDT merge “calls for a different tool.” (`website/src/content/docs/domain/local-first.mdx:6-22`). Reconciliation reduces to one key used in four places: the client allocates `commandId` as `${session}:${sent}` with a fresh session per page load through `DomainFoldkit.next(model.commandIds)`, whose returned id and next state must be stored in the Model (`packages/domain/src/Foldkit.ts:28-37`), with the warning “Do not reuse a session from cached HTML.” (`website/src/content/docs/domain/foldkit.mdx:42`); the server stamps that id into every event envelope (`packages/domain/src/Kernel.ts:1069`); the platform dedupes by it under the contract “single writer per id; dedupe by `commandId`; persist events, state, receipt and deliveries atomically; then deliver at least once, in order.” (`packages/domain/src/Platform.ts:249-251`); and the View feed echoes it so the client confirms the exact intent. Result handling is a small state machine in which success moves a line to Pending to wait for the feed, rejection is terminal showing the Rejection fields, denial from middleware is retryable after authentication, and unknown outcome becomes Queued for retry with the original id (`website/src/content/docs/domain/optimistic-updates.mdx:36-43`), classified identically in Foldkit by matching the error against `command.rejects` for rejection, middleware errors for denial and everything else including defects as Unknown (`packages/domain/src/Foldkit.ts:169-177,146-162`). Two races define correctness here. A successful reply is not confirmation, because “A successful command reply means the write committed. The line waits for the feed before it becomes confirmed.” (`website/src/content/docs/domain/optimistic-updates.mdx:6`), and a late reply must never demote a confirmed line since “The feed can arrive before the reply.” (`website/src/content/docs/domain/optimistic-updates.mdx:43`). Read-your-write without the feed uses the receipt, where `snapshot({ atLeast: receipt })` or `get(key, { atLeast: { stream, version } })` waits until the view checkpoint reaches the version and otherwise fails `ConsistencyTimeout` after ten seconds (`website/src/content/docs/domain/view.mdx:81-93`), implemented as checkpoint comparison (`packages/domain/src/Model.ts:744-772`). This gives causal read-your-write per stream and version, not linearisable reads across views, and the docs confess the general limit that confirming one bank line by `commandId` “does not prove that every effect of an arbitrary command has reached every View… Do not infer completion from a count of output events.” (`website/src/content/docs/domain/optimistic-updates.mdx:114-118`). Offline semantics are deliberately narrow: “Save unresolved intents in order… When online, send the oldest queued intent first.”, stop the batch on Unknown because “a withdrawal cannot pass an earlier deposit”, let Denied park without blocking others and let Rejected end its intent (`website/src/content/docs/domain/optimistic-updates.mdx:104-110`), persist queued and pending intents after each Model change while dropping Denied lines so reload replays the feed to confirm writes applied before the page closed (`website/src/content/docs/domain/optimistic-updates.mdx:112`), with the concrete store being `localStorage` under `bank:intents:${customerId}` (`website/src/content/docs/domain/local-first.mdx:61-62,217-225`) and no IndexedDB or SQLite client store in the pattern. Client-side prediction through `Aggregate.predict` runs the aggregate's own `decide` and `evolve` locally returning `Accepted`, `Rejected` or `Unpredictable` ([Source](packages/domain/src/Aggregate.ts:782)), and `View.evolve(state, input)` applies one input exactly as the server does ([Source](packages/domain/src/View.ts:555)), but the shipped optimistic pattern does not use prediction for state; it shows intent only and derives displayed balance as newest confirmed balance plus pending signed amounts so a later-rejected line simply stops counting (`website/src/content/docs/domain/local-first.mdx:449-461`). **Optimism is therefore an overlay on confirmed View state, never a fold of speculative state**, which is why rejection handling is trivially dropping a line and why no merge code exists anywhere. First paint ships a server `snapshot()` as `{state, cursor}` in Flags decoded defensively so a stale schema falls back to empty plus a fresh watch instead of failing boot (`website/src/content/docs/domain/foldkit.mdx:123-135`; `packages/domain/src/Foldkit.ts:465-470`), and `watch` for View state and `events` for the confirmation feed remain separate obligations because “A View can change its state without an output event, so `events` cannot replace the state watch.” (`website/src/content/docs/domain/foldkit.mdx:121`). WebSocket push requires a store with `connect` such as Cloudflare Durable Objects (`website/src/content/docs/domain/foldkit.mdx:161`), so the Postgres host's live-read behaviour is **UNVERIFIED** and v1 may serve live reads as streamed `changes` and `tail` responses without `connect`. Multi-tab behaviour over a shared intent key and `localStorage` exhaustion behaviour are likewise **UNVERIFIED**.

Prior art explains why refusing a rebase engine is the correct default for invariant-governed domains rather than a missing feature. Replicache keeps server state plus pending mutations client-side and on pull restores prior server state, applies the diff and replays pending mutations on top as a rebase where the server is authoritative ([Replicache — How it works](https://doc.replicache.dev/concepts/how-it-works)); Zero evolves that into synced queries from Postgres through a cache to client SQLite where clients cannot submit arbitrary queries and the server can add permission filters beyond the client's query ([Zero — Queries](https://zero.rocicorp.dev/docs/queries); [Zero — Auth](https://zero.rocicorp.dev/docs/auth)); LiveStore commits typed events to a log whose materializers translate each event into SQL against embedded reactive SQLite ([LiveStore](https://livestore.dev/)); and Electric is “a read-path sync engine for Postgres” whose Shapes stream filtered subsets to clients while writes go through the application's own API on a separate path ([Electric — Sync](https://electric.ax/docs/sync/)), with authorisation enforced outside the engine through an app or auth proxy ([Electric — Security guide](https://electric.ax/docs/guides/security)). Beep should copy Replicache's and Zero's confirmation discipline, in which confirmed work leaves the pending set exactly once, and Zero's rule that clients never submit arbitrary queries, which Alchemy's Views plus narrowing-only `where` already embody, and it should copy LiveStore only conceptually because event-to-materializer is already event-to-View server-side, and Electric only as shape discipline in which read surfaces are named server-owned subsets. It should not adopt a client rebase engine, a client event log or a second write path, because speculative client state is exactly what produces unreconcilable UI around balances, uniqueness and deadlines. The first slice is additive on beep's current client, whose verified pattern is `AtomRpc.Service` over `RpcClient.Protocol` with `Atom.make` and `Atom.keepAlive` workbench state and no optimistic machinery in `packages/ontology/client` (`/home/elpresidank/YeeBois/projects/beep-effect3-worktrees/alchemy-domain-adoption/packages/ontology/client/src/aggregates/Session/Session.atoms.ts:114-137,469`), so an intent queue sits beside the existing atoms without touching the RPC transport; the Effect `Atom` equivalent of Foldkit's cursor dedupe and `CaughtUp` handling must be reimplemented there and its effort is **UNVERIFIED**, as is whether other client families share the verified ontology pattern.

**MCP exposure is safe only to the extent that authorisation lives below the transport, and Alchemy inherits that property while leaving three explicit gaps.** Generation is verified in source: `toToolkit` builds tools from `operationsOf(api.serves).filter(isToolCall)` where `isToolCall = !op.stream`, and `toMcp` is `McpServer.toolkit(toolkit)` plus a handler layer (`packages/domain/src/Ai.ts:99-102,212-266,296-306`), so each tool invokes the Api's in-process client through the same RPC server and “its middleware, its `decide` and `validate` checks and its rejections work for an agent as they do for every other client.” (`website/src/content/docs/domain/mcp.mdx:6`). Tool parameters, success and failure reuse the call's own RPC schemas, non-object success is wrapped as `{ value }` because “MCP clients reject a tool whose output is not an object” (`packages/domain/src/Ai.ts:116-139`), reads are annotated Readonly and Idempotent while commands are annotated Destructive and not idempotent despite `commandId` dedupe underneath (`packages/domain/src/Ai.ts:135-137`), and rejections return as typed tool failures under `failureMode: "return"` because “A rejection is a result the model can act on, not a failed generation” (`packages/domain/src/Ai.ts:129-133,188-194`). Principal propagation is a per-call `headers` Effect defaulting to the current `HttpServerRequest` headers and otherwise no headers (`packages/domain/src/Ai.ts:48-57,168-171,244-248`), and a server-side client credential layer “still can't sign an agent in as itself” because the client half of middleware never runs for tool calls (`website/src/content/docs/domain/mcp.mdx:106-117`), which operators can still defeat with a careless `headers` option. Against the MCP specification, Alchemy's 64-character underscore tool names are stricter than the spec's 128 characters, annotations are hints clients must treat as untrusted with human-in-the-loop as a SHOULD ([MCP Tools spec](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)), and the authorisation profile requiring OAuth 2.1 resource-server behaviour, Protected Resource Metadata, audience-bound tokens and no token passthrough ([MCP Authorization spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)) is implemented by none of `Ai.ts`, which forwards headers to Api session middleware instead. The docs confess the operational limits directly: “`tools/list` shows every tool to every MCP client… Listing only the tools a caller may use needs `McpServer` to filter per request, which Effect does not do yet.”, “Nothing asks a person before a dangerous write… neither is set from the Api yet.” and `watch`/`events` are not exposed as tools (`website/src/content/docs/domain/mcp.mdx:125-131`). The prescription is architectural rather than configurational: “Every call the Api serves is a tool, so give agents their own Api with only what they may reach” (`website/src/content/docs/domain/mcp.mdx:133-145`), read tools first, command tools only behind the same Session and MFA the command declares plus an operator-provided approval step, and no server-held credential fallback. Agent idempotency needs special care because `commandId` passes through only if present (`Ai.ts:154-159`), so an LLM retrying a timed-out send without resupplying the same id can double-apply, and reusing an id for a different payload silently returns the first receipt. MCP resources, prompts and subscriptions are absent from `Ai.ts`, Effect `McpServer` conformance is **UNVERIFIED** against the spec, and MCP usage in `examples/cloudflare-domain` was not found, so MCP is library-verified but example-**UNVERIFIED**.

## Conclusion

The adoption thesis survives contact with both codebases because the library and the codebase want the same thing from opposite directions: Alchemy supplies a domain language in which invariants, reactions, security and time are declared once and enforced by a kernel, while beep's standards already demand rich schema-first models, slice-bounded coordination and proof in the real world, so the migration replaces hand-threaded tenant scope, anemic entity bags and implicit table filters with explicit `decide`, `validate` and scheduled commands. What changes understanding is that the risky artefact is not any single slice port but the Postgres Platform and its `WorkflowEngine`, since that one package must simultaneously be Emmett's compare-and-swap append, Marten's progression-tracked projection host, the Durable Objects token-timer and staged-outbox protocols and Alchemy's five-store contract, and every later slice inherits whatever it gets wrong about commit visibility, generation rebuilds and timer races. Prove that package against DocketIntake's real deadlines, real uniqueness and real confidentiality, with parity and rollback rehearsed rather than asserted, and the fleet migration becomes repetition; skip that proof and each subsequent slice reopens the same unanswered questions with more data at stake.

## Risks and sharp edges

- **No verified Postgres Platform exists upstream.** Only InMemory and Cloudflare Durable Objects hosts are shipped ([Source](packages/domain/src/Platform.ts:662); [Source](packages/cloudflare/src/Domain/index.ts:2257)), so atomic commit, live reads without `connect`, backfill cost and deploy behaviour on Postgres are all built and proven by beep, not inherited.
- **Sequence-gap watermark trap.** A projector advancing a single `global_seq` watermark can permanently skip late-committing transactions; per-source checkpoints avoid it and a global watermark must only ever return in visibility-checked form.
- **Saga exactly-once illusion.** At-least-once workflow steps re-execute after crashes between effect and progress recording; only `commandId` receipts, external idempotency keys and compensation defend against it, and no dedupe table makes external effects exactly-once.
- **Generation rebuilds racing live traffic.** A view or projection generation bump that resets state without atomic compare-and-swap against arriving deliveries silently mixes old and new state, the failure mode where nothing errors.
- **`commandId` misuse is silent.** Reusing an id for a different payload returns the first receipt, retrying with a fresh id after an unknown outcome double-applies, and agent tool calls only pass `commandId` when present (`Ai.ts:154-159`), so idempotency must be taught and enforced rather than assumed.
- **Optimistic completion is unprovable in general.** Confirming one line by `commandId` does not prove every effect reached every View (`website/src/content/docs/domain/optimistic-updates.mdx:114-118`), so UIs must confirm per View or wait through `atLeast` receipts and never infer completion from event counts.
- **MCP enumerates capabilities to everyone.** `tools/list` shows every tool to every client (`website/src/content/docs/domain/mcp.mdx:125-131`), destructive annotations are untrusted hints, and no approval, elicitation, rate-limiting, audit or OAuth 2.1 profile ships in `Ai.ts`; per-call rejection plus a least-privilege Api is the only control until that changes.
- **Any rule living only in a UI is bypassed by construction.** MCP calls and offline replay both enter below the interface, so validation, authorisation or redaction enforced only in forms or filters is unenforced for agents and queued intents alike.
- **Deadline races punish app clocks and tokenless timers.** Firing must use database time, absolute due times computed once at scheduling and token re-check inside the fire transaction, or failover and cancel races will double-fire or fire after cancellation.
- **Parity drifts where nobody looks.** Soft-deleted rows, legacy timestamps carried as event time instead of data, multi-event commands breaking `rowVersion` equivalence and org-scoping differences are the measured drift sources, and each needs an explicit per-entity rule before cutover.
- **Point-of-no-return creep.** Dropping an old table, deleting genesis-import code or letting another slice consume an event stream as truth each end rollback quietly; the cutover runbook must name the moment per entity rather than discovering it afterwards.
- **Beta drift between pin and research surface.** beep pins beta.84 while the researched surface is beta.85 dated 2026-11-02, the beta.84-to-beta.85 changelog delta is **UNVERIFIED** from docs alone, and a full live-versus-local byte diff of all 40 domain pages is **UNVERIFIED**; the pin bump must re-run `Domain.verify` and the Story suites, and ordinary failures require remediation rather than invented APIs.
- **Doc-light surfaces carry integration-test authority.** Filter, OrderBy, Key, CatchUp and Predict lack dedicated doc depth, Foldkit targets its own runtime rather than Effect `Atom`, and Effect `McpServer` conformance is **UNVERIFIED**, so source and integration tests are the contract for those seams and client-side reimplementation effort should be budgeted as real work.
