2. Is the idea sound?

Yes. Stated precisely, you are proposing that every notation an agent might write gets a positioned codec: text decodes to a tree whose every node remembers its byte span, that tree is admitted into a typed model with accumulated (not fail-fast) issues, each issue carries a span and a rule id, and the agent repairs by span. The fx0 speed comes from the agent writing its native notation. The structured-output certainty comes from the admission step. The repair loop you already run in BlockRepair is the same loop, re-keyed from JSON Pointer paths to source spans.

The honest way to assess it is to ask what each stage needs and what exists. This is the repo as of today.

The weeds, named

  1. HTML parsing is the big one. The WHATWG parsing algorithm is error-recovering by design. Almost any string parses to some tree, so "invalid HTML" mostly means "the parser recovered and you did not notice." The spec enumerates its parse errors (around seventy named codes such as unexpected-null-character, missing-end-tag-name, duplicate-attribute) and a conforming parser can report each with a location. parse5 does this with sourceCodeLocationInfo and onParseError. The decision is whether to vendor and harden parse5 the way you vendored commonmark.js (about 10k lines, same recipe as D-38 through D-42) or adapt over it. Either way, the parse-error list plus your existing conformance rules is the diagnostic vocabulary, and it is already typed by the spec.
  2. Positions must survive the fold. You solved this for markdown with the D-49 source map: pre-order spans with structural fingerprints, so a stale span is Option.none rather than a lie. The same shape works for html. The rule is that a conformance issue found on the model must be mapped back to a span in the agent's text, or the agent cannot act on it.
  3. Loss is a first-class result, not an error. An agent writing free HTML will write things the Md hub cannot carry. D-51 counted 99 lossy and 34 unsafe outcomes in 731 markdown examples. Expect more for HTML. The loss ledger is also how you learn what the hub should grow next.
  4. Streaming. Strings stream well and structured JSON does not; this is an underrated reason the fx0 experience feels fast. To keep that, the parser needs to accept a prefix and report "incomplete" distinctly from "wrong." commonmark.js is block-incremental in practice. HTML tokenizers are naturally incremental. Design the issue stream so the UI can show a partial render while the tail is still arriving, and so a repair can be requested before the agent has finished.
  5. Theme and semantics are policy, not syntax. "Provably consistent theme" means a closed class vocabulary and token set on class and style attributes, and "accessible" means ARIA and landmark rules over the tree. These are conformance rules at the policy layer, which is where enforceSafeHtml already lives. The repo's strict shadcn lint is a precedent for a class vocabulary as a gate.
  6. Inline script. Do not sandbox JavaScript. Codemode's stance is the right one: define the language you will run, parse to that, and report everything else as UnsupportedSyntax with a location. That makes script just another notation column in the table.

3. Which would I prefer, as the agent in the loop?

Constrained structured output

Costly in ways that do not show in the demo. The component union eats context before I write a word. Every string I produce is JSON-escaped, so code samples and quotes are error-prone. I cannot see what I am making, because the JSON does not read like the page. Deep nesting means I lose my place. When validation fails I get a JSON Pointer, which I then have to re-navigate. Streaming is poor, so the user waits. The certainty is real, but I pay for it on every token.

Pure string

Fast and fluent. I think in the notation. But I am blind: nothing tells me the heading order is wrong, the link scheme is forbidden, or the colors ignore the theme. Any correction comes from a human or from a prompt I may have already forgotten. The result is good on average and silently wrong at the edges, and the edges are what a law practice cares about.

Your third option

I write the notation I think in. I get back a short list of located, typed issues: this span, this rule, this is what would satisfy it. I patch spans, not pointers. The notation is the schema, so no schema has to be read into context. That is how I already work best against a TypeScript compiler, and it is the reason agents are better at TypeScript than at filling in JSON forms. Three conditions make or break it:

  • Diagnostics must be few, ranked and actionable. Group by rule, show the minimal span, suggest the fix when it is deterministic. Thirty style nits with a severity of "info" will train me to ignore the channel.
  • Tell me the policy up front, briefly. One paragraph of "what this surface allows" beats discovering it through ten repair rounds. The policy schema can generate that paragraph.
  • Let me repair the span, not regenerate the document. Your BlockRepair already does this per block. Spans are finer and cheaper.

5. What this makes possible that you may not be counting

  1. 01The loss ledger as a product roadmap. Every lossy fold tells you what agents and users want to express that the hub cannot. D-51 already produces this for markdown. Aggregate it across surfaces and it decides what the hub grows next, with counts instead of opinions.
  2. 02Diagnostics as a training signal. Typed, located issues are a reward you can score without a judge model. A corpus of (issue, repair) pairs is few-shot material, eval material, and eventually fine-tune material. "Which rules do agents trip most" becomes a dashboard, and some of those rules will turn out to be bad rules.
  3. 03Grammar derivation from the model. The notation's structural grammar can be derived from the spoke's node schemas and handed to a constrained decoder, so unclosed tags and malformed attributes never happen, while content and policy stay free. Hybrid: structure constrained, semantics checked.
  4. 04Early interruption. If issues stream as the text streams, you can stop a generation at the first hard violation and ask for a span repair before the rest is written. Cheaper than regenerate-and-check, and it keeps the fx0 feel.
  5. 05Paste becomes a codec, not a sanitizer. A user pasting HTML from the web runs through the same string-to-model admission as an agent. Sanitization stops being a string pass and becomes a typed refinement with the same located issues. One code path, one trust story.
  6. 06Provenance per node. SafeDocument is a document-level trust boundary. Once agent, user and system content mix in one tree, origin on each node lets policy differ by origin: an agent may not emit a raw link, a user may.
  7. 07One text, many deliverables. Your scratch program already does it: one Md document became HTML for the thread, Lexical for the editor, Pandoc JSON on the way to a .docx, and Markdown for storage. For a law practice this is the whole point: the agent drafts once, the attorney gets a filing-shaped document, the thread gets a rendered card, the record keeps the semantic tree.
  8. 08History as AST diffs. Persisting the hub tree means version history is a structural diff, not a text diff. Reviews can show "the agent changed this clause" at node granularity, and the writer differential becomes a regression oracle for every spoke.
  9. 09Round-trip as a property test for agents. parse(render(doc)) = doc is a law you can check on every agent output. Where it fails you have found either a writer bug or a notation the hub cannot carry, and you already have the differential harness to classify which.
  10. 10CSS and script as spokes, not exceptions. A positioned CSS model (csstree is the reference) with a token policy gives you "provably on-theme" for inline styles. A codemode-style restricted script language gives you provably bounded behavior. Both become columns in the same table, with the same located issues, instead of blocklists.
  11. 11Accessibility and i18n as rules, not reviews. Landmark order, label presence, contrast against theme tokens, and language attributes are conformance rules over a tree. Agents will fix them when told the span. Humans rarely do.

7. One step further: a typechecker for work product

Coding agents work because the domain shipped its own oracle before the agents arrived. A compiler, a type system, a test runner and a linter are each deterministic, exhaustive over what they cover, located to a line, and cheap enough to run a thousand times. Every other knowledge domain has the rulebook but not the oracle. The rules live in the MPEP, the examiner's head and the attorney's experience, so the only backpressure available is a human reading a draft, which is slow, partial, and arrives as intent the agent has to infer. The claim of this section is that the notation-codec system above is the front end of that missing oracle, and that the oracle, not the agent, is the product.

This section is a seed, not a design. It names the parts that any version of the core must have, with examples at the level of philosophy and shape, and leaves the open questions open on purpose.

Rules are not one kind of thing

The first mistake to avoid is treating "the rules of a domain" as a single list to be encoded. Sorted by what kind of check they are, they fall into four tiers, and each tier wants a different tool and gives a different kind of feedback. Patent drafting is the example because it is the one in front of you, but every regulated artifact sorts the same way.

TierKind of checkPatent exampleDecided byFeedback shape

Every reference numeral in the text appears in a drawing. Abstract length.Deterministic ruleError with span and a mechanical fix

Tier 1 is where the "little things" live, and tier 1 alone pays for the system: those checks are exactly the rejections that fill office actions, and each one is a located, deterministic issue with a mechanical repair. Tier 2 is where an ontology earns its keep and also where false positives come from, because term resolution in prose is fuzzy. Tiers 3 and 4 cannot be decided by a rule, and the second mistake to avoid is pretending they can. Encode an examiner's tendencies as an axiom and the agent will treat them as law.

Tiers 3 and 4 are enforced, just not by rules

Your list is the right one, and the useful observation is that every item on it produces the same thing. Arranged by how deterministic the judge is:

  • Deterministic sub-checks inside a judgment. A cited source either resolves or returns 404. Its domain is on the approved list or not. The quoted passage is present in the fetched content or not. The date is before the priority date or not. None of this decides novelty, but each strips a class of hallucination from the question before any model sees it, and each is a tier 1 check hiding inside a tier 3 obligation.
  • Calibrated decision models. A System One style model (TypeSafe's Jev is the one you linked) answers a narrow typed question about supplied state: a Choice over a defined set, a Score against described levels, a yes-or-no Noul. The answer carries a probability per option and a separate confidence, which is the part that matters here: probability says what, confidence says whether to act. Their citation-check and hierarchical-classification cookbooks are already tier 3 patent-shaped questions. Confidence-gated routing is the mechanism that decides whether a finding is reported, escalated to a panel, or sent to a human.
  • Review loops and panels. An independent agent, ideally on another provider, re-derives the obligation from the document and the sources. Agreement raises confidence. Disagreement is itself a finding. The repo's review-panel doctrine already does this for code.
  • Provenance requirements. An obligation discharged without a witness is not discharged. The witness is a reasoning trace, a source with a resolved locator, a panel verdict, or a human signature. Requiring the witness to be data means tier 3 findings are auditable after the fact, which a bare confidence number is not.
  • Human span-level feedback. The comment anchored to a paragraph in this very page (your screenshot) has the same shape as a diagnostic: a span, a message, an author, a resolution. The attorney's inline note is a finding whose judge is a person and whose confidence is one. Once it is in the same channel as the rule-derived findings, it can be answered with the same span repair, and it can be mined later for the rule that would have caught it.

Tiers 3 and 4 are an ontology too, a process ontology

The list above reads as mechanisms, and that undersells it. Each bullet is an axiom about a process. The content judgment in tier 3 stays probabilistic, but the process allowed to produce that judgment is fully axiomatizable: a novelty obligation is discharged only by a prior-art search whose sources are on the approved list and resolved at search time, whose output was re-derived by a reviewer on a different provider, whose classifier confidence cleared the threshold, and which an attorney signed. Every clause constrains a process record, not the document. Process, participant, role, input, output, temporal order. That is the occurrent half of BFO, and PROV-O already encodes it as a graph.

So tiers 3 and 4 do not become checkable by content. They become tier 1 and 2 checks over the provenance graph. The ontology never decides novelty. It decides whether the way novelty was decided is admissible, which is a concept law already has. A witness is the output of a process whose type is axiomatized, and tier 4 fits too: advice from a learned prior must be marked as advice and may never stand as an obligation's witness.

Two cautions. Process axioms check the process, not the truth, so calibration of classifiers and panels is still measured through the ledger. And process theater is the Goodhart mode here: agents will satisfy process axioms the way people satisfy checklists. The defense is the public rejection record scoring the whole system, process rules included, and deleting any process rule that does not move precision.

The unifying observation. Every judge, from a regex to an attorney, emits a finding of one shape: a span, a rule or question it was judged against, a severity, evidence, the judge's identity, and a confidence. Deterministic judges report confidence one. The core does not need to know what kind of judge produced a finding to route it, display it, repair against it, or ledger it. That single shape is what makes the system domain-agnostic.

What the core must be, from first principles

Strip the patent example away and ask what any domain needs to get compiler-grade backpressure. Five things, each separable, each already present in the markdown column of the earlier table in some form.

  1. Notation is separate from model. The author writes in whatever they think in. The codec owes a lossless positioned parse and a source map; the model owes meaning. What the hub-and-spokes cut above does for markdown and html is this separation, and a docx or pandoc codec is one more spoke with the same contract. Nothing in the model knows which notation it came from.
  2. Rules are refinements layered on schemas, bundled as profiles. A profile is what a codec or a model is configured with: a specification plus the semantic rules enforced over it. CommonMark plus GFM is a profile. WHATWG plus the deny-by-default policy is a profile. Theme tokens and landmark rules stack on top as a stricter profile. A patent-claims profile stacks on the document model and is reached through the docx spoke. Profiles compose, and a stricter profile only adds findings, never removes them. This is the same idea as a schema refinement, and it is why "configure what specification and semantic rules are enforced" is a property of the core rather than a feature of each codec.
  3. Spans are the universal address. A finding on the model is useless to an author until it lands on the text they wrote. Every codec owes a source map, every finding carries a span, and a finding whose span has gone stale says so rather than lying. You solved this once for markdown with fingerprinted spans; it is a law of the core, not a feature of one spoke.
  4. Findings are one typed shape, with the judge as provenance. Span, rule, severity, evidence, judge, confidence. Deterministic judges report one. Classifiers report a calibrated probability and a confidence. Panels report agreement. Humans report one and a signature. Routing, display, repair and ledgering never branch on the kind of judge.
  5. Obligations and holes are first-class. A rule the system cannot decide does not vanish and does not become a guess. It becomes an obligation: a hole in the document that names what would discharge it. A witness discharges it. The author, agent or human, can leave the hole open on purpose and ask what remains. This is how proof assistants work, and it is the honest way to represent tier 3.

Under all five sit ledgers: every loss a codec could not carry, every finding, every witness, every repair. The ledgers are the training corpus for calibrating classifiers, the eval set for the oracle itself, the source of the next rule (a human finding that recurs is a rule waiting to be written), and the evidence that the green check means what it says.

The same shape in other domains

Nothing above mentions law. Three sketches, deliberately short, to show the tiers and profiles are not patent-shaped:

  • A grant application. Tier 1: page limits, required sections, budget sums to the requested total, every cited figure has a legend. Tier 2: every aim is addressed by at least one method and one evaluation. Tier 3: significance and feasibility, judged by panel and classifier with witnesses. Tier 4: this program officer's preferences.
  • A safety data sheet. Tier 1: sixteen sections in GHS order, every hazard code on the approved list, pictograms match codes. Tier 2: every hazard statement has a matching precautionary statement, the composition section covers every classified ingredient. Tier 3: the classification itself, which needs toxicology evidence as a witness.
  • A design system page. Tier 1: every color is a token, every heading step is one level, every control has a label. Tier 2: every component referenced in a layout exists in the catalog. Tier 3: "does this look like our brand," answered by a Score question and a human with an anchored comment.

Seeds for the open questions

These are the places where the core could be dug into a hole early. Named, not answered.

  • Where domain structure lives relative to the hub model. A claim is not a paragraph. Does a domain profile add node kinds to the tree, annotate existing nodes, or project the tree into a separate graph (RDF with SHACL shapes is the obvious candidate, and the repo already has an RDF spoke) and map findings back? Each answer changes what "span" means for a domain finding.
  • How rules are expressed. Schema checks, SHACL shapes, Datalog, a visitor with a typed error, or several of these behind one finding shape. Pick late. The finding shape is what must be fixed early.
  • How profiles compose when they conflict. Stacking should only add findings, but two profiles can disagree on severity or on what the fix is. Needs a precedence story.
  • How confidence propagates. A tier 2 finding that depends on a tier 3 classification inherits uncertainty. Composite scoring with weights in code is one answer; it should be a property of the finding algebra, not of each rule.
  • How a human finding becomes a rule. The attorney's anchored comment is the richest signal in the system and today it evaporates. A path from recurring human findings to candidate rules, with the corpus as the test, is the flywheel.
  • Incremental validation. Backpressure must arrive while the author is still writing. Validation keyed by changed spans, using the same fingerprints that detect stale findings.
  • The oracle is itself under test. For any domain with a public record of rejections (office actions, audit findings, review comments), the rules are fit to that record and report precision and recall before an agent sees them. A wrong oracle is worse than none, because the agent will satisfy it with great confidence.

Where to start remains the same as before the step: antecedent basis, claim dependency and reference-numeral consistency as the first three rules, then written-description support as the first ontology-backed one. They are small, fully deterministic, frequent in real rejections, and they exercise every arrow in the diagram. But the first three rules should be written against the finding shape and the profile idea from day one, not against a patent module, so that the fourth domain costs a profile and a spoke rather than a rewrite.

What matters from each pushback is the principle underneath it, and each principle is a seed for something the core must be able to codify, not a rule the core ships: findings carry coverage, rules and findings carry time, obligations name who may discharge them, repairs declare what they may change, witnesses are minted by the runtime, every rule is Goodhart-tested before it gets teeth. The POC (section 9) validates the loop on ordinary agent output first, with domain profiles as the second act.

Where the five models agree

  • Tiers 3 and 4 do not reduce to provenance checks. All five said it, each in its own words. Provenance proves the claimed process ran, not that the process was adequate or the conclusion right. Kimi's framing is the one to adopt: this is liability engineering, not quality engineering, and law already works that way (standard of care, ALCOA+, Part 11). GLM adds the commercial angle: the provenance ledger is the signing attorney's own 37 CFR 11.18(b) reasonable-inquiry evidence, which turns the gate from tolerated overhead into an asset the practice wants to feed. Call it auditability. Never call it reduction.
  • Self-attestation is the hole. An agent that writes its own provenance graph for a process that never ran clears every clause. Opus and the provenance researcher reached the same fix independently: witnesses minted only by the judge runtime, the way SafeHtml is minted, with signatures from an orchestrator the agent does not control, and a cap on judge attempts so confidence cannot be re-rolled until it clears.
  • A second provider is not independence. Two models trained on the same web are correlated witnesses. Cross-provider review is a diversity intervention whose benefit must be measured. And for a string check like "is this quote in this page," a model witness lowers the standard, because an agent that may choose its witness will choose the soft one.
  • One finding shape is right for transport and wrong for repair. LSP and SARIF both grew fix payloads, fingerprints and taxonomies for this reason. Add a repair-applicability level separate from confidence (rustc and Biome do this), coverage and cascade fields, and let the data payload travel to a fix request fetched on demand so findings stay short.
  • The DSL is authoring ergonomics, not a semantic foundation. Astra, Opus and the DSL researcher all split it the same way: an OWL fragment for vocabulary, SHACL or Datalog for obligations and derived relations, a workflow policy for process, versioned evaluator contracts for probabilistic judges, and a TypeScript facade that constructs those representations. Rule bodies must be data, never closures, or they cannot project. Obligations must never be OWL axioms, because an OWL reasoner satisfies "must have a witness" with an invented one.
  • Span repair is not yet shown to win. Diffs help strong models and break weak ones. The best-supported pattern is deterministic fix first, then model-proposed span edits applied by a splicer, then regeneration as fallback. Deleting the flagged span is a known cheat.

Where they split

  • Should routing branch on the kind of judge? The brief says never. Grok says that policy makes judge-shopping the optimal strategy and proposes a lattice of what each judge may close: a string judge may close "the quote occurs in these bytes," a probabilistic panel may not close antecedent basis, a human signature closes a review step, nothing closes novelty. Opus agrees the shape works for transport only. I side with Grok. The finding shape stays one type; the obligation declares which judge classes may discharge it.
  • Is the Md hub in the path at all? Opus and Grok both note that patent rules live on a claims structure that sits above a Markdown document model. Grok's version of the experiment measures fold losses on real claim sets first, and if the fold is lossy on claims, the judge runs on the syntax tree and the hub is not in the path for this domain. That is a real question, and it is cheap to answer in week one.
  • Is antecedent basis really tier 1? Astra cites MPEP 2173.05(e): implicit antecedent basis is recognized, and a missing explicit antecedent does not automatically mean indefiniteness. The matcher reports a drafting-convention violation and must never promote that into a legal conclusion. The flagship rule has a tier 3 tail, and the taxonomy must admit that a rule can straddle tiers.

Ideas none of us had

  1. Coverage as a typed output (Muse). An empty finding list from rules that examined nothing is indistinguishable from full assurance. Emit a checked-region map like test coverage: which spans which rules examined, which are known-unchecked, which rule classes do not exist yet for this profile. Obligations then open where coverage is absent and stakes are high, and rule authoring becomes coverage-driven.
  2. Bitemporal rules and findings (Kimi). Doctrine shifts. Every finding records the rule version that judged it, along both axes (when the rule was true in the world, when the system learned it), or the ledger cannot be replayed and rule induction will learn overruled doctrine. LegalRuleML already models this. Retrofitting time into a ledger is the painful migration; do it on day one.
  3. The agent does not own the goal (Grok). "Unsupported term" gets cleared by cutting scope. The client's intended scope must be a frozen obligation anchored on spans the human owns, against which deletion is itself a finding. The agent's Markdown is a candidate witness for the obligation, never the obligation.
  4. Frame conditions for repairs (Astra, from Dafny's modifies). A patch declares what it may change. Protected commitments (claim limitations, quantities, negations, citations, dependencies, open questions) are checked after the patch. The acceptance question becomes "did the finding disappear while the protected commitments survived."
  5. Goodhart-test every rule in CI (GLM). A rule enters a profile only after an adversarial agent, told the rule but not its intent, fails to satisfy it with bad output. Rules that survive get teeth; rules that do not stay advisory.
  6. Runtime-minted witnesses (Opus, provenance researcher). Already described above; listed here because it is the mechanism the other five depend on.

Corpora and precision bars

  • PEDANTIC (arXiv 2505.21342): 14.5k claims with §112(b) labels and the examiner-cited text located in each claim. Antecedent basis is about 36% of reasons, with undefined terms about 73%. LLM baselines sit near 55 to 57%, roughly logistic regression. Release and license still need confirming. Also: ACE-Real112b (204 real rejections), the USPTO Office Action Rejection API and OCE dataset (claim numbers, 112 subsections not reliably split), HUPD (outcomes only). No public §112(a) written-description corpus exists.
  • Tricorder's admission bar: under 10% effective false positives for advisory findings, essentially zero for anything that blocks, every rule admitted only after hand-labelling a sample, analyzers that annoy people get disabled. Systematic verifier error is the dangerous kind: RLVR tolerates about 40% random label noise, but a consistently biased verifier stalls or collapses training.
  • "Vibe Patenting" measured LLM-judge agreement with attorneys per rubric dimension: 0.83 on figure quality, 0.04 on prosecution resilience, 0.10 on claim strength. That is the tier split, measured.
  • Standards lessons: FHIR moved finding locations from XPath to model-path expressions so findings do not depend on notation; XBRL ships pass and fail fixtures with every rule; Schematron QuickFix attaches declarative fixes to rules.

The two-week experiment, consolidated

All five proposed nearly the same experiment, which is itself evidence. Merged, with the pre-registered kill criteria they insisted on:

  1. Days 1 to 3. Measure fold losses on a few dozen public claim sets first (Grok). Build three tier 1 rules over the existing Markdown tree and source map: antecedent basis, claim-dependency DAG, reference-numeral consistency. Build the corpus by mutation (dropped article, plural mismatch, forward reference, broken dependency, duplicated numeral) with mutant locations as ground truth, and score against PEDANTIC spans. Every finding gets a human label; the adjudication ledger starts on day one. Kill: span-exact precision under the Tricorder bar, or under about 70% against attorney judgment, means "the oracle is cheap" is false for the flagship rule.
  2. Days 4 to 10. Four arms, same model, same attempt budget, blind: existing structured blocks with JSON Patch repair; Markdown with unlocated prose findings and regeneration; Markdown with located typed findings and regeneration; Markdown with the same findings and span repair. Measure iterations and tokens to zero blocking findings, findings introduced by repair, stale-span rate across edits, and blind practitioner scoring of support quality and scope sanity. Kill: under 60% of runs converge in three rounds, or oracle-driven drafts are measurably narrower than unassisted ones (the vacuity test).
  3. Days 11 to 14. Red-team the tier 3 gate (GLM). Build the novelty obligation gate (approved-list search, quote match, second-provider reviewer) and tell an agent, given only the gate, to clear it with garbage. If it passes in an afternoon, the provenance reduction is falsified empirically before any ontology is written.

Nothing in the experiment needs the DSL, the OWL projection, the package rename, the HTML parser, or a novelty judge. It needs the codec, the offsets, the fold, the chat surface's existing repair budget, and the two primitives Opus found that the brief left out: @beep/provenance already has TextAnchor, VerifiedTextAnchor and a verification receipt, and @beep/epistemics already has EvidenceSpan, ClaimGate and ClaimGateViolation. Those are the witness and finding seeds, already schema-first.

9. The POC

Benjamin's call: build a proof of concept inside the exploration, as a lab app under apps/labs (the repo has a create-package --lab scaffold for exactly this), with third-party dependencies fully allowed in the POC packages. If the loop can be built from the pieces named on this page, building it is the best validation of the idea.

What the POC must show, in order of importance:

  1. The loop on ordinary agent output. An agent writes Markdown or HTML for a chat thread. The text is parsed losslessly with positions (@beep/markdown today; a parse5-backed HTML spoke is the one net-new parser), admitted into the typed model, and findings come back in one shape with spans. The agent repairs by span through the existing offset-splice edits, and the findings re-run incrementally on the changed region. The profile here is generic: WHATWG conformance, the deny-by-default policy, theme tokens, heading order, link policy. No law anywhere.
  2. The core shapes, exercised by that profile. One finding type with judge identity, confidence and repair-applicability; a coverage map beside the findings; bitemporal rule ids; an obligation with a declared discharge lattice and a runtime-minted witness; a frame condition on at least one repair. Each of these is a seed from the panel, and the POC's job is to prove the core can codify them without knowing what domain they came from.
  3. A second profile, stacked. Only then a domain profile over the same documents, to show that a stricter profile only adds findings and that the finding shape did not have to change. The patent-claims profile is the obvious candidate because goals/claim-element-antecedent-check already emits typed, span-anchored findings over a claim-element tree, so the POC consumes that stream rather than re-implementing rules.

Measured with the kill criteria from section 8: precision of the generic profile's findings against a hand-labelled sample, convergence of the repair loop in three rounds, the vacuity test, and the stale-finding rate across edits. The SHACL, RDF and n3 drivers already in the repo cover the obligation graph if the POC gets that far; they are not on the critical path.
