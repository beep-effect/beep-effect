## Which systems give located diagnostics plus machine-applicable fixes, and what is the data shape of a finding?

### Takeaway
"Located, typed, fixable finding" is a mature, convergent shape: every serious linter and LSP uses {range, message, code/ruleId, severity, source, data} plus a separately classified fix as non-overlapping text edits, and they all split "safe to auto-apply" from "suggestion needing judgment" (ESLint fix/suggest, Biome safe/unsafe, rustc Applicability, html-validate fix/suggestions, LSP isPreferred/quickfix). The brief's single finding shape (span, rule, severity, evidence, judge, confidence) matches this core but lacks an explicit applicability/safety tier on the fix, which every one of these systems found necessary.

### Cited Findings
- **LSP 3.17 Diagnostic**: required `range` and `message`; optional `severity` (Error=1, Warning=2, Information=3, Hint=4; missing means Error), `code` (int or string), `codeDescription.href`, `source`, `tags` (Unnecessary, Deprecated), `relatedInformation[]` ({location, message}), and `data` (LSPAny), which is "preserved between `textDocument/publishDiagnostics` and `textDocument/codeAction`" — [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- **LSP positions**: zero-based line plus character offset whose unit is negotiated (`utf-8`, `utf-16`, `utf-32`); UTF-16 is mandatory and the default; Range end is exclusive — [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- **LSP edits**: `TextEdit {range, newText}`; `AnnotatedTextEdit` adds `annotationId` pointing at a `ChangeAnnotation {label, needsConfirmation?, description?}`; "Text edits ranges must never overlap"; `TextDocumentEdit` uses `OptionalVersionedTextDocumentIdentifier` "to allow clients to check the text document version before an edit is applied" — [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- **LSP pull diagnostics**: `textDocument/diagnostic` returns `full` reports (with optional `resultId`) or `unchanged` reports (required `resultId`); `relatedDocuments` carries diagnostics another file caused; workspace reports carry `version`, and "higher document versions win over lower ones" — [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- **LSP CodeAction** (fields `title`, `kind`, `diagnostics`, `isPreferred`, `disabled {reason}`, `edit`, `command`, `data`; kinds `quickfix`, `refactor.*`, `source.organizeImports`, `source.fixAll`; lazy `codeAction/resolve`). **[memory, not re-verified]**: the fetches of the spec did not reach that section — [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- **ESLint**: `context.report({ node | loc, messageId | message, data, fix, suggest })`; fixes are range edits over a two-item `[start, end)` character range (`replaceTextRange`, `insertTextAfterRange`, `removeRange`, ...); fixes returned together must not overlap; when fixes conflict "only one is applied"; up to 10 multipass fix rounds; rules must declare `meta.fixable` ("code"/"whitespace") or `meta.hasSuggestions`; suggestions cover cases where a fix might change behavior or several valid fixes exist, and are never auto-applied — [ESLint custom rules](https://eslint.org/docs/latest/extend/custom-rules)
- **Biome**: diagnostic = category (e.g. `lint/a11y/noAccessKey`), severity (Fatal/Error/Warning/Information), optional location (path, source, range), tags (Verbose, Internal, Fixable, Deprecated), and advices (messages, lists, diffs, code frames) — [Biome diagnostics](https://biomejs.dev/reference/diagnostics/). Safe fixes "are guaranteed not to change your code's semantics" (`--write`, `source.fixAll.biome` on save); unsafe fixes need `--write --unsafe`; per-rule `fix: none | safe | unsafe` lets users reclassify — [Biome linter](https://biomejs.dev/linter/)
- **rustc**: diagnostic = level, optional code (E0308), message that "should stand on its own", primary span plus labeled secondary spans, children (note/help); suggestions carry `Applicability` = `MachineApplicable` | `HasPlaceholders` | `MaybeIncorrect` | `Unspecified`; `--error-format json` emits `message, code, level, spans, children, rendered` per line, consumed by `cargo fix` — [rustc dev guide: diagnostics](https://rustc-dev-guide.rust-lang.org/diagnostics.html)
- **html-validate**: `this.report({ node, message, location?, context?, related?, fix?, suggestions? })`; location `{filename, line, column, offset, size}`; `documentation(context)` returns `{description, url}` specialized by the reported context; fixable rules declare `static fixable = true`; "Suggestions are never applied automatically" — [html-validate writing rules](https://html-validate.org/dev/writing-rules.html)
- **markdownlint** `onError({ lineNumber, detail?, context?, information?, range?: [column, length], fixInfo?: { lineNumber?, editColumn?, deleteCount? (-1 = whole line), insertText? } })`; rules choose parser `micromark` (recommended), `markdownit` (legacy) or `none` — [markdownlint custom rules](https://github.com/DavidAnson/markdownlint/blob/main/doc/CustomRules.md)
- **vfile-message** (unified/remark): `reason` (markdown), `place` (point or position), `line`, `column`, `ruleId`, `source`, `fatal` (true = "file not usable", false = warning, undefined = info), `ancestors`, `cause`, plus `actual` and `expected[]` ("acceptable values that can be used instead of `actual`"), `url`, `note`. No edit/fix object — [vfile-message](https://github.com/vfile/vfile-message)
- **Nu HTML Checker JSON**: `type` (`info` | `error` | `non-document-error`), `subType` (`warning`, `fatal`, `io`, `schema`, `internal`), plain-text `message`, `extract`, one-based `firstLine/lastLine/firstColumn/lastColumn` (UTF-16, inclusive end, described as "approximate"), `url`. `fatal` means well-formedness error after which "Further errors are suppressed." No fixes — [validator wiki: JSON output](https://github.com/validator/validator/wiki/Output-%C2%BB-JSON)
- **Markdoc**: `validate(ast, config)` returns `ValidateError[]` = `{ type, lines, location {start,end}, error { id, level, message } }` (e.g. `missing-closing`, level `critical`); tag/node schemas and custom attribute types contribute `validate` functions — [Markdoc validation](https://markdoc.dev/docs/validation)
- **Vale**: JSON alerts with `Check`, `Line`, `Span`, `Severity`, `Message`, `Link`, `Match`, and an `Action {Name: suggest|replace|remove|edit, Params}` hint used by editor integrations. **[memory, not re-verified]**

### Inferences
- The convergent finding shape is: stable rule id with docs URL; severity enum; primary span plus related spans; human message; opaque `data` round-tripped to the fix provider; zero or more fixes, each a set of non-overlapping text edits, each with an applicability class. The brief's shape adds `judge identity` and `confidence`, which none of these have (they are all deterministic, so confidence is implicitly 1). That is the novel part, not the span/rule/severity part.
- Every system distinguishes "safe to auto-apply" from "needs judgment", and two (Biome, rustc) make it a typed enum. The brief should add an applicability field on the repair, separate from finding severity and judge confidence; otherwise "confidence" will be overloaded to mean both "is this finding true" and "is this fix safe".
- LSP's `data` round-trip and lazy `codeAction/resolve` are a direct answer to the brief's context-cost worry: findings stay short, and the expensive repair payload is fetched only for the finding the agent acts on.
- The `vfile-message` `actual`/`expected[]` pair is the cheapest useful fix shape for agents (replace this token with one of these), and it maps well to tier-1 cases like antecedent basis ("the member" -> expected `a member`).
- Fix-conflict policy matters: ESLint drops conflicting fixes silently and multipasses up to 10 times. An agent-repair loop needs an explicit rule (reject overlap, rebase, or re-run) rather than inheriting "one wins at random".
- rustc's `rendered` field (structured plus human rendering in one record) is a good model for findings that both agents and attorneys read.

### Gaps
- I did not confirm the CodeAction section text of LSP 3.17 or any 3.18 additions in this session.
- I found no linter whose finding shape carries a judge identity or calibrated confidence; if one exists (e.g. in AI code review products) it was out of scope here.

## Has anyone formalized "lossy fold with a loss ledger" between a CST and a semantic AST (and a source map back)?

### Takeaway
The pieces exist separately: lossless CSTs (Roslyn, rowan, Oil's LST), CST-to-semantic-tree projections that carry positions forward (mdast-util-to-hast, Pandoc with `sourcepos`), loss warnings as untyped log messages (Pandoc), and a formal theory of lossy bidirectional transforms (symmetric lenses, quotient lenses, constant-complement lenses). I found no system that combines a positioned lossless tree, a fold into a separate persisted semantic model, a typed enumerated loss ledger, and a source map that detects stale spans. The brief's `@beep/markdown` -> `@beep/md` fold appears novel as a combination; the closest single precedents are Pandoc (hub-and-spokes, lossy, warnings) and unified (positions propagated across tree projections).

### Cited Findings
- **Roslyn red/green trees**: the green tree is immutable, shared, and an implementation detail; the red tree is "an immutable façade that is built around the green tree", built top-down on demand and discarded on each edit — [Eric Lippert, Red-green trees](https://ericlippert.com/2012/06/08/red-green-trees/)
- **rust-analyzer / rowan**: syntax trees are "lossless, or full fidelity. All comments and whitespace get preserved"; Roslyn attaches leading/trailing trivia to non-trivia tokens; "red-green terminology comes from Roslyn and gives the name to the `rowan` library" — [rust-analyzer syntax.md (mirror)](https://git.dreamy.place/mirrors/rust/plain/src/tools/rust-analyzer/docs/dev/syntax.md?h=1.65.0); rowan describes itself as a library for lossless syntax trees "inspired in part by Swift's libsyntax" — [rowan](https://github.com/rust-analyzer/rowan). `cstree` is a rowan derivative — [cstree](https://docs.rs/crate/cstree/0.8.1)
- **Oil shell "Lossless Syntax Tree"**: an ordered ASDL tree plus an array of line spans whose concatenation reproduces the source byte-for-byte; the "lossless invariant" is checked by `test/lossless.sh`; motivated by translating shell to Oil while keeping style — [oilshell blog 2017-02-11](https://oilshell.org/blog/2017/02/11.html); [discuss.python.org: Lossless Syntax Trees](https://discuss.python.org/t/lossless-syntax-trees/520.md); [syntax.asdl](https://oilshell.org/release/0.23.0/pub/src-tree.wwz/frontend/syntax.asdl.html)
- **unist positions**: `Position {start, end}` of `Point {line (1-based), column (1-based), offset (0-based, UTF-16 units)}`; "The `position` field must not be present if a node is generated" — positionlessness is the marker for synthesized nodes — [unist spec](https://github.com/syntax-tree/unist)
- **mdast-util-to-hast** (mdast -> hast projection): exposes a `patch(from, to)` helper (copies position), default handling turns unknown nodes into text or `<div>`, raw `html` nodes are dropped unless `allowDangerousHtml`, `data.hName/hProperties` can produce XSS; the README mentions no reporting of dropped content — [mdast-util-to-hast](https://github.com/syntax-tree/mdast-util-to-hast)
- **remark-stringify**: serialization is best effort; "there are several cases where that is impossible" to match the tree, so round-tripping is not guaranteed — [remark-stringify](https://npmjs.com/package/remark-stringify)
- **parse5** `sourceCodeLocationInfo`: every non-root node gets `sourceCodeLocation`; elements created by tree correction get `undefined` location (an implicit "not from source" marker); `onParseError` callback for WHATWG parse errors — [parse5 ParserOptions](https://parse5.js.org/interfaces/parse5.ParserOptions.html)
- **Pandoc**: states that "conversions from formats more expressive than pandoc's Markdown can be expected to be lossy"; warnings via `--verbose`, `--fail-if-warnings` (exit 3), and `--log=FILE` writes "log messages in machine-readable JSON format" — [Pandoc manual](https://pandoc.org/MANUAL.html). The `sourcepos` extension on the commonmark/gfm readers emits `data-pos` attributes **[memory, not re-verified]**.
- **Lenses**: quotient lenses are "well-behaved modulo specified equivalences" chosen by the programmer and tracked in the type, a refinement of Boomerang — [Quotient Lenses (Foster, Pilkiewicz, Pierce, ICFP 2008)](https://repository.upenn.edu/cis_papers/390). A later synthesis distinguishes bijective lenses, symmetric lenses ("permit losing information when going from one format to another") and quotient lenses — [arXiv 1903.03671](https://arxiv.org/pdf/1903.03671)
- **Markdoc** keeps a typed schema over a markdown superset and validates against it, but projects to a render tree, not a persisted semantic model, and reports no losses — [Markdoc validation](https://markdoc.dev/docs/validation)

### Inferences
- Formal framing worth adopting: the fold is the `get` of an asymmetric lens from CST to `Md.Document`; the loss ledger is a *typed description of the complement* (what `put` would need to restore). Constant-complement / symmetric-lens theory says when an edit to the hub can be pushed back to the source without clobbering lost material. Offset splicing is effectively `put` with the original source as complement, which is why it preserves untouched bytes. This is a precise way to state the brief's claim and to test it (lens laws as property tests: GetPut over the lossless subset, PutGet modulo the quotient of author spellings).
- unist's "generated nodes have no position" rule and parse5's `undefined` location for tree-corrected elements are the same idea as the brief's `Option.none` source-map entries, applied at construction time rather than at staleness time. Both should be in the source map: none-because-synthesized vs none-because-stale are different findings.
- Pandoc is the nearest system to the hub-and-spokes thesis (one semantic AST, many readers/writers) and its main known weakness is exactly what the brief adds: losses are free-text log lines, not typed rows, and positions are opt-in per reader. That is a strong "adjacent but not the same" citation.
- unified/mdast-util-to-hast shows the cost of not having a ledger: unknown nodes silently become `<div>` or text, and raw HTML silently disappears unless a flag is set. That is a concrete failure the 20-reason loss enum prevents.
- Roslyn shows that "typed model" and "lossless tree" can be the same object (typed red-node façade over lossless green tree). The brief separates them into two packages and a fold. That is defensible (the hub must be notation-free and persisted), but it means positions live only in the source map, never in the hub; findings computed on the hub must go through the map, which is where staleness bugs will concentrate.

### Gaps
- I found no published system with an enumerated, typed loss ledger for a document format conversion. Candidates I could not check: MyST (myst-spec / mystmd) transformations, Quarto, djot (jgm), Typst's importers, docx converters such as mammoth.js (which does emit conversion "messages" for unrecognized styles **[memory, not re-verified]**). Worth a targeted search before claiming novelty publicly.
- I did not find the remark maintainers' longer statements on lossless serialization; only the best-effort disclaimer.

## What is the state of the art for keeping positions valid under edits (rope/CRDT position mapping, incremental parsing, stale-span detection)?

### Takeaway
Two mature mechanisms: (1) map positions through an edit description with explicit deletion tracking (CodeMirror `mapPos` with `MapMode.TrackDel` returns `null`, ProseMirror `MapResult.deleted`, LSP versioned edits, Yjs relative positions), and (2) incremental reparse from a recorded edit (tree-sitter `ts_tree_edit` + reparse with structure sharing; Roslyn red trees rebuilt per edit). The brief's fingerprinted spans returning `Option.none` is a content-hash variant of (1); the prior art suggests also keeping an edit-mapping path so spans survive unrelated edits instead of going stale.

### Cited Findings
- **CodeMirror 6** `ChangeDesc.mapPos(pos, assoc, mode)`: `MapMode.Simple` always returns a position; `TrackDel` returns null "if deletion happens across the position"; `TrackBefore`/`TrackAfter` return null if the adjacent character is deleted; `ChangeSet.compose` and `map` (rebase) satisfy `A.compose(B.map(A)) == B.compose(A.map(B, true))`, the basis for OT-style collaboration — [CodeMirror reference](https://codemirror.net/docs/ref/#state.ChangeDesc.mapPos)
- **ProseMirror** maps selections and decorations through a `Mapping`; inline decorations have `inclusiveStart`/`inclusiveEnd` controlling boundary behavior — [ProseMirror reference](https://prosemirror.net/docs/ref/#transform.Mapping). `MapResult` exposes `deleted`, `deletedBefore`, `deletedAfter`, `deletedAcross` **[memory, not re-verified; the fetched portion did not reach that section]**
- **tree-sitter**: `ts_tree_edit` with `TSInputEdit {start_byte, old_end_byte, new_end_byte, start_point, old_end_point, new_end_point}` "adjusts the ranges of its nodes so that they stay in sync"; reparse with the old tree and the new tree "internally shares structure with the old tree"; `ts_node_edit` updates retained node handles — [tree-sitter advanced parsing](https://tree-sitter.github.io/tree-sitter/using-parsers/3-advanced-parsing.html). `ts_tree_get_changed_ranges` and `ERROR`/`MISSING` recovery nodes **[memory, not re-verified]**
- **LSP** version numbers on `TextDocumentEdit` let a client refuse an edit computed against an older document; workspace diagnostic reports carry `version` and higher versions win — [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- **Roslyn** red trees are thrown away and rebuilt on every edit while green nodes are reused — [Lippert](https://ericlippert.com/2012/06/08/red-green-trees/)
- Yjs `RelativePosition` / Automerge cursors anchor positions to CRDT item ids so they survive concurrent edits; Wagner & Graham (1998) "Efficient and flexible incremental parsing" is the classic algorithm behind tree-sitter-style incremental LR parsing **[memory, not re-verified]**

### Inferences
- Three distinct staleness policies exist and the brief should name which it uses per finding: (a) version-pinned (LSP: reject if doc version changed), (b) mapped (CodeMirror/ProseMirror: carry the span through edits, null only if its content was deleted), (c) fingerprinted (the brief: re-check a content hash, none if mismatched). (c) is the most conservative; (b) avoids invalidating every finding after each agent repair. A combined approach — map through the splice log, then verify fingerprint — gives both survival and safety.
- For an agent repair loop, the edit log is already available (the agent's own splices), so CodeMirror-style mapping is cheap: after applying fix k, map the spans of findings k+1..n instead of re-validating everything. This directly addresses brief risk "validation must be incremental to be backpressure".
- `assoc` / inclusive-boundary semantics matter for insertions at a span edge (e.g. inserting "a " before "member"). The brief's source map should define boundary association explicitly.

### Gaps
- I did not verify current tree-sitter changed-ranges API text or any 2025-2026 incremental-parsing papers.
- I found no published work on fingerprint-based stale-span detection for diagnostics specifically; GitHub's suggested-changes and code-review "outdated comment" logic is a likely analogue but I did not verify how it decides staleness.

## Any work on streaming / incremental validation of partially generated text?

### Takeaway
Two active lines: grammar-constrained decoding with incremental parsers over partial output (SynCode, IterGen; also Outlines/XGrammar-style engines), which prevents syntax errors but checks only syntax; and streaming Markdown renderers for LLM output that either buffer open blocks until closed (markdown-parser, mdstream) or auto-close unterminated syntax (Vercel streamdown + remend). Neither does semantic or conformance validation of partial documents with located findings; the brief's chat surface (validate structured blocks during streaming, batch failures, JSON Patch repair) goes beyond these, and the committed/pending block split is the right primitive to borrow.

### Cited Findings
- **SynCode** (UIUC + VMware Research, arXiv 2403.01632, ICLR 2025): an incremental parser returns, for partial code, accept sequences of terminals plus a "remainder" suffix that may still change terminal type; an offline DFA mask store filters next tokens; reports eliminating syntax errors for JSON and reducing 96.07% of syntax errors in Python and Go; parser state is cached per lexical-token prefix — [SynCode paper](https://arxiv.org/pdf/2403.01632); [repo](https://github.com/uiuc-focal-lab/syncode). Follow-up **IterGen** adds backward navigation (backtracking) using grammar symbols — [SynCode repo](https://github.com/uiuc-focal-lab/syncode)
- **markdown-parser** streaming mode buffers incomplete blocks and emits only finalized nodes; code blocks emit after the closing fence, tables close at the first non-table line — [markdown-parser streaming docs](https://www.mintlify.com/nimeshnayaju/markdown-parser/concepts/streaming)
- **mdstream** (Rust) separates committed from pending blocks; committed blocks are immutable, giving stable cache keys — [mdstream](https://docs.rs/crate/mdstream/latest)
- **remend** (used by Vercel **streamdown**) auto-completes unterminated bold, italic, code, links, images, strikethrough and math — [remend README](https://cdn.jsdelivr.net/npm/remend@1.3.0/README.md); [streamdown](https://www.mintlify.com/vercel/streamdown)
- **TanStack Markdown** re-parses the whole string on every update, no incremental state — [TanStack AI streaming guide](https://tanstack.com/markdown/latest/docs/guides/ai-streaming)

### Inferences
- The committed/pending split gives a natural rule for streaming findings: run conformance rules only on committed blocks (their spans are final), and treat findings on the pending tail as provisional (or suppress them). This avoids the "auto-close then flip" flicker that remend accepts for rendering but that would be noise as agent feedback.
- Constrained decoding and the brief's thesis are complementary, not competing: constrained decoding can only enforce what a grammar (CFG/regex) expresses; tier-1 rules like antecedent basis and DAG-shaped claim dependencies are context-sensitive and need post-hoc located checks. Remainder/accept-sequence ideas from SynCode could still let the codec report "this block cannot yet be judged" precisely.
- Nobody I found validates partial *documents* against semantic rules and feeds located findings back mid-generation; that is an opening, but also untested, and the cost of mid-stream interruptions on model quality is unknown.

### Gaps
- I did not survey Outlines, XGrammar, llguidance or LMQL in this session; they are well-known constrained-decoding engines **[memory]** but their partial-validation APIs were not checked.
- I found no study comparing span repair vs whole regeneration for LLM-produced documents; the closest evidence would be in program-repair literature (compiler-feedback loops), covered by another researcher's scope.

## Cross-cutting design lessons that transfer to the brief

### Takeaway
The notation-spoke design is well supported by prior art on every axis except the typed loss ledger and fingerprinted source map, which appear to be its own contribution. The main lessons are: separate fix applicability from finding confidence, round-trip opaque finding data to a lazy fix resolver, define position encoding and boundary association explicitly, prefer edit mapping plus fingerprint verification over fingerprint-only staleness, and frame the fold as a lens so its laws are testable.

### Cited Findings
- Position-unit mismatch is a known hazard: LSP negotiates UTF-8/16/32 with UTF-16 mandatory; unist offsets and Nu checker columns are UTF-16; tree-sitter uses bytes — [LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/); [unist](https://github.com/syntax-tree/unist); [Nu JSON](https://github.com/validator/validator/wiki/Output-%C2%BB-JSON); [tree-sitter](https://tree-sitter.github.io/tree-sitter/using-parsers/3-advanced-parsing.html)
- Conformance oracles can be partial and still useful: Nu suppresses further errors after a `fatal` well-formedness error and calls its positions "approximate" — [Nu JSON](https://github.com/validator/validator/wiki/Output-%C2%BB-JSON)
- Context-specialized rule docs: html-validate passes the report `context` into `documentation()` to produce error-specific explanations and a URL — [html-validate](https://html-validate.org/dev/writing-rules.html)

### Inferences
- `@beep/markdown` uses byte offsets; any LSP/editor projection (Lexical, VS Code, agent tools that count UTF-16) needs a conversion layer. Make the encoding part of the finding type, not an implicit convention.
- Add `applicability: MachineApplicable | MaybeIncorrect | HasPlaceholders | Suggestion-only` to the repair, borrowed from rustc/Biome. Keep `confidence` for whether the finding is true.
- Stable rule ids with docs URLs (ESLint messageId, Biome category, rustc E-codes, Markdoc error ids) are what make findings ledgerable and rule-precision measurable over time; the brief's ledger plan depends on that stability.
- The hub must not carry positions (it is notation-free and persisted), so every hub-level finding needs a source-map lookup; treat "no source span" as a first-class finding outcome (synthesized vs stale vs lost-in-fold), following unist/parse5's positionless-generated-node convention.
- A spoke without a lossless parser (`@beep/html` today) cannot offer span repair at all; parse5 with `sourceCodeLocationInfo` (start/end tag and attribute locations) is the obvious front end to make HTML a full spoke, but its tree correction creates positionless nodes that must flow into the loss/source-map ledger.

### Gaps
- No primary source found for any system that unifies human review comments and machine diagnostics in one finding type with judge identity; code-review tools (GitHub suggested changes, Gerrit robot comments) are plausible analogues — Gerrit "robot comments" with `fix_suggestions` exist **[memory, not re-verified]** and would be worth checking as the closest "human and machine findings in one shape, with fixes" precedent.
