# Declarative rule/schema DSLs projecting to OWL 2, SHACL, JSON Schema; DDD-shaped modeling DSLs

Scope note: researched 2026-10-28. Sources marked "(not re-fetched)" are canonical spec/doc URLs whose content I am stating from prior knowledge, not from a page I read in this session. Treat those claims as lower confidence. Local source reads are cited by absolute path.

## Q1. What does LinkML's experience say about one schema projecting to OWL + SHACL + JSON Schema: where do projections diverge and what annotations were needed?

### Takeaway
LinkML is the closest existing system to the thesis's "one declarative schema, many formal projections". Its own docs and paper say the projections are lossy, and its generators need many per-target switches. The main split: the LinkML source is closed-world, OWL output is a weaker open-world rendering, and SHACL output is where the closed-world validation intent lands. Rules mostly do not reach OWL and only partly reach SHACL.

### Cited Findings
- Canonical paper: "LinkML: an open data modeling framework", Moxon, Solbrig et al. (30+ authors), *GigaScience* 15, giaf152, DOI 10.1093/gigascience/giaf152, accepted Dec 2025. arXiv preprint 2511.16935 (v4 March 2026). Precursor: Moxon, Solbrig, Unni 2024, "The Linked Data Modeling Language (LinkML): A General-Purpose Data Modeling Framework Grounded in Machine-Readable Semantics". — [escholarship](https://escholarship.org/uc/item/895730mq); [arXiv 2511.16935](https://arxiv.org/abs/2511.16935v2)
- The paper lists generated targets as JSON Schema, Pydantic, SQL DDL, RDF, OWL, ShEx and SHACL. It says outright that "conversions are constrained by the expressiveness of the target framework and may result in some loss of information." — [arXiv 2511.16935v4 PDF](https://arxiv.org/pdf/2511.16935v4), section "Deriving Schema Serializations"
- The validator is plugin-based and runs JSON Schema validation, "SHACL for semantic validation", and SQL constraints, all from constraints declared once "independent of the underlying data storage format". — same paper, section "Validating Data"
- Ontology use is optional. The paper describes it as lightweight: URIs on classes and slots, SKOS mappings (`skos:exactMatch`, `broadMatch`, `narrowMatch`), and enums whose permissible values come from an ontology branch (e.g. ENVO under "soil"). — same paper, section "Optional Ontology Integration"
- From the OWL generator docstring: "OWL is open-world, whereas LinkML is closed-world." The docs say "OWL reasoners enforce a weaker model". A missing required value is not an OWL error, so the OWL output "may not be complete for data validation." — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html)
- OWL cardinality mapping: single-valued slots get `max 1`. Required single-valued slots get `exactly 1`, and other required slots get `min 1`. Non-required slots get `min 0`, which the docs call "formally tautological" but kept to show intent. Ranges become universal (`only`) restrictions. — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html)
- `is_a` and mixins both become `rdfs:subClassOf` by default. With `--mixins-as-expressions`, mixins become existential restrictions plus GCIs, so only `is_a` forms the subclass backbone. — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html)
- Enums: by default each permissible value becomes an OWL class and the enum becomes `owl:unionOf`. `--default-permissible-value-type` switches this to `owl:NamedIndividual` + `owl:oneOf`, or to literals + `oneOf`. A per-value `meaning` URI or `implements` annotation overrides it. The same LinkML enum can therefore be a class taxonomy or a closed individual set, and the author has to pick. — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html)
- Rules: "only a subset of LinkML rules can be expressed as OWL". SWRL output is listed as future work. — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html)
- Known breakages: an any-range slot has "no direct translation" to OWL-DL because OWL-DL forces a choice between DatatypeProperty and ObjectProperty, which can push the output into OWL Full. `--metaclasses` introduces punning. The docs contradict themselves on the metaclasses default and warn that `metaclasses` and `type-objects` defaults may change. — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html)
- The SHACL generator defaults to closed shapes (`--closed`, emitting `sh:closed true` with `sh:ignoredProperties (rdf:type)`). It emits `sh:maxCount 1` for single-valued slots. With `--emit-rules` it emits `sh:sparql` constraints from `rules:` blocks, but only for "recognised rule patterns (e.g. boolean-guard)". When several LinkML classes share a `class_uri`, their properties are merged into one shape by default (`--use-class-uri-names`). — [LinkML SHACL generator](https://linkml.io/linkml/generators/shacl.html)
- Rules (pre/postconditions) and boolean class expressions (`any_of`, `all_of`, `exactly_one_of`, `none_of`) are described as experimental, with behavior "not guaranteed to stay consistent". — [LinkML advanced features](https://linkml.io/linkml/schemas/advanced.html)

### Inferences
- LinkML's working pattern is "one closed-world source, two semantic projections": OWL for vocabulary and classification, SHACL for obligations and validation. It is not "one semantics everywhere". The beep DSL should make that split explicit in the AST rather than discover it per generator.
- The divergences fall in a few places: (a) required vs. open-world existence, (b) enums as classes vs. individuals vs. literals, (c) mixins as subclassing vs. restrictions, (d) any-typed slots vs. the DL property split, (e) rules, and (f) shape identity when several classes share one IRI. Each needed an author-visible switch. A faithful TS DSL needs these as first-class declaration fields, not generator flags. Otherwise the same declaration projects to different ontologies depending on CLI options.
- Effect v4's `SchemaRepresentation` already has the right meta-pattern for divergence (see Q5): each check declares whether its projection is exact or a "safe looser approximation", and approximation propagates. LinkML has no equivalent per-element soundness marker that I found.

### Gaps
- I did not find a LinkML document listing which generators honor `rules` and boolean expressions end to end. The advanced page points to an "implementation status" it does not contain.
- I could not confirm from the docs how the SHACL generator handles `required` (`sh:minCount 1`). The example output on the page showed none. I believe it emits `sh:minCount 1`, but that is unverified.
- I did not verify the JSON Schema generator's handling of `rules` or `any_of`.

## Q2. Has anyone mapped a DDD aggregate/command/event model to an ontology or used it as a rule carrier?

### Takeaway
I found no published work that maps DDD aggregates, commands and events to OWL/SHACL or uses them as a rule carrier for ontologies. DDD DSLs exist (Context Mapper CML, Alchemy `@alchemy.run/domain`), but they project to code, diagrams and service contracts, not to ontologies. Alchemy's declarations are only partly data: the handlers are functions. The thesis's DDD-to-ontology carrier would be new, which also means it is unproven.

### Cited Findings
- Alchemy `@alchemy.run/domain` v2.0.0-beta.84 (Apache-2.0, author Sam Goodwin) describes itself as "Domain-driven backends for Alchemy: aggregates, commands, events, projections, sagas and stories over Effect." About 11.1k lines across 27 modules. — local: `~/YeeBois/references/effect/alchemy/packages/domain/package.json` (checkout at commit 29537a8f4, 2026-10-27)
- In Alchemy, a Command class is an Effect `Schema.Top` with introspectable static metadata: `kind: "Command"`, `tag`, `target` (aggregate id schema), `events`, `rejects`, `reply`, `middleware`, and a derived Effect `rpc`. — local: `.../packages/domain/src/Command.ts`
- `Domain.verify(model)` / `Kernel.verify(definitions)` statically check a Model's definitions without hosting it. Examples: a view consuming a source keyed by another aggregate without `keyOf`, a policy listening for an event no source emits, a stream with two writers. All problems come back as `DefinitionError[]` in definition order. Problems that depend on handler output, such as `decide` returning an undeclared event, "still surface when the handler runs". — local: `.../packages/domain/src/Model.ts` (lines ~200–221), `.../src/Kernel.ts`
- Alchemy Story steps are a tagged union of data: `Given`, `When`, `Then`, `Rejected`, `Replied`, `State`, `View`, `Emitted`, `Streamed`, `Call`, `Answer`, `Returned`, `Clock`, `Advance`, `Signal`, `Saga`, `Provide`. — local: `.../packages/domain/src/Story.ts` (lines ~73–155)
- Context Mapper's CML is a DDD DSL for bounded contexts and aggregates, with Sculptor's DSL at the tactical level. Its generators target graphical context maps, PlantUML, MDSL service contracts, and a generic Freemarker template generator. I found no ontology layer. — [Context Mapper generators](https://contextmapper.org/docs/generators); [Bounded Context](https://contextmapper.org/docs/bounded-context/)
- A targeted search for papers mapping DDD aggregates or bounded contexts to OWL turned up only general DDD material. — search null result, 2026-10-28

### Inferences
- Alchemy shows two-layer validation: declaration-time structural checks (`verify`, deterministic, exhaustive over the declared graph) and runtime checks over handler behavior. This matches the thesis's tier 1/2 vs. tier 3 split. Alchemy also accepts that anything inside a function body is invisible to static analysis. For beep: anything written as a TS closure (a judge's `run`, a rule's predicate) cannot be projected to OWL/SHACL. Projectable content has to be data (expression ASTs), not lambdas.
- Alchemy's declaration-to-Effect-RPC derivation (Command to `Rpc`) and Story-as-data are the parts worth porting: one declaration yields a transport contract and a test vocabulary. The OWL/SHACL projection would be a new generator over the same metadata.
- A DDD aggregate is a consistency boundary and an event-sourced state machine. OWL has no notion of state, transition or time. The process ontology the thesis wants (PROV-O, BFO occurrents) can describe events after the fact as provenance individuals, but cannot express "command C is only valid in state S". That belongs in SHACL (closed-world shape on the provenance graph) or in rules. Mapping Command/Event/Policy to OWL classes is easy. Mapping their behavior is not possible in OWL.

### Gaps
- I did not search the MDE literature exhaustively, e.g. EMF/Ecore metamodels of DDD with OWL bridges. A DDD-to-OWL paper could exist in workshop proceedings that a web search misses.
- Alchemy's public docs site (alchemy.run/domain) was not fetched. Findings come from the local source checkout only.

## Q3. How do extensible declarative DSLs (Ash extensions, LinkML extensions/mixins, Effect Schema annotations) let a domain be "molded" on shipped primitives?

### Takeaway
All three use the same mechanism: a core that ships a small metamodel, plus third-party extension points that (1) add new declaration sections or annotation keys, (2) transform the declared structure at build time, (3) verify the final structure read-only, and (4) expose generated introspection. Ash/Spark is the most complete industrial example. Effect v4's `SchemaRepresentation` reviver registry is the most direct TypeScript precedent for keeping extensions serializable.

### Cited Findings
- Spark, Ash's DSL engine: "All DSLs are defined in extensions." A DSL is assembled from extensions via `use Spark.Dsl, default_extensions: [extensions: [...]]`. Extensions declare sections, entities and typed fields (`Spark.Builder.Section/Entity/Field`). — [Spark get-started](https://spark.hexdocs.pm/get-started-with-spark.html)
- Spark pipeline: transformers "allow for arbitrary transformations of the data structure backing our Dsl at compile time" (e.g. `Spark.Dsl.Transformer.add_entity/4`). Persisters run after all transformers and only cache derived values (`persist/3`). Verifiers validate the final DSL state read-only, return `:ok | {:error, _} | {:warn, _}`, and "avoid circular compile-time dependencies". `Spark.InfoGenerator` generates introspection functions. — [Spark get-started](https://spark.hexdocs.pm/get-started-with-spark.html)
- Ash: an extension defines sections and transformers. Transformers run in sequence over `dsl_state`. Ordering relative to other extensions is declared with `before?/1` and `after?/1`. Info accessors "can take a `dsl_state` *or* a module". To order against another library's transformers you have to read that library's source. — [Ash writing extensions](https://ash.hexdocs.pm/writing-extensions.html)
- LinkML extensibility: schemas `imports` other schemas, enums can be imported, mixins and `slot_usage` refine inherited slots. Schemasheets (spreadsheet authoring) and SchemaAutomator (import from TSV, SQL, JSON Schema, OWL) act as alternative front ends. — [arXiv 2511.16935v4](https://arxiv.org/pdf/2511.16935v4), sections "Author Schemas" and the intro; [LinkML advanced](https://linkml.io/linkml/schemas/advanced.html)
- Effect v4 `SchemaRepresentation` (module doc: "Open, compiler-extensible representation of Effect schemas"). Opaque declarations and checks carry a `RepresentationAnnotation { id: string; payload: Json }`. A registry of `Reviver`s (`DeclarationReviver`, `FilterReviver`, `FilterGroupReviver`, each `{ id, payloadSchema, revive }`) rebuilds live schemas from JSON. The module ships many built-in revivers (`isPatternReviver`, `isBetweenReviver`, `isUUIDReviver`, ...). It exposes `toRepresentation`, `toJson`, `fromJson`, `fromRepresentation`, `toJsonSchemaDocument`, `fromJsonSchemaDocument`, `toCodeDocument`. — local: `~/YeeBois/references/effect/effect/packages/effect/src/SchemaRepresentation.ts` (lines 1–40, 530–680, 2628–3260; checkout dated 2026-10-28)
- Effect `Schema.Annotations` include a per-check `toJsonSchema` compiler callback (`readonly toJsonSchema?: SchemaRepresentation.ToJsonSchema.Check`). — local: `.../packages/effect/src/Schema.ts` line ~17906

### Inferences
- What lets a domain be molded without core changes, judging by Spark, is the phase separation: declare, then transform, then persist, then verify, then introspect. Verifiers being read-only is what makes third-party verifiers composable. A stricter beep profile that only adds verifier findings (thesis point 7) matches this exactly. Transformers are where non-monotonicity sneaks in, because they rewrite. Ash handles transformer ordering with `before?/after?`, which is ad hoc. A beep design should either ban profile-level transformers or make them a separate, ordered, and ledgered phase.
- Effect's reviver registry is the TypeScript-native answer to "how does a third-party rule stay serializable": a custom rule is `{id, payload}` in the AST, plus a reviver keyed by `id` that rebuilds behavior and a per-target compiler (e.g. `toJsonSchema`) that declares exact vs. approximate. The beep DSL can reuse this directly. An `owl`/`shacl` projection callback per rule kind, with the same `[fragment, approximate]` contract, would give every projection a soundness tag.
- LinkML's extension story is weaker for behavior. Mixins and imports compose structure, and new behavior means writing a Python generator or validator plugin. Ash's model, where an extension owns DSL sections plus transformers and verifiers, is the better template for "judges" and "profiles".

### Gaps
- I did not confirm from docs how one Ash extension adds sections to another extension's DSL (e.g. AshPostgres's `postgres` block on `Ash.Resource`). The guide only shows an extension declaring its own section. I believe `Ash.Resource` accepts `extensions: [AshPostgres.DataLayer]` and that the extension contributes the `postgres` section, but I did not verify that this session.
- I did not verify whether `Spark.Dsl` declarations can be serialized to a data file. As far as I know they are compile-time Elixir module state, not a portable AST.

## Q4. What is the practical pattern for expressing obligations (must-have) given OWL's open-world assumption?

### Takeaway
The settled practice is to split: OWL (or RDFS/SKOS) for vocabulary, classification and disjointness, and SHACL (or OWL-under-closed-world-ICV, or rules) for obligations. The precise statement is that SHACL is closed-world on relations of focus nodes but open-world on the domain. Defeasible and deontic legal obligations (exceptions, permissions, time) are outside OWL and only partly inside SHACL. That is why LegalRuleML and Catala exist.

### Cited Findings
- LinkML: required-ness under OWL becomes `min 1` / `exactly 1`, which a reasoner satisfies by inferring an unknown value rather than flagging absence. Validation intent goes to SHACL closed shapes. — [LinkML OWL generator](https://linkml.io/linkml/generators/owl.html); [LinkML SHACL generator](https://linkml.io/linkml/generators/shacl.html)
- Stardog ICV evaluates OWL axioms (and SPARQL, SWRL, SHACL) as integrity constraints under closed-world semantics, assuming "all relevant data is known". The result is a boolean plus explanations via proof trees. A "guard mode" rejects violating transactions. Stardog notes that "a legal OWL 2 inference may violate or satisfy an Integrity Constraint". — [Stardog Data Quality Constraints 7.8.2](https://docs.stardog.com/archive/7.8.2/data-quality-constraints); [Stardog ICV blog](https://stardog.com/blog/data-quality-with-icv/)
- Heimsbakk & Torkelsen (2023), "Using the Shapes Constraint Language for modelling regulatory requirements" (arXiv:2309.02723): OWL's open-world assumption and expressiveness limits make it less suitable for regulations. They prefer closed-world SHACL for compliance checking, show that alternative requirements can be encoded as constraints, and argue that domain experts can maintain SHACL models. — [arXiv:2309.02723](https://arxiv.org/abs/2309.02723)
- A Hasselt University paper argues that "SHACL uses closed-world assumptions" is imprecise: SHACL is closed-world with respect to relations but open-world on the domain. — [documentserver.uhasselt.be (Genova)](https://documentserver.uhasselt.be/bitstream/1942/38989/2/Genova.pdf) (seen via search snippet; full paper not read)
- EDM Council (FIBO) working design for automated OWL-to-SHACL generation: "OWL does not imply anything, while SHACL implies a negation of a statement when a statement is absent". Shapes are generated only for leaf classes, with `sh:closed=False`. This is a working draft, not a standard. — [EDM Council wiki](https://dil-edmcouncil.atlassian.net/wiki/x/Do9u)
- Practical friction: closed shapes conflict with subclass extension (a subclass adding properties violates the parent's closed shape). The suggested workarounds (`sh:ignoredProperties`) are "not straightforward". — [public-rdf-shapes thread, Oct 2020](https://lists.w3.org/Archives/Public/public-rdf-shapes/2020Oct/0001.html)
- SHACL 1.2 Rules is a W3C Working Draft (latest snapshot I found: 2026-07-27). It has `infer` and `query` operations, negation-as-failure with stratification, and recursive rules. Rule heads may create new terms, and users must avoid non-termination. Open issues included attaching rules to shapes and IMPORTS. It is explicitly a work in progress. — [SHACL 1.2 Rules WD 2026-07-27](https://www.w3.org/TR/2026/WD-shacl12-rules-20260727/); [latest](https://www.w3.org/TR/shacl12-rules/)
- SHACL Advanced Features (SHACL-AF, a 2017 W3C Working Group Note, not a Recommendation) introduced `sh:rule` (TripleRule, SPARQLRule), SHACL functions and custom targets. — [SHACL-AF](https://www.w3.org/TR/shacl-af/) (not re-fetched)
- SHACL Core `sh:severity` takes `sh:Violation`, `sh:Warning`, `sh:Info`. Validation reports carry `sh:focusNode`, `sh:resultPath`, `sh:value`, `sh:sourceShape`, `sh:sourceConstraintComponent`, `sh:resultMessage`. — [W3C SHACL](https://www.w3.org/TR/shacl/) (not re-fetched)
- LegalRuleML Core Specification v1.0 became an OASIS Standard in August 2021. It covers legal sources, time, defeasibility, and deontic operators (obligation, permission, prohibition). Papers note that "OWL does not support defeasibility, time management, and other operators... required in normative reasoning". Workarounds include OWL restrictions over complement subclasses for exceptions (Francesconi & Governatori 2023) and a LegalRuleML metamodel in OWL with norms as SPARQL rules. — [OASIS announcement](https://www.oasis-open.org/?p=7617); [arXiv 1711.06128](https://arxiv.org/pdf/1711.06128v1); [arXiv 2411.19918](https://arxiv.org/pdf/2411.19918)
- Catala, a lawyer-readable DSL by Merigoux et al.: its semantics are a default calculus for exception-heavy law. The compiler is a nanopass/CompCert-style chain of IRs. Defaults are compiled away with catchable exceptions, a scheme described as certified. Documented backends: OCaml, Python, C, with Java in the 1.1.0 architecture diagram, plus a `Driver.Plugin` backend API. JavaScript via js_of_ocaml is suggested by a runtime module name but not confirmed. — [Catala package docs](https://ocaml.org/p/catala/latest/doc/index.html); [Catala 0.8.0 lcalc](https://ocaml.org/p/catala/0.8.0/doc/lcalc.html)
- TypeDB 3.0 replaced 2.x inference `rule`s with explicit, recursive, negatable `fun`ctions ("requiring explicit functions execution instead of inference"). The stated reason is a move from predicate-logic to type-theory semantics, so there is no inference toggle. — [TypeDB 2→3 diff](https://typedb.com/docs/reference/typedb-2-vs-3/diff/index.md); [Functions vs rules](https://typedb.com/docs/typeql-reference/functions/functions-vs-rules/)

### Inferences
- The pattern for beep: every obligation-shaped declaration (`requires`, `mustHave`, `dischargedBy`) projects to SHACL with `sh:severity` taken from the declared rule severity. Optionally it also emits a weak OWL existential (`min 1`), marked as non-enforcing documentation. Vocabulary declarations (taxonomy, disjointness, subproperty) project to OWL. A declaration that tries to be both needs an explicit marker for which semantics is authoritative.
- Legal obligations with exceptions ("must X unless Y, except where Z") are defeasible. SHACL-with-stratified-negation (SHACL 1.2 Rules) can encode simple priority via negation-as-failure, but there is no standard SHACL encoding of the defeasible priority relations LegalRuleML expresses. Catala's default calculus is the closest proven carrier for exception-structured rules that compile to several targets. This is a real expressivity gap for patent-practice rules (e.g. MPEP exceptions).
- TypeDB's move from inference rules to explicitly invoked functions is a relevant data point for the oracle use case. Explicit derivation is easier to trace and ledger, and leaves no ambiguity about whether a finding came from stored or inferred data. It supports judges as explicit functions over a closed graph, rather than a forward-chaining reasoner whose derived facts silently satisfy obligations. Stardog's warning that OWL inference can satisfy an IC points the same way.
- Witness and discharge semantics (thesis point 5) map naturally to SHACL `sh:qualifiedValueShape` / `sh:qualifiedMinCount` over a provenance graph ("a NoveltyObligation must have ≥1 `prov:wasGeneratedBy` a Search whose `prov:used` sources are all `sh:in` an approved list"). Deterministic sub-checks that need fetching (link resolves, quote present) cannot be SHACL. They are judges whose results are asserted into the graph as facts with provenance, and only then does SHACL check them.

### Gaps
- I did not read the SHACL 1.2 Core draft. I don't know whether 1.2 changes `sh:closed` semantics or adds anything obligation-specific.
- I found no peer-reviewed comparative evaluation (precision/recall) of SHACL-encoded legal obligations against human review.
- I did not read the Catala papers themselves (Merigoux, Chataing, Protzenko, ICFP 2021 "Catala: A Programming Language for the Law") this session. The default calculus description comes from compiler docs.

## Q5. What must the AST contain for faithful OWL 2 / SHACL projection, what is lost in each direction, and has bidirectional projection (OWL in, DSL out) been done?

### Takeaway
Bidirectional projection exists but is lossy and heuristic in every case I found. LinkML SchemaAutomator imports schema-style OWL "experimentally". Effect v4 has `fromJsonSchemaDocument` and JSON round-trip of its own representation. OMG ODM says outright that UML and OWL are each more and less expressive than the other. A faithful projection needs the AST to carry IRIs, world-assumption markers, cardinality, disjointness and closure, severity, provenance, and a per-element exact/approximate tag for each target. Effect's `ToJsonSchema.CheckOutput` is the best existing model for the last item.

### Cited Findings
- SchemaAutomator importers "generally take a less expressive language than LinkML" and produce a schema that "may be less optimal than a hand-crafted schema". OWL import accepts only schema-style OWL in functional syntax (convert first with ROBOT: `robot convert -i x.ttl -o x.ofn`, then `schemauto import-owl`). The LinkML FAQ says importers are experimental: "a number of heuristic measures are applied, and the results are not guaranteed to be correct." — [schema-automator importers](https://linkml.io/schema-automator/packages/importers.html); [LinkML FAQ tools](https://linkml.io/linkml/_sources/faq/tools.md.txt)
- The LinkML paper confirms SchemaAutomator converts "TSV files, HTML tables, SQL databases, JSON Schemas, and OWL/RDF files, into the LinkML format". — [arXiv 2511.16935v4](https://arxiv.org/pdf/2511.16935v4), "Author Schemas"
- linkml-owl, a separate package, generates OWL *instance-level* axioms from LinkML data using templated annotations. This is a different direction from gen-owl. — [linkml-owl usage](https://linkml.io/linkml-owl/usage/) (seen in search; not fetched)
- OMG ODM UML-to-OWL: "UML is both more expressive than and less expressive than OWL – the mapping is not straightforward". The ODM mapping section was deliberately non-normative because "all mappings are [not] created equal" depending on purpose. The Eclipse ATL UML2OWL implements the ODM QVT mapping (classes to OWL classes, attributes to datatype properties, associations to object properties). — [public-owl-dev 2008](https://lists.w3.org/Archives/Public/public-owl-dev/2008OctDec/0094.html); [Eclipse ATL ODM](https://eclipse.dev/atl/usecases/odmimplementation/)
- TwoUse (Univ. Koblenz) integrates UML models with OWL ontologies. I found only a catalog entry. — [TwoUse](https://kola.opus.hbz-nrw.de/frontdoor/index/index/docId/123)
- Effect v4 JSON Schema export from a representation document is "intended for preliminary validation... the Effect decoder remains the final authority. Passing JSON Schema validation does not guarantee that Effect decoding will succeed." Filters without a `toJsonSchema` callback and opaque declarations are approximate. Approximation propagates through checks, nested schemas, dependencies and recursive refs, and a `oneOf` union with an approximate branch exports as `anyOf`. A check compiler returns a fragment for exact output or `[fragment, true]` for "a safe, looser approximation: it must accept every value accepted by the check, but may accept additional values". "The compiler trusts the callback's declaration; it does not prove" it. — local: `~/YeeBois/references/effect/effect/packages/effect/src/SchemaRepresentation.ts` lines ~48–100, ~2680–2700
- Effect v4 `fromJsonSchemaDocument` (draft 2020-12 to `Schema.Top`) errors on `pattern` constraints by default (`patterns: "apply"` only for trusted documents, `"ignore"` can both admit invalid and reject valid values). — same file, ~3195–3215
- OWL 2 profiles: EL (polynomial classification, existentials, no universals or cardinality), QL (query rewriting to SQL), RL (rule-implementable, forward-chaining). Full OWL 2 DL is N2EXPTIME-complete. — [W3C OWL 2 Profiles](https://www.w3.org/TR/owl2-profiles/) (not re-fetched)

### Inferences
Minimum AST content for a faithful OWL 2 + SHACL projection, synthesized from the LinkML divergences, the Effect approximation contract, and the SHACL/OWL specs:
1. **Identity**: a stable IRI per declaration (class, property, individual, rule, shape), separate from the TS class name, plus a prefix map. LinkML needed `class_uri`/`slot_uri` and hit shape-merging problems when IRIs were shared. Declare whether an element is a class, an individual, or punned (enum values!), and do not leave that to a generator flag.
2. **World assumption per constraint**: each constraint is tagged `vocabulary` (OWL, open-world, inferential) or `obligation` (SHACL, closed on relations, reported). A `both` tag gets a declared authoritative side.
3. **Property kind**: object vs. datatype vs. annotation property, fixed at declaration. Any-typed slots force OWL Full, as LinkML found.
4. **Cardinality and range** with both readings: OWL `min/max/exactly` + `only/some`, SHACL `minCount/maxCount` + `sh:class/sh:datatype`. Plus qualified cardinality (needed for witness counts).
5. **Taxonomy semantics**: `is_a` vs. mixin vs. role. Disjointness and covering (`owl:disjointUnionOf`) declared explicitly, because OWL infers nothing from sibling-ness. Shape closure (`sh:closed` + ignored properties) with a declared policy for subclass extension.
6. **Rule bodies as data**: a restricted expression AST (path, comparison, boolean, negation, aggregation) whose fragments map to SHACL-SPARQL / SHACL 1.2 Rules / SWRL / Datalog. Rules written as TS closures are opaque and must project as approximate (`[{}, true]`), as Effect does.
7. **Severity and judge**: SHACL's Violation/Warning/Info is too coarse for the thesis's single finding shape. Carry the beep severity and map it down, and keep judge identity and confidence as annotations (`sh:resultAnnotation`-style; check against SHACL 1.2).
8. **Provenance of the declaration itself**: authored by whom, derived from which source (e.g. an MPEP section, an office-action corpus), version. PROV-O annotations on axioms, using OWL axiom annotations.
9. **Per-target soundness tag**: each element's projection to each target is `exact | sound-approximation (looser) | omitted`, propagated upward the way Effect propagates it. This is how a profile can state "the OWL view is documentation only, SHACL is authoritative".
10. **OWL profile target**: declare EL/QL/RL/DL so the generator can refuse constructs outside it.

What is lost going DSL to OWL: closed-world obligations, defaults, rule bodies beyond Horn/RL, ordering and state (aggregate lifecycles), numeric aggregation, and defeasibility. DSL to SHACL loses inference (subsumption, equivalence), and the open-domain reasoning that lets OWL classify new terms. OWL to DSL loses arbitrary class expressions (nested existentials, GCIs, property chains, inverse and transitive characteristics), which have no natural class-declaration form; LinkML gets around this by accepting only "schema-style" OWL. SHACL to DSL loses SPARQL-based constraints unless the DSL embeds SPARQL.

- Bidirectionality in practice: a round trip DSL to OWL to DSL is only faithful on the fragment the DSL can express natively. A realistic design treats OWL import as a lossy front end with a loss report, which is the same "fold with typed losses" pattern the beep markdown codec already uses. That is a strong reuse argument for the thesis's own architecture.
- Alternatives the brief names that I did not research in depth: Soufflé (Datalog to C++, stratified negation, aggregates), Datomic Datalog rules, Stardog rules (SRS, Datalog-like, plus SWRL), Alloy/TLA+ (relational/temporal model finding and checking, which do not project to OWL in any standard way), OSLC (resource shapes, a precursor of SHACL), Prisma/Drizzle (schema DSLs projecting to SQL and TS types only), Zod and TypeBox (JSON Schema derivation; TypeBox *is* JSON Schema at runtime). I have no sourced claims on these this session.
