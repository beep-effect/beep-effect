# Pstack principles versus beep-effect doctrine

## Principle rules, triggers, and tells

### Boundary Discipline

The rule is to decode, validate, narrow, and translate failures once where untrusted data enters, then pass typed domain values to a thin shell and pure business logic without repeated defensive checks. It triggers at CLI, configuration, network, storage, framework, and external API boundaries, or whenever validation and framework concerns begin leaking into domain code. The tell is a reply that identifies the exact boundary, names the typed value produced there, and points to the redundant internal guard or framework dependency it removed; saying only that “boundary discipline was applied” proves nothing. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-boundary-discipline/SKILL.md`.

### Build the Lever

The rule is to build the smallest deterministic codemod, script, generator, query, check, or delegate skill that performs or proves any non-trivial task, and to make that artifact safe to rerun. It triggers even for one-off work when hand execution would be hard to reproduce or review; only a couple of obvious edits that can be checked at a glance are exempt. The tell is a concrete lever file in the diff or evidence bundle, plus a reply that names the manual step it replaced and shows a rerun produced the same result; if no such artifact exists, the principle was not applied. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-build-the-lever/SKILL.md`.

### Encode Lessons in Structure

The rule is to turn recurring corrections into the strongest available mechanism, preferring an unrepresentable state, failing lint or CI rule, canonical helper, runtime check, or script over another paragraph of advice. It triggers when an instruction or correction appears for the second time, when the same failure recurs, or when surrounding code is teaching agents the wrong pattern. The tell is a reply that names the repeated failure and the structural enforcement added or strengthened, with a concrete lint, metadata, type, helper, check, or script to inspect; a note that merely promises to remember is the failure mode. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-encode-lessons-in-structure/SKILL.md`.

### Exhaust the Design Space

The rule is to produce two or three genuinely different prototypes or sketches for a novel interaction or architecture choice, compare them side by side, and commit only after the comparison resolves the decision. It triggers when the codebase has no precedent and more than one viable UI, product, or architecture shape exists; it does not trigger for mechanical changes, clear bug fixes, or constraint-determined work. The tell is a reply that links or describes the competing artifacts, states the comparison criteria, and names the choice that changed because of the comparison; three cosmetic variants of one design do not count. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-exhaust-the-design-space/SKILL.md`.

### Experience First

The rule is to optimize technical and scope decisions for the experience of the end user, library consumer, and next maintainer, accepting fewer features when that produces a more coherent and polished core loop. It triggers when feature count, controls, implementation convenience, polish, feedback, error handling, or API ergonomics compete with the consumer's result. The tell is a reply written from the affected consumer's seat that names the feature, option, or shortcut removed or changed and the observable experience it improves; a generic claim that the implementation is cleaner is insufficient. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-experience-first/SKILL.md`.

### Fix Root Causes

The rule is to reproduce a defect, inspect real state and errors, keep asking why until the causal mechanism is located, fix that mechanism, and search for the same pattern elsewhere instead of silencing the symptom with a guard. It triggers whenever debugging starts, especially for restart-only failures where persistent configuration, caches, locks, or serialized state may differ between runs. The tell is a reply containing the reproduction, the causal chain, the instrumentation or evidence that distinguished the cause from guesses, and proof that the original reproduction now passes; an unexplained nil check or workaround comment is evidence that the principle was skipped. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-fix-root-causes/SKILL.md`.

### Foundational Thinking

The rule is to choose the core data shape, access patterns, ownership, concurrency isolation, shared types, and enabling scaffold before feature logic, while keeping premature abstractions out of the path. It triggers before choosing types or data structures, before actors share mutable state, and when deciding whether CI, linting, test infrastructure, or another capability should precede later phases. The tell is a reply that names the foundational structure or scaffold, traces the dominant access and mutation paths it supports, and explains which later decisions became simpler; abstraction added only to remove repeated lines is not proof. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-foundational-thinking/SKILL.md`.

### Guard the Context Window

The rule is to spend session context only on material that will affect the task, isolating bulk payloads and retaining concise findings while keeping frequently reused instructions inline. It triggers when outputs, screenshots, long files, repeated reads, fan-out, or an oversized phase threaten to fill the main context. The tell is a reply that states what bulk material was isolated or skipped, preserves the conclusions needed for the next decision, and gives the phase or file cap used; dumping raw payloads into the main thread and later summarizing them does not satisfy it. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-guard-the-context-window/SKILL.md`.

### Laziness Protocol

The rule is to seek deletion first, keep call hierarchies flat, centralize each decision, avoid threading new signals through multiple layers, and make the smallest diff that solves the problem without exhausting a human maintainer. It triggers during refactors, diff-size reviews, and any temptation to introduce an abstraction, layer, compatibility path, or cross-pipeline signal. The tell is a reply that identifies what was deleted, inlined, flattened, or left unbuilt and how the smaller result still meets the acceptance criteria; a large “clean architecture” scaffold is contrary evidence. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-laziness-protocol/SKILL.md`.

### Make Operations Idempotent

The rule is to make every state-changing command, lifecycle step, or processing loop converge to the same correct state after retries, restarts, and crashes at any intermediate point. It triggers when an operation can run twice, resume after partial mutation, recover stale locks or sessions, or respawn failed scheduled work. The tell is a reply that answers the run-twice and crash-at-each-step tests, identifies the reconciliation step, and shows repeated execution reaches the same end state; dependence on creation order or unexplained leftover state proves the operation is not idempotent. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-make-operations-idempotent/SKILL.md`.

### Migrate Callers Then Delete Legacy APIs

The rule is to inventory and migrate internal callers, remove the superseded API and tests in the same refactor wave, and allow a temporary adapter only as an exceptional, time-boxed compatibility measure. It triggers when a better internal API has been selected, the project controls its callers, and coordinated breaking changes are possible. The tell is a reply that shows the caller inventory is empty for the legacy symbol, identifies the deleted export and implementation, and points to tests of the new contract; keeping both paths “for now” without a dated external constraint is evidence that it was not applied. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-migrate-callers-then-delete-legacy-apis/SKILL.md`.

### Minimize Reader Load

The rule is to reduce both the layers a reader must trace and the hidden or mutable state they must remember, collapsing pass-through boundaries and shrinking state to the narrowest useful scope. It triggers when the origin or mutation of a value is hard to locate, a wrapper has one caller, adjacent layers repeat the same interface, or a broad abstraction hides little. The tell is a reply that names the collapsed layer or reduced state scope and demonstrates that a new reader can answer “where does this come from?” and “what can change it?” in roughly 30 seconds; line-count reduction alone is not the measure. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-minimize-reader-load/SKILL.md`.

### Model the Domain

The rule is to encode valid states, invariants, transitions, and access patterns in a fitting structure such as a state machine, typed model, discriminated union, registry, reducer, queue, cache, or graph instead of spreading them through branches and synchronized booleans. It triggers when stateful logic grows an if/else chain, a second boolean must remain synchronized, shape assumptions repeat across files, or modules are divided by execution phase rather than domain ownership. The tell is a reply that names the domain structure, identifies the invalid state or duplicated branch it eliminates, and points to exhaustive construction or matching; adding one more conditional is the clearest sign it was skipped. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-model-the-domain/SKILL.md`.

### Never Block on the Human

The rule is to proceed on reversible, reviewable execution decisions, present the result for asynchronous correction, and reserve questions for genuine ambiguity, irreversible actions, or product direction. It triggers whenever an agent is about to ask “should I do X?” for an edit, note, split, or other reversible action that can be inferred from the task. The tell is a reply that names the reasonable assumption, shows the completed reversible work, and calls out any irreversible or product decision it correctly left for the user; a permission pause with no material ambiguity is contrary evidence. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-never-block-on-the-human/SKILL.md`.

### Outcome-Oriented Execution

The rule is to optimize a planned rewrite or migration for the verified target architecture, allowing scoped and reversible intermediate breakage instead of accumulating throwaway compatibility code to keep every intermediate state smooth. It triggers only when the target, phase boundaries, permitted breakage, focused checks, and final verification are explicit. The tell is a reply that names the target state, declares where temporary breakage was allowed, shows high-signal checks during the migration, and reports full static and runtime proof at completion; an unexplained compatibility layer left after the migration fails the rule. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-outcome-oriented-execution/SKILL.md`.

### Prove It Works

The rule is to verify the real output or behavior directly after every task, treating compilation and derived indicators as necessary but insufficient proxies and preferring a deterministic rerunnable check when feasible. It triggers before any done claim and after delegated work, integrations, generated output, or a failed observation method. The tell is a reply that names the actual feature path or artifact inspected, shows the input-to-output chain or runtime result, and links the check or evidence a reviewer can rerun; “build passed” or an agent self-report alone fails the principle. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-prove-it-works/SKILL.md`.

### Redesign From First Principles

The rule is to integrate a new requirement as though it had been a foundational assumption from the first design, propagating the resulting model through types, code, documentation, examples, and rationale instead of adding a local bolt-on. It triggers when an existing design must absorb a new requirement whose implications cross its current representation or boundaries. The tell is a reply that states the day-one design, lists the affected references updated to match it, and explains which bolt-on path was avoided; changing one adapter while leaving the old conceptual model everywhere else does not qualify. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-redesign-from-first-principles/SKILL.md`.

### Separate Before Serializing Shared State

The rule is to eliminate a shared mutable write target whenever actors can own independent facts, and to use structural serialization such as a single writer, sequential phase, lock, or compare-and-swap only when one canonical object is a real invariant. It triggers when concurrent actors may write the same file, branch, key, API surface, or state object. The tell is a reply that identifies the shared target and either assigns separate owned files, keys, branches, or state directories, or proves why sharing is intrinsic and names the enforced serialization mechanism; telling actors to take turns is not evidence. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-separate-before-serializing-shared-state/SKILL.md`.

### Sequence Work into Verifiable Units

The rule is to divide multi-step work into the smallest coherent units that each end in a real check, keep every unit green before advancing, and order commits or PRs so the delivery itself demonstrates the argument. It triggers for sweeps, migrations, repeated edits, and delivery stacks where a late batch failure would hide the responsible change. The tell is a reply that shows the ordered unit list and the check after each unit, ideally a red test followed by the green fix or an equivalent proof sequence; a large batch followed by one final verification run does not satisfy it. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-sequence-verifiable-units/SKILL.md`.

### Subtract Before You Add

The rule is to remove dead code, redundant validation, obsolete references, unused options, and speculative behavior before constructing the replacement, leaving a simpler and no larger design surface. It triggers when sequencing an addition, refactor, rewrite, prompt revision, or new validator and whenever current complexity may be hiding the essential design. The tell is a reply that identifies the subtraction performed first and shows how it reduced the following addition; polishing or extending the old surface before removing its dead weight is contrary evidence. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-subtract-before-you-add/SKILL.md`.

### Type System Discipline

The rule is to use the type checker as a proof assistant by constructing legal states, branding semantic primitives, parsing external data, rejecting casts, matching variants exhaustively, deriving from authoritative schemas, and strengthening types only where an operation would otherwise be partial. It triggers when designing a type or function signature, encountering `any`, assertions, synchronized optionals, interchangeable primitives, unhandled variants, or a type that duplicates another source of truth. The tell is a reply that names the impossible state or unchecked case removed and points to the construction, brand, parser, exhaustive match, or derivation that makes the compiler enforce it; a cast or comment that asks callers to maintain an invariant proves it was not applied. Source: `~/YeeBois/dev/cursor-plugins/pstack/skills/principle-type-system-discipline/SKILL.md`.

The common tell for all 21 principles is stricter than name citation: the reply must name the principle and the concrete decision it changed. That is the contract stated in `~/YeeBois/dev/cursor-plugins/pstack/docs/guide/08-principles.md`, “Steer with principle names.”

## Repo laws with no pstack principle

These are candidate beep-specific principles because no pstack principle states the rule. A broad pstack principle may support the intent, but it does not encode the required repository mechanism or completion tell.

1. **Design schema first, then implement.** Before code, audit live source, model vocabulary, valid states, invariants, boundaries, construction, encoded forms, and proof; grill one material question at a time; wait for explicit authorization; then implement from the decision-complete Schema graph. `Model the Domain`, `Foundational Thinking`, and `Type System Discipline` do not impose this design order or align gate. Sources: `standards/schema-first-development-prompt.md`, “Session Protocol,” Task Mode `new`, and “Core Modeling Contract”; `standards/effect-first-development.md`, EF-33; `AGENTS.md`, Code Laws.

2. **Effect v4 only, verified from live source.** Do not write non-trivial Effect or Schema APIs from memory. Resolve the current vendored Effect checkout and verify symbols and signatures against its live v4 documentation and source. None of the pstack principles pins a runtime/library generation or defines a live-source authority order. Sources: `standards/schema-first-development-prompt.md`, “Authority and Live-Source Rule”; `.claude/skills/effect-first-development/SKILL.md`, “Source of Truth References”; `standards/effect-first-development.md`, EF-33.

3. **Use Effect collections, never native `Map` or `Set` in domain logic.** Domain collection work uses `HashMap`, `HashSet`, `MutableHashMap`, `MutableHashSet`, `effect/Array`, and `effect/Record`; native `Object`, `Map`, and `Set` are forbidden. `Model the Domain` recommends a generic map or registry but does not select the repo's lawful collection type. Sources: `standards/effect-laws-v1.md`, Short Law 6; `standards/effect-first-development.md`, EF-5; `.claude/skills/effect-first-development/SKILL.md`, Non-Negotiable Law 7.

4. **Use `effect/unstable/http`, never `node:http` or native runtime HTTP.** Runtime requests, responses, headers, parameters, methods, and bodies use `effect/unstable/http` modules with an explicitly provided platform client layer; native `fetch`, `node:http`, and other Node runtime HTTP shortcuts do not define a lawful domain or tooling boundary. `Boundary Discipline` says where the adapter belongs but not which runtime vocabulary it must use. Sources: `standards/effect-laws-v1.md`, Short Laws 9 and 14; `standards/effect-first-development.md`, EF-9b; `.claude/skills/effect-first-development/SKILL.md`, Non-Negotiable Law 50.

5. **Use `LiteralKit` for internal literal domains.** When a finite internal domain needs `.is`, `.thunk`, `$match`, subset helpers, enum-like access, annotations, or tagged-union construction, `LiteralKit` owns the literal set and derived behavior. Neither `Model the Domain` nor `Type System Discipline` specifies this canonical repo primitive. Sources: `AGENTS.md`, Code Laws; `standards/effect-laws-v1.md`, Short Law 19; `standards/effect-first-development.md`, EF-12b, EF-13, and EF-35b; `standards/schema-first-development-prompt.md`, “Derive behavior instead of duplicating truth” and “Finite variants are discriminated.”

6. **Proof over assertion uses beep QA for gesture-bearing UI.** A UI milestone with gestures requires the `browser-qa-loop` and a recorded `bun run beep qa` session, extraction, and schema-validated witness/judge inventory. `Prove It Works` requires real behavior, but it does not require this repo's video and event-log evidence chain. Sources: `AGENTS.md`, “Browser QA” and the “Touch → Skill / Command” row for gesture-bearing UI.

7. **Worktree hygiene preserves operator work and publication authority.** Inspect dirty state before editing, preserve unrelated staged, modified, and untracked files, keep full worktrees out of `/tmp`, do not stage, commit, push, publish, rebase, switch branches, or regenerate broad snapshots without authorization, and attribute failures before repair. `Separate Before Serializing Shared State` helps divide writers but does not protect operator-owned work or git publication authority. Sources: `standards/schema-first-development-prompt.md`, “Hard Boundaries”; `AGENTS.md`, “Quality Operator.”

8. **Friction receipts are immediate, redacted outputs.** When work is slower, harder, or riskier than it should be, immediately add a redacted receipt to the active packet's `research/OPPORTUNITIES.md` with the task, minimal evidence, and the prevention mechanism. `Encode Lessons in Structure` closes recurring corrections, but it has no public packet ledger, immediate receipt timing, or redaction contract. Source: `AGENTS.md`, “Docs & Knowledge.”
