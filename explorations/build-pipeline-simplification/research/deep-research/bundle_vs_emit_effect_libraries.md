# Bundling vs unbundled `tsc`-style emit for libraries built on Effect (v3/v4)

Research date: 2026-10-09. Sources checked live (effect.website, Effect-TS/effect repo at `main` = `effect@4.0.2`, `effect@3.21.2` on jsdelivr, Turborepo/Next.js/Rolldown/oxc/esbuild/tsdown docs, GitHub issues via `gh`). Where a claim is Effect-team guidance it is marked **(official)**; where it is third-party or inferred it is marked **(opinion/inference)**.

## Q1. Why do `effect` / `@effect/*` ship unbundled per-module output with a big `exports` map, `sideEffects` narrow, and `babel-plugin-annotate-pure-calls`?

### Takeaway
The Effect team deliberately emits one JS file per source module with `tsc -b` and then post-processes `dist/` with `babel-plugin-annotate-pure-calls`; the package is "tree-shaking friendly" by construction (functions, not methods; per-module files; a 179-entry (v3) / wildcard (v4) `exports` map), and v4 tightened `sideEffects` from `[]` to a two-file allowlist. They never bundle their own packages. **(official, verified in repo)**

### Cited Findings
- `effect@4.0.2` (`main`) build pipeline is `"build": "tsc -b tsconfig.json && pnpm babel"`, `"babel": "babel dist --plugins annotate-pure-calls --out-dir dist --source-maps"`. No bundler in the chain. — [Effect-TS/effect packages/effect/package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json) (verified 2026-10-09)
- `effect@4.0.2` `sideEffects` is an allowlist, not `false`: `["./src/schema/SchemaJITCompiler/enable.ts", "./dist/schema/SchemaJITCompiler/enable.js"]` — i.e. exactly one module is permitted to have import-time side effects; everything else is droppable. — [same package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json)
- `effect@4.0.2` is `"type": "module"` (ESM-only), with 28 `exports` entries in dev (`"./*": "./src/*.ts"`, `./internal/*: null`, `./*/index: null`) and `publishConfig.exports` rewritten to `"./*": "./dist/*.js"`. `files` ships `src/**/*.ts`, `dist/**/*.js`, `dist/**/*.js.map`, `dist/**/*.d.ts`, `dist/**/*.d.ts.map` — source is published so source maps and declaration maps resolve. — [same package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json)
- Repo `tsconfig.base.json` emits with `"module": "NodeNext"`, `"target": "ES2022"`, `"verbatimModuleSyntax": true`, `"declarationMap": true`, `"sourceMap": true`. — [Effect-TS/effect tsconfig.base.json](https://raw.githubusercontent.com/Effect-TS/effect/main/tsconfig.base.json)
- `effect@3.21.2` (v3) was dual CJS/ESM: `main: ./dist/cjs/index.js`, `module: ./dist/esm/index.js`, 179 `exports` entries each of shape `{ types: ./dist/dts/X.d.ts, import: ./dist/esm/X.js, default: ./dist/cjs/X.js }`, `sideEffects: []`. — [effect@3.21.2 package.json](https://cdn.jsdelivr.net/npm/effect@3.21.2/package.json)
- Third-party Effect libraries built with the Effect-team toolchain show the full v3 recipe verbatim: `@effect-atom/atom@0.7.1` runs `build-utils prepare-v2` → `tsc -b tsconfig.build.json` (ESM) → `babel build/esm --plugins @babel/transform-export-namespace-from --plugins @babel/transform-modules-commonjs --out-dir build/cjs --source-maps` → `babel build --plugins annotate-pure-calls --out-dir build --source-maps` → `build-utils pack-v2`; `sideEffects: []`; `effect` is a peer dependency (`^3.22.1`). — [tim-smart/effect-atom packages/atom/package.json](https://raw.githubusercontent.com/tim-smart/effect-atom/main/packages/atom/package.json)
- Official import guidance: "named imports may generate tree shaking issues when a bundler doesn't support deep scope analysis"; bundlers that do not have the problem are listed as Rolldown, Rollup, Webpack 5+. Both `import { Effect } from "effect"` and `import * as Effect from "effect/Effect"` are documented as valid. — [effect.website Importing Effect (v4)](https://effect.website/docs/v4/getting-started/importing-effect) **(official)**
- Design rationale for functions over methods: "only the functions that are actually imported and used in your application will be included in the final bundled code"; methods "cannot be easily tree shaken." — [same page](https://effect.website/docs/v4/getting-started/importing-effect) **(official)**
- Official "Myths" page: minimum cost "approximately 25KB gzipped" for the runtime + common functions; "From that point on Effect is tree-shaking friendly so you'll only include what you use"; they claim apps where adopting Effect "led to reduction of the final bundle." — [effect.website Myths](https://effect.website/docs/additional-resources/myths) **(official)**
- v4 beta announcement (2026-02-18): a minimal program using Effect, Stream and Schema "dropped from roughly 70 kB in v3 to about 20 kB in v4"; v4 merges `@effect/platform`, `@effect/rpc`, `@effect/cluster` etc. into core `effect` with `effect/unstable/*` paths; all packages share one version. — [Effect 4.0 beta blog](https://www.effect.website/blog/releases/effect/40-beta) **(official)**
- `babel-plugin-annotate-pure-calls` README: it adds `#__PURE__` to "top level call expressions and new expressions in assignment contexts"; target audience is libraries; warns "The plugin might break your code." — [babel-plugin-annotate-pure-calls](https://app.unpkg.com/babel-plugin-annotate-pure-calls@0.5.0/files/README.md)

### Inferences
- The pure-annotation pass exists because almost every Effect module-level binding is a call result (`dual(...)`, `Context.Tag(...)`, `Symbol.for(...)`, `Schema.Struct(...)`, `globalValue(...)`). Without `/* @__PURE__ */`, a bundler cannot prove those top-level calls are droppable, so an unused `Schema.Struct` or `Tag` would be retained for every importer. The Effect team solves this once at publish time, in `dist/`, so every consumer bundler (including esbuild and Bun, which do not infer purity) benefits. **(inference from sources above)**
- Two separate requirements. (a) *Type navigation*: "go to definition" lands on TypeScript source only when `.d.ts.map` files point at shipped `src/**/*.ts`; a rolled-up `.d.ts` or a tarball without `src` loses that, and affects only editor navigation. (b) *Readable JavaScript stack traces*: these need `.js.map` files whose `sources` resolve, either because `src/` ships or because the maps inline `sourcesContent`; a rolled-up declaration has no bearing on them. Effect ships both `src/` and both map kinds, which satisfies (a) and (b) at once. **(inference; see the source-map note under Q5)**
- v4 moving from `sideEffects: []` to an explicit allowlist shows the team treats `sideEffects` as a correctness contract: when they added a genuinely side-effectful module (`SchemaJITCompiler/enable`), they listed it rather than flipping the whole package. A library that bundles everything into one entry file cannot express "this one module is side-effectful" at file granularity. **(inference)**

### Gaps
- I did not find an Effect Days talk or a long-form post by Arnaldi/Smart/Canti specifically about *why not bundle*; the rationale is encoded in the repo config and in issue #1561 (see Q2), not in a standalone essay.
- The root `.babel.mjs.json` referenced by older build-utils docs 404s on `main`; v4 passes the plugin on the CLI instead, so no separate config was retrievable.

## Q2. Dual-instance hazard: what breaks if a library bundles `effect` into itself, and what the Effect team decided

### Takeaway
Two copies of `effect` in one process is a known, tracked hazard (issues #1479, #1561, #3308). The team explicitly called "folks bundling effect in their own libs" a bad idea, chose to *tolerate* duplicates via `globalValue`/string-keyed Tags/`Symbol.for` TypeIds, and in v3 added a runtime version check whose user-facing symptom is `RuntimeException: Cannot execute an Effect versioned X with a Runtime of version Y`. The `effect-language-service`/tsgo `duplicatePackage` diagnostic exists because duplicates "break `Context` lookups silently." **(official, GitHub issues + source)**

### Cited Findings
- Michael Arnaldi (2023-10-25), in the "CJS-ESM Hazard" issue: "Another scenario is folks bundling effect in their own libs, as much as this is a bad idea, some folks are worried about 'effect' as an explicit dependency and would like to bundle it. In such case we will be running multiple versions anytime the user is also running effect." — [Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561) **(official)**
- Same issue lays out the four packaging options (CJS-only / dual / dual+ESM-proxy / ESM-only) and the chosen "2.5": dual ESM/CJS *plus* isolating shared state with `globalValue("id", maker)`. Arnaldi: "It is a bit error prone as there is no check to know when we are allocating state and it's easy to forget." — [Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561)
- Tim Smart (2023-10-25): "Currently you can have two different versions of effect and still have a working app, because of the global value workaround." — [Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561)
- Arnaldi (2023-10-26) linking PR #1564: "it tracks versions and isolate state between different versions so effectively we can run two independent versions of effect without issues ... the only stateful piece of effect a client uses are tags and when tags have identifiers they become globally shared, note that tags are also using globalValue so they become versioned." — [Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561), [PR #1564](https://github.com/Effect-TS/effect/pull/1564)
- fubhy (2023-10-25) listing the breakage classes under duplication: `instanceof`, symbol identity, global state — "I cannot claim with certainty that we can prevent all potential runtime issues with the workarounds we've named so far (`globalValue`, avoiding `instanceof`, etc.)." — [Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561)
- Issue #1479 "Graceful handling of running multiple versions of Effect in the same project" (2023-10-04) was closed in favour of #1561. — [Effect-TS/effect#1479](https://github.com/Effect-TS/effect/issues/1479)
- Real-world report (2024-07-19): Next.js on Vercel threw `(FiberFailure) RuntimeException: Cannot execute an Effect versioned 3.5.6 with a Runtime of version 3.4.7` from a `.next/server/chunks/*.js` file; maintainer Max Brown: "this error occurs when you have duplicate versions of `effect` in your program, usually as a result of out-of-sync dependencies." Fixed by purging the Vercel build cache. — [Effect-TS/effect#3308](https://github.com/Effect-TS/effect/issues/3308)
- v3 source of that check (`fiberRuntime.ts`): it reads `(cur as core.Primitive)[core.EffectTypeId]._V` and logs "Executing an Effect versioned ${effectVersion} with a Runtime of version ${version.getCurrentVersion()}, you may want to dedupe the effect dependencies, you can use the language service plugin to detect this at compile time". — [effect@3.21.2 src/internal/fiberRuntime.ts](https://cdn.jsdelivr.net/npm/effect@3.21.2/src/internal/fiberRuntime.ts) (line ~1391)
- v3 mitigation mechanics (verified in source): `TagTypeId = Symbol.for("effect/Context/Tag")`, `TypeId = Symbol.for("effect/Context")` (global symbol registry, so TypeIds match across copies); Context lookups are keyed by the Tag's **string `key`** (`new Map([[tag.key, service]])`, `map.set(tag.key, service)`), and the error is `Service not found: ${tag.key}`. — [effect@3.21.2 src/internal/context.ts](https://cdn.jsdelivr.net/npm/effect@3.21.2/src/internal/context.ts)
- `GlobalValue` doc comment: "a single instance of a value is created globally, even when modules are imported multiple times (e.g., due to mixing CommonJS and ESM builds) or during hot-reloading"; the store is `globalThis["effect/GlobalValue"]` (a `Map`). — [effect@3.21.2 src/GlobalValue.ts](https://cdn.jsdelivr.net/npm/effect@3.21.2/src/GlobalValue.ts)
- tsgo / effect-language-service `duplicatePackage` diagnostic (V3/V4): "Duplicate packages cause services to have different identities in each copy, breaking `Context` lookups silently." Example: "Multiple versions of package 'effect' detected: 2.x.x, 3.x.x. Consider cleaning up your lockfile, or add 'effect' to allowedDuplicatedPackages". — [tsgo diagnostics (mintlify mirror)](https://mintlify.wiki/Effect-TS/tsgo/diagnostics/correctness); project: [Effect-TS/language-service](https://github.com/Effect-TS/language-service)
- v4 `effect/Version` module (added 4.0.2) exposes `getCurrentVersion`/`setCurrentVersion` "used in telemetry headers, resources, and scopes" with the gotcha "Applies to this copy of the module." — [Effect-TS/effect packages/effect/src/Version.ts](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/src/Version.ts)
- tshy README (cited by fubhy in #1561) frames duplication as unavoidable: "Dual Module Hazard is a fact of life anyway". — [isaacs/tshy](https://github.com/isaacs/tshy#dual-module-hazard-is-a-fact-of-life-anyway)

### Inferences
- Concretely, if a library inlines `effect` (not externalized): (a) services registered by the app's copy are found by the library's copy *only* because Tags are string-keyed and TypeIds use `Symbol.for` — any `Equal`/`Hash` structure or `instanceof` check against class identity (e.g. `Schema.Class`, `Data.TaggedError` subclasses, `Cause` constructors) will fail across copies; (b) `globalValue` state lives in a fixed `globalThis["effect/GlobalValue"]` map, and the cited v3.21.2 `fiberRuntime` registers under a non-versioned key, so two copies of `effect` on one page share that state regardless of version; what is version-scoped is only the runtime check in (c), not the global store; (c) in v3 the runtime logs/throws the version-mismatch message when the app's `Runtime` executes an effect primitive constructed by the other copy (#3308). **(inference from the source and issues above)**
- A GitHub code search for the v3 "Runtime of version" string on `main` (v4) returned only `Version.ts` and Otlp files, so the v4 fiber runtime appears to have dropped the cross-version runtime check; in v4 the detection story is the compile-time `duplicatePackage` diagnostic. **(inference; code search is fuzzy — see Gaps)**
- If `effect` and workspace deps are externalized, the "bundle" of a typical Effect library is just its own modules concatenated. That removes the *bundler-created* duplicate: the library no longer embeds its own copy. It does not guarantee a single instance in the consumer, because the consumer's dependency graph can still resolve two `effect` versions on its own (the v4 `duplicatePackage` diagnostic exists for exactly that case). What remains for the library is the Q3 tree-shaking question plus fewer files for the loader. **(inference)**

### Gaps
- Could not confirm with certainty that v4 removed the `_V` version check in the fiber runtime (GitHub code search is not exhaustive; I did not grep the whole v4 `internal/` tree).
- Found no GitHub issue where a *third-party library* shipped with `effect` inlined and a user reported the resulting breakage; the hazard is documented by maintainers in #1561 and via lockfile-duplicate reports (#3308), not by a bundled-library incident.

## Q3. Does bundling a library's own modules into one file per entry hurt consumer tree-shaking vs per-module files? (rollup/rolldown/esbuild/tsdown/e18e guidance)

### Takeaway
Bundler docs agree that a consumer's bundler can tree-shake *within* a single ESM file if the exports are statically analysable and side-effect-free, but the practical guidance from Rollup/Rolldown (`preserveModules`), tsdown (`unbundle`) and component-library experience is that per-module output tree-shakes more reliably and gives consumers the option to import individual modules; correctness of removal rests on `sideEffects` and `/* @__PURE__ */`, which a bundled file concentrates into one all-or-nothing module. **(official bundler docs + community opinion)**

### Cited Findings
- Rolldown `output.preserveModules` (default `false`): "separate chunks are created for all modules, using original module names as file names ... Tree-shaking will still be applied, suppressing files that are not used by the provided entry points or do not have side effects when executed and removing unused exports." Docs warn not to import those files directly "as expected exports may be missing"; declare entry points via `input`. — [rolldown.rs OutputOptions.preserveModules](https://rolldown.rs/reference/OutputOptions.preserveModules)
- Rolldown DCE docs: `"sideEffects": false` marks all files side-effect-free; arrays with globs are accepted; "CSS imports require explicit sideEffects configuration or risk removal"; plugins can override per-module via `moduleSideEffects`. — [rolldown.rs Dead Code Elimination](https://rolldown.rs/in-depth/dead-code-elimination)
- tsdown `unbundle` option: "each source file is compiled and transformed individually, and the output directory will contain a one-to-one mapping of your source files to output files"; recommended to "Avoid bundling all modules together, for example in monorepo or library scenarios where consumers may want to import individual modules". — [tsdown.dev unbundle](https://tsdown.dev/options/unbundle)
- tsdown positions itself as "The Elegant Library Bundler" with sensible defaults, `.d.ts` generation and multi-format output; it does not publish a "why bundle" argument beyond config simplicity and speed. — [tsdown.dev guide](https://tsdown.dev/guide/)
- Vite library mode: "make sure to externalize deps that shouldn't be bundled into your library" via `rolldownOptions.external`; recommends named exports from the entry. — [vite.dev Library Mode](https://vite.dev/guide/build#library-mode)
- Turborepo (Compiled Packages): "The majority of Compiled Packages should use tsc ... the application's bundler will prepare the library package for distribution." Use a bundler only for specific needs such as static assets. Compiled packages carry "More configuration: TypeScript compiler options and optimization settings like `sideEffects` need management." — [turborepo.dev Internal Packages](https://turborepo.dev/docs/core-concepts/internal-packages) **(official Vercel guidance)**
- Component-library field reports: a package "built with preserveModules ... will be able to tree-shake the rest of the code in the package, while if everything is bundled in one file webpack seems to be unable to tree-shake" (tsdx issue thread). — [lightrun mirror of jaredpalmer/tsdx preserveModules issue](https://lightrun.com/answers/jaredpalmer-tsdx-support-rollups-preservemodules) **(opinion/anecdote)**
- Carl Rippon's guide: ESM output + `sideEffects: false` is what makes a library tree-shakeable; "it is the consuming app doing the tree shaking and not the component library." — [carlrippon.com](https://carlrippon.com/how-to-make-your-react-component-library-tree-shakeable/) **(opinion)**
- esbuild on annotation risk: "The sideEffects field is particularly error-prone for developers because by default it causes all files in your package to be considered dead code if no imports are used. If you add a new file containing side effects and forget to update that field, your package will likely break." esbuild offers `--ignore-annotations` as a workaround. — [esbuild API: Ignore annotations](https://esbuild.github.io/api/#ignore-annotations)
- 2026 ecosystem summary: "package authors who want consumers to get optimal bundle sizes must publish ESM with named exports and set `sideEffects: false`." — [pkgpulse guide](https://www.pkgpulse.com/guides/package-size-optimization-tree-shaking-2026) **(secondary/opinion)**
- Vercel conformance rule `PACKAGE_JSON_SIDE_EFFECTS_REQUIRED`: workspaces should set `sideEffects` to `false` unless they have global side effects, in which case `true` or an array of globs. — [Vercel conformance docs](https://examples.vercel.com/docs/workflow-collaboration/conformance/rules/PACKAGE_JSON_SIDE_EFFECTS_REQUIRED)

### Inferences
- For an Effect library the "one chunk per entry" model interacts badly with the Q1 pure-annotation story: top-level `Context.Tag(...)`, `Schema.Struct(...)`, `Layer.effect(...)` in a single bundled file are all evaluated when *any* export is imported unless each is `/* @__PURE__ */`-annotated; with per-module files, unused modules are never loaded at all, so the annotation only has to be right for the modules that *are* imported. Per-module emit is therefore the more forgiving failure mode. **(inference)**
- Bundling your own modules while externalizing `effect` is safe for correctness but not strictly better for size: in a Node/Bun service nothing is tree-shaken at runtime anyway, and in a Next.js/Vite app the app bundler would have tree-shaken per-module files equally well (Rolldown/Rollup/Webpack 5 are the bundlers Effect lists as safe). **(inference)**

### Gaps
- No e18e-authored page stating "do/don't bundle libraries" was found; e18e's public material centres on dependency cleanup and lighter alternatives (podcast/summary pages only). Treat "e18e says X about bundling" as unverified.
- No controlled measurement comparing consumer bundle size for an Effect library shipped per-module vs single-chunk was found.

## Q4. Pure annotations: do rolldown/oxc, esbuild, Bun preserve `/* @__PURE__ */`, do any *insert* them, and is `babel-plugin-annotate-pure-calls` still the standard?

### Takeaway
All four mainstream tools **respect** `@__PURE__`/`#__PURE__` (and oxc/rolldown also `@__NO_SIDE_EFFECTS__`) on input; **none** of them infers purity for arbitrary library call patterns like `dual(...)`, `Schema.Struct(...)` or `Context.Tag(...)` — esbuild auto-annotates only JSX and configurable globals (`--pure:`), oxc's docs say it "does not inject" them. In 2026 the Effect team still runs `babel-plugin-annotate-pure-calls` over `dist/` after `tsc`, so that remains the de-facto standard for Effect libraries. **(official tool docs + Effect repo)**

### Cited Findings
- esbuild: "a special comment containing either /* @__PURE__ */ or /* #__PURE__ */ before a new or call expression means that that expression can be removed if the resulting value is unused ... Some expressions such as JSX and certain built-in globals are automatically annotated as /* @__PURE__ */ in esbuild. You can also configure additional globals to be marked /* @__PURE__ */ as well" (`--pure:document.createElement`). Effect of the annotation "only extends to the call itself, not to the arguments." Output example shows esbuild **re-emits** the comment in unminified output. — [esbuild API: Pure](https://esbuild.github.io/api/#pure) (note: an automated summariser incorrectly reported "pure comments are not respected"; the raw page text, verified by curl, says the opposite)
- esbuild: "Inline /* @__PURE__ */ comments before function calls tell esbuild that the function call can be removed ... The sideEffects field in package.json can be used to tell esbuild which files in your package can be removed"; `--ignore-annotations` disables both. — [esbuild API: Ignore annotations](https://esbuild.github.io/api/#ignore-annotations)
- Rolldown: `treeshake.annotations` (default `true`) controls respect for `/*@__PURE__*/` and related hints; `@__NO_SIDE_EFFECTS__` on a function declaration marks every call pure; `/* #__PURE__ */` accepted for tool compatibility. — [rolldown.rs InputOptions.treeshake](https://rolldown.rs/reference/InputOptions.treeshake), [rolldown.rs DCE](https://rolldown.rs/in-depth/dead-code-elimination)
- oxc minifier: "By default, Oxc minifier respects pure annotations" (`compress.treeshake.annotations`); supports `#__PURE__`/`@__PURE__` and `#__NO_SIDE_EFFECTS__`; "it only marks the function call itself and does not cover the arguments"; the minifier does **not** inject annotations. — [oxc.rs Dead Code Elimination](https://oxc.rs/docs/guide/usage/minifier/dead-code-elimination)
- oxc transformer has a tracked feature "add `/* @__PURE__ */` annotation for pure functions" (codspeed branch `02-28-feat_transformer_add____pure_____annotation_for_pure_functions`), scope appears limited to its own transforms (e.g. JSX/class-helper output), not user-library calls. — [codspeed oxc branch](https://codspeed.io/oxc-project/oxc/branches/02-28-feat_transformer_add____pure_____annotation_for_pure_functions) **(weak evidence; branch name only)**
- Bun bundler: `ignoreDCEAnnotations` — Bun "recognizes dead code elimination/tree-shaking annotations such as @PURE and package.json 'sideEffects' fields"; the option disables them "as a temporary workaround for incorrect annotations." — [bun.com BuildConfig.ignoreDCEAnnotations](https://bun.com/reference/bun/BuildConfig/ignoreDCEAnnotations)
- Effect (v4, 2026) still emits with `tsc` then `babel dist --plugins annotate-pure-calls`; `@effect-atom/atom` (v3 toolchain) runs `babel build --plugins annotate-pure-calls`. — [effect package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json), [effect-atom package.json](https://raw.githubusercontent.com/tim-smart/effect-atom/main/packages/atom/package.json)
- `babel-plugin-annotate-pure-calls` annotates "top level call expressions and new expressions in assignment contexts"; README warns it "might break your code." — [README](https://app.unpkg.com/babel-plugin-annotate-pure-calls@0.5.0/files/README.md)
- Alternative: `rollup-plugin-tree-shakeable` adds `@__PURE__` to top-level expressions as a Rollup plugin. — [TomerAberbach/rollup-plugin-tree-shakeable](https://github.com/TomerAberbach/rollup-plugin-tree-shakeable) **(community tool)**

### Inferences
- If a beep-effect package is bundled with tsdown/rolldown or Bun, *existing* `/* @__PURE__ */` comments in the externalized `effect` dependency are irrelevant (not bundled) and the package's **own** top-level `Context.Tag`, `Schema.*`, `dual`, `Layer.*` calls will have no annotations unless a post-pass adds them. Options: keep the Babel pass over the bundler output; annotate by hand (`/* @__PURE__ */` at call sites or `@__NO_SIDE_EFFECTS__` on local factory functions); or accept that unused module-level values survive consumer tree-shaking. **(inference)**
- oxc/rolldown have *not* replaced `babel-plugin-annotate-pure-calls` for library authors as of 2026-10; they are consumers of annotations, not producers. **(inference from docs)**

### Gaps
- No tsdown/rolldown option equivalent to "annotate all top-level calls as pure" was found in their docs.
- No measurement of how much bundle size Effect's annotation pass saves for consumers was found.

## Q5. Runtime performance: bundling vs many small ESM files for Node/Bun startup; hot-path effects

### Takeaway
Module-graph size (file count, IO, parse) is a measured driver of Node CLI startup; bundling is the recognised remedy and can cut hundreds of ms, with a crossover where one giant file parses slower than a few chunks. No Effect-specific or Bun-specific numbers were found; hot-path performance is not affected by file layout. **(community measurements; no official Effect data)**

### Cited Findings
- Pedro Piñera (2022-12-23): "there's a strong correlation between the size of the graph and the time it takes to load" since loading "entails doing IO and in-memory parsing operations"; ESM CLIs "can end up ... slow to launch (above hundreds of milliseconds)"; remedies in order: fewer deps, dynamic imports, subpath exports, and "as a last resort" bundling/tree-shaking with the caveat of runtime-failure risk needing integration tests. — [pepicrft.me Startup time in Node CLIs](https://pepicrft.me/blog/startup-time-in-node-clis/)
- Marvin Hagemeister (2023-03-19), profiling `npm run`: ~400 ms baseline, "module loading consumed the majority of execution time"; after lazy-loading and dependency removals ~138 ms; a minimal re-implementation ran in ~22 ms; concludes "Bundling code when publishing to npm represents the most viable current workaround" for eager module graphs. — [marvinh.dev Speeding up the JavaScript ecosystem part 4](https://marvinh.dev/blog/speeding-up-javascript-ecosystem-part-4/)
- Counter-point from the same search set: "The bigger the file, the longer it takes to parse it, so there will be a threshold after which the parse cost of a single gigantic file is higher than splitting it up"; an 11.3 MB single-file bundle "takes ~300ms to parse before any application code executes." — [claudeissues.com issue summary](https://claudeissues.com/issue/29481-feature-bundle-architecture-improvements-lazy-loading-async-i-o-platform-specifi) **(secondary; anecdotal)**
- Jest users report slowness "when importing from a big esm bundle" (transform cost on large single files). — [lightrun mirror of facebook/jest thread](https://lightrun.com/answers/facebook-jest-slow-when-importing-from-a-big-esm-bundle) **(anecdotal)**
- Effect `3.12` (2024-12-23) added `Effect.fnUntraced` "for when performance is critical" — indicating trace capture (Error.stack) is the measurable hot-path cost in Effect, not module layout. — [Effect 3.12 release](https://effect.website/blog/releases/effect/312) **(official)**

### Inferences
- For a long-running Node/Bun server or Next.js route the startup delta of per-module emit is a one-time cost of tens to a few hundred ms and immaterial; for a CLI invoked repeatedly (beep CLI) bundling the CLI *entry* (externalizing nothing, or externalizing only native deps) is where the gain lives — and that is an app-bundling decision, not a library-publishing one. **(inference from sources)**
- Bun's loader is faster per file than Node's but the graph-size correlation still holds; absence of Bun-specific data is a gap, not evidence of no effect. **(inference)**

### Gaps
- No published numbers from Vite, oxlint (Rust binary; not applicable), or any Effect-based CLI quantifying startup gains from bundling were found.
- No benchmark for "1000 small ESM files vs 10 chunks" on Node 22+/Bun 1.x was found.

## Q6. Source maps and debugging in bundled vs emitted Effect libraries

### Takeaway
The Effect team ships `src/`, `.js.map`, `.d.ts` and `.d.ts.map` so stack traces and go-to-definition resolve to TypeScript source; Effect 3.12+ stack traces include the *definition site* of `Effect.fn` functions, which only stays readable if the published artefact maps back to source. Bundled libraries can match this only if they emit source maps with `sourcesContent`/`sources` resolvable and keep declaration maps (rolled-up `.d.ts` loses `declarationMap`). **(official repo config + inference)**

### Cited Findings
- Effect publishes `src/**/*.ts`, `dist/**/*.js.map`, `dist/**/*.d.ts.map`; `tsconfig.base.json` sets `declarationMap: true`, `sourceMap: true`. — [effect package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json), [tsconfig.base.json](https://raw.githubusercontent.com/Effect-TS/effect/main/tsconfig.base.json)
- Effect 3.12: "Stack traces will now include the location where the function was defined, not just where it was called"; example shows definition site `4:29` and call site `9:1`. — [Effect 3.12 release](https://effect.website/blog/releases/effect/312)
- Sentry maintains an Effect-specific source-maps guide (upload maps so bundled stack traces are readable). — [docs.sentry.io Effect source maps](https://docs.sentry.io/platforms/javascript/guides/effect/sourcemaps/)
- `@savvy-web/bun-builder` (used by `@effected/*`): default is "Bundled output with rolled-up .d.ts via API Extractor"; `bundle: false` preserves "the source directory structure in output ... raw .d.ts files are emitted directly (no DTS rollup)". — [savvy-web/bun-builder](https://github.com/savvy-web/bun-builder)
- Vercel/Next.js dual-copy failure in #3308 surfaced as `at /var/task/website/.next/server/chunks/76767.js:3:111012` — a bundled, minified location with no useful frame, illustrating debuggability loss when maps are absent. — [Effect-TS/effect#3308](https://github.com/Effect-TS/effect/issues/3308)

### Inferences
- `Effect.fn` captures `Error.stack` at definition and call sites; in a bundled library without published `sources`, those frames point into `dist/index.js:1:NNNNN`. Node (`--enable-source-maps`) and Bun apply source maps to `Error.stack` only when the `.map` and its `sources`/`sourcesContent` are reachable, so a bundler config must keep `sourcemap: true` and either inline `sourcesContent` or publish `src/`. **(inference)**
- DTS rollup (API Extractor/tsdown `dts` bundling) produces one `.d.ts` without `declarationMap`, so WebStorm "go to definition" lands in the rolled-up declaration instead of source — a DX regression relative to the Effect-team layout. **(inference)**

### Gaps
- No first-hand DX reports comparing Effect fiber stack traces through a bundled vs an emitted library were found.

## Q7. Monorepo-internal consumption: built dist vs raw `src` for a Next.js app importing many workspace packages (Turborepo/Vercel guidance 2025–2026)

### Takeaway
Turborepo's current docs define three strategies — Just-in-Time (app transpiles `src`), Compiled (package runs `tsc`; "the majority of Compiled Packages should use tsc"), Publishable — and recommend JIT only when you accept no Turbo caching and cross-package type-error leakage; Next.js 16 Turbopack auto-transpiles workspace packages so `transpilePackages` is mainly for `node_modules` TS/JSX or webpack Pages Router. **(official)**

### Cited Findings
- JIT packages: compiled "by the application that uses it"; use when apps use "a modern bundler like Turbopack, webpack, or Vite", you "want to avoid configuration", and are "satisfied with your applications' build times, even when you can't hit cache for the package". Tradeoffs: "Turborepo cannot cache a build for a Just-in-Time Package"; type errors in a dependency fail the dependent's type-check; cannot use TypeScript `paths`. — [turborepo.dev Internal Packages](https://turborepo.dev/docs/core-concepts/internal-packages)
- Compiled packages: "handle its own compilation using a build tool, like tsc"; "The majority of Compiled Packages should use tsc ... the application's bundler will prepare the library package for distribution"; use a bundler only for special needs like static assets; costs are "more configuration" incl. `sideEffects`; benefit is Turbo caching. — [same](https://turborepo.dev/docs/core-concepts/internal-packages)
- Next.js 16.4 (`lastUpdated: 2026-05-27`): "Turbopack transpiles workspace packages (npm, pnpm, or Yarn workspaces) in your monorepo automatically under both routers. Webpack does the same for the App Router." Use `transpilePackages` when "A `node_modules` dependency ships raw TypeScript or JSX", for webpack Pages Router with sources outside the app dir, or to bundle a Pages Router server dep. A package "cannot appear in both `transpilePackages` and `serverExternalPackages`". — [nextjs.org transpilePackages](https://nextjs.org/docs/app/api-reference/config/next-config-js/transpilePackages)
- Next.js package-bundling guide: "Performance can be impacted if external packages are not pre-bundled, for example, if imported from a monorepo or node_modules"; `transpilePackages` is the bundling opt-in. — [nextjs.org Package Bundling](https://nextjs.org/docs/pages/guides/package-bundling)
- Effect's own repo uses the dev-vs-publish pattern: `exports` points at `./src/*.ts` in the workspace and `publishConfig.exports` rewrites to `./dist/*.js` for publishing. — [effect package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json)
- `@effected/semver` does the same: workspace `exports: { ".": "./src/index.ts" }`, `publishConfig.directory: "dist/dev/pkg"`, `sideEffects: false`, `effect` as peer. — [spencerbeggs/effected packages/semver/package.json](https://raw.githubusercontent.com/spencerbeggs/effected/main/packages/semver/package.json)

### Inferences
- For beep-effect's Next.js apps the Vercel-aligned default is Compiled-with-`tsc` (per-module `dist/`), since the app bundler (Turbopack/webpack 5) is on Effect's list of deep-scope-analysis bundlers and will tree-shake per-module files; bundling the workspace lib first adds a stage whose only consumer benefit would be fewer files, which Next.js re-bundles anyway. **(inference)**
- JIT (`src` via `exports`/`publishConfig` swap) is what Effect and `@effected` use *inside* their own monorepos; it trades Turbo cache hits for zero build steps, and surfaces in Next.js through Turbopack's automatic workspace transpilation (no `transpilePackages` needed under Next 16). **(inference from docs)**

### Gaps
- No 2025–2026 benchmark comparing Next.js build time for N workspace packages consumed as `src` vs `dist` was found.

## Q8. Community exemplars: which Effect-ecosystem libraries bundle vs emit, and their rationale

### Takeaway
The Effect core and Tim Smart's libraries emit per-module with `tsc` + Babel pure-annotations (v3 via `@effect/build-utils pack-v2`, v4 via `tsc -b` + `babel`); `@effect-aws/*` uses projen with `main/module/types` triple pointing at `build/{cjs,esm,dts}/index.js` and `sideEffects: []`; Spencer Beggs's `@effected/*` builds with `@savvy-web/bun-builder` (Bun bundler, rolled-up `.d.ts`, `effect` as peer, `sideEffects: false`) with speed/zero-config as the stated rationale. No exemplar inlines `effect`. **(verified package.json files)**

### Cited Findings
- `effect@4.0.2`: `tsc -b` → `babel dist --plugins annotate-pure-calls`; ESM-only; per-module wildcard exports; `sideEffects` allowlist. — [package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json)
- `@effect-atom/atom@0.7.1` (Tim Smart): `build-utils prepare-v2` / `tsc -b` / Babel CJS transform / Babel `annotate-pure-calls` / `build-utils pack-v2`; `sideEffects: []`; `publishConfig.directory: "dist"`; `effect ^3.22.1`, `@effect/platform`, `@effect/rpc`, `@effect/experimental` as peers. — [package.json](https://raw.githubusercontent.com/tim-smart/effect-atom/main/packages/atom/package.json)
- `@effect-aws/client-s3` (floydspace): projen-driven (`npx projen build`); `type: module`, `main: build/cjs/index.js`, `module: build/esm/index.js`, `types: build/dts/index.d.ts`; `sideEffects: []`; peer `effect: ">=4.0.0-beta.66 <5.0.0"`. — [package.json](https://raw.githubusercontent.com/floydspace/effect-aws/main/packages/client-s3/package.json)
- `@effected/semver@0.11.0` (spencerbeggs/effected): `build:dev`/`build:prod` = `node savvy.build.ts --target …`; workspace `exports` → `./src/index.ts`; `publishConfig.directory: dist/dev/pkg`; `sideEffects: false`; peer `effect: catalog:effect:peers`. Repo has ~40 packages (app, cli, config-file, jsonc, schema-org, semver, toml, yaml, xdg …). — [packages/semver/package.json](https://raw.githubusercontent.com/spencerbeggs/effected/main/packages/semver/package.json), [repo](https://github.com/spencerbeggs/effected)
- `@savvy-web/bun-builder` (same author's org): "Build modern ESM Bun libraries with minimal configuration"; "Bundled output with rolled-up .d.ts via API Extractor"; `bundle: false` mode emits per-file; rationale "Sub-Second Builds — Bun's native bundler" and "Zero Configuration — Auto-detects entry points from package.json exports"; resolves `catalog:`/`workspace:` protocols for publishing; Effect not mentioned. — [savvy-web/bun-builder](https://github.com/savvy-web/bun-builder)
- Anthony Fu's widely cited post is **pro-bundling for libraries** (tsup/unbuild) but is dated 2021-11-29 and pre-dates tsdown and the ESM-only shift; it argued for dual CJS+ESM at the time. — [antfu.me Publish ESM and CJS](https://antfu.me/posts/publish-esm-and-cjs) **(opinion, dated)**
- Effect maintainers' own 2023 decision (#1561) considered ESM-only, dual, and proxy strategies for the core library and never proposed bundling. — [Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561)

### Inferences
- The split in the ecosystem is "Effect-team toolchain (tsc + annotate-pure-calls, per-module)" vs "Bun/tsdown bundlers for speed and single-entry simplicity" — and the bundler camp still externalizes `effect` (peer dep) and sets `sideEffects: false`; nobody inlines Effect. **(inference from the five package.json files)**
- Projects on the bundler path (`@effected/*`) have small single-entry packages (`"."` only), where single-chunk output costs little tree-shaking; beep-effect packages with many subpath entries and many `Context.Tag`/`Schema` module-level values are closer to the Effect-core shape where per-module emit + pure annotations is the lower-risk choice. **(inference)**

### Gaps
- `@uploadthing/*`, `effect-http`, `@okfit/*` and `@savvy-web/*` build configs were not individually inspected (budget); `okfit` is a spencerbeggs repo and likely shares the bun-builder pipeline but this is unverified.
- No written rationale from Spencer Beggs or floydspace on *why* bundle vs emit for Effect was found; bun-builder's README gives generic speed/zero-config reasons only.
- `savvy.build.ts` in `effected` 404s at `main` root (likely lives elsewhere), so the exact bun-builder options (bundle vs unbundle, externals) used by `@effected/*` were not confirmed.
