## Key Question 1 — What does `@savvy-web/bundler` 2.4.x do end to end? What are the concrete steps of `build()` for `--target dev` vs `--target prod`, and what differs in output?

### Takeaway
`build()` is a thin front door (`defineBuild` + `runBuild`) that reads the package's own `package.json` `exports`/`bin` to derive tsdown entries, then runs **per target group** a tsdown **JS pass** (`unbundle: true` = per-module output, `dts: false`), a **bundled-declarations pass** (one self-contained `.d.ts` per public entry via `rolldown-plugin-dts` with `generator: "tsc"`), and — for prod only — a third **per-module declarations pass** feeding an **API Extractor meta pass**, plus a `targets.json` binding and declaration-map stripping. A rolldown `generateBundle` plugin emits the transformed `package.json` + `LICENSE` + `README.md` into `dist/<target>/pkg`. Every dev/prod run also writes `dist/<target>/issues.json`. Dev: sourcemaps on, never minified, `catalog:`/`workspace:` specifiers preserved, output `dist/dev/pkg`. Prod: sourcemaps off, minify opt-in (default off), specifiers resolved to concrete ranges, output `dist/prod/<group>/pkg` (default group `npm`), api-model emitted, `.d.ts.map` stripped.

### Cited Findings

**Front door and argument parsing**
- `build(input, overrides)` = `runBuild(defineBuild(input), { cwd: dirname(process.argv[1]), argv: process.argv.slice(2), ...overrides })`. Documented: "`cwd` is the directory of the entry script (`process.argv[1]`) — the faithful equivalent of the old `import.meta.dirname`" — `.../@savvy-web/bundler/run.js` (function `build`).
- `parseArgs` accepts `--target dev|prod|meta|exe`, `--watch`, `--no-exe`, `--verbose`; default target is `dev` — `.../@savvy-web/bundler/config.js`.
- `defineBuild` defaults: `formats: ["esm"]`, `externals: []`, `minify: false`, `devManifest: "preserve"`, `transform: defaultManifestTransform`, `emitDts: true` — `.../@savvy-web/bundler/config.js`.
- Package scripts in every effected package: `"build:dev": "node savvy.build.ts --target dev"`, `"build:prod": "node savvy.build.ts --target prod"`, `"prepare": "turbo run build:dev"`, `"types:check": "tsc --noEmit"` — `~/YeeBois/references/effect/effected/packages/semver/package.json`. These run under Node's native TS stripping (README: "run them with Node's native TypeScript support (Node 24.11+)") — bundler README; `engines.node >=24.11.0` in semver's manifest.

**`runBuild` orchestration (in order)** — all from `.../@savvy-web/bundler/run.js`:
1. Read `package.json` at `cwd`; `version`, `name`.
2. Create a `BuildCollector` (diagnostics) and a best-effort `writeIssuesArtifact` closure invoked on both success and failure paths (only for `dev`/`prod` targets).
3. Resolve JSX from tsconfig (`readTsconfigJsx` + `resolveJsxConfig`), then `writeResolvedTsconfig` → a temp tsconfig with absolute paths (see dts section).
4. Read `publishConfig.targets`; run the Effect-based `ConfigValidator` service (`Effect.runPromise(... Effect.provide(ConfigValidator.layer))`) to fast-fail on bad `targets`/`exe`/`meta`/`looseFiles`.
5. `packageJsonEntries({ pkg: { exports, bin } })` → `Record<entryName, sourcePath>`; `extractAmbientDts` for hand-authored `.d.ts` exports; `assertNoEntryCollisions`.
6. `--target meta` → prints deprecation and returns (no-op). `--target exe` → `runExeBuild` into `dist/dev/pkg/bin` and returns.
7. Compute override partitions (`overrides[]` → per-entry `format`/`bundle`/`platform`/`css`/`outSubdir`).
8. Groups: `dev` → single group `{ id: "dev", name: packageName }`; `prod` → `deriveProdGroups(publishConfig.targets ?? { npm: true })` → one byte-variant group per distinct name (default one group `npm`).
9. `buildTargetGroups({...})` with `emitDeclarations: true` only when `target === "prod"`.
10. prod only: `writeTargetsBinding(cwd, resolution)` → `dist/prod/targets.json`.
11. prod only (unless `meta === false` or `emitDts === false`): `runMetaPass({ ci: process.env.CI === "true" || GITHUB_ACTIONS === "true", ... })`.
12. prod only: `removeDeclarationMaps(dist/prod/<g>/pkg)` for each group.
13. Optional SEA compile per group (`exe` config) into `<pkg>/bin`.
14. Write `issues.json`; render the report (`renderReport` via `ReportPipeline`, formats terminal/json/markdown/ci-annotations/silent).

**Per-target tsdown options** — `.../@savvy-web/tsdown-plugins/build/target-groups.js`:
- `outDirFor`: `dev` → `dist/dev/pkg`; otherwise `dist/prod/<group>/pkg`.
- JS pass (`deriveTargetGroupOptions`): `sourcemap: !isProd`, `minify: isProd && (options.minify ?? false)`, `format` (default `["esm"]`), `unbundle: !(bundleNodeModules ?? false)`, `clean: true`, `platform: "node"` (default), `fixedExtension: false`, `dts: false`, `define: { "process.env.__PACKAGE_VERSION__": JSON.stringify(version), ...define }`, `cjsDefault: true` when cjs.
- Bundled-dts pass (`deriveDtsPassOptions`): same outDir, `sourcemap: false`, `unbundle: false`, `clean: false`, drops `bin/*` entries, `dts: { tsconfig, emitDtsOnly: true, generator: "tsc" }`.
- Per-module declarations pass (`deriveDeclarationsPassOptions`): `outDir: dist/prod/<group>/declarations` (a sibling of `pkg/`, "NOT published, used only as API Extractor's diagnostics-run input so locations resolve to per-file source. Kept (not stripped) as a cacheable, inspectable build artifact (issue #162)"), `unbundle: true` ("preserveModules → 1:1 source positions"), esm-only.
- `buildTargetGroups` loop (`.../build/build-target-groups.js`): lazily `import("tsdown").build`; for each group and partition: (a) JS pass with `plugins: [emitManifest (base partition only), cjs interop plugins if cjs, extraPlugins, metrics]` and `deps: { neverBundle: externals, alwaysBundle: bundle }`; (b) skip dts if `emitDts === false`; otherwise **one tsdown dts build per entry** (`entry: { [entryName]: entrySource }`), with a "re-export stub" shortcut: a secondary entry that is a pure named re-export subset of `index` is written as a thin `export { … } from "./index.js"` stub instead of re-rolling; (c) prod + `emitDeclarations` → the per-module declarations pass (failure downgraded to a warning); (d) `looseFiles` extra passes; (e) `copyPublicDir(public/ → pkg/)` and `copyAmbientDts`.
- `dtsDeps`: `neverBundle: [...externals, ...dtsExternals]`; `bundledPackages` → `dts: { alwaysBundle }` with `neverBundle: true` for everything else unless `bundleNodeModules`.

**Dev vs prod differences (observable)**
- Sourcemaps: dev emits `.js.map` next to every module (observed `App.js.map`, `AppConfig.js.map`, `internal/filename.js.map` in `~/YeeBois/references/effect/effected/packages/app/dist/dev/pkg/`); prod sets `sourcemap: false` (`target-groups.js`).
- Declaration maps: the dts tsconfig overlay forces `declarationMap: true` (`dts/resolved-tsconfig.js` `DTS_OVERLAY`); dev keeps `index.d.ts.map` (observed in `app/dist/dev/pkg`); prod strips `.d.ts.map`/`.d.cts.map` after meta generation — `strip-maps.js`: "they are dead weight in a PUBLISHED package — they reference `.ts` sources the tarball does not ship — and they leak local source paths, so the prod build strips them AFTER meta generation has consumed them. The dev build keeps them (it is never published...)".
- Minify: "Prod output is not minified by default. This builder targets Node libraries, where readable output matters more than bundle size — minified code degrades stack traces and trips some security scanners. Set `minify` to opt back in... dev is never minified" — bundler README, "Minified output".
- Manifest specifiers: "`--target dev` writes `dist/dev/pkg`, the local-link target with `catalog:`/`workspace:` specifiers preserved. `--target prod` writes `dist/prod/npm/pkg` with those specifiers resolved to concrete ranges, ready to publish — and emits the API Extractor api-model alongside it." — bundler README. Implementation: `buildEmittedManifest` resolves only when `targetGroup.isProd || devManifest === "resolve"` and the manifest actually has `catalog:`/`workspace:` specs (`manifest/emit-manifest.js`); resolution delegates to `@effected/workspaces`' `Workspaces.resolveManifest` with `@effect/platform-node` layers (`catalog/resolve-catalogs.js`). Observed dev output still carries `"effect": "catalog:effect:peers"` and `"@effected/glob": "workspace:^"` (`app/dist/dev/pkg/package.json`).
- API model: prod only, written to `dist/prod/<group>/meta` (`<unscoped>.api.json`, `tsdoc-metadata.json`, resolved `tsconfig.json`) and copied into `meta.localPaths` — bundler README, "API Extractor meta". Forgotten exports fail the build under CI, warn locally; `tsdoc.suppressWarnings` suppresses both — same section.
- `optimistic` (default `"auto"`) forward-looks the meta bundle's version from pending changesets; off under CI — bundler README.
- Pure annotations: the built dev JS contains **zero** `@__PURE__` markers in a real module (`grep -c '@__PURE__' app/dist/dev/pkg/AppConfig.js` → 0; `index.js` → 0). The bundler does not run `babel-plugin-annotate-pure-calls` or any equivalent; nothing in the README or source mentions pure annotation.
- `issues.json`: written to `dist/<target>/issues.json` "on every build, successful or failed... so an agent or CI script reads the diagnostics straight from disk instead of parsing terminal output. The artifact lands through a temp file and a rename" — tsdown-plugins README. Observed shape: `{"generatedAt","package","target","buildOk":true,"warnings":[],"errors":[],"suppressed":[]}` (`~/YeeBois/references/effect/effected/packages/commands/dist/dev/issues.json`). README warns: "a crashed build leaves `warnings`, `errors` and `suppressed` empty, which is byte-for-byte what a clean build writes, so empty buckets alone prove nothing" → read `buildOk` first.

**`tsconfig/ecma.json` base** — `.../@savvy-web/bundler/tsconfig/ecma.json`: `target: "es2025"`, `module`/`moduleResolution: "nodenext"`, `lib: ["esnext"]`, `types: ["node"]`, `strict`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `isolatedModules: true`, `isolatedDeclarations: false`, `declaration: true`, `declarationMap: false`, `sourceMap: false`, `composite: false`, `incremental: true`, `tsBuildInfoFile: ${configDir}/dist/.tsbuildinfo.lib`, `jsx: "preserve"`; includes `src/**`, `lib/**`, `__test__/**`, root `*.ts`, `public/**/*.json`. Header comment: "types and lib REPLACE the base list rather than merging with it." Each effected package's `tsconfig.json` is just `{"extends": "@savvy-web/bundler/tsconfig/ecma.json"}` (`packages/semver/tsconfig.json`); repo root extends `@savvy-web/silk/tsconfig/node/root.json` with `skipLibCheck: true` (`~/YeeBois/references/effect/effected/tsconfig.json`; the override exists only for a broken `vitest@5.0.0` `.d.ts` — `okf/gotchas/vitest-broken-dts-needs-skiplibcheck.md`).
- Dts-pass tsconfig: `buildResolvedTsconfig` resolves the package's `tsconfig.json` through `@effected/tsconfig-json`'s `TsconfigLoaderSync` (honouring `extends` and `${configDir}`), overlays `declaration: true, declarationMap: true, emitDeclarationOnly: false, composite: false, incremental: false, tsBuildInfoFile: undefined`, fixes `include` to `src/**/*.{ts,mts,tsx}`, `types/*.d.ts`, `package.json`, writes it to the OS temp dir ("so type declarations emit cleanly under pnpm symlinks" — tsdown-plugins README). A second `tsconfig-dts-emit-*.json` adds `stableTypeOrdering: true` "so a multi-union `.d.ts` (e.g. an Effect `Layer.Layer<…>` requirement channel) does not flip member order across otherwise-identical builds (#156)"; kept separate because "`@microsoft/api-extractor` pins `typescript ~5.9`, which predates the flag" — `dts/resolved-tsconfig.js`.

### Inferences
- Target naming: README and `run.js` agree that prod output is `dist/prod/<group>/pkg` (default `dist/prod/npm/pkg`), not a flat `dist/prod/pkg`. The task brief's "dist/prod" is the parent; the publishable tarball root is `dist/prod/npm/pkg`.
- `unbundle: true` (tsdown's preserve-modules mode) is the default because `bundleNodeModules` defaults to false; so JS structure mirrors `src/` (observed: `app/dist/dev/pkg/{index,App,AppCache,AppConfig,AppStore}.js` + `internal/*.js`; yaml has 42 `.js` files and exactly 1 `.d.ts`).
- There are three tsc program loads per prod build (bundled dts, per-module declarations, api-extractor), which is why `emitDts: false` is advertised as cutting "a ~13s/build cost" (`index.d.ts` JSDoc on `emitDts`).

- I did not find the raw `build()` source (`src/run.ts`) on GitHub; findings come from the shipped, readable `run.js` (not minified) which is functionally the same.
- No prod build (`dist/prod/**`) existed in the local checkouts, so the prod manifest, `targets.json` and `meta/` outputs were not inspected directly; their shape is taken from README + source + the `packed-install-pack-source.md` probe (which did pack real `dist/prod/npm/pkg` trees).

## Key Question 2 — What is in `dist/dev/pkg` that makes it the publish directory? How does the manifest transform rewrite `exports`/`main`/`types`/`files`, remove `devDependencies`, drop `private`?

### Takeaway
Source manifests are deliberately `"private": true` with `exports: { ".": "./src/index.ts" }`; `publishConfig: { access: "public", directory: "dist/dev/pkg", linkDirectory: true, targets: { npm: true } }`. pnpm honours `publishConfig.directory`/`linkDirectory`, so workspace consumers link to the built `dist/dev/pkg` (not `src/`), and `pnpm pack`/`publish` from source would pack the **dev** build. The transform (`transformManifest`) flips `private` to `!(publishConfig.access === "public")`, strips `publishConfig`, `scripts`, `devDependencies`, `bundleDependencies`, `packageManager`, `devEngines`, rewrites every TS export target to `{ types, import, [require], default }` conditions keyed off the export key, adds `./package.json`, rewrites `bin`, and sorts keys. `main`/`types`/`files` are not synthesised — the packages don't use them. The actual release, however, publishes from `dist/prod/npm/pkg` via silk-release-action, not from `dist/dev/pkg`.

### Cited Findings
- Source manifest shape (`~/YeeBois/references/effect/effected/packages/semver/package.json`): `"private": true`, `"sideEffects": false`, `"type": "module"`, `"exports": { ".": "./src/index.ts", "./package.json": "./package.json" }`, `devDependencies: { "@effect/vitest": "catalog:effect", "@savvy-web/bundler": "^2.4.24", "@types/node": "catalog:build", "effect": "catalog:effect", "typescript": "catalog:build" }`, `peerDependencies: { "effect": "catalog:effect:peers" }`, `publishConfig: { access: "public", directory: "dist/dev/pkg", linkDirectory: true, targets: { npm: true } }`. No `main`, `types`, or `files` fields.
- Built dev manifest (`~/YeeBois/references/effect/effected/packages/app/dist/dev/pkg/package.json`): `"private": false`; `exports: { ".": { types: "./index.d.ts", import: "./index.js", default: "./index.js" }, "./package.json": "./package.json" }`; `peerDependencies` retained with `workspace:^` / `catalog:effect:peers` intact; `devDependencies`, `scripts`, `publishConfig` gone; `engines`, `sideEffects`, `repository`, `homepage`, `keywords`, `author`, `license` retained.
- `transformManifest` (`.../tsdown-plugins/manifest/transform.js`): `const { publishConfig, scripts, ...rest } = pkg; const isPrivate = !(publishConfig?.access === "public"); result = { ...rest, private: isPrivate }` → then `transformExports`, add `"./package.json": "./package.json"` if missing, `transformBin`, user/default `transform`, `normalizeBinPaths` ("npm 11.x drops ./-prefixed bins"), `PackageJsonFormat.sortValue(result)`.
- `defaultManifestTransform` strips `NON_PUBLISHED_FIELDS = ["devDependencies","bundleDependencies","scripts","publishConfig","packageManager","devEngines"]`; comment: "they describe how the package is BUILT/DEVELOPED, not how it is CONSUMED... This is the pattern nearly every package repeated by hand (inherited from rslib-builder); `defineBuild` now applies it automatically" — same file.
- `transformExports`: a TS string target becomes `tsConditions(exportKey)` = `{ types: ./<entry>.d.ts, import: ./<entry>.js, [require: ./<entry>.cjs], default: ./<entry>.js }`; "The output path is derived from the export KEY via the shared entry-name function, never from the source path"; `.` → `index`, nested subpaths flatten to dashes (`./changesets/markdownlint` → `changesets-markdownlint.js`); `.json` and `.d.ts` keys pass through (with `./public/` prefix stripped); ambient `.d.ts` exports become `{ types }` only; `emitDts: false` omits `types` — same file. The trailing `default` condition exists because "Node's require() matches `node`/`require`/`default` but never `import`, so an import-only map dies with ERR_PACKAGE_PATH_NOT_EXPORTED even where require(esm) works" (changelog 2.1.0: "Emit a trailing `default` exports condition mirroring the `import` target" — https://raw.githubusercontent.com/savvy-web/systems/main/packages/tsdown-plugins/CHANGELOG.md).
- `transformBin`: TS bin targets → `bin/<command>.js` (string form → `bin/cli.js`) — same file. Entry extraction maps `bin` to tsdown entries `bin/<command>` and `exports` to `index`/flattened names; `/dist/*.js` targets are resolved back to `/src/*.ts` — `.../entry/extract.js`.
- `emitManifest` is a rolldown plugin whose `generateBundle` emits `package.json` (tab-indented) plus `LICENSE` and `README.md` as assets — `.../manifest/emit-manifest.js`. Observed: `LICENSE` and `README.md` present in `app/dist/dev/pkg`.
- `files` handling: only touched to append `bin/<exe>` for SEA builds (`transformManifest` exeRewrite branch). Everything in `pkg/` is the tarball root, so `files` is unnecessary.
- Publishability signal convention: "Every source manifest in this repo sets `"private": true`, intentionally, on all thirty-one publishable packages... The machine-checkable publishability signal is `publishConfig.access === "public"`... never 'fix' a source manifest's `"private": true` believing it blocks a release — it does not" — `okf/conventions/publishability-signal.md`. Mirrored in `CLAUDE.md`: "The bundler's `publishConfig` transform produces the publishable manifest at build time, and publishability is `publishConfig.access === "public"`."
- Why `dist/dev/pkg` is `publishConfig.directory`: "`publishConfig.linkDirectory: true` with `directory: dist/dev/pkg` means pnpm links a workspace `@effected/*` dependency into its consumer's `node_modules` pointing at the dependency's `dist/dev/pkg`, not its source (for example `node_modules/@effected/npm -> ../../../npm/dist/dev/pkg`). So the dependency must be **built** before the consumer can import it... The fix is the `prepare` pattern: ... `"prepare": "turbo run build:dev"`" — `okf/conventions/package-manifest-and-scaffold.md`.
- Release does not publish `dist/dev/pkg`: silk-release-action "publishes every bumped package through silk-release-action's own publish-target resolution (`publishConfig` targets, per-target `directory` and `registry`)" — `okf/runbooks/publish-a-snapshot.md`; and probe P3: "Under the effected bundler `publishConfig.directory` names `dist/dev/pkg`, so candidate A [`pnpm pack` from source] packs the **dev** build: source maps present, `tsdoc-metadata.json` absent. Candidate B [`npm pack` in `dist/prod/npm/pkg`] is the file list a release actually publishes." Both candidates' packed manifests had no `workspace:`/`catalog:` specifier and `private: false` — `okf/decisions/packed-install-pack-source.md`.
- Turbo: `build:dev` outputs `dist/dev/**`, depends on `^build:dev`; `build:prod` outputs `dist/prod/**`, depends on `types:check` and `build:dev`; prod inputs add `$TURBO_ROOT$/.changeset/**` (for optimistic versions) — `~/YeeBois/references/effect/effected/turbo.json`. Vitest `globalSetup` runs `turbo run build:dev` before every test run so tests import built `dist/dev` artifacts — `okf/modules/workspace.md`.

### Inferences
- `dist/dev/pkg` is the publish *directory* for pnpm's **linking** semantics, not for the actual registry upload: it gives in-repo consumers (and vitest) a registry-identical package shape with sourcemaps, while the prod tree is what silk-release-action uploads. This dual role is why the dev manifest preserves `catalog:`/`workspace:` specifiers — pnpm still needs to resolve them locally.
- `main`/`types` fields are never emitted because the packages are exports-only ESM; the transform assumes an `exports`-first manifest.

### Gaps
- I could not read silk-release-action's source to confirm exactly how it selects `dist/prod/<target>/pkg` per target; the effected runbook and the P3 probe decision are the evidence.

## Key Question 3 — One file per entry or preserved module structure? Are declaration files bundled (rolldown-plugin-dts / oxc isolated declarations)?

### Takeaway
JavaScript is **not** bundled: tsdown runs with `unbundle: true` (preserve-modules), so output mirrors `src/` one file per module. Declarations **are** bundled: one rolled-up, self-contained `.d.ts` per public export entry, produced by `rolldown-plugin-dts` with `generator: "tsc"` (the full TypeScript emitter, not oxc isolated declarations; `isolatedDeclarations: false` in `ecma.json`). A second, unpublished per-module declaration tree is emitted on prod solely for API Extractor diagnostics.

### Cited Findings
- "Every build emits per-module JavaScript alongside a single rolled-up, self-contained `.d.ts` per public entry. Each entry's declaration file pulls in every re-exported type, so a consumer that infers a type from your public API never has to reach into a deep sibling module that no export subpath addresses." — bundler README (intro).
- "each target runs two `tsdown` passes: a JavaScript pass that preserves per-module output, then a declaration-only pass that rolls every re-exported type into a single `.d.ts` per public entry (`deriveDtsPassOptions`). Per-module JavaScript stays intact while consumers keep reaching re-exported types through your published subpaths." — tsdown-plugins README, "Bundled declarations".
- JS pass: `unbundle: !(options.bundleNodeModules ?? false)`; dts pass: `unbundle: false`, `dts: { tsconfig, emitDtsOnly: true, generator: "tsc" }` — `.../build/target-groups.js`.
- Observed: `@effected/app` dev output has 5 top-level `.js` + 2 `internal/*.js` and exactly one `index.d.ts` (774 lines) whose only imports are external packages (`@effected/store`, `@effected/xdg`, `effect`, `@effected/config-file`) — `~/YeeBois/references/effect/effected/packages/app/dist/dev/pkg/`. `@effected/yaml`: 42 `.js`, 1 `.d.ts`.
- Changelog 0.12.0: "The declaration pass now emits one self-contained `.d.ts` per public entry instead of rolling every entry through a single multi-entry pass" and "runs with `stableTypeOrdering`, so union and type members serialize in a stable order across builds" — https://raw.githubusercontent.com/savvy-web/systems/main/packages/bundler/CHANGELOG.md. tsdown-plugins 0.12.0: pure re-export secondary entries are emitted as `export { … } from "./index.js"` stubs "so re-export-heavy multi-entry packages stay compact" — tsdown-plugins CHANGELOG.
- `bundleNodeModules: true` flips to a single self-contained file per format ("`unbundle` now turns off automatically whenever `bundleNodeModules` is set" — tsdown-plugins CHANGELOG 1.1.5). Used e.g. for pnpm config-dependency `pnpmfile.mjs` loose files — bundler README "Loose files".
- `isolatedDeclarations: false`, `isolatedModules: true` — `tsconfig/ecma.json`. The `rolldown-plugin-dts` instance is pinned against `typescript@6.0.3` (plugin pack's dep) and `7.0.2` (effected's) in the store listing.
- Known cost of dts bundling with Effect: in `@effected/cli`, "`./ui` imported those types relatively, the rollup put **copies** of them into `ui.d.ts`. `Status` has a private member, so a copy is nominally distinct from the original... 'Types have separate declarations of a private property 'defs''"; fix = `dtsExternals: ["@effected/cli", "@effected/cli/ui"]` so the ui declarations import the root's types by package name — `okf/decisions/ui-declarations-reference-the-root-by-name.md` and `packages/cli/savvy.build.ts`.
- API Extractor noise specific to Effect: "Effect class factories (Schema.Class, TaggedError, Context.Service) synthesize an anonymous `_base` class that cannot be exported or release-tagged from source; suppress only that warning" — `~/YeeBois/references/effect/pluginfinity/packages/core/savvy.build.ts` (comment); every effected/okfit package suppresses `ae-forgotten-export` with pattern `_base`.

### Inferences
- The design deliberately decouples "how JS is laid out" (unbundled, so Node loads only what is imported and stack traces map 1:1 to source modules) from "how types are delivered" (bundled, so there is one type surface per subpath and no deep `.d.ts` imports). This is the inverse of a typical tsup/tsdown library build (bundle JS, bundle dts) and of a typical tsc build (unbundle both).
- `generator: "tsc"` was chosen over oxc isolated-declarations because Effect-heavy code (class factories, inferred `Layer`/`Effect` types) does not satisfy `isolatedDeclarations`; the `_base` suppressions and `stableTypeOrdering` work are symptoms of leaning on the full checker.

### Gaps
- No doc states explicitly *why* JS is left unbundled while dts is bundled; the README states the behaviour and its consumer benefit, not a comparison with alternatives.

## Key Question 4 — Does he externalize `effect` and workspace deps? How are `peerDependencies` + `catalog:effect:peers` used?

### Takeaway
Yes. Everything declared in `package.json` (including peers) is auto-externalised in both the JS and dts passes; `effect` is always a **peer** on libraries, declared via the `effect:peers` catalog (caret `^4.0.0` floor) while `devDependencies` use the `effect` catalog (`^4.0.2`); internal `@effected/*` edges are `workspace:^` peers (or regular deps, decided per edge) so consumer trees dedupe onto one copy. The bundler's own `effect` runtime is a regular dependency so it never fights the consumer's version.

### Cited Findings
- "Dependencies you declare in `package.json` are externalized automatically — they stay `import`ed from the published `.js` and referenced from the `.d.ts`, and the consumer resolves them from their own `node_modules`. ## Key Question 5 — Any README/blog/changelog/commit/discussion explaining the "why" of bundling for libraries?

### Takeaway
There is no blog post or discussion thread found. The "why" is stated piecemeal in the bundler README, the tsdown-plugins README, source comments, and effected's `okf/` conventions. Stated reasons: one devDependency with a pinned, transitively tested toolchain; a zero-config self-executing `savvy.build.ts`; publishable manifests generated from private source manifests (dual dev/prod with catalog resolution); bundled declarations so re-exported types are reachable via published subpaths; API Extractor as a CI gate for forgotten exports; machine-readable `issues.json`; readable, unminified prod output for stack traces and SCA scanners; multi-registry publishing; SEA binaries; and a build-time version constant. The original motivation was replacing an earlier in-house `rslib-builder`.

### Cited Findings
- Stated goal: "Configure a package with a single self-executing `savvy.build.ts`, run it against the `dev` or `npm` target and get a clean, publishable `dist/<target>/pkg`. Install one devDependency; `tsdown` is pinned and tested transitively, so a toolchain upgrade is a bundler release rather than a peer bump across your repos." — bundler README (intro). Also "**One devDependency** — `tsdown` is a regular dependency, pinned and tested transitively, so you never carry it or its plugin peers in your own tree."
- Dual outputs rationale: "**Build targets** — `dev` for local linking, `prod` for a resolved publishable manifest (which also emits an API Extractor api-model) and `exe` for SEA binaries, on disjoint `dist/dev` and `dist/prod` output paths for clean caching." — bundler README "Features".
- Declarations rationale: "**Bundled declarations** — per-module JavaScript with a single rolled-up `.d.ts` per public entry, so re-exported types stay reachable through your published export subpaths." — README "Features".
- Manifest rationale: "**Manifest resolution** — `catalog:` and `workspace:` specifiers are resolved against the workspace for the published target, and preserved for the linked dev target." and "**Default manifest stripping** — the published `package.json` drops build- and dev-only fields automatically" — README "Features".
- Readability over size: "**Readable prod output** — prod output is unminified by default to keep stack traces legible and pass security scanners; `minify` opts back in." — README.
- Quality gate: "API Extractor's analyzer messages — forgotten exports, missing release tags and TSDoc issues — surface in the build log rather than being dropped. A forgotten export... fails the build under CI" — README "API Extractor meta". Changelog 0.9.0: API Extractor diagnostics surfaced with CI enforcement; 0.7.0: "Generate the API Extractor meta bundle from the production build instead of the development build, so the package manifest... carries fully resolved dependency versions" — bundler CHANGELOG (summarised by fetch).
- Agent/CI-oriented diagnostics: issues.json "so an agent or CI script reads the diagnostics straight from disk instead of parsing terminal output" — tsdown-plugins README. Output formats include `agent` console and `ci-annotations` — `OutputConfig` in `index.d.ts`.
- Lineage: changelog v0.2.0 "Initial tsdown-based replacement for rslib-builder. Established dual esm+cjs format, bundling-posture controls (`bundleNodeModules`/`dtsExternals`), and multi-target publishing (`--target prod`)" — bundler CHANGELOG (fetch summary). Source comments repeatedly reference rslib parity: "restoring the self-contained bundle the rslib builder produced", "the rslib `dtsBundledPackages` equivalent" — `index.d.ts`; "inherited from rslib-builder" — `manifest/transform.js`.
- Effect-specific friction acknowledged in docs: `dtsExternals` for `declare module` augmentations (README); `_base` forgotten-export suppressions (every `savvy.build.ts`); `stableTypeOrdering` for `Layer.Layer<…>` unions (`dts/resolved-tsconfig.js`); the `@effected/cli` private-member copy problem (`okf/decisions/ui-declarations-reference-the-root-by-name.md`); gotcha file `okf/gotchas/api-extractor-forgotten-export-on-class-factories.md` (title).
- Effected's own framing: "Build tooling comes from two `@savvy-web` packages: `bundler` (each package's `savvy.build.ts`, the dual dev/prod outputs, and the `publishConfig` manifest transform that produces the publishable manifest at build time from a `"private": true` source manifest) and `silk` (the Biome, commitlint, lint-staged and markdownlint presets, plus the tsconfig bases), orchestrated by Turbo." — `okf/modules/workspace.md`. CONTRIBUTING.md: "Each package builds with @savvy-web/bundler and emits dual outputs: a development build under `dist/dev/` and a production build under `dist/prod/`."
- Guardrails born from the design: "Never run `node savvy.build.ts --target prod` directly: it skips `build:dev`, emits no `.d.ts`, and leaves a truncated `issues.json` shaped exactly like a clean gate" — `okf/modules/workspace.md`; `okf/conventions/build-through-turbo-only.md`; `okf/gotchas/direct-prod-build-fakes-a-clean-gate.md`; `okf/gotchas/turbo-cache-hit-replays-clean-log.md` (title).
- Tree-shaking posture is handled at the source-layout level, not the bundler: "Only entrypoint files — `src/index.ts` and any published subpath entrypoints — may re-export... a namespace object is a **single live binding**... An unbundled Node consumer has no tree-shaker... The only mechanism that answers 'does a consumer that wants one class pay for the rest of the package' is a published subpath entrypoint" — `okf/conventions/no-barrel-re-exports.md`. `okf/conventions/bundle-reachability-suite.md` exists (title only).
- The systems repo describes itself as the "coordination hub and shared libraries for the Silk Suite open-source ecosystem, maintained by Savvy Web Systems" — https://github.com/savvy-web/systems.
- Web search for a blog/discussion by Spencer Beggs on this topic returned nothing relevant (results were generic tsdown pages and his `workspaces-effect` package) — WebSearch "spencerbeggs effected Effect libraries bundler tsdown blog"; WebSearch "\"@savvy-web/bundler\" tsdown" also found no third-party coverage.

### Inferences (my reading of the "why", flagged as inference)
- The dominant driver is **monorepo DX and publishing mechanics**, not bundle size: private source manifests pointing at `src/*.ts` give editors/tests/turbo a single source of truth; the bundler materialises registry-identical packages for both linking (dev) and release (prod) without hand-maintained `publishConfig.exports` overrides.
- A second driver is **type-surface hygiene for Effect code**: Effect libraries lean on inferred types and class factories; a rolled-up `.d.ts` plus API Extractor turns "forgotten export" into a CI failure and gives him api-model JSON for his RSPress docs sites (`meta.localPaths` → `website/lib/models/*`).
- A third driver is **toolchain centralisation across ~6 repos** (effected, okfit, pluginfinity, tsdoctor, vitest-agent, systems): every `savvy.build.ts` is 3–15 lines; all version pins live in one package.
- He is explicitly **not** optimising for minified size or pure-annotated tree-shaking (no `@__PURE__` pass, minify off by default); `sideEffects: false` and no-barrel source discipline carry that load.
- Consumers install slightly fewer files than a tsc emit would ship (one `.d.ts` instead of N, no `.d.ts.map`, no `src/`), but no doc claims install weight as a motive; `okf/decisions/github-references-extracted-for-install-weight.md` (title) suggests install weight is managed by package splitting instead.

### Gaps
- No author-written narrative (blog, discussion, design doc) comparing bundling to `tsc` emit was found anywhere. The "why" above is reconstructed from feature docs and conventions.
- The upstream `systems` repo's `packages/bundler/src` and any ADRs under `okf/` there were not read (only READMEs and CHANGELOGs via fetch).

## Key Question 6 — How does the Effect monorepo (v4) build and publish, and why unbundled per-module emit?

### Takeaway
Effect v4 is **ESM-only**, built with plain `tsc -b` into `dist/` (per-module `.js` + `.js.map` + `.d.ts` + `.d.ts.map`), then `babel dist --plugins annotate-pure-calls` adds `/*#__PURE__*/` markers in place. No `build/esm` + `build/cjs` split and no `@effect/build-utils pack-v2` in v4: publishing uses pnpm's `publishConfig.exports` override to swap a `src/*.ts` exports map for a `dist/*.js` one, ships `src/**/*.ts` alongside `dist/**` in `files`, and `sideEffects` lists exactly one file. Release is `changesets/action` running `pnpm changeset-publish` = `set-strip-internal` + codemod + build + `changeset publish`. The stated motivation is tree-shakeable, per-module import granularity ("A minimal Effect program bundles to 7.1 kB").

### Cited Findings
- `packages/effect/package.json` (`~/YeeBois/references/effect/effect/packages/effect/package.json`): `"type": "module"`, version `4.0.2`; `scripts`: `"build": "tsc -b tsconfig.json && pnpm babel"`, `"babel": "babel dist --plugins annotate-pure-calls --out-dir dist --source-maps"`, `"check": "tsc -b tsconfig.json"`, `"codegen": "effect-utils codegen"`.
- Exports map (28 keys) points at **source**: `".": "./src/index.ts"`, `"./schema": "./src/schema/index.ts"`, `"./*": "./src/*.ts"`, with `null` blocks for `./internal/*`, `./cli/internal/*`, `./cluster/internal/*`, `./index`, `./*/index`. `publishConfig.exports` mirrors it onto `./dist/*.js`; `publishConfig: { access: "public", provenance: true }`. `files: ["src/**/*.ts","dist/**/*.js","dist/**/*.js.map","dist/**/*.d.ts","dist/**/*.d.ts.map","AGENTS.md","CLAUDE.md","ai-docs/**/*"]`. `sideEffects: ["./src/schema/SchemaJITCompiler/enable.ts","./dist/schema/SchemaJITCompiler/enable.js"]` — same file. (No `main`, no `types`, no CJS condition.)
- `tsconfig.base.json`: `outDir: ${configDir}/dist`, `rootDir: ${configDir}/src`, `composite: true`, `incremental: true`, `target: "ES2022"`, `module: "NodeNext"`, `verbatimModuleSyntax: true`, `rewriteRelativeImportExtensions: true` ("Rewrite `.ts` imports to `.js` at build time"), `erasableSyntaxOnly: true` ("Allows to run directly with node and type removal"), `declarationMap: true`, `sourceMap: true`, `stripInternal: false` ("tests require `false` because project references type-check against those declarations"), `@effect/language-service` plugin with `apiStabilityLeak: "error"` outside `internal/` — `~/YeeBois/references/effect/effect/tsconfig.base.json`.

- Release: `.github/workflows/release.yml` uses `changesets/action` with `version-script: pnpm changeset-version` and `publish-script: pnpm changeset-publish`; `.changeset/config.json` has a single `fixed` group covering `effect` and all `@effect/*` packages, `access: "restricted"` (overridden per-package by `publishConfig.access`), `privatePackages: false`.
- Dist layout observed: `packages/effect/dist/` has 559 entries at top level (`Array.js`, `Array.js.map`, `Array.d.ts`, `Array.d.ts.map`, ...), 458 `.js` files in total, `dist/internal/` with 121 entries; `dist/Effect.js` begins with per-module relative imports (`import * as Context from "./Context.js"; ... import * as core from "./internal/core.js";`) and retains full JSDoc — `~/YeeBois/references/effect/effect/packages/effect/dist/Effect.js`.
- Pure annotations: the local `dist` contains **0** `@__PURE__` occurrences across all `.js` files (`grep -o '@__PURE__' -r dist --include='*.js' | wc -l` → 0), i.e. this checkout's `dist` was produced by `tsc -b` (`check`) without the `pnpm babel` step; the published artefact gets them via the `build` script.
- Stated rationale: "### Performance and Bundle Size ... The core `effect` package supports aggressive tree-shaking. A minimal Effect program bundles to 7.1 kB (minified + gzipped)." — `~/YeeBois/references/effect/effect/MIGRATION.md` lines 71–75.
- Tooling: `pnpm@11.20.0`; workspace `verifyDepsBeforeRun: error`; `packages/tools/` contains `ai-codegen, ai-docgen, api-diff, bundle, docgen, doctest, jsdocs, openapi-generator, oxc, utils` — `pnpm-workspace.yaml` and `ls packages/tools`.
- Not present in v4: no `.babel.mjs.json`/`.babel.cjs.json`, no `build/esm`/`build/cjs`, no `@effect/build-utils` or `pack-v2` reference anywhere in root or `packages/effect` manifests (grep returned only the `annotate-pure-calls` lines).

### Inferences
- Effect's per-module, unbundled emit exists so that consumer bundlers can tree-shake at module granularity and `sideEffects` can be an explicit one-file allowlist; `publishConfig.exports` lets the same package resolve to `src/*.ts` in the monorepo (tests/tsgo/`erasableSyntaxOnly` make `.ts` runnable directly) and to `dist/*.js` when published — the same "two manifests" problem Spencer solves by generating a new manifest, Effect solves with pnpm's built-in override.
- Shipping `src/**/*.ts` plus `.d.ts.map`/`.js.map` optimises for debuggability and go-to-definition at the cost of install size; Spencer's prod build drops `.d.ts.map` and `.js.map` and never ships `src/` — opposite trade.
- Effect has no API Extractor gate; it substitutes `@effect/language-service` `apiStabilityLeak`, `check-dist-types`, `stripInternal` at publish, and `api-diff`.

### Gaps
- `.repos/effect` was not inspected separately (assumed the same upstream repo at a similar ref).
- v3-era mechanics (`build-utils pack-v2`, `build/esm` + `build/cjs`) are not present in the v4 checkout and were not verified from a v3 checkout; I only confirm their absence in v4.
- No explicit Effect-maintainer statement on "why tsc emit rather than a bundler" was found in the checkout beyond the MIGRATION.md tree-shaking paragraph.
