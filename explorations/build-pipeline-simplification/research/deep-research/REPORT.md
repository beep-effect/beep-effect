# Keep tsgo emitting; bundle only what ships

**BLUF.** The evidence does not support moving beep-effect's 161-manifest library build onto `bun build`, and it only weakly supports moving it onto any bundler at all. The build today is a declaration pipeline: `dist/*.js` has no runtime consumer (Next/Turbopack, Vitest, and the Bun CLIs all resolve `exports` to `src/*.ts`), while `dist/*.d.ts` is load-bearing for project-reference type checks, Next's Vercel type check, and docgen's example compile ([pipeline audit Q2–Q3](../../../../packages/foundation/modeling/schema/package.json)). Bun 1.4.2 emits no `.d.ts` in any mode, has no preserve-modules output, silently accepts unknown flags and options, and carries an open `sideEffects: false` barrel re-export bug (#18008) that is confirmed on 1.4.3-canary ([bun.com/docs/bundler](https://bun.com/docs/bundler), [oven-sh/bun#5141](https://github.com/oven-sh/bun/issues/5141), [oven-sh/bun#18008](https://github.com/oven-sh/bun/issues/18008)); it fails the one hard constraint outright. The credible alternative emitter is tsdown (rolldown + `rolldown-plugin-dts`), which is what `@savvy-web/bundler` 2.4.24 actually is under the hood, but its declaration pass is still a TypeScript program, so it buys publishing hygiene (generated `exports`, publint/attw, unbundle, one shared config), not wall-clock speed, and it drops the Effect-diagnostics gate that currently rides on the emitting compiler. The recommendation is a two-tier pipeline: keep `effect-tsgo` emit for every private package, collapse the per-package script to one generated `beep:build` call owned by a shared build-kit package that asserts artifacts and manages tsbuildinfo coherence, make the Babel pure-annotation pass conditional on publishability, and reserve a tsdown `unbundle` + `exports` + `attw` lane for the handful of ecosystem packages that will actually be published. `bun build --compile --bytecode` belongs in the CLI release lane, where the repo already uses it. Effect's SchemaCompiler should not influence any of this: the repo's own 2026-09-28 ruling is DEFER, the AOT output is one side-effectful ES module per application entry (not per library), and measured gains on `@beep` shapes are 1.2–1.5x ([DECISIONS.md](../../../../explorations/effect-schema-parity/DECISIONS.md), [compiler-evaluation.md](../../../../explorations/effect-schema-parity/research/2026-09-28-compiler-evaluation.md)).

Convention used below: a claim followed by a citation is sourced from a note's primary evidence; claims tagged **[inferred]** are this report's reading of that evidence.

## The build is a declaration pipeline, and the pain is coherence, not compile time

The census is unambiguous about what the 161 manifests do. 149 define `"build": "bun run beep:build"`, 123 of those run the canonical `tsc -p tsconfig.json && bun run babel` where `babel dist --plugins annotate-pure-calls --out-dir dist --source-maps` rewrites `dist/` in place; 13 run bare `tsc -p`, 5 run `tsgo -p tsconfig.check.json`, 4 `vite build`, 2 `next build --turbopack` ([root package.json census](../../../../package.json)). The `tsc` binary is `@typescript/native` 7.0.2 with its binary swapped for `effect-tsgo 0.47.2` in the root `prepare` script, so every emit also runs roughly 130 Effect diagnostics as errors ([docs/runbooks/typescript-toolchain.md](../../../../docs/runbooks/typescript-toolchain.md)). Emit is per-package `tsc -p` (not `tsc -b`) with `composite`/`incremental` on and project references into dependency tsconfigs; there is no `isolatedDeclarations` and no `tsconfig.build.json` ([tsconfig.base.json](../../../../tsconfig.base.json)).

Who reads `dist`? **136/161 manifests point `exports["."]` at `./src/index.ts`**, with `publishConfig.exports` rewriting every subpath to `./dist/*.js` for a publish that has never happened: 152 manifests are `private: true`, changesets are `access: restricted`, and no release workflow runs `changeset publish` ([schema package.json](../../../../packages/foundation/modeling/schema/package.json), [.changeset/config.json](../../../../.changeset/config.json)). Next's shared config sets `transpilePackages` defaults and reads source; Vitest installs 797 generated aliases to `src/**`; six `bin` fields point at `src/bin.ts` under `#!/usr/bin/env bun` ([SharedNextConfig.model.ts](../../../../packages/tooling/policy-pack/repo-configs/src/next/SharedNextConfig.model.ts), [vitest.shared.ts](../../../../vitest.shared.ts)). The runtime consumer of `dist/*.js` is nobody **[inferred from the above]**. What consumes `dist` is `.d.ts`: Turbo's `check`, `coverage`, `test:integration`, and `dev` all `dependsOn: ["^build"]`, docgen compiles examples against built declarations, and the todox Vercel deploy failed with `TS6305: Output file '.../identity/dist/index.d.ts' has not been built` until its `buildCommand` ran `turbo run build` with a tsbuildinfo purge ([turbo.json](../../../../turbo.json), `vercel-next-app-workspace-deps-need-turbo-build.md` (local checkout `~/.claude/memory/beep-effect/vercel-next-app-workspace-deps-need-turbo-build.md`)).

That reframes all four goals. "Faster builds" is already mostly solved by the compiler: warm `bun run build` passes **131/131 in 24 s**, a cold `turbo run build --filter=@beep/repo-cli...` runs 33 tasks in 6.7 s, and TypeScript 7 native is 7.7–11.9x faster than TS 6 ([OPPORTUNITIES.md](../../../../explorations/fleet-coordination/research/OPPORTUNITIES.md), [c3-2b-implementation.md](../../../../goals/time-to-certainty/research/c3-2b-implementation.md), [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). The measurable costs are elsewhere: the serial 21-sub-lane pre-push proof averaging 17 min, and the memory footprint that forced the three-slot `beep-heavy` admission queue after two oomd kills ([quality-time-inventory.md](../../../../goals/quality-speedup/research/quality-time-inventory.md), `workstation-beep-heavy-admission-wrapper.md` (local checkout `~/.claude/memory/beep-effect/workstation-beep-heavy-admission-wrapper.md`)). The documented pain tied to emit shape is coherence: non-build-mode incremental `tsc -p` never checks that its outputs exist, so a restored tsbuildinfo made Vercel's `tsc` exit 0 in under a second with no `dist` and Babel then died on a missing directory; a Turbo cache restore of `check`'s tsbuildinfo once produced phantom missing-export errors; fresh worktrees hit TS6305 until dependency dists exist (`vercel-build-cache-stale-tsbuildinfo-skips-emit.md` (local checkout `~/.claude/memory/beep-effect/vercel-build-cache-stale-tsbuildinfo-skips-emit.md`), `turbo-build-check-cache-race.md` (local checkout `~/.claude/memory/beep-effect/turbo-build-check-cache-race.md`)). "Smaller bundles" and "runtime performance" are app-side properties: the repo already runs Turbopack/webpack for Next, Vite for the desktop and three labs, and `bun build --compile` for the Tauri sidecar and the kg-mcp binary, none of which read `tsc`'s `dist/*.js` ([build-sidecar.ts](../../../../apps/professional-desktop/scripts/build-sidecar.ts), [package.ts](../../../../apps/practice-kg-mcp/src/package.ts)).

The constraint set any replacement must satisfy therefore reads: per-module `.d.ts` and `.d.ts.map` into `dist/` so project references keep resolving (or `check` moves off project references); stable Turbo outputs without new restore-coherence hazards; `exports` to `src` preserved with `publishConfig` to `dist`; running under `beep-heavy` caps and the 40-minute hosted Build lane; no weakening of the Effect-diagnostics gate; and `#__PURE__`-equivalent output or a justification for dropping Babel while nothing is published ([pipeline audit Q8 inference](../../../../turbo.json)) **[inferred constraint set]**.

## bun build fails the hard constraint and the evidence contradicts the lean

The case for `bun build` rests on speed, a single toolchain, and the runtime wins of `--bytecode`/`--compile`. The speed claim is real on the rolldown team's own benchmark (updated 2026-10-07, Bun 1.4.2 vs rolldown 1.2.13 vs esbuild 0.28.2): **955 ms vs 1,822 ms vs 2,108 ms** on a 19,014-module app on Ubuntu, with the caveat in the same repo that Bun "produces substantially different output", so the comparison is not like-for-like ([rolldown/benchmarks](https://github.com/rolldown/benchmarks)). For library-sized inputs the JS pass is tens of milliseconds for every tool, and in a monorepo the dominant cost is declaration emit, where Bun contributes nothing **[inferred]**.

The declaration gap is total. The bundler docs say "It does not generate type declarations. Use `tsc` to produce `.d.ts` files"; issue #5141 (opened 2023-09-12, 109 upvotes) is open with no maintainer post since 2023; and a local probe on 1.4.2 showed `bun build --dts` printing "Bundled 2 modules", emitting only `a.js`, and `Bun.build({ dts: true })` succeeding with a `.js`-only output ([bun.com/docs/bundler](https://bun.com/docs/bundler), [oven-sh/bun#5141](https://github.com/oven-sh/bun/issues/5141)). The community answer is to pair `bun build` with `tsc --emitDeclarationOnly` (2,084 package.json hits on GitHub code search) or wrap it in bunup, whose own rationale concedes that Bun's inability to generate declarations "defeats the purpose of Bun's speed advantage" ([Why bunup](https://bunup.dev/notes/why-bunup.html)). In other words, a "Bun-only" library build still runs the TypeScript program; it adds a tool rather than removing one.

Per-module output does not exist either. Bun has no `preserveModules` or `unbundle`; `--no-bundle` transpiles per file but leaves `export * from "./b"` extensionless, so Node fails with `ERR_MODULE_NOT_FOUND` on the output ([bun.com/docs/bundler/vs-esbuild](https://bun.com/docs/bundler/vs-esbuild), local probe). For a package like `@beep/schema` with roughly 130 subpath exports, single-chunk-per-entry output would also fight the pure-annotation story: top-level `Context.Tag(...)`, `Schema.Struct(...)`, and `Layer.*` calls concentrated into one file are evaluated whenever any export is imported unless each is `/* @__PURE__ */`-annotated, whereas per-module files are simply never loaded when unused ([effect-community-guidance.md](../../../../goals/per-module-imports/research/effect-community-guidance.md)) **[inferred]**.

Silent acceptance is the operational hazard. On 1.4.2, `bun build --totally-bogus-flag` ran with no warning, as did `--dts`, `--preserve-modules`, and `--check`; `Bun.build({ bogusOption: true })` returned `success: true`. The documented `check: true` type-check option is from PR #44361, merged 2026-10-06, after 1.4.2 shipped on 2026-09-05; on the installed version a file containing `export const n: number = "str"` built successfully with `check: true` (local probe; [bun.com/docs/runtime/check](https://bun.com/docs/runtime/check)). The follow-up PRs on 2026-10-07/08 fix "378 more differences from `tsc`", and #44763 already reports load time growing with the number of project references ([oven-sh/bun PRs via gh](https://github.com/oven-sh/bun/pulls)). A gate whose implementation is fixing hundreds of tsc divergences per day is pre-production, and a repo whose correctness gate is `effect-tsgo` diagnostics cannot swap it for `bun check` without losing those diagnostics entirely **[inferred]**.

The barrel bug is a live correctness risk for this repo's shape. With `"sideEffects": false`, a barrel `export * from './impl.cjs'` loses its re-exports and throws `ReferenceError` at runtime; a maintainer bot located the fault in `src/bundler/linker_context/scanImportsAndExports.rs`, and the issue is confirmed on 1.4.3-canary.1 and main as of September 2026 ([oven-sh/bun#18008](https://github.com/oven-sh/bun/issues/18008)). The repo has 132 manifests with `sideEffects: []`, and `@beep/effect-drizzle`'s bundle probe already switched to esbuild because `Bun.build` 1.3.14 "tree-shakes this package's re-export graph down to a stub that exports a dropped binding (an invalid module)" ([bundle-build.ts](../../../../packages/ecosystem/effect-drizzle/test/bundle-build.ts)). That note is one Bun minor old and should be re-tested on 1.4.2, but it is in-repo evidence against trusting Bun's tree-shaking on re-export-heavy Effect packages, and the adoption ratio tells the same story: **53,632 package.json files reference tsdown versus 677 for bunup**, and no Effect-ecosystem library was found publishing through `bun build` alone (GitHub code search counts, 2026-10-09).

Where Bun is right: `--compile` with cross-targets, `--asset` embedding, `--bytecode` (ESM allowed with `--compile` since 1.4), and the 1.4 Rust port's startup and memory claims. Vendor numbers put bytecode at roughly 2x startup for `tsc`-sized CLIs and 1.5–2x for small ones; one independent measurement was 1.38x (52.7 ms to 38.3 ms), bytecode is Bun-only and version-locked, and a `--compile` binary is about 81 MB ([bun.com/docs/bundler/bytecode](https://bun.com/docs/bundler/bytecode), [peterbe.com](https://peterbe.com/plog/trying-bun-compile-to-bytecode)). That is a release-lane optimisation for `beep-cli` and the kg-mcp binary, both of which already run under Bun, and it has nothing to do with how 150 library packages emit declarations **[inferred]**.

## tsdown is the only credible alternative emitter, and it buys hygiene, not speed

Among the non-Bun options, tsdown is where the library ecosystem has consolidated: tsup's README now says it "is not actively maintained anymore" and points to tsdown; tsdown lives under the `rolldown` GitHub org; VoidZero names it the foundation for Vite's library mode; Rolldown itself reached 1.0.0 on 2026-05-07 and is Vite 8's single default bundler ([tsup README](https://github.com/egoist/tsup), [tsdown FAQ](https://tsdown.dev/guide/faq), [Vite 8 announcement](https://vite.dev/blog/announcing-vite8)). tsdown 0.23.0 (2026-09-03) is still pre-1.0 and that release was a breaking reorganisation with a migration guide, so config churn is a real cost ([tsdown releases](https://github.com/rolldown/tsdown/releases)). Its feature set maps onto the Effect layout closely: `unbundle: true` emits a one-to-one file mapping and is recommended "in monorepo or library scenarios where consumers may want to import individual modules"; `exports: true` generates the `exports` map and `exports.devExports` points top-level exports at source while writing built-output exports into `publishConfig` (honoured by pnpm/yarn publish, not npm); publint and attw are built in with a `ci-only` mode; `-W/--workspace` inherits a root config ([tsdown unbundle](https://tsdown.dev/options/unbundle), [tsdown package-exports](https://tsdown.dev/options/package-exports), [tsdown lint](https://github.com/rolldown/tsdown/blob/main/docs/options/lint.md)).

The declaration story is the catch. tsdown's `.d.ts` comes from `rolldown-plugin-dts`, which auto-selects `oxc` when `isolatedDeclarations` is on, `tsgo` when TypeScript 7 is installed, else `tsc`; the `tsgo` generator is "experimental and requires a tsconfig.json" and ignores `tsconfigRaw`/`compilerOptions` ([rolldown-plugin-dts README](https://github.com/sxzz/rolldown-plugin-dts)). The oxc fast path, the only one that is not a full TypeScript program, needs `isolatedDeclarations`, which the repo does not use and which Effect-heavy code (class factories, inferred `Layer`/`Effect` channels) typically fails; Spencer Beggs set `isolatedDeclarations: false` and forced `generator: "tsc"` for exactly this reason (`ecma.json` (local checkout `~/YeeBois/references/effect/effected/node_modules/.pnpm/@savvy-web+bundler@2.4.24_*/node_modules/@savvy-web/bundler/tsconfig/ecma.json`)) **[inferred motive]**. So a tsdown build of a `@beep` package is: oxc transpiles JS in milliseconds, then a TypeScript program emits declarations, which is the same program `tsgo -p` runs today minus the Effect diagnostics. There is no wall-clock win to be had unless `isolatedDeclarations` is adopted repo-wide, and the TS 7 announcement is explicit that project-reference builds are "fundamentally bottlenecked by the dependency graph of projects (with the exception of type-checking on codebases that leverage `--isolatedDeclarations`)" ([Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). That is a schema-authoring decision (explicit return types on every export), not a bundler decision, and a 2025 migration report notes it "forced explicit return types" ([alan.norbauer.com](https://alan.norbauer.com/articles/tsdown-bundler/)).

Rslib 1.0.0 (2026-09-03, ByteDance Web Infra) is the strongest "tsc replacement with rewrites": bundleless mode rewrites tsconfig `paths` aliases and output extensions in both JS and `.d.ts` by default, and its dts has three generators (tsc API, tsgo auto for TS 7, SWC `dts.isolated` experimental), with the 1.0 blog quoting 2.4x (tsgo) and 4.2x (isolated) declaration speedups against a tsc baseline ([Rslib dts](https://rslib.rs/guide/advanced/dts), [Rslib redirect](https://rslib.rs/config/lib/redirect), [Rslib 1.0 blog](https://github.com/web-infra-dev/rslib/blob/main/website/docs/en/blog/v1-0.mdx)). It is a second Rust ecosystem (Rspack) next to the Rolldown one Vite 8 already pulled in, it needs a per-package `rslib.config.ts`, and no notable library adopters were found; its alias-rewrite strength matters most for repos that build from tsconfig `paths`, which beep's `NodeNext` + `rewriteRelativeImportExtensions` setup does not need **[inferred]**. esbuild 0.28.2 (2026-08-08) is at three releases in 2026, last commit 2026-08-09, no `.d.ts`, and Vite 8 replaced it with Oxc; it remains the right engine for the existing effect-drizzle bundle-size probe and nothing more ([esbuild releases](https://api.github.com/repos/evanw/esbuild/releases), [Vite 8 announcement](https://vite.dev/blog/announcing-vite8)).

On pure annotations every tool agrees and none helps. Rolldown/Oxc, Rspack, esbuild, and Bun all respect `@__PURE__` and (Rolldown/Oxc) `@__NO_SIDE_EFFECTS__` on input; none of them infers purity for `dual(...)`, `Schema.Struct(...)`, or `Context.Tag(...)`; the only insertion tools are `babel-plugin-annotate-pure-calls`, which Effect 4.0.2 still runs over `dist/` after `tsc -b`, and `rollup-plugin-pure`; rolldown's "opt-in heuristic DCE for pure top-level call/new initializers" is an open discussion (#10068) ([rolldown DCE](https://rolldown.rs/in-depth/dead-code-elimination), [oxc minifier DCE](https://oxc.rs/docs/guide/usage/minifier/dead-code-elimination), [effect package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json), [rolldown#10068](https://github.com/rolldown/rolldown/issues/10068)). Swapping emitters does not remove the Babel pass; only deciding that unpublished packages do not need annotations does.

## Spencer bundles for manifests and type surfaces, not for size

First, the discrepancy. One note describes `@effected/*` as built with `@savvy-web/bun-builder` ("Bun's native bundler", "rolled-up .d.ts via API Extractor") based on that repo's README ([savvy-web/bun-builder](https://github.com/savvy-web/bun-builder)). The note that read the installed `@savvy-web/bundler` 2.4.24 sources in the effected checkout found a different engine: `dependencies` are `@savvy-web/tsdown-plugins 2.8.22`, `tsdown ^0.23.0`, `rolldown ^1.2.12`, `@tsdown/exe`, and `effect ^4.0.2`, with `@microsoft/api-extractor 7.59.1` in the plugin pack; `build-target-groups.js` lazily `import("tsdown")` (`installed package.json` (local checkout `~/YeeBois/references/effect/effected/node_modules/.pnpm/@savvy-web+bundler@2.4.24_*/node_modules/@savvy-web/bundler/package.json`)). The installed-source finding is authoritative: effected, okfit, pluginfinity, tsdoctor, and vitest-agent run on tsdown/rolldown, and `bun-builder` is a sibling project in the same org, not what these libraries use. Every `savvy.build.ts` is `node savvy.build.ts --target dev|prod` under Node 24.11+ native TypeScript stripping, and his `types:check` is `tsc --noEmit`, with `@effect/tsgo` surviving "only as a `pnpm-workspace.yaml` catalog entry with no consumer" (`okf/decisions/tsc-not-tsgo.md` (local checkout `~/YeeBois/references/effect/effected/okf/decisions/tsc-not-tsgo.md`)). Bun is not in his library build at all.

What the bundler does per target is precise. For each target group it runs a tsdown **JS pass** with `unbundle: true`, `dts: false`, `platform: "node"`, sourcemaps on for dev and off for prod, minify off unless opted in; a **bundled-declarations pass** that emits one self-contained `.d.ts` per public entry via `rolldown-plugin-dts` with `generator: "tsc"` and `emitDtsOnly: true`; and for prod only a third **per-module declarations pass** into `dist/prod/<group>/declarations` as API Extractor's diagnostics input, followed by an **API Extractor meta pass**, a `targets.json` binding, and stripping of `.d.ts.map` (`target-groups.js` (local checkout `~/YeeBois/references/effect/effected/node_modules/.pnpm/@savvy-web+tsdown-plugins@2.8.22_*/node_modules/@savvy-web/tsdown-plugins/build/target-groups.js`)). A rolldown `generateBundle` plugin emits the transformed `package.json`, `LICENSE`, and `README.md` into `dist/<target>/pkg`; every run writes `dist/<target>/issues.json` with `buildOk`, `warnings`, `errors`, `suppressed`. The manifest transform is the heart of it: source manifests are deliberately `"private": true` with `exports: { ".": "./src/index.ts" }` and `publishConfig: { access: "public", directory: "dist/dev/pkg", linkDirectory: true }`; the transform flips `private` to `!(publishConfig.access === "public")`, strips `devDependencies`, `scripts`, `publishConfig`, `packageManager`, `devEngines`, rewrites each TS export to `{ types, import, default }` keyed off the export key, and resolves `catalog:`/`workspace:` specifiers to concrete ranges for prod while preserving them for dev so pnpm can still link (`transform.js` (local checkout `~/YeeBois/references/effect/effected/node_modules/.pnpm/@savvy-web+tsdown-plugins@2.8.22_*/node_modules/@savvy-web/tsdown-plugins/manifest/transform.js`), [bundler README](https://github.com/savvy-web/systems)). `effect` is always a peer declared through an `effect:peers` catalog (`^4.0.0` floor) while devDependencies use the `effect` catalog (`^4.0.2`); everything declared in `package.json` is externalised automatically in both passes; `dtsExternals` exists "to externalize effect's cross-module `declare module` augmentations, which inline into conflicting interface-extension errors in consumers" (`pnpm-workspace.yaml` (local checkout `~/YeeBois/references/effect/effected/pnpm-workspace.yaml`), bundler `index.d.ts`).

No author-written essay on "why bundle rather than tsc" exists; the why is reconstructed from feature docs and his `okf/` conventions **[inferred synthesis]**. The dominant driver is **publishing mechanics across roughly six repos**: one devDependency where "tsdown is pinned and tested transitively, so a toolchain upgrade is a bundler release rather than a peer bump across your repos", private source manifests that become registry-identical packages for both pnpm linking (`dist/dev/pkg`) and release (`dist/prod/npm/pkg` via silk-release-action), and `catalog:` resolution so the shipped peer range is `^4.0.0` while tests run on the newest minor. The second driver is **type-surface hygiene for Effect code**: one rolled-up `.d.ts` per entry so "a consumer that infers a type from your public API never has to reach into a deep sibling module that no export subpath addresses", plus API Extractor turning a forgotten export into a CI failure and producing api-model JSON for his RSPress docs. The third is **agent-readable diagnostics** (`issues.json`, `ci-annotations`, an `agent` console format). He is explicitly not optimising for size: the built dev JS contains **zero `@__PURE__` markers**, minify is off by default because "minified code degrades stack traces and trips some security scanners", and tree-shaking is handled at the source level by a no-barrel convention ("Only entrypoint files ... may re-export") rather than by the bundler (`okf/conventions/no-barrel-re-exports.md` (local checkout `~/YeeBois/references/effect/effected/okf/conventions/no-barrel-re-exports.md`)).

The costs are also on record. Three TypeScript program loads per prod build, which is why `emitDts: false` is advertised as cutting "a ~13s/build cost"; `.d.ts.map` stripped and `src/` never shipped, so go-to-definition lands in a rolled-up declaration rather than source (the opposite of Effect's `files` list, which ships `src/**/*.ts`, `.js.map`, and `.d.ts.map`); Effect-specific friction that needed `stableTypeOrdering` "so a multi-union `.d.ts` (e.g. an Effect `Layer.Layer<…>` requirement channel) does not flip member order", `ae-forgotten-export` suppressions for the anonymous `_base` class every `Schema.Class`/`TaggedError`/`Context.Service` synthesises, and a private-member duplication bug when `./ui` rolled copies of root types ("Types have separate declarations of a private property 'defs'") fixed by `dtsExternals` (`resolved-tsconfig.js` (local checkout `~/YeeBois/references/effect/effected/node_modules/.pnpm/@savvy-web+tsdown-plugins@2.8.22_*/node_modules/@savvy-web/tsdown-plugins/dts/resolved-tsconfig.js`), `pluginfinity savvy.build.ts` (local checkout `~/YeeBois/references/effect/pluginfinity/packages/core/savvy.build.ts`), `okf/decisions/ui-declarations-reference-the-root-by-name.md` (local checkout `~/YeeBois/references/effect/effected/okf/decisions/ui-declarations-reference-the-root-by-name.md`)). His own guardrails say never to run `--target prod` directly because it "emits no `.d.ts`, and leaves a truncated `issues.json` shaped exactly like a clean gate" (`okf/modules/workspace.md` (local checkout `~/YeeBois/references/effect/effected/okf/modules/workspace.md`)).

The contrast with Effect's own build is instructive. Effect 4.0.2 is ESM-only, built with `tsc -b tsconfig.json && pnpm babel`, 458 `dist/*.js` files, `exports` pointing `./*` at `./src/*.ts` with `publishConfig.exports` rewriting to `./dist/*.js`, `files` shipping source and both map kinds, and `sideEffects` tightened from `[]` to a two-file allowlist naming only `SchemaJITCompiler/enable` ([effect package.json](https://raw.githubusercontent.com/Effect-TS/effect/main/packages/effect/package.json)). Arnaldi called "folks bundling effect in their own libs" a bad idea in 2023 and the team chose `globalValue`, string-keyed Tags, and `Symbol.for` TypeIds to tolerate duplicates rather than prevent them ([Effect-TS/effect#1561](https://github.com/Effect-TS/effect/issues/1561)). Spencer agrees on the one point that matters for correctness (effect is external and a peer), and both camps publish per-module JS; they differ only on whether declarations are rolled up and whether maps and source ship. beep-effect's packages, with up to 130 subpath entries each and many module-level `S.Class`/`Context.Tag` values, sit on Effect-core's side of that line, where per-module declarations and shipped `declarationMap` are the lower-risk choice **[inferred]**.

Worth borrowing: the generated-manifest idea (publishable `package.json` derived from a `private: true` source manifest, with `exports` conditions derived from export keys rather than hand-maintained `publishConfig.exports` blocks of 130 entries); the `effect` / `effect:peers` two-catalog pattern for a wide published floor; auto-externalising everything declared; `issues.json` as a machine-readable build artifact that agents read instead of parsing terminals; and the reflex of asserting on emitted artifacts rather than exit codes. Not worth borrowing: rolled-up `.d.ts` (Effect-specific breakage, loses `declarationMap`), API Extractor (the repo's `@effect/language-service` `apiStabilityLeak`, docgen, and `check-dist-types`-style gates cover the same ground without a `typescript ~5.9` pin), stripping maps and source, and `tsc` over `tsgo` (he has no Effect-diagnostics gate to lose).

## SchemaCompiler must not drive the bundler choice

The three compilers are small and the API is explicit about what it is. `SchemaCompiler` is one `WeakMap<AST, Entry>` registry keyed by AST identity that `SchemaParser` consults transparently; `SchemaJITCompiler.enable` fills it via `globalThis.Function` with silent fallback to the interpreter; `SchemaAOTCompiler.compile(targets)` returns a JavaScript string, and `SchemaAOTCompiler/Build.build` discovers `Schema.isSchema` exports from loaded modules and writes one self-installing ES module (`SchemaCompiler.d.ts` (`node_modules/effect/dist/schema/SchemaCompiler.d.ts`, installed package), `Build.d.ts` (`node_modules/effect/dist/schema/SchemaAOTCompiler/Build.d.ts`, installed package)). Every symbol is `@stability unstable`, the compilers landed in PR #7908 on 2026-09-18, three weeks before 4.0 stable, and were still being patched on 2026-10-06 ([PR #7908](https://github.com/Effect-TS/effect/pull/7908)).

The generated module's shape settles where it lives. It begins `import { runtime } from "effect/schema/SchemaCompiler/runtime"`, defines deduplicated factory functions, and exports `install(asts)` which walks the live AST graph by path (`a0.propertySignatures[1].type`) and calls `runtime.setCompiler`; the `Build` variant adds `import * as m0 from "<relative path to schema module>"` per module and a trailing top-level `install([...])`, so importing the file installs as a side effect. It carries no `.d.ts`, "Generated modules must use the same Effect version as their generator", installs are keyed by AST identity so a duplicated schema module in a bundle graph silently misses, and the bare `effect/schema/SchemaCompiler/runtime` specifier "does not resolve outside a package tree" so the repo spike rewrote it to a file URL (`SchemaAOTCompiler.ts` (local checkout `~/YeeBois/references/effect/effect/packages/effect/src/schema/SchemaAOTCompiler.ts`), [compiler-evaluation.md](../../../../explorations/effect-schema-parity/research/2026-09-28-compiler-evaluation.md)). The natural unit is therefore **one generated module per application entry** (server, oip-web, Tauri), produced from that app's dependency graph, listed in `sideEffects`, and imported first in the entry file before any module-initialisation decode; it is not a per-library artifact, and shipping one inside `@beep/schema`'s `dist` would pin that package to an exact Effect version **[inferred from the API contract]**. No Vite, rolldown, tsdown, or Bun plugin exists; the Effect repo uses the compilers only in its `runtimeperf` suites; the single external adopter found is effective-rsc enabling JIT per graph ([effective-rsc PR #53](https://github.com/nikhilsnayak/effective-rsc/pull/53)).

The performance evidence argues for patience. Upstream's paired benchmarks show JIT and AOT within noise of each other and 20–60x faster than the interpreter on validation-only shapes (Moltar parseSafe 325.8 ns to 5.42 ns), at a bundle cost of +6.77 KB min+gz for JIT and +2.12 KB for AOT ([PR #7908](https://github.com/Effect-TS/effect/pull/7908)). The repo's own spike on `@beep` shapes found **3.7x on transformation-free wire structs, 1.2–1.5x on class and transformation-heavy rows, and no gain on the recursive Pandoc graph** (AOT 0.69–0.78x on the model path), because every `S.Class` is a `Declaration` the code generator never emits and any child with `encoding` demotes its parent to loop-only; "The class wrapper costs about 30–35% of throughput, and the compiler does not remove it" ([compiler-evaluation.md](../../../../explorations/effect-schema-parity/research/2026-09-28-compiler-evaluation.md), `codegen.ts` (local checkout `~/YeeBois/references/effect/effect/packages/effect/src/internal/schema/codegen.ts`)). The operator's 2026-09-28 ruling is DEFER with three re-entry triggers: a measured bulk server hot path decoding transformation-free wire shapes at 10k+ rows, upstream lifting the `Declaration` exclusion or following `Suspend` in AOT, or the API leaving `unstable`; the cheapest re-entry experiment is the global `effect/schema/SchemaJITCompiler/enable` import on one server entry behind a flag ([DECISIONS.md](../../../../explorations/effect-schema-parity/DECISIONS.md)). Production CSP is the one place AOT beats JIT: oip-web's production `script-src 'self' 'nonce-…'` and the Tauri shells block eval, so "JIT works in dev and silently falls back in prod" while a same-origin static AOT module satisfies `'self'`.

The bundler-relevant requirements collapse to two: honour `sideEffects` so the generated import survives, and run a pre-build script. Every option in the matrix satisfies both, including `tsc`, because the AOT step is a Bun script importing `@beep/*` barrels through workspace symlinks and running `Build.build` under `BunFileSystem`/`BunPath` layers, not a bundler plugin **[inferred]**. Letting SchemaCompiler steer the bundler choice would be optimising for a feature the repo has ruled out of production and whose only shipped integration is a file-writing Effect.

## Proposed pipeline shape

The shape below is a proposal derived from the constraint set; the repository paths and command names are sourced, the composition is **[inferred]**.

**Package scripts.** The generator in `PackageScriptsPolicy.ts` already owns every scripts block and `beep:preflight` runs its `--write` form ([PackageScriptsPolicy.ts](../../../../packages/tooling/tool/cli/src/internal/package-scripts/PackageScriptsPolicy.ts)). The `beep:build` value becomes a single call for every library package, with the tier decided from the manifest, not from the script text:

```jsonc
// generated by `beep lint package-scripts --write`
"build":      "bun run beep:build",
"beep:build": "beep-cli build package",   // replaces `tsc -p tsconfig.json && bun run babel`
// the `babel` script key disappears from every manifest
```

**One shared build-kit package owns the pipeline.** A `packages/tooling/library/build-kit` (created via `bun run beep create-package`) exposes a `BuildPackage` service whose schema is the manifest-derived `BuildPlan`: `tier: "private" | "publishable"`, `emitter: "tsgo"`, `entries` from `exports`, `externals` (every `dependencies`/`peerDependencies` key plus `@beep/*`, `effect`, `effect/*`), `annotate: boolean`, `assertArtifacts`. Its implementation, in design order schema → service → implementation, does the following for the private tier (150 packages): run `tsc -p tsconfig.json` (the effect-tsgo binary, so the Effect-diagnostics gate stays on the emit), then **assert** that every `exports` subpath has a `dist/**/*.d.ts` on disk and fail loudly if not; when `node_modules/.tmp/*.tsbuildinfo` exists but `dist/` does not, delete the tsbuildinfo before invoking (this is the Vercel stale-tsbuildinfo incident fixed at the source instead of in each `vercel.json`); skip Babel entirely, since no consumer bundles `dist/*.js` and `sideEffects: []` already marks the modules droppable. For the publishable tier (manifests with `publishConfig.access: "public"`, today the ecosystem family such as `@beep/effect-drizzle`): run the same tsgo emit for declarations and Effect diagnostics, then a tsdown `unbundle: true` JS pass with `deps.neverBundle` from the externals list and `dts: false` (declarations already exist), then `babel dist --plugins annotate-pure-calls` because no Rust tool inserts annotations, then `attw`/`publint` in `ci-only` mode, and generate `publishConfig.exports` from the export keys with the Spencer-style key-derived conditions rather than hand-maintaining 130 entries. The Effect `sideEffects` allowlist convention (name the one side-effectful module, do not flip the package) carries over verbatim.

**Turbo caching.** Keep `build` as a per-package task so `dist/**` and tsbuildinfo hash per package; add the build-kit package as a `dependsOn` (`^build` already covers it if every library depends on it, otherwise `@beep/build-kit#build`) so a change to the shared pipeline invalidates every package's cache, mirroring how `tools/tsgo-shim/tsgo.js` is already a global input ([turbo.json](../../../../turbo.json)). Never let the build write `package.json`: tsdown's `exports: true` mutates a task input, so the manifest projection runs in the `lint:package-scripts`-style `--check`/`--write` lane and is committed, exactly like `tsconfig-sync` and `vitest.aliases.generated.json` today. The `check` task keeps `outputs: []`, which already closes the 2026 tsbuildinfo cache race.

**Externals and runtimes.** `effect` is always external and, for publishables, a peer with a wide floor; `@beep/*` siblings are external in library builds and resolved through workspace symlinks; native addons (`@duckdb/*`) stay `--external` in the `bun build --compile` binaries, where the repo already copies them beside the executable ([package.ts](../../../../apps/practice-kg-mcp/src/package.ts)). The CLI release lane is the only place `bun build` appears: `bun build --compile --bytecode --target bun-linux-x64 packages/tooling/tool/cli/src/bin.ts`, rebuilt per Bun version, with the artifact assertion habit applied there too because unknown flags are silently accepted.

**Where an AOT module would be generated, if ever.** `apps/<app>/src/_generated/schema-aot.js`, one per application entry, produced by a `beep generate schema-aot` step that imports that app's `@beep/*` schema barrels, runs `SchemaAOTCompiler/Build.build` under Bun platform layers, rewrites the runtime specifier if needed, and ships with a `--check` drift lane comparing bytes (the build is deterministic). The app's `package.json` lists the file in `sideEffects`; the entry imports it on line one; the Turbo `codegen` task owns it, not `build`. Nothing in `packages/**` emits or ships compiled schema code.

## Conclusion

The question was framed as "which bundler", but the repository's own numbers say the library build is not where bundles come from and not where time goes. Every bundler that could replace `tsc` for these packages still runs a TypeScript program for declarations, and the one that does not (`bun build`) cannot emit them at all; meanwhile the compiler already in place is the Go-native TypeScript 7 patched with the Effect diagnostics that are the repo's correctness gate. The honest upgrade is organisational rather than technological: one generated script, one build-kit service that owns tiering, artifact assertions, and tsbuildinfo hygiene, and a clean split between the 150 private packages (emit declarations, skip Babel) and the few that will be published (tsdown unbundle, annotations, attw). That split also resolves the apparent tension with Spencer Beggs's setup: his bundler is a publishing manifest machine built on the same rolldown-plugin-dts/tsc program, and the parts worth taking are the manifest projection, the two-catalog peer discipline, and `issues.json`, not the rolled-up declarations that cost him `stableTypeOrdering`, `_base` suppressions, and his declaration maps.

Two experiments would turn the inferred parts of this report into measured ones before any migration PR: re-run the effect-drizzle `Bun.build` tree-shaking probe on Bun 1.4.2 to date-stamp or retire the 1.3.14 finding, and time one `@beep/schema` build three ways on a quiet machine (`tsc -p` as today, `tsc -p` without Babel, tsdown `unbundle` + `rolldown-plugin-dts` with `generator: "tsgo"`) so the "no wall-clock win from a bundler" claim stands on the repo's own hardware rather than on vendor benchmarks. If those come back as the evidence predicts, the bundler decision is closed and the remaining work is the build-kit package.
