# Nobody ships the expiring repo-fact ledger yet

No tool found in 2025–2026 covers the whole loop: an agent records a temporary repo fact (for example "dependency X held at 1.4 because 1.5 breaks `bun install`") in a schema-checked store, gives it a re-check timer that later agents can extend only by re-proving it, wakes an agent at an exact time when it comes due, and routes that work across LLM providers until it lands as a mergeable PR. Pieces of the loop are mature, but each lives in a different ecosystem. Vulnerability scanners (Snyk, OSV-Scanner, Trivy, audit-ci) already store `{id, reason, expiresAt}` ignore records that come back to life after their date. eslint-plugin-unicorn and Rust `todo-or-die` expire comments when a dependency version or upstream issue changes. HashiCorp Vault and cert-manager define renewal semantics with caps and fresh evidence. GitHub Agentic Workflows (gh-aw) is the most complete design for turning an unattended agent run into a draft PR without giving the agent write access. Systemd timers, Temporal, Inngest, Trigger.dev and Restate give exact-time wakeups. The empty spot is specific: **dependency-update tools (Renovate, Dependabot, syncpack, pnpm/Bun overrides) have no first-class "why is this held, and when do we look again" record**, no agent-memory system pairs an asserted fact with a scheduled probe, and **no orchestrator documents cross-provider quota fallback**. gh-aw explicitly refuses cross-provider chains at compile time. A workstation-native ledger that borrows from all five areas would fill a real gap rather than duplicate a product.

## The pinned-dependency fact is the one thing no updater models

The motivating example, a held-back dependency, falls exactly where the mainstream tools stop. Renovate offers relative delays and age flags but nothing with a date or condition attached to a hold. `minimumReleaseAge` holds a PR back for some time after a release, and `abandonmentThreshold` marks packages that have gone a period without updates without disabling anything. No `expires` or `until` field turned up in the portion of the options page that was read ([Renovate config options](https://docs.renovatebot.com/configuration-options/)). The only temporary-disable advice found is `"enabled": false`, which has no time limit ([Cambridge UIS DevOps guidebook](https://guidebook.devops.uis.cam.ac.uk/howtos/disable-renovatebot)). Dependabot's `ignore` takes a dependency name, version ranges and update types, and its `cooldown` delays updates by **a default of 3 days even when unset**. Neither one carries an expiry ([Dependabot options reference](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference)). syncpack version groups have a free-text `label` for explaining why a rule exists and nothing more ([syncpack docs index](https://docsearch.algolia.com/mcp/docs/repo/jamiemason/syncpack), secondary mirror). pnpm `overrides` can only be set at the project root and have no reason or expiry field ([pnpm settings](https://pnpm.io/settings)). Bun `overrides` and `patchedDependencies` were not checked. The assumption that they carry no metadata either is unverified.

Vulnerability tooling is the clearest proof that a dated, reasoned ignore record works in a repo. Snyk's `.snyk` file nests `reason` and `expires` under each vulnerability ID and path. It also shows the main hazard: **a malformed `expires` makes the ignore permanent**, so it fails open ([Snyk .snyk docs](https://docs.snyk.io/manage-risk/policies/the-.snyk-file)). OSV-Scanner has `[[IgnoredVulns]]` with `ignoreUntil` and `reason`, plus `[[PackageOverrides]]` whose expiry field is `effectiveUntil` ([OSV-Scanner configuration](https://google.github.io/osv-scanner/configuration/)). Trivy accepts `exp:2023-01-01` inline or `expired_at` in an experimental YAML ignore file ([Trivy filtering](https://trivy.dev/latest/docs/configuration/filtering/)). IBM audit-ci's object form adds `active`, `notes` and `expiry` ([IBM/audit-ci](https://github.com/IBM/audit-ci)). That is six spellings of the same idea across four tools, and they share a record shape: subject, scope, reason, optional expiry. That shape is a good baseline for a general ledger. Every one of these tools is date-only, though. None re-checks a condition such as "a fixed version now exists", and that is the weakness a probe-backed ledger would fix.

## Condition-based expiry beats guessing a date

The best prior art for "this fact retires itself" doesn't use dates at all. TypeScript's `// @ts-expect-error` suppresses an error and then becomes one itself ("Unused '@ts-expect-error' directive.") once the underlying problem goes away, while `// @ts-ignore` stays silent forever ([TypeScript 3.9 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html)). eslint-plugin-unicorn's `expiring-todo-comments` applies the same idea to comments. `// TODO [vue@>=3]`, `[+read-pkg]` (fires when a dependency is added), `[-vue-function-api]` (fires when one is removed), `[peer:eslint@>=9]` and `[engine:node@>=8]` all fail lint when a fact in the manifest changes. **Date checks are off by default** (`checkDates: false`), and `checkDatesOnPullRequests: false` keeps an expired date from turning an unrelated PR red ([unicorn rule docs](https://github.com/sindresorhus/eslint-plugin-unicorn/blob/main/docs/rules/expiring-todo-comments.md)). The sources disagree on whether the rule is in the recommended preset. The rule page lists it in `recommended`, while the v66 readme notes say it is not and that it needs ESLint ≥ 9.18 flat config ([v66 readme](https://cdn.jsdelivr.net/npm/eslint-plugin-unicorn@66.0.0/readme.md)). One limitation matters directly for a Bun catalog monorepo: **`catalog:` references are not resolved and are reported as unsupported**, so a condition like `[effect@>=4.1]` won't fire against catalog-pinned versions unless the ledger resolves catalogs itself ([unicorn rule docs](https://github.com/sindresorhus/eslint-plugin-unicorn/blob/main/docs/rules/expiring-todo-comments.md)).

Rust's `todo-or-die` 0.1.2 adds remote conditions. `issue_closed!` and `pr_closed!` cause a compile error when an upstream GitHub issue closes, and `crates_io!` fires when the latest published version matches an expression. When the network fails, the macros only warn, and `TODO_OR_DIE_SKIP` turns them off locally so they bite only in CI ([docs.rs todo-or-die](https://docs.rs/todo-or-die/latest/todo_or_die/)). The original Ruby `todo_or_die` takes `by:` (a date) and `if:` (a boolean or callable). When both are given, both must hold, and in Rails it only warns in production ([searls/todo_or_die](https://github.com/searls/todo_or_die)). Go has `gostale` (`stale:` and `expires:` dates on TODOs, [pkg.go.dev](https://pkg.go.dev/github.com/cbrgm/gostale)), and PHPStan has `phpstan-todo-by` ([packagist](https://packagist.org/packages/staabm/phpstan-todo-by)). Feature-flag platforms take a third approach based on lifetimes. Unleash marks a release flag potentially stale after **40 days** and an operational flag after **7** ([Unleash flag types](https://docs.getunleash.io/reference/feature-toggles)), and it emits a `feature-stale-on` event that integrations can use to fail builds or open PRs ([Unleash technical debt](https://docs.getunleash.io/reference/technical-debt)). LaunchDarkly moves a flag through "ready for code removal", "ready to archive" and "extinct", using code-reference scans as evidence ([LaunchDarkly flag status](https://launchdarkly.com/docs/home/flags/flag-status)). Uber's Piranha closes the loop with a codemod that deletes the dead branch of a stale flag ([uber/piranha](https://github.com/uber/piranha)). Piranha only works because removing a flag is mechanical. A pinned dependency or a workaround needs an agent to fix it, not a rewrite rule.

These tools separate along two axes that a ledger design needs to keep apart: where the condition's truth comes from, and how the tool fails.

| Expiry class | Examples | Source of truth | Failure mode |
| --- | --- | --- | --- |
| Self-expiring, local | `@ts-expect-error`, unicorn `[pkg@>=x]`/`[+pkg]`/`[-pkg]` | compiler, manifest | deterministic, offline, CI-safe |
| Self-expiring, remote | Rust `issue_closed!`, `crates_io!`; Ruby `if:` | forge/registry API, runtime | degrades to warning, so a silent miss |
| Date-based | unicorn dates, Snyk, OSV, Trivy, audit-ci, gostale | wall clock | breaks unrelated PRs without a PR/local skip valve; Snyk fails open on bad dates |
| Lifetime-based | Unleash, LaunchDarkly | platform age + code refs | needs a hosted platform |

The strongest combination pairs a date as a "re-check by" backstop with a probe as the actual truth test, which is Ruby's `by:` plus `if:`. Strict date decoding should fail closed, the opposite of what Snyk does.

## Lease semantics: renew from now, cap it, and require fresh evidence

Issue-tracker staleness is the pattern to avoid. `actions/stale` defaults to **60 days to stale and 7 to close**, and `remove-stale-when-updated: true` means **any comment resets the clock** ([actions/stale](https://github.com/actions/stale)). It measures activity, not whether the fact is still true, so a drive-by "still needed" renews an entry that may be false. Developer portals are better structured but still have no deadlines on the facts themselves. Backstage/Roadie Tech Insights ingests facts and runs boolean checks over them ([Roadie](https://roadie.io/docs/getting-started/creating-a-scorecard/)), and Cortex keeps deadlines on a separate Initiative object that "take[s] one or more rules from your scorecards along with a deadline" ([Cortex](https://docs.cortex.io/standardize/scorecards)). The design lesson from Cortex is to store *what to check* and *by when* as separate fields.

The renewal model to copy comes from secrets and certificates. In Vault, a renewal is "an increment _from the current time_", not added to the end of the remaining TTL. The requested increment is advisory and the backend may cap it ([Vault leases](https://developer.hashicorp.com/vault/docs/concepts/lease)). An explicit max TTL "becomes a hard limit on the token's lifetime" that even periodic tokens can't exceed, and the system default max is **32 days** ([Vault tokens](https://developer.hashicorp.com/vault/docs/concepts/tokens)). Prefix revocation (`vault lease revoke -prefix aws/`) maps neatly onto expiring every entry under a package path when that package is deleted. cert-manager renews **2/3 of the way through** a certificate's lifetime by default and recommends `renewBeforePercentage` over an absolute value "to prevent renewal loops" ([cert-manager Certificate](https://cert-manager.io/docs/usage/certificate/)). ACME ARI (RFC 9773, June 2025) has the server publish a renewal window, and each client renews at a uniformly random time inside it so load spreads out ([RFC 9773](https://rfc-editor.org/rfc/rfc9773.html)). Kubernetes Leases are the counterexample: a live holder updates `renewTime`, and nothing else is proven ([Kubernetes Leases](https://www.kubernetes.io/docs/concepts/architecture/leases/)).

Taken together, Vault and Kubernetes renewals are blind, while certificate renewal is evidence-bearing, because every reissue repeats domain validation. A facts ledger should follow the certificate model. Extending an entry re-runs its probe and records the result and the commit SHA. Renewal counts from now and is capped per policy. A max lifetime measured from creation forces someone to re-justify the entry. A due-soon state opens at about 2/3 of the lease. Due dates get jitter so entries created together don't all come due on the same night. No surveyed system caps the *number* of renewals, so Vault's cap on total lifetime is the one to borrow.

Agent memory systems offer the bookkeeping model but not the probe. Mem0 has a per-memory `expiration_date` that hides a memory from search without deleting it, and **an unparseable date is treated as not expired** ([Mem0 memory expiration](https://docs.mem0.ai/platform/features/memory-expiration)). Its cookbook says expired memories are "automatically removed", which conflicts with that; the feature page is the more precise source. Zep/Graphiti uses two timelines: `t_valid`/`t_invalid` for when a fact held in the world, and `t′_created`/`t′_expired` for when the system recorded or invalidated it. Contradicted facts are invalidated, not deleted ([Zep paper](https://arxiv.org/html/2501.13956v1); [graphiti](https://github.com/getzep/graphiti)). Claude Code auto memory has **no TTL**. Its files "stay until you or Claude edits or deletes them", and pruning is left to the model ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Letta's "Dreaming" consolidates memory with no expiry or re-validation ([Letta docs](https://docs.letta.com/guides/agents/architectures/sleeptime)). None of them has an agent assert a fact with an expiry and then has a scheduler re-check it with a probe. In a git-tracked ledger, history supplies Graphiti's system timeline for free. The real-world validity interval still has to be written explicitly.

## gh-aw has the PR pipeline but forbids the fallback chain

For turning an unattended run into a reviewable PR, GitHub Agentic Workflows is the reference design. A Markdown workflow with YAML frontmatter compiles to a `.lock.yml` with this job chain: pre-activation, activation, a sandboxed **read-only agent job**, a separate **detection job with no write permission** in which "a threat blocks all external writes", and then permission-scoped safe-output jobs such as `create_pull_request` ([gh-aw architecture](https://github.github.com/gh-aw/introduction/architecture/)). The PR controls are policy, not suggestions. `draft` defaults to true and "the agent cannot override it". `max` is 1 per run. Patches are limited to **100 files and 4096 KB** by default. Protected files trigger a `request-review` that submits REQUEST_CHANGES. `fallback-as-issue` keeps a failed PR from vanishing silently ([gh-aw PR safe outputs](https://github.github.com/gh-aw/reference/safe-outputs-pull-requests/)). Engines are pluggable (copilot, claude, codex, pi, with gemini deprecated and agy experimental), and a custom `command` can replace the executable. The fallback, however, is same-provider only. `fallback-models` does not switch on HTTP 429, auth failures or job timeouts, and **"Cross-provider chains fail compilation"** ([gh-aw engines](https://github.github.com/gh-aw/reference/engines/)). That is the opposite of a Claude, then Codex, then Cursor, then Grok chain triggered on quota failures. On scheduling, gh-aw has fuzzy cron spread deterministically by file path, `skip-if-match` gates driven by search queries, and `stop-after`, which expires the *workflow* rather than a fact. It documents no one-shot datetime trigger ([gh-aw triggers](https://github.github.com/gh-aw/reference/triggers/)).

Every vendor-native scheduler is tied to its own vendor. Claude Code cloud scheduled tasks, formerly called routines, are the only first-party product with a native **"once at a specific future time"** trigger (`/schedule in 2 weeks, open a cleanup PR…`). They reject cron that runs more often than hourly, can start several minutes late on the hour, push only to `claude/` branches, require a claude.ai subscription login, and run only Claude models ([Claude Code scheduled tasks](https://code.claude.com/docs/en/routines)). `claude-code-action@v1` runs in automation mode on `on: schedule`, but GitHub runs cron only from the default branch, disables schedules after **60 days of inactivity in public repos**, and commits made with the default `GITHUB_TOKEN` don't trigger CI ([Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)). `openai/codex-action@v1` contributes privilege-reduction modes (`drop-sudo` by default, `unprivileged-user`, `read-only`) but has no PR-creation or schedule example ([openai/codex-action](https://github.com/openai/codex-action)). Cursor Automations launched on 2026-03-05 with schedule and event triggers ([Cursor changelog](https://cursor.com/changelog/03-05-26)). Jules reportedly has scheduled maintenance tasks, though only secondary sources confirm it ([Tessl](https://tessl.io/blog/google-wants-to-make-jules-a-more-proactive-coding-colleague)). OpenHands is model-agnostic through LiteLLM, but its Automations are cloud-only beta, and its resolver action is triggered by labels, not cron ([OpenHands Automations](https://docs.openhands.dev/openhands/usage/automations/overview)).

Agent-agnosticism has settled on ACP, whose directory lists adapters for Claude, Codex, Gemini CLI, Cursor, Copilot, Junie, Factory Droid, OpenHands, Goose and more ([ACP agents](https://agentclientprotocol.com/overview/agents)). The older terminal-scraping wrapper, coder/agentapi, is **deprecated and archived** ([coder/agentapi](https://github.com/coder/agentapi)). No orchestrator surveyed documents automatic cross-provider quota fallback. The logic that sorts failures into quota or availability problems (relaunch on the next provider) versus code failures (fix it, don't switch models) has to live in the scheduler that owns the launch. Devin, aider-in-CI, Sweep, Factory, claude-squad and Terragon were not researched, so this absence is based on a bounded search.

## Exact-time wakeups need a durable source plus a reconciler

The schedulers split into periodic pollers and per-item exact timers. GitHub Actions cron (minimum interval **5 minutes**), gh-aw fuzzy schedules, Claude cloud tasks, and Cursor/Jules automations all fire on a tick and have to query for due work. systemd `OnCalendar`, Temporal timers, Inngest `step.sleepUntil` or an event `ts`, Trigger.dev `wait.until`, and Restate delayed sends wake once per item at an absolute time. Temporal timers are stored server-side and can last "days to years" ([Temporal timers](https://docs.temporal.io/develop/go/timers)). Inngest sleeps can last up to a year, or 7 days on the free plan ([Inngest sleeps](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/sleeps)). Trigger.dev checkpoints waits longer than about 5 seconds so they use no compute ([Trigger.dev wait](https://trigger.dev/docs/wait)). Restate guarantees delivery "no earlier than specified" and recommends delayed messages over long sleeps ([Restate durable timers](https://docs.restate.dev/develop/ts/durable-timers)). Each of those needs a server running.

On a single workstation, systemd is the lightest option, with one caveat. `systemd-run --user --on-calendar=` creates a transient timer ([systemd-run(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html)), but the man page doesn't promise transient units survive a reboot. The inference is that they don't. `Persistent=true` on a regular timer catches up on missed runs, `AccuracySec` defaults to 1 minute, and `RandomizedDelaySec` adds the jitter that ARI recommends ([systemd.timer(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)). A reboot-safe design keeps the in-repo ledger as the source of truth and runs a persistent daily reconciler timer that re-creates per-item transient timers for entries coming due, or acts directly on entries already due. That combines exact-time precision with durability, and wiping every timer costs nothing because the ledger can always rebuild them.

## Conclusion

The pieces of the loop exist, but they have never been assembled into one product. The tools that store facts with expiries (vuln ignores, Mem0) re-check nothing. The tools that check conditions (unicorn, `todo-or-die`, `@ts-expect-error`) have no lease, no scheduler and no agent. The tools that run agents on schedules (gh-aw, Claude tasks, Cursor) know nothing about the facts they should be checking, and they either lock to one vendor or forbid cross-provider fallback by design. A ledger built for this repo therefore has no product to defer to. Its value comes from the joins: a single strictly decoded record (subject, reason, condition probe, backstop date, Graphiti-style validity interval), Vault-style capped renewals from now that only a passing probe can grant, gh-aw-style separation in which the agent produces a patch and a separate privileged step opens a draft PR, and a reconciler that turns due entries into exact-time systemd wakeups.

One design question is easy to underrate: evidence for a renewal matters more than when it is scheduled. `actions/stale` shows that when a touch can renew an entry, entries pile up. Snyk and Mem0 show that a lenient date parser turns expiries into permanent exemptions. If renewals must carry a fresh probe result and a commit SHA, and malformed entries fail CI, then most entries close themselves when the probe flips and agents are woken only for the residue that needs judgment. For the dependency-hold case specifically, the probe has to resolve Bun catalogs itself, because the best existing condition syntax does not.
